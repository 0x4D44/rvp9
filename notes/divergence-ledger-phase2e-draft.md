### 7.1 AQ modes 1 and 2 not ported (already in ledger)

**Where:** `rvp9_encoder::aq::cyclic_refresh` is the entire `aq`

**libvpx counterpart:** `vp9_aq_variance.c` (255 ll),
`vp9_aq_complexity.c` (228 ll) — both guarded by
`!CONFIG_REALTIME_ONLY` per A5 Q-RC-15 and the encoder dispatch

(our target, PLAN.md D1) neither is reachable. **Byte-parity impact:**
none in matched configs. **CE impact:** none. **Future plan:** out of
scope; revisit only if a non-realtime preset is ever added.

### 7.2 `time_for_refresh` field dropped (already in ledger)

**Where:** `CyclicRefresh` struct has no `time_for_refresh` field.
**Status:** already documented at
`notes/divergence-ledger.md:195-206`. **Origin:** L-03 RESOLVED
(`notes/vp9-analysis/decisions-needed.md:153-154`),
A5 Q-RC-24 (`notes/vp9-analysis/05-rate-control.md:1916-1922`).
**libvpx counterpart:** `cr->time_for_refresh`
(`vp9_aq_cyclicrefresh.h:43`) — declared and written to 0 in
`update_parameters:509`, read only in `update_segment:203` (where the
write is `new_map_value = -cr->time_for_refresh` = `-0` = `0`).
**What rvp9 does:** the field is omitted from the struct; the
`new_map_value = 0` write in `update_segment` is hard-coded (§5.4).
**Byte-parity impact:** none — `-0i8 == 0i8`; libvpx writes `0` and so
do we. **Future plan:** none; if an external API ever needed
`time_for_refresh` for tuning, a separate `cycle_extra_wait_frames:
u8` field could be added without revisiting this divergence.

### 7.3 `weight_segment` integer-shift order preserved (L-21 RESOLVED) — NEW ledger entry

**Where:** §5.2, the `weight_segment` computation block. **Origin:**
L-21 (`notes/vp9-analysis/decisions-needed.md:211-212`), A5 Q-RC-22
(`notes/vp9-analysis/05-rate-control.md:1885-1898`). **libvpx
counterpart:** `vp9_aq_cyclicrefresh.c:572-575`,
`weight_segment = (double)((target + s1 + s2) >> 1) / num8x8bl` —
i.e., integer `>> 1` on the i32 sum BEFORE the cast to double. **What
rvp9 does:** preserve the integer shift exactly (i32 sum → i32 shift
→ `as f64 / num8x8bl as f64`). Do NOT rewrite as
`(target + s1 + s2) as f64 * 0.5 / num8x8bl as f64`. **Why:** the i32
`>> 1` discards the low bit before division; re-ordering changes
`weight_segment` by up to `0.5 / num8x8bl` and compounds across frames
into 0.1-0.3% BD-rate drift (A5 Q-RC-22). **Byte-parity:** none.
**CE impact:** none. **Future plan:** revisit only if `weight_segment`
is replaced with a deterministic alternative.

`CyclicRefresh::limit_q` is callable in any context, but the only
call site enforces the gate. The function's own internal check

**Byte-parity impact:** none. **CE impact:** none. **Future plan:**
none. **Ledger status:** **NEW** entry — needed because the gate is a
load-bearing assumption (without it, non-screen-content CR would
*also* clamp frame-level Q decreases, changing the BD-rate). The
ledger entry documents the gate to prevent silent regression.

## From `notes/lld/bitstream.md` (§7 at line 1259)

### §7 — Deliberate divergences (from `bitstream.md`)

Each entry feeds `notes/divergence-ledger.md` per the divergence-ledger
template. Format: **what we change, why, impact on byte parity**.

### §7.1 Drop parallel tile-packing (L-35 RESOLVED)

**What:** the libvpx `encode_tiles_mt` path
(`vp9_bitstream.c:991-1090`) parallelises the *boolean coder pass*
across workers within `vp9_pack_bitstream`. We do not.

**Why:** in our design, each tile worker has already produced its
own per-tile byte buffer during mode-decision (the tile worker
drives `BoolWriter` directly). At pack time the main thread only
does concatenation + size-prefix arithmetic, which is memcpy-bound
and trivial to parallelise but yields no measurable speedup (a few
hundred KB per frame at 1080p60 is ~1 ms of memcpy). L-35.

**Impact on byte parity:** none. The byte order in the output is
identical to libvpx's. The only observable difference is wall-clock
during the pack call (a few hundred μs lower in libvpx's MT path,
not enough to measure against the frame budget).

**Ledger fields:** *Reason*: simplification. *Effect on byte
parity*: zero. *Effect on perf*: negligible (within noise of the
real-time budget).

### §7.2 Replace `setjmp/longjmp` error model with `Result`

**What:** libvpx errors via `vpx_internal_error()` →
`longjmp(error_info.jmp)`. Encountered at
`vp9_bitstream.c:1027-1029`, `:1085-1087`, `:1121-1124`,
`:1131-1134`, `:1412-1413`, `:1427-1430`, `:1441-1444`. We propagate
`Result<T, BitstreamError>` instead.

**Why:** HLD-arch §4 + D-09 RESOLVED. `setjmp/longjmp` is not
expressible in safe Rust without `nightly` features and `unsafe`
blocks at every call site; `Result` is the idiomatic alternative.

**Impact on byte parity:** none on success. On error, libvpx aborts
the frame and the partial bytes are abandoned. Our `Result` does the
same — caller discards `dest` content on `Err`. Functionally
equivalent.

### §7.3 Drop altref-driven multi-frame superframes (D-13)

**What:** libvpx's `write_superframe_index` is driven by
`pending_frame_count` which can be `> 1` when an altref frame is
queued ahead of a "show_existing" reveal. With altref **excluded**
in v1 (D-13 RESOLVED), the only sources of multi-frame superframes
in v1 are:

- SVC spatial layers (one frame per spatial layer per packet); and
- `show_existing_frame` paired with a hidden non-shown ref-creating
  frame (intra-only inter frame with `show_frame = 0`).

**Why:** D-13 RESOLVED — no altref in v1.

**Impact on byte parity:** none for streams that wouldn't use
altref anyway (real-time / WebRTC). The `SuperframeBuilder` API is
identical; the encoder simply never queues an altref frame for it.

### §7.4 Per-tile output is owned `Vec<u8>`, not `&mut [u8]` slice into a shared arena

**What:** libvpx allocates a single arena
`vp9_bitstream_worker_data[]` (`vp9_bitstream.c:967-989`) and hands
each worker a non-overlapping slice. We use `Vec<u8>` per `TileBuffer`.

**Why:** L-13. The arena pattern requires raw-pointer slice
arithmetic that survives across the multi-threaded boundary, with
no escape hatch when one worker's tile exceeds its slice budget.
With per-tile `Vec`, each tile grows naturally if its budget is
exceeded; no SAFETY contract needs to claim "tile `t` writes only
to bytes `[off_t, off_t+len_t)` of the shared arena". The cost is a
heap allocation per `TileBuffer` (amortised — the `Vec` is reused
frame-to-frame, sized to libvpx's `encode_tiles_buffer_alloc_size`
on first use).

**Impact on byte parity:** zero. The final packed frame is identical.

### §7.5 `show_existing_frame` is `Option<u8>`, not "bit + literal"

**What:** libvpx packs `show_existing` as a 1-bit flag followed by
an unconditionally-emitted 3-bit `alt_fb_idx` when the flag is set
(`vp9_bitstream.c:1253-1257`). The Rust port uses `Option<u8>` for
the in-memory representation; the wire form is identical (1 + 3
bits when `Some(idx)`).

**Why:** type safety. The libvpx layout makes it possible for an
inconsistent state (`show_existing = false` but `alt_fb_idx`
nominally set) to slip into the writer. `Option<u8>` makes this
unrepresentable.

**Impact on byte parity:** zero.

### §7.6 `BitstreamError::CompressedHeaderTooLarge` carries the actual size

**What:** libvpx errors with a string `"compressed_hdr_size > 16
bits"`. Our error carries the offending byte count for diagnostic
purposes. Functional behaviour identical.

**Why:** debuggability.

**Impact on byte parity:** none (error path).

### §7.7 No callback-based error handler on the raw-bit reader

**What:** libvpx `struct vpx_read_bit_buffer` (`bitreader_buffer.h:24-31`)
holds `error_handler_data` and `error_handler` callbacks that fire
on out-of-bounds read. We omit them and return
`BitstreamError::Truncated` instead.

**Why:** Rust's `Result` propagation makes the callback redundant.
The callback exists in libvpx only because C lacks `Result` and
because the caller wants to longjmp back to a recovery frame.

**Impact on byte parity:** none.

### §7.8 Reserve a typed `SuperframeBuilder` rather than per-frame mutate of `ctx->pending_*`

**What:** libvpx accumulates frames into `vpx_codec_alg_priv_t`
fields (`pending_cx_data`, `pending_frame_count`,
`pending_frame_sizes[]`, `pending_frame_magnitude`,
`vp9_cx_iface.c`). We expose a dedicated `SuperframeBuilder` type
the encoder constructs explicitly when SVC or `show_existing_frame`
queues multiple frames.

**Why:** Rust separation of concerns. The "pending superframe" state
is conceptually a builder, not a tangled field of the encoder root.

**Impact on byte parity:** zero. The wire form is identical.

### §7.9 `tile_buffer.buf` is byte-tight, not over-allocated to libvpx's worst-case constant

**What:** libvpx pre-allocates each worker's slice to
`mb_cols * mb_rows * 8 * 16 + (32 << 20) / num_workers`
(`vp9_bitstream.c:967-973`). Our `Vec<u8>` is grown on demand and
shrunk only by `Encoder` shutdown. Memory peak is similar; peak
allocation point differs.

**Why:** Rust's `Vec` is a better fit than malloc-and-track. The
libvpx constant is a hard cap with no fallback; ours is amortised.

**Impact on byte parity:** zero.

### §7 — Deliberate divergences (from `denoiser.md`)

### 7-D1 — Denoiser `running_avg_y` indexing flattened to `[layer][ref]`

**Where:** `rvp9_encoder::denoiser::Denoiser::running_avg_y`. libvpx
counterpart: `vp9/encoder/vp9_denoiser.c:344-353`
(`INTRA_FRAME + shift` arithmetic).

**What libvpx does:** stores `running_avg_y[]` as a flat array of
`num_ref_frames * num_layers` `YV12_BUFFER_CONFIG`s and indexes via
`running_avg_y[INTRA_FRAME + shift]` where `shift = layer * num_ref_frames`.
This is a layered array disguised as a flat one.

**What rvp9 does:** uses a 2D `[layer][ref]` accessor over the same underlying
storage. The flat layout is preserved for SIMD-friendly stride math, but the
public method `Denoiser::ref_slot_mut(layer, ref) -> &mut FrameBuffer` makes
the layering explicit.

**Why:** the flat indexing is the source of Q-RC-8 ("layered array disguised
as a flat one"). It also creates a per-block aliasing question (whether two
slots overlap) that we resolve by making the layer dimension explicit at
compile time. No runtime overhead; the flattening is purely a public-API
choice.

**Byte-parity impact:** none. The pixel storage is identical; only the access
pattern differs.

**Compression-efficiency impact:** none.

**Future plan:** keep this in v2 unless the storage becomes an SIMD bottleneck.
Decision: L-22 (sub-issue).

### 7-D2 — Rename "slot 0" of `running_avg_y` to `current_denoised_frame`

**Where:** internal API only: `Denoiser::current_denoised_frame_mut(layer)` and
`Denoiser::ref_slot_mut(layer, ref)`. libvpx counterpart: the implicit dual
use of `running_avg_y[INTRA_FRAME + shift]` as both "current denoised output"
and (after `update_frame_info`) "previous-frame ref slot 0".

**What libvpx does:** writes the per-block denoised pixels to
`running_avg_y[INTRA_FRAME + shift]` during the frame, then swaps that slot
into a ref-frame slot post-encode. The same `YV12_BUFFER_CONFIG` therefore
plays two roles at different points in the frame loop. Q-RC-9 documents this
as "easy to get wrong in a port."

**What rvp9 does:** keeps the same storage but exposes two named accessors so
the dual role is visible at every call site. `current_denoised_frame_mut` is
the per-block write target during the frame; `ref_slot_mut(layer, ref)` is
the post-encode swap target. Internally they alias the same `FrameBuffer`
when `ref == 0`; the swap in `post_encode_frame` moves the buffer to a
non-zero ref slot.

**Why:** Q-RC-9 / A5 §7 lists this as a documented trap. Naming costs nothing
and prevents class of bugs.

**Byte-parity impact:** none.

**Compression-efficiency impact:** none.

**Future plan:** keep. Decision: L-22 (sub-issue).

### 7-D3 — Move `running_avg_y[]` re-init from post-encode to pre-encode

**Where:** `rvp9_encoder::denoiser::Denoiser::pre_encode_frame`. libvpx
counterpart: `vp9/encoder/vp9_denoiser.c:790-806`
(`vp9_denoiser_update_ref_frame` re-init branch).

**What libvpx does:** on KEY_FRAME or `reset == 1`, copies the source into all
`running_avg_y` slots inside `vp9_denoiser_update_ref_frame`, which is
called **after** the frame is encoded. The effect is that the next frame's
encode reads the just-initialised slots.

**What rvp9 does:** moves the re-init to `pre_encode_frame`, which runs
**before** the workers spawn. Read-write order across frames is unchanged;
the slot is read by next-frame workers either way.

**Why:** ordering between `noise_estimate.update` (reads `last_source`) and
`pre_encode_frame` (reads `source`) is unambiguous in our split. In libvpx
the timing is implicit; in Rust we want the per-frame hooks to be obvious
fn calls in a single function.

**Byte-parity impact:** none (read and write sets of the two hooks are
disjoint across the frame boundary).

**Compression-efficiency impact:** none.

**Future plan:** keep. Decision: this LLD.

### 7-D4 — Denoiser does not read or write the segmentation map (L-67 resolution)

**Where:** `rvp9_encoder::denoiser`. libvpx counterpart: `cm->seg_map` is
read/written by `vp9_aq_cyclicrefresh.c` and read by no part of
`vp9_denoiser.c`.

**What libvpx does:** AQ-CR (cyclic refresh) owns `cm->seg_map`. The denoiser
does not read it. There is a transitive coupling via the speed-feature
cascade and `sb_skip_denoising`, which AQ-CR populates upstream
(`vp9_pickmode.c:1721-1747`).

**What rvp9 does:** make the boundary explicit. `rvp9_encoder::aq::cyclic_refresh`
owns `seg_map` (HLD-threading §5.2 row "segmentation_map"). The denoiser
reads only the derived `PickModeCtx::sb_skip_denoising` boolean.

**Why:** L-67 (devil's advocate #14) raised the segmentation-map ownership
question. The right answer is "the denoiser is a read-only consumer of a
derived boolean, not of the map." Documenting it here closes L-67 for this
LLD; HLD-threading owns the map's tile-disjoint write discipline for AQ-CR.

**Byte-parity impact:** none.

**Compression-efficiency impact:** none.

**Future plan:** keep. Decision: L-67.

### 7-D5 — Denoiser SIMD bit-parity caveat (L-22 / R-03 — the load-bearing entry)

**Where:** `rvp9_encoder::denoiser::filter::{scalar,sse2,neon}`. libvpx
counterpart: `vp9/encoder/vp9_denoiser.c:65-67` TODO comment; the scalar
implementation at `:68-180`; the SSE2 implementation at
`vp9/encoder/x86/vp9_denoiser_sse2.c`; the NEON implementation at
`vp9/encoder/arm/neon/vp9_denoiser_neon.c`.

**What libvpx does:** ships three implementations of `vp9_denoiser_filter`.
The scalar version walks pixels row-major and accumulates `total_adj` as a
single running `i32`. The SSE2 version reduces 16-pixel vectors with
`_mm_sad_epu8`-style horizontal adds and accumulates a partial sum per row.
The NEON version is structurally similar to SSE2. **For
`increase_denoising = 0`** all three produce identical pixels and identical
return values: the per-pixel computation has no accumulation-order
sensitivity. **For `increase_denoising = 1`** the larger `adj_val`
magnitudes can push `total_adj` close to the threshold from different
directions in the scalar vs SIMD reductions; the `delta` derived from
`total_adj` in the second pass then differs by 0 or 1, which causes a
≤1-pixel divergence in some second-pass outputs and (rarely) a different
`FILTER_BLOCK` vs `COPY_BLOCK` decision. libvpx has a TODO at lines 65-67
acknowledging this is not bit-exact and **does not fix it**.

> /* If increase_denoising is enabled in the future, we might need to
>  * update the code for calculating 'total_adj' in case the C code is
>  * not bit-exact with corresponding sse2 code. */
> — `vp9/encoder/vp9_denoiser.c:65-67`

**What rvp9 does:**

1. **Designate the scalar Rust implementation as the canonical
   implementation.** It mirrors `vp9_denoiser_filter_c` line-for-line
   (§5.5). The C scalar reference is libvpx's "spec-of-record" — when in
   doubt, the scalar wins.

2. **The SSE2 Rust implementation mirrors `vp9_denoiser_filter_sse2`
   line-for-line.** Goal: matched-config byte-parity with libvpx-SSE2 at the
   pixel level. This means a user who runs both libvpx-with-SSE2 and
   rvp9-with-SSE2 on the same input gets identical bitstreams, even though
   that output may diverge from libvpx-C-without-SSE2 by ≤ 1 pixel per
   block. **Same constraint applies to NEON ↔ libvpx-NEON.**

3. **Differential testing:**
   - Scalar-vs-scalar (rvp9 vs libvpx): bit-exact, no epsilon, all
     `increase_denoising` values.
   - SSE2-vs-SSE2 (rvp9 vs libvpx): bit-exact, no epsilon, all
     `increase_denoising` values.
   - NEON-vs-NEON (rvp9 vs libvpx): bit-exact, no epsilon, all
     `increase_denoising` values.
   - Scalar-vs-SSE2 (within rvp9): bit-exact for `increase_denoising = 0`;
     ≤ 1 ULP per pixel for `increase_denoising = 1` (allowed epsilon).
     `FILTER_BLOCK` vs `COPY_BLOCK` mismatches are permitted with
     `increase_denoising = 1` and noted in test output for triage.
   - Scalar-vs-NEON (within rvp9): same as scalar-vs-SSE2.

4. **Production dispatch:** at runtime the dispatch table picks SSE2 if
   available, else NEON if available, else scalar. The choice is deterministic
   per machine. A "force-scalar" environment variable
   (`RVP9_DENOISER_FORCE_SCALAR=1`) is provided for byte-parity diagnostic
   runs against libvpx-without-SSE2.

5. **BD-rate impact:** in matched-config CI (rvp9-SSE2 vs libvpx-SSE2), zero.
   In mixed configs (rvp9-scalar vs libvpx-SSE2), the divergence ledger
   notes that we expect ≤ 0.01% BD-rate noise on
   `increase_denoising = 1` content (i.e., `denoising_level == kDenHigh`).

**Why:** L-22 + R-03 in `decisions-needed.md`; Q-RC-23 in A5;
HLD-simd §5.5 / divergence-ledger L-RTCD-04. The alternative — picking one
canonical impl and forcing all ISAs to match it bit-exactly — would require
either (a) a non-SIMD-friendly scalar-emulation in the SSE2 path (defeats
the purpose), or (b) a non-libvpx-compatible SIMD reduction in the scalar
path (introduces divergence with libvpx-C, our spec-of-record). Neither is
worth ≤ 0.01% BD-rate noise on a narrow subset of content.

**Byte-parity impact:** minor. Matched-config byte-parity is preserved at
every supported ISA. Mixed-config byte-parity (one side using SSE2, the
other not) admits ≤ 1-pixel per-block divergence on
`increase_denoising = 1` blocks only. PLAN.md D8 makes byte-parity a
diagnostic tool, not a release gate; this divergence does not gate release.

**Compression-efficiency impact:** ≤ 0.01% BD-rate noise on
`denoising_level == kDenHigh` content. Well within the 0.5% PLAN.md gate.

**Future plan:** revisit if libvpx fixes their TODO. As of v1.14.1 (the
pinned version), the TODO is open and we mirror as-is. Decision: L-22 / R-03;
shares L-RTCD-04 with HLD-simd §5.5.

### 7-D6 — Skin detection moved to mode-decision LLD

**Where:** `rvp9_encoder::mode_decision::skin` (mode-decision LLD).
libvpx counterpart: `vp9/encoder/vp9_skin_detection.c` is its own file in the
encoder directory.

**What libvpx does:** ships skin detection as a standalone file called by the

### 7.1 Trellis-quant (`vp9_optimize_b`) not ported — L-28 RESOLVED

**Where:** `rvp9-core::transforms` does not expose any "optimize
coefficients" entry point; `rvp9-encoder::quant` does not call one.

**libvpx:** `vp9_optimize_b()` in `vp9/encoder/vp9_encodemb.c:66-300`
plus its callsites at lines 632, 884, 900, 917, 935, 963, 975, 987,
1003. Runs a trellis-quant optimization over each coded block,
reading `scan`, `neighbors`, `token_costs[tx_size][...]`, and choosing
between "keep current value" and "reduce by 1" per scan position
greedily.

**Why drop:** at cpu-used 6-8 libvpx sets `sf->optimize_coefficients =
0` in `set_rt_speed_feature_framesize_independent` (A6 §5.12 line 1514
analysis). Every `enable_trellis_opt` flag derives from this; the
function body is never executed at our speed setting. Drop it entirely.

**Byte-parity impact:** none in matched configs (`--cpu-used 7
--rt` is our reference).

**Future plan:** if a quality preset (cpu-used ≤ 4) is added in
v2, this becomes a new LLD entry. Status: ledger entry exists
(2026-05-16 — Trellis-quantization). This LLD does **not** add a new
ledger row — it confirms the existing one applies.

### 7.2 Lossless encoder path not built; decoder honors lossless

**Where:** `rvp9-encoder::*` cannot produce a lossless frame —
the encoder's rate controller (LLD-rate-control) refuses `base_qindex
== 0`. `PerFrameTransforms::select(_, lossless: true)` therefore is
only ever invoked from the **decoder** path. The forward WHT
(`vp9_fwht4x4`) is shipped in `FwdTxfm` for completeness + future
proofing but its only test consumer is the round-trip differential.

**libvpx:** `vp9_encodeframe.c:6093-6097` flips both forward and inverse
based on `xd->lossless`. The full lossless encode flow runs at the
slowest quality presets (cpu-used 0, plus the lossless config flag).

**Why split:** v1 encoder does not target lossless (no real-time use
case). The decoder must still honor lossless frames in conformance
vectors.

**Byte-parity impact:** none in matched configs. A lossless conformance
vector exercises the WHT inverse path only; the WHT forward path is
exercised by tests, not by production encode.

**Future plan:** if a lossless encoder preset is ever added, the
forward WHT is already wired in `FwdTxfm` — only the rate-controller
gate needs lifting. **New ledger entry needed.**

### 7.3 Hybrid scan for 32×32: dispatch redundancy preserved

**Where:** `SCAN_ORDERS[Tx32x32][*]` repeats the same `ScanOrder`
struct four times (one per `TxType`), even though libvpx semantically
never reaches the non-default slots.

**libvpx:** `vp9_scan.c:707-723` does the same — four redundant entries
in the dispatch array. We mirror exactly to keep the indexing pattern
uniform; the alternative (returning the default scan from `scan_for`
when `size == Tx32x32` and skipping the entry storage) would diverge
from libvpx's data layout. Memory cost is 3 × `sizeof(ScanOrder) = 72
bytes` per ISA. Trivial.

**Byte-parity impact:** none.

**Future plan:** none.

**Ledger:** no new entry — this is byte-for-byte parity with libvpx.

### 7.4 SSSE3 promoted to required for three inverse-DCT kernels

**Where:** `SimdDispatch::detect()` (HLD-simd §3.18) refuses to start
on an x86_64 host without SSSE3 when those three kernels would
otherwise fall back to the slower SSE2 variants.

**libvpx:** allows SSE2-only x86 to run; the SSSE3 paths are optional.
SSE2 fallbacks for `idct8x8_12 / idct32x32_135 / idct32x32_34` exist
and work correctly.

**Why diverge:** SSSE3 is universal on hardware shipped since 2007; the
SSE2 fallback is markedly slower (~30% on Skylake-class) and harms our
realtime gate. HLD-simd §3.18 owns this decision.

**Byte-parity impact:** none — the SSSE3 and SSE2 paths produce
bit-exact output (verified in §6.4 differential tests).

**Future plan:** revisit only if a pre-Nehalem (pre-2008) target
becomes interesting. None planned.

**Ledger:** **new entry** to be added at Stage 2 close — "SSSE3
mandatory for three inverse-DCT kernels on x86_64".

### 7.5 EOB-bucket dispatch centralised in `EobBucket::for_size`

**Where:** `rvp9-core::transforms::EobBucket::for_size` replaces the
inline `if/else` cascades in `vp9_idct.c:119-179`.

**libvpx:** four separate functions (`vp9_idct4x4_add`,
`_8x8_add`, `_16x16_add`, `_32x32_add`) each with its own
`if eob == 1 { ... } else if eob <= N { ... }` ladder.

**Why centralise:** preserves byte-identical dispatch decisions while
making the test surface cleaner (`EobBucket::for_size` is unit-testable
in isolation). The dispatch tables in §3.4 still hold one entry per
EOB bucket per size, exactly mirroring libvpx's per-size kernel set.

**Byte-parity impact:** none — same kernel selected for the same `(size,
eob)`.

**Future plan:** none.

**Ledger:** no new entry — pure refactoring with provable equivalence.

### 7.6 Scan-order tables: alignment via `#[repr(align(16))]`

**Where:** the wrapper struct `Align16<T>` in §4.3.

**libvpx:** `DECLARE_ALIGNED(16, static const int16_t, ...)` in
`vp9_scan.c` lines 3254 etc. (compiler attribute).

**Why mirror:** unverified whether 16-byte alignment is load-bearing
for any SIMD kernel that reads scan tables directly. libvpx's
alignment is defensive; we mirror to avoid a guessing game. See §8 O-1.

**Byte-parity impact:** none.

**Ledger:** no new entry — implementation detail.

### 7.7 32×32 hybrid (`vp9_fht32x32` / `vp9_iht32x32`) absent

**Where:** `FwdTxfm` has no `fht32x32` field; `InvTxfm` has no
`iht32x32_*_add` field.

**libvpx:** also absent. 32×32 hybrid is not part of the VP9 spec; the
scan-table dispatch (`vp9_scan_orders[3][*]`) forces every 32×32 block
to use the default DCT-DCT scan, which means `tx_type` at 32×32 is
unobservable in the bitstream and the encoder/decoder always run the
DCT.

**Why document:** future readers may wonder why the table is 14
forward / 17 inverse rather than 16 / 20. This is the answer.

**Byte-parity impact:** none.

**Ledger:** no new entry — spec-mandated.

### 7.8 Forward 32×32 _rd vs full split

**Where:** `FwdTxfm.fdct32x32` and `FwdTxfm.fdct32x32_rd` are two
separate fields; `forward()` selects by `rd_transform` parameter.

**libvpx:** `vp9_encodemb.c:331-337` (`static INLINE void
fdct32x32(int rd_transform, ...)`) does the same — selects based on
`x->use_lp32x32fdct`.

**Why mirror:** the two kernels produce different coefficients
(`vpx_fdct32x32_rd_c` uses an extra rounding shift). Byte parity at
cpu-used 6-8 requires the same selection (KF runs full precision,
inter runs `_rd`).

**Byte-parity impact:** none in matched configs.

**Ledger:** no new entry — byte-for-byte parity.
