# G5.2 follow-up — tile_rows > 1 parallelism

## Status

**Deferred.** G5.1 ships parallel tile dispatch for the
overwhelmingly common case (`tile_rows == 1`). Multi-tile-row
frames fall back to the inline path.

## Why deferred

VP9's `tile_rows` field is in `[0..=2]` (1, 2, or 4 tile rows). All
conformance vectors in our corpus use `tile_rows = 1` (only
`tile_cols` varies, hence `tile_1x2`, `tile_1x4`, `tile_1x8`). The
real-world distribution similarly skews to `tile_rows = 1` because
encoders prefer column tiles for parallel encode + decode latency.

## What G5.2 would add

For `tile_rows > 1` the disjoint-column split is no longer
sufficient — multiple tile rows write to overlapping column ranges
in the same row-strided buffer. Two implementation options:

### Option A: 2D rect split

Each `(tile_row, tile_col)` pair owns a rectangle. The merge
becomes a 2D memcpy. Same per-tile-fresh-`Yv12Buffer` shape, just
with a row-range parameter added to `merge_tile_columns_from`:
`merge_tile_rect_from(src, luma_col_start, luma_col_end,
luma_row_start, luma_row_end)`.

Allocation cost grows linearly with `tile_rows * tile_cols` rather
than `tile_cols` alone — for `tile_rows = 4` × `tile_cols = 4` that's
16 scratch frames, ~50 MB at 1080p. Still feasible but worth
recycling.

### Option B: Encoder-side tile sub-frames

For `tile_rows > 1`, dispatch each tile to a sub-frame-sized
scratch `Yv12Buffer` (rebased coords). Decoder code would need to
accept tile-local coords, which is a substantial refactor.

## Recommendation

Pursue Option A when the need arises. Today's inline fallback is
correct + bit-exact; it just leaves wall-clock on the table for
4-tile-row vectors.

## Eligibility gate location

`crates/rvp9-decoder/src/lib.rs` — the `let parallel = ...` line in
both `decode_intra_frame_inner` and `decode_inter_frame`. Currently
checks `tail.tile_info.log2_tile_rows == 0`. To enable G5.2,
remove that check and add the 2D rect split + merge.
