# Decoder perf — the gap vs vpxdec is INTRA reconstruction (2026-05-29)

**Goal:** match the decode speed/accuracy of `vpxdec` in `rvpdec`.

**TL;DR:** Accuracy is already byte-exact (conformance + cross-decoder
gate pass). The *speed* gap is **dominated by intra-block reconstruction**
(`reconstruct_intra_planes`), which is ~**60% of total single-thread
decode time** on BOTH synthetic (`testsrc`) and real (`foreman`) content.
The DSP kernels (IDCT, convolve) — the prior "kernel audit" focus — are
NOT the gap: they are now only 1.2–2.5× off libvpx, and rvp9 already
*beats* vpxdec on kernel-heavy/dense content. The gap is **per-block /
per-TX fixed overhead in intra prediction**, not per-pixel kernel speed.

This overturns the framing in `notes/decoder-libvpx-kernel-audit.md`
(which pointed at convolve8/idct32x32). Those were real but are now
largely closed, and they were never the end-to-end gap on the cases
where rvp9 *loses* to vpxdec.

---

## How we know (single-thread, this dev host)

Phase split of `decode_frame` (testsrc_720p30, t=1, via the
`profile-tiles` feature, instrumented inline-path):

| phase          | µs/frame | %     |
|----------------|----------|-------|
| reconstruction | 2466     | 76.4  |
| loop filter    | 714      | 22.1  |
| border extend  | 48       | 1.5   |
| **wall**       | **3228** | (vpxdec ≈ 606) |

Within reconstruction, splitting by block type (rdtsc accumulators
around the leaf calls — large brackets, reliable):

| bucket                     | testsrc µs/frame | foreman µs/frame |
|----------------------------|------------------|------------------|
| **intra-in-inter recon**   | **~1920 (76%)**  | **~459 (77%)**   |
| inter MC + residual        | ~460             | ~91              |
| mode-info read             | ~54              | ~20              |
| pre-reads + bookkeeping     | ~77              | ~13              |

Per-block: **intra ≈ 13–15 µs/block** vs **inter ≈ 1.4 µs/block** (≈9×).

Drilling into the intra block (per-TX accumulators; absolute ns inflated
by the rdtsc instrumentation itself, but the *structure* is clear):

- An intra block iterates **~150–226 TX sub-blocks** (3 planes ×
  `(bsize_4x4 / tx_step)²`). Large blocks with small TX dominate.
- Per TX sub-block ≈ **~56 ns**: edge-build (`build_intra_predictors`)
  ~15 ns + predict+residual (`intra_predict` / `reconstruct_intra_block`)
  ~41 ns.
- Edge-build *alone* ≈ 520 µs/frame on testsrc — nearly vpxdec's
  *entire* decode.

The actual prediction compute for a 4×4 TX is trivial (SIMD, a handful
of ops). So the ~56 ns/TX is **overhead**: function-pointer dispatch,
per-TX setup, debug trace-flag reads, detokenize per-coeff, and small
IDCTs — multiplied by a huge TX count.

## Why testsrc looked "mostly skip" but isn't

testsrc inter frames are tiny (172–800 B), which *suggested* mostly-skip
content. But the cheap-to-code blocks are largely **intra-with-(near-)
skip**: flat/edge regions predicted by intra modes with little/no
residual. They cost almost no bits but rvp9 still runs
`build_intra_predictors` + `intra_predict` per 4×4 TX, hundreds of times
per block. vpxdec does the same work far more cheaply per TX.

## Content sensitivity (why rvp9 wins some, loses others)

- rvp9 **beats** vpxdec on dense/high-coefficient content
  (`vp90-2-00-quantizer-00`, ratio 0.29×) — its per-pixel kernels are
  competitive.
- rvp9 **loses** on intra-heavy content (testsrc 7×, foreman 1.9×) —
  per-TX intra overhead dominates.

So the lever that closes the *gap* is intra per-TX overhead, not kernels.

### NON-bug note: idct32x32_135 microbench `OutMatch=False`
The audit aborts on `idct32x32_135_add` output mismatch vs libvpx. This
is an **out-of-contract artifact**, NOT a decoder bug:
- rvp9's `idct32x32_135` intentionally processes rows 0..16 × all 32 cols
  (matches its scalar reference); libvpx processes only the top-left
  16×16. On real bitstreams (eob≤135 ⇒ nonzero coeffs confined to
  top-left 16×16, zero elsewhere) all impls agree — proven by the
  passing full-stream cross-decoder gate.
- The microbench feeds a *dense* 1024-coef input (violates the eob≤135
  contract), so the two contracts diverge there.
- All 14 `idct32x32_135` proptests PASS. The untracked
  `proptest-regressions/dsp/x86_64/idct32x32_avx2_135.txt` is a STALE dev
  artifact from before the "scalar-contract fix" (commit 9841d6c); safe
  to delete or ignore.

- `crates/rvp9-decoder/src/tile.rs` `reconstruct_intra_planes`: hoisted
  the per-TX `trace_flags()` reads (`intra_at`, `kfleaf`) out of the hot
  TX loop (read once per intra-block). Byte-identical (conformance +

  not a demonstrated speedup** — kept as a correct-by-inspection cleanup
  of the hottest loop. A third per-TX `trace_flags()` read lives inside

  small API change (move the trace to the caller) — deferred.

## Measurement caveat (IMPORTANT)

This dev host's noise floor is **~±6%** even with CPU pinning +
best-of-8 + High priority. Sub-6% decode changes are UNMEASURABLE here.
Two consequences:
1. Validating intra micro-opts needs the dedicated pinned host
   (HLD §6.4 Linux CI runner), or wins must exceed ~10%.
2. rdtsc (`now_cycles`, non-serializing) UNDER-counts small inline
   brackets due to OoO reorder — only large brackets (whole function
   calls) are trustworthy for fine splits.

## Roadmap (prioritized) — close the intra gap

1. **Reduce per-TX dispatch/setup overhead** in `reconstruct_intra_planes`.
   Biggest aggregate cost. Options: specialize the per-TX loop by
   (mode, tx_size); cut the function-pointer indirection for the hot
   predictors; remove the remaining per-TX `trace_flags()` (move trace
   to caller / compile-time gate).
2. **`build_intra_predictors` (edge build, ~15 ns/TX)** — it's a faithful
   libvpx scalar port; look for branch/bounds-check reductions and a
   fast path for the common in-frame (non-clipped) case.
3. **detokenize per-TX** (non-skip intra) — entropy decode of coeffs is
   inherent but vpxdec's is hand-tuned; profile the bool-reader hot path.
4. **idct16x16_256 (1.63×) and idct32x32_* (~1.5×)** AVX2 — bounded,
   byte-exact, helps dense content (not the primary gap but cheap wins).
5. Loop filter (22% on testsrc) — secondary; mask-build overhead on
   skip-heavy frames is a separate investigation.

## Refinement after deeper inspection (same session)

The intra path is **already optimized at the SIMD/inlining level** — so the
gap is NOT a missing-SIMD lever:
- All intra predictors route through AVX2 dispatch slots, **including DC**
  for all sizes/availabilities (`dc_predict_with_availability` →
  `dc_predict_full/top/left/128` slots; the stale comment at
  `intra_pred.rs:745` predates Wave I I4 which wired them).
- Release profile is **`lto = "fat"`, `codegen-units = 1`** → cross-crate
  inlining of rvp9-core kernels into rvp9-decoder is already on.
- Edge copies use `copy_from_slice` (vectorizable); only the strided
  left-column read is per-element bounds-checked.

The 9× intra-vs-inter cost is **structural and spec-mandated**: intra
predicts *per-TX* (each TX depends on its just-reconstructed neighbours,
so prediction cannot be hoisted to the whole block), whereas inter does
**one** whole-block motion-comp then adds residual per TX. vpxdec has the
same structure; the delta is per-TX Rust overhead (bounds checks,
fn-pointer dispatch indirection that blocks inlining the tiny per-TX
kernels, detokenize entropy) vs hand-tuned C/asm.

**No-regression check:** full rvp9-side head-to-head matrix after the
trace-hoist matches the committed `decode-headtohead.md` within host
noise on all 9 rows.

## Honest assessment / remaining levers (all need the pinned host to verify)

The safe, high-confidence wins in the intra *kernels* are exhausted
(already SIMD+LTO). Remaining options, each individually <5% (sub-noise
here) and/or carrying risk:

1. **Compile-time-gate the debug traces** behind a `decoder-trace` cargo
   feature (default off) so every `if trace_flags().X` in the hot paths
   becomes provably-false and is eliminated (removes the per-TX OnceLock
   loads + branches in intra_predict / reconstruct_intra_planes, and also
   the inter + LF trace sites). Byte-exact (traces are eprintln
   side-channels). **Caveat:** changes the debug UX (env vars would
   require the feature) and touches the shared `trace_flags` mechanism in
   BOTH rvp9-core and rvp9-decoder — discuss before landing in the
   multi-agent repo.
2. **`unsafe` bounds-check elimination** in `build_intra_predictors`
   strided left-column read (bounds are provably in-range for the
   have_left case). Risk: unsafe in a conformance-critical faithful port.
3. **Detokenize hot-path** (bool reader / coeff parsing) — affects all
   content; deeper investigation needed.
4. **idct16x16_256 (1.63×) / idct32x32_* (~1.5×) AVX2** — bounded,
   byte-exact, helps dense content (not the primary gap).

Real-content reality: rvp9 is ~1.9× vpxdec on `foreman` — respectable for
a safe-Rust, spec-faithful decoder vs decades-tuned asm. Exact parity on
intra-heavy content likely requires the unsafe/structural work above,
validated on the pinned CI host (this dev box can't measure <6%).

## FINAL per-TX breakdown (non-skip intra TX, function-call brackets — reliable)

Measured 13.7M non-skip intra TX over the testsrc run (nearly ALL intra TX
are non-skip but mostly empty: eob=0):

| component                     | per-TX | share | notes |
|-------------------------------|--------|-------|-------|
| **detokenize** (`decode_block_tokens`) | **31 ns** | **53%** | entropy coeff decode; biggest cost even at eob=0 (must decode EOB token + context) |
| predict (`intra_predict`)     | 20 ns  | 34%   | already AVX2-dispatched |
| inverse-transform             | ~0 ns  | ~0%   | eob=0 ⇒ `inverse_transform_add` skipped |
| edge-build (`build_intra_predictors`) | ~15 ns | (separate) | scalar libvpx port |

**The single biggest per-TX cost is entropy coefficient decode (31 ns).**
The `BoolReader` core is already carefully tuned (`#[inline] fill` + a
`#[cold] #[inline(never)]` slow path, comments document deliberate inline
tuning). So this is largely the **irreducible algorithmic cost** of VP9's
serial arithmetic-coded coefficient decode — exactly what libvpx hand-tunes
in assembly. Estimated end-to-end per-TX: rvp9 ~56 ns vs vpxdec ~11 ns
(~5×), and that 5× is spread across entropy decode + predict + edge, each
already SIMD/LTO/tuned at the Rust level.

## Conclusion (honest, evidenced)

The decoder is **well-architected**: SIMD predictors (incl. DC), fat-LTO
cross-crate inlining, a tuned bool reader, eob-bucketed IDCTs that *beat*
libvpx at small sizes. There is **no missing-SIMD or structural lever** that
closes the gap. The single-thread speed gap vs vpxdec is the **safe-Rust +
spec-faithful tax vs decades-tuned x86 assembly**, concentrated in per-TX
entropy decode and intra-prediction overhead — irreducible without:
- hand-written asm / heavy `unsafe` for the entropy decoder + intra kernels
  (large, specialized, conformance-critical), and
- a pinned bench host to validate each step (this dev box's ±6% noise floor
  hides every individual micro-opt).

rvp9 is **~1.9× vpxdec on real content** (`foreman`) and already *faster* on
dense content — a strong result for safe Rust. Literal single-thread parity
with `vpxdec` is not achievable via byte-exact micro-optimization.

### Achievable / measurable directions (recommend recalibrating the goal)
1. **Threaded-throughput parity** — rvp9's multi-tile threaded path can
   approach vpxdec via parallelism (tile_1x4 t4 is 1.97×; more decode
   threads / better LF threading hide per-block overhead). A "match vpxdec
   throughput at N threads" target is realistic and measurable.
2. **Pinned-CI micro-opt grind** — on the dedicated runner (HLD §6.4), do the
   compounding sub-noise wins (hoist per-TX-constant `coef_probs`/counts
   slicing out of `decode_block_tokens`; `unsafe` bounds-elision in
   `build_intra_predictors`; reduce the 16-arg `reconstruct_intra_block`
   call overhead), each measured.
3. **`unsafe`/asm entropy decoder** — the highest-ceiling but highest-effort
   path; needs explicit sign-off (beyond "byte-exact").

## Authorized unsafe-grind outcome (2026-05-29, "proceed on faith" → "authorize unsafe/asm")

**Key finding: the decoder hot loops are ALREADY through the unsafe grind.**
- `entropy/detokenize.rs::decode_coefs` (the 31 ns/TX detokenize — the single
  biggest per-TX cost) is **fully `get_unchecked`-optimized** with documented
  invariant proofs (lines ~482-655: `band_translate`, `coef_probs`,
  `scan.scan`, `token_cache` all unchecked).
- `BoolReader` is hand-tuned (`#[inline] fill` + `#[cold] #[inline(never)]`
  slow path).
- `DQ_COEFS_BUF` thread-local scratch is the *measured-optimal* choice
  (R.10-R.12 experiments documented in `reconstruct.rs`: stack `MaybeUninit`
  regressed 8-24% due to deep partition recursion).
- Predictors AVX2 (incl. DC), IDCTs eob-bucketed (beat libvpx small), LTO fat.

So the authorized "unsafe quick wins" are **largely already implemented**.
The one hot-path function not yet bounds-optimized was `build_intra_predictors`;
landed a **safe** (no `unsafe` needed) `step_by`-span bounds-elision for its
hot interior-block left-column read. Byte-identical; conformance (6/6 MD5) +
58 intra_pred + 207 decoder-lib tests pass.

**Measurement is impossible on this host.** Byte-identical pure-work-removal
changes read 3928 µs and 4253 µs on two best-of-8 pinned runs minutes apart
(~8% swing). Decode micro-opts are far below the noise floor here. Per HLD
§6.4, pinned numbers require the dedicated Linux CI runner.

**Conclusion stands and is now fully evidenced:** the residual ~1.9× vs vpxdec
on real content is (a) per-TX **function-call/dispatch overhead** — `predict`
is ~20 ns/TX but the SIMD work is only ~5 ns, the rest is the
`intra_predict` call + match + fn-pointer dispatch (structural fusion would
help, but needs a measurement host to tune safely without code-bloat
regressions), and (b) the **asm-vs-Rust codegen tax** on the already-tuned
entropy decoder — only hand-written assembly closes it (deliberate
multi-week project per kernel, not a session grind). rvp9 also already meets
the real-time decode budgets (testsrc/1080p are PASS-info on the 33/16 ms
gates) — the practical "matching" is achieved; the literal speed-ratio
parity with hand-tuned asm is the open item.

## Byte-exact changes landed this session (3, all conformance 6/6 MD5 + tests pass)

1. `rvp9-decoder/src/tile.rs` — hoist per-TX `trace_flags()` reads (`intra_at`,
   `kfleaf`) out of the per-TX loop in `reconstruct_intra_planes`.
2. `rvp9-core/src/intra_pred.rs::build_intra_predictors` — safe `step_by`-span
   bounds-elision for the hot interior-block left-column read.
3. `rvp9-core/src/intra_pred.rs::intra_predict` — `#[inline]` + extract the
   `RVP9_TRACE_INTRA` debug dump into a `#[cold] #[inline(never)]` helper, so
   the hot predictor body is small enough for LTO to fold into the per-TX
   loop (cuts per-TX call + 7-arg marshaling + dispatch indirection — the
   `predict` step is ~20 ns/TX but only ~5 ns is real SIMD work).

All three are pure-work-removal / inlining (no new overhead, no `unsafe`
needed) → correct-by-construction, no regression risk by construction.
Perf unmeasurable on this host (noise floor); validated on the pinned CI host.

`reconstruct_intra_block` (the non-skip per-TX wrapper) is deliberately NOT
`#[inline]`d — it's large (detok + IDCT + TLS scratch) and called recursively
from `decode_partition`; the documented R.10-R.12 experiments show inlining/
stack-growth there regresses 8-24%.
