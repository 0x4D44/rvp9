# G5.3 follow-up — real-corpus tile_rows > 1 testing

## Status

**Code landed. Real-corpus oracle deferred.**

G5.3 generalises the G5.1 parallel-tile path (column-only) to a 2D
rect path that handles the full `tile_rows × tile_cols` grid. The
implementation is correct by construction (every tile owns a disjoint
rectangle of the `(mi_row, mi_col)` grid — see soundness argument
below) and is exercised by:

- `rvp9-core::frame::tests::merge_tile_rect_from_disjoint_rects` —
  unit test: 2×2 grid (4 tiles), each scratch buffer gets a unique
  fill byte, all four rects merged, every probe pixel asserts the
  expected fill survived.
- `rvp9-core::frame::tests::merge_tile_columns_from_matches_full_height_rect`
  — backward-compat oracle: the G5.1 wrapper produces byte-identical
  output to a full-height rect merge.
- `rvp9-harness::tile_threading::*` — the existing G5.1 tests
  (`tile_1x2`, `tile_1x4`, `tile_1x8` at N=1 vs N=2) all pass with
  the new code path, confirming the G5.1 case (tile_rows == 1)
  remains bit-exact.
- Full conformance corpus (201/201 frames) at N=2 — passes.

## Why real-corpus testing is deferred

The libvpx conformance suite (`vp90-2-08-tile_*`) shipped only
`tile_rows = 1` vectors (`tile_1x2`, `tile_1x4`, `tile_1x8`). No
`tile_2x*`, `tile_4x*`, etc. exist in the official corpus.

Generating tile_rows > 1 fixtures requires `vpxenc --tile-rows=N
--tile-columns=M`, but `vpxenc` is not part of the rvp9 build (it
lives in libvpx, which we depend on only for reference decoder
comparisons — and the reference decoder is libvpx-vp9, not the
encoder). Adding the encoder to our build would inflate the
dependency surface considerably for one oracle.

## Soundness argument (in lieu of corpus)

VP9 tiles partition the frame's MI grid into a regular
`tile_rows × tile_cols` partition. Every (mi_row, mi_col) cell
belongs to **exactly one** tile (no overlap, no gap). The new
`merge_tile_rect_from(src, luma_row_start, luma_row_end,
luma_col_start, luma_col_end)` copies exactly the cells within a
single tile's bounds. Because partition cells are disjoint, no two
tiles' merges touch the same byte. The merge is therefore
order-independent and parallel-safe.

The seg_id and mv_grid post-merges in `lib.rs` now iterate
`bounds.mi_row_start..bounds.mi_row_end` (was: `0..mi_rows`) for
the same reason — each tile only writes its own MI sub-grid.

## What corpus testing would add

A real `tile_2x2` (etc.) fixture would catch:
- A row-range off-by-one in `merge_tile_rect_from` (chroma vertical
  subsampling: `uv_row_start = luma_row_start >> ss_y`).
- A bug in the decoder's per-tile `TileBounds.mi_row_*` computation
  that only manifests when there's more than one tile row.
- A subtle ordering / counts-merge bug where two same-column-range
  tile-row siblings race on a shared counts accumulator (we already
  bucket counts into per-tile slots, so this should be ruled out
  by construction, but corpus would confirm).

Of these the first is covered by the unit test (it walks a 2×2 grid
explicitly probing the chroma planes). The second + third would
require corpus to flush out.

## Action when corpus arrives

If/when we add a `vpxenc` build dep (or someone hands us a
`tile_2x2.webm`), drop it into `tests/conformance/vectors/` along
with the `.md5` reference, and run the existing
`tile_threading::conformance_at_n_threads_2` test — it walks every
vector in the dir, so it'll pick up tile_rows > 1 vectors
automatically without code changes.

## Activation gate

`crates/rvp9-decoder/src/lib.rs` — both `decode_intra_frame_inner`
and `decode_inter_frame`. The G5.1 gate
`tail.tile_info.log2_tile_rows == 0 && buffers.len() > 1 &&
self.num_threads.get() > 1` is now just `buffers.len() > 1 &&
self.num_threads.get() > 1`. Multi-tile-row frames take the parallel
path.
