# RVP9-BUG-KIL-00097 — Validate Y4M output metadata

The Y4M writer validated chroma tags but emitted invalid dimensions or zero
framerate components. Its own 4:2:0 reader rejected those headers, breaking the
documented writer/reader contract.

The fix validates 4:2:0 geometry through the reader's existing checked layout
helper and shares the nonzero framerate check with the parser. Writer validation
returns `InvalidInput` before making any write; parser validation retains
`InvalidData`. Geometry rules for the other supported chroma formats remain.
The existing unsupported-Yuv440 rejection remains before output.

The table-driven regression covers ten invalid metadata combinations: zero,
odd, over-limit and extreme-even dimensions on both axes, plus zero numerator
and denominator. Each call starts with a nonempty output prefix and requires
`InvalidInput` plus identical output afterward. It aggregates failures so all
cases execute. Before the fix it failed its named assertion, exit 101: every
case was accepted and changed output (20 listed mismatches).

After validation was added, the focused `y4m` filter passed 23 unit and nine
integration tests, including existing writer/reader round trips and chroma-tag
checks. No new positive fixture is needed because those tests cover valid
behavior. The selected final smoke is `cargo test -p rvp9-io y4m`, bounded to
60 seconds after final fetch/catch-up.

The neighboring parser header-cap, zero-frame allocation, and relative-cursor
bugs are distinct ledger records and are outside this fix. Final formatting,
linting and diff checks passed: `cargo fmt --all --check`,
`cargo clippy -p rvp9-io --all-targets`, and `git diff --check`. Clippy emitted
no warnings. Lead reviewed the final source diff and confirmed validation
precedes the first write and preserves the parser's error message and kind.
