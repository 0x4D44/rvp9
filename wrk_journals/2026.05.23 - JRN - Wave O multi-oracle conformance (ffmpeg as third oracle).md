# Wave O — Multi-oracle conformance (ffmpeg as the third oracle)

**Date:** 2026-05-23
**Lead:** Claude (supervisor)
**Trigger (Arthur):** "we think this is a decoder bug? we're comparing rvp9dec vs
vpxdec on material encoded with vpxenc?" + "let's add ffmpeg to the oracle — the
goal is that all three agree."

## Why
Wave N closed with `foreman_c440.ivf` failing 12/12 frames in rvp9dec, attributed to
"pre-existing parser desync." But that attribution rested on libvpx (vpxdec) being
the sole oracle — and vpxenc/vpxdec ship from the same codebase, so a vpxenc-emitted
quirk would be bug-compatible with vpxdec, and we'd wrongly blame our decoder.
Arthur sharpened: bring in a second, independent VP9 decoder (ffmpeg's NATIVE `vp9`,
NOT `libvpx-vp9`) and require all three to agree.

## Log
- **Spot-check:** ffmpeg native `vp9` decoder on `foreman_c440.ivf` → ALL 12 frames
  byte-identical to vpxdec. Two independent VP9 decoder implementations agree →
  bug is **unambiguously in rvp9dec** (confirms the Wave N attribution, with no
  remaining ambiguity).
- Built `scripts/oracle-ledger-ffmpeg.ps1`: native-chroma per-frame visible MD5
  via `ffmpeg -c:v vp9 -pix_fmt <native> -f rawvideo` + per-frame slicing. Stem
  derived from the sibling vpxdec ledger's first line so the two ledgers are
  diff-identical when oracles agree.
- Ran with `-Verify` on all 7 current oracle vectors (6 Profile-1 + frame_parallel
  fixture). **All agree byte-for-byte: 94 frames total, 0 disagreement.**
  | Vector | Frames | vpxdec ↔ ffmpeg |
  |---|---|---|
  | vp91-2-04-yuv444.webm | 10 | identical |
  | foreman_c444.ivf | 12 | identical |
  | vp91-2-04-yuv422.webm | 10 | identical |
  | foreman_c422.ivf | 12 | identical |
  | vp91-2-04-yuv440.webm | 10 | identical |
  | **foreman_c440.ivf** | **12** | **identical** (← the suspected case) |
  | foreman-fp1.ivf (4:2:0) | 30 | identical |
- Rust harness wiring: new `rvp9_harness::md5file::read_triangulated_ledger(vector)`
  loads both `<vector>.md5` and `<vector>.ffmpeg.md5`, asserts they agree on every
  frame's hash, and returns the validated entries. Panic messages on disagreement
  explicitly name libvpx/ffmpeg as suspect — NOT the consumer's decoder.
- Swapped `read_md5_file` → `read_triangulated_ledger` in both
  `profile1_decode.rs` and `frame_parallel_regression.rs`. Every gated-test run
  now triangulates first, then compares rvp9dec. All tests still green (the
  oracles really do agree on every existing vector).
- Extended `scripts/encode-corpus.ps1` `-WithLedger` path to auto-call the
  ffmpeg ledger script with `-Verify` after the vpxdec ledger is written, so
  new fixtures get triangulated by default. Best-effort: warns rather than
  fails if ffmpeg isn't on PATH.

## Wave O outcome
- The multi-oracle conformance is in place. From now on, every test using
  `read_triangulated_ledger` will fail loudly if vpxdec and ffmpeg ever
  disagree on a vector — and that failure will explicitly NOT be blamed on
  our decoder.
- `foreman_c440.ivf` rvp9dec failure is now triangulated: confirmed our bug,
  no libvpx-quirk hiding behind it. The `#[ignore]`d follow-up test
  (`profile1_440_parser_desync_followup`) stands; diagnosis from Wave N
  (keyframe Y-mode parser at mi=(0,28) Block16x16) is correct.
- Future fixtures generated via `encode-corpus.ps1 -WithLedger` will get
  the cross-check for free.

**Headline:** "libvpx is the spec" was always a working assumption. With ffmpeg
as a second independent decoder, it's now a verified one — and one we'd catch
if it ever stopped being true. Cost: one PowerShell script + ~70 LOC of Rust
+ 7 small ledger files. Strong testability-multiplier per CLAUDE.md ("testing
oracles are the critical multiplier — without them, compute hours are worthless").
**Wave O CLOSED.**
