# 2026.05.27 — JRN — inter-frame drift fix (SEVERITY-1)

Finishing the drift-diagnosis agent's work (checkpoint 505c433). Goal:
drive the committed `drift_diag` oracle's STORED-recon-vs-true-decode SSE
to ~0 for every frame at both cpu-used 7 (RT) and cpu-used 4 (RDO), so the
encoder's stored reference == the true decode of its own bitstream (the
root cause of the 11-28 dB-below-libvpx compounding drift).

## Method

Used the committed `crates/rvp9-encoder/tests/drift_diag.rs` oracle as the
metric (encoder STORED + PRE-LF recon vs rvp9-decoder decode, per frame).
Localized divergences to the first diverging pixel/block, then to the exact
code path. Three distinct, independent bugs found — each fixed and verified
to collapse its divergence to 0.

## Root causes + fixes (all ENCODER-side)

### 1. KEYFRAME divergence (dominant, 3.18M SSE) — raster vs Z-order
`crates/rvp9-encoder/src/frame_loop.rs::leaves_from_decision` emitted
partition leaves in **raster order**, but the decoder reconstructs in VP9
**quadtree Z-order** (TL, TR, BL, BR). The intra-prediction simulator
reconstructs leaves in the leaf-vector order, so a bottom-right 32×32 leaf
was predicted before its bottom-left neighbour existed in the recon buffer
— its DC predictor averaged in 16 zero-initialised left-column samples,
producing a value ~19 below the decoder's (which sees the real,
already-decoded bottom-left edge). That seeded an intra-prediction cascade
across the whole lower-right of the keyframe (manifested as a contiguous
constant-19 region). Width-dependent: 256-wide partitions happened not to
trigger it; 320-wide did. **Fix:** recurse the partition tree in Z-order
(`walk` helper). All splat consumers are grid-based (order-independent), so
the emitted bitstream is unchanged — only the simulator reconstruction
order is corrected. → KF SSE 3.18M → **0** at both cpu4 and cpu7.

### 2. inverse-transform dispatch mismatch — scalar vs SIMD/eob-bucket
The encoder's IDCT-add helpers called the **scalar full** kernels
(`idct16x16_256_add`, …) unconditionally, while the decoder routes every TX
block through `SimdDispatch` with eob-bucketed fast paths
(`idct16x16_10_add`/`_38_add`, `idct8x8_12_add`, the `_1_add` DC paths, the
32×32 `_34`/`_135` sparse paths, and the dense SSE2/AVX2 kernels). The
sparse kernels are NOT bit-exact to the scalar full kernel (`idct16x16_38`
differs ±1/px). **Fix:** new `enc_inverse_transform_add` in
`crates/rvp9-encoder/src/lib.rs` mirrors the decoder's `inverse_transform_add`
exactly (same tx_type split, eob buckets, dispatch slots). The intra
simulator, `inter_inverse_dct_add`, and `intra_inverse_transform_add` all
delegate to it. (Not the KF root cause on foreman — those origin blocks
were eob=1 DC, bit-exact — but a real latent drift source for any TX block
whose eob lands in a divergent bucket.)

### 3. INTER divergence — per-block interp filter dropped by the writer
`crates/rvp9-encoder/src/frame_loop.rs::build_inter_mi_grid_from_picker`
(the mi-grid the bitstream **writer** reads) hardcoded
`interp_filter: EightTap`, ignoring each leaf's `picked_interp_filter`. The
frame-level filter is `Switchable`, so the writer serialised EightTap while
the encoder's MC simulator had already reconstructed the stored reference
with the PICKED filter (e.g. EightTapSmooth). The decoder reconstructed
with EightTap → diverged from the encoder's stored reference → compounding.
**Fix:** emit `leaf.picked_interp_filter` in both the single-ref and
compound arms. → inter frame 1 SSE 40k → **0** (256 and 320, cpu7).

## MC-border WIP (enc_build_mc_border) — KEPT
Assessed via drift_diag: every diverging inter block on foreman had an
in-bounds convolve footprint (no scratch fired), so the WIP is neutral for
this corpus — but it is the correct, gate-green mirror of the decoder's
`build_inter_predictor_with_mc_border` and is NECESSARY for any off-edge MV
(which other content/resolutions hit). Keeping it (not a red herring;
correct + required for robustness, just not exercised by this test).

## What remains (frame-2+ residual drift) — GOLDEN ref-index mismatch
Frames 0–1 are SSE 0; frame 2 onward still diverges (~2M, compounding).
Localized to GOLDEN-referencing blocks (ZeroMv-golden-skip diverges 1–3/px;
NewMv-golden integer-MC diverges more). Root cause is the writer's
`ref_frame_indices = [0, 0, 0]` in `encode_inter_internal`
(`frame_loop.rs`, the "A11 — every logical ref → slot 0" simplification):
it tells the DECODER that GOLDEN resolves to pool slot 0. But after frame 1
refreshes LAST (`refresh_frame_flags = 0x01`), pool slot 0 now holds
**frame 1**, while GOLDEN should still be **frame 0** (the KF; golden only
refreshes every `GOLDEN_REFRESH_PERIOD = 8`). Meanwhile the encoder's
picker/simulator predicts GOLDEN from `named_ref_planes(GOLDEN_REF)` (its
golden mirror = frame 0). So a GOLDEN-picked block: encoder reconstructs
from frame 0, decoder reconstructs from slot 0 = frame 1 → drift. This is a
ref_frame_map / refresh-rotation bookkeeping bug (A15 Phase B enabled
GOLDEN *picking* but the wire ref-index wiring still collapses GOLDEN→slot
0). Fix is to emit the correct `ref_frame_indices` for GOLDEN (the slot
actually holding the golden frame) and keep the encoder's golden mirror in
lock-step with that slot. Deferred here because it's a distinct ref-pool
subsystem change with byte-exact-gate risk, separate from the three
recon-kernel/order bugs fixed above.
