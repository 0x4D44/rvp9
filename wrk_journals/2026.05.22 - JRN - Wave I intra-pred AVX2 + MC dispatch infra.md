# Wave I — intra-prediction AVX2 family + MC dispatch infrastructure

Wave H closed the loopfilter + dequant frontier (25 of ~26 slots live).
The remaining two large scalar-only surfaces in the decoder hot path are:

1. **Intra prediction** — 10 modes × 4 sizes = 40 potential kernels;
   currently only `dc_predictor_4x4` has AVX2. Every other intra path
   (V, H, TM, D45, D63, D117, D135, D153, D207, plus DC for sizes
   ≥8x8 and the fallback DC variants) is scalar.
2. **Motion compensation 8-tap subpel filter** — `inter/filter.rs`
   hosts the convolve family (`convolve8_horiz`, `convolve8_vert`,
   `convolve_copy`, `convolve_avg`, plus scaled variants and bilinear).
   No dispatch slots exist at all — the call sites bypass
   `SimdDispatch` and call scalar directly.

Wave I tackles **non-directional intra modes (V/H/TM + DC family
extension)** and lays down the **MC dispatch infrastructure** so that
future MC AVX2 kernels (Wave J) can slot in without touching call sites.

Directional intra modes (D45/D63/D117/D135/D153/D207) and MC AVX2
implementations themselves are deferred to Wave J — they're lower
priority in real corpus (DC/V/H/TM dominate intra-block frequency)
and higher implementation cost per kernel.

## Operating principles

- **Size-parametric slots**: new intra slots take `(dst, stride, bs, …edge_slices)`.
  AVX2 impl dispatches internally on `bs` to size-specific code paths
  (4x4 → 4-byte stores; 8x8 → 8-byte stores; 16x16 → 16-byte stores
  via SSE; 32x32 → 32-byte AVX2 stores).
- **Conformance gate**: 201/0/0/0/201 at each commit.
- **Differential test 1024 iters** mandatory per kernel — scalar vs AVX2 bit-exact.
- **Tautology guard** per slot test (every new slot test must prove the AVX2 path actually fires when caps.avx2=true).
- **Worktree isolation per deliverable** with `git -C` discipline.
- **Sequential agent dispatch**: I1 → I2 → I3 → I4 → I5. I3/I4 could overlap
  with I1/I2 in theory but their `intra_pred.rs` router edits overlap, so
  serialize for safety.

## Sub-sequencing rationale

I1 first (V predictor) because it's the simplest — a sanity check on the
new size-parametric slot pattern. If anything is mis-shaped in the slot
signature design, V is the cheapest place to discover it.

I2 (H predictor) lands the slot pattern for "left-edge only" inputs.

I3 (TM predictor) is the arithmetic test — exercises saturated subtract +
broadcast accumulator. If TM lands clean, the pattern is solid.

I4 (DC family) consolidates: 4 closely-related variants share AVX2 code.
By I4 the dispatcher's `intra_pred.rs:720-773` router has settled into
the new shape and the encoder-team-safe scope is well established.

I5 (MC infrastructure) is the easiest wave-end task — pure slot wiring,
no new AVX2 kernel code. Lands cleanly and unblocks Wave J.

### I1 close-out @ `90ad858`

V_PRED size-parametric AVX2 kernel landed cleanly. Pattern shaping
choices that all of I2/I3/I4 inherit:

- **Single slot for all bs sizes**: instead of `v_predictor_4x4`,
  `v_predictor_8x8`, etc., one slot `v_predictor` takes `bs: usize`
  and the AVX2 wrapper dispatches internally to the matching wide-store
  width (4-byte, 8-byte, 16-byte, 32-byte). This is more compact than
  the per-size pattern used for `dc_predictor_4x4` (which stays as-is
  for the bs=4 fast path).
- **Scalar adapter rebuilds `PredCtx`** with empty slices for unused
  edges (V_PRED ignores `left`; H_PRED ignores `above`). Matches the
  existing `scalar_dc_predictor_4x4` style.
- **Router edit pattern**: change the existing scalar call in
  `intra_pred.rs::intra_predict` (around line 761-772) to
  `(dispatch.X_predictor())(...)`. The router already has `dispatch`
  in scope from its `dispatch: &SimdDispatch` parameter.

### I3 close-out @ `a2d46c6`

TM_PRED — the arithmetic test. The lane-unscramble gotcha for
`_mm256_packus_epi16` came up exactly as flagged in the brief: pack
interleaves the two 128-bit halves, so a 16-byte saturated result of
the un-clipped values needs a `_mm256_permute4x64_epi64(packed, 0xD8)`
shuffle (= `_MM_SHUFFLE(3,1,2,0)` over 64-bit lanes) to bring the low
bytes of each 128-bit half adjacent in the low 128 of the 256.

The arithmetic broadcasts `delta = left[r] - above_left` once per row,
widens `above[..bs]` u8→i16, adds, packs with unsigned saturation
(which IS the [0, 255] clip — the saturation directly implements the
scalar's `clamp(0, 255)`).

### I4 close-out @ `64b65ad`

DC predictor family extension. The most ambitious deliverable: 4 AVX2
kernels × 4 sizes each, all size-parametric. Strategy choice that
proved out:

- **Four NEW slots** (`dc_predict_full`, `dc_predict_top`,
  `dc_predict_left`, `dc_predict_128`) rather than reshaping the
  existing `dc_predictor_4x4` slot. Each new slot is size-parametric
  on `bs ∈ {4, 8, 16, 32}` and corresponds to one of the 4
  availability quadrants. The existing `dc_predictor_4x4` slot stays
  for the (bs=4, both-avail) fast path.
- **`dc_predict_with_availability` signature change**: function now
  takes `dispatch: &SimdDispatch` and routes through the 4 new slots.
  Grep verified no encoder caller (only `intra_predict` and one
  test) — Option A signature change was safe.
- **Sum reductions use `_mm{,256}_sad_epu8`** against zero: since
  unsigned bytes, SAD-vs-zero is the horizontal sum. One instruction
  for an 8-byte or 16-byte sum; two with a reduce for 32-byte or
  64-byte. DC value is `(sum + count/2) >> log2(count)` (count and bs
  always powers of 2 in VP9).

7 files changed, +1430/-14. The largest single Wave I commit by far —
warranted because the DC family is the most arithmetically structured
of the intra modes and the slot count tripled (existing 1 + new 4).

### Notable design points

1. **Size-parametric slots are the right shape for intra-pred**: the
   per-size pattern (DC 4x4 only) was right for the pilot but doesn't
   scale to 10 modes × 4 sizes = 40 kernels. One slot per mode with
   `bs: usize` runtime dispatch consolidates the dispatch surface
   while letting the AVX2 implementation specialise internally per
   size. Wave J's directional modes (D45/D63/D117/D135/D153/D207) will
   follow this pattern.

2. **Sum-reduction via SAD-vs-zero**: `_mm_sad_epu8(x, _mm_setzero_si128())`
   returns the horizontal sum of `x`'s 8 unsigned bytes in lane 0.
   Used by I4's DC variants for the `sum(above) + sum(left)` step in
   ONE instruction per 8 bytes (16 instructions for a 32-element sum
   reduction would otherwise take ~5 stages of `_mm256_hadd_epi32` /
   shuffle / extract). Saves measurable ALU work even on this not-very-
   ALU-bound path.

3. **TM_PRED's pack-lane unscramble** required `_mm256_permute4x64_epi64`
   after `_mm256_packus_epi16` — a non-obvious step that the brief
   pre-emptively documented and the agent verified empirically.
   Lesson: hard-won SIMD gotchas should be threaded INTO the agent
   brief, not left for the agent to rediscover.

4. **`inter_predictor` dsp::get() lookup** uses the H1 pattern verbatim
   — `let dispatch = crate::dsp::get();` once at function top, no
   public signature change, encoder caller unaffected. The pattern is
   now established and reusable.

5. **MC dispatch infrastructure as a Wave-end task**: I5 was the
   safest landing point because it's a pure refactor — no new AVX2
   kernels, no behaviour change, just dispatch surface preparation.
   Future AVX2 MC kernels (Wave J's hot work) can drop into the
   existing slots without touching call sites.

### Lessons captured (Wave I)

1. **Serialize agents touching the same dispatch surface, OR require
   them to fast-forward before working.** I3's worktree was based on
   pre-I1 main → 8 conflict regions on cherry-pick. I4 and I5 both
   fast-forwarded before starting → zero conflicts. Going forward,
   include `git fetch origin && git merge --ff-only origin/main` as a
   standard step in every agent brief that touches a shared file.

2. **Lane-interleave gotchas are worth documenting in the brief.**
   `_mm256_packus_epi16` interleaves 128-bit halves — non-obvious from
   the intrinsic name. Pre-documenting in the brief saved the I3 agent
   a debug cycle.

3. **MC dispatch is best landed as a pure refactor.** Wiring 8 slots
   without AVX2 impl is cheaper than wiring + implementing simultaneously.
   The implementation work has independent risk (subpel math, taps,
   rounding). Land the surface; iterate AVX2 in Wave J.

4. **Pre-existing test failures matter.** `pick_inter_mode_ctx_affects_rate`,
   `captured_header_round_trip`, and `write_compressed_header_captured_frame_round_trip`
   were failing on baseline (pre-Wave-I). I5's agent flagged them
   explicitly; this saved chasing red herrings. Each Wave's
   pre-commit checklist should include a "baseline reproduces failures"
   verification step.

### Wave J catalog (future direction — NOT in active scope)

Wave I closes the intra-pred non-directional family and the MC
dispatch infrastructure. Remaining DSP work:

- **Directional intra modes**: D45, D63, D117, D135, D153, D207 ×
  4 sizes = 24 kernels. Each mode has a 4x4 hand-unrolled special
  case (per libvpx) plus a generic `bs >= 8` form. AVX2 for these is

- **MC AVX2 kernels** (drop into the I5 slots): `convolve8_horiz_avx2`,
  `convolve8_vert_avx2`, etc. The horizontal 8-tap convolution is a
  classic AVX2 win — 16-lane i16 inner accumulation, single-shuffle
  filter row, single-store-per-row. Expected to be one of the largest
  hot-path wins for the decoder.
- **Scaled MC slots + AVX2** (`convolve8_scaled_*`): lower priority
  (only fires on actual frame resize / spatial SVC) but the slot
  pattern from I5 extends naturally.
- **vpxenc-gated items** still blocked: G5.3 corpus, G6.1, G7.1, G8.1.
- **The "smarter" dual loopfilter kernels** (process both halves in
  one 256-bit register vs the two-singles delegation): still optimisation-
  only, bit-exactness proven.
