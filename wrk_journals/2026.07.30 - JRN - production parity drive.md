## Unit 3 — portable fixed-Q reference harness

The E9 fixed-Q diagnostic silently skipped libvpx on macOS because it only
looked for `D:\language\libvpx-stock\vpxenc.exe`. It now prefers the repository's
approved `build/libvpx` tools, retains the known Windows locations, and finally
searches `PATH`. The sibling decoder derives the correct platform suffix.

Fresh pinned-reference E9 results at commit `79667d8`:

- Q80: rvp9 `40.50 dB / 28,540 bits`; libvpx `41.78 dB / 30,595 bits`;
  gap `1.29 dB`
- Q120: rvp9 `37.61 dB / 15,004 bits`; libvpx `39.23 dB / 15,602 bits`;
  gap `1.62 dB`
- Q160: rvp9 `34.50 dB / 7,678 bits`; libvpx `36.19 dB / 7,329 bits`;
  gap `1.69 dB`

This confirms a coding-efficiency gap independent of the VBR rate controller.
The product baseline also chooses intra prediction for `20.34%` of blocks at
250 kbps versus libvpx's `2.00%`, so the next single hypothesis is that the
real-time intra fallback over-selects intra blocks.

The existing `RVP9_RT_NO_INTRA_FALLBACK=1` diagnostic produced only small
fixed-Q gains:

- Q80 gap `1.25 dB` (`+0.04 dB`)
- Q120 gap `1.61 dB` (`+0.01 dB`)
- Q160 gap `1.64 dB` (`+0.05 dB`)

It lowered mode-syntax cost but worsened prediction PSNR and raised coefficient
bits, so it is not established as a Pareto improvement. Next: run the legacy
Stage 4a VBR curve with the diagnostic enabled. Reject it unless the curve-level
gain and timing justify a production policy change.
