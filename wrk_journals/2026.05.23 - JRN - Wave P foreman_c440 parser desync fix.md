# Wave P — foreman_c440.ivf parser desync (root-cause + fix)

**Date:** 2026-05-23
**Lead:** Claude (supervisor)
**Trigger (Arthur):** "We'd better go and fix the foreman_c440 followup bug, hadn't we?"
**Goal:** Resolve the foreman_c440 bug. Iterate until 100% resolved.

## Brief

From Wave N (triangulated by Wave O):

- `tests/corpus/profile1/foreman_c440.ivf` decodes byte-exact in libvpx-vpxdec
  AND ffmpeg-native-vp9 (triangulation says: the bitstream is well-formed and
  the libvpx ledger is authoritative).
- rvp9dec mismatches all 12 shown frames. Loop filter is innocent (frame 0 has
  `filter_level == 0`).
- Diagnosis from Wave N: keyframe Y-mode parser at **mi=(0,28) Block16x16**
  reads `y_mode = Dc` where libvpx reads a directional mode. From frame 0
  onward all 12 frames cascade-mismatch.
- Other 4:4:0 vector (`vp91-2-04-yuv440.webm`) decodes byte-exact — so the
  general 4:4:0 chain is sound; this is a syntax-combo our parser mishandles
  that the official vector doesn't exercise.
- Test gated behind `#[ignore = "pre-existing 4:4:0 keyframe parser desync at
  mi=(0,28) — see Wave N journal 2026-05-22"]` in
  `crates/rvp9-harness/tests/profile1_decode.rs` (function
  `profile1_440_parser_desync_followup`).

## Plan (live — updated as we go)

- **P1 — Locate the parser.** Find the keyframe Y-mode parser in
  rvp9-core/rvp9-decoder. Identify the context model (above + left neighbour
  prediction modes) and the probability table feeding the tree.
- **P2 — Snapshot the suspect block.** Build a one-shot diagnostic that dumps,
  for frame 0 of `foreman_c440.ivf`, the partition tree leading to mi=(0,28),
  the above/left neighbour modes our parser sees, the boolean-coder state
  before the tree-read, and the resulting `y_mode`.
- **P3 — Compare to libvpx.** Use the spec + (if needed) libvpx source we
  already have at `build/libvpx/` to identify the divergence (wrong context?
  wrong tree? wrong neighbour-default for out-of-frame? off-by-one in mi
  indexing for 4:4:0?).
- **P4 — Fix.** Smallest change that makes the diagnostic match libvpx.
- **P5 — Verify.** Re-enable the vector in `PROFILE1_VECTORS`, remove
  `#[ignore]`, run the full triangulated gate. All 12 frames must pass; no
  regressions on the other 6 oracle vectors or the official 201 corpus.

## Log

### P1 — Locate the parser ✓

**rvp9 side** (Explore agent):

- Keyframe Y-mode read: `D:\language\rvp9-2\crates\rvp9-decoder\src\tile.rs:1167`
  `read_keyframe_y_mode_traced`. Dispatches on block size (BLOCK_4X4 / 4X8 /
  8X4 / >=8X8), walks `INTRA_MODE_TREE` with
  `VP9_KF_Y_MODE_PROB[above_mode as usize][left_mode as usize]`.
- Neighbour-mode lookup: `above_block_mode` / `left_block_mode` at
  `tile.rs:1306` / `tile.rs:1331`; default to `IntraMode::Dc` when neighbour
  is `None`.
- Probability table: `VP9_KF_Y_MODE_PROB` at
  `crates/rvp9-core/src/entropy/kf_probs.rs:27`; shape `[10][10][9]`.
- Y-mode read itself is chroma-agnostic. Subsampling only affects coefficient
  context and reconstruction, NOT mode parsing.

**libvpx side** (Explore agent):

- `read_intra_frame_mode_info` at
  `third_party/libvpx/vp9/decoder/vp9_decodemv.c:192-233`. Identical shape.
- `vp9_above_block_mode` / `vp9_left_block_mode` at `vp9_blockd.c:13-35`.
  Default DC_PRED when neighbour is NULL (`above_mi == NULL` when
  `mi_row == 0`).
- `vp9_kf_y_mode_prob` at `vp9_entropymode.c:16-147`.

Mode-reading logic appears spec-faithful on both sides. Hypothesis: bug is
NOT in the y_mode tree-read; it's either (a) cursor-desync upstream
(segment_id / skip / tx_size / partition read consumed wrong bits earlier),
(b) wrong above/left context fed to the prob table, or (c) wrong block_size
at mi=(0,28). DC=mode 0 = first leaf in the tree, so any wrong-probability
path can plausibly land on DC — that's why the symptom is DC.

### P2 — Tracing inventory ✓

The decoder already has extensive env-var tracing (Wave M/N legacy):

- **`RVP9_TRACE_KFLEAF=1`** — per-mi cursor state at entry + per-syntax
  checkpoints (segment_id, skip, tx_size, y_mode, uv_mode) on every keyframe
  `decode_block`. **This is exactly what we need.**
- `RVP9_TRACE_KFSB=1` — per-SB cursor state.
- `RVP9_TRACE_PARTITION=1` — per-partition decision (first SB row only).
- `RVP9_TRACE_INTRA_AT="plane,x,y"` — per-TX intra-pred state.
- `RVP9_TRACE_FRAME=N` (via counter) — frame filter.

libvpx side has nothing comparable wired in (`CONFIG_BITSTREAM_DEBUG = 0`,
`CONFIG_MISMATCH_DEBUG = 0` in the current build); `vp9_print_modes_and_motion_vectors`
exists but has zero callers. A small libvpx patch is doable but a rebuild
is required — defer until we know we need it.

### P3 — Capture our trace at mi=(0,28) ✓

- Built rvp9dec; ran with `RVP9_TRACE_KFLEAF=1 RVP9_TRACE_KFSB=1
  RVP9_TRACE_PARTITION=1` → 24k lines → `notes/foreman_c440_kfleaf_frame0.log`.
- At mi=(0,28) entry: range=200 value=0x4100… count=1 pos=3585. y_mode read
  arithmetic-correctly produced DC from (range=146, value=0x0c00, p[0]=137).
- DC at the Y-mode root is forced by ANY plausible context probability when
  `value < bigsplit_min` (~0x1f00) — the value is too small for SPLIT under
  any 16x16 context. **Conclusion**: cursor is desynced upstream; not a
  wrong-context or wrong-probability issue at the y_mode read.

### P4 — Bisect with a libvpx mi-grid dump ✓

- Wired up `vp9_print_modes_and_motion_vectors` (already in libvpx, no
  callers) — opted for an inline patch in `vp9_decode_frame` instead
  (smaller diff). Gated by `RVP9_LIBVPX_TRACE_KFMI=1`. Rebuilt libvpx and
  vpxdec.
- Captured `libvpx_mi_dump.txt` for foreman_c440.ivf frame 0 (mi grid:
  sb_type, segment_id, skip, tx_size, y_mode, uv_mode).
- Wrote `scripts/compare_kfleaf_to_libvpx.py` to diff per-mi-owner cell.
- **First divergence: mi=(0,28).** libvpx sees sb_type=0 (Block4x4) with
  y_mode=7 (D207); rvp9 sees Block16x16 with y_mode=Dc. So the bug is
  upstream of the y_mode read — it's the **partition tree** at the
  Block16x16 level returning NONE where libvpx returns SPLIT.

### P5 — Bisect the partition cursor ✓

- The keyframe partition path had no trace; added `RVP9_TRACE_KFPARTITION=1`
  to `decode_partition` in `tile.rs` (mirrors the existing inter-frame
  trace).
- Added a parallel `RVP9_LIBVPX_TRACE_KFPARTITION=1` patch to libvpx's
  `read_partition` in `vp9_decodeframe.c`.
- Wrote `scripts/diff_kf_partition_cursors.py` to walk pre/post pairs in

- **First divergence: mi=(3,25) Block8x8 partition_pre.** Cursors agreed
  exactly through mi=(3,24) Block8x8 partition_post. So bug is inside the
  decode_block call for mi=(3,24).

### P6 — Bisect inside decode_block via libvpx token trace ✓

- Added `RVP9_LIBVPX_TRACE_KFTOK=1` to libvpx's `vp9_decode_block_tokens`,
  dumping `(plane, x, y, tx, a, l, range, value, count, pos)`.
- Compared rvp9's `kfleaf` plane/row/col entries with libvpx's `tok_pre`.
- Inside (3,24) Block8x8: agree on plane=0 Y Tx8x8 and plane=1 col=0.
  **DIVERGE** at plane=1 col=1: rvp9 has `above[49..50]=[1]`, libvpx has
  `a=0`. (Same for plane=2 col=1.) So the bug is in the chroma
  above-context: we have a stale `1` at x4=49 where libvpx has `0`.

### P7 — Trace back the stale context bit ✓

The chroma above-context at x4=49 for planes 1 and 2 should have been set
to 0 by the previous block in column 49 — which is mi=(2,24) Block4x8 with
`skip=true` (from libvpx mi grid). Looking at our `reset_skip_context` in
`crates/rvp9-decoder/src/tile.rs:886`:

```rust
let (n4_w, n4_h) = if sub8_luma && plane == 0 {
    (2usize, 2usize)        // Y: parent-8x8 extent (CORRECT)
} else {
    let plane_bsize = if plane == 0 { mi.block_size }
                      else { uv_plane_block_size(mi.block_size, ss_x, ss_y) };
    (plane_bsize.n_4x4_wide(), plane_bsize.n_4x4_high())  // Chroma:
                                                          //   sub-block extent (WRONG)
};
```

For (2,24) Block4x8 chroma in 4:4:0: `plane_bsize = Block4x4` → `n4_w=1`,
`n4_h=1`. So we only reset above_context[x4=48]; x4=49 stays at its
pre-existing value (1 from an earlier block).

**libvpx's `dec_reset_skip_context` resets `pd->n4_w` cells, where
`pd->n4_w` was set by `set_plane_n4(xd, 1, 1, 1, 1)` for sub-8 blocks
(triggered by the `if (!hbs)` branch of `decode_partition`):
`n4_w = (1<<1) >> ss_x = 2>>ss_x`.** So for chroma 4:4:0 sub-8 the libvpx
reset covers 2 cells (x4=48 AND x4=49).

Our iteration loop for sub-8 ALREADY uses `(2>>ss_x, 2>>ss_y)` (line 992)
— so the iteration and the reset are inconsistent. The reset needs to match.

### P8 — Fix ✓

One-liner-shaped fix in `crates/rvp9-decoder/src/tile.rs::reset_skip_context`:

```rust
// Before (D.15 era):
let (n4_w, n4_h) = if sub8_luma && plane == 0 {
    (2usize, 2usize)        // Y: parent-8x8 (correct)
} else { ... };             // Chroma: sub-block extent (BUG — too small)

// After (Wave P):
let (n4_w, n4_h) = if sub8 {
    (2 >> ss_x, 2 >> ss_y)  // ALL planes: parent-8x8, matches libvpx
} else { ... };
```

The chroma transform-iteration loop in `reconstruct_intra_planes` already
used `(2 >> ss_x, 2 >> ss_y)` for sub-8 (line 992) — so the reset and the
iteration were inconsistent. Fix makes them match.

## Wave P outcome

**The foreman_c440 parser desync is fixed. The fix is two LOC and is
arguably the deepest single-cell change of any wave so far — root cause
was 4 mi blocks upstream of the symptom, and required a libvpx mi-grid
dump (1 day of patch-and-rebuild) plus a partition-cursor diff to bisect.**

The bug was latent in any sub-8 block with `skip=true` in a 4:2:2 or
4:4:0 chroma format — but the official 201-vector corpus (Profile 0,
4:2:0 only) cannot exercise it, and the 4:4:0 official vector
(`vp91-2-04-yuv440.webm`) happens not to have a skip-true sub-8 block
adjacent to a column-2 same-row read pattern. Self-encoded vpxenc-default
streams DO exercise it routinely — hence why `foreman_c440.ivf`
surfaced it but the official vector didn't.

The triangulated oracle (Wave O) was instrumental: it let us assert
"libvpx is the spec" with full confidence before chasing the
divergence into our parser. Without ffmpeg as third oracle the
hypothesis "vpxenc/vpxdec quirk" would have stayed plausible and
delayed the diagnosis.

**Cost ledger**:
- 2 LOC of decoder fix
- ~60 LOC of new env-var trace in rvp9 (one new gate, mirrors existing
  inter-frame trace)
- 2 new Python diff scripts (~120 LOC total) — future-debug tooling
- ~200 LOC of libvpx diagnostic patches — applied, used, REVERTED
- 1 retired `#[ignore]`d test → 1 named fix-lock test

**Headline**: "It worked in the official corpus, broke in the wild" —
the official 201-vector corpus had no coverage of skip-true sub-8 blocks
in non-4:2:0 chroma. The triangulated 4:4:0 vector we added in Wave M
caught it. Without an oracle for self-encoded vectors, we'd have shipped
this bug.
