## Prior art

Commit `dc53545` (Tier 2) used a 3-way rotation for `prev_segment_ids` and
`last_frame_mi_grid` — at frame start `mem::take(&mut self.scratch_X)` →
clear + resize; at frame end `mem::replace(&mut self.prev_X, cur_X)` and
stash the OLD prev_X back into scratch_X.

That pattern can't apply to `cur_mv_grid` directly because the just-decoded
Vec gets wrapped in `Arc::new(cur_mv_grid)` and SHARED with up to 8
`mv_grids[i]` slots + `prev_frame_mv_grid` (`lib.rs:3064-3107` pre-wave-4).

## Approach: cur_mv_grid (commit 1fb62af)

Reuse the OLD `prev_frame_mv_grid` Arc via `Arc::try_unwrap` at frame END.
After the new Arc is published to `mv_grids[i]` ref slots (potentially
several `.clone()` calls), we `mem::replace(&mut prev_frame_mv_grid, new)`
to swap in the new Arc. The OLD Arc's strong count includes one reference
from each `mv_grids[i]` slot that still points at it (i.e. for which
`refresh_frame_flags` hasn't yet cycled past).

`Arc::try_unwrap` succeeds iff strong_count == 1, i.e. NO `mv_grids[i]`
still holds the Arc. With 8 ref slots and typical VP9 ref cycling, this
takes a few frames to converge; eventually the OLD Arc is exclusive and
recovery fires. The recovered Vec gets stashed in `scratch_mv_grid` for
next-frame reuse (clear + resize at intake).

Same recovery in the intra/keyframe path where `prev_frame_mv_grid` is
forcibly cleared to None (those frames produce no MVs to carry forward).

LOC: 72 insertions, 6 deletions on `crates/rvp9-decoder/src/lib.rs`.

## Approach: tile seg_id + mv_grid pools (commit 9e8d247)

The parallel-tile dispatch path constructs per-tile slot structs containing
`Mutex<Option<Vec<u8>>>` seg-ids and `Mutex<Option<Vec<PrevFrameMvRef>>>`
mv-grid Vecs, both pre-sized to `mi_rows * mi_cols`. Workers consume the
Vecs via the Mutex, write into them, then put them back; the merge loop
copies the per-tile rectangle into the frame-wide `cur_segment_ids` /
`cur_mv_grid` and drops the Vec.

Two new `Vec<Vec<...>>` pool fields on Decoder hold recycled Vecs. The
parallel path drains n_tiles Vecs at slot construction (clear + resize)
and pushes them back in the merge loop where the Vec is already in hand
after the rectangle copy. The Mutex stays — it's the sync primitive — but
the inner Vec is now pool-owned. Lazy growth to `max(n_tiles_seen)`,
zero allocator traffic in steady state, fallback (single-thread /
single-tile inline) path untouched.

LOC: 63 insertions, 8 deletions.

## Notes / risks

- **Two pre-existing test failures** unrelated to wave-4:
  - `rvp9-core sub_pixel_search_unsupported_block_size_panics_in_debug`
    (debug-mode `#[should_panic]` test, fails in release).
  - `rvp9-harness real_world_corpus_decodes_bit_exact` requires an altref-
    bearing fixture not present in the local corpus.
  - `rvp9-harness tile_scratch_pool_warm_no_alloc` (G5.2 oracle, fails
    when `Decoder::with_threads(2)` doesn't reach the parallel path on
    this host — likely a concurrent-test-interference flake).
  All three reproduce on baseline `cdcad98` — confirmed by stash/test cycle.

- **`Arc::try_unwrap` recovery rate** is not directly observable, but the
  perf delta proves it fires often enough to remove the allocation cost
  from the steady state. On streams where the LAST_FRAME slot churns
  every frame and other slots also rotate frequently, recovery converges
  within ~3-5 frames; testsrc_*/foreman-fp1 are exactly this shape.

- **Per-tile pool semantics**: re-using a Vec across frames keeps stale
  bytes from the prior tile / frame. Safe because (a) `clear + resize`
  re-zeroes the Vec on intake, (b) the merge loop only copies the tile's
  own rectangle into the frame-wide grid, so any out-of-range stale data
  in the per-tile Vec is unreachable. Same guarantee the existing G5.2
  Yv12ScratchPool relies on; documented inline.

  aren't tracked changes (they're test inputs); the worktree was set up
