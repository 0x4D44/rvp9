## What landed (commit 697384d)

`VbpThresholds::for_inter` ports libvpx `set_vbp_thresholds`' non-keyframe
branch (speed 7, all resolution bands, small-res `>200`/`>220`
threshold[2] boost). `choose_partitioning` now dispatches keyframe vs
inter; `frame_width`/`frame_height`/`avg_inter_qindex` threaded through
`PartitionSearchParams`. The avg-inter-qindex is the real RC EWMA (libvpx's
`avg_frame_qindex[INTER_FRAME]`), not a proxy.

Results:
- Foreman BD-rate **+395% → +367.8%** (+27 pp; real but modest).
- Inter 8×8 area **85% → 77.2%**; 64×64 ~unchanged at 0.2% (libvpx ≈79%).
- Cross-decode **BYTE-EXACT** (vpxdec + ffmpeg). 94 encoder + 32 core
  partition tests pass. Clippy clean on touched files.

This was a genuine bug (KF thresholds applied to inter; 16×16 split
threshold ~50× too low) and the fix is correct and on the critical path —
but it does not close the gap.

## Why it didn't close the gap (E2's honest finding)

The partition threshold only bites at moderate Q. On foreman the rate
controller **saturates Q at 255**, where even libvpx's *own* inter 64×64
threshold collapses to ~1 per-pixel-variance (split everything). The
difference is that **libvpx never reaches q=255**: it codes 143 kbps at
the 100k target while rvp9 codes 250 kbps. So the binding constraint is
the **bitrate overshoot itself**.

Root of the overshoot: **ineffective motion compensation.** rvp9 picks
**0% NEWMV** on foreman (E1 §3); it codes NEARESTMV/ZEROMV against a
LASTFRAME that, for panning/head-motion content, is a poor zero-motion
predictor. The residuals are genuinely large → high coding cost (→ bit
overshoot → q=255) AND high variance (→ partitions re-split regardless of
threshold). Both symptoms trace to the same cause.

This connects to **A18's orphaned observation** ("foreman never picks
NEWMV; prev_mv_grid stays all-zero"). At the time its *impact* wasn't
understood. E1+E2 now show it is central.

## Updated causal chain

```
no effective NEWMV / motion estimation
   → large ZEROMV/NEARESTMV residuals on panning content
      → (a) high bits  → bitrate overshoot → RC pushes Q to 255
      → (b) high variance → partitions split to 8×8 (independent of threshold)
         → q=255 makes partition thresholds collapse anyway
            → +368% BD-rate
```

The partition fix (E2) addresses one downstream branch. The trunk is
motion compensation.

## Next: Track E3 (task #64) — diagnostic

Localize *why* 0% NEWMV on foreman. Three hypotheses to discriminate:
1. **ME absent/not wired** — the full-pel motion search isn't run for
   foreman's block sizes / conditions in the inter picker.
2. **ME ineffective** — search runs but returns poor MVs (seed, range, or
   sub-pel issue), so NEWMV never beats NEARESTMV on RD.
3. **RD imbalance** — ME finds good MVs but the NEWMV MV-bit cost is
   weighted so heavily that NEARESTMV always wins the RD comparison.

Each implies a very different fix scope. E3 is diagnostic-only; its result
tells us whether the remaining gap is a tractable wiring/tuning fix (like
E2 was) or a genuine multi-week ME build.
