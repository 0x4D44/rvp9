# P21 — Pred-buffer reuse: analysis, SKIP recommendation

Inventory item: `wrk_docs/2026.05.24 - pick_inter_mode gap inventory.md:462`
("Pred-buffer reuse, ~30 LOC, Performance optimization, no quality impact").

libvpx reference: `third_party/libvpx/vp9/encoder/vp9_pickmode.c:2298-2306` and
`:2460-2466` (the `PRED_BUFFER` ring + `get_pred_buffer` / `free_pred_buffer`
calls inside `vp9_pick_inter_mode`).

## TL;DR

**SKIP.** rvp9's current allocation pattern is already structurally equivalent
to libvpx's `pred_buf` stack arena. libvpx's PRED_BUFFER ring exists to thread
the *best-so-far* prediction across candidates for downstream-encoder handoff
— a use case rvp9 does NOT have because the encoder rebuilds the prediction
from the picked `(mode, mv, filter)` tuple. Porting the ring would add
plumbing without a clear semantic or perf win. Recommend retaining stack
arrays and adding a comment to that effect IF a future regression points back
here.

## What libvpx actually does

`vp9_pick_inter_mode` (pickmode.c:1729-1730) declares the prediction arena on
its own stack:

```c
PRED_BUFFER tmp[4];                                       // 4 PRED_BUFFER
                                                          // structs (data ptr,
                                                          // stride, in_use)
DECLARE_ALIGNED(16, uint8_t, pred_buf[3 * 64 * 64] ...);  // 12 KiB stack
```

The three slots `tmp[0..2]` get pointers into `pred_buf`; `tmp[3].data` points
into the destination `pd->dst.buf` (the post-pick recon buffer).
`get_pred_buffer(tmp, 3)` (line 917) returns the first index in `[0,3)` whose
`in_use == 0` and marks it used. `free_pred_buffer` clears the `in_use` flag.

Usage at :2298-2306:

```c
if (reuse_inter_pred) {
  if (!this_mode_pred) {
    this_mode_pred = &tmp[3];                       // start in the dst buffer
  } else {
    this_mode_pred = &tmp[get_pred_buffer(tmp, 3)]; // grab a scratch slot
    pd->dst.buf = this_mode_pred->data;
    pd->dst.stride = bw;
  }
}
```

And at :2460-2466 the picker preserves the best candidate's buffer and frees
the loser's:

```c
if (this_rdc.rdcost < best_rdc.rdcost || x->skip) {
  ...
  if (reuse_inter_pred) {
    free_pred_buffer(best_pickmode.best_pred);     // last best loses its slot
    best_pickmode.best_pred = this_mode_pred;      // winner keeps its slot
  }
} else {
  if (reuse_inter_pred) free_pred_buffer(this_mode_pred);  // candidate loses
}
```

**The point of the ring:** at the END of `vp9_pick_inter_mode`, downstream
encoding (`set_ref_ptrs` + transform pipeline) reads the prediction pixels
out of `best_pickmode.best_pred->data` *without rebuilding them*. The ring
just keeps the winning prediction alive across iterations of the candidate
loop without overwriting it.

It is **not** a heap-allocation-avoidance optimisation. The arena itself is a
single stack array.

## Why rvp9's pattern is libvpx-faithful

libvpx's `pred_buf[3 * 64 * 64]` lives in `vp9_pick_inter_mode`'s stack
frame. rvp9 puts its equivalent buffer (`let mut pred = [0u8; 64*64]`) in
`evaluate_candidate_for_filter`'s stack frame — one level further down. Each
new candidate gets a fresh stack frame; each one re-overwrites the buffer
with the new prediction. Both compilers (libvpx's C; rustc/LLVM here) emit
the same lowering: a single `sub rsp, N` at function entry, no heap traffic.

The ONLY observable difference is the implicit zero-init that Rust's
`[0u8; N]` semantics require. For Block64x64 (`bw == bh == 64`) the entire
4096-byte buffer is overwritten by `build_inter_prediction` before any read,
so LLVM's dead-store elimination can drop the zero-init. For smaller blocks
(16×16, 32×32) only `bw*bh` bytes are touched, but the unread tail is also
never read (all consumers use `&pred[..bw*bh]` slicing or
`pred[(off_y+r)*bw + (off_x+c)]` indexing). LLVM is generally able to
recognise this and elide the zero-fill — but cross-function visibility may
limit how much.

A `MaybeUninit<[u8; 64*64]>` wrapping could guarantee no zero-fill but adds
`unsafe` and complicates the code for a sub-microsecond per-call saving that
is below the bench noise floor on the existing 9-fixture sweep.

## Why porting the PRED_BUFFER ring would not help

The ring's value in libvpx is **handoff to downstream encoding**: after
`vp9_pick_inter_mode` returns, the encoder reads pixels from
`best_pickmode.best_pred->data` without re-running interpolation. Skipping
the second MC pass is a real save — that's where the perf win lives.

rvp9's picker only returns RD scoring + the winning `(mode, mv, filter)`
tuple in `InterModeSearchResult` (no pixel buffer). The caller in
`frame_loop.rs` then rebuilds the prediction during the actual encode step.

For a faithful port of the libvpx perf win, the real work would be:
1. Add a `winning_pred: [u8; 64*64]` field to `InterModeSearchResult`
   (or thread an out-parameter).
2. Have the picker copy the winning candidate's prediction into it.
3. Have the encoder pickup path skip `build_inter_prediction` and read
   from that field instead.

That's a non-trivial cross-module refactor that touches:
- `InterModeSearchResult` struct (public-ish API)
- `PickInterModeResult`
- `frame_loop.rs` encode-block path
- All the test harnesses that consume the result

For an "estimated 30 LOC" inventory item flagged "low (perf)", this is well
out of scope. It would more sensibly be a separate, larger work item
("eliminate the redundant MC pass in encode_block") whose primary win is
NOT pred-buffer reuse — it is removing one full luma + chroma interpolation
pass per coded block.

## What about the `for filter in filter_set` loop?

`evaluate_candidate_with_filter_set` (line 2188-2214) iterates the two
filters `[EightTap, EightTapSmooth]` and calls
`evaluate_candidate_for_filter` for each. The pred / recon buffers are
re-allocated (stack-wise) per call.

Hoisting them up to `evaluate_candidate_with_filter_set` to be passed by
`&mut` would (a) save two stack-frame setups per candidate and (b) make
the elision pattern more obvious to LLVM. But:
- The save is on the order of `sub rsp, 0x2000` × 2 — a handful of cycles.
- We have a clear bench-driven Wave 4 win on heap allocs (-16.72%), and
  the perf headline gap is no longer in the encoder picker; the recent
  benches focus on the decoder loopfilter and IDCT paths.
- Adding `&mut` plumbing through 4 layers (`pick_inter_mode_luma` →
  `evaluate_candidate` → `evaluate_candidate_with_filter_set` →
  `evaluate_candidate_for_filter` → `reconstruct_via_round_trip`) is a
  visible API hit for an unmeasured saving.

## Recommendation

**SKIP** P21. Inventory checklist should mark it `LIBVPX-FAITHFUL EQUIVALENT
(stack arena)`, not `NOT PORTED`. The libvpx ring solves a problem rvp9
doesn't have (avoiding a second MC pass during encode); the underlying
allocation pattern (stack-resident arena) is already what rvp9 does.

If a future encoder profiling pass shows `evaluate_candidate_for_filter`
zero-fill as a hot spot, the surgical fix is `MaybeUninit<[u8; 64*64]>` at
the two `pred`/`recon` sites with a brief `unsafe { ... }` block — NOT a
full PRED_BUFFER ring port.
