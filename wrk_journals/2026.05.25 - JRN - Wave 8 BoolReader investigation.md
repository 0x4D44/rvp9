# Wave 8 — BoolReader re-evaluation (post-W1+W4)

**Date:** 2026-05-25 (closing session, after the perf drive that landed
W1 + W4)
**Author:** investigation agent (READ-ONLY on source; report-only)
**Scope:** re-evaluate the survey's "honourable mention" decision to skip
BoolReader optimisation, now that the frame is half the size and the
prob-table-locality wall argument from T-3 may no longer dominate.

---

## TL;DR — recommendation: **DEFER** (with one cheap measurement option)

The T-3 contrarian finding (HLD `wrk_docs/Track_T/T3_bitreader_phase2_HLD.md`)
still holds. The argument was never "locality wall"; it was four
concrete, technique-by-technique rejections:

1. **BMI2 BLSR/PEXT do not semantically slot into VP9's renorm** — wrong
   tools, not a "we didn't try hard enough" problem.
2. **SHLX/LZCNT are already used today** via `target-cpu=native` (LZCNT
   shipped in R.7; SHLX is the variable-shift LLVM emits for BMI2-capable
   targets).
3. **Inline-asm `read()` is 2-3 weeks and post-RA — LLVM register
   allocation should already do most of the work** for a 14-22 instruction
   loop. The defensive bet is "remove LLVM's discretion"; honest expected
   win 5-20% **on the kernel**, not on the frame.
4. **The R.15 precedent** (commit `4286269`): an `#[inline]` change to
   the full `fill` body — a much milder change than inline-asm — regressed
   testsrc_1080p30 t=4 by **23%** because of icache bloat. The bool-coder
   hot loop is icache-sensitive, and we have empirical evidence that
   touching it badly is catastrophic.

The post-W1+W4 frame budget moves a 7% kernel win on `BoolReader::read`
to ~1-2% on wall (see §5). Below the established bench noise floor.
Don't ship.

The only positive option is a one-shot **re-measurement** of `BoolReader`'s
*absolute* share of frame time using a `rdtsc`-instrumented decode (vs.
the T-3 baseline ledger's 4.45 ns/call microbench, which is a per-kernel
ruler, not a per-frame attribution). If the measured share is >15%, we
should reopen — but the rough arithmetic in §2-§5 below puts the upper
bound near 8% and the realistic mean near 4-6%. Not worth the wave slot
ahead of higher-EV candidates (#1, #2, #3 in the post-W1+W4 survey).

## 1. Where is BoolReader hot?

### 1.1 The kernel itself

Single file, single hot function: `D:\language\rvp9-2\crates\rvp9-core\src\entropy\bool_reader.rs:79-117`
(`BoolReader::read`). 25 lines of post-R.7 + post-R.8 + post-Phase 1
code. Per-call dispatch:

- `split = (range * prob + (256 - prob)) >> 8` — 1 IMUL + 1 ADD + 1 SHR (~4 cycles).
- `if self.count < 0 { self.fill() }` — branch predicted not-taken (~1 cycle).
- 8-byte register move + bigsplit shift + conditional update of `(value, range, bit)` — ~3 cycles, CMOV-able.
- LZCNT-based renorm shift via `((range & 0xff) as u8).leading_zeros() & 7` (R.7) — ~3 cycles LZCNT latency.
- 3 SHLs and the `count -= shift` — ~3 cycles.
- 3 writes back to `(value, count, range)` — ~3 cycles.

Total ~14-22 instructions, ~10-15 cycles latency on Arrow Lake-HX.

### 1.2 Hottest call sites

Two call sites consume virtually all of `read()`'s traffic per frame:

**(a) coefficient EOB / ZERO / token-tree** — `crates/rvp9-core/src/entropy/detokenize.rs`:

- `:532` — `reader.read(prob[EOB_CONTEXT_NODE])` (1 read per non-EOB coef + 1 per block).
- `:542` — `while reader.read(prob_local[ZERO_CONTEXT_NODE]) == 0` (1 read per coef in any zero-run; often 0-4 per coef).
- `:598-639` — `reader.read(prob_local[ONE_CONTEXT_NODE])` and the Pareto8 cascade (1-7 reads per non-zero coef).
- `:658` — `reader.read_bit()` for sign (1 per non-zero coef, max-entropy).
- `:296-302` `read_coeff_bits` — 1-14 reads per non-zero coef in CAT1..CAT6 extension.

Roughly **3-10 `read()` calls per non-zero coefficient**, plus 1 EOB-branch read per scan position visited.

**(b) read_tree** — `bool_reader.rs:163-172` — used by partition trees, intra mode, MV components. The token-tree walker for coefficients is *not* `read_tree`; the coef decoder hand-rolls the tree at `detokenize.rs:530-660` for the EOB-context fast path. So `read_tree` traffic is the header / MV / mode bits, smaller than coefficient bits by 1-2 orders of magnitude.

**(c) read_literal** — `bool_reader.rs:131-139` — header-only, sub-1% of frame time.

### 1.3 Auxiliary functions

- `fill()` (`bool_reader.rs:205-229`) — fires about once every 7 `read()` calls (after the value register drains). One u64 big-endian load + one shift after Phase 1 (R.8 + bddcc64); fully inlined.
- `fill_slow()` (`bool_reader.rs:240-259`) — `#[cold] #[inline(never)]` per Phase 1 design; only fires within 8 bytes of EOF. Not on the hot path.

## 2. How many BoolReader ops per frame?

### 2.1 The survey's "~50k tokens/frame" is a loose lower bound

The honourable mention says "tokens/frame ~50k". Let's tighten this.

At 1080p (1920×1080):

- 8×8 cells: 32 400 luma + 16 200 chroma (4:2:0) = **48 600 transform candidates**.
- Empirically, most 1080p coefficient blocks at moderate QP have eob in the **2-12** range (post-W1 EOB histogram in the IDCT sparse paths: ~80% of blocks at eob ≤ 16; ~50% at eob ≤ 4 on testsrc).
- Each non-zero coef → 3-10 `read()` calls (EOB + token-tree + sign + CAT extension bits).
- Each EOB-stopped coef position → 1 EOB `read()`.

**Estimated read() calls per frame (testsrc_1080p30):**

| Source | Count |
|---|---:|
| Coefficient EOB / ZERO / token-tree | ~200k-500k |
| MV components, mode bits, partition, segment ID, etc. | ~20k-50k |
| Header (per-frame, decode_compressed_header) | <1k |
| **Total** | **~250k-550k reads/frame** |

The survey's "50k tokens" is **per non-zero coefficient token**, not per `read()`. Each token expands to multiple `read()` calls. The corrected estimate is **5-11× higher**.

### 2.2 Frame-time share at 4.45 ns/call

T-3 baseline ledger (`wrk_docs/Track_T/T3_baseline_ledger.md`):
**4.45 ns/call median** for `BoolReader::read` over a synthetic 50/30/20
coefficient-like prob distribution on the same Arrow Lake-HX host.

- 250k calls × 4.45 ns = **1.11 ms**
- 550k calls × 4.45 ns = **2.45 ms**

Against the 3 256 µs post-W1+W4 wall-clock frame: **34% to 75% of the
frame**.

**That number is suspect**. The frame runs across 4 tile workers in
parallel, so the per-thread `read()` traffic is ~1/4 of the per-frame
total. Per-thread share: 8-19% of wall. That aligns much better with the
survey's "8-23%" honourable-mention estimate, and the upper bound is
about half of the survey's range.

### 2.3 Recalibrated honest estimate

- ~62k-138k `read()` calls per tile (one of 4 workers) per frame
- × 4.45 ns/call = **275-615 µs/tile worker per frame**
- Of which the tile worker's total `tile_decode` is 1 087 µs median (4 348 / 4).
- **BoolReader is therefore ~25-57% of *tile_decode* time** on testsrc_1080p30 t=4.

That share is high enough to matter on its face — but the relevant
denominator for "should we pursue?" is *wall-clock*, not tile_decode,
because tile_decode runs concurrent with the main thread's other work
and the critical path is actually loopfilter + join. See §5.

## 3. What does the T-3 finding actually say?

Source: `D:\language\rvp9-2\wrk_docs\Track_T\T3_bitreader_phase2_HLD.md`
+ ledger at `D:\language\rvp9-2\wrk_docs\Track_T\T3_baseline_ledger.md`
+ kickoff/close journals.

The finding is **specific, not general**:

> "BMI2 (BLSR / PEXT) is the wrong tool semantically. The renorm shift
> is `range <<= leading_zeros(range & 0xff)`, which has no
> 'lowest-set-bit' or 'masked-bit-extract' shape. SHLX (variable-shift)
> is already used by LLVM with `target-cpu=native`."

> "Inline asm could give 5-20% on the kernel, but the function is 14-22
> instructions and LLVM's register allocator should already do most of
> the work. Multi-week effort for a defensive-bet win."

> "Bulk `read_n` helps only `read_literal`, which is header-only and
> sub-1% of frame."

> "Algorithmic redesign breaks bit-exactness — non-negotiable."

The finding **does not** say "the prob-table-locality wall is the
floor". The survey's honourable-mention summary mis-attributes the
reasoning. The actual argument is *per-instruction-family*: none of
BLSR, PEXT, inline-asm, or bulk-read have favourable risk-adjusted EV
for *this specific* algorithm.

### 3.1 What changes post-W1+W4?

Two things in principle, neither materially:

**(a) Frame is 3× smaller.** True, but the *kernel*'s absolute speed
(4.45 ns/call) and the per-frame call count are unchanged (~250-550k).
The kernel's share of frame time *went up*, not down — but the
*absolute* µs/frame attributable to BoolReader didn't change.

**(b) Other bottlenecks are gone.** Mostly true (W1 cut IDCT, W4 cut
allocs). The remaining bottlenecks (LF ~55% of frame, tile imbalance
~35%) are both bigger targets than BoolReader.

The T-3 four-fold rejection is unchanged by W1+W4. The argument was
never about absolute frame share; it was about whether *any specific
technique* on the candidate list has favourable EV. Frame share doesn't
change the answer to "does PEXT help this renorm shape?"

## 4. What optimisations exist in libvpx that we don't have?

Source files inspected:
- `D:\language\rvp9-2\third_party\libvpx\vpx_dsp\bitreader.h:77-156`
- `D:\language\rvp9-2\third_party\libvpx\vpx_dsp\bitreader.c:21-100`
- `D:\language\rvp9-2\third_party\libvpx\vpx_dsp\prob.c:13` (`vpx_norm[256]`)

### 4.1 Side-by-side: libvpx vs rvp9-core

| Feature | libvpx | rvp9 | Verdict |
|---|---|---|---|
| BD_VALUE size | `size_t` (64-bit on x86_64) | `u64` fixed | **Same.** |
| `vpx_read` body | 14-22 instructions, branch on `value >= bigsplit` | Identical (line-for-line port) | **Same.** |
| Renorm normaliser | `vpx_norm[(unsigned char)range]` — 256-byte L1 table lookup | `(range & 0xff).leading_zeros() & 7` — LZCNT intrinsic (R.7) | **rvp9 is faster** by ~3 cycles per renorm (LZCNT ~1c throughput vs table-load ~4c). |
| fill() fast path | `memcpy(&nv, buffer, 8) + HToBE64(nv) + shift` — 1 load + 1 BSWAP | `u64::from_be_bytes(buffer[pos..pos+8]) + shift` — 1 load + 1 BSWAP (R.8) | **Same.** Identical codegen. |
| fill() cold path | inline in `vpx_reader_fill` | `#[cold] #[inline(never)] fn fill_slow` (Phase 1, commit `bddcc64`) | **rvp9 is faster** in steady-state (smaller icache footprint on `read` callsite — see commit `4286269` for the 23%-regression precedent). |
| `vpx_read_tree` | `while ((i = tree[i + vpx_read(r, probs[i >> 1])]) > 0) continue;` | Identical structural port at `bool_reader.rs:163-172` | **Same.** |
| `vpx_read_literal` | `for (bit = bits-1; bit >= 0; bit--) literal \|= vpx_read_bit(r) << bit;` | Identical port at `bool_reader.rs:131-139` | **Same.** |
| Platform-specific intrinsics | None. The bitreader.h hot loop is plain C; LZCNT/SHLX come from `-march=native`. | None at the source level. R.7's LZCNT is via `u8::leading_zeros()` which compiles to LZCNT on `target-cpu=native`. | **rvp9 is slightly ahead** — explicit LZCNT, libvpx still has the table-lookup. |
| Batched/SIMD reads | **None.** libvpx decodes one bit at a time per `vpx_read`. | **None.** Same. | **Same.** No path for SIMD batching exists in this algorithm — each read depends on the previous read's renorm output. |
| Branchless inner loop | **No.** libvpx has the `if (value >= bigsplit)` branch. | Same. | **Same.** Could in principle be CMOV-flattened (modern LLVM often does this anyway for small bodies — needs `cargo asm` to confirm). |
| Macro-fusion via `always_inline` | `static INLINE int vpx_read(...)` | `#[inline]` annotation | **Same**; both let the compiler decide and both inline at every callsite. |

### 4.2 Gaps where libvpx is doing something we aren't

**None of material consequence.** libvpx's hot path is *behind* rvp9-core's
in two places (renorm intrinsic; cold fill split). It is not ahead anywhere
in the bitreader.h hot loop.

The only "gap" is that libvpx has a `--enable-better-hw-compatibility`
option that does scalar-only paths for safety on ancient CPUs — irrelevant
to rvp9 (we target Sandy-Bridge+).

### 4.3 Anything in libvpx we should consider porting?

- `vpx_reader_find_end` (`bitreader.c:93-100`) — finds the true end of
  the bitstream by rewinding partial buffered bytes. Used by the partition
  decoder to learn where the next partition begins. We have an equivalent
  via `BoolReader::bytes_consumed`. **No gap.**
- Decryption callback (`decrypt_cb`, `decrypt_state`) — explicitly out
  of scope per entropy LLD §7.2. Not applicable.
- Bitstream-debug queue (`CONFIG_BITSTREAM_DEBUG`) — internal libvpx
  development aid. Already covered by our M.5/M.6 cursor diff infrastructure.

## 5. Realistic upper bound on perf gain

### 5.1 The arithmetic

Use the high end of the §2.2 attribution (615 µs per tile, in parallel
across 4 tiles).

The honest question is *which µs are on the critical path?* The
post-W1+W4 survey breakdown:

- Main thread serial: 3 256 µs wall = 85 + 16 + 1 131 (join) + 85 + 1 780 (LF) + 85 = 3 182 µs known + 74 µs unaccounted.
- Tile workers (parallel): 4 348 µs total, ÷ 4 ≈ 1 087 µs per worker = the join-time anchor.

`BoolReader` work happens **inside** tile_decode (parallel work). A 30%
kernel win → ~185 µs reduction per tile worker. The critical-path effect
depends on whether the slowest tile worker stops being the slowest:

- If tile workload is *balanced*: join time drops from ~1 087 µs to ~900
  µs, but the main thread is *also* waiting on LF (1 780 µs) which is
  not parallel. The slowest item on the critical path is LF — *not* the
  tile join — so the wall-clock effect of speeding up join is bounded
  by `min(join_drop, max(0, join_time - lf_time))`. With join = 1 131
  µs and LF = 1 780 µs, the join is *already* shorter than LF — so the
  tile work is *hidden* behind LF on the critical path.

That last bullet is the killer. Even **if BoolReader were 30% faster**,
the wall-clock savings would be **zero on the headline fixture**, because
tile workers finish before LF starts. The main thread already waits ~650
µs after tile-join for LF; making tile_decode faster just makes that
wait longer.

- If tile workload is *imbalanced*: P95 join = 3 513 µs (3.1× spread).
  In that case, the longest tile dictates wall time and BoolReader IS on
  the critical path of THAT tile. 30% on the slowest tile → ~185 µs off
  P95 wall. But P95 is not the headline; the median is.

### 5.2 Best-case wall-clock impact

Using the median attribution:
- BoolReader: 250-615 µs/tile worker (parallel).
- 30% kernel optimisation (per T-3 §3, optimistic for inline-asm
  excluding regression): **75-185 µs per tile worker**.
- Wall impact at median (tile work is already off critical path): **~0 µs.**
- Wall impact at P95 (slowest tile = critical path): **~75-185 µs out of 6 800-9 000 µs P95.**

That is **0-3% on median wall**, **1-3% on P95**.

### 5.3 Bench gate

The T-3 ledger's decision criterion (§"Decision criterion for Phase 2"):

> "Median ns/call on the same host drops by ≥10% (clear of the ~6%
> intra-run noise band with ≥4% safety margin)."

A 30% kernel win clears the microbench gate easily. The headline gate
(`decode-throughput on testsrc_1080p30 t=4 shows a directionally
consistent improvement`) is the killer: **at 0-3% wall-impact, the
bench is in the noise band** (~5% σ/μ on this fixture per T-3 §7), so
even a real kernel-level 30% win is *unprovable* at the wall level.

The T-3 power analysis: detecting a 5% wall-clock effect needs **n=25
runs per side**; 2% needs **n=150 per side**. Each run is ~30 min on
this fixture. Pinned-host CI does not exist; the bench would report
NOISE.

## 6. Final recommendation

### **DEFER.**

The T-3 four-fold rejection (BMI2 wrong tool, inline-asm low-EV-vs-effort,
bulk-read wrong hot path, algorithmic-redesign breaks bit-exact) is
**unchanged by W1+W4**. The kernel is already within 5% of libvpx's
post-`-O3 -march=native` codegen; we are ahead in two specific places
(LZCNT renorm, cold fill split) and behind nowhere.

The arithmetic in §5 is the killer for the new context: even an
ambitious 30% kernel optimisation lands in the **0-3% wall-clock band**
on testsrc_1080p30 t=4 because **tile_decode (where BoolReader lives)
already finishes ~650 µs before LF**, so wall-time is bounded by LF, not
tile_decode. The work is parallel-hidden behind the critical path.

Bench noise floor on this fixture is ~5% (σ/μ). A 0-3% win is below the
noise floor and below the T-3 ledger's "ship gate" (≥10% on the
microbench AND directionally-consistent wall improvement).

### The killer argument (one line)

**BoolReader work is on the parallel tile_decode path, which already
finishes ~650 µs before the serial loopfilter starts. Speeding up
tile_decode has zero wall-clock effect on the median frame.**

### What we should pursue instead

The post-W1+W4 survey #1, #2, #3 are all on the *serial* critical path
(LF setup hoist, tile imbalance / join tail, convolve8_horiz 256-bit
retry). All three have predicted wall-clock impact 5-25%, well above the
noise floor. BoolReader doesn't make the top 3 because of *where* it
lives in the dependency graph, not because of *what* the kernel costs.

### Optional cheap measurement (if you disbelieve §5)

Add an `rdtsc`-style cycle counter wrapper around `BoolReader::read` in
the tile workers (gated by a `--features profile-boolreader` flag in
`rvp9-decoder`) and run on the headline fixture. Cost: ~30 LOC of
instrumentation, one bench run. If measured share of *wall* time
(NOT of `tile_decode`, which is parallel) is >10%, reopen this. The
prediction from §5 is the answer will be <5%.

But honestly: don't even do this measurement. The structural argument
("parallel work hidden behind serial LF") is what dominates, and that
holds whether the kernel is 5 ns/call or 50 ns/call. Spend the slot on
LF-prereq decoupling instead.

## Appendix B — what we did NOT do (and why)

- **No `cargo asm` disassembly run.** Would show whether LLVM is CMOV-ing
  the `if value >= bigsplit` branch. Useful to know but not load-bearing
  for the DEFER conclusion — the kernel is already within 5% of libvpx
  per T-3, and the §5 arithmetic doesn't care about CMOV-vs-branch at
  the wall-clock level.
- **No fresh microbench run.** The T-3 ledger from 2026-05-24 on the
  same host is canonical. The kernel was not modified between then and
  now. (Verified via `git log -- crates/rvp9-core/src/entropy/bool_reader.rs`:
  no changes since `bddcc64` Phase 1, all post-baseline commits are in
  unrelated files.)
- **No rdtsc instrumentation.** §5's structural argument
  (parallel-hidden-by-LF) makes the measurement redundant.

## Appendix C — if a future agent disbelieves the DEFER

The single bit of evidence that would flip this is **wall-clock benchmark
data showing testsrc_1080p30 t=4 frame time dropping by >5% after a
BoolReader change**, surviving 5 independent re-runs at p<0.05. None of
the analytical arguments here would survive that data. Until that data
exists, DEFER is the responsible call. The T-3 ledger's gates apply.
