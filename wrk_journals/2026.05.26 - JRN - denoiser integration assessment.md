# 2026.05.26 — JRN — W5 denoiser integration assessment

**Verdict: ARCHITECTURALLY BLOCKED (for the requested simple post-reconstruction pass).**
No code changes were made. The cross-decoder gate stays green because nothing
touched the hot path. This journal records the precise constraint and the
libvpx-faithful alternative so a future wave can pick it up with eyes open.

## Task recap

Wire the W5 temporal denoiser (`crates/rvp9-encoder/src/denoiser.rs`, standalone
since commit d80c545) into `StreamEncoder::encode_frame`. The suggested simple
integration: run the denoiser as a post-reconstruction pass on `last_recon_*`
when `noise_sensitivity > 0`, so the next inter frame references denoised pixels.

The task explicitly required: assess honestly whether denoising the reference
desyncs encoder/decoder; if it does, DO NOT force it — document the constraint
and make no gate-breaking changes.

## The architectural constraint (why the simple pass desyncs)

### What libvpx actually does

In libvpx the denoiser does **not** denoise the reconstructed reference pool. It
maintains a *separate* buffer family, `VP9_DENOISER::running_avg_y[]`
(`vp9/encoder/vp9_denoiser.h:46`), distinct from the codec's reference
reconstruction pool `cm->frame_refs[]` / `cpi->ref_frame_map[]`.

Data flow, per-block, during the RT pickmode:

1. `vp9_denoiser_denoise` (`vp9_denoiser.c:336-437`) runs the two-pass NLM
   filter and, on `FILTER_BLOCK`, copies the filtered running-avg window back
   **into the MACROBLOCK source plane** (`src.buf`), not into a reference:
   - `vp9_denoiser.c:425-428` — `FILTER_BLOCK`:
     `vpx_convolve_copy(avg_start, ..., src.buf, ...)`. The denoised signal
     replaces the *source* the encoder then codes against.
2. The denoised running-avg buffers become the *motion-estimation predictor*
   for the next frame: `perform_motion_compensation` points
   `filter_mbd->plane[0].pre[0].buf` at `running_avg_y[frame]`
   (`vp9_denoiser.c:294-304`) and re-runs the inter predictor into
   `mc_running_avg_y`.
3. The running-avg slots are rotated to track LAST/GOLDEN/ALTREF in
   `vp9_denoiser_update_frame_info` (`vp9_denoiser.c:464-524`,
   `copy_frame`/`swap_frame_buffer` at lines 439-462).
4. Caller: `vp9_pickmode.c:2677-2696`, gated on
   `cpi->oxcf.noise_sensitivity > 0`.

Crucially: the **residual-coding reference** and the **bitstream-committed
reconstruction** still come from `cm->frame_refs[]` — the genuine decoded
frame. `vpxdec` reproduces that exact reconstruction from the bitstream. The
denoiser biases *motion search and the source being coded*, never the reference
pixels the decoder adds residuals to. Encoder and decoder never diverge.

### What rvp9's architecture does

rvp9 has **one** reference buffer per ref slot, used for BOTH motion search AND
residual prediction. There is no separate ME-only buffer analogous to libvpx's
`running_avg_y[]`.

- `StreamEncoder::last_recon_{y,u,v}` (`frame_loop.rs:385-389`) is the single
  LAST reference.
- `encode_frame` → `encode_inter_internal` passes it as ONE tuple into the
  picker/simulator: `frame_loop.rs:1244`
  `(&self.last_recon_y, &self.last_recon_u, &self.last_recon_v)`.
- Inside `pick_and_simulate_inter_encode_partitions` (`lib.rs:2319`) that same
  `last_recon_yuv` is:
  - the ME-search reference: `lib.rs:2454`
    `let ref_y = PlaneRef { data: last_recon_yuv.0, ... }`, and
  - the residual-prediction reference for the actual recon write-out:
    `lib.rs:4466-4468`
    `(0, _) => (input_yuv.0, last_recon_yuv.0, &mut *recon_yuv_out.0)`.
- The resulting `new_recon_*` is committed verbatim as the next LAST ref:
  `frame_loop.rs:1456-1458`.
- The cross-decoder invariant is explicit at `frame_loop.rs:1284-1288`: LF runs
  on the recon *before* committing to `last_recon_*` "so the next inter frame's
  reference is the post-LF pixels — same as the decoder's pool." The decoder
  rebuilds these exact pixels (IT-add + LF on the bitstream residuals added to
  its own LAST ref, which equals `last_recon_*` byte-exactly).

### The desync

If we denoise `last_recon_*` after LF (the requested simple post-reconstruction
pass), then for frame N+1:

- The ENCODER predicts/codes residuals against **denoised** pixels.
- The DECODER has no denoising step (it is not, and cannot be, in the
  bitstream) — it adds those residuals to the **un-denoised** reconstruction it
  rebuilt from frame N's bitstream.
- `pred_enc != pred_dec` ⇒ `recon_enc != recon_dec` ⇒ drift accumulates ⇒
  cross-decoder gate (`tests/cross_decoder_gate.rs`) FAILs (vpxdec diverges or
  the stream becomes undecodable).

This is the non-negotiable failure the task warned about. The simple pass is
exactly the desyncing operation.

## Could it be wired gate-safe? (the libvpx-faithful path)

Yes — by mirroring libvpx: make the denoiser affect ONLY the ME-search
reference, never the residual-prediction reference. Concretely that needs a
*second* reference buffer threaded through the picker:

1. Add `denoised_ref_{y,u,v}` to `StreamEncoder`, allocated iff
   `noise_sensitivity > 0`, holding the per-frame denoised running-avg.
2. Split the single `last_recon_yuv` picker argument into a `me_ref` (denoised,
   for `find_mv_refs` + `single_motion_search`) and a `pred_ref` (the true
   `last_recon_*`, for residual prediction and the recon write-out). This
   touches every inter call site in `lib.rs` (lines 2454, 3096-3097, 3696-3697,
   3818-3819, 4033-4034, 4087-4088, 4466-4468) plus the
   `pick_and_simulate_inter_encode_partitions` signature.
3. Run the per-block denoiser driver during the pick loop (where the picked MV
   and SSE context exist to populate `DenoiserBlockCtx`), not as a post-pass.

This keeps the gate green (the committed reference and bitstream are untouched;
only MV *selection* may differ). But note the consequences:

- The PROOF the task asked for ("noise_sensitivity>0 produces a *different
  reference* than =0") is **not achievable** in this design — by construction
  the reference pixels are identical; only the chosen MVs (hence residuals/bits)
  may differ. The honest PROOF would be "different MV picks / different coded
  bits, output still decodes byte-exact."
- It is an invasive, multi-call-site refactor of the inter picker plumbing — a
  full wave of its own, not the smallest-change post-recon pass described in the
  task. Forcing the simpler pass to land "something" would break the gate;
  doing the faithful version is a real picker-plumbing project that should be
  scoped and discussed (it changes mode-decision behaviour, so it needs its own
  BD-rate / quality validation, not just the cross-decoder gate).

Per the task's own instruction — "If denoising the reference necessarily
desyncs encoder/decoder in rvp9's current architecture: DO NOT force it" — and
the global CLAUDE.md guidance to discuss architectural decisions before
invasive refactors, I am stopping here with the assessment rather than landing
either the desyncing pass or a half-wired second-reference refactor.

## Decision

- **No code changes.** `denoiser.rs` stays standalone; the hot path is
  unchanged.
- Cross-decoder gate verified GREEN before this assessment
  (`cargo test -p rvp9-encoder --test cross_decoder_gate -- --ignored` →
  4 passed; `cross_decoder_gate_vpxdec_ffmpeg` = PASS, byte-exact vs vpxdec).
- Lib tests GREEN: 409 passed, 1 ignored.

## Recommended follow-up (if denoiser ME-bias is wanted)

Scope a dedicated wave "W5.5 — denoiser ME-reference plumbing": add the second
(denoised) reference buffer, split `me_ref`/`pred_ref` through the inter
picker, run `vp9_denoiser_denoise` per-block inside the pick loop, and validate
with (a) cross-decoder gate byte-exact, (b) a BD-rate sweep showing the
ME-bias's quality effect. The standalone `denoiser.rs` API
(`Denoiser::alloc`, `vp9_denoiser_denoise`, `DenoiseBlockInputs`) is already
shaped to slot into that pick-loop call site without modification.
