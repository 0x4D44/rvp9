# Journal: convolve8_horiz_avx2 optimization drive

**Date opened:** 2026-05-27
**Driver:** Arthur (supervisor: Claude as PM, agents do the legwork)

## Background

Completed the full kernel audit (rvp9 vs libvpx, 17 kernels, all bit-exact,
pinned CPU0 min-of-5). Findings written to
`notes/decoder-libvpx-kernel-audit.md` and CSV at
`bench/results/kernel-audit-fullmap-2026-05-27.csv`.

**Headline:** `convolve8_horiz_avx2` is the #1 optimization target by a
wide margin — **9.39× slower than libvpx at 16×16** (168.1 ns vs 17.9 ns).
The vertical pass is near-parity (1.17–1.85×), confirming the asymmetry
is intrinsic to rvp9's *horizontal* AVX2 path. Since 2-D path = horiz +
vert, fixing horiz also closes the 2-D gap (currently 2.65–8.92×).

Goal of this drive: bring rvp9 `convolve8_horiz` AVX2 to within ~1.2× of
libvpx, gated by the existing bit-exact harness.

### 2026-05-27 — Implementation agent — kernel landed, parity met

**Step 1 — baseline (-Runs 3, affinity 0x1, this host):**
- `convolve8_horiz_halfpel 16x16` → 140.5 ns / 15.7 ns = **8.96×**
- `convolve8_horiz_halfpel 64x64` → 788.5 ns / 209.8 ns = **3.76×**
- `convolve8_2d_halfpel  8x8 / 16x16 / 32x32 / 64x64` → 8.94× / 6.52× / 3.51× / 2.55×
- All hashes match. Baseline reproduces the audit's headline within run noise.

**Step 2 — 128-bit → 256-bit ops (kept scratch buffer, 2 rows / pair):**
- Added `convolve8_8x2` (256-bit twin of `convolve8_8`), `tap_pair_256`,
  `bcast_mask` (broadcasts a 128-bit shuffle mask to both lanes since
  `_mm256_shuffle_epi8` indexes per-lane).
- Outer loop now iterates pairs `(y, y+1)` with row `y` in the low lane
  and row `y+1` in the high lane via `_mm256_inserti128_si256::<1>`.
  Odd-`h` tail processed via the old 1-row 128-bit path.
- Result: **16x16 8.96× → 6.08×**, **64x64 3.76× → 2.53×**, all bit-exact.
  Scratch-copy overhead became the dominant cost — confirmed expected.

**Step 3 — caller-contract audit + scratch elimination (non-tail rows):**
- Caller contract (documented + `debug_assert`'d): `src.len() >=
  (h-1)*src_stride + w + 7`. A 16-byte load at column `w-8` of row `r`
  reads up through `r*src_stride + w + 7`. For `r < h-1` that's
  guaranteed in-bounds (next row's data follows); only the **last
  row** can OOB by one byte.
- Restructured the kernel: bulk 2-row 256-bit loop reads directly
  from `src` while `y + 2 < h` (both rows of the pair are non-last).
  The remaining 1–3 rows are processed via the 1-row 128-bit
  `process_row` helper — direct read for any non-last row, scratch-
  staged read for the last row. The scratch is now allocated once
  per call (only when needed) rather than per row.
- Result with `-Runs 5`:
  - `convolve8_horiz_halfpel 16x16` → 21.04 ns / 15.11 ns = **1.39×**
  - `convolve8_horiz_halfpel 64x64` → 255.67 ns / 207.50 ns = **1.23×**
  - `convolve8_2d_halfpel  8x8` → 41.46 / 17.08 = **2.43×**
  - `convolve8_2d_halfpel 16x16` → 71.83 / 36.74 = **1.96×**
  - `convolve8_2d_halfpel 32x32` → 146.07 / 114.10 = **1.28×**
  - `convolve8_2d_halfpel 64x64` → 511.65 / 417.55 = **1.23×**
- All hashes match. **Goal of ≤1.5× on horiz 16×16 met (1.39×).**

**Step 4 — coverage hardening:**
- Added `differential_odd_and_narrow_shapes` test:
  - `(8, 4)`, `(8, 5)` — exercises the 2-row pair loop with small w
  - `(16, 15)`, `(32, 33)` — odd `h`, both pair loop + 1-row tail
  - `(32, 32)` — wider square (multi-inner-iter pair loop)
  - `(4, 1)`, `(8, 1)`, `(16, 1)` — `h == 1`, zero pairs, tail only
  - 4 kernel tables × 4 sub-pel rows per shape = 128 differential
    checks; passes against the scalar reference.
- The existing `differential_all_filters`, `tautology_guard_avx2_path`,
  and `dispatch_round_trip` tests still pass unmodified.

**No hash mismatches observed at any step.**

**Residual gap:** `convolve8_2d_halfpel 8x8` and `16x16` still sit
above the horiz-only ratios (2.43× / 1.96×). The 2-D kernel composes
horiz + vert through a `[u8; INTER_STRIDE * 72]` intermediate
(`convolve8_avx2.rs`). For small `w`, the horiz path is now fast but
the vertical path keeps a meaningful constant cost (vert ratios are
1.83× at 16×16 and 1.15× at 64×64 — the vert kernel is the next
lever). The 8×8 case in particular exercises 15 horiz rows and 8
vert rows with non-trivial per-call dispatch cost. Out of scope for
this drive (the brief was the horizontal kernel and the 16×16 target
is met by a wide margin).

### 2026-05-27 — Code review (REQUEST-CHANGES)

Reviewer agent flagged one real correctness regression and a coverage
gap, plus several quality suggestions.

**Blockers:**
- **B1.** Pair-loop direct read OOBs on `w == 4` with tight `src_stride`.
  Doc/code formula `r*src_stride + (w-8) + 15 = r*src_stride + w + 7`
  only holds when `w >= 8`. For `w == 4`, max-read byte is
  `r*src_stride + 15` (4 bytes past contract). Concrete OOB:
  `(w=4, h=5, src_stride=4)` overruns by 1 byte. The `debug_assert`
  only enforces the scalar contract, so any future caller honoring it
  can hit this. Likely never triggered in production (frame-stride
  callers have plenty of slack), but it's a contract regression — the
  AVX2 kernel is no longer a strict drop-in for the scalar.
  **Fix:** gate the pair loop on `w >= 8` (one-token change; `w == 4`
  is already routed through the 128-bit tail anyway, gains nothing
  from the pair loop).
- **B2.** `differential_odd_and_narrow_shapes` doesn't cover the OOB
  case — all (4, _) shapes have `h == 1` (tail-only). Add a case with
  tight `src_stride` after B1 lands.

**Suggestions to take (selected):**
- S1: update pair-loop safety comment to state `w >= 8` precondition.
- S2: extend `debug_assert` (or add a second one) to reflect the
  AVX2 kernel's actual footprint.
- S6: refresh module doc's "Aligned-load discipline" — most loads
  are now direct, not from scratch.

**Suggestions deferred (nits):**
- S3 (tail-loop comment phrasing), S4 (`store_row_8` name), S5
  (`broadcastsi128` vs insert+cast). Not blocking; defer.

**Reviewer confirmed correct:** 256-bit math regroup, rounding-bias
placement, saturation order, packus lane behavior, filter-tap
broadcast, `target_feature` discipline, dispatch wiring, existing
test surface (`differential_all_filters`, `dispatch_round_trip`).

### 2026-05-27 — Apply-feedback agent — blockers + selected suggestions landed

**Scope:** only `crates/rvp9-core/src/dsp/x86_64/convolve8_horiz_avx2.rs`
+ this journal (multi-agent checkout discipline).

**Edits applied:**
- **B1** — Pair-loop entry guard widened from `while y + 2 < h` to
  `while y + 2 < h && w >= 8`. For `w == 4` the loop is now skipped
  entirely; all four rows of a `(w=4, h=*)` block fall to the
  single-row 128-bit tail, which already supports `w == 4` cleanly
  (via `_mm_cvtsi128_si32` + `write_unaligned`) and stages the last
  row through the zeroed `[u8; 80]` scratch. Closes the contract
  regression: the AVX2 kernel is once again a strict drop-in for the
  scalar's `(h-1)*src_stride + w + 7` footprint.
- **S1** — Pair-loop safety comment now states `w >= 8` precondition
  explicitly and names the `w == 4` over-read in plain prose, so the
  next reader of this code sees the constraint without having to
  rederive it.
- **S2** — Added a width assertion:
  `debug_assert!(w == 4 || w == 8 || w == 16 || w == 32 || w == 64)`.
  The inner column loop steps `x += 8`; all wider widths must be
  multiples of 8 so the step lands on `x == w`. VP9 block widths
  satisfy this. Catches future callers that pass e.g. `w = 12`,
  which would currently silently write garbage past column 8.
- **S6** — Module-doc "Aligned-load discipline" paragraph rewritten
  to call out both the direct-from-`src` loads (pair loop and the
  non-last-row tail) and the scratch-staged loads (last row, and
  for `w == 4` every row whose tail read would otherwise escape).
- **B2** — `differential_odd_and_narrow_shapes` extended:
  - Shape tuple widened to `(w, h, src_stride)`; `src_stride == 0`
    keeps the original randomized-slack behavior, `> 0` pins a
    tight stride.
  - Added regression-guard cases: **`(4, 6, 4)`** (the exact shape
    that pre-fix overran by 1 byte at row 3), **`(4, 2, 4)`**
    (minimal tight-stride `w == 4` with `h >= 2`), **`(8, 5, 8)`**
    (tight stride at the next-narrower width), **`(16, 8, 16)`**
    (tight stride at `w == 16` — exercises the pair loop's
    right-edge load, which is safe by contract). All allocate
    `src` to **exactly** `(h-1)*src_stride + w + 7` bytes so any
    over-read trips a Vec OOB (MIRI) or reads adjacent heap.
  - Failure message now includes `src_stride` so failures bisect
    by stride too.
