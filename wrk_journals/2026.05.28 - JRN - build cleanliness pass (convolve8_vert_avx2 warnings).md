## Finding 1 — one real compiler warning (investigated, not suppressed)

`cargo build -p rvp9-core` emitted exactly one warning:

```
warning: unused imports: `_mm256_castsi128_si256`, `_mm256_castsi256_si128`,
         `_mm256_extracti128_si256`, and `_mm256_inserti128_si256`
  --> convolve8_vert_avx2.rs:76
```

**Investigation.** These four 256-bit lane-manipulation intrinsics are
*exactly* the ones the journal's optimization plan (Steps 2 & 3) and the
module doc (lines 20–52) describe for the **pair-row `s32b` topology**
(`inserti128` of two adjacent 128-bit row halves into one 256-bit
register). That topology was **never implemented** — the code that
landed took the simpler Step-1 route: a 256-bit sliding window over
*full* 256-bit row loads (`r[0..8]`), 2 output rows per iteration, no
`s32b` packing.

So the warning is not a bad merge and not a defect in working logic —
it is **speculative imports left over for code that was planned but not
written**, plus a knock-on **documentation defect**: the module doc and
the inner-loop tail comment described an implementation that doesn't
exist (`s32b` / `ss_lo` / `ss_hi`, "gw==16/8 256-bit pair-row path").

**Decision.** Do *not* implement the full pair-row optimization here —
that is net-new, bit-exact-gated feature work belonging to the active
supervised drive. Instead make the tree honest:
1. Remove the four speculative imports (not dead-code suppression — the
   code that would use them isn't being added).
2. Rewrite the `## Algorithm` / `## Bounds` module doc to describe the
   *actual* two-tier implementation (256-bit sliding window for
   `w-cg>=32`; 128-bit per-row path for the `cg<w` remainder), and note
   the pair-row port as explicit future work.
3. Clean up the rambling, self-doubting tail comment that ended with
   "so… hmm, actually the check needs to be… Let's be conservative" —
   replaced with a correct, concise invariant description. (The code was
   already correct: the odd-`h` tail unconditionally re-primes the
   trailing register `r[7]` before use, so the suppressed speculative
   load is harmless.)

## Correctness check (the logic itself)

Traced the 256-bit sliding window for the bound contract (last loadable
row = `h+6`):
- Priming loads rows `0..=7`; for all `h>=1`, row 7 <= `h+6`. ✓
- Pair loop (`while y+1<h`): first slide loads row `y+8`, max at
  `y=h-2` → row `h+6` (exactly the contract edge). ✓
- Second slide loads row `y+9` only when `y+3<h` → max `h+5`. ✓
- Odd-`h` tail re-primes `r[7]=row y+7`, max at `y=h-1` → row `h+6`. ✓

Max row touched = `h+6`, matching the documented footprint. No OOB.

## CORRECTION (2026-05-28, later) — multi-agent collision discovered

The narrative above (Findings 1–3) describes my *intent*, but it is not
what actually landed. After committing I found the working tree had
moved underneath me:

- A **concurrent agent** (Arthur's Step-2/3 implementation agent from
  the `2026.05.27 - JRN - convolve8_vert_avx2 optimization drive`) was
  writing the **pair-row optimization into the same file in the shared
  working tree** during my session. Its own journal even refers to my
  edits as "a format-on-save / `cargo fix` pass [that] tidied the
  recon's uncertain tail comment and removed its unused imports."
- My `cargo fmt -p rvp9-core` reformatted **119 unrelated files**
  (the crate was not rustfmt-clean under rustfmt 1.95.0). All were
  clean at session start, so this is purely my noise.
- Between my `cargo fmt` (disk still showed the Step-1 version) and my
  `git commit -o <file>`, the concurrent agent's pair-row version was
  written to disk. My commit `784a062` therefore captured a **merged /
  intermediate state**: my doc rewrite (which still says "pair-row port
  is future work") sitting on top of *their* pair-row implementation
  that re-adds and uses the four intrinsics my commit message claims to
  have dropped. The commit is internally inconsistent and its message
  is misleading.

**True final state (verified):**
- Working tree (merged pair-row version + my fmt noise) **builds clean,
  0 warnings**; convolve8_vert tests **4/4 pass** (incl. the concurrent
  agent's new `differential_odd_and_narrow_shapes`). Their work is good.
- My 2 commits are **local only — never pushed** (2 ahead of
  `origin/main`), so nothing is lost and everything is reversible.

**Arthur's decisions (asked before any git surgery, per the
don't-touch-others'-in-flight-work rule):**
1. My 2 commits (`784a062`, `4ba5ab9`) — **keep as-is**. No reset/rebase.
2. The 119 accidentally-reformatted files — **leave them**. No restore.

So I performed **no** reverts and **no** history rewrites. The
concurrent agent will commit their pair-row work on top.

**Lesson for next time:** in this shared-working-tree multi-agent setup,
`cargo fmt -p <crate>` (whole-package) is dangerous — it rewrites every
file in the package, colliding with concurrent edits. Use
`rustfmt <single-file>` (or `cargo fmt -- <path>`) scoped to only the
file under change. And re-check `git status`/`git diff` immediately
before `git commit` to confirm the staged content is actually mine and
not a snapshot of a concurrent write.
