## Finding 1 — one real compiler warning (investigated, not suppressed)

`cargo build -p rvp9-core` emitted exactly one warning:

```
warning: unused imports: `_mm256_castsi128_si256`, `_mm256_castsi256_si128`,
         `_mm256_extracti128_si256`, and `_mm256_inserti128_si256`
  --> convolve8_vert_avx2.rs:76
```

**Investigation.** These four 256-bit lane-manipulation intrinsics are
*exactly* the ones the journal's optimization plan (Steps 2 & 3) and the
module doc (lines 20–52) describe for the **pair-row `s32b` topology**
(`inserti128` of two adjacent 128-bit row halves into one 256-bit
register). That topology was **never implemented** — the code that
landed took the simpler Step-1 route: a 256-bit sliding window over
*full* 256-bit row loads (`r[0..8]`), 2 output rows per iteration, no
`s32b` packing.

So the warning is not a bad merge and not a defect in working logic —
it is **speculative imports left over for code that was planned but not
written**, plus a knock-on **documentation defect**: the module doc and
the inner-loop tail comment described an implementation that doesn't
exist (`s32b` / `ss_lo` / `ss_hi`, "gw==16/8 256-bit pair-row path").

**Decision.** Do *not* implement the full pair-row optimization here —
that is net-new, bit-exact-gated feature work belonging to the active
supervised drive. Instead make the tree honest:
1. Remove the four speculative imports (not dead-code suppression — the
   code that would use them isn't being added).
2. Rewrite the `## Algorithm` / `## Bounds` module doc to describe the
   *actual* two-tier implementation (256-bit sliding window for
   `w-cg>=32`; 128-bit per-row path for the `cg<w` remainder), and note
   the pair-row port as explicit future work.
3. Clean up the rambling, self-doubting tail comment that ended with
   "so… hmm, actually the check needs to be… Let's be conservative" —
   replaced with a correct, concise invariant description. (The code was
   already correct: the odd-`h` tail unconditionally re-primes the
   trailing register `r[7]` before use, so the suppressed speculative
   load is harmless.)

## Correctness check (the logic itself)

Traced the 256-bit sliding window for the bound contract (last loadable
row = `h+6`):
- Priming loads rows `0..=7`; for all `h>=1`, row 7 <= `h+6`. ✓
- Pair loop (`while y+1<h`): first slide loads row `y+8`, max at
  `y=h-2` → row `h+6` (exactly the contract edge). ✓
- Second slide loads row `y+9` only when `y+3<h` → max `h+5`. ✓
- Odd-`h` tail re-primes `r[7]=row y+7`, max at `y=h-1` → row `h+6`. ✓

Max row touched = `h+6`, matching the documented footprint. No OOB.
