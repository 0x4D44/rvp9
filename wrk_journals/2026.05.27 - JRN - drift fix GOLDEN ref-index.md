# 2026.05.27 — JRN — drift fix: GOLDEN ref-index / refresh mismatch (SEVERITY-1)

Continues the inter-frame drift fix (Arthur's top priority). Prior agent
(commit 58d0592) fixed the KF Z-order, IDCT dispatch, and per-block
interp-filter causes — frames 0–1 became byte-exact (drift_diag SSE 0).
This wave fixes the residual frame-2+ drift's dominant cause: a GOLDEN
reference-index / refresh bookkeeping mismatch between the encoder's
prediction and the decoder's resolution.

## Root cause (encoder-side)

`crates/rvp9-encoder/src/frame_loop.rs:2676` (show-frame path) and
`:3091` (ARF path) emitted the wire `ref_frame_indices = [0, 0, 0]`
(the "A11 — every logical ref → slot 0" collapse).

The DECODER resolves logical inter ref `i` as
`ref_frame_map[ref_frame_indices[i]]`
(`crates/rvp9-decoder/src/lib.rs:2295-2312`). So `[0, 0, 0]` told the
decoder "GOLDEN → ref_frame_map[0]".

But the ENCODER's internal named-ref model reads GOLDEN through the
IDENTITY selector `named_ref_planes(GOLDEN_REF) =
slots[ref_frame_map[1]]` (`buffer_pool.rs::frame_refs/named_ref_planes`,
LAST→map[0], GOLDEN→map[1], ALTREF→map[2]). After frame 1's LAST-only
refresh (`refresh_frame_flags = 0x01`), `ref_frame_map[0]` holds frame 1
while `ref_frame_map[1]` still holds the frame-0 KF (GOLDEN only rotates
on the `0x03` golden-refresh, every 8 inter frames). The encoder picker
is NOT golden-disabled at speed 4/7 (`disable_golden_ref` is `1` only at
speed 9), so it freely picks GOLDEN blocks.

Result, from frame 2 onward: a GOLDEN-picked block was PREDICTED by the
encoder from the KF (map[1]) but RECONSTRUCTED by the decoder from frame
1 (map[0]) → the encoder's stored reference diverged from the true
decode → compounding SEVERITY-1 drift.

## The fix

Emit the IDENTITY logical-ref map `ref_frame_indices = [0, 1, 2]` on
both the show-frame and ARF writer calls, so the decoder resolves each
named ref through the SAME `ref_frame_map` slot the encoder's
`named_ref_planes(i)` reads. The refresh rotation is applied identically
on both sides (decoder `lib.rs:2112`, encoder
`RefFramePool::update_reference_frames`), so slot `i` holds the same
physical frame on both. Two lines changed (+ comments).

Note: the writer always emits "size_in_found = 0" + a fresh 32-bit frame
size (`header.rs:694`), so the new ref indices never feed the
size-inheritance path — no risk there.

Measured with real binaries (built HEAD 58d0592 in a throwaway worktree
for "before"; current tree for "after"), `scripts/psnr_per_frame.py`:

- cpu7: mean 26.57 → **30.13 dB** (+3.56). f2 30.86→33.62; f7 25.44→**30.13** (+4.7); f20 26.18→**31.20** (+5.0).

## Residual drift cause (reported, not fully fixed)

frame-2+ at 320×256 still has a SMALL residual (cpu7 frame 2 = 162K,
max-abs ≤ 19/px). Localized via `drift_diag_localize_frame2`: 85
diverging 8×8 blocks split ~50/50 LAST(43)/GOLDEN(42), all small
magnitude. GOLDEN-skip blocks (reading the byte-exact KF at half-pel)
diverge only ±1-3/px; LAST `EightTapSmooth` blocks up to 19. This is
width-dependent (256×256 is byte-exact through frame 2; 320 is not),
which points at a sub-pel-MC / edge-replication rounding cause — the
SAME class for LAST and GOLDEN, distinct from the (now-fixed) gross
"wrong-frame" GOLDEN ref-index bug. The GOLDEN reference pixels are
correct (KF, SSE 0); the residual is in the convolve, not the
reference selection. Deferred — a separate, much smaller cause.
