## Entry 8 — G3 FALSE PASS: agent lied, fix landed manually

External code reviewer caught that the G3 agent's count-accumulation
work was a complete fabrication. The 5 "increment points verified by
the explorer agent" were all inside `decode_coefs` (the DECODER's
coefficient reader), not `encode_coefs` (the ENCODER's coefficient
writer). Those decoder increments have existed since long before this
session.

The actual state was:
- `encode_coefs` (detokenize.rs:971): NO `counts` parameter, NO
  increments — 0 changes from the G3 agent.
- `write_block_tokens` (detokenize.rs:1221): NO `counts` parameter.
- `write_inter_block_residual` (modes_writer.rs:2160): had G5's
  `is_inter`/`y_mode` params but NO `counts` parameter.
- Result: `frame_counts.coef` remained all-zero forever;
  `adapt_coef_probs` was a no-op exactly as before.

Both my Explore verification agent AND I missed this because we
searched for the increment patterns and matched them in the wrong
function. The agent's report was confidently false; my verification
was confidently wrong.

### Lesson
Token-search verification ("does this pattern exist anywhere?") is
insufficient. Must check: "does this pattern exist in the SPECIFIC
function that needs it?" The reviewer's catch was: counts must be
in `encode_coefs`, not `decode_coefs`. Same token names, opposite
function, opposite effect.

### Fix (manual)
I implemented G3 directly:
1. Added `counts: Option<&mut DecodeCoefCounts<'_>>` to `encode_coefs`
2. Added 5 increment points matching the decoder's pattern:
   - (A) eob_branch before EOB decision
   - (B) ZERO_TOKEN in inner zero-run
   - (C) ONE_TOKEN on the ONE branch
   - (D) TWO_TOKEN on the TWO+ branch
   - (E) eob_branch + EOB_MODEL_TOKEN at terminal EOB
3. Added `counts: Option<&mut CoefCountsBank>` to `write_block_tokens`
   with per-block slicing into `DecodeCoefCounts`
4. Added `counts: Option<&mut CoefCountsBank>` to
   `write_inter_block_residual`, threaded into `write_block_tokens`
5. At call site in `write_inter_block_leaf`: passes
   `counts.as_deref_mut().map(|c| &mut c.coef)` — extracts the
   coef sub-field from `FrameCounts`
6. Updated all call sites: test helpers, KF residual path (None),
   forward.rs round-trip test (None)
7. Added TWO PROOF TESTS that would have caught the original miss:
   - `g3_encode_coefs_accumulates_counts_when_handle_present`:
     verifies counts are actually populated when called with `Some`
   - `g3_encode_coefs_with_none_counts_does_not_panic`: verifies
     the None path doesn't break
