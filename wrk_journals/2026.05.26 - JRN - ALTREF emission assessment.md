# 2026.05.26 — JRN — ALTREF emission integration assessment

**Verdict: TOO BIG for the ≤500 LOC + gate-green budget.**
No code changes were made. Cross-decoder gate stays green because nothing
touched the hot path. This journal records the precise missing pieces and a
sized breakdown so a future wave can pick it up with eyes open.

## Task recap

Wire `crates/rvp9-encoder/src/temporal_filter.rs` (W3.1-W3.5, commit 3df4fd4)
into `StreamEncoder::encode_frame`. Suggested integration: trigger an ALTREF
every `gop_length/2`, build the filtered ARF via the existing
`vp9_temporal_filter`, emit it as `show_frame=0` + `refresh_alt_ref=1`
(`refresh_frame_flags` bit 2), and ensure the decoder updates its ALTREF slot
while remaining byte-exact with vpxdec.

Constraints: stay under 500 LOC; keep the cross-decoder gate green
(`cargo test -p rvp9-encoder --test cross_decoder_gate -- --ignored` = 4
passed); preserve 412+ lib tests; cite libvpx file:line for the emit
semantics; ship a PROOF that the encoder emits a non-show frame at the gop
boundary AND the decoded stream contains exactly as many show frames as input
frames.

## What's already in place (the green parts)

1. **Filter pipeline.** `temporal_filter.rs::vp9_temporal_filter(data)` takes
   `ArnrFilterData` (frames + alt_ref_index + strength) and returns a
   `FilteredArnrFrame { y, u, v, width, height }`. Standalone, tested, ready.
2. **Bitstream writer.** `UncompressedHeader` supports `show_frame: false` on
   `InterFrame` (header.rs:675-678 writes the intra_only=0 bit when
   `!show_frame`). `refresh_frame_flags` is already an 8-bit field threaded
   through `build_inter_packet_with_residuals` (frame_loop.rs:2375). Setting
   bit 2 for ALTREF refresh is a one-byte change at the writer call site.
3. **Decoder accepts non-show.** `rvp9-decoder` already handles non-show
   frames (`lib.rs:3216-3220` even has a D.20 dump hook for altref Y planes).
   `last_show_frame` tracks correctly (lib.rs:2159, 3296).
4. **Superframe builder.** `rvp9-core::bitstream::superframe::SuperframeBuilder`
   packs `[non_show_arf, show_inter]` into one transport packet (libvpx
   `vp9_encoder.c:5093-5142` `vp9_pack_bitstream`).
5. **ALTREF as a RefFrame.** `RefFrame::AltrefFrame = 3` already exists in
   `mode_info.rs:866`. The picker enumerates LAST + GOLDEN today; adding
   ALTREF-aware reads (without actually picking it) is a no-op at the writer
   if no leaf carries `picked_ref_frame = AltrefFrame`.

## The blockers (what makes this >500 LOC)

### 1. Lookahead depth is hardcoded to 0 (passthrough)

`frame_loop.rs:614-618` constructs the lookahead with depth=0, which makes
`max_sz = 0 + MAX_PRE_FRAMES = 1`. The ring fits exactly one frame; the only
peek that returns data is `peek(0)` on the just-pushed frame. There is no way
to "see" frames K+1..K+N from inside `encode_frame(yuv_K)`.

libvpx's temporal filter builds the ARF from `cpi->lookahead` with
`vp9_lookahead_peek(lookahead, alt_ref_distance)` — it requires
`lag_in_frames >= alt_ref_distance + 1` (`vp9_temporal_filter.c:1104-1205`).
Without lag, you have no future frames; without future frames, you cannot
build a temporal-filtered ARF.

**LOC to lift this:** raising default depth from 0 to (gop/2 + 1) is one
line, BUT it changes the public API contract: `encode_frame(yuv) -> packet`
becomes "push N frames before any packet comes out". Today every caller
(cross_decoder_gate, bench harness, examples) assumes one-in-one-out. The
API redesign needs `Option<EncodedFrame>` or `Vec<EncodedFrame>` plus a
`flush()` for end-of-stream. Conservatively: ~150 LOC for the API change
+ ~80 LOC fan-out fix across every caller. Plus all the tests that assert
"frame 0 is KF, frame 1 is inter" (e.g. `encode_frame_dispatches_kf_then_
inter_then_kf_at_gop_end` at frame_loop.rs:2895) will need to assert against
the *delayed* output stream and accept N startup `None`s.

### 2. Display-order vs encode-order reordering

ALTREF must arrive at the decoder BEFORE the inter frames that reference it.
The bitstream order is: `KF, ARF(centered on F_k+m/2), F_1, F_2, ... F_m,
KF_next`. Today's `encode_frame` emits in display order: `KF, F_1, F_2, ...`.

libvpx accomplishes this via the GF group machinery (`vp9_firstpass.c::
define_gf_group` and `vp9_encoder.c:setup_frame` reordering). For rvp9 the
minimum viable version is: at the start of each gop, encode the ARF first
(`show_frame=0`), then encode each P-frame in order (`show_frame=1`). The
state-machine change inside `encode_frame` needs to: (a) detect "ARF
boundary" before encoding the next show frame, (b) call a new
`encode_altref_internal(filtered_yuv)` that emits a non-show inter packet
without advancing the show-frame counter, and (c) pack that packet plus the
current show frame's packet into a superframe via `SuperframeBuilder`.

**LOC:** ~120 for the state machine + ~50 for `encode_altref_internal` (most
of `encode_inter_internal` is reusable but needs a `show_frame: false`
+ `refresh_frame_flags |= 0x04` override).

### 3. ALTREF reconstruction slot

`StreamEncoder` has `last_recon_*` and `golden_recon_*` (and the parallel
`me_ref_*`). Mirroring this for `altref_recon_*` is straightforward (~30 LOC
of field allocation + initialise-on-KF), but every refresh code-path needs to
learn that `refresh_frame_flags` bit 2 means "write recon into
altref_recon_*". Today the refresh logic is a single bit (LAST + optional
GOLDEN per A14_GOLDEN_REFRESH_PERIOD); growing it to a third bit touches the
end-of-frame commit (`frame_loop.rs` around line 1456) and the rate-control
counters.

**LOC:** ~80 across slot allocation, commit logic, KF initialisation.

### 4. Simulator/picker for the synthetic ARF

`encode_inter_internal` runs the picker/simulator against the input YUV,
producing real residuals and a reconstruction. For the ARF, we feed the
*filtered* YUV (output of `vp9_temporal_filter`) as if it were a source
frame; the simulator then chooses modes that code it efficiently against the
LAST + GOLDEN refs. That's structurally fine — the filtered frame IS just
another inter frame at the bitstream level.

BUT there's a quality cliff: the picker's RD model assumes the source is
camera-natural pixels. NLM-filtered ARF pixels have different residual
statistics, so the speed-7 partition picker may over- or under-partition.
This is not a correctness blocker — the cross-decoder gate cares about
"vpxdec reproduces our reconstruction byte-exactly", not "the ARF is well-
compressed". But it surfaces as bd-rate noise unless the picker is told the
frame is an ARF (libvpx flips a `cpi->refresh_alt_ref_frame` flag and tunes
several speed features off it).

**LOC:** 0 for correctness; the picker can run unchanged. ~30 for a minimal
"this-is-an-ARF" pass-through flag if we want to suppress the worst tuning
mismatches.

### 5. PROOF test

The required PROOF is: (a) the encoder emits a non-show frame with
refresh_alt_ref=1 at the gop boundary, (b) the decoded stream contains the
same number of show frames as input frames. Both halves require N≥4 frames
of input, the IVF wrap, an rvp9-decoder run, and assertions on
`ParsedFrame::header.show_frame` per frame. Roughly 80-120 LOC for a
self-contained test in `tests/altref_emit.rs`.

### Cross-decoder gate risk

Every change above touches the inter packet writer or the encode-order
sequence. The cross-decoder gate (`tests/cross_decoder_gate.rs`) compares
byte-for-byte against vpxdec. With ALTREF emit on, vpxdec must accept our
multi-frame superframe AND produce the same show-frame YUV stream we
produce. That hinges on getting refresh_frame_flags right, the
ref_frame_indices right (the inter frames now have access to slot 2), and
sign-biases right. Any single bit wrong here causes a divergence.

| Lookahead depth + delayed-output API                 | 230      |

| Touch-up tests that assumed one-in-one-out           | 60       |
| **Total**                                            | **740**  |

That's 1.5x the budget. And it's the optimistic estimate that assumes no
cross-decoder gate regression — every other vpxenc-parity wave so far has
discovered at least one round-trip subtlety (refresh_frame_flags=0x01 in
A11; FC bank drift in P0b; ref-buffer split in W5/denoiser). Allow another
~150 LOC of contingency for those.

## libvpx file:line citations (the emit semantics)

- `vp9/encoder/vp9_encoder.c:setup_arf_frame` — pre-encode ARF selection
  + temporal filter call (around lines 4500-4600 in the stock libvpx tree).
  Reads `cpi->rc.source_alt_ref_pending`, peeks `cpi->lookahead`, dispatches
  `vp9_temporal_filter(cpi, distance)`.
- `vp9/encoder/vp9_temporal_filter.c:1104-1205` — `vp9_temporal_filter`
  top-level dispatcher (already cited in the standalone module).
- `vp9/encoder/vp9_bitstream.c::vp9_pack_bitstream` — emits the superframe.
  The non-show ARF gets `show_frame=0`, `refresh_frame_flags |=
  1 << ALT_REF_FRAME_IDX` (where `ALT_REF_FRAME_IDX = ALTREF_FRAME -
  LAST_FRAME = 2`, so `refresh_frame_flags |= 0x04`). See
  `vp9_encoder.c:5093-5142` (`vp9_pack_bitstream`) for the superframe-index
  trailer assembly.
- `vp9/encoder/vp9_encoder.c:setup_frame` — assigns
  `cm->frame_type=INTER_FRAME`, `cm->show_frame=0`, and the refresh mask for
  ARF emission.

## Recommendation

Park this until two prerequisites land:

1. **Lookahead depth>0 default.** `--lag-in-frames` plumb through
   `EncoderConfig` (master inventory A19 P0 follow-up). Lookahead module is
   already libvpx-faithful (W1.4); only the consumer-side API change is
   pending.
2. **Public API supports delayed output.** Either `Option<EncodedFrame>`
   return or a separate `flush()` path. This is the load-bearing API change
   for *any* lookahead-dependent feature (ARF, two-pass, scene-cut-driven
   GOP).

Once those two are in, the ARF emit itself is roughly 280 LOC — well inside
the 500 budget. Doing them together is what blows it.
