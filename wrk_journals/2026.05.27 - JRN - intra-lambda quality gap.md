# JRN — Intra/lambda quality gap (Track F closure batch)

**Date:** 2026-05-27
**Driver:** Claude (with Arthur)
**HEAD prior:** 0796879 (drift fix landed; gap 4.5 / 3.3 / 2.4 dB @ 400/1200/2000k cpu7)
**Why:** With the inter-frame drift fixed (commits 58d0592 / b8d2327 / 2067127),
the remaining gap to libvpx narrowed to ~2.4–4.5 dB. The gap NARROWED with
bitrate, which pointed at a fixed-cost component dominating the residual:
keyframe quality / lambda. This journal records the localization, the
single dominant cause we found, the fix, and the verification.

## Localization (per-frame PSNR breakdown, foreman 320x256 60f, cpu7 + cpu4)

### vpxenc baseline (cpu7)
| target | KF (frame 0) | f1   | steady-state (~f50) | mean |
|--------|--------------|------|---------------------|------|
| 400k   | 57.08 dB     | 37.7 | ~37.6               | 37.55 |
| 1200k  | inf          | 38.2 | ~41.6               | 41.20 |
| 2000k  | inf          | 38.2 | ~41.6               | 42.46 |

### rvp9enc PRE-FIX (cpu7)
| target | KF (frame 0) | f1   | steady-state (~f50) | mean |
|--------|--------------|------|---------------------|------|
| 400k   | **42.08 dB** | 34.5 | ~32-33              | 33.05 |
| 1200k  | **42.08 dB** | 34.5 | ~38                 | 37.92 |
| 2000k  | **42.08 dB** | 34.5 | ~38-40              | 40.09 |

The **KF Y-PSNR was IDENTICAL at every bitrate (42.08 dB)**. That's a
red flag — the keyframe quality is being floored by the rate controller
independent of the bitrate target. libvpx's KF can reach near-lossless
at 1200k+ (the source frame 0 happens to be encodable losslessly at
modest bits).

## Dominant cause (file:line + libvpx ref)

`crates/rvp9-encoder/src/rate_control/cbr.rs:567` (pre-fix line). The KF
`active_best_quality` (= the FLOOR on KF Q-index, lower Q = better
quality) was computed as:

```rust
let basis = worst.min(KF_ACTIVE_QUALITY_BASIS_CAP);  // CAP = 122
let best = get_kf_active_quality(basis);
```

`KF_ACTIVE_QUALITY_BASIS_CAP = 122` was a workaround (commit E7) for the
first-KF-no-feedback case. It pinned the KF basis at 122 regardless of
bitrate, which makes `get_kf_active_quality(122)` return ~57. Any
bitrate above the level where the picker would pick Q=57 organically
THEN gets stuck at Q=57. At Q=57, foreman 320x256 KF lands at 42.08 dB
— matching the measurement exactly.

libvpx reference (`vp9/encoder/vp9_ratectrl.c:1013-1042` in
`rc_pick_q_and_bounds_one_pass_cbr`):

```c
if (frame_is_intra_only(cm)) {
  active_best_quality = rc->best_quality;      // line 1014
  if (rc->this_key_frame_forced) { ... }       // skip — not our path
  else if (cm->current_video_frame > 0) {
    active_best_quality = get_kf_active_quality(
        rc, rc->avg_frame_qindex[KEY_FRAME], ...);  // line 1029-30
    // optional small-image adjustment (lines 1033-41)
  }
}
```

Two key differences from rvp9 pre-fix:
1. **First frame of stream (`current_video_frame == 0`)**: libvpx sets
   `active_best = rc->best_quality` (default 0 / CBR-realtime preset 4).
   `regulate_q` is then free to walk the full `[best_quality,
   active_worst]` range. **rvp9 pre-fix capped it at q≈57 even on the
   first frame** — that's the bug.
2. **Subsequent KFs**: libvpx uses
   `get_kf_active_quality(avg_frame_qindex[KEY])` with **the previous
   KF's qindex** as the basis (NOT the buffer-driven `active_worst`).
   rvp9 pre-fix was using `min(active_worst, 122)` instead.

## The fix

`crates/rvp9-encoder/src/rate_control/cbr.rs:538-590` —
libvpx-faithful KF Q policy:

```rust
let worst = active_worst_quality(rc, i32::from(rc.avg_frame_qindex_key));
let is_first_frame = rc.total_actual_bits == 0 && rc.frames_since_key == 0;
let best = if is_first_frame {
    rc.best_quality                                          // libvpx:1014
} else {
    get_kf_active_quality(i32::from(rc.avg_frame_qindex_key)) // libvpx:1029-30
};
(best.min(worst), worst)
```

Plus removal of the now-unused `KF_ACTIVE_QUALITY_BASIS_CAP` constant.

## Residual gap analysis

- **400k cpu7 gap = 4.5 dB (no change)**: the KF fix opens the door for
  q=4 at 400k, but the small 400k buffer (1.6 Mbit @ 4 sec) drains
  on a 50 kB KF. Inter frames then run at high Q (small remaining
  budget) and PSNR drops into low 30s. vpxenc's content-aware
  `bits_per_mb` lets it tune the KF spend better at low bitrates. This
  is a SECOND-order RC issue — not a KF-floor problem, and orthogonal
  to the Track F intra/lambda fix.
- **2000k cpu7 gap = 1.2 dB**: well inside the target. Remaining gap
  is likely a mix of intra mode-selection sub-optimality (the picker
  uses `block_yrd`-style transform-domain distortion + simple mode-bit
  rate, vs libvpx's SATD/Hadamard mode-search + per-pixel SSE
  reconstruction distortion) and small inter RDO differences. These
  are second-order improvements; the KF floor was a 12 dB single-frame
  effect that dominated.

## Why this matches the brief's hypothesis

The brief said:
> Gap NARROWS with bitrate (4.5→2.4) → suggests the residual is
> dominated by fixed-cost components (KF intra + RD-lambda calibration)
> more than inter coding.

Localization confirmed it: **the KF Q was pinned at 57 (≈42 dB) at all
bitrates**. That's the "fixed-cost component". The fix removed the cap
and let regulate_q operate as libvpx does.

The brief listed candidate fixes:
> - KF intra mode selection (SATD/Hadamard)
> - RD lambda calibration
> - KF intra extension / transform-size selection

None of these were the dominant cause — the issue was upstream in the
rate controller capping the KF Q-index regardless of available rate.
Once the cap is removed, KF Q drops to q=4 (best_quality, near-lossless)
and the KF intra path produces 54 dB. That validates the existing
KF intra path is competent; the previous "42 dB KF" was an RC artifact,
not an intra coder failing.

## Files touched

- `crates/rvp9-encoder/src/rate_control/cbr.rs` — KF Q policy (~50 LoC
  changed: removed `KF_ACTIVE_QUALITY_BASIS_CAP` constant and its
  documentation; rewrote the KF arm of `pick_q_and_bounds` to match
  libvpx).
- `crates/rvp9-encoder/tests/w_buffer_pool.rs`,
  `crates/rvp9-encoder/tests/w_gop_topology.rs` — golden byte-identity
  hashes updated for the intentionally changed bitstream (same pattern
  as the prior drift-fix golden bump). Comments explain why the change
  is correct and not a masked regression.
- `crates/rvp9-core/src/dsp/x86_64/dc_predict_{left,top,128,full}_avx2.rs`,
  `crates/rvp9-core/src/dsp/x86_64/tm_predictor_avx2.rs` — defensive
  scalar fallback for `bs = 64` (Block64x64). The inter picker's
  intra-fallback path in `mode_decision::inter::evaluate_intra_fallback`
  (`inter.rs:1853`) calls `intra_predict` with the full block size,
  including `bs = 64` on Block64x64 leaves. At the previous high KF Q
  the picker never reached this path; with the libvpx-faithful KF Q
  policy the inter picker considers Block64x64 leaves and hits the
  panic. The AVX2 specialisations cover `bs ∈ {4, 8, 16, 32}` only;
  `bs = 64` now routes to the scalar reference (already shipped, used
  by the v/h predictors' same defensive fallback pattern). This is
  not a decoder-touching change — the decoder is invariably called with
  `bs = tx_size.side() ≤ 32` (4 × Tx32x32 for a Block64x64
  reconstruction, never a single Tx64x64).

No decoder files touched. No bench/script files touched. The change
is encoder-side and DSP-fallback only.
