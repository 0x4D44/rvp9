# JRN — Profile-driven hotspot hunt (samply + DbgHelp)

**Date:** 2026-05-26
**Author:** team-lead (with Arthur present)
**Goal context:** /goal "match vpxdec perf". Headline `testsrc_1080p30 t=4`
= 4.79× (PGO) / 5.78× (no-PGO). The paper surveys proved unreliable
(survey #2 reverted), so we switched to **measurement**: a real sampling
profile of the decode hot path.

## TL;DR — the gap is SERIAL WORK, not parallelism

The single most important finding: **the vpxdec gap is dominated by
per-frame serial work efficiency, NOT parallel-scaling overhead.**

- `testsrc_1080p30 t=4` ratio = 4.79×; `testsrc_720p30 t=1` ratio = 5.94×.
  Those are nearly equal → we are ~5–6× slower than vpxdec *per unit of
  decode work*, and parallelism divides that for both of us. Frame
  pipelining (Lever A) would NOT close a serial gap. **Deprioritise Lever A.**
- The ~28% worker-idle seen at t=4 is real fork-join overhead, but it is
  secondary; vpxdec pays fork-join cost too.

## Tooling (now reusable — `scripts/`)

- `samply` records on Windows via xperf/ETW (needs admin; elevation was
  flaky once, retried fine). `--unstable-presymbolicate` emits a
  `.syms.json` sidecar, but **samply's own PDB parser does NOT name Rust
  symbols** (gives `fun_<rva>` placeholders) even with full debuginfo.
- Fix: `scripts/symbolize_pdb.py` — resolves module-relative RVAs to real
  Rust names via the Windows **DbgHelp** API (ctypes). Gotchas baked in:
  `SizeOfStruct = 88` (not the ctypes field offset 84), and a symbol
  search path pointing at `target/release/deps` (the release exe is a
  copy; its matching PDB is `deps/decode_headtohead.pdb`).
- `scripts/profile_hotspots.py <profile.json.gz> <exe>` — reduces the
  profile to self/inclusive tables, module-qualified, split into ALL /
  WORKER-ONLY / MAIN-ONLY cohorts. Use MAIN-ONLY on a t=1 capture for
  the clean serial work composition (≈0% idle).
- Build for profiling: `CARGO_PROFILE_RELEASE_DEBUG=2 cargo build
  --release -p rvp9-bench --bin decode-headtohead` (env override, no
  Cargo.toml change). Non-PGO for clean symbol attribution.
- Capture: `samply record --save-only --no-open --unstable-presymbolicate
  -r 2000 -o <out>.json.gz -- <exe> --row "<label>=<path>:<threads>"
  --min-timed <N>`. A high `--min-timed` makes `decode_frame` dominate.

## Serial work composition (t=1, MAIN-thread-only, ~0.2% idle)

Two fixtures, near-identical shape → the picture GENERALISES (testsrc is
synthetic, tile_1x4 is a real libvpx conformance vector):

| bucket                | testsrc_1080p30 t=1 | tile_1x4 t=1 |
|-----------------------|--------------------:|-------------:|
| **Intra prediction**  | **~38%**            | **~39%**     |
| — `dc_pred_4x4_avx2`  | 10.9%               | 10.5%        |
| — `reconstruct_intra_planes` | 9.7%         | 10.7%        |
| — `build_intra_predictors`   | 7.9%         | 8.6%         |
| — `intra_predict`     | 4.6%                | 5.0%         |
| — `reconstruct_intra_block`  | 3.5%         | 3.4%         |
| **Entropy/detokenize**| **~23%**            | **~25%**     |
| — `decode_block_tokens` | 16.8%             | 17.2%        |
| — `bool_reader::read` | 6.2%                | 7.5%         |
| **Loop filter** (lpf_* + filter_selectively) | ~16% | ~18% |
| memset + Vec<ModeInfo> resize | ~8%         | ~6%          |
| Inter/MC (`decode_inter_block`, convolve) | ~5% | <2% |

Notable ABSENCE: **no IDCT/inverse-transform kernel in the top 40.** The
earlier "higher-EOB IDCT" work paid off; transforms are not the bottleneck.

## The smoking gun: intra prediction is structurally inefficient

`dc_pred_4x4_avx2` is ~10.5% of *all* decode time. The kernel itself
(`crates/rvp9-core/src/dsp/x86_64/dc_pred_4x4_avx2.rs`) is tight —
effectively SSE2, ~10 instructions (2 loads, unpack, `_mm_sad_epu8`,
extract, scalar round, broadcast, 4 stores). So the cost is **call
frequency × per-call overhead**, not a slow kernel:

- Called once per 4×4 block, through an **indirect dispatch function
  pointer** (no inlining), with per-call slice/bounds setup, for ~10
  instructions of actual work. Classic "death by a thousand tiny SIMD
  calls."
- libvpx's intra prediction is cheap and not a top hotspot for these
  vectors; ours is 38%. The delta is structural: per-block dispatch
  indirection + redundant `above`/`left` reference-array construction
  (`build_intra_predictors` 8.6%).

In libvpx the per-vector hotspots are detokenize, idct, and (inter)
convolve — intra prediction is minor. Our profile is intra-heavy because
our intra PATH is slow, not because these vectors are unusual.

## Recommendation (data-backed, ranked)

1. **Restructure the intra-prediction path (~38% of work).** Highest
   value, generalises across fixtures. Targets:
   - Kill the per-4×4-block indirect dispatch for the tiny DC/TM/H/V
     predictors — inline the common small-block predictors at the
     reconstruct site, or batch them.
   - Audit `build_intra_predictors` vs libvpx `vp9_build_intra_predictors`
     — we likely over-copy / over-bounds-check the reference arrays.
   - This is a medium-large careful refactor (NOT a 5-LOC fix), but it is
     measured, not guessed. A 2–3× speedup on 38% of the work could move
     the headline from 4.79× toward ~2.5–3×.
2. **Entropy/detokenize libvpx-parity audit (~24%).** `bool_reader::read`
   + `decode_block_tokens`. Harder (inherently serial), but libvpx is
   faster here too — worth a structural comparison.
3. **DEPRIORITISE Lever A (frame pipelining).** It addresses parallel
   scaling, which the data says is NOT the dominant problem.

## Caveats / honesty

- These conformance vectors are keyframe/intra-heavy and low-motion. Real
  streaming video is inter-dominated, where our convolve/MC path (small
  here) would matter more. But the GATE is these vectors vs vpxdec, so
  optimising them is legitimate for the /goal.
- foreman-fp1 (real motion, 352×288) is already 1.75×, consistent with
  "inter-heavy content is closer to parity; intra-heavy 1080p is where
  we're 5×."
