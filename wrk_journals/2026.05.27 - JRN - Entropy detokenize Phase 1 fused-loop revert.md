## What changed

Reverted `decode_coefs` (`crates/rvp9-core/src/entropy/detokenize.rs`)
to libvpx's fused single-pass token loop. Inside the loop, the moment a
non-zero coefficient's `val`/`sign` are known we now compute
`v = (val * dqv) >> dq_shift` and write
`dq_coefs_out[raster_idx] = if sign { -v } else { v }` inline — the
exact shape of the verbatim `decode_coefs_libvpx_ref` and libvpx C
`vp9_detokenize.c:218-250`.

Deleted from the decode path:
- the four scratch `Vec`s (`scratch_raster/dqv/val/sign`) from
  `DecodeCoefsScratch` + their per-call `clear()`;
- the pass-2 loop;
- the `crate::dsp::get_ref()` atomic load + indirect
  `plane_dequant_finisher` invocation.

Kept (per §8 condition 2 — minimal):
- the `token_cache` memset (sub-step 1b is a separately-gated later
  phase — NOT bundled here);
- the M.6 `RVP9_DEBUG_REFCOEFS` runtime differential;
- the `counts` backward-adaptation tallies;
- the M.17 `RVP9_DEBUG_SCAN_WRITE` trace (now prints the inline
  `signed_v` directly);
- the `plane_dequant_finisher` kernel (scalar + AVX2) and its
  differential tests — they stay in `quant`/`dsp`, just no longer
  called from decode.

Differential proptest bumped N=100 → N=1000 (`N_PER_CONFIG` 10 → 100,
×10 configs covering all four tx sizes + all scan orders) per HLD §4.1.

## WHY we revert (provenance, §8 condition 4)

The two-pass split was Wave H H5/H6 (`992a9c1`,
`wrk_journals/2026.05.22 - JRN - Wave H apply-wiring...`). **Original
rationale:** separate per-coefficient dequant arithmetic from the
bool-coder loop so it could be vectorised 8-wide (AVX2
`plane_dequant_finisher`). Well-intentioned, but the measured workload
is eob-dominated:

- 95.5% of transform blocks decode to eob == 0 (libvpx: one read +
  return). These are **genuinely-entered, coded-but-all-zero** blocks —
  `decode_coefs` IS called for them (skipped blocks never call it). On
  the C side this is the `read_bool(EOB) == 0 -> break -> return 0`
  path; our two-pass version saddled it with a token_cache memset, four
  Vec clears, an OnceLock atomic load, and an empty indirect call.
- The AVX2 main loop needs ≥8 coefficients; only ~2.6% of blocks reach
  it. We paid the two-pass + indirect-dispatch tax on every block to
  vectorise 1-in-40.

R.14 (`2026.05.23 - JRN - Track R...`) already noted LLVM was NOT
eliding the `get_ref()` indirect call here (too short-lived). So the
overhead was real, measured, and net-negative end-to-end on the
eob-dominated gate workload. The fused loop removes it AND simplifies
the code (deletes the H5/H6 hot-path machinery), converging
structurally onto the verbatim ref port — a maintenance win.

**Reversibility:** the `plane_dequant_finisher` kernel + its
scalar-vs-AVX2 differential tests are untouched, so if a future
coefficient-dense fixture changes the calculus the two-pass path can be
re-wired trivially.

### Verdict (§5.3 honesty)

The decisive gate-fixture experiment shows the Phase 1 win is REAL but
SMALLER than the HLD's 5–9pp estimate **on the intra-heavy gate
fixtures**: on `tile_1x4` it is roughly perf-neutral (~2-3%, within
noise), because intra prediction (~38% per the profiling journal)
dominates there and detokenize is a smaller slice. On inter-heavy
content (foreman) it is a clear ~5-6%. Per §8 condition 1 I do NOT
claim a confident gate-fixture win. But the change is at least
perf-neutral AND a clear simplification (deletes H5/H6 hot-path
machinery, converges structurally onto the verbatim ref port), so it
clears the "keep if neutral + simplification" bar. The smaller-than-
expected gate gap is flagged to team-lead.

`testsrc_1080p30` (the second gate fixture) could NOT be measured —
fixture absent and unbuildable in this worktree (no vpxenc, no y4m
source). This is the one open item I cannot close here.
