# RVP9-BUG-KIL-00095 — Bound Y4M frame parameter tails

The Y4M reader scanned an extended FRAME header until any newline or EOF, issuing
one-byte reads against a File with no length bound. A malformed parameter tail
could therefore consume an arbitrarily long portion of the input.

The reader now keeps a private `BufReader<File>` after parsing the global header.
For extended frame headers, `Take` limits `read_until` to 79 bytes after the
initial six-byte prefix, including the newline. A missing newline at that limit
returns `InvalidData`; a shorter EOF retains `UnexpectedEof`. The ordinary
`FRAME\n` path is unchanged. Buffering preserves prefetched frame data for later
reads instead of issuing a syscall per parameter byte.

The tail count follows the bounded loop in the official
[libvpx v1.6.1 y4minput.c](https://chromium.googlesource.com/webm/libvpx/+/v1.6.1/y4minput.c).
The repo's pinned source submodule was not populated and its specific revision
was not available through the browser; this is not a claim of a local pinned
reference comparison.

## Evidence

- With the unbounded parameter loop restored temporarily, five focused tests ran:
  three passed and the two new rejection regressions failed. A header with 79
  non-newline tail bytes and then a newline plus a complete 384-byte body was
  accepted. The long unterminated tail reached EOF and returned `UnexpectedEof`
  instead of the required `InvalidData`.
- With the bound restored, rejection tests require the logical cursor to stop
  after the initial prefix plus 79 bytes. They also verify unread suffix/body
  sentinels and unchanged caller frame buffers. Their expected limit is a literal
  79, independently of the implementation constant.
- The valid boundary test uses 78 parameter bytes plus newline and checks all
  three decoded planes. Adding one parameter byte made the selected test fail
  with `InvalidData`. Restoring the input returned that one test to green. This
  is input calibration of the positive oracle, not another defect reproduction.
- The focused `cargo test -p rvp9-io y4m` run passed 26 unit tests and nine
  integration tests, including normal parameters, short EOF, full-frame and
  cropped multi-frame reads. Formatting and scoped I/O Clippy checks passed.

Commands used a task-local `.scratch` TMPDIR, stdin at EOF and harness timeouts.
The preselected final smoke is `deltic timeout 60 cargo test -p rvp9-io y4m`
after the final fetch/catch-up. No workspace suite was run.

## Limits and cleanup

Cursor assertions measure logical consumption. A buffered reader may physically
prefetch later bytes, which remain available through its buffer. The fix bounds
the scan and preserves those bytes; it does not forbid read-ahead.

A guard refused a worker's scratch-file removal and a subsequent scratch-clear
request. No further cleanup was attempted after those refusals. The failed-run
fixtures and logs remain in the task's `.scratch` for normal integration reap,
as required by the fleet scratch policy. The unrelated zero-limit allocation and
position-relative helper bugs are unchanged.

The lead reviewed the implementation and rejection evidence. This fixing pass
leaves the bug Fixed for a separate verifier and does not close it.
