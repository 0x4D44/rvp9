## Step 0: Verify 3 Code Claims — ✅ COMPLETE

Directly inspected source. All three claims from the Devil's Advocate report confirmed:

1. **IDCT uses i32 lanes (8/ymm)** — `idct16x16_avx2.rs:4` says verbatim "fully vectorised in AVX2 with 32-bit lanes". Uses `_mm256_mullo_epi32` (32-bit lane multiply). Confirmed at line 53 import.

2. **convolve8_horiz "AVX2" is actually 128-bit SSE** — `convolve8_horiz_avx2.rs:55-60` imports list contains zero `_mm256_*` intrinsics, only `_mm_*` (128-bit). The file documents "Eight output columns are produced per 128-bit group" — confirming half-width vs libvpx's 16 columns/iteration.

3. **i16 SSE2 kernel exists, wired as fallback only** — `dispatch.rs:1282-1290` contains the smoking gun comment: *"The AVX2 arm keeps the existing i32-lane kernel UNCHANGED (today's production path). The new SSE2 i16-lane kernel... is wired into the non-AVX2-but-SSE2 arm — a conservative initial rollout that installs the new code only on the (vanishingly small) cohort of x86_64 CPUs without AVX2. Slice 1.5 (next session) will flip the AVX2 arm to the SSE2 i16 kernel after bench A/B."* Slice 1.5 was never executed.

Decision: proceed with Tier 1 plan as designed. The findings are real and the fix for Step 4 is already written — just needs to be wired.

## Step 2: CPU Profile — COMPLETE (with caveat)

Attempted samply at 4kHz × 5 iterations on testsrc_1080p30 t=4. **Blocked**: samply requires Administrator privileges on Windows. cargo flamegraph, VTune, and Windows Performance Toolkit (xperf/WPA) all have the same admin requirement. No interactive admin shell available in this session.

**Pivot**: Use `dsp-microbench` to capture per-kernel baseline timings instead. Per-kernel microbench data is in some ways better than a system profile — it directly measures kernel throughput, which is exactly what the IDCT/convolve hypothesis predicts will be slow.

### dsp-microbench Baseline (saved to `wrk_docs/dsp-microbench-baseline-2026-05-25.txt`)

```
== Motion compensation (8-tap) ==
convolve8_vert 16x16               avx2     34.6 ns
convolve8 (2D) 16x16               avx2    365.5 ns
convolve8_vert 32x32               avx2    157.5 ns
convolve8 (2D) 32x32               avx2    699.2 ns
convolve8_vert 64x64               avx2    680.4 ns
convolve8 (2D) 64x64               avx2   1795.2 ns
```

**Smoking gun for convolve8_horiz**: at 16x16, vert is 34.6 ns and the 2D (vert + horiz) is 365.5 ns. The implied horiz contribution is **~320 ns — almost 10x slower than vert**. If horiz used true 256-bit AVX2 like vert, the 2D timing should be ~70-100 ns total. The horiz path is the bottleneck within MC.

For IDCT, no direct microbench coverage in `dsp-microbench.rs`. The Step 0 source-level evidence stands: `idct16x16_avx2.rs` line 4 self-documents as i32-lane AVX2; `dispatch.rs` line 1282-1290 documents the i16-lane SSE2 kernel is wired as fallback only.
