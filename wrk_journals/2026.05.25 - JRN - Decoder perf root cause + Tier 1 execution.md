## Step 0: Verify 3 Code Claims — ✅ COMPLETE

Directly inspected source. All three claims from the Devil's Advocate report confirmed:

1. **IDCT uses i32 lanes (8/ymm)** — `idct16x16_avx2.rs:4` says verbatim "fully vectorised in AVX2 with 32-bit lanes". Uses `_mm256_mullo_epi32` (32-bit lane multiply). Confirmed at line 53 import.

Slice 1.5 (next session) will flip the AVX2 arm to the SSE2 i16 kernel after bench A/B."* Slice 1.5 was never executed.

Decision: proceed with Tier 1 plan as designed. The findings are real and the fix for Step 4 is already written — just needs to be wired.

**Pivot**: Use `dsp-microbench` to capture per-kernel baseline timings instead. Per-kernel microbench data is in some ways better than a system profile — it directly measures kernel throughput, which is exactly what the IDCT/convolve hypothesis predicts will be slow.

```

convolve8_vert 16x16               avx2     34.6 ns
convolve8 (2D) 16x16               avx2    365.5 ns
```

**Smoking gun for convolve8_horiz**: at 16x16, vert is 34.6 ns and the 2D (vert + horiz) is 365.5 ns. The implied horiz contribution is **~320 ns — almost 10x slower than vert**. If horiz used true 256-bit AVX2 like vert, the 2D timing should be ~70-100 ns total. The horiz path is the bottleneck within MC.

## Step 6: convolve8_horiz 256-bit AVX2 rewrite — ❌ NO WIN ON THIS HARDWARE

Agent C ran a clean experiment per task spec — rewrote the kernel to process 16 cols/iter via YMM `_mm256_maddubs_epi16`, preserved source over-read avoidance, added 256-bit-path-specific differential tests. All tests passed. Conformance 6/6.

But the bench **regressed**:

| Size | Baseline 128-bit | 256-bit (storel×2) | 256-bit (storeu+unpacklo) |
|------|-----------------|--------------------|----------------------------|
| 16x16 | **307.8 ns** | 347.3 (+12.8%) | 381.2 (+23.8%) |
| 32x32 | **651.0 ns** | 816.8 (+25.5%) | 845.0 (+29.8%) |
| 64x64 | **1699.3 ns** | 2081.0 (+22.5%) | 2261.4 (+33.1%) |

Per the constraint *"if 256-bit is somehow slower, STOP and report — don't ship a regression"*, the agent reverted the file. Working tree clean.

**Hypothesis on the regression** (from the agent's report):
1. Cross-lane `_mm256_inserti128_si256` serializes through a single port on Arrow Lake's hybrid vector pipeline.
2. The bench may be migrating across P/E cores between runs (large spread: 16x16 ranges 286-420 ns).
3. Sustained 256-bit work triggers different P-state policy than 128-bit on hybrid CPUs (AVX2 license effects).

Lesson: source-level "libvpx does 256-bit, we don't" was a real finding, but the assumed-2x-throughput inference was wrong on this specific CPU. The microbench showing horiz=10x slower than vert at 16x16 must be due to other factors (different shuffle patterns, different intermediate handling). A proper investigation needs pinned-core profiling.

**Step 6 closed as "attempted, no win on Arrow Lake hybrid".** Could be retried on a homogeneous P-core only chip or with `SetThreadAffinityMask` + VTune. Deferred to future investigation.
