# Pinned libvpx exact-symbol profile

The prior 1.182520× process-CPU screen had an exact pinned libvpx binary but no reference hotspot map. Inspection showed its PE retains 13,647 defined `nm` symbols, including global assembly functions, although its DWARF source lines cover only runtime code. This allowed WPR/xperf sampling of the **same** binary, not a diagnostic rebuild.

Three canonical single-thread 60-frame captures reproduced the pinned IVF hashes and had numeric zero lost buffers/events. Function maps were resolved from each target PID's loaded image base and the binary's own text symbols. A first mapper that trusted only COFF `ty 20` entries falsely charged 184 Ducks samples to `vpx_clear_system_state`; direct IP offsets proved impossible for that tiny function. The corrected map includes `nm` global `T` starts, classifies local labels, and replays the original ETLs without changing any raw IP/count tuple. It attributes 122 of those samples to SSE2 16×16 SAD4D and 47 to SSE2 16×16 SAD. Full scripts and per-clip maps are in `wrk_docs/evidence/2026-09-26-pinned-libvpx-exact-symbol-profile/`.

Tree and Town show much larger RVP9 than libvpx sub-pixel sample shares, but that is not yet proof of redundant calls or a kernel-speed gap. Ducks has no corresponding sub-pixel-share excess. The next bounded question is how often a search repeats the same horizontal input/phase across vertical probes, and what fraction of the hot AVX2 kernel is the reusable horizontal pass. Do not revive the already rejected single-call 16×16 temp fusion or TX4 batching from this map.

The WPR runs are unpaired and Ducks CPU time varied materially, so they do not replace the earlier paired process-CPU ratio. No production code changed in this unit.
