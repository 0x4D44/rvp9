# JRN — Encoder quality + speed measurement (first real BD-rate/PSNR read)

**Date:** 2026-05-27
**Driver:** Claude (with Arthur)
**Why:** The vpxenc-parity drive (May 26, 12 milestones) validated the encoder
for *correctness* (byte-exact cross-decoder gate) and micro-RD ordering, but
**never measured end-to-end compression efficiency**. README goal is BD-rate
within 0.5 % of libvpx. The last quality datapoint was Track F (May 23):
~+9 dB PSNR gap on the RT picker, pre-RDO. This session measures where the
encoder *actually* stands today, post-RDO/ALTREF/compound.

## Method

- **Source:** `tests/corpus/foreman_cif.y4m` cropped to **320×256** (multiple of
  64 — rvp9enc's coded-dim constraint) and limited to **60 frames**, so both
  encoders read byte-identical input. Crop tool: `scripts/crop_y4m.py` →
  `tests/corpus/foreman_320x256_60f.y4m`.
- **Encoders:** anchor = `build/libvpx/vpxenc.exe` (v1.14.1), test =
  `target/release/rvp9enc.exe`. Identical flags via `bdrate` bin:
  `--codec=vp9 --passes=1 --rt --cpu-used=N --end-usage=cbr
  --target-bitrate=B --lag-in-frames=0`.
- **Decode + PSNR:** both streams decoded by the SAME `vpxdec` + mean-Y-PSNR
  path (`crates/rvp9-bench/src/bin/bdrate.rs`). **Validation anchor:** vpxenc's
  streams produce correct 35–44 dB through this path, so the harness is sound —
  any low number is a real property of rvp9enc's bitstream, not a measurement
  bug.
- **Speeds:** cpu-used 7 (RT picker) and cpu-used 4 (RDO dispatch path, the new
  May-26 work). Bitrate sweep 200/400/700/1200/2000/3500 kbps.
- CSVs: `bench/results/encoder-bdrate-foreman-cpu{7,4}.csv`.
  Per-frame PSNR tool: `scripts/psnr_per_frame.py`.

## Results

### BD-rate: UNMEASURABLE (curves do not overlap)

rvp9enc's entire RD curve sits 11–28 dB below libvpx's, so there is **no common
PSNR range to integrate** — `bdrate` reports "insufficient points". This is a
*worse* outcome than a large finite BD-rate %.

| target | vpxenc PSNR (cpu7 / cpu4) | rvp9enc PSNR (cpu7 / cpu4) |
|--------|--------------------------|----------------------------|
| 200k   | 35.4 / 36.9              | 24.1 / **17.3**            |
| 400k   | 37.6 / 38.9              | 25.8 / **17.0**            |
| 700k   | 39.8 / 41.0              | 26.1 / **18.0**            |
| 1200k  | 41.2 / 42.1              | 27.1 / **15.4**            |
| 2000k  | 42.5 / 43.1              | 25.6 / **14.6**            |
| 3500k  | 43.7 / 44.2              | 24.9 / **14.0**            |

Two pathologies:
1. **rvp9 quality DROPS as bitrate rises** (more bits → worse picture). Classic
   sign of a systematic per-frame error that compounds — more coded frames /
   lower Q makes it worse, not better.
2. **The RDO path (cpu4) is ~10 dB WORSE than the RT picker (cpu7)** — the exact
   opposite of intended. The May-26 "RDO is a genuine upgrade" claim was based
   on a unit-RD-ordering oracle + byte-exactness, never on PSNR; measured, it
   regresses quality hard.

### Root cause: inter-frame DRIFT (localized via per-frame PSNR)

| frame | rvp9 cpu7 | rvp9 cpu4 | vpxenc cpu7 |
|-------|-----------|-----------|-------------|
| 0 (KF)| 31.79     | 31.79     | ∞ (near-lossless) |
| 1     | 30.28     | 30.24     | 38.24       |
| 2     | 28.80     | 27.96     | 36.19       |
| 3     | 27.82     | 26.36     | 35.56       |
| 4     | 27.48     | 25.28     | 35.49       |
| 5     | 27.31     | 24.23     | 35.59       |
| 7     | 27.83     | 23.77     | 35.74       |

- **Keyframe (intra-only):** 31.8 dB for both rvp9 speeds — ~6–8 dB below
  libvpx. Known structural intra gap (Track F: SATD/Hadamard units + lambda
  co-tuning).
- **Inter frames:** rvp9 PSNR **decays monotonically** across the GOP; vpxenc
  stays FLAT at ~35.7 dB. Drift is **definitively rvp9-specific**, not a clip /
  GOP artifact. RDO (cpu4) drifts faster than RT (cpu7).
- The byte-exact cross-decoder gate is **blind** to this: encoder and decoder
  agree on the same poor-but-self-consistent reconstruction. Byte-exactness
  proves self-consistency, never closeness-to-source.

### Encode speed (single-thread, 320×256, 60f, 1000 kbps)

| config            | ms/frame | fps   | vs vpxenc |
|-------------------|----------|-------|-----------|
| vpxenc  cpu-used 7| 3.68     | 271.7 | 1.0×      |
| rvp9enc cpu-used 7| 28.49    | 35.1  | **7.7× slower** |
| vpxenc  cpu-used 4| 9.80     | 102.0 | 1.0×      |
| rvp9enc cpu-used 4| 111.68   | 9.0   | **11.4× slower** |

At 320×256 single-thread rvp9enc clears 30 fps at cpu7; naively scaled to 1080p
(~25× pixels) it would be far off the README's 1080p30/60 real-time targets.
No tile/row threading was exercised here.

## Interpretation

The encoder is **self-consistent but not yet competitive**. The May-26 work
delivered feature/correctness parity (byte-exact streams, real ALTREF/compound,
RC modes) but the two metrics that define "is this a good encoder" — BD-rate and
real-time speed — are both far from target:
- BD-rate vs libvpx: unmeasurable (11–28 dB below; curves don't overlap).
- Speed: 7.7–11.4× slower than vpxenc single-thread.

**The dominant quality bug is inter-frame drift**, not the intra gap. Mean PSNR
is dragged from a ~32 dB keyframe into the low-20s purely by accumulation. Fix
the drift and mean PSNR should jump 5–10 dB before any intra/lambda work.

The RDO-worse-than-RT inversion is the highest-priority lead: the new RDO
dispatch path actively accelerates drift. Whatever the RDO inter
reconstruction/residual path does differently from the RT picker is making
prediction error compound faster.

## Recommended next steps (in priority order)

1. **Diagnose the drift.** Per-block: is the encoder's *stored reference*
   reconstruction equal to what it coded (residual fully applied), or is there a
   systematic under-correction (e.g. dropped/halved residual, wrong dequant,
   skip chosen too often, MC rounding)? The reference-buffer split (`me_ref` vs
   `last_recon`, commit a26f6d4) is a prime suspect — verify inter frames code
   residual against, and commit, the TRUE decoded recon.
2. **Explain RDO-worse-than-RT.** Diff the inter reconstruction between the
   speed-7 RT picker and the speed-4 RDO dispatch path on the same frame.
3. **Re-measure** after each fix on this exact harness (regression oracle now
   exists).
4. Only then return to the intra/lambda gap (Track F) and the +7000-LOC full
   integration roadmap.

**Strategic note for Arthur:** this validates the concern raised before the run —
we have been optimizing for a correctness oracle (byte-exact gate) that is blind
to compression quality. Before pouring the planned ~7000 LOC into TPL/SVC/ML/HBD
integration, the drift bug should be found and fixed, because right now those
features would be layered on an encoder that loses ~10 dB to drift over a GOP.

### Verdict

Three of the four findings from run 1 are *materially resolved*:
1. ✅ **Drift fixed** — was monotonic decay, now stable/rising.
2. ✅ **RDO inversion fixed** — cpu4 RDO now correctly higher PSNR than cpu7.
3. ✅ **Inverted RD curve fixed** — more bits → more quality, as expected.
4. ⚠ **Coding efficiency still ~2× off libvpx** (BD-rate +86–95 %).

The previous strategic recommendation — *stop the +7000-LOC roadmap and fix
the drift first* — was correct and acted on between the two runs. Drift is
gone. The next-frontier question is whether to push BD-rate down (intra/lambda,
inter mode-decision quality, more Track-F levers) before or alongside the
remaining parity zones (SVC/HBD/TPL). Speed will need attention separately;
the cpu-used 7 path is now 13.6× slower than vpxenc on a small clip.
