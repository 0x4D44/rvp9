### 2026-05-28 — Recon COMPLETE — gap is vector width (128 vs 256-bit)

**The finding (high confidence):** rvp9's `idct32x32_1024_add` dispatches
to a **128-bit SSE2 i16-lane** kernel — `dispatch.rs:1298-1299` gates on
`caps.sse2` and installs `idct32x32_add_sse2_1024`
(`idct32x32_sse2_1024.rs`). libvpx's rtcd patches `vpx_idct32x32_1024_add`
to the **256-bit AVX2 i16-lane** `vpx_idct32x32_1024_add_avx2`
(`inv_txfm_avx2.c:574`). **Both are the same algorithm, same constants,
same rounding — libvpx just does 2× elements per instruction.** That
width mismatch *is* the 1.71×.

An existing rvp9 *AVX2* idct32 (`idct32x32_avx2.rs:907`) is **i32-lane**
(`_mm256_mullo_epi32`, only 8/ymm) — worse for the dense case, so
dispatch deliberately uses it only for the EOB-34/135 fast paths. Do
NOT reuse it for the dense 1024 path.

**Mechanism detail:** rvp9 SSE2 processes 32×32 as 4 row-strips×8 +
4 col-strips×8 = 8 `idct32_1024_8x32` runs (8 lanes each). libvpx AVX2
= 2 row-strips×16 + 2 col-strips×16 = 4 `idct32_1024_16x32` runs (16
lanes each): same butterfly work, **half the instruction count, half
the transposes, half the intermediate load/store traffic**. Explains
~1.7–1.9×.

**Proposed fix (stepwise, bit-exact-checkable):** port
`vpx_idct32x32_1024_add_avx2` as a NEW 256-bit i16-lane module
(`idct32x32_avx2_1024.rs`) — a 1:1 widening of the already-bit-exact
SSE2 port — then flip dispatch to prefer it on AVX2.
1. Port leaf helpers (256-bit): `butterfly16` (2× `_mm256_madd_epi16`
   + `(x+8192)>>14` + **saturating** `_mm256_packs_epi32`),
   `add_sub_butterfly`, `recon_and_store16` (note the
   `_mm256_permute4x64_epi64(_,0xd8)` lane-fix), `store_buffer_16x32`,
   `transpose_16bit_16x16_avx2`. Keep rvp9's unaligned-`dst` discipline
   + the `// G4:` grep sentinels.
2. Port the 1-D engine `idct32_1024_16x32` + quarter helpers — mechanical
   i16→ymm copies of the SSE2 quarter helpers, **same cospi constants +
   butterfly arg order** (copy verbatim; that's the bit-exact contract).
3. Assemble the driver (2 row-strips + 2 col-strips), add safe wrapper
   `idct32x32_add_avx2_1024`.
4. Flip `dispatch.rs:1297-1299`: avx2 → new kernel, else sse2 → existing,
   else scalar. Update dispatch unit tests.
5. Gate: clone the SSE2 differential proptest for the AVX2 kernel + add
   an SSE2-vs-AVX2 equality test, then the bit-exact harness.

**Bit-exact contract / risks:** the SSE2 kernel SATURATES
(`_mm_packs_epi32`) where the scalar truncates modularly — the AVX2 port
MUST saturate to match SSE2 + libvpx (tests stay in the bounded ≤i12
envelope, validate vs the SSE2 kernel as primary oracle, NOT the scalar
on i16-extreme inputs). Top silent-bug risk: cospi pairing/sign in
`butterfly16` calls (cross-check libvpx AVX2 *and* rvp9 SSE2). Test the
16×16 transpose + `recon_and_store16` lane-permute in isolation first.

**Expected:** ~1.0–1.15× (parity or slight win); ≤1.3× very realistic.
Lower risk than the convolve drives — the AVX2 is simply *absent* here,
and the proven SSE2 algorithm just needs widening. Labor is volume of
mechanical helper porting, not novel logic.

**Port target:** `third_party/libvpx/vpx_dsp/x86/inv_txfm_avx2.c:574-601`
+ helpers `:63,179,237,297,311,550`. rvp9 oracle:
`idct32x32_sse2_1024.rs`. Microbench row:
`crates/rvp9-bench/src/bin/dsp-microbench.rs:363`.

### 2026-05-29 — 135 debug+fix pass — input-contract mismatch with rvp9 scalar

**Root cause (one-liner):** the first cut of `idct32x32_avx2_135.rs`
was a faithful port of upstream libvpx's `vpx_idct32x32_135_add_avx2`
(load only the top-left 16×16, ignore cols 16..32), but the rvp9
scalar reference `idct32x32_135_add` reads ALL 32 cols of rows 0..16
— a strictly broader input domain. On any input with non-zero
coefficients in cols 16..32 of rows 0..16, the libvpx-faithful AVX2
kernel silently dropped those coefficients and diverged from scalar.
The SSE2 135 sibling (`idct32x32_add_sse2_135`) has the same bug —
it too implements only the top-left-16×16 libvpx contract — which
masked the divergence whenever the AVX2 kernel was compared against
the SSE2 sibling (4 of the 5 originally-failing tests had been
compared against SSE2; one of those passes had been a coincidence
of "buggy == buggy"). The bug was visible only on
scalar-comparison tests, of which 5 were failing.

**Diagnostic that nailed it:** added a temporary directed test that
ran four kernels (scalar, AVX2 dense 1024, SSE2 135, AVX2 135) on
the same dense-i12 input and printed pairwise equality. Result:
`scalar == avx2_1024 : true`,
`scalar == sse2_135  : false`,
`scalar == avx2_135  : false`,
`sse2_135 == avx2_135: true`. The dense AVX2 1024 driver matches
scalar (proves the engine + helpers are correct); both 135 drivers
agree with each other but DISAGREE with the dense 1024 driver and
the scalar — so both 135 drivers share the same input-contract bug.

**Fix (minimal-diff in this file only):** mirror the AVX2 dense
1024 driver's strip-0 row pass — load BOTH 16-col halves of rows
0..16, transpose each, run the engine — then skip strip 1 (rows
16..32 are zero under the 135 contract, so `r = [zero; 32]` is the
bit-exact engine output) and run the existing 2-iteration column
pass with `out[0..16]` from `l` and `out[16..32]` from the zero
`r`. Net cost = 3 `idct32_1024_16x32` runs (1 row + 2 col) — same
