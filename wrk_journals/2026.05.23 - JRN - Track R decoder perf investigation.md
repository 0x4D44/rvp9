Observations to investigate:

1. **testsrc_720p30 (87 ms) is dramatically slower than testsrc_1080p60
   (11 ms p50).** A 720p single-tile clip decoding 8x slower per frame
   than a 1080p 4-tile clip is backwards. Either (a) the 720p clip is
   pathologically hard (higher bitrate, more residual), (b) tile
   threading helps even at t=1 by giving the kernels smaller work units,
   or (c) there's a fixture-specific bug. Diagnose first.
2. **Tile threading scales negatively** (tile_1x4: 272 ms → 339 ms going

   tile_1x4 — needs profiler.

   meets gate, the priority shifts from "make decoder faster" to "fix
   the tail / fix tile threading."
4. **vpxdec 1593 fps at 720p (627 us/frame) is borderline-incredible.**
   Sanity-check: is vpxdec actually decoding the bitstream or short-
   circuiting somewhere? Verify with `--md5` and confirm the output is

### R.1 — env::var hot-path cache (CLOSED — commit `ff4f5d8`)

**Diagnosis path:** R.1 investigation agent hit the session limit
before producing the HLD. Lead bypassed the agent and ran the
diagnosis directly via grep — 43 `std::env::var` sites across the
decoder, 25 of them per-block / per-transform in `tile.rs`,
`detokenize.rs`, `reconstruct.rs`, `reconstruct_inter.rs`. Worst
single site (`tile.rs:1089`) fires inside the per-transform loop of
`reconstruct_intra_planes`: 30k–100k syscalls per 1080p keyframe.

**Fix:** new `trace_flags.rs` modules in both `rvp9-decoder` and
`rvp9-core`, each backed by `std::sync::OnceLock<TraceFlags>`. Every
hot-path call becomes a single struct-field access. Implementation
agent did the mechanical refactor end-to-end, including:
- 28 call-site conversions (12 tile.rs, 6 detokenize.rs, 4 reconstruct.rs,
  3 reconstruct_inter.rs, 1 intra_pred.rs, 2 entropy/detokenize.rs).
- Two new modules (137 LOC + 49 LOC), wired into `crates/rvp9-decoder/src/lib.rs`
  and `crates/rvp9-core/src/lib.rs`.
- Combined-logic sites (e.g. `tile.rs:1773-1784` reading two env vars and
  combining them) refactored to precompute the boolean in the cache.
- Trade-off documented: setting RVP9_* env vars AFTER the first decoder
  API call has no effect. No test in workspace relies on mid-decode env
  mutation.

### R.2 — decode_coefs scratch hoist (in progress)

**Diagnosis path:** R.2 investigation agent produced solid HLD; R.2
implementation agent attempted twice and reported "files reverted by
external process" / borrow-checker tangles. Lead took over and did
the implementation directly with the simpler `thread_local!` design.

**Fix (lead direct implementation):**

- Single file changed: `crates/rvp9-core/src/entropy/detokenize.rs`.
- New private struct `DecodeCoefsScratch` (5 reusable `Vec`s sized to
  `MAX_TX_COEFFS = 1024`).
- New `thread_local!` static `DECODE_COEFS_SCRATCH: RefCell<DecodeCoefsScratch>`.
- The body of `decode_coefs` is wrapped in `with_borrow_mut(|scratch|
  { let DecodeCoefsScratch { token_cache, scratch_raster, scratch_dqv,
  scratch_val, scratch_sign } = scratch; ... })`. The destructured
  bindings preserve the existing local-variable names, so the body of
  `decode_coefs` (over 300 LOC, lots of pass-1/pass-2 references)
  needed zero edits.
- The 5 inline `Vec::with_capacity(...)` / `vec![...]` calls are
  replaced with `.clear()` (Vec) and a prefix-fill (`token_cache`).
- Bit-exactness: trivially preserved (pure storage hoist; same data,
  same offsets, same dispatch arguments).
- Out of scope: the per-block `let mut dq_coefs = [0i32; MAX_TX_COEFFS]`
  4 KB stack arrays at `reconstruct.rs:188` / `reconstruct_inter.rs:544`
  stay for now — stack writes are L1-hot and not the dominant cost.
  Defer to R.3 if R.2 numbers warrant chasing.

### R.3 — extend trace_flags + intra dq_coefs hoist

Scope (final, after bisection):
1. trace_flags::TraceFlags extended with 9 lib.rs env::var sites
   (disable_lf, trace_seg, trace_fc, dump_altref, dump_lf_masks).
   The dump_lf_masks site is per-SB (~500/frame at 1080p).
2. crates/rvp9-decoder/src/reconstruct.rs: new thread_local
   `DQ_COEFS_BUF: RefCell<Vec<i32>>` (sized MAX_TX_COEFFS). Replaces
   the per-call `let mut dq_coefs = [0i32; MAX_TX_COEFFS]` (4 KB
   stack zero) in `reconstruct_intra_block`.

Bisection (what was dropped):
- Same dq_coefs hoist on `reconstruct_inter_block` regressed
  testsrc_1080p60 by 30% (5.1ms → 6.7ms). The per-call RefCell+TLS
  cost exceeds the 4KB-zero savings for Tx4x4-heavy synthetic
  inter content. Reverted.
- `#[inline(always)]` on `BoolReader::read` / `read_bit` /
  `read_tree` regressed 1080p60 by 35%. Code bloat hypothesis;
  reverted to plain `#[inline]`.

### R.4 plan

R.4 needs to attack the **decode_coefs hot loop itself** (likely the
remaining bottleneck on testsrc content; testsrc has lots of
non-skip blocks where coefficient decode dominates) OR find another
structural inefficiency (per-tile allocations, MC prediction, etc.).

Attempted samply profiling on Windows — sandbox unable to produce
output (process hung after capture, killed manually). Falling back
to differential measurement and code analysis.

Quick differential probe: `RVP9_DISABLE_LF=1` on testsrc_1080p30 t=4
showed only ~5% delta (12.7ms → 12.1ms). Loopfilter is NOT the
dominant remaining cost. Coefficient decode / MC are.

Other potential R.4 levers identified but not yet shipped:
- Use UnsafeCell instead of RefCell for the thread_local pattern
  to remove borrow-counter overhead. May enable the inter dq_coefs
  hoist that was reverted.
- Per-tile state hoist: `TileDecodeCtx::new_with_grid` allocates two
  Vecs per tile (size O(tile_mi_cols × tile_mi_rows)). 4 tiles
  × 30fps × 2 allocs = 240 allocs/sec, not huge but reusable per
  stream.
- Look at MC kernel coverage / sub-pel filter selection for any
  scalar fallthrough.
- Consider library-level inline hints around bool_reader at specific
  hot call sites (read_tree → mode_info readers).
