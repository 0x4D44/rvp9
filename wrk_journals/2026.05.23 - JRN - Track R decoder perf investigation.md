### R.1 — env::var hot-path cache (CLOSED — commit `ff4f5d8`)

**Diagnosis path:** R.1 investigation agent hit the session limit
before producing the HLD. Lead bypassed the agent and ran the
diagnosis directly via grep — 43 `std::env::var` sites across the
decoder, 25 of them per-block / per-transform in `tile.rs`,
`detokenize.rs`, `reconstruct.rs`, `reconstruct_inter.rs`. Worst
single site (`tile.rs:1089`) fires inside the per-transform loop of
`reconstruct_intra_planes`: 30k–100k syscalls per 1080p keyframe.

**Fix:** new `trace_flags.rs` modules in both `rvp9-decoder` and
`rvp9-core`, each backed by `std::sync::OnceLock<TraceFlags>`. Every
hot-path call becomes a single struct-field access. Implementation
agent did the mechanical refactor end-to-end, including:
- 28 call-site conversions (12 tile.rs, 6 detokenize.rs, 4 reconstruct.rs,
  3 reconstruct_inter.rs, 1 intra_pred.rs, 2 entropy/detokenize.rs).
- Two new modules (137 LOC + 49 LOC), wired into `crates/rvp9-decoder/src/lib.rs`
  and `crates/rvp9-core/src/lib.rs`.
- Combined-logic sites (e.g. `tile.rs:1773-1784` reading two env vars and
  combining them) refactored to precompute the boolean in the cache.
- Trade-off documented: setting RVP9_* env vars AFTER the first decoder
  API call has no effect. No test in workspace relies on mid-decode env
  mutation.

### R.2 — decode_coefs scratch hoist (in progress)

**Diagnosis path:** R.2 investigation agent produced solid HLD; R.2
implementation agent attempted twice and reported "files reverted by
external process" / borrow-checker tangles. Lead took over and did
the implementation directly with the simpler `thread_local!` design.

**Fix (lead direct implementation):**

- Single file changed: `crates/rvp9-core/src/entropy/detokenize.rs`.
- New private struct `DecodeCoefsScratch` (5 reusable `Vec`s sized to
  `MAX_TX_COEFFS = 1024`).
- New `thread_local!` static `DECODE_COEFS_SCRATCH: RefCell<DecodeCoefsScratch>`.
- The body of `decode_coefs` is wrapped in `with_borrow_mut(|scratch|
  { let DecodeCoefsScratch { token_cache, scratch_raster, scratch_dqv,
  scratch_val, scratch_sign } = scratch; ... })`. The destructured
  bindings preserve the existing local-variable names, so the body of
  `decode_coefs` (over 300 LOC, lots of pass-1/pass-2 references)
  needed zero edits.
- The 5 inline `Vec::with_capacity(...)` / `vec![...]` calls are
  replaced with `.clear()` (Vec) and a prefix-fill (`token_cache`).
- Bit-exactness: trivially preserved (pure storage hoist; same data,
  same offsets, same dispatch arguments).
- Out of scope: the per-block `let mut dq_coefs = [0i32; MAX_TX_COEFFS]`
  4 KB stack arrays at `reconstruct.rs:188` / `reconstruct_inter.rs:544`
  stay for now — stack writes are L1-hot and not the dominant cost.
  Defer to R.3 if R.2 numbers warrant chasing.

### Realism on "match vpxdec"

The R.1+R.2+R.3 path closed 90-99% of the original gap on most
fixtures (60-250× → 5-20×). The remaining 5-20× gap to vpxdec on
testsrc is genuinely structural work:

- **Coefficient decode hot loop**: vpxdec's libvpx asm
  (`vp9_iht*_add.asm`, `vpx_dsp/x86/vpx_subpixel_8t_intrin_*.c`) is
  hand-tuned over 10+ years. Matching it requires similar effort.
- **Per-block overhead**: libvpx pre-computes neighbor state and
  uses pointer-arithmetic indexing where we use slice-bounds-checked
  indices. ~5-10% per-call cost is plausible.
- **MV / mode-info reading**: each block does many bool reads on
  per-block-context-derived probabilities. Tight inlining matters.

These are wave-sized efforts, not single-session fixes. The /goal
"match vpxdec" should be read as a multi-session commitment.

For this session, the trajectory has been:
- Baseline: 60-250× slower than vpxdec
- After 3 mechanical, bit-exact, conformance-preserving fixes: 5-20×
  slower (or FASTER on small fixtures), all PLAN budgets met with
  significant headroom.

That's a substantial win delivered safely. The next phase is
genuine algorithmic / kernel work, which needs proper profiling
infrastructure (samply with admin, or instrumented release builds)
to target effectively.

### R.4 — target-cpu=native (commit 99e3800)

Surprise win. Tried compiling with `RUSTFLAGS="-C target-cpu=native"`
and re-benched. **Consistent 1.01-1.23× speedup across all fixtures**
with zero regressions. Shipped via `.cargo/config.toml` so all
release builds inherit.

Mechanism: with `target-cpu=native`, LLVM uses the host's full
instruction set (BMI2, FMA, AVX-512 where present) for plain Rust
code, in addition to our hand-written AVX2 intrinsics. The compiler
auto-vectorizes loops in `inter_predictor`, mode info readers,
`dec_find_mv_refs`, etc.

### R.5 plan

Remaining gap is in the deepest hot loops. Approaches:

1. **Bool reader + read_tree hand-tuning.** Look at the assembly LLVM
   produces and see if there's a tighter sequence. With native CPU
   features, we might have BMI2 PEXT/BLSR or other bitfield ops
   that would speed up the renormalization step.
2. **Pareto8 table access pattern.** The token tree walk reads from
   a 255×8 pareto table per token. If the access pattern is
   predictable, prefetching might help.
3. **Per-block neighbor lookup.** `dec_find_mv_refs` walks neighbors
   via dispatch. The trait could be replaced with concrete types
   to enable inlining.
4. **Mode info parser hot path.** Each block does 10-30 bool reads
   for mode/MV info. Specialized fast paths for common modes
   (NEARESTMV, ZEROMV) might cut this.

Each is medium-to-large effort. Realistic to ship one or two more
in this session if time allows.

### R.5 — explored, NOT shipped

Two further attempts, both REGRESSED bench numbers:

**R.5a — `#[inline(always)]` on `read_segment_id`, `read_skip`,
`read_partition`.** These are per-block bitstream readers, called
on every mi-block decode. Hypothesis: forced inlining would let
LLVM see through the bool-reader call chain into each call site.

Result: regressed every fixture by 1-11%. Same code-bloat issue
as the earlier attempt on `BoolReader::read` itself (R.3
investigation). Reverted to plain `#[inline]`.

**R.5b — `lto = "fat"` instead of `"thin"` in workspace
Cargo.toml.** Full LTO can produce better code than thin in some
cases.

Result: REGRESSED most fixtures by 5-24%. testsrc_1080p30 t=2 was
hit hardest (12.3ms → 15.4ms, -20%). Likely interaction with
target-cpu=native — when the compiler can optimize across crate
boundaries with all CPU features, it inlines too aggressively,
causing icache pressure. Reverted.
