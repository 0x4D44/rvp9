## 3. What ML partition pruning IS

In libvpx (`vp9_encodeframe.c:3155-3618`) the ML pruners are **encode-time speed features**. They predict — from cheap features (variance, MV magnitude, neighbour block sizes, EOB sums, qindex, current RD) — whether to:
- skip evaluating SPLIT/rect partitions (`ml_pruning_partition`),
- break out of the partition search early (`ml_predict_breakout`),
- skip the rectangular HORZ/VERT arms (`ml_prune_rect_partition`),
- short-circuit RD partitioning with a variance-based motion-search prediction (`ml_predict_var_rd_partitioning`).

They change **which** partitions/modes the encoder bothers to evaluate, and therefore can change the final mode chosen — but a stream encoded without them is fully exhaustive (or as-exhaustive-as-the-current-search) and **fully valid**. ML pruning never alters the bitstream syntax or any decode-time constraint; it only makes the search faster and slightly less thorough.

## 4. Default-path / cost / knob analysis

**(a) Does the default encode path use ML code?** No. The default (and every) encode path runs zero ML code. The RDO descent at `lib.rs:3810-3884` dispatches to `pick_inter_sb_leaf`; nothing reads a pruning decision. Removing `ml_partition/` entirely would not change a single emitted byte.

**(b) Full-integration cost.** The expensive part is **done**: the scalar `nn_predict` kernel exists and all 13 NN/linear weight tables are transcribed verbatim and PROOF-tested (`nn_predict.rs`). So no trained-weights or NN-kernel prerequisite remains. The remaining work is **wiring** (~150 LOC per re-audit §3 row 8): the pruners need a real RDO partition descent (A4 — HORZ/VERT/PC_TREE arms, `force_split[21]`, `min/max_partition_size` clamps, `PICK_MODE_CONTEXT` caching) to gate. Today's production descent is leaf-dispatch only (8/16/32, NONE-ish), so there is no descent loop for a pruner to short-circuit. Net: blocked on A4 descent, then ~150 LOC of feature-extraction + gate plumbing. It also needs `cpi->sf.rd_ml_partition.*` speed-feature fields (A7) to be reachable.

**(c) Purely a speed/quality knob?** Yes. In libvpx these live entirely behind `sf.rd_ml_partition` / `sf.simple_pred_partition` speed-feature gates and are tuned per cpu-used level. They trade encode time for search exhaustiveness. No effect on stream validity.

## 5. Classification + rationale

**ACCEPTABLE DEFERRAL.**

The project gate is a **valid-stream gate**, not an encoder-output-identity gate: `cargo test -p rvp9-encoder --test cross_decoder_gate -- --ignored` requires rvp9 output to be byte-exact DECODABLE by libvpx vpxdec + ffmpeg (a valid VP9 stream), not that rvp9 emits the identical bytes vpxenc would. ML partition pruning is a search-time speed optimization that changes which partitions/modes are evaluated — it can shift the chosen mode (and thus the exact bytes), but a stream produced *without* it remains a fully valid, byte-exact-decodable VP9 stream. The current encoder already passes the sacred gate 4/4 (re-audit §1) with zero ML code on any path. A21 therefore falls in the **same class as TPL (A23) and HBD (A20)**: it affects quality/speed/search-exhaustiveness but **not stream validity**, so it is an acceptable deferral for the valid-stream gate. It is NOT an in-scope correctness gap: no valid-stream requirement and no default-path correctness requirement touches the ML code.

(It remains an in-scope *parity* gap for a full "vpxenc speed-feature parity" goal — re-audit §3 ranks it #8 — but that is a speed/quality lever, not a validity blocker.)
