### F12 midpoint measurement (RC.1+RC.2 in place, RC.5 not yet)

Ran F12 (`bdrate_gate_stage4a`) on the new y4m source at 256×256, 16 frames:

```
Target=250kbps  → rvp9 actual=56.7kbps, PSNR=23.45dB  |  libvpx actual=93.8kbps,  PSNR=55.11dB
Target=500kbps  → rvp9 actual=56.8kbps, PSNR=23.45dB  |  libvpx actual=119.2kbps, PSNR=58.88dB
Target=1Mbps    → rvp9 actual=56.2kbps, PSNR=23.74dB  |  libvpx actual=128.0kbps, PSNR=59.23dB
Target=2Mbps    → rvp9 actual=56.4kbps, PSNR=23.74dB  |  libvpx actual=133.6kbps, PSNR=59.55dB
```

**Two problems**:

1. **rvp9 PSNR stuck at 23 dB** — that's severely degraded quality. Hypothesis: `avg_frame_qindex_inter` initializes to `worst_quality=255` (libvpx-faithful, `vp9_rc_init:364`), and the EWMA `(3*prev + new)/4` only moves it down ~5%/frame. After 16 frames, ambient_q is still ≥150, which clamps `active_best = rtc_minq_approx(ambient_q) ≈ 190`. So the encoder picks Q ≥ 190 on every inter, giving severely degraded PSNR. RC.1's oracle saw this and noted a 60-frame warmup window; the 16-frame F12 test is well inside that warmup.
2. **Both encoders saturate against the corpus** — libvpx-stock also produces ~120 kbps actual regardless of target (55-59 dB PSNR — near-lossless on this short, easy content). 16 frames of testsrc at 256×256 doesn't have enough complexity to consume 1+ Mbps; libvpx ceilings at "I'm done, no point spending more". Same root cause noted in night-5's AQ.5 gate journal.

**Implications for RC.6 (final re-measurement)**:
- F12 + AQ.5 need ≥60 frames to escape the EWMA warmup. Currently set to 16 / 8.
- The testsrc corpus might not have enough complexity at 256×256. Larger crop (512×512 or 720p native) should help.
- We may want a second source with higher motion / texture density.
- Alternative: fix the init (start `avg_frame_qindex_inter` at a midpoint like 80, not worst_quality=255). This is a libvpx-divergence but a defensible one for short-sequence-bench scenarios. Decision: address in RC.6 dispatch.

The infrastructure is GREEN: both encoders run, both decoders verify, BD-rate function returns numbers when curves overlap. The issue is purely "we don't yet have enough frames + complexity to make the literal gate measurable." That's the RC.6 work.
