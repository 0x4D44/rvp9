## SCOPE RULES (read twice)

- **Everything libvpx/vpxenc does is IN-SCOPE.** If you find yourself thinking "this is an advanced feature for an edge case", that does not make it out-of-scope. Arthur has called full parity.
- **DO NOT use language like "MVP scope", "RT-only scope", "Phase 1 deferred", "advanced feature", "out of RT path".** Items are PORTED / PARTIAL / NOT PORTED / OUT-OF-SCOPE.
- The ONLY valid OUT-OF-SCOPE classifications are:
  - The item is absent from libvpx itself (cite the absence by showing the surrounding code OR confirming via libvpx-source grep).
  - The item is ARM SIMD (NEON/SVE) — out per Arthur 2026-05-25.
  - The item is GPU acceleration — libvpx is CPU-only.
- For every OUT-OF-SCOPE row, you must include a one-line justification with a libvpx-source citation (or the Arthur sign-off line).

## Citation rules (G3 lesson)

- Every row in the summary table must have a `libvpx file:line` citation for the function or feature in question. A bare function name is INSUFFICIENT.
- For PORTED rows: also cite the rvp9 `file:line` where the implementation lives AND where it is called from in the encoder hot path. Pattern-matching tokens in any file is not sufficient — you must confirm the call site is the function that actually runs at encode time.
- For PARTIAL rows: provide BOTH (a) what exists in rvp9 with `file:line`, AND (b) what is missing relative to libvpx with `file:line`.
- For NOT PORTED rows: grep across `crates/rvp9-encoder/` and `crates/rvp9-core/` for the function name AND for any obvious token from its libvpx body, to confirm genuine absence.

## Output format — MUST match the picker inventory exactly

Write a single markdown file at `{OUTPUT_PATH}` with these sections, IN THIS ORDER:

1. **Header**: title, date (2026-05-26), audit zone ID, scope statement (libvpx files + rvp9 files), method statement.
2. **Summary Table** — one row per identified helper/subsystem. Columns: `#`, `Helper / Subsystem`, `libvpx file:line`, `Status` (PORTED / PARTIAL / NOT PORTED / OUT OF SCOPE), `LOC (approx)`, `Quality Impact` (high / medium / low — your best read from libvpx context), `Dependencies`. The picker inventory has 45 rows for a 2820-LOC subsystem — yours should have a comparable rows-per-LOC density.
3. **Section-by-section narrative** — group items into logical sub-systems (e.g. for frame-loop driver: "Per-frame setup", "Tile dispatch", "Ref-buffer rotation", "Recode loop", "Post-encode bookkeeping", "Config / reconfig", "Cross-cutting"). For each item give a 1-3 sentence description of what libvpx does, then status + citations.
4. **PARTIAL Items Detail** table — for every PARTIAL row in the summary, a `What exists` vs `What is missing` row.
5. **Cross-cutting gaps** — items that aren't a single function but affect the whole subsystem (the picker inventory's "inter_mode_ctx hardcoded to 0" is the model).
6. **Porter's Checklist (Priority Order)** — your priority tiers (Tier 0..3) of NOT-PORTED + PARTIAL items by ROI (impact / LOC). Each tiered item gets a P-number, name, LOC estimate, and a "Why" sentence.

## Row-count sanity check

Before writing the final document, count your rows.
- If you have substantially fewer rows than the picker inventory's 45 for a subsystem of comparable LOC, you are missing items. Go back and re-audit.
- "Comparable LOC" means: divide your libvpx-source LOC by 2820 (picker baseline) to get a scale factor. Your row count should be in the same ballpark as 45 × scale_factor.
- This is a sanity check, not a hard requirement — but if you fall outside ~50%–150% of the expected band, you must justify the deviation in your method statement.

## Self-verification before declaring done

1. Pick 3 random "PORTED" rows. For each, re-grep `crates/` and confirm the function/path actually exists AND is called from the encoder hot path. Cite the call site.
2. Pick 3 random "NOT PORTED" rows. For each, grep `crates/` for the function name AND a key token from the libvpx implementation to confirm genuine absence.
3. Pick 3 random "PARTIAL" rows. For each, confirm BOTH the "what exists" citation and the "what is missing" citation are accurate.
4. Note any row where you are <80% confident in the classification — leave it as PARTIAL with an explicit "AUDIT-UNCERTAIN" tag and explanation.
