## Architectural calls taken (Arthur's "make sensible decisions" remit)

### Call 1: `TileCoefCtx` — **MOVE to rvp9-core**, not duplicate

Confirmed by inspection (`tile_ctx.rs:482-700`): `TileCoefCtx` is pure
data — `[Vec<u8>; 3]` per side, methods are slice arithmetic. No decoder-
specific imports. The sibling `TileDecodeCtx` already pulls from
`rvp9_core::mode_info::ModeInfo` + `rvp9_core::inter::mv_ref::*`, so
rvp9-core is already a dependency one direction. Promoting `TileCoefCtx`
to rvp9-core has no cycle risk.

Single source of truth > duplicate type. Decoder gets a re-export so the
existing `use crate::tile_ctx::{TileCoefCtx, combine_entropy_contexts}`
sites in `detokenize.rs` keep working.

### Call 2: Coef-source API into the writer — **flat slice per TX block, not a trait**

For `write_block_tokens` and `write_inter_block_leaf` integration, the
writer takes `coefs: &[i32]` + `eob: usize` per TX block (mirroring
`decode_coefs`'s `dq_coefs_out` parameter shape). No trait wrapping yet.

Rationale: the *caller* organizes coefs. For tests the caller passes
a single big zero vec. For a real encoder later, the caller is the
mode-decision driver which already has the coefs in hand (post forward-
DCT + quant). Adding a trait now is premature abstraction (the M8
ring-road anti-pattern from CLAUDE.md).

### Call 3: First non-skip test — **all-zero coefs**

Skip=false but every TX block has eob=0 and zero coefs. This is the
trivial proof-of-life: writer emits the EOB-at-pos-0 token for every
TX block; decoder reads it, runs inverse-transform-of-zero (identity),
adds to predictor (no change). Same pixel result as skip=true, but
the entire coef-encode/decode plumbing fires.

Non-zero coefs come AFTER skip=false plumbing is proven correct.
