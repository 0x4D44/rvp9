# 2026.05.27 — JRN — spatial SVC (resolution scalability) feasibility

## Outcome: BLOCKED on ENCODER (decoder is ready). DO NOT BUILD yet — scope is a multi-subsystem foundation, not a "smallest verifiable increment".

A18 follow-up after temporal SVC (dc53eec). Investigated feasibility of
landing VP9 **spatial SVC** (resolution scalability) in the encoder.
Verdict: the DECODER prerequisite is fully satisfied and validated; the
BLOCKER is entirely encoder-side. Spatial SVC needs four encoder
subsystems that do not exist today, and the minimal verifiable increment
still requires all four. Same discipline that parked HBD (A20) and the
compound-prediction blocker: honest blocker over an unverifiable build.

---

## PART 1 — DECODER reference-scaling: SUPPORTED + byte-exact validated

Spatial SVC's inter-layer prediction = a frame referencing a
DIFFERENT-resolution reference = VP9 reference scaling. The decoder side
is the critical prerequisite, and it is DONE.

### rvp9-decoder: full, production reference scaling

- `crates/rvp9-core/src/inter/scale.rs` — complete port of libvpx
  `vp9_scale.{c,h}`: `ScaleFactors` (`scale.rs:67`), `ScaleFactors::new`
  = `vp9_setup_scale_factors_for_frame` (`scale.rs:90`),
  `valid_ref_frame_size` (`scale.rs:157`), `is_scaled`/`is_valid`
  (`scale.rs:117-126`), and the `inter_predictor` dispatcher
  (`scale.rs:242`) that routes to `convolve8_scaled` /
  `convolve8_scaled_avg` when `sf.is_scaled()` (`scale.rs:303-327`).
- `crates/rvp9-decoder/src/reconstruct_inter.rs` — production scaled-MC
  path. Builds per-ref `ScaleFactors` at frame-header time
  (`reconstruct_inter.rs:207-240`, mirrors
  `vp9_decodeframe.c:2928-2935`), and inside the per-block driver runs
  the libvpx-faithful asymmetric scaled mapping (`reconstruct_inter.rs:
  376-402`): integer base from the PLANE coord, sub-pel mask from the
  LUMA coord, with the chroma off-by-one fix (`scale_mv` vs
  `scaled_buffer_offset` split).
- `crates/rvp9-decoder/src/lib.rs:2536-2560` — per-frame `ScaleFactors`
  array built for every active ref against the current frame's crop
  dims (`vp9_setup_scale_factors_for_frame` at frame start).

### EMPIRICAL PROOF: resize vector byte-exact

`vp90-2-05-resize.ivf` (CIF/QCIF 352x288 <-> 176x144 transitions — the
canonical libvpx reference-scaling corpus) decodes byte-exact:

```
RVP9_CONFORMANCE_PER_VECTOR=1 cargo test -p rvp9-harness --test conformance
  vp90-2-05-resize.ivf: 10 passed / 0 mismatched / 0 skipped
conformance: 201 passed / 0 mismatched / 0 skipped / 0 gated / 201 total
```

The resize vector carries inter frames whose reference is a different
resolution than the current frame — the EXACT mechanism spatial SVC
inter-layer prediction uses. rvp9-decoder reproduces libvpx's MD5s
exactly (D.24 fix at `conformance.rs:262-292` lit it from 3->10). The
conformance gate asserts `total_mismatched == 0` (hard zero,
`conformance.rs:252`), so reference scaling is a load-bearing,
regression-gated capability — not aspirational.

### vpxdec

vpxdec is libvpx's own decoder; reference scaling is native VP9 and
vpxdec has always supported it (it is how vpxdec plays the resize
corpus). A spatial-SVC superframe is standard VP9 (normal frames +
reference scaling), so vpxdec would decode it. Both arms of the
cross-decoder gate (vpxdec + rvp9-decoder) can validate a correctly-
encoded spatial-SVC stream.

**Decoder verdict: NOT blocked. Reference scaling is supported and
byte-exact validated on both decoders.**

## PART 2 — ENCODER: the blocker (four missing subsystems)

The encoder cannot produce a spatial-SVC stream today. Verified against
actual code, not self-reports:

### Blocker 2.1 — NO source downscaler (the hard one)

There is no image-resize / downsample / bilinear path for the SOURCE
frame anywhere in `crates/rvp9-encoder/src` (grep for
`downscale|resize|downsample|bilinear` on the encoder src: only doc
comments and unrelated `_scale` math; no scaler). Spatial SVC requires
each layer to encode a downscaled copy of the source. libvpx uses
`vp9_scale_and_extend_frame` (`vp9/common/vp9_scale.c` /
`vp9/encoder/vp9_encoder.c::scale_and_extend_frame`). This must be
ported and produce output the encoder AND decoder agree on. The
encoder's reconstruction must match the decoder's scaled-MC of the
upscaled base; if the downscale filter differs from what the bitstream
implies, the enhancement layer cannot be byte-exact.
Estimate: ~250-400 LOC (the resampler + border extend + wiring), plus
careful filter-parity work.

### Blocker 2.2 — encoder inter-prediction HARD-FORBIDS scaled refs

`crates/rvp9-encoder/src/lib.rs:5316` `build_inter_pred_plane_unscaled`
(the encoder's recon MC, called at `lib.rs:4871` and `:4924`) hardcodes
identity scale and asserts against scaling:

```rust
// lib.rs:5347-5349
let sf = ScaleFactors::new(ref_w, ref_h, ref_w, ref_h);  // identity
debug_assert!(!sf.is_scaled(), "F10.1c v1 encoder assumes identity ref scale");
```

The whole encoder MC / picker / motion-search pipeline assumes the
reference is the same resolution as the current frame. Inter-layer
prediction (referencing the upscaled lower layer) needs a scaled
encoder MC path AND scaled motion search (MV limits, ME ref reads in
`frame_loop.rs`, `me_ref_yuv`/`last_recon_yuv` at `lib.rs:2326-2374`).
Estimate: ~400-700 LOC (scaled recon + scaled-aware ME + MV-limit
adjustments), and it must be made byte-exact against the decoder's
scaled MC — the same multi-frame divergence-hunt cost that D.24 paid on
the decode side.

### Blocker 2.3 — single fixed resolution per encoder

`EncoderConfig::width`/`height` (`frame_loop.rs:142-144`) are set at
construction and never change. `encode_frame_delayed` validates the
source against the single configured size (`frame_loop.rs:1361-1371`).
Per-layer resolution needs either a re-architected per-layer encode
context or a resolution override per access unit. The config doc even
says "future stages ... 4d/e SVC will widen the surface"
(`frame_loop.rs:138`).
Estimate: ~150-300 LOC.

### Blocker 2.4 — per-layer ref/refresh routing + superframe assembly

- `SuperframeBuilder` (`crates/rvp9-core/src/bitstream/superframe.rs:145`)
  EXISTS and supports multi-frame packing (`push_frame`/`finish`,
  MAX_SUPERFRAME_FRAMES) — this part is ready (spatial layers DO
  superframe-pack, confirmed vs `vp9_svc_layercontext.c`; temporal do
  not). Reusable as-is.
- BUT the encoder's reference management is a 2-slot (LAST + GOLDEN/
  ALTREF) projection (`me_ref`/`last_recon`/`golden_recon`/altref). The
  spatial setters in `svc.rs:780-1049` assign `current_{lst,gld,alt}_fb_idx`
  into an 8-slot pool indexed by spatial layer. The buffer_pool
  (`crates/rvp9-encoder/src/buffer_pool.rs`, A10) tracks refcounts but
  the StreamEncoder does NOT yet route reads/refreshes through 8 owned
  slots per spatial layer. The inter-layer reference (upscaled base) has
  to live in a slot the enhancement layer reads.
  Estimate: ~300-500 LOC (per-layer pool ownership + refresh routing +
  access-unit superframe assembly + per-layer save/restore via the
  existing `svc.rs` scaffold).

### What's already done (reusable)

- `svc.rs` scaffold (1341 LOC): `Svc`/`LayerContext`/`alloc_layers`/
  save-restore + the spatial layer-id machinery (`layer_ids_to_idx`,
  `number_spatial_layers`) — ALL ported and test-backed. Temporal SVC
  (dc53eec) already activated it for the 1-spatial-layer path.
- `SuperframeBuilder` (core) — ready.
- Decoder reference scaling — ready + validated.

## PART 3 — Why NOT a "smallest verifiable increment"

The brief asked to scope to e.g. 2 spatial layers (half-res base +
full-res enhancement using the upscaled base). Even THAT minimal slice
requires ALL of 2.1 + 2.2 + 2.3 + 2.4: you cannot encode a half-res base
without a downscaler (2.1) and per-layer resolution (2.3); you cannot
make the enhancement layer reference the base without a scaled encoder
MC path (2.2) and the inter-layer ref slot (2.4). There is no bounded
sub-piece that produces a byte-exact spatial-SVC stream on its own. A
layered stream that is NOT byte-exact through a validating decoder
fails the PROOF requirement — exactly the "broken/unverifiable encoder"
the brief says to refuse.

The one genuinely independent, byte-exact-landable sub-piece would be
the **source downscaler (2.1) alone**, validated as a standalone
resampler against a libvpx `vp9_scale_and_extend_frame` reference
(unit-level differential test) — but that produces no SVC stream and no
layer structure, so it does not meet the A18 spatial-SVC deliverable.
It would be a prerequisite-only landing.

---

## Total estimate + recommendation

End-to-end minimal 2-layer spatial SVC, byte-exact:
**~1100-1900 LOC of new encoder code** on top of the ready scaffold +
SuperframeBuilder + decoder, dominated by:
- scaled encoder MC + scaled ME byte-exact vs decoder (2.2) — the
  riskiest (a divergence-hunt like D.24, multi-day),
- source downscaler with filter parity (2.1),
- per-layer pool/refresh routing + superframe assembly (2.4),
- per-layer resolution plumbing (2.3).

**Recommendation: DEFER spatial SVC (BLOCKER documented here). No code
landed.** The decoder is ready (a future spatial-SVC stream WILL
validate), so this is purely an encoder-foundation gap, not a wire/
decode-validity gap. It sits in the same deferral class as HBD (A20):
honest blocker until the scaled-encoder foundation (a scaled MC + ME
path proven byte-exact against the decoder's already-validated scaled
MC) is built as its own zone. If a bounded first step is wanted, land
**2.1 (the source downscaler) standalone** with a differential test vs
libvpx `vp9_scale_and_extend_frame` — a real, verifiable prerequisite —
before attempting the layered encode.
