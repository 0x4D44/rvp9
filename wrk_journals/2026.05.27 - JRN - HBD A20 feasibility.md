# 2026.05.27 — JRN — HBD A20 (u16 pixel pipeline) feasibility

**Verdict: BLOCKED on decoder HBD support. NEITHER available decoder can
validate a 10/12-bit VP9 stream, so an HBD encoder cannot be verified
end-to-end byte-exact. DO NOT build it. The blocker is decoder-side
(out of encoder scope); the decoder-HBD work is the documented Track T
(T-1) effort, ~2-3 weeks of scalar kernel porting.**

No code changed. The cross-decoder gate is untouched and stays green at
HEAD; `cargo build --workspace` (default) is clean; `cargo build
-p rvp9-core --features highbitdepth` is also clean (scaffold only).
This is the same "don't wire to a sink the producer can't legally feed"
discipline that correctly scoped down compound and ALTREF.

---

## Step 1 — rvp9-decoder HBD support: **NO (explicitly rejected)**

The decoder hard-rejects every 10/12-bit frame at the decode gate:

- `crates/rvp9-decoder/src/lib.rs:1264-1273` — `decode_frame` matches
  `frame.header.bit_depth`; `BitDepth::Eight => {}` falls through, but
  `BitDepth::Ten | BitDepth::Twelve` returns
  `DecodeError::UnsupportedProfile`. The comment (lib.rs:1251-1259)
  states this is a deliberate, bisectable gate "every per-block kernel
  below assumes 8-bit pixel storage."
- The dequant path is hard-coded 8-bit:
  `crates/rvp9-decoder/src/tile.rs:350-351` calls
  `dc_quant(.., BitDepth::Eight)` / `ac_quant(.., BitDepth::Eight)` with
  a comment that Phase 1 would thread the real `frame.header.bit_depth`.
- Reconstruction operates on `Box<[u8]>` plane storage
  (`crates/rvp9-core/src/frame.rs:6,186` — "8-bit only, owned
  `Box<[u8]>` backing"; `PlaneRef.data: &[u8]` at `frame.rs:1078`).

So the decoder parses the HBD header fine but cannot reconstruct a
10-bit frame.

## Step 2 — vpxdec (external oracle) HBD support: **NO (built without HBD)**

The gate invokes the canonical binary at
`D:\language\libvpx-stock\vpxdec.exe`
(`crates/rvp9-encoder/tests/cross_decoder_gate.rs:60,186-199`) with
`--codec=vp9 --i420 -o`. That binary is **libvpx v1.14.1 built without
high-bit-depth**:

- `D:\language\libvpx-stock\vpx_config.h:95` — `#define
  CONFIG_VP9_HIGHBITDEPTH 0`.
- `D:\language\libvpx-stock\vpx_config.asm` — `CONFIG_VP9_HIGHBITDEPTH
  equ 0`.
- `D:\language\libvpx-stock\config.log` configure line:
  `./configure --disable-vp8 --enable-vp9-decoder --enable-vp9-encoder
  --enable-static --disable-unit-tests --disable-docs` — **no
  `--enable-vp9-highbitdepth`**.

(The `CONFIG_VP9_HIGHBITDEPTH` string is present in the .exe only as the
config-symbol name; its compile-time value is 0.) A Profile 2/3 stream
fed to this vpxdec would be rejected, and `--i420` only emits 8-bit
output anyway — there is no HBD output container plumbed in the gate
(`yv12_to_i420_bytes` / `run_vpxdec` assume 1 byte/sample,
cross_decoder_gate.rs:116-199).

ffmpeg is a soft/PSNR-only oracle (not byte-exact authoritative) and is
not a substitute for an HBD reconstruction reference.

## Step 3 — consequence: HBD encoder is unverifiable

A byte-exact HBD encoder needs a byte-exact HBD decoder to validate
against. With **both** decoders unable to reconstruct 10/12-bit, any HBD
encoder we built would emit streams we could not prove correct. Building
it would violate G3 ("do NOT build an unverifiable HBD encoder").

## Scaffold state (what exists today)

The HBD scaffold is **metadata + 3 kernel functions**, nothing more:

- **`BitDepth { Bd8, Bd10, Bd12 }`** (the pixel-storage enum) —
  `crates/rvp9-core/src/lib.rs:78-87`; `Bd10`/`Bd12` are
  `#[cfg(feature = "highbitdepth")]`. Separate from the wire-format
  `bitstream::BitDepth { Eight, Ten, Twelve }`
  (`crates/rvp9-core/src/bitstream/frame.rs:91-98`).
- **`pub type Pixel = u8`** (keystone alias, `lib.rs:54`) and
  **`pub type HbdPixel = u16`** (`lib.rs:63-64`, feature-gated).
- **`EncoderConfig::bit_depth: BitDepth`**
  (`crates/rvp9-encoder/src/frame_loop.rs:214`) — its own doc
  (lines 205-210) says "**Currently a metadata field only** — kernel
  paths are u8 across the board." The encoder input `YuvFrameRef`
  (`frame_loop.rs:661-667`) is `&[u8]`; the wire header is hard-coded
  `WireBitDepth::Eight` (`frame_loop.rs:3806,4233`); the whole encoder
  pipeline (lookahead/buffer_pool/temporal_filter/TPL) is `Vec<u8>`.
  HBD is structurally unrepresentable on the encoder side today.
- **The entire existing HBD kernel inventory is 3 functions** (grep
  `fn highbd_` across core/decoder/encoder = 13 hits, 10 of which are
  unit tests):
  - `highbd_wraplow`, `highbd_clip_pixel_add`
    (`crates/rvp9-core/src/transforms/constants.rs:218,242`)
  - `highbd_idct4` + `highbd_idct4x4_16_add`
    (`crates/rvp9-core/src/transforms/inverse.rs:149,186`)
  - one dispatch slot `highbd_idct4x4_add`
    (`crates/rvp9-core/src/dsp/dispatch.rs:707,2094`) pointing at the
    scalar reference, **no decoder/encoder call sites** ("phase 0 has no
    decoder call sites").
- The doc references `dsp/highbd.rs` (`lib.rs:51`) but **that file does
  not exist** — there is no `dsp::highbd` kernel module.

`cargo build -p rvp9-core --features highbitdepth` compiles clean
(scaffold-only, no behavioural code).

## Recommendation

1. **A20 (HBD encoder) is BLOCKED** on a decoder that can reconstruct
   10/12-bit. That prerequisite is **Track T / T-1**
   (`wrk_docs/Track_T/T1_HBD_decode_HLD.md`), a documented ~2-3 week
   scalar decoder effort, and it is **out of encoder scope**.
2. **Do not land an HBD encoder increment now.** Even the smallest
   "keyframe-intra-DC 10-bit encode" cannot be proven byte-exact: no
   decoder validates it. Landing storage-only plumbing behind the flag
   would be premature-abstraction on-ramps-to-nowhere (we'd be guessing
   the shape of the u16 pipeline before the decoder pins it).
3. **Sequencing if Arthur wants HBD:** T-1 decoder first (gate it against
   the six 10-bit conformance vectors via a HBD-built vpxdec — which we'd
   also need to build, `--enable-vp9-highbitdepth`), THEN the A20 encoder
   against that now-validating decoder. Building a HBD vpxdec is the
   cheapest unblock for the *oracle* leg; the rvp9-decoder T-1 port is
   the larger of the two.

**Bottom line:** the keystone is missing. A20 stays parked until decoder
HBD (T-1) lands. The scaffold (`BitDepth`/`HbdPixel`/metadata field) is
correct and sufficient — it should NOT grow until there is something to
verify against.
