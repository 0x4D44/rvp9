### G.3 — diagnosis (CLOSED)

Findings written to `notes/G3-foreman-block-diff-findings.md`.

**Headline:** `find_mv_refs` returns `Mv::ZERO` for NEAREST 38 % of the
time on rvp9 vs 17 % on libvpx (100 kbps). For NEARMV: 27 % vs 0 %.
The NEAR gap is the cleanest signal — libvpx never produces (0,0)
NEARMVs; rvp9 produces them in 13-35 % of NEARMV picks across all four
bitrates.

This poisons motion compensation on ~16 % of inter blocks and feeds a
self-reinforcing cycle: zero NEAREST/NEAR → picker commits ZEROMV →
mi_grid populated with (0,0) → next block's `find_mv_refs` reads
those zeros → returns (0,0) → cycle continues.

Supporting evidence (all at 100 kbps):
- Over-partitioning: rvp9 64 % at 8×8 vs libvpx 41 %.
- NEWMV picked half as often (8 % vs 18 %).
- ZEROMV picked 3× as often (15 % vs 5 %).
- rvp9's NEWMV motion vectors are 6× larger mean magnitude (median
  34 vs 14, max 1610 vs 260) — independent diamond-search overshoot
  bug (F3, not the priority lever).
- rvp9 never picks GOLDEN (libvpx 0.6 %) — secondary cleanup item.
- Skip rate +7 pp on rvp9 (89 % vs 82 %).

### G.4 — picking the lever

Per the findings doc, L1: **when `find_mv_refs` returns
`mvs[0] == Mv::ZERO`, substitute the SB-level `int_pro` MV seed as the
NEAREST candidate** before the picker compares modes. This:

1. Injects a non-zero NEAREST when spatial+temporal salvage fails,
   so the picker has something useful to evaluate at NEAREST's low
   mode-rate cost.
2. Self-bootstraps the mi_grid out of the all-zero degenerate state.
3. Hooks into existing infrastructure — `int_pro` is already computed
   per-SB at `lib.rs:2654` and held in `sb_newmv_seed`.

Scope: ~50 LOC at `lib.rs::pick_and_simulate_inter_encode_partitions`'s
`build_mvc` callback. Risk: testsrc near-zero motion → int_pro
returns Mv::ZERO → substitution is a no-op there; low risk to the
testsrc halt threshold.

### G.4-attempt-1 — search-anchor swap in `run_newmv_search` (REVERTED)

**Hypothesis:** when `find_mv_refs` returns `Mv::ZERO` for NEAREST
AND `int_pro` provides a non-zero seed, switch the diamond's
`ref_mv` (cost-attractor) from `Mv::ZERO` to the seed. The picker's
bitstream-rate term stays honest (charges `mv_costs[mv - 0]`); only
the search anchor shifts.

**Wait —** swapping `mv_candidates.nearest` directly would break
cross-decode: the writer recomputes `best_ref_mv` from the mi_grid,
so changing the picker-side NEAREST while the decoder still reads
(0,0) would split the prediction. Limited the change to the
search-cost attractor only (the rate model stays aligned with the
bitstream).

**Result:** ~zero effect on the F.0.2 oracle re-run.
- Zero-NEAREST rate: 38% → 39% (slightly worse, within noise).
- Zero-NEAR rate: 27% → 29% (slightly worse).
- NEWMV count: 2,501 → 2,481 (basically unchanged).

The change either fires rarely (int_pro returns Mv::ZERO too often
on the SBs where find_mv_refs returns Mv::ZERO — likely correlated),
or the picker rejects what the diamond found because the bitstream
rate term still over-charges at high q.

**Reverted** (clean revert; no LOC delta on main).

### G.5-attempt-2 — partition threshold boost (REVERTED)

**Hypothesis:** rvp9's over-partitioning to 8×8 (64 % vs libvpx
41 %) consumes the bit budget on per-leaf overhead, forcing q up.
Boosting the small-res inter `t2` threshold (16→8 split) by 2×
unconditionally should reduce 8×8 partitioning and converge toward
libvpx's bsize distribution.

**Result:** distribution converged beautifully. PSNR cratered.

| metric | baseline | post-G.5 |
|---|---:|---:|
| rvp9 inter blocks (100 kbps) | 30,778 | 23,788 |
| 8×8 fraction | 64 % | 43 % (matches libvpx 41 %) |
| 16×16 fraction | 36 % | 57 % (matches libvpx 56 %) |
| NEWMV picks | 2,501 | 2,953 (+18 %) |
| **foreman PSNR-delta mean** | **+9.00 dB** | **+10.19 dB** (worse) |
| foreman 250 kbps PSNR | 27.22 dB | 23.43 dB (-3.8 dB collapse) |

The 250 kbps regression is the killer — at high bitrate, smaller
blocks ARE useful for capturing detail, and forcing fewer
partitions deprives the picker of that capability.

**Lesson:** matching libvpx's bsize distribution does NOT directly
imply matching libvpx's PSNR. libvpx achieves 41 % 8×8 AND high
PSNR; rvp9 at 43 % 8×8 lost PSNR. So libvpx's 8×8 leaves must be
doing MUCH better per-leaf work than rvp9's, and partition density
isn't the load-bearing factor.

**Reverted** (clean revert; no LOC delta on main).

### Why I'm closing the session here

Two single-knob interventions targeting the F.0.2 findings both
failed (one neutral, one regressive). The E13 oracle shows the
diamond is healthy on its own; the failure mode is in the
RC × partition × rate-model coupling.

The remaining genuine levers identified are multi-day architectural
items that need design discussion before code:

1. **RC q-saturation fix.** rvp9 hits its target bitrate at ~+25 %
   overshoot vs libvpx's +43 %. Letting rvp9 overshoot more would
   drop q and unlock NEWMV. This is RC-tuning, not picker work.
   Risk: regressing the carefully-built Track E rate-control
   convergence.
2. **Per-leaf prediction quality at small block sizes.** libvpx's
   8×8 leaves produce much better predictions than rvp9's same-size
   leaves. The reason isn't bsize density (G.5 proved that). Probably
   a combination of: better int_pro seed precision, better sub-pel
   refinement, `vp9_refining_search_8p_c` port (L-08 not done),
   `accurate_sub_pel_search` (L-05 stubbed).
3. **Intra-in-inter evaluation widening.** rvp9 has 1.7 % intra in
   inter frames vs libvpx 1.6 % — close but the modes differ; rvp9
   has many D207/D135/D45 picks where libvpx has DC/H/V. The intra
   picker's mode set or candidate selection differs.

These are HLD-driven sub-tracks, not autonomous one-session work.
