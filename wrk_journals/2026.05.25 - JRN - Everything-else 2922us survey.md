## §3 — Lever candidates ranked

Ranking: predicted µs cut × ease (LOC, risk). All numbers assume Lever B (row-MT LF) lands cleanly and brings LF to ~300 µs.

### #1 — Tile workload balancing (decode side) — **biggest single µs target**

The "join" line is the biggest item in §1. P95 join = 3 513 µs, median = 1 131 µs → **3.1× spread**. The slowest tile is dragging the frame. Two flavours:

- **(1a) Within-tile row-MT decode** (libvpx's `pbi->row_mt = 1` mode, `vp9_decodeframe.c:2325`). Multiple workers pipeline rows of the same tile, signalling progress. *This is the libvpx fast-decoder mode rvp9 has not ported.* Predicted cut: **~300-600 µs** (collapses join tail when tile-row work is uneven).
- **(1b) Static tile re-balance via column shifting** (not legal — encoder owns the tile boundaries) — not viable.

| | |
|---|---|
| Predicted µs cut | 300-600 µs |
| LOC | 400-700 (port row-MT decode + signal protocol) |
| Risk | high (conformance; complex sync; libvpx ref impl exists) |
| Lever-B compatible | yes — both row-MT decode and row-MT LF can share the SAME scope (single-scope topology — see Wave 7 HLD) |

### #2 — Remove `extend_frame_borders` from decode path

Pure libvpx-conformance cleanup. Decoder doesn't need the border extension — MC border reads handle on-demand. **Verify rvp9-encoder doesn't depend on the decoder writing borders.**

| | |
|---|---|
| Predicted µs cut | ~85 µs (full reclaim) |
| LOC | ~5 (delete two call sites + tests) |
| Risk | low if rvp9-encoder is independent; medium if encoder reads decoded borders |
| Lever-B compatible | yes (independent) |

### #3 — Pool the Yv12Buffer allocation

Replace `Yv12Buffer::alloc` per frame with pool-pull (same pattern as `tile_seg_id_pool`). The pool already exists for the `frame_pool` slot, but the *output buffer for the new frame* is freshly allocated each call (`lib.rs:1472`). Either:

- (3a) Allocate from `frame_pool` immediately and write into it (libvpx-faithful)
- (3b) Add a `Decoder::yv12_pool: Vec<Yv12Buffer>` recycling list

| | |
|---|---|
| Predicted µs cut | 120-200 µs |
| LOC | 30-60 |
| Risk | low (Arc lifecycle, ref-count semantics need care but follow `tile_seg_id_pool` pattern) |
| Lever-B compatible | yes |

### #4 — Single-scope topology (merge tile-decode + LF into one `WorkerPool::scope`)

Wave 7 HLD lays this out (`wrk_docs/2026.05.25 - HLD - Wave 7 intra-scope LF mask build.md`). Tile workers stream `decode_progress[r]` Releases; LF workers Acquire-gate. Both share one scope → halves the scope open/close + cross-frame thread-park latency.

| | |
|---|---|
| Predicted µs cut | 100-200 µs (scope amortisation + reduced kernel-park) |
| LOC | 200-400 (single-scope dispatcher, signal protocol, conformance tests) |
| Risk | medium (atomic-ordering bugs, no libvpx 1:1 ref but similar to its `row_mt` flag) |
| Lever-B compatible | **converges with** Lever B — Wave 7 explicitly defined for the post-row-MT-LF world |

### #5 — Drop the `frame_mi_grid` `Option<>` wrap

Wave 5b pre-fills with `Some(default_padding_modeinfo())`. If padding is sentinel-detectable inside `setup_mask`, the slab can be `Vec<ModeInfo>` directly. Saves the per-cell `Some(...)` write at frame start (~60-100 µs) AND the `expect` in `setup_mask`.

| | |
|---|---|
| Predicted µs cut | 60-100 µs |
| LOC | 50-100 (cell type change, callsite cleanup, sentinel design) |
| Risk | medium (sentinel value must not collide with legal ModeInfo; Wave 5b carefully chose this shape so the touch is invasive) |
| Lever-B compatible | yes |

## §4 — The 2× math

Goal: `frame ≤ 2 × vpxdec = 982 µs`. Today: 4 050 µs.

| Scenario | LF | Else | Frame | Ratio vs 491 µs |
|---|---:|---:|---:|---:|
| Today | 1 128 | 2 922 | 4 050 | 8.25× |
| + Lever B perfect | 300 | 2 922 | 3 222 | 6.56× |
| + #2 borders removed | 300 | 2 837 | 3 137 | 6.39× |
| + #3 yv12 pool | 300 | 2 687 | 2 987 | 6.08× |
| + #5 mi-grid wrap drop | 300 | 2 607 | 2 907 | 5.92× |
| + #1 row-MT decode (-450) | 300 | 2 157 | 2 457 | 5.00× |
| + #4 single-scope (-150) | 300 | 2 007 | 2 307 | 4.70× |

After **all five #1-#5 levers AND Lever B**, the projection is ~2 300 µs frame → **4.7× vpxdec**. Still not 2×. To hit 982 µs we need to cut another ~1 300 µs from the tile-decode join wall — i.e. **the tile_decode parallel work itself must shrink by ~60%**, not just its scheduling/serial complement.

**Honest conclusion:** 2× is *not reachable* via parallelism rebalancing alone. The tile_decode parallel wall today is ~1 100-2 000 µs even idealised; vpxdec hits ~491 µs total frame, so its tile_decode wall is at most ~400 µs. We are ~3-5× behind libvpx on **the kernels that run inside tile_decode** (MC, IDCT, BoolReader, detokenize, etc.) when scaled per-thread.

The only paths to 2× I can see are:
1. **Lever A — frame pipelining** (decode frame N+1 in parallel with display/refs from frame N). Doubles steady-state throughput without changing per-frame work. Reaches 2× if per-frame work doesn't get worse. Major architectural change; conformance neutral (different threading model, not different bits).
2. **Kernel-level catch-up on tile_decode internals** — convolve8_horiz wider SIMD (W3), BoolReader inline-asm (T-3 said no), detokenize hot-path tightening, IDCT sparse-EOB further (W1 already done). Each is 3-10% of frame at best; cumulative ~30% reachable, gets us to ~3× not 2×.

**For tomorrow's planning: 2× requires Lever A. Lever B + #1-#5 gets us to ~4-5×. We should communicate this honestly to whoever set the 2× target.**

## §5 — Tomorrow's decision menu

Four distinct paths, in increasing scope:

### Path A — "Finish what we started, ship the singles" (1-2 days)

Land Lever B (row-MT LF, in flight). Do #2 (kill border extend, ~5 LOC, ~85 µs) and #3 (yv12 pool, ~50 LOC, ~150 µs) as low-risk pure-wins. Expected outcome: **frame ~2 900-3 000 µs, ratio ~6×**. Not 2× but defensible-shippable. Avoids any new architectural work.

### Path B — "Convergence with the libvpx fast decoder" (1-2 weeks)

Land Lever B, then #1 (row-MT *decode*, the libvpx `row_mt=1` flag we never ported) + #4 (single-scope topology). Wave 7 HLD already sketches the merger. Expected outcome: **frame ~2 300-2 500 µs, ratio ~4.7-5×**. Major effort, conformance-risk, but ports a known-working libvpx pattern with a clear reference impl.

### Path C — "Frame pipelining" (2-4 weeks; what 2× actually needs)

Architect Lever A: decode frame N+1 on a side worker pool while the caller-thread does ref-management + display for frame N. This requires:
- Per-frame state isolation (`Decoder` becomes Send+Sync via per-frame contexts)
- Ref-frame ownership rules (libvpx uses ref-counted YV12 buffers via `vpx_ref_frame_buffer_pool_t`)
- API decision (sync caller wants one frame back; pipeline wants N-of-N-in-flight)

Expected outcome: **steady-state ratio close to 2×** even if per-frame work doesn't shrink, because the caller-side serial work hides behind the prior frame's decode. **The only path to 2× we have.**

### Path D — "Re-measure first, then choose" (0.5 day, then re-plan)

Today's 2 922 µs is reconstructed from ledger data; it might be hiding a regression in the tile-decode join wall (note the §1 gap: ledger says ~1 476 µs non-LF, today's diagnostic says 2 922 µs). Before committing to A/B/C, **rerun `profile-tiles` on testsrc_1080p30 t=4 with the current build** (including whatever Lever B intermediate state is in tree) and confirm the per-bucket numbers. If join has actually grown to ~2 000 µs since the post-W1+W4 ledger, that's a *regression* to investigate before any new optimisation work.

**My recommendation:** **Path D first (0.5 day), then Path A while Path C is being designed.** Path C is the only 2× path; A is the "ship a respectable number" path; B is overkill compared to A and undershoot compared to C.
