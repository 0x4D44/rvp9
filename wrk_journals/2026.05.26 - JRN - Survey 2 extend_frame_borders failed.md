**Author:** team-lead (autonomous)

## What I tried

Survey `wrk_journals/2026.05.25 - JRN - Everything-else 2922us survey.md` §3 #2 claimed:

> `extend_frame_borders` called per-frame in rvp9 (`lib.rs:2058, 3194`); libvpx does NOT call it in the decode path → ~85 µs/frame waste.
> **~85 µs/frame pure waste vs libvpx.** Pure-win removal candidate.
> (Caveat: encoder still uses this output as ref; verify rvp9-encoder doesn't depend on it.)

I verified:
- libvpx claim is correct: `vpx_extend_frame_borders` is called ONLY in `vp9/encoder/*` files, never in `vp9/decoder/*`.
- Encoder claim is correct: `rvp9-encoder` does NOT consume the decoder's `extend_frame_borders` output (grep returned 0 matches in encoder paths).
- rvp9 DOES have a `build_mc_border` function at `crates/rvp9-decoder/src/reconstruct_inter.rs:971` mirroring libvpx's lazy on-demand border extension.

I removed the two `extend_frame_borders(&mut yv12);` calls + their timing wrappers from `crates/rvp9-decoder/src/lib.rs` (intra path :2059, inter path :3196), plus the unused `use` statement.

## What broke

Conformance went **201/201 → 14/201 (187 mismatched)** on BOTH default-on column-wavefront AND `RVP9_DISABLE_LF_MT=1` serial paths. Same failure profile on both LF paths confirms the bug is in MC inter prediction, not LF.

## Why the survey was wrong

The survey assumed rvp9's `build_mc_border` covered the same cases as libvpx's lazy path. But the **187 mismatched frames** prove rvp9's MC code has at least one inter-prediction read path that goes through the YV12 buffer's border region *directly* (without invoking `build_mc_border`), and relied on `extend_frame_borders` having pre-populated that region.

Candidate culprits (NOT investigated — out of scope tonight):
- Sub-pel MC reads that don't cross the visible boundary but go through the 7-tap filter's tail
- 16-tap H-filter reads on the LF path? (No — LF doesn't touch border)
- Direct frame buffer reads in the MC path that bypass `build_mc_border`
- Subsample chroma reads at the boundary

## Recovery

Reverted via Edit tool (not git restore — staying within CLAUDE.md's non-destructive constraint). 3 edits to put back the calls + `use` statement. Build green; conformance back to 201/201.

No commits authored or amended. The working tree is now clean (only `m third_party/libvpx` submodule remains, not mine).

## Lesson

The survey's "pure-win removal candidate" framing was overconfident. A "libvpx doesn't do X" finding is necessary but not sufficient — rvp9 must also have the compensating mechanism that libvpx uses to handle the case X covered. **The next-time check**: before removing any per-frame work, identify what fills the gap on the libvpx side and confirm rvp9 has it implemented at full coverage (not just "the function exists").

For #2 to become viable as a real lever:
1. Audit rvp9's MC code paths comprehensively
2. Identify which paths bypass `build_mc_border` and read raw frame buffer pixels in the border region
3. Either route them through `build_mc_border` OR keep `extend_frame_borders` for those paths only

That's an 80-200 LOC audit-driven refactor, not a 5-LOC removal. Survey #2 is downgraded from "low risk, 5 LOC" to "medium risk, audit-first, ~1 day."
