Diagnosis:
- Direct `LookaheadCtx::push` validated tight plane sizes (`w * h`, chroma analogue)
  and `stride >= row_width`, then copied each row from
  `row * stride .. row * stride + row_width`. A padded-stride buffer could pass
  validation but panic on a later row.
- `StreamEncoder::encode_frame_delayed` validated public `YuvFrameRef` buffers with
  unchecked `stride * rows`; oversized strides could panic in debug before returning
  `EncodeError::InvalidConfig`, and could wrap in release.
- Three read-only skeptic agents checked the diagnosis. Two found no blockers; one
  found a helper-contract mismatch for zero-size planes, so I tightened
  `strided_plane_covers` and added a helper-level regression.

Red-before-green evidence:
- `$null | mdtimeout 120 cargo test -p rvp9-encoder lookahead::tests::push_rejects_strided_short_plane_without_panicking -- --exact`
  failed by panicking at `lookahead.rs` with "range end index 272 out of range for
  slice of length 256".
- `$null | mdtimeout 120 cargo test -p rvp9-encoder frame_loop::tests::encode_frame_rejects_overflowing_y_stride -- --exact`
  failed by panicking at `frame_loop.rs` on unchecked multiplication overflow.

Fix:
- Added checked row-window extent validation:
  `(rows - 1).checked_mul(stride).and_then(|base| base.checked_add(row_width))`.
- Reused the helper from both public stream validation and direct lookahead push.
- Updated `YuvFrameRef` docs to describe row-window coverage rather than requiring
  full `stride * rows` backing after the last visible row.
- Added / kept regressions for direct short strided lookahead input and stream-level
  overflowing luma stride.
- Ran the code-reviewer pass locally; after applying the skeptic zero-size helper
  markup, it found no remaining blocking findings.
- Bumped the workspace package version to `0.1.9`.
