# 2026.08.19 — JRN — Overnight code-review pass over `crates/rvp9-cli/`

Read-only review pass. Area assigned by the driver: `crates/rvp9-cli/`, which the
coverage ledger showed last reviewed 2026-07-07 (STALE, 43 days) and which has
changed since — spatial-SVC CLI, `--frame-time-csv`, and the `EncoderParallelism`

## What I did

Read the whole crate myself (four source files, four test files, `Cargo.toml`),
then ran three agents in parallel: two adversarial verifiers each briefed to
*refute* one of my two headline findings, and a standing devil's advocate. Both
verifiers came back CONFIRMED with independent line citations. The devil's
advocate raised eight further candidates; I re-verified each against source
before believing any of them, and the split was instructive — three promoted
(two bug drafts, one note), three demoted to notes because the behaviour was
real but not a defect, two left as speculative.

Output: `wrk_docs/2026.08.19 - CR - 20260819-REV-RVP9-CLA@CRUCIBLE-code-review-154318.md`
with five bug drafts and one req draft, plus the coverage artifact.

## What I found

1. **`--passes 2` silently ignores `--threads` and `--tile-columns`** (Medium).
   `run()` returns into `run_two_pass` *before* `build_encoder_parallelism` is
   ever called, and `encode_two_pass` has no parallelism parameter at all — it
   builds `StreamEncoder::new`, i.e. `SINGLE_THREADED` (1 thread, log2 tile cols
   0), against the one-pass defaults of 8 and 6. Tile columns are written into
   the VP9 frame header, so the user's request silently fails to reach the
   bitstream while `--help` keeps calling both flags `[supported]`.

2. **`rvp9dec --y4m` corrupts output on a mid-stream resolution change** (Medium).
   The YUV4MPEG2 header is written once from the first displayed frame; later
   frames are emitted at their own geometry with no check. The repo's own
   `vp90-2-05-resize.ivf` reproduces it, and libvpx's remedy (`vpxdec --scale`)
   is a warn-only no-op here, so there is no workaround. Raw `--i420`/`--yv12`
   share the flaw.

3. **Silent clamping of out-of-range `--min-q`/`--max-q`/`--cq-level`/
   `--noise-sensitivity`** (Low), where sibling flags in the same table reject.

4. **`--inter-layer-pred` is validated and then discarded** unless
   `--spatial-layers > 1` (Low) — a second, independent instance of finding 1's
   class, found by the devil's advocate.

5. **Every non-SVC CLI test fixture is square 64×64** (Low) — a width/height
   transposition anywhere in the CLI would pass the whole suite.

## Surprises worth keeping

- **Finding 1 is a recurrence, not a new class.** RVP9-BUG-KILN-00050 was closed
  on 2026-07-31 by demoting every unplumbed flag to `apply: None`, and its
  closure note explicitly checked the converse direction — "every flag left as
  `apply: Some` is genuinely consumed by the config builder". That audit was
  true and is still true *for the one-pass path*. `--threads`/`--tile-columns`
  were later re-plumbed for one-pass and spatial, and the two-pass path was
  simply not revisited. A point-in-time audit cannot hold a contract that a new
  code path can break; that observation is what DRAFT-REQ-1 asks for as a
  mechanical oracle.

- **A correct, passing test can hide finding 2.**
  `dec_y4m_single_header_then_per_frame_tags` asserts "exactly one YUV4MPEG2
  header for the stream" — right for its constant-size fixture, and green while
  the bug is live. The conformance suites *do* exercise resize vectors, but they
  drive `Decoder` directly and compare MD5s of the visible buffer, never routing
  through the CLI's Y4M writer. The gap is precisely at the seam between two
  well-tested things.

- **A square test fixture cannot tell width from height.** Both CLI test files
  fix `W = H = 64`, so nearly every test in the crate is blind to a dimension
  swap. The one non-square fixture in the crate (256×128) exists only in the
  spatial-SVC test. This is the "fixture whose fields all hold the same value"
  trap, sitting under a large and otherwise genuinely good suite — the CLI tests
  are unusually disciplined about asserting user-visible contracts rather than
  internal state, which is probably why nobody looked at the fixture itself.

- **The devil's advocate earned its keep, but only after re-verification.**
  Of its eight candidates, three survived as reportable and three were real
  behaviours that are not defects — a required-argument flag swallowing the next
  token is plain `getopt` semantics, and truncating an existing `-o` file after
  the first emitted frame is inherent to streaming. Taking them at face value
  would have put three plausible-but-wrong items in the ledger.

- **A comment documented a guard that does not exist.** The
  `--noise-sensitivity` PROOF test says "the parser's range-check should catch
  this too" — there is no parser range check. That sentence is why the missing
  validation read as intentional.

## Dedup work that paid off

Three plausible findings turned out to be already-tracked or deliberate, and
were not re-filed: the partial IVF left after a failed encode (Open as
RVP9-BUG-KILN-00065), two-pass whole-sequence memory residency (explicitly
permitted in RVP9-BUG-KILN-00053's closure), and `--summary` counting skipped
frames as "showed" (pinned deliberately for vpxdec byte-compatibility).

## Blocked

`deltic bugs new` / `deltic reqs new` need a shell, and this session's permission
mode denies both Bash and PowerShell outright. IDs must not be hand-derived — the
number space is host-wide and shared across `bugs/`, `reqs/` and `issues/` across
sibling worktrees, so `max+1` over one ledger reissues a number another holds and
git merges the collision silently. The drafts are therefore written out in full
in the CR report, ready to mint verbatim. Until minted they are **not** in the
Open queue the fix-loop drains. The `crates/rvp9-bench/` pass earlier today hit
the identical blockade and took the identical route.

Nothing was executed this pass — no build, test, clippy or binary run. Every
claim in the report is from reading source at cited lines.
