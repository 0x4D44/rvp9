## Step 2 — 256-bit kernel implementation (libvpx pattern)

Wrote a 256-bit `_mm256_maddubs_epi16` kernel mirroring libvpx's
`vpx_filter_block1d16_h8_x_avx2` (third_party/libvpx/vpx_dsp/x86/
vpx_subpixel_8t_intrin_avx2.c:63-153). Key design choice: **process 2 rows
in parallel**, one per YMM lane. All shuffles and maddubs are lane-local —
no cross-lane permutes in the hot path; the only cross-lane operation is the
`vinserti128`-style load that builds the YMM input from two `_mm_loadu_si128`
results, which executes once per (pair-of-rows x 16 columns).

This is **fundamentally different from the prior agent's attempt** — they
apparently tried to fit 16 cols of a single row into a YMM, which requires
cross-lane shuffles or wider permutes and is the regression they hit.

- Inner kernel: `horiz_two_rows_256` — 16 cols per outer iter via two
  16-byte loads (`src+x-3` and `src+x+5`), 8 shuffles, 8 maddubs across both
  lanes. Pack interleaves both rows; `castsi256_si128` writes row Y, lane-1
  extract writes row Y+1.
- Width fallback: `w < 16` falls through to the 128-bit per-row kernel
  (same math, lower throughput — fine for the rare narrow blocks).
- Odd-row tail: if `h & 1 != 0` the final row also uses the 128-bit kernel.

## Hypothesis on what's happening

The pinned dsp-microbench has the kernel called back-to-back ~8000 times per
batch, in a tight loop with hot icache + hot dcache. End-to-end decode has
the kernel called from inside the inter-prediction stage interleaved with
~100 different functions per block: entropy decode, partition context,
ScaleFactors, dqcoeff, idct, loopfilter, etc. The differences this can drive
include:

1. **AVX2 per-core power state**. Modern Intel cores enter a deeper AVX state
   only when sustained 256-bit pressure passes a threshold (Intel calls these
   "frequency licensing" states; AVX1 = L1 license, AVX2 = L2 license). The
   128-bit kernel keeps the core in L0/L1; the 256-bit kernel pushes it into
   L2 briefly per block, then transitions back. The transition latency is
   real (1-100 us on the literature) and is dominated by the 256-bit
   *enable*, not the work itself. For a kernel that runs 1-2 us per call,
   the transition overhead can swamp the work savings. The microbench hides
   this by staying in L2 for the whole batch.

2. **L1d cache thrash from the per-pair scratch copy**. The new kernel
   allocates TWO 80-byte scratches per pair iteration (vs one per row in
   the 128-bit version). At pair-rate that's 32x more scratch write traffic
   for a 64x64 block. The microbench batches over the same `src` slice
   8000x and probably caches that scratch behavior away; real decode hits
   fresh source data every block.

3. **µop-cache / front-end pressure**. The 256-bit kernel uses larger
   shuffle masks (32-byte `_mm256_setr_epi8` initialisers) and YMM intrinsics
   that decode to slightly more µops per instruction. In a hot tight loop
   that all hits the LSD/µop-cache; in real decode the µop cache is shared
   with everything else and may be cold-fetching.

4. **Decoder code that runs MORE per-block now**. If the new kernel finishes
   faster, the surrounding decoder code (which is the bottleneck) runs
   slightly more often per unit time. If that code has any cache or branch
   penalties, the apparent regression could be a wallclock-vs-throughput
   artefact. **This is the most likely culprit IMO** — the per-block decode
   cost is dominated by entropy/tile mgmt, not by SIMD; making the SIMD
   faster just lets the decoder spin its wheels on the non-SIMD bottleneck.

Hypothesis (4) implies the headline ratio is bottlenecked by something OTHER
than convolve8_horiz, and that improving it just exposes the next bottleneck
(which the 256-bit kernel may incidentally make slightly worse via icache/
prefetch displacement).

## Decision

Per task spec: keep code in worktree, **do not merge**. The kernel is
provably 40% faster in isolation but provably regresses the only metric that
matters (end-to-end wallclock). Until the decoder bottleneck driving (4) is
identified, the 256-bit horiz is dead weight at best.

## Recommendation

The pinned bench discipline is valuable and should land regardless of the
kernel decision — it dropped run-to-run noise from 25% to <8% on the
microbench. Suggest committing just `scripts/bench-pin.ps1` plus the
dsp-microbench horiz case (no kernel change) as a separate small PR, so
future SIMD experiments have a reliable measurement floor.

The 256-bit kernel itself should sit on a branch until either:
- The end-to-end bottleneck driving (4) is identified and fixed (most likely
  in entropy decode or tile management), AT WHICH POINT the kernel speed
  should become visible.
- An A/B test under the bench shows the 256-bit kernel winning on a
  representative fixture — this run is conclusive evidence that it does not
  under the current decoder shape.
