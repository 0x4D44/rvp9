  v1.14.1 (libvpx-stock build at `D:/language/libvpx-stock/`) and

- **Build path that worked:** option (b) — MinGW gcc 15.2 via msys2.
  libvpx-stock was already configured + built for `x86_64-win64-gcc`,
  so we link against `libvpx.a` + reuse its `vpx_config.h`. The
  oracle `#include`s libvpx's `vp9_detokenize.c` and exposes a
  wrapper that builds a minimal `MACROBLOCKD` (mi[0].ref_frame[0]=0
  for intra; fc->coef_probs filled with the captured slice) and
  pokes the captured `(value,range,count,pos)` directly into
  `vpx_reader`. Built first try.
- **Oracle result on the M.6 snapshot:**
  - libvpx `decode_coefs` output **= rvp9 production output** —
    both produce `[177, 0, 0, 0, -693, -231, 0, 0, 462, 231, 0, 0,
    231, 231, 231, -231]`. **decode_coefs is bit-exact.** That
    finally puts decode_coefs to rest.
  - But the oracle's `vp9_iht4x4_16_add_c(DCT_ADST, ...)` on those
    dq_coefs gives residual row 0 = `[+2, +2, -14, -3]`, while
    rvp9's `iht4x4_16_add` gives `[+15, +9, -16, +3]` — diverge
    on every cell. M.1 was right; iht4x4 IS the bug.
  - Drilling deeper via the oracle's intermediate-state probes:
    - rvp9's row-pass intermediate matches libvpx exactly:
      row 1 = `[-703, -578, -402, -277]` etc.
    - rvp9's col-pass output matches libvpx exactly:
      col 0 = `[242, -1092, 30, 872]` etc.
    - But the **final residual** differs.
  - The only thing left between "col-pass output" and "final
    residual" is the row/col **interpretation** — and that's where
    the bug lives.
- **Root cause:** libvpx's `transform_2d` struct in
  `vp9/common/vp9_idct.h:29-31` is:
  ```c
  typedef struct { transform_1d cols, rows; } transform_2d;
  ```
  `cols` is the FIRST field. So
  `IHT_4[DCT_ADST] = { idct4_c, iadst4_c }` actually means
  `cols=idct4_c, rows=iadst4_c` — i.e. **for DCT_ADST: row-pass =
  iadst4, col-pass = idct4** (the OPPOSITE of what you'd read as
  English). For ADST_DCT it's the converse swap.
  - rvp9's `iht_4_dispatch` (and `iht_8_dispatch` / `iht_16_dispatch`)
