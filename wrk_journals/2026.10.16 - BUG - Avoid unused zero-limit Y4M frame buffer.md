# Avoid unused zero-limit Y4M frame buffer — KIL-00096

The queue selected KIL-00096. `Y4mReader::open` validates the header and crop, then unconditionally allocates its source-sized frame buffer. Both next-frame APIs already stop before reading anything when the configured frame limit is zero. The allocation is therefore unused for that request, including a valid maximum-size header whose frame body would occupy 384 MiB.

The repair leaves the source body vector empty only for a zero frame limit, after all existing header and crop validation. Active readers retain their current allocation layout. This preserves the separately benchmarked active-read behavior and avoids changing the API or making active allocations lazy.

The new internal regression first checks an 8×8 full-size zero-limit reader: the unmodified constructor failed its capacity assertion with `96 != 0` (one test selected and executed). Root read the raw red log. That small assertion precedes the maximum-size header case, preventing the old-code proof from allocating 384 MiB. The regression also covers a cropped zero-limit reader, both next-frame APIs, unchanged caller planes, preserved source metadata, invalid-header and invalid-crop rejection, and the valid 16384×16384 header with an empty body. After the repair, the worker observed the focused regression pass (one test) and all 28 Y4M tests pass. Root independently ran the complete I/O library unit target: all 61 tests passed, including active full-frame/cropped reads and the new regression. Formatting, scoped `cargo clippy -p rvp9-io --all-targets` (no warnings in the inspected output), and whitespace checks passed. The preselected final smoke is `TMPDIR="$PWD/.scratch" deltic timeout 60 cargo test -p rvp9-io --lib y4m::tests:: -- --nocapture </dev/null`. This pass makes no codec performance or conformance claim.
