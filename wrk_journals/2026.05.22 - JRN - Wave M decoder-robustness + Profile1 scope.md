Two follow-ups inherited from the Wave L closeout:

1. **Decoder-robustness gap (M1).** Our decoder is bit-exact vs the official 201-vector
   corpus and every SIMD kernel is bit-exact vs scalar, yet it mismatches a *default*
   `vpxenc` foreman encode on ~1/10 frames. **Keyframe decodes clean; an inter frame
   diverges** → bug is in an inter-only path that a default encode exercises but the
   starter corpus doesn't. Pre-existing, not a Wave L regression. Plan: differential
   bisect against `vpxdec` (the oracle), localize the diverging frame, fingerprint its
   compressed-header flags, feature-isolate via `encode-corpus.ps1` toggles, then fix.

   Candidate ranking (most→least likely):
   - Compound prediction (default vpxenc keeps `--auto-alt-ref=1` → bi-dir compound; our
     `encode-corpus.ps1` *disables* it, so a bare-vpxenc repro is the suspect path).
   - Switchable interp filter (per-block EIGHTTAP / SMOOTH / SHARP).
   - Loopfilter mode/ref deltas; segmentation (lower probability).
   - NOT the MC kernels — proven bit-exact vs scalar + corpus-green.

2. **Profile 1 decode (M2).** Genuinely engineering-gated: lift the 4:2:0-only
   invariant (recon plane dims, inter chroma MV derivation, intra chroma sizing,
   transform/recon chroma loops, loopfilter chroma) + lift the `UnsupportedProfile`
   gate. Wave-sized. Deliverable for M2 is a **scope/HLD doc**, not the implementation.

- **M1 agent #3 ROOT CAUSE (libvpx oracle trace, 135 tool-uses) — DEFINITIVE:**
  - Both decoders agree bit-for-bit through the mode-info of intra block mi=(10,24)
    BLOCK_16X8 (post-modeinfo cursor identical in both). Desync is the FIRST luma token
    read of that block: libvpx uses coef-prob EOB=125 (= `DEFAULT_COEF_PROBS_8X8[0][0][0]
    [0]`), rvp9 uses a wrongly-ADAPTED 91. Same count delta, different `range` after the
    read ⇒ only the probability differs.
  - **Root cause:** the foreman encode sets `error_resilient=0, refresh_frame_context=1,
    frame_parallel_decoding_mode=1` on every frame. libvpx gates backward adaptation on
    `!error_resilient && !frame_parallel_decoding_mode` (`vp9_decodeframe.c:3077`) → with
    frame_parallel=1 it SKIPS adaptation, so the keyframe saves the un-adapted (default)
    context and frame 1 loads defaults. rvp9's two adapt gates (`lib.rs:1697` keyframe,
    `:2590` inter) omitted the `frame_parallel_decoding_mode` term → wrongly adapted the
    keyframe's probs → polluted the saved bank → frame 1 loaded prob 91 not 125 → first
    token read desyncs → cascade. **Why the 201 corpus passed:** every official vector
    uses `frame_parallel_decoding_mode=0`, so adaptation correctly fires there.
