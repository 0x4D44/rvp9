# Track E breakthrough — over-partitioning is the foreman root cause

Date: 2026-05-22.
Author: night-7 team-lead (Claude).
Session: continuation of `/goal Complete tracks A, B, C & D`.

## TL;DR

After 20 tuning experiments (A0–A19) concluded the foreman +395% BD-rate
gap was "structurally unachievable in single-agent scope," Arthur steered
us to do what those experiments never did: **a direct, data-driven
side-by-side comparison of rvp9 vs canonical libvpx on the same frames.**

That comparison (Track E, agent E1) found the root cause in one shot, and
it is **tractable, not architectural**:

> **rvp9 over-partitions. On foreman inter frames at 100 kbps it codes 85%
> of the area as 8×8 leaves; libvpx codes 79% as 64×64.** Every 8×8 leaf
> pays partition + mode + skip + coef-context overhead 30–60× too often
> over the static background, overshooting the target bitrate 1.7–3.0×,
> which forces the rate controller to push Q to 255. The q=255 saturation
> that A0–A19 chased is a **symptom**, not the disease.

The mechanism is now pinned to a **single missing port**: rvp9's variance
partitioner (`choose_partitioning`) uses keyframe variance thresholds for
inter frames. libvpx's `vp9_set_vbp_thresholds` has a separate,
much-higher inter-frame branch that keeps static content at 64×64. rvp9
never ported it.

## E1 ranked findings

1. **Over-partitioning (LARGEST).** 85% 8×8 (rvp9) vs 2.5% (libvpx);
   10% 64×64 (rvp9) vs 79% (libvpx). ~55,000 8×8 leaves / 63 inter frames.
2. **Bitrate overshoot / Q saturation (SYMPTOM of #1).** rvp9 achieves
   1.7–3.0× its target bitrate; RC pushes Q to 255 to recover.
3. **Inverted keyframe allocation (secondary, independent).** rvp9 KF =
   13.7 kbit @ q=177; libvpx KF = 74.5 kbit @ q=57. libvpx spends 5× more
   on the keyframe to seed a cheap-to-reference LAST. Independently fixable.

q=255 verdict: data **refutes** Q saturation as root cause — at 100k
rvp9's avg inter Q (211) is *higher* than libvpx's (204) yet rvp9 spends
2.3× the bits. Lowering Q won't help; coding fewer blocks will.

Honesty caveat from E1: the libvpx-side mode/skip/ref columns are
untrustworthy (report impossible 80–100% intra on <100-byte inter frames)
— a likely **decoder mi-grid mode-field population bug**, surfaced but not
fixed (logged for the decoder team). Findings #1–3 rest only on bits,
block_size, and Q, which are byte-exact-trustworthy.

## Root-cause pin (team-lead follow-up)

- `crates/rvp9-core/src/mode_decision/partition.rs:248` —
  `choose_partitioning` calls `VbpThresholds::for_keyframe(q_index)`
  unconditionally. There is no `for_inter`.
- `partition.rs:218-237` — `for_keyframe` sets `thresholds[2]` (16×16) =
  `threshold_base >> 2` (LOW → easy 16×16→8×8 split). libvpx's keyframe
  branch matches this, but its **inter** branch uses much higher
  thresholds (split far less). rvp9 applies the keyframe curve to inter.
- The variance computation itself is correct: source-minus-ZEROMV-
  reference residual variance (`partition.rs:316-323`), matching libvpx's
  `vp9_choose_partitioning` pre-check. So the *mechanism* is right; only
  the *thresholds* are wrong for inter.
- The partitioner IS wired into the inter path (`frame_loop.rs:720-728`);
  the module doc at `frame_loop.rs:34-42` claiming "no mode decision on
  inter frames / forced ZEROMV" is **stale** — post-A11 work widened the
  loop.

## Why A0–A19 missed it

Every one of the 20 experiments operated *downstream* of partitioning —
tuning the mode picker, MV cost, lambda, rate model, GOLDEN ref, sub-pel,
loop filter. None questioned the partitioner's inter thresholds. A7 even
capped inter partitioning, saw a ~30% bitrate drop, but mis-concluded
(from rvp9-only measurements) that "residuals are empty because q=255
quantizes all coefficients to zero" — a circular trap: the q=255 was
itself caused by the over-partition overshoot. E1's cross-encoder
comparison broke the circularity.
