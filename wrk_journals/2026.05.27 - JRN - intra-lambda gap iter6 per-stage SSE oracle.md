## Goal

Iters 1-5 ruled out the mode-decision levers (KF cap the only win; intra,
lambda, skip-plumbing, model_rd-skip all null). The combined iter4+5 finding:
the encoder is NOT residual-bound at CBR — the gap lives in transform/quant
precision or reference quality. This iter builds a permanent diagnostic that
reports per-frame SSE-to-source at three pipeline stages and compares rvp9's
final reconstruction to vpxenc's at the SAME quantizer, to localize WHERE.

## What was built

1. **`crates/rvp9-encoder/tests/stage_sse_diag.rs`** — the per-stage SSE
   oracle (committed; a keeper like `drift_diag`). For a fixed-qp encode of
   `tests/corpus/foreman_320x256_60f.y4m` it reports, per frame + aggregate:
   - **pred-SSE**: `SSE(source, prediction)` before any residual.
   - **post-quant-SSE**: `SSE(source, pre-LF recon = pred + dequant(quant(res)))`.
   - **post-recon-SSE**: `SSE(source, decode)` (final, incl. loop filter).
   Then drives vpxenc at the matched internal qindex (`--end-usage=q
   --cq-level=N`), decodes with vpxdec, and prints the
   rvp9-vs-vpxenc post-recon delta + SSE ratio.

2. **`diag_pred_y()` accessor** on `StreamEncoder` (gated like
   `diag_prelf_recon`): a whole-frame Y PREDICTION snapshot. Backed by a new
   `predstat::record_y_pred_block` / `take_pred_frame` pair that copies the
   per-TX prediction pixels (the moment `recon_plane` holds pure prediction,
   before the residual IT-add) into a thread-local frame buffer at the three
   existing E9 residual-tap sites (`lib.rs` KF-intra ~1524, intra-in-inter
   ~4798, inter-MC ~5052). Gated by `RVP9_E9_PREDSTAT`; no-op otherwise.
   Instrumentation only — drift_diag SSE still 0/0/0 on every frame.

## LOCALIZATION VERDICT

The gap is **transform-domain (transform-size decision + quant precision),
NOT prediction and NOT loop filter**.

- **NOT pred-bound**: residual coding ADDS ~3 dB (q160 INTER: pred 30.17 ->
  post-quant 33.22). The prediction is fine; residual recovery works.
- **NOT loop-filter**: post-quant -> post-recon is only +0.19 dB (q160) /
  -0.00 dB (q80) — negligible, consistent with libvpx's LF contribution.
- **The committed reconstruction (post-quant) is already 3.27 dB worse than
  vpxenc's FINAL at the SAME quantizer AND the SAME byte budget** (q160:
  24373 vs 24421 bytes). rvp9 spends the same bits and reconstructs 2.1×
  more error. That is the signature of a coarser transform/coefficient
  representation, not rate control and not prediction.

The corroborating smoking gun (from the E9 harness TX histogram, re-confirmed
this iter): rvp9's Y transform-size histogram `[4x4, 8x8, 16x16, 32x32]` is
`[0, 0, 15484, 161]` — **ZERO 4x4 and ZERO 8x8 transforms**. Every coded
block uses Tx16x16 or Tx32x32. libvpx's per-block RD TX-size search routinely
picks 8x8/4x4 in textured/high-detail regions, concentrating energy into
fewer, better-placed coefficients for the same bits.

## Concrete next-fix target for iter7

The divergence is **`tx_size = max_txsize(leaf_bsize)` with NO per-block
TX-size RD search**:

- `crates/rvp9-encoder/src/lib.rs:4698` (intra-in-inter) and
  `crates/rvp9-encoder/src/lib.rs:4870` (inter) both set
  `let luma_tx = rvp9_core::block::max_txsize(leaf_bsize);` and code every
  TX at that single (largest) size.
- `crates/rvp9-core/src/block.rs:264 max_txsize()` always returns the
  LARGEST TX for the block (Block16x16 -> Tx16x16, Block32x32 -> Tx32x32).
- libvpx instead runs a TX-size RD loop: `vp9/encoder/vp9_rdopt.c`
  `tx_size_select` / `choose_tx_size_from_rd` / `super_block_yrd` iterate
  `tx_size` from `max_txsize_lookup[bsize]` DOWN to TX_4X4, scoring each with
  `txfm_rd_in_plane`, and keep the RD-best. The realtime path uses
  `vp9/encoder/vp9_pickmode.c` `vp9_pick_inter_mode`'s `block_yrd` which also
  evaluates sub-block TX. rvp9 ports neither — it pins the max.

The quantizer kernels themselves are NOT the divergence: the inter path uses
the zbin-gated `vp9_quantize_b` / `vp9_quantize_b_32x32`
(`crates/rvp9-core/src/quant/forward.rs`), a faithful libvpx
`vpx_quantize_b_c` port (zbin / round / quant_shift / dequant all match; unit
tests + the round-trip integration test pin it). So iter7 should target the
**TX-size decision**, not the zbin/round/dead-zone (those were the iter4/5
hypothesis but the per-stage numbers + the same-bits comparison show the loss
is in HOW the residual is transformed, before quant). Secondary contributor
worth measuring: the variance partition picker under-splits (no 8x8 leaves on
foreman), which also forces large TX — a TX-size RD search alone may be partly
masked unless partitions can go finer.

Recommended iter7 probe: add a TX-size RD search (start with allowing Tx8x8
on Block16x16 leaves), re-run `stage_sse_diag`, and check whether post-quant
PSNR closes toward vpxenc at matched bytes.
