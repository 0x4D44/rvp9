# Unit 1386 — A4 calibration cache hoist rejected

## Decision

Reject and do not retain the code change. The final-leaf picker can select
between two frame-level A4 calibration values, but this reuse was slower on
the exact Crucible protocol. The task branch is restored to docs-only evidence
so the rejected result remains auditable without changing shipped behavior.

## Why this candidate

The fresh profile at integrated source `a94c8ce8` attributes 12.543% of
19,597,341 weighted RVP9 user samples to
`pick_and_simulate_inter_encode_partitions::closure$10`. The proposed change
reused `a4_rd_calibration_zero` and `a4_rd_calibration_nonzero` at the final
leaf instead of reconstructing the same frame-constant calibration and its
model-only-large policy. The descent path already used this cache.

## Correctness evidence

- A temporary candidate regression test covered CBR/VBR, CPU-used 6/7/8,
  cyclic-refresh on/off, exact-VBP on/off, model-only-large present/absent,
  segment IDs 0/1/7, and both spatial policy flags.
- The deliberate red run swapped the cache selector's zero/nonzero branches.
  It failed immediately for CBR CPU-used 6 with cyclic refresh enabled at
  segment 0, showing the test detects the wrong selection. The branch was
  restored afterward.
- Candidate validation passed the full encoder library: 780 tests passed and
  one was ignored. The x86-64 cross-compile (`x86_64-apple-darwin`) and
  rustfmt also passed.

## Performance evidence

The relaxed Crucible screen used CPU-used 6, CBR 1260 kbps, 30 fps, one
thread, zero tile columns, AQ 0, 60 frames, KF interval 60, one warmup, 15
alternating pairs, two rotations, and no `--max-load1` cap. Ratios are
candidate/control; lower is faster.

| clip | separate | paired | candidate ms/frame | control ms/frame |
| --- | ---: | ---: | ---: | ---: |
| ducks | 1.015647× | 1.014304× | 18.1515 | 17.8719 |
| in-to-tree | 1.015502× | 1.015870× | 11.8785 | 11.6972 |
| old-town-cross | 1.015431× | 1.014959× | 10.7226 | 10.5596 |
| three-clip corpus geomean | 1.015527× | 1.015044× | — | — |

All three output hashes matched the integrated control exactly, so this is a
clean speed regression rather than a quality change. Completion load stayed
below 0.73 load1. Because the candidate failed the plain retention screen, no
pinned-libvpx run was warranted.
