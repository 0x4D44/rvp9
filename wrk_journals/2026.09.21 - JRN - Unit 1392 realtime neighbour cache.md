# Unit 1392 — realtime neighbour lookup cache

## Outcome

Unit 1392 caches the eight `ModeInfo` references resolved by
`find_realtime_refs_nearest_near_mvs_with_context` during its direct-reference
walk. The scaled-candidate walk consumes that cache in the same order instead
of resolving each spatial position a second time. The change is committed as
`a5713039` (`perf(core): reuse realtime reference lookups`).

## Why this candidate

The fresh x86-64 Crucible profile for integrated commit `56aebd72` mapped
47,670,251 weighted RVP9 user samples. The top realtime-specific resolver was
the sixth RVP9 symbol at 1,675,783 samples (3.515364%). Its second pass used
the same eight positions as the first pass, so caching the immutable lookup
results removes repeated tile/frame bounds work without changing candidate
ordering or reference selection.

## Correctness evidence

- `cargo fmt --all -- --check` passed.
- `cargo test -p rvp9-core inter::mv_ref --lib -- --nocapture` passed: 56/56.
- A deliberate red run set every cached entry to `None`; the existing
  `paired_last_golden_walk_matches_four_independent_queries` oracle failed.
  Restoring the cache assignment returned the suite to green.
- `cargo test -p rvp9-core --lib` passed: 1718 passed, 2 ignored.
- `cargo test -p rvp9-encoder --lib` passed: 780 passed, 1 ignored.
- The x86-64 release candidate built on Crucible. A relaxed 15-pair, two-
  rotation screen across three 1280x720@30 clips produced byte-identical
  candidate/control streams on every rotation. The corpus paired ratio was
  `0.995414x` (candidate/control), with ducks `0.997390x`, in-to-tree
  `0.991414x`, and old-town `0.997451x`.

## Current parity

The same relaxed matrix against pinned libvpx measured RVP9 at `1.437268x`
overall: ducks `1.446280x`, in-to-tree `1.507166x`, and old-town `1.362071x`.
This is the remaining production-parity gap; the candidate is a reproducible
increment within RVP9, not a claim of libvpx parity.

The raw symbolized profile and compact screen manifests live under
`wrk_docs/evidence/2026-09-21-unit1392-*`. The ETL remains on Crucible and is
identified by its SHA-256 in the profile manifest; it is intentionally not
checked into the repository.
