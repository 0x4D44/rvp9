## Background

The horiz drive closed at 1.23× / 1.27× (16×16 / 64×64) vs libvpx, but
the residual composite-`2d` gap at small sizes (8×8: ~2.7×, 16×16:
~2.1×) is now **vert-dominated**. From the kernel audit
(`bench/results/kernel-audit-fullmap-2026-05-27.csv`):

| kernel | size | rvp9 ns | libvpx ns | ratio |
|---|---|---|---|---|
| `convolve8_vert_halfpel` | 16×16 | 30.44 | 16.44 | **1.85×** |
| `convolve8_vert_halfpel` | 64×64 | 233.07 | 199.17 | **1.17×** |

Goal of this drive: bring rvp9 `convolve8_vert` AVX2 16×16 to within
≤1.5× of libvpx (same target as horiz). 64×64 is already near-parity
but should not regress. Bit-exact gate is non-negotiable.

### 2026-05-27 — Recon agent — gap characterized, fix proposed

**Mechanism (the headline finding):** the current rvp9 kernel re-loads
**all eight source rows for every output row** (`convolve8_vert_avx2.rs:209-290`).
libvpx **primes seven rows once, then loads only 1–2 new rows per output
(pair)** via a sliding window, reusing the previously-loaded rows held in
registers. That's an 8× load-traffic ratio in the inner loop — exactly
why the gap is **size-dependent**: at 16×16 the per-row constants
dominate (1.85×), at 64×64 the wasted loads are partly hidden behind
useful column-direction compute (1.17×). Bonus: a dummy load at line 247
(`[loadu; 8]` then immediately overwritten) on every output row.

**libvpx's structure** (`third_party/libvpx/vpx_dsp/x86/vpx_subpixel_8t_intrin_avx2.c:222-324` for 16-wide; `:902-994` for 8-wide):
- 256-bit, 2 output rows per iteration (asserts `!(output_height & 1)`).
- Pre-pack rows once before the loop into `s32b[0..5] = inserti128` of
  consecutive 128-bit row pairs, then `s1[0..2] = unpacklo`,
  `s2[0..2] = unpackhi` — holds tap-pair operands for the first 6 taps.
- Sliding window: per 2 output rows, **2 new 128-bit row loads**, build
  `s1[3]`/`s2[3]`, `convolve8_16_avx2` × 2, `mm256_store2_si128`, then
  shift the window (`s1[0]=s1[1]; ...; srcRegHead1 = srcRegHead3`).
- `convolve8_16_avx2` reduction (`convolve_avx2.h:53-74`) is **identical
  to rvp9's `combine256`** — `(x0+x2)+(x1+x3)+64`-then-`adds`-then-`srai 7`.
  Math is already bit-exact compatible; only the **dataflow** differs.

**Proposed fix (sequence of self-contained, bit-exact-checkable steps):**
1. Keep 32-col 256-bit fast path, switch to sliding window — hoist 8
   `r[k]` loads outside `for y`, per row load only `r[7]`, rotate
   `r[0..6] = r[1..7]`. 8 loads/row → 1.
2. Pair output rows in 32-col path (libvpx's `s32b` pattern,
   `inserti128` of two adjacent row halves; 2 output rows per iteration).
3. Port the same sliding pattern to the 8/16-column path (the
   `while cg < w` 128-bit loop, lines 262-289). This is the dominant
   case for the 16×16 headline.
4. Drop the dummy `[loadu; 8]` initializations (line 247, 266).

**Contract for vert** (existing, from `convolve8_vert_avx2.rs:220`):
`src.len() >= (h - 1 + 7) * src_stride + w`. The kernel reads exactly
columns `0..w` of rows `0..=h+6`. **New vulnerability introduced by
Step 2/3:** the sliding window must always pair `(row k, row k+1)` for
`k ≤ h+5`, never reaching row `h+7`. The analogue to horiz's
`w == 4 + tight src_stride` OOB is: tight `src_stride == w` with `h == 8`
(exactly seven priming rows + one output) — the pair-load must not
naively grab row `h+7`.

**Risk register** (for impl agent):
- Rotation off-by-one in Step 1.
- Wrong unpack-vs-pack lane semantics (256-bit interleave is per-128-bit-lane).
- `h < 7` can't fully prime; need fall-through to current 1-row path.
- Odd `h`: 2-row pair loop must have a 1-row tail.
- `w == 4`: keep on the current 1-row path; gate the pair loop on `w >= 8`
  (mirrors the horiz drive's apply-feedback fix B1).
- **DO NOT TOUCH:** `convolve8_avx2.rs` 2-D composite, `combine` /
  `combine256` ordering (bit-exact contract).

**Expected outcome** (honest):
- 16×16 → **1.4×–1.5×** target; ≤1.3× is optimistic.
- 64×64 → **1.05×–1.10×**; less headroom (already only 35 ns off).
- 8×8 → should drop noticeably (sliding-window proportional saving).

### 2026-05-28 — Implementation agent — 16/8-wide pair paths landed

**Starting state.** The recon handoff already had Step 1 + Step 2
applied to the **32-col 256-bit fast path** (`w >= 32`): sliding window,
2-output-rows/iter, slide-by-2, odd-h tail. That alone is what drove
64×64 down to the recon's ~1.10×. The `while cg < w` path (the 8/16-wide
tier, i.e. the 16×16 **headline**) was still the OLD single-row code:
8 row-loads per output row plus a dummy `[load_cols(..); 8]` init. The
module doc already described the full plan; only the 8/16 code was
missing. (A format-on-save / `cargo fix` pass also tidied the recon's
uncertain 32-col tail comment and removed its unused imports before I
started — Step 4's "drop dummy load" for the 32-col path was thus
already done; I dropped the 8/16 dummy load as part of the rewrite.)

**What I did (Step 3 — port the sliding window to the 8/16 tier).**
- Added two helpers: `pair_rows(a, b)` =
  `inserti128(row_a low-lane, row_b high-lane)` (libvpx `s32b[k]`), and
  `vconv256_pair(ss, f01..f67)` = the four `maddubs` + `combine256`
  reduction over pre-`unpack`ed tap-pair operands (reuses the existing
  bit-exact `combine256` verbatim — no reduction-order change).
- Replaced the `while cg < w` body. For `gw >= 8` (the {8, 16} groups)
  it now runs a **pair-row sliding window** mirroring
  `vpx_filter_block1d{16,8}_v8_avx2`: prime rows 0..6 once into
  `ss_lo[0..2]` (+`ss_hi[0..2]` when `gw == 16`), then per pair load
  only 2 new rows, build the trailing `ss[3]`, reduce, `packus`
  (lane0 = output row y, lane1 = row y+1), store both rows, slide the
  `ss` window by 2. Odd-h falls to a 1-row 128-bit `vconv` tail; `head`
  carries the last primed row across the boundary. `gw == 4` keeps the
  original single-row path (gated by `gw >= 8`, the vert analogue of
  horiz's `w >= 8` gate).
- 8-wide uses `_mm_loadl_epi64` loads + low-lane-only reduction +
  `storel`; 16-wide uses `_mm_loadu_si128` + lo&hi + `storeu`. One
  unified loop, branched on `do_hi = (gw == 16)`.

**Deviation from the recon plan.** The plan listed Step 2 (pair output
rows in the 32-col path) as a separate step; the recon had already
implemented the 32-col path as a 2-row pair loop, so there was nothing
left to do there. I did **not** convert the 32-col path to the
`ss`-pre-pack `inserti128` topology (it uses the per-row `vconv256`
sliding window instead) — it's already at parity (64×64 ≈ 1.04–1.08×)
and the directive says don't over-engineer a path that's already there.
Untouched: `combine`/`combine256`/`vconv`/`vconv256`, the safe wrapper,
dispatch, and `convolve8_avx2.rs` (2-D composite).

**Bounds / the new-vulnerability analysis.** The pair loop runs while
`y + 1 < h`; its largest read is `row y + 8`, and `y + 1 < h ⇒
y ≤ h-2 ⇒ y+8 ≤ h+6` = the contract's last loadable row
(`(h-1+7)*src_stride + w`). The odd-h tail at `y = h-1` reads rows
`h-1..=h+6` (also in-bounds). Priming reads rows 0..6, in-bounds for
any `h >= 1`. So no over-read; the slide-by-2 never reaches `h+7`.

**Tests added.** New `differential_odd_and_narrow_shapes` (mirrors the
horiz drive's same-named test): tight-stride (`src_stride == w`, **no
slack**, so a 1-row over-read trips a Vec OOB) cases `(8,8,8)`,
`(16,16,16)`, odd-h `(8,7,8)`/`(16,15,16)`, `h==1` `(8,1,8)`/`(16,1,16)`,
`h==2` `(8,2,8)`/`(16,2,16)`, the 32-col odd-h `(32,33,32)`, slack
odd-h `(8,9,0)`/`(16,17,0)`, and `(4,8,4)` to guard the `gw == 4`
single-row fallthrough. 4 sub-pel rows × 4 kernel tables per shape. All
green. Full vert suite: **4 tests pass** (`differential_all_filters`,
`differential_odd_and_narrow_shapes`, `tautology_guard_avx2_path`,
`dispatch_round_trip`). Broader `dsp::x86_64::convolve` suite (24 tests,
incl. `convolve8_avx2::differential_2d` and the avg/scaled consumers of
the vert kernel): all pass — no consumer regressed.

**Harness results (`run-kernel-audit.ps1`, affinity 0x1).** Every row
`InMatch=True OutMatch=True` (bit-exact preserved). The libvpx side of

**Bottom line.** 16×16 hits the ≤1.5× target (1.47× on a clean floor;

pair, 1 row-load per output row).

**For the code-reviewer to scrutinize:**
1. The `ss_lo`/`ss_hi` slot-`[3]` seeding: I init slot 3 = slot 2 (a
   valid register) purely to fill the array; it is overwritten with the
   fresh `unpack(r6, r7)` before every `vconv256_pair`. Confirm slot 3
   is never read before that write (it isn't — the write precedes the
   reduce in both the lo and hi branches).
2. `head` carry across the slide: `head = s[6]` at prime, `head = s8`
   after each pair. First pair must pair (row6,row7) and (row7,row8) —
   verify against libvpx `srcRegHead1 = srcRegHead3` semantics.
3. The `gw >= 8` vs `gw == 4` branch and the claim that `gw == 16 ⇒
   w == 16` here (32-col path drains 32-col groups first), so `gw` is
   always the full remaining group width for VP9 widths {4,8,16,32,64}.
4. The 8-wide `packus(lo, lo)` lane semantics (lane0[0..8] = row y,
   lane1[0..8] = row y+1) — covered by the differential test but worth
   an eyeball.
