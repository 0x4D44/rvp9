# Goal Prompt: vpxenc Parity Compressor Work

Use this prompt when starting an aggressive compressor-performance session. The intent is to keep the work focused on the product goal: matching `vpxenc` rate-distortion behavior under declared presets, while preserving decodability and realtime latency.

```text
Goal: make rvp9 match vpxenc, not merely complete the VP9 port.

You are working on rvp9's compressor. The product oracle is vpxenc behavior under declared presets. Internal libvpx faithfulness and byte parity are diagnostic tools only; they are not success. Feature parity is also not success. Success is rate-distortion performance under the latency budget.

Primary target:
- Stage 4a realtime: match vpxenc `--rt --cpu-used=7 --lag-in-frames=0 --tune-content=default`
- Required gates:
  1. Cross-decoder validity stays clean: rvp9-decoder, vpxdec, and ffmpeg agree on decoded output for the exercised gate streams.
  2. 720p30 realtime stays at or below 33 ms/frame median on the release realtime gate.
  3. Real-content BD-rate moves materially toward <= +2% vs vpxenc. A +20% class BD-rate result is failure, even if temporary PSNR-delta thresholds pass.
  4. Fixed-Q Foreman decomposition must improve or explain the residual. Do not hide behind rate-control if matched-Q still trails.

Current known state:
- Decodability is good on exercised gates.
- A dirty large-frame speed stack has measured ~32.97 ms/frame, narrowly passing 720p30.
- Quality is still poor: around +22.88% BD-rate / +2.36 dB matched-bitrate gap on the current realtime real-content gate.
- Stronger cpu4 Foreman sweep shows roughly +29.4% BD-rate / -0.91 dB BD-PSNR, with rvp9 crossing vpxenc only at higher bitrates.
- Fixed-Q evidence says the residual is coding/prediction efficiency, not just bitrate allocation.

Operating rule:
Do not start with "what feature is missing?" Start with "where does rvp9's RD curve diverge from vpxenc, and which block/frame/mode decisions explain it?"

Work loop:
1. Establish a clean baseline from the current branch/worktree state.
2. Run the smallest meaningful gates:
   - encoder lib tests
   - cross-decoder gate
   - realtime gate
   - real-content quality gate
   - fixed-Q Foreman decomposition if quality changes
3. Pick one measured hypothesis about the low-bitrate/high-Q gap.
4. Make the smallest code change that should move that metric.
5. Re-run the same gates and report before/after numbers.
6. Keep the change only if it improves rate-distortion without breaking decodability or blowing the speed budget.

Non-goals:
- Do not work on AQ, denoiser, SVC, high bit depth, CLI polish, or branch hygiene unless they directly block the vpxenc parity gates.
- Do not chase byte-identical output as an end goal.
- Do not land a single-clip win without a generalization check.
- Do not weaken thresholds, skip tests, or call a loose diagnostic threshold a product pass.
- Do not merge old branch work wholesale; reproduce the win on current main.

Priority hypotheses:
- Low-bitrate/high-Q inter prediction efficiency.
- RT picker / motion-field micro-decisions.
- Skip and residual coding decisions where fixed-Q rvp9 trails vpxenc.
- Large-frame speed defaults only insofar as they preserve the speed gate without worsening BD-rate.

Stop conditions:
- If cross-decoder validity breaks and the cause is not obvious, stop and localize before more changes.
- If a speed win worsens BD-rate, report the tradeoff instead of burying it.
- If a quality win helps Foreman but regresses synthetic/testsrc or another real clip, keep it gated and report it as content-dependent.
- If profiling contradicts the assumed hot path, update the hypothesis instead of stacking fixes.

Final report must include:
- git state and whether changes are committed or dirty
- exact validation commands run
- before/after realtime median
- before/after BD-rate or matched-bitrate PSNR gap
- fixed-Q decomposition if relevant
- cross-decoder result
- whether the change should land, stay gated, or be discarded
```
