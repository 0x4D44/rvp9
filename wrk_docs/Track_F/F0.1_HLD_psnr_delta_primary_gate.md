## 1. Problem statement

After Track E (E1–E14) landed, the foreman BD-rate gate
(`bdrate_gate_stage4a_realcontent` in
`D:\language\rvp9-2\crates\rvp9-encoder\tests\bdrate_gate.rs`) cannot
produce a usable number: rvp9's PSNR curve sits entirely below libvpx's
on real content (24–27 dB vs 28–37 dB at matched bitrates per
`wrk_docs/Track_F_baseline_numbers.md`), so the Bjøntegaard cubic has
no PSNR overlap to integrate. E15 (`7166e8b`) bolted on a
matched-bitrate PSNR-delta interpolation as a *fallback*, which is what
currently produces the foreman headline — **mean +9.07 dB, max +9.50,
min +8.65 across four in-range points**. Until Track F's coupled
picker work (block_yrd / find_mv_refs / motion-aware partition) lifts
rvp9's curve high enough to overlap libvpx's, BD-rate is structurally
undefined. Track F needs a single number to drive down at every
milestone, and that number is the PSNR-delta mean — not BD-rate. This
HLD promotes the fallback to **primary signal**, demotes BD-rate to
**secondary line that returns when the gap closes**, and renames the
gate so its identity matches what it now measures.

## 3. Proposed change

Make PSNR-delta the primary success signal. Three things change in
behaviour, one in vocabulary.

### 3.1 Primary metric — mean PSNR-delta (in-range, dB)

For each rvp9 operating point `(br_rvp9, psnr_rvp9)`:
- Interpolate libvpx's curve at `br_rvp9` via `psnr_at_bitrate` (no
  extrapolation; out-of-range → counted, not interpolated).
- Compute `Δ = psnr_libvpx_interp − psnr_rvp9` (positive = rvp9 trails).

Summary stats over the **in-range subset only**:

| Field | Meaning |
|---|---|
| `mean_delta_db`        | Arithmetic mean of in-range Δ. **Primary metric.** |
| `min_delta_db`         | Min in-range Δ (best block-level match to libvpx). |
| `max_delta_db`         | Max in-range Δ (worst gap). |
| `count_in_range`       | Number of rvp9 points where libvpx's curve covers the bitrate. |
| `count_out_of_range`   | Number of rvp9 points outside libvpx's bitrate range (skipped). |

**Sign convention and the eventual success case.** A positive Δ means
rvp9 trails libvpx (the current Track F state). A negative Δ means
rvp9 beats libvpx at that operating point — the eventual success
regime once block_yrd + find_mv_refs + motion-aware partition land.
The PASS condition `mean_delta_db <= threshold` handles negative
values correctly (any negative mean passes any positive threshold).
The harness must not assume Δ is always positive — emit `+X.XX` or
`−X.XX` per point as the existing E15 reporter already does.

### 3.2 Pass / fail condition

The gate becomes:

```
PASS if  mean_delta_db <= track_f_psnr_delta_threshold_db  AND  count_in_range >= 2
FAIL otherwise
DEFERRED if libvpx leg unavailable OR count_in_range < 2
```

The `count_in_range >= 2` requirement (rather than `>= 1`) reflects
that a single-point mean is not a meaningful summary of
curve-distance: it could pass on a fluke operating point while the
rest of the curve diverges. Two in-range points is the minimum for
the mean to represent a region rather than a single sample.
DEFERRED (not FAIL) is the right status for `count_in_range < 2`
because that condition reflects oracle coverage, not encoder
quality.

The threshold is a literal constant in the test, updated per
milestone after measurement. F.0.1 lands at +9.5 dB purely as a
regression-guard at the current baseline (mean Δ = +9.07 dB). Each
Track F milestone HLD (F.1, F.2, F.3, F.4) is responsible for
measuring the new mean Δ and updating the constant in its own
implementation PR. We do not predict future milestone values —
milestone-exit-PSNR is a measurement, not a prediction.

### 3.3 Secondary — BD-rate stays as a reported line

When BD-rate is finite, the gate reports it on its own line and treats
it as additional information. **BD-rate alone does not gate Track F
milestones during F.1–F.3** (it's NaN, so it can't). At F.4 it
returns as a co-gate.

### 3.4 Other rvp9-curve sanity asserts unchanged

The existing ~monotonicity assert on rvp9 curves (lines 530–538 of
`bdrate_gate.rs`) stays. It catches encoder regressions
("higher target should give higher PSNR") that the PSNR-delta
summary alone wouldn't catch (e.g. if the entire curve shifts
uniformly downward, mean Δ moves but monotonicity reveals whether
the encoder is broken vs the gap widening).

## 4. Interface changes

All changes are in the two files cited in §2. No public API in
`rvp9-core` / `rvp9-decoder` / `rvp9-encoder` touched.

### 4.1 `rvp9-harness/src/bdrate.rs` — add a summary helper

Add (no changes to existing items):

```rust
/// Summary of matched-bitrate PSNR-delta evaluation between an rvp9
/// curve and a libvpx reference curve. Produced by
/// `psnr_delta_summary`.
///
/// `count_out_of_range` rvp9 points fall outside the libvpx curve's
/// bitrate span and are *excluded* from the mean/min/max — there is
/// no extrapolation. Callers should report the count separately.
#[derive(Debug, Clone, Copy, PartialEq)]
pub struct PsnrDeltaSummary {
    pub mean_delta_db: f64,
    pub min_delta_db: f64,
    pub max_delta_db: f64,
    pub count_in_range: usize,
    pub count_out_of_range: usize,
}

/// Compute libvpx-vs-rvp9 PSNR-delta summary at the rvp9 curve's
/// operating points. `libvpx_curve` is the reference; `rvp9_curve` is
/// queried point-by-point against it via `psnr_at_bitrate`.
///
/// Returns `None` if no rvp9 point falls in the libvpx bitrate range
/// (caller should report DEFERRED). Otherwise the returned summary's
/// `count_in_range >= 1`.
#[must_use]
pub fn psnr_delta_summary(
    libvpx_curve: &[(f64, f64)],
    rvp9_curve:   &[(f64, f64)],
) -> Option<PsnrDeltaSummary>;
```

This is **additive only**. `bdrate(...)` and `psnr_at_bitrate(...)`
are unchanged.

### 4.2 `rvp9-encoder/tests/bdrate_gate.rs` — gate semantics swap

In `run_stage4a_gate`, replace the current three-branch dispatch
(lines 432–521) with:

1. **Always** call `psnr_delta_summary` when a libvpx curve exists.
   Print the per-point Δ table (unchanged format) and the summary.
2. **Always** call `bdrate` and print its result on a single line. If
   NaN, print "BD-rate: not measurable" — do not gate on it during
   F.1–F.3.
3. The "Exit gate status:" line is computed from
   **`mean_delta_db <= TRACK_F_PSNR_DELTA_THRESHOLD_DB`** when a
   libvpx curve is present and `count_in_range >= 2`, otherwise
   DEFERRED.

Add a single milestone constant near the top of the file:

```rust
/// Track F pass/fail threshold on the foreman PSNR-delta mean (dB).
/// Updated per milestone — see the F.0.1 HLD §3.2 table.
/// 2026-05-23: +9.5 dB (initial — purely a regression guard at the
/// baseline; F.1 will tighten this).
const TRACK_F_PSNR_DELTA_THRESHOLD_DB: f64 = 9.5;
```

A second constant covers testsrc (which is a content-artefact corner
case per `Track_F_baseline_numbers.md`):

```rust
/// testsrc is a content-artefact corner case where libvpx wins on
/// flat-content luck (78 dB on colour bars at 68 kbps — a regime no
/// realtime encoder follows without flat-content specific
/// optimisations per Track_F_baseline_numbers.md). This constant is a
/// COHERENCE SANITY CHECK, NOT A TRACK F GATE — its only job is to
/// catch wholesale rvp9 regression on testsrc. The Track F headline
/// metric lives on foreman.
const TRACK_F_PSNR_DELTA_THRESHOLD_TESTSRC_DB: f64 = 50.0;
```

`run_stage4a_gate` takes a `psnr_delta_threshold_db: f64` parameter
and the two test functions pass the right constant.

## 7. Risks / open questions

### Risks

1. **Threshold table in §3.2 is a best-guess.** The +6–7 dB / +4–5 dB
   /  +1 dB cascade is from the kickoff journal, which itself is an
   estimate. If F.1 lands at +8 dB instead of +6–7 dB, the milestone
   gate fails for a reason that has nothing to do with implementation
   quality. **Mitigation:** the threshold is a literal constant the
   team-lead edits per milestone, not a CI hard line. Treat the gate
   as a smoke test; the canonical signal is the printed mean Δ.

2. **`count_in_range` could drop to 0 mid-experiment.** If a Track F
   change shifts rvp9's bitrate range entirely outside libvpx's
   (e.g. an RC regression), the summary becomes `None` and the gate
   DEFERS. That's an honest signal — but it means F.x could "regress
   to undetectable" without a hard FAIL. **Mitigation:** the
   monotonicity assert on the rvp9 curve still fires, and the
   DEFERRED status itself is loud. We trust the human in the loop.

3. **Floating-point reproducibility of the baseline table.** §5.2
   demands the exact +9.07 / +9.50 / +8.65 numbers. PSNR involves
   summed squared differences over 64 frames; tiny float-order
   changes could perturb the last decimal. **Mitigation:** if the
   numbers move by ≤0.02 dB, accept it; if they move more, halt and
   investigate — that signals an encoder change crept in.

4. **Test name rename breaks any external invocation script.** A
   grep for `bdrate_gate_stage4a` outside the repo finds nothing
   anyone outside this workspace runs. But internal docs
   (`PLAN.md`, `wrk_docs/E15_psnr_delta_fallback.md`, this HLD) cite
   the old name. **Mitigation:** during implementation, also update
   `wrk_docs/Track_F_baseline_numbers.md` §"How to reproduce" and
   `PLAN.md` Stage 4a §"Empirical status" (Track E references) to
   the new names. PR description should list every doc that needs
   the rename.

### Open questions for team-lead

- **Q1: Threshold cascade — confirm or revise the §3.2 table?**
  Best guess is in the HLD; would prefer a Track F lead call so the
  F.0.1 PR lands with the right initial value.

- **Q2: Should the gate hard-fail at `count_in_range < 2`, or
  DEFER?** I've proposed DEFER — but a hard fail might be safer
  during F.1–F.3 to make sure curve-range regressions can't sneak
  through. Open to either.

- **Q3: Rename scope.** I'm proposing renaming the two Stage 4a
  tests + the runner function + the file. Should the file rename
  also bump anything in `Cargo.toml`? Check: `rvp9-encoder/Cargo.toml`
  doesn't enumerate test files individually (cargo auto-discovers
  `tests/*.rs`), so the rename is local. Confirm we want it.

- **Q4: Where does the F.0.1 commit's metric printout get
  archived?** `wrk_docs/Track_F_baseline_numbers.md` is the natural
  home; should the implementer regenerate that doc as part of the
  PR, or just cite it as already-current?

- **Q5: testsrc threshold of +50 dB is essentially "always pass".**
  Should testsrc be removed from the Track F gate set entirely
  (per the baseline doc "Foreman is the fairer gate for Track F"),
  or kept as a regression-only smoke test? Proposal: keep, with
