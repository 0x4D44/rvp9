# HLD — Phase 2: Shared Frame-Wide MI Grid

**Date:** 2026-05-24
**Status:** Draft
**Predecessor:** Phase 1 (direct-to-frame tile decode) — landed

---

## 1. Problem Statement

After all tiles complete decoding, the decoder stitches per-tile MI grids
into a frame-wide `Vec<Option<ModeInfo>>` via `build_frame_mi_grid`
(`crates/rvp9-decoder/src/lib.rs:3105`). This function allocates
`mi_rows * mi_cols` cells and performs a row-by-row `copy_from_slice` from
each tile's local grid (tile-local stride) into the frame grid (frame-wide
stride).

On 1080p content (mi_rows=136, mi_cols=240, 32 640 cells of 56 bytes each)
this costs ~663 us (6.8% of frame time) — a pure data-movement tax with
no algorithmic purpose. The per-tile grid exists solely because
`TileDecodeCtx` owns its storage; nothing prevents writing directly into
the frame grid if tiles receive non-overlapping views.

---

## 2. Design

### 2.1 Pre-allocate the frame-wide MI grid

Before tile dispatch (both parallel and serial paths), allocate a single
frame-wide grid:

```rust
let mut frame_mi_grid: Vec<Option<ModeInfo>> = vec![None; mi_rows * mi_cols];
```

This replaces the post-decode `build_frame_mi_grid` allocation. The grid
uses frame-wide stride (`mi_cols`), identical to what the loop filter and
`last_frame_mi_grid` accessor already expect.

### 2.2 Per-tile MI grid view — `TileMiView`

Following the Phase 1 `TileFrameView` pattern, introduce a lightweight
view that gives each tile mutable access to its column-range within the
frame-wide grid:

```rust
/// Non-overlapping mutable view into a rectangular sub-region of the
/// frame-wide MI grid. Analogous to `TileFrameView` for pixels.
///
/// # Safety invariants (construction-time)
///
/// 1. The parent `Vec<Option<ModeInfo>>` must outlive all `TileMiView`s.
/// 2. No two `TileMiView`s may cover overlapping cell ranges.
/// 3. No other `&mut` to the parent Vec exists while any view is alive.
pub struct TileMiView {
    /// Raw pointer to the first cell of the frame-wide grid (row 0, col 0).
    /// We point at the grid origin (not the tile's first cell) so that
    /// frame-absolute (mi_row, mi_col) indexing works unchanged.
    ptr: *mut Option<ModeInfo>,
    /// Total number of cells in the grid (mi_rows * mi_cols).
    len: usize,
    /// Frame-wide stride (= mi_cols).
    mi_stride: usize,
    /// Tile's column bounds (inclusive start, exclusive end).
    mi_col_start: usize,
    mi_col_end: usize,
    /// Tile's row bounds (inclusive start, exclusive end).
    mi_row_start: usize,
    mi_row_end: usize,
}

// SAFETY: TileMiView is Send because:
// 1. Raw pointer into a single Vec allocation.
// 2. Construction contract guarantees non-overlapping write ranges;
//    each tile writes only within [mi_row_start..mi_row_end,
//    mi_col_start..mi_col_end].
// 3. The parent Vec's lifetime is guaranteed by the scoped thread pool.
unsafe impl Send for TileMiView {}
```

Construction (one view per tile, immediately before the scope):

```rust
let mi_views: Vec<TileMiView> = per_tile_bounds
    .iter()
    .map(|bounds| {
        // SAFETY: bounds are non-overlapping by VP9 spec (tile boundaries
        // are SB-aligned); frame_mi_grid lives through the scope; no
        // other &mut to frame_mi_grid exists between view construction
        // and scope.join().
        unsafe {
            TileMiView::new(
                frame_mi_grid.as_mut_ptr(),
                frame_mi_grid.len(),
                mi_cols, // mi_stride
                bounds,
            )
        }
    })
    .collect();
```

### 2.3 `TileDecodeCtx` changes

Currently `TileDecodeCtx` owns three fields relevant to the MI grid:

| Field | Current role |
|-------|-------------|
| `above: Vec<Option<ModeInfo>>` | 1-D above-row reduction (survives SB rows) |
| `left: Vec<Option<ModeInfo>>` | 1-D left-column within SB row |
| `mi_grid: Vec<Option<ModeInfo>>` | 2-D tile-local grid, stride = tile_mi_cols |

**Change:** Replace the owned `mi_grid` field with a borrowed
`TileMiView`. The `above` and `left` vectors remain owned (they are
small — 240 and 8 cells respectively — and their per-SB-row lifecycle
is orthogonal to the grid).

The struct becomes lifetime-parameterised:

```rust
pub struct TileDecodeCtx<'grid> {
    above: Vec<Option<ModeInfo>>,
    left: Vec<Option<ModeInfo>>,
    /// Mutable view into the pre-allocated frame-wide MI grid.
    /// Writes are restricted to the tile's (row, col) rectangle.
    mi_view: TileMiView,  // carries its own bounds
    /// Cached from bounds for fast indexing.
    tile_mi_rows: usize,
    tile_mi_cols: usize,
    /// Frame-absolute column offset so that `write_block` can
    /// translate tile-relative mi_col to frame-absolute coordinates.
    mi_col_start: usize,
    mi_row_start: usize,
    _phantom: PhantomData<&'grid mut [Option<ModeInfo>]>,
}
```

> **Alternative (simpler, no lifetime):** Because `TileMiView` uses raw
> pointers (like `TileFrameView`), the struct does NOT actually need a
> lifetime parameter. The safety contract is enforced at construction
> time, not by the borrow checker. This mirrors Phase 1's approach and
> avoids propagating `'grid` through the entire tile-decode call stack.
> **Recommended:** use the lifetime-free form with `TileMiView` stored
> by value, same as `TileFrameView`.

### 2.4 `write_block` changes

Currently `write_block` writes into the tile-local grid at
`mi_grid[r * tile_mi_cols + c]` using tile-relative coordinates.

After the change, writes go through `TileMiView` at frame-absolute
coordinates:

```rust
pub fn write_block(
    &mut self,
    mi_row: usize,       // frame-absolute
    mi_row_in_sb: usize, // SB-relative (for left[] write)
    mi_col: usize,       // tile-relative (as today)
    n_8x8_wide: usize,
    n_8x8_high: usize,
    mi: &ModeInfo,
) {
    // above[] and left[] writes — unchanged (tile-relative mi_col).
    // ...existing code...

    // 2D grid splat — now at frame stride.
    let abs_col = self.mi_col_start + mi_col;
    let abs_row = self.mi_row_start + mi_row;  // mi_row is already tile-relative row index
    let stride = self.mi_view.mi_stride;
    let row_end = (abs_row + n_8x8_high).min(self.mi_row_start + self.tile_mi_rows);
    let col_end = (abs_col + n_8x8_wide).min(self.mi_col_start + self.tile_mi_cols);
    for r in abs_row..row_end {
        let base = r * stride;
        // SAFETY: we only write within [mi_row_start..mi_row_end,
        // mi_col_start..mi_col_end] — guaranteed non-overlapping.
        unsafe {
            let slice = std::slice::from_raw_parts_mut(
                self.mi_view.ptr.add(base + abs_col),
                col_end - abs_col,
            );
            for slot in slice.iter_mut() {
                *slot = Some(*mi);
            }
        }
    }
}
```

### 2.5 `mi_at` / `mi_at_relative` changes (neighbour lookups)

These currently read from the tile-local `mi_grid`. After the change they
read from the frame-wide grid via `TileMiView`, still clamped to tile
bounds (preserving the `is_inside` semantics from libvpx):

```rust
pub fn mi_at(&self, mi_row: usize, mi_col: usize) -> Option<&ModeInfo> {
    // mi_row / mi_col are tile-relative.
    if mi_row >= self.tile_mi_rows || mi_col >= self.tile_mi_cols {
        return None;
    }
    let abs_row = self.mi_row_start + mi_row;
    let abs_col = self.mi_col_start + mi_col;
    let idx = abs_row * self.mi_view.mi_stride + abs_col;
    // SAFETY: idx is within [mi_row_start..mi_row_end,
    // mi_col_start..mi_col_end] which is within the grid allocation.
    unsafe { (*self.mi_view.ptr.add(idx)).as_ref() }
}
```

The `above()` and `left()` accessors remain unchanged — they read from
the owned 1-D vectors and don't touch the grid.

### 2.6 Removal of `build_frame_mi_grid`

The function `build_frame_mi_grid` (lib.rs:3105-3128) is deleted. Its
sole call sites (lib.rs:1863, lib.rs:2854) are replaced by passing the
already-populated `frame_mi_grid` directly to:

1. `apply_loop_filter_to_frame` — receives `&frame_mi_grid` (same type
   as today, `&[Option<ModeInfo>]`).
2. `self.last_frame_mi_grid = frame_mi_grid` — moves the Vec into the
   decoder's retained state (same as today, just no intermediate stitch
   step).

### 2.7 Consumer impact: loop filter + bitstream-diff harness

Both consumers already expect a `&[Option<ModeInfo>]` with stride =
`mi_cols`. Since the pre-allocated grid uses exactly that layout, no
changes are needed in `apply_loop_filter_to_frame` or
`last_frame_mi_grid()`.

## 3. Safety & Correctness

### 3.1 Non-overlapping column ranges

VP9 tile boundaries are SB-aligned (64-pixel = 8 MI-unit boundaries).
Tiles in the same tile-row share `mi_row_start..mi_row_end` but have
disjoint `mi_col_start..mi_col_end` ranges. Tiles in different tile-rows
have disjoint `mi_row_start..mi_row_end` ranges entirely. Therefore no
two tiles can write to the same `(mi_row, mi_col)` cell — the grid
regions are strictly non-overlapping.

### 3.2 `above()` at tile's first row

The 1-D `above` vector is reset to all-`None` at construction. On the
first SB row of a tile, `above(col)` returns `None` — matching libvpx's
`up_available = 0` at frame-top. This is unchanged by the Phase 2 design.

For the 2-D `mi_at` path (used by `NeighbourLookup` / `find_mv_refs`):
reading `mi_at(row: -1, col)` resolves to a negative tile-relative row,
caught by the `mi_row >= self.tile_mi_rows` unsigned underflow check
(since `mi_row` is `usize`, a negative value wraps to `>= tile_mi_rows`).
This returns `None`, consistent with today.

In multi-tile-row layouts, the tile's first row corresponds to a frame row
that may have been written by a tile in the preceding tile-row. Since
`mi_at` is clamped to the current tile's bounds, it will NOT read across
tile-row boundaries — matching libvpx's `is_inside(tile, ...)` predicate.
This is the correct VP9 behaviour: cross-tile-row MV references are
explicitly disallowed by the spec.

### 3.3 Thread safety for concurrent writes

The same safety argument as Phase 1's `TileFrameView`:

1. Each tile writes only within its own `(mi_row_start..mi_row_end,
   mi_col_start..mi_col_end)` rectangle.
2. These rectangles are non-overlapping (Section 3.1).
3. No `&` or `&mut` reference to the parent `frame_mi_grid` vector
   exists between `TileMiView` construction and `scope.join()`.
4. `TileMiView` is `Send` (same reasoning as `TileFrameView`).
5. The scoped thread pool guarantees that `frame_mi_grid` outlives all
   views.

Reads via `mi_at` during decode only access cells within the same tile's
rectangle — cells that were written earlier in the same tile's SB walk.
No cross-tile reads occur during decode (only post-decode consumers like
the loop filter read the full grid, after all tiles have joined).

## 4. Integration Points

### 4.1 `TileDecodeCtx` struct (`tile_ctx.rs`)

- Remove the owned `mi_grid: Vec<Option<ModeInfo>>` field.
- Add `mi_view: TileMiView` field (by-value, no lifetime parameter).
- Add `mi_col_start: usize`, `mi_row_start: usize` fields.
- Remove `new_with_grid` constructor; replace with
  `new_with_view(tile_mi_cols, tile_mi_rows, mi_view, mi_col_start, mi_row_start)`.
- Update `mi_grid()` accessor: return a slice from the view
  (or remove if no longer needed — the loop filter reads the frame grid
  directly now).
- Update `write_block`, `mi_at`, `mi_at_relative` per Sections 2.4-2.5.
- `TileNeighbourLookup` (`tile_ctx.rs:422`) — no changes needed; it
  delegates to `mi_at_relative` which is updated in place.

### 4.2 Parallel dispatch (`lib.rs`, intra path ~line 1530)

Before the scope:
```rust
let mut frame_mi_grid: Vec<Option<ModeInfo>> = vec![None; mi_rows * mi_cols];
let mi_views: Vec<TileMiView> = per_tile_bounds.iter().map(|b| { ... }).collect();
```

Inside `TileSlot`:
- Replace `result: Mutex<Option<Result<TileDecodeCtx, ...>>>` — the
  `TileDecodeCtx` now borrows from `frame_mi_grid` via raw pointer, so
  it can still be moved out of the slot without lifetime issues.
- Alternatively, workers return only the `above` row (needed for nothing
  post-decode) and the error status. The MI data is already in
  `frame_mi_grid`.

Post-scope:
- Remove the `tile_grids` collection + `build_frame_mi_grid` call.
- Pass `&frame_mi_grid` directly to `apply_loop_filter_to_frame`.
- Move `frame_mi_grid` into `self.last_frame_mi_grid`.

### 4.3 Parallel dispatch (`lib.rs`, inter path ~line 2456)

Identical pattern to 4.2. The inter path's `InterTileSlot` struct gets
the same treatment.

### 4.4 Serial (inline) path

The serial path currently runs tiles sequentially, each owning a
`TileDecodeCtx`. After the change:

```rust
let mut frame_mi_grid: Vec<Option<ModeInfo>> = vec![None; mi_rows * mi_cols];
for tile_buf in &buffers {
    let bounds = tile_bounds(...);
    let mi_view = unsafe { TileMiView::new(...) };
    let decode_ctx = decode_tile_intra(tile_data, bounds, ..., mi_view, ...)?;
    // decode_ctx can be dropped — MI data is already in frame_mi_grid.
}
// No stitch needed.
apply_loop_filter_to_frame(&mut yv12, &frame_mi_grid, ...);
```

Since tiles run sequentially on the serial path, only one `TileMiView`
exists at a time — no aliasing concern even without the scope.

### 4.5 Consumers of the MI grid

| Consumer | Change needed? |
|----------|---------------|
| `apply_loop_filter_to_frame` | No — already takes `&[Option<ModeInfo>]` with stride = mi_cols |
| `self.last_frame_mi_grid` | No — receives the Vec by move |
| `last_frame_mi_grid()` accessor | No — returns `&[Option<ModeInfo>]` |
| Bitstream-diff harness (L4) | No — reads via `last_frame_mi_grid()` |
| Unit test `build_frame_mi_grid_stitches_two_tiles_in_row` | Remove or rewrite as a `TileMiView` integration test |

## 5. Conformance Guarantee

### 5.1 Bit-exactness

This change is purely a storage-layout optimisation. The decode logic
writes the same `ModeInfo` values to the same logical `(mi_row, mi_col)`
cells; only the physical address computation changes (from
`tile_row * tile_mi_cols + tile_col` to
`frame_row * mi_cols + frame_col`). The values written are identical,
the order of writes is identical (within each tile, the SB walk order is
unchanged), and the post-decode grid contents are byte-for-byte identical
to what `build_frame_mi_grid` previously assembled.

No prediction context is affected because:
- `above()` / `left()` still read from the owned 1-D vectors (unchanged).
- `mi_at` / `mi_at_relative` (used by `find_mv_refs`) read from the same
  logical cells — just at a different physical stride.

### 5.2 Verification plan

1. **Existing conformance suite** — run the full corpus (keyframe +
   inter, single-tile + multi-tile, Profile 0 + Profile 1). Bit-exact
   output match confirms no regression.

2. **Bitstream-diff harness (L4 MI grid)** — the harness already
   compares `last_frame_mi_grid()` cell-by-cell against libvpx's
   `mi_grid_visible` dump. Any mismatch triggers a hard failure.

3. **Unit test replacement** — replace
   `build_frame_mi_grid_stitches_two_tiles_in_row` with a test that
   constructs two `TileMiView`s over a shared grid, writes via
   `TileDecodeCtx::write_block` from each, then asserts the frame grid
   is correctly populated.

4. **Profile measurement** — re-run the `profile-tiles` timing harness.
   The `grid_stitch` bucket should drop to zero (or be removed from the
   timing struct). Net frame-time improvement: ~663 us on 1080p.

## 6. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| Lifetime propagation if `TileMiView` uses references instead of raw pointers | Medium | High — touches entire call stack | Use raw-pointer design (no lifetime parameter), same as Phase 1's `TileFrameView`. Safety enforced by construction contract, not borrow checker. |
| `mi_at` reads stale `None` during decode if indexing is wrong | Low | High — silent conformance failure | Bitstream-diff L4 catches any mi_at mismatch immediately. Add debug_assert in `write_block` that frame-absolute coords are within bounds. |
| Multi-tile-row: tile B reads from tile A's region via `mi_at` | None (by design) | N/A | `mi_at` clamps to tile bounds (Section 3.2). VP9 spec forbids cross-tile-row MV references. |
| `Send` impl unsoundness if bounds overlap | None (by VP9 spec) | Critical | Add a debug-mode assertion at `TileMiView` construction that no two views' rectangles overlap (O(n^2) check, debug-only). |
| Serial-path regression (single tile, no stitch was needed) | Low | Low — already fast | Single-tile frames skip `build_frame_mi_grid` today via a short-circuit; Phase 2 makes this path even simpler (the one tile writes directly into the frame grid, no special case needed). |
| Increased peak memory (grid allocated before tiles start) | Negligible | None — same total allocation | Today's flow allocates per-tile grids (total cells = sum of tile_mi_rows * tile_mi_cols = mi_rows * mi_cols) PLUS the frame grid post-stitch. Phase 2 allocates only the frame grid — net memory reduction. |
