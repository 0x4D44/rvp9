branch coverage sits at **69.41%** — a 23-point delta. That is the symptom of
a test suite that has been built mostly around *happy-path bit-exactness*
(does our output match libvpx?) rather than *path enumeration* (does every
`if`/`else` arm fire?). Hitting the **98% branch target** means roughly
1,329 currently-missed branches need a triggering test — about 91% of the
ones we have today.

## 5. Where the missed branches concentrate

Reading the per-file table alongside the source, the 1,422 missed branches
fall into a small number of structural buckets:

### 5a. Env-gated diagnostic / instrumentation modules
Code paths gated on `RVP9_E*_*`, `RVP9_TRACE_*`, `RVP9_DEBUG_*`,
`RVP9_DUMP_*` env vars. With the env unset, the gate flips off the
recording path entirely, so every branch inside fires zero times.

| File | Missed branches |
|:-----|---:|
| `rvp9-encoder\src\e12stat.rs` | 40/40 (0%) |
| `rvp9-core\src\mv_search\e12stat.rs` | 12/12 (0%) |
| `rvp9-encoder\src\skipstat.rs` | 5/6 (16.7%) |
| `rvp9-encoder\src\predstat.rs` | 3/4 (25%) |
| `rvp9-core\src\entropy\bitacct.rs` | 3/4 (25%) |

These are deliberately silent in production — but they still need
**enable-the-env, exercise-the-path** tests so the diag accumulator
arithmetic and serialization don't quietly rot.

### 5b. Error / validation branches in CLI + container code
The `?` operator on every `parse`/`read` produces a branch; the
unhappy arm only fires for malformed input.

| File | Missed branches |
|:-----|---:|
| `rvp9-io\src\container.rs` | 34/51 (33%) |
| `rvp9-cli\src\bin\rvp9dec.rs` | 29/54 (46%) |
| `rvp9-cli\src\bin\rvp9enc.rs` | 16/28 (43%) |
| `rvp9-io\src\y4m.rs` | 12/30 (60%) |

Mostly fixable with truncated-input fixtures (`&buf[..n]` for various `n`)
and a CLI argument-table walk.

### 5c. Large state-machine modules with heavy `match`-on-enum

## 6. Test failure fixed pre-baseline

One test failed under coverage instrumentation before this run:

**`rvp9-cli::cli_roundtrip::help_lists_supported_and_not_yet_tags`** —
asserted that *every* CLI binary's `--help` contains both `[supported]`
and `[not yet]` tags. Commit `e434ff5` ("Wire all niche CLI flags in
rvp9dec to match vpxdec surface") removed the last `[not yet]` flag
from the decoder, so the assertion is now stale.

**Fix.** Asserted `[not yet]` appears across the *union* of binary
help outputs (so any CLI still surfacing unimplemented flags satisfies
the test), and kept the per-binary `[supported]` check intact. The
encoder still has 28 `[not yet]` tags, so the assertion still has bite.
See `crates/rvp9-cli/tests/cli_roundtrip.rs:165`.

This is the only `failed` test in the baseline run. All 1591 other
tests pass.

## 7. Excluded scopes (and why)

**`rvp9-harness`** — excluded from `--exclude` for the test set. Its
`tests/conformance.rs` walks all 28 conformance vectors which is
multi-minute; the harness lib code is still exercised by the
non-harness crates that depend on it. Future runs can include it on a
schedule.

**`rvp9-bench`** — same rationale; bench code is exercised only by
microbenchmarks and the throughput ratchet test.

**`rvp9-fuzz`** — `cargo-fuzz` `#![no_main]` crate, deliberately not a
workspace member. Out of scope for normal coverage runs; fuzz harness
coverage is separately tracked.

These exclusions affect the *test set*, not the *report set* — the
target files still have all their `#[cfg(test)]` blocks compiled in
and their coverage measured from whatever calls them through
intra-workspace dependencies. The cost of including them in the test
set is wall-time, not measurement accuracy.

## 8. Implications for the 98% branch target

Going from 69.41% → 98.00% on 4,649 branches means cutting missed
branches from 1,422 → ~93 — i.e. **covering 1,329 additional branches**.

A few inferences from the data above:

1. **Top-20 files first** — they hold 80% of the missed branches.
   A focused per-file push can move the needle far more cheaply than
   shotgun coverage.
2. **Env-gated diag modules are low-hanging fruit** — exhausting
   their branches is ~100 branches by enabling the env in 4–5 test
   fixtures. The branches are simple arithmetic / counter updates.
3. **The big state-machine files** (`mode_info`, `tile`, `lib.rs` in
   decoder + encoder) need **targeted unit tests** that construct
   specific `BlockSize × TxSize × Mode × RefFrame` combinations,
   *not* longer end-to-end runs. Adding a 4-second conformance vector
   will cover at most 5 new branches; a 50-line `#[test]` written to
   poke a specific arm covers 1–4 branches per test.
4. **A few files will fall just short of 98% in practice**: panic-only
   `else { unreachable!() }` arms, `cfg(target_arch)` fallbacks, and
   "ENOENT" branches on platform syscalls. The plan needs a documented
   list of accepted exclusions (with `#[cfg_attr(coverage, ...)]`
   guards) so the 98% target reflects *meaningful* coverage, not 100%
   of every `unreachable!()` arm.

## 9. Where to find the raw artifacts

| Artifact | Path |
|:---------|:-----|
| Full text summary | `target/coverage/baseline-summary.txt` |
| Per-file table (text) | `target/coverage/per-file.txt` |
| Per-file table (TSV) | `target/coverage/per-file-tsv.txt` |

To regenerate from scratch:
```bash
rm -rf target/llvm-cov-target target/coverage
mkdir -p target/coverage
cargo +nightly llvm-cov --workspace --branch --summary-only \
    --ignore-run-fail \
    --exclude rvp9-harness --exclude rvp9-bench \
  > target/coverage/baseline-summary.txt 2>&1
```

To produce an HTML report instead (drill-down per file, line-level
coverage in colour):
```bash
cargo +nightly llvm-cov --workspace --branch --html \
    --ignore-run-fail \
    --exclude rvp9-harness --exclude rvp9-bench
# Then open target/llvm-cov/html/index.html
```
