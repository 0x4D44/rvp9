**Scope statement (rvp9):** today a Profile-0/1 (8-bit) encoder only.
  - HBD presence is limited to the decoder-side scalar `highbd_idct4` / `highbd_idct4x4_16_add` skeleton (`crates/rvp9-core/src/transforms/inverse.rs:140-225`) plus its SimdDispatch slot (`crates/rvp9-core/src/dsp/dispatch.rs:701-2095`). No HBD predictor, loopfilter, fwd-txfm, quantize, SAD, variance, hadamard, subtract, satd, block-error or temporal-filter kernel exists.
  - `BitDepth::Ten` / `BitDepth::Twelve` are decoded from the bitstream (`crates/rvp9-core/src/bitstream/header.rs:494-526`) and written by the bitstream packer (`header.rs:748-776`) but **every encoder caller hardcodes `bit_depth: BitDepth::Eight`** (`crates/rvp9-encoder/src/lib.rs:526, 683, 874, 5976`; `frame_loop.rs:1645, 1910`). No `use_highbitdepth`-equivalent plumbing exists.
  - No `u16` frame-buffer plane type. All frame-buffer planes are `u8` in `rvp9-core` plane storage; `pred_high[][]` / `dc_pred_high[][][]` tables are absent.
  - No `YV12_FLAG_HIGHBITDEPTH` equivalent. No `xd->bd` field carried through `MacroBlockD`.
  - No HBD entry point in any encoder feature: rate-control `bit_depth` parameter is explicitly dropped (`crates/rvp9-encoder/src/rate_control/mod.rs:55`); RD threshold compute uses `bit_depth` for `convert_qindex_to_q` only (`mode_decision/rd_thresh.rs:180`).
  - Two `BitDepth` callers exist that gate on `BitDepth::Ten` / `BitDepth::Twelve`: `quant::dc_quant` / `ac_quant` (`crates/rvp9-core/src/quant/mod.rs:53-75`) and dequant tables (`quant/tables.rs:67-152`). These are wire-format-shared and would feed an HBD path but are never exercised on the encoder side.

**Method statement:** grepped `third_party/libvpx` recursively for `highbd_` and `HIGHBITDEPTH` (210 source files matched, 308 `vpx_highbd_*` rtcd entries, 25 `vp9_highbd_*` entries). Cross-grepped `crates/rvp9-encoder/`, `crates/rvp9-core/`, `crates/rvp9-decoder/` for `highbd`, `HighBd`, `BitDepth::Ten`, `BitDepth::Twelve`, `Profile2`, `Profile3`, `u16` plane buffers. Grouped findings by subsystem; within each subsystem listed each kernel/family with a single representative `file:line` (and a count of variants where applicable). Row-count sanity: this is a cross-cutting zone touching every encoder DSP family — 80 rows is in the expected band for a subsystem ~10× the picker's 2820 LOC in raw kernel count (308 rtcd protos alone), but the rows-per-LOC is intentionally compressed by treating each `*_{4x4,8x8,16x16,32x32}` set as one row (per the audit-template convention used in A1).

## Section-by-section narrative

### Transforms — inverse (IDCT / IHT / IWHT)

libvpx ships a complete HBD inverse pipeline: scalar `vpx_highbd_idct{N}x{N}_*_add` for `N ∈ {4,8,16,32}` with multiple sparse-coefficient fast paths (`_1`, `_10`, `_12`, `_38`, `_34`, `_135`, `_256`, `_1024`), the hybrid ADST/DCT `vp9_highbd_iht*` family for intra-mode-driven `tx_type ≠ DCT_DCT`, and the lossless Walsh-Hadamard `vpx_highbd_iwht4x4_*`. rvp9 has the **start** of this in `crates/rvp9-core/src/transforms/inverse.rs:140-225`: scalar `highbd_idct4` + `highbd_idct4x4_16_add`, with a `SimdDispatch::highbd_idct4x4_add` slot reserved (`dsp/dispatch.rs:701-2095`) but populated only with the scalar reference fallback. ## Cross-cutting gaps

### CC-1: u16 plane storage absent everywhere — single largest blocker

**Status: NOT PORTED**

Every kernel in `crates/rvp9-core/src/dsp/` operates on `&[u8]` / `&mut [u8]` slices. `PlaneRef` in `rvp9-core` is `u8`-only. There is no `u16` plane type and no `Pixel: Copy + Into<i32>` trait. Without this foundation, every one of the ~70 kernel rows above is unimplementable, and any HBD encoder feature is unreachable.

Two viable architectures:
(a) **Generic-over-Pixel** rewrite (`Pixel: Copy + From<u8> + …`) — minimal source duplication, max generic-instantiation surface, requires touching every kernel signature and call site.
(b) **Duplicate API** (`fn foo_8` / `fn foo_16`) — mirrors libvpx's approach with `vpx_*` / `vpx_highbd_*` pairs, doubles kernel files, easier per-kernel SIMD specialization.

Estimated work (option b, kernel only — excludes generics): ~30,000 LOC across DSP + 200 call-site fixes in the encoder. **HIGH impact** — gates every other HBD work item.

### CC-2: `BitDepth::Eight` hardcoded in every encoder caller

**Status: NOT PORTED**

Six call sites in `crates/rvp9-encoder/` and `frame_loop.rs` hardcode `bit_depth: BitDepth::Eight` (lib.rs:526, 683, 874, 5976; frame_loop.rs:1645, 1910). The encoder's `EncoderConfig` does not surface a `bit_depth` field. The bitstream writer's Profile-2/3 branch (`header.rs:748-776`) is therefore dead code at encode time even though it works correctly when an HBD header is round-tripped through the decoder.

~50 LOC to surface `bit_depth` from CLI/config and thread it through to every header build site. Independent of CC-1 — this row alone unblocks the Profile 2/3 *bitstream signalling* path even if all kernels stay scalar+8-bit (assuming downstream short-circuit to a "Profile 0 fallback" warning until kernels land).

### CC-3: No `xd->bd` / `MacroBlockD::bd` plumbing

**Status: NOT PORTED**

libvpx threads `bd` via `xd->bd` (set in `vp9_encoder.c:2088`). Every HBD kernel reads it. rvp9's `MacroBlockD`-equivalent (`mode_decision/state.rs`) has no `bd` field. Adding it is trivial (5 LOC); making every callee read it is the work — partially subsumed by CC-1 if we go generic, but still required to select between 10-bit and 12-bit clamp constants when both `BitDepth::Ten` and `BitDepth::Twelve` are valid for the same Profile (Profile 2: 10-or-12-bit 4:2:0; Profile 3: 10-or-12-bit non-420).

### CC-4: No `YV12_FLAG_HIGHBITDEPTH` equivalent — frame I/O is 8-bit only

**Status: NOT PORTED**

`vpx_scale/generic/yv12config.c:270` flips plane allocation to `uint16_t`. rvp9's frame-buffer types in `crates/rvp9-core/src/frame/` have no equivalent flag. The CLI (`crates/rvp9-cli/src/bin/rvp9enc.rs`) has no y4m/raw 10-bit ingest path; `tests/cli_arg_coverage.rs:1209` only verifies a *decoder* warning when output bit-depth ≠ 8 (rows 1189, 1209, 1227 are decoder-side). HBD I/O is a precondition for end-to-end Profile-2/3 encoding.

### CC-5: Cost-model / lambda / RD tables are 8-bit-tuned

**Status: PARTIAL → NOT PORTED for HBD**

libvpx's `compute_rd_mult` (rd.c) and `vp9_set_speed_features_framesize_independent` both scale lambda by `bit_depth`. rvp9's `compute_rd_mult` (`crates/rvp9-core/src/cost/rd_mult.rs`) — verified by grep, no `bit_depth` parameter — uses the 8-bit lambda mapping unconditionally. Even when HBD kernels land, the RD model will mis-budget by ~16× (10-bit) / ~256× (12-bit) coefficient magnitudes unless the lambda scaling is re-introduced.

### CC-6: SIMD dispatch table has only one HBD slot

**Status: PARTIAL**

`crates/rvp9-core/src/dsp/dispatch.rs:701-2095` exposes a single `highbd_idct4x4_add` slot, populated with the scalar reference. The other ~30 HBD-relevant entries (idct8/16/32, fdct, fht, lpf{H,V}{4,8,16}, quantize_b, quantize_fp, hadamard, satd, sad ladders × 13 sizes, variance ladders × 13 × 3-bd, convolve8 H/V, subtract, predictors × 11 modes × 4 sizes) have **no slot at all** — they cannot be specialized to AVX2/SSE4 even if scalar reference code lands.

This is a deliberate Track-T-phase-0 scaffold (per the `dispatch.rs:701` comment), so it's correctly PARTIAL rather than ABSENT, but the kernel families that need to be plumbed in for HBD parity are ~30 entries deep.

### CC-7: No HBD test fixtures

**Status: NOT PORTED**

The proptest regressions under `crates/rvp9-core/proptest-regressions/dsp/` are all 8-bit. No HBD differential-test fixture exists. When HBD kernels do land they will need libvpx-c-reference oracles per kernel — this is a prerequisite for any anti-G3 PROOF test that gates the wiring.
