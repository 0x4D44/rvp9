## Headline

The kernels themselves are in good shape. Every bounds proof holds, every rounding formula
matches its scalar oracle, and the one numeric guard in the batch (`pass1_is_safe`) is exactly
— not approximately — tight. **No wrong-output defect was found in any of the five new
kernels.**

What this batch did lose is *verification*. On x86_64 the five commits replaced the scalar arm
of six kernel families with SSE2 selected at compile time, outside the runtime dispatch table
that `RVP9_FORCE_SCALAR` masks. The documented cross-process byte-identity oracle therefore now
runs the same code in both legs for exactly the newest kernels. Alongside that, the 8x8 DCT's
extreme-value tests turn out to be vacuous, and the integral-projection kernel's scalar oracle
is no longer compiled on x86_64. Three independent holes in the net, all pointing the same way:
the new code is less checked than it looks.

### F1 — `RVP9_FORCE_SCALAR` no longer yields a scalar encoder on x86_64
**Severity: Medium · Confidence: High · Filed as RVP9-BUG-CRU-00001 · Effort: medium**

`crates/rvp9-core/src/dsp/caps.rs:56-79` documents the byte-identity oracle: encode twice,
once with `RVP9_FORCE_SCALAR=1`, byte-diff to prove no SIMD kernel moved a decision. It works
by masking every ISA tier in `X86Caps::detect()`, which only reaches kernels resolved through
the `SimdDispatch` table.

Six families now bypass that table entirely, selected by bare
`#[cfg(all(target_arch = "x86_64", not(miri)))]`:

- `crates/rvp9-core/src/transforms/forward.rs:506-509` — `sse2::fdct8x8`
- `crates/rvp9-core/src/transforms/forward.rs:1099-1102` — `sse2::fdct16x16`
- `crates/rvp9-core/src/mv_search/int_pro_me.rs:340-343` — `vpx_vector_var_sse2`
- `crates/rvp9-core/src/mv_search/int_pro_me.rs:716-726` — `int_pro_64x64_fused_sse2`
- `crates/rvp9-core/src/mode_decision/hadamard.rs:219-222, 235-238, 296-299` — SSE2 Hadamard
- `crates/rvp9-core/src/mode_decision/inter.rs:5580-5616` — `quantize_metrics_sse2`

Verified: `crates/rvp9-core/src/dsp/dispatch.rs` holds no slot for any of them, and none of the
six files mention `force_scalar_env`, `X86Caps`, or `is_x86_feature_detected!`. Both legs of the
oracle run identical SSE2 code, so a divergence introduced into any of these six is invisible to
it.

Before this batch x86_64 ran scalar for all six, so the variable was effectively honoured there.
The same structural gap already existed on AArch64; this batch makes it live on x86_64, the
platform the PLAN.md §2 release gates target. `scripts/qualify-conformance.sh:28,31` and
`scripts/qualify-alpha-conformance.sh:25` do run a forced-scalar leg, but they gate the
*decoder*; all six kernels are encoder-only, so those scripts never covered them.

Found independently by the quantizer, Hadamard and test-coverage lenses and by the lead.

**Fix:** give the six families `SimdDispatch` slots and route callers through
`crate::dsp::get_ref()` — sibling commit `daae16aaa` did exactly this, correctly, for the large
candidate IDCTs in the same batch. Cheaper stopgap: consult `force_scalar_env()` in each public
wrapper. Either way, correct the now-false claims in `crates/rvp9-core/src/dsp/caps.rs:56-66`
and in CLAUDE.md. Structural version captured as RVP9-REQ-CRU-00006.

### F2 — `fdct8x8` SSE2 extreme-residual tests are vacuous
**Severity: Medium · Confidence: High · Filed as RVP9-BUG-CRU-00002 · Effort: low**

In `fdct8x8_sse2_matches_scalar_valid_residuals`
(`crates/rvp9-core/src/transforms/forward_sse2.rs:295-348`), the three "extreme" groups —
constant residual (`:318-325`), axis-alternating extremes (`:327-337`), per-index impulse
(`:339-347`) — all drive `pass1_is_safe` (`:102-110`) to `false`. `fdct8x8_inner` then returns
early at `:127-129` and `fdct8x8` calls `super::fdct8x8_scalar` at `:154-156`. The test asserts
`vector == scalar` where `vector` *is* `scalar`. Those assertions cannot fail.

Derived in closed form rather than by running anything. The guard rejects any first-pass output
outside `[-4096, 4095]`. For a constant residual of magnitude `v`, inputs are `4v` after the
`_mm_slli_epi16(_, 2)` at `:117`, so `x0 + x1` at `:85` is `32v` and
`output[0] = round(32v · COSPI_16_64 / 2^14) = round(22.62·v)`. The guard fires for `|v| > 181`:

| Test group | Largest first-pass output | Guard |
|---|---|---|
| constant ±255 | `\|output[0]\| = 5771` | fires |
| axis 0 (rows alternate ±255) | `output[7] = -5228` | fires |
| axis 1 (columns alternate ±255) | `\|output[0]\| = 5771` | fires |
| impulse (63 lanes −255, one +255) | `\|output[0]\| = 5770` | fires |

So the SSE2 arithmetic is covered only by the 512 random cases at `:296-317`. Those draw
residuals uniform in `[-255, 255]`, whose per-column means sit near zero — roughly 3.5 sigma
from the guard boundary. The kernel's behaviour just *below* the guard, where `x0 + x1` reaches
`8 · 4095 = 32760` and comes within 7 of `i16::MAX`, is untested. That is exactly where an i16
wrap would first appear, and where the saturating `_mm_packs_epi32` in `mul_round16` (`:23`)
would diverge from the oracle's truncating `wraplow`
(`crates/rvp9-core/src/transforms/constants.rs:183-185`).

Found independently by the lead and the performance lens.

**Fix:** add cases engineered to land just inside the guard (a constant residual of ±180 gives
`|output[0]| = 4072`), and assert the vector path actually ran, so the case cannot silently
degrade to scalar-vs-scalar again. Add a matching just-outside case asserting the fallback *is*
taken.

### F3 — `vpx_vector_var_scalar` is not compiled on x86_64, including under `cargo test`
**Severity: Medium · Confidence: High · Filed as RVP9-BUG-CRU-00003 · Effort: low**

Commit `edd62aa9e` tightened the cfg at `crates/rvp9-core/src/mv_search/int_pro_me.rs:316` to
`#[cfg(any(not(any(target_arch = "aarch64", target_arch = "x86_64")), miri))]` without adding
`test`. Every sibling oracle touched in the same batch did add it —
`fdct16x16_scalar` at `crates/rvp9-core/src/transforms/forward.rs:1011`, and all four scalar
helpers at `crates/rvp9-core/src/mode_decision/hadamard.rs:40, 82, 123, 179`.

Not a build break: the scalar arm of `vpx_vector_var` (`int_pro_me.rs:344-347`) is cfg'd out on
the same configuration, so nothing calls the missing function. The cost is to test integrity.
The SSE2 kernel's only check is `scalar_vector_var`
(`crates/rvp9-core/src/dsp/x86_64/int_pro_sse2.rs:273-283`), a second implementation of the
formula hand-written inside the SSE2 file's own test module. The production oracle and the thing
the kernel is tested against are now two pieces of code that nothing keeps in agreement.

**Fix:** add `test` to the cfg, raise `vpx_vector_var_scalar` to `pub(crate)`, and have the SSE2
test call it instead of the local copy.

### F4 — x86_64 realtime `fdct8x8` pays a range check AArch64 avoids
**Severity: Medium · Confidence: High (mechanism) / estimate (frequency) · Filed as RVP9-BUG-CRU-00004 · Effort: medium**

`fdct8x8_libvpx_lowbd` (`crates/rvp9-core/src/transforms/forward.rs:521-530`) is the realtime
8x8 forward DCT — called from `crates/rvp9-core/src/mode_decision/inter.rs:5847` and
`crates/rvp9-encoder/src/lib.rs:13172, 13947`. On AArch64 it uses a dedicated unchecked kernel
(`crates/rvp9-core/src/transforms/forward_neon.rs:1493-1500`). On x86_64 it falls through to
the general `fdct8x8`, which since `a39734335` is the *checked* SSE2 kernel: full first pass,
range check, and on failure a complete scalar redo of both passes.

Two consequences.

**Performance.** By the F2 derivation the guard fires when mean `|residual| > 181`, about 71% of
the legal ±255 range — reachable on keyframes, scene cuts, fades, and badly-predicted blocks,
i.e. where realtime throughput is tightest. When it fires the cost is the vector first pass plus
the check plus a full scalar redo: strictly worse than having called scalar directly. The
threshold is exact; how often it happens on real footage was not measured and is the open
question.

**Parity.** AArch64 realtime uses libvpx's approximate kernel and x86_64 an exact one, so the
same input yields different 8x8 coefficients on the two architectures. This predates the batch
(x86_64 previously used the exact `fdct8x8_scalar`) and is therefore not a regression — but it
is undocumented, and this batch did not close it.

Neither behaviour is in `notes/divergence-ledger.md`: searches for `lowbd`, `4095`, `pass1` and
"approximate first-pass" return nothing, though the NEON `fdct16x16` entry at
`notes/divergence-ledger.md:894-911` shows the format such entries take. CLAUDE.md requires
every deliberate departure from libvpx behaviour to be recorded. The doc comment at
`forward.rs:518-520` ("Other architectures use that implementation") is also stale — on x86_64
"that implementation" is now the SSE2 kernel, not the scalar one it described when written.

**Fix:** add the two missing ledger entries first (cheap, closes the process gap); then consider
porting a true unchecked SSE2 lowbd variant mirroring `forward_neon.rs:1005-1020`, gated on a
BD-rate delta; refresh the stale comment.

### F5 — Public bitstream writers silently truncate out-of-range fields
**Severity: Low · Confidence: High · Filed as RVP9-BUG-CRU-00005 · Effort: low**

Commit `bdb22b494` replaced a release-mode no-op `debug_assert!` in `write_tile_info` with real
validation (`crates/rvp9-core/src/bitstream/sub_parsers.rs:574-590`). Two siblings in the same
file still have the original defect.

`write_loopfilter` (`crates/rvp9-core/src/bitstream/sub_parsers.rs:135-140`) writes
`filter_level` as a 6-bit literal and `sharpness_level` as a 3-bit literal. Both are public
`u8` fields with no invariant (`:71-75`). Set `filter_level = 64`: `64 & 0x3F == 0`, so the
function returns `Ok(())` and emits a structurally valid header describing a different loop
filter than the caller asked for.

`write_delta_q` (`:226-232`) is the same class — a 4-bit magnitude plus sign, valid range
`-15..=15`, reached through public `write_quantization` (`:237-245`). `y_dc_delta_q = 100`
round-trips as `4`; `delta_q = -128` round-trips as `0`.

Low severity because `rvp9-encoder` never supplies out-of-range values. These are reachable only
by an external consumer of the published `rvp9-core` crate driving the writers directly — which
is exactly the audience `write_tile_info` was just hardened for.

Checked and already correct, so excluded: `QuantizationParams.base_qindex` (u8 into
`QINDEX_BITS = 8`), and `RawBitWriter::write_literal` / `write_bit` themselves (documented clamp
at `crates/rvp9-core/src/bitstream/raw.rs:96-101`, overflow poison flag at `:66-75`).

### F6 — Quantizer-metrics test domain stops at half the reachable coefficient magnitude
**Severity: Low · Confidence: High (gap) / Medium (whether it hides a bug) · Report only · Effort: low**

`sse2_matches_scalar_across_sizes_quantizers_and_extremes`
(`crates/rvp9-core/src/dsp/x86_64/quantize_metrics_sse2.rs:430-482`) bounds coefficients to
±16,320, including its explicit extremes. But Hadamard-domain coefficients reach ±32,640: the
16x16 combine computes `b0 + b2` in i16 where each term is already bounded by ±16,320
(`crates/rvp9-core/src/mode_decision/hadamard.rs:161-169`, and the SSE2 `combine_16` at
`crates/rvp9-core/src/mode_decision/hadamard_sse2.rs:150-169`). The quantizer and Hadamard
lenses derived the ±32,640 figure independently and agreed.

So the kernel's near-saturation band (16,321..32,767) — where `abs_saturating_i16`, the
saturating round-add, and the 32x32 `dequant>>2` gate interact — is exercised only by
hand-derivation, never by the test. Hand-derivation says it matches; that is inference, not
evidence. **Fix:** widen the PRNG range to at least ±32,640 for Tx16x16/Tx32x32 and add explicit
`i16::MIN`/`i16::MAX` boundary cases.

### F7 — No test pins the fused 64x64 integral projection to the scalar path it replaces
**Severity: Low · Confidence: High · Report only · Effort: low**

`fused_64x64_projections_match_scalar_with_padding_and_extremes`
(`crates/rvp9-core/src/dsp/x86_64/int_pro_sse2.rs:227-271`) checks the SSE2 kernel against
`fused_projection_oracle`, a bespoke oracle in the same test module — not against
`fill_int_pro_rows` / `fill_int_pro_cols`
(`crates/rvp9-core/src/mv_search/int_pro_me.rs:251-302`), which is what actually runs when
`used_fused_projection == false`.

The lead traced both by hand and they agree, so there is no live bug: the fused kernel's
`ref_h` covers rows `sb_px_y..+64` and columns `base_x_row..+128` normalised `>>5`, matching
`vpx_int_pro_row`'s `/ (height>>1)` for non-negative sums; `ref_v` covers rows
`base_y_col..+128` and columns `sb_px_x..+64` at `norm_factor = 3 + (bw>>5) = 5`; `src_h` and
`src_v` likewise. But the two paths are chosen by a runtime interior-vs-edge condition
(`int_pro_me.rs:693-702`) and nothing keeps them pinned together, so a future edit to either
side can silently change encoder decisions on interior superblocks only. **Fix:** one test that
runs both paths at the same superblock position and asserts equality.

### F8 — Misattributed SAFETY comment
**Severity: Low · Confidence: High · Report only · Effort: trivial**

`crates/rvp9-core/src/mode_decision/hadamard_sse2.rs:92-99` splits load and store into two
`unsafe` blocks with the comments swapped in meaning: the block that performs the `coeff` store
carries "The helper operates only on local SSE2 registers", while the load-only block carries
the comment mentioning the output store. The store is genuinely safe — `validate()` in the
`transform_wrapper!` macro (`:310-318`) proves it — but a reader auditing that block alone is
misled. `hadamard_8x8_subtract_inner` (`:112-127`) shows the correct pattern. **Fix:** merge the
two blocks, or move the comment.

### F9 — Weak Hadamard unit tests
**Severity: Low · Confidence: High · Report only · Effort: low**

Three tests in `crates/rvp9-core/src/mode_decision/hadamard.rs` cannot detect position or sign
errors:

- `hadamard_8x8_impulse_at_origin_is_constant_output` (`:384-399`) asserts `c.abs() == 5` for
  all 64 outputs — the all-same-value fixture anti-pattern; a swapped output lane still passes.
- `hadamard_8x8_dc_only_concentrates_in_dc` (`:344-364`) checks "exactly one nonzero bin, value
  `64*dc`" but never asserts the surviving bin is index 0.
- `hadamard_16x16_dc_concentrates` (`:401-414`) checks `coeff[0]` and none of the other 255.

These are not the primary defence — the differential tests at `:444-583` compare full arrays
against an independent scalar implementation across sizes, stride jitter and ±255 checkerboards,
and are strong. So the impact is false confidence in isolation, not an uncovered kernel.

### F10 — Unenforced input-domain preconditions on public kernels
**Severity: Low · Confidence: High · Report only · Effort: low**

Several new `pub fn`s assert slice lengths but silently depend on a value-range precondition
their SAFETY comments assert without enforcing:

- `crates/rvp9-core/src/transforms/forward_sse2.rs:258-260` — "Valid 8-bit residuals keep the
  first-pass schedule within signed i16". True (worst case `16 × 1020 = 16,320`, roughly 2×
  margin), but nothing checks it, unlike the 8x8 sibling's `pass1_is_safe`.
- `crates/rvp9-core/src/dsp/x86_64/int_pro_sse2.rs:169-171` — "Projection values are in
  `[0, 510]`". True for all current callers; the i16 lane accumulator at `:150` would wrap
  silently for anything larger, while the scalar oracle accumulates in i32.
- `crates/rvp9-core/src/dsp/x86_64/quantize_metrics_sse2.rs:31-33` — `abs_saturating_i16` maps
  `i16::MIN` to 32,767 where the scalar computes 32,768 in i32.

None is reachable today; the forward-DCT lens audited every caller and found all of them feed
`u8 − u8` residuals. Worth a `debug_assert!` each so a future caller fails loudly rather than
diverging silently.

## Not reported, and why

These were investigated and refuted. Recording them so the next pass does not re-chase them.

- **Decoder-reachable tile-geometry vulnerability.** The unsafe lens was briefed to treat
  `bdb22b494` as attacker-facing. It is not: the commit only touches `write_tile_info`, the
  *encoder's* writer. `parse_tile_info` (`crates/rvp9-core/src/bitstream/sub_parsers.rs:531-563`)
  is unchanged, and was separately verified sound — `mi_cols` derives from a 16-bit frame-size
  read giving `[1, 8192]`, `log2_tile_cols > 6` is rejected by a pre-existing (and load-bearing,
  since `get_tile_n_bits(8192)` can return 7) check, `log2_tile_rows` is structurally bounded to
  `{0,1,2}` by the two-bit read, and errors propagate via `?`.
- **`pass1_is_safe`'s `[-4096, 4095]` bound is wrong.** It is exactly right. `8 × 4095 = 32,760`
  fits i16 with 7 to spare, while a symmetric ±4096 bound would give `8 × 4096 = 32,768` and
  wrap. The asymmetry is deliberate, and the check sits at the correct point — before
  `transpose8`, which only permutes lanes.
- **`fdct16x16` missing an equivalent guard is a live bug.** It is not. Only the first pass is
  vectorized; the second pass calls the exact i64 scalar `fdct16_butterfly`
  (`crates/rvp9-core/src/transforms/forward_sse2.rs:263-287`), so the i16 second-pass overflow
  that the NEON kernel needed a guard for (see `notes/divergence-ledger.md:894-911`, where the
  constant −255 residual gave 13,701 instead of −32,639) cannot arise here. The first pass has
  ~2× margin, and a full caller audit found no path supplying residuals outside ±255.
- **Saturation-vs-truncation divergence between `_mm_packs_epi32` and `wraplow`.** Real in
  principle — `wraplow` is `x as i16 as i32` (`crates/rvp9-core/src/transforms/constants.rs:183-185`),
  a truncating wrap, while `packs` saturates. But `pass1_is_safe` keeps every value inside i16
  for the 8x8, and the 16x16 second pass never narrows. No reachable divergence.
- **Off-by-one in strided loads.** Checked in all four new kernels. Every one uses the correct
  `(H-1)·stride + W` form, not `H·stride` — `crates/rvp9-core/src/dsp/x86_64/int_pro_sse2.rs:107-116`
  (`127·stride+128` and `63·stride+64`, via `checked_mul`/`checked_add`),
  `crates/rvp9-core/src/mode_decision/hadamard_sse2.rs:288-308`,
  `crates/rvp9-core/src/transforms/forward_sse2.rs:150-151, 254-255`. The lesson from
  `lessons_learnt.md` ("a strided 64x64 tail needs 63*stride+64, not 64*stride") was applied
  correctly. Caller-side gating at `crates/rvp9-core/src/mv_search/int_pro_me.rs:693-702` was
  traced too and does prove the tail slices are long enough.
- **`RawBitWriter::write_literal` accepting `bits > 32`.** Documented and clamped
  (`crates/rvp9-core/src/bitstream/raw.rs:96-101`); buffer overflow sets a poison flag surfaced
  by `finish()`. Not the same class as F5.
- **Cfg exhaustiveness across build configurations.** Every dispatch site was enumerated over
  {x86_64, aarch64, other arch} × {miri, not-miri} × {test, not-test} plus
  `--features highbitdepth`. Exactly one branch compiles in every combination, including the
  nested cfgs in `forward.rs::fdct16x16` and `int_pro_me.rs::vpx_vector_var`. No build break, no
  double-execution.
- **Missing libvpx file:line citations.** `int_pro_sse2.rs`, `quantize_metrics_sse2.rs` and
  `forward_sse2.rs` lack the citations CLAUDE.md asks for, where `hadamard_sse2.rs:1-4` has them.
  Real but a nit; noted here rather than tracked.

## Verification limits

State plainly what this pass did *not* establish.

- **No code was executed.** No `cargo test`, no `cargo clippy`, no Miri, no benchmark. Every
  claim above is from reading source and deriving arithmetic by hand. F2's derivation in
  particular predicts which branch the existing tests take; it has not been observed.
- **libvpx was unavailable.** `third_party/libvpx/` is not checked out in this worktree, so no
  finding was cross-checked against the reference C. Verification is against the repo's own
  scalar oracles, which is the documented bit-exactness contract for these dispatches, but it
  means a shared error between a scalar oracle and its SIMD port would not be caught here. The
  Hadamard lens specifically could not confirm whether `hadamard_8x8_scalar`'s coefficient
  *ordering* matches `vpx_hadamard_8x8_c` — self-consistent and irrelevant to SATD (an
  order-invariant sum of magnitudes), but the module doc's "mirrors libvpx's ordering" claim is
  unverified.
- **F4's trigger frequency is an estimate.** The `|v| > 181` threshold is exact; how often real
  footage crosses it is not measured.
- **`PlaneRef`'s own length invariant was assumed, not re-derived.** The fused int_pro call
  site's gating was verified against `plane.width`/`plane.height`; the construction sites that
  guarantee `data.len() >= stride * height` were not chased.
- **Scope was the diff, not the whole crate.** `crates/rvp9-core/` has ~145 files. This pass
  covered the 11 changed since `06cf08bca` plus the immediate context needed to judge them.
