# HLD: Phase 3 — Row-Parallel Loop Filter

**Date:** 2026-05-24
**Status:** Draft (pre-implementation review)
**Scope:** Parallelize the VP9 in-loop deblocking filter across horizontal SB-row bands to eliminate its 35.5% frame-time bottleneck on 1080p content.

---

## 1. Problem Statement

The loop filter (`apply_loop_filter_to_frame` in `crates/rvp9-decoder/src/lib.rs:3145`) currently runs entirely on the main thread after all tile decode completes. On 1080p content (17 SB rows x 30 SB cols = 510 superblocks), profiling under the `profile-tiles` feature shows:

| Phase | Cycles | Time (us) | % Frame |
|-------|--------|-----------|---------|
| Tile decode (parallel, 4T) | ~4,100 | 4,100 | 42.2% |
| **Loop filter (serial)** | ~3,448 | **3,448** | **35.5%** |
| Grid stitch + border extend | ~2,170 | 2,170 | 22.3% |

The LF is the single largest sequential bottleneck. By Amdahl's law, with 4 threads the maximum theoretical speedup without parallelizing the LF is:

    Speedup_max = 1 / (0.355 + (1 - 0.355) / 4) = 1 / (0.355 + 0.161) = 1.94x

Parallelizing the LF across N=4 threads reduces its sequential fraction to near zero:

    Speedup_new = 1 / (0.355/4 + 0.645/4) = 1 / 0.250 = 4.0x (ideal)

In practice, inter-band dependency staggering and synchronization overhead reduce this, but the target is 2.8-3.2x total frame speedup (up from the current ~1.9x with only tile parallelism).

## 2. Design

### 2.1 Band Decomposition

The frame is divided into N horizontal **bands**, where N equals the number of worker threads (typically 4). Each band spans a contiguous range of SB rows:

```
Band 0:  SB rows [0 .. sb_rows/N)        → mi_rows [0 .. B)
Band 1:  SB rows [sb_rows/N .. 2*sb_rows/N) → mi_rows [B .. 2B)
  ...
Band N-1: SB rows [(N-1)*sb_rows/N .. sb_rows) → mi_rows [(N-1)*B .. mi_rows)
```

where `B = (sb_rows / N) * MI_BLOCK_SIZE` is the MI-row extent of each band (except the last, which absorbs the remainder).

The existing `loop_filter_frame_with_non420` already accepts `start_mi_row` / `end_mi_row` parameters (see `crates/rvp9-core/src/loopfilter/apply.rs:168-180`), so band dispatch requires zero changes to the inner filter logic — each worker simply calls the existing function with its band's MI-row range.

### 2.2 Data Access Classification

| Data | Access Pattern | Synchronization |
|------|----------------|-----------------|
| `lfm_grid: &[LoopFilterMask]` | Read-only | None needed (shared `&` across all bands) |
| `info: &LoopFilterInfo` | Read-only | None needed |
| `non420.mi_grid: &[ModeInfo]` | Read-only | None needed |
| `non420.levels: &FrameFilterLevels` | Read-only | None needed |
| `yv12: &mut Yv12Buffer` (pixels) | Read+Write (in-place) | Split-borrow by row range (see 2.3) |
| `SimdDispatch` | Read-only (function pointers) | None (Arc clone, immutable after init) |

All inputs except the pixel buffer are immutable after construction. The only mutable state is the `Yv12Buffer` pixel data, which each band writes in-place within its own row range.

### 2.3 Pixel Buffer Split-Borrow

The `Yv12Buffer` must be shared for concurrent read+write. The approach mirrors Phase 1's `TileFrameView` pattern but with row-range splits rather than column-range splits:

```rust
/// A non-overlapping mutable view into a horizontal row-range of a
/// Yv12Buffer's planes. Provides &mut [u8] slices over exactly the
/// pixel rows this band is allowed to write.
pub struct LfBandView {
    // Per-plane raw pointers to the first byte of band's writable region.
    y_ptr: *mut u8,
    u_ptr: *mut u8,
    v_ptr: *mut u8,

    // Byte lengths of the writable regions (rows_in_band * stride).
    y_len: usize,
    u_len: usize,
    v_len: usize,

    // Strides (same as parent).
    y_stride: usize,
    uv_stride: usize,

    // Plane total dimensions (for offset computation into the full slice).
    y_total_len: usize,
    uv_total_len: usize,

    // Chroma format for dispatch.
    chroma: ChromaFormat,
}
unsafe impl Send for LfBandView {}
```

**However**, an `LfBandView` is insufficient on its own because the horizontal filter reads pixels from adjacent bands (see Section 3). The actual implementation must expose the full plane as a single `&mut [u8]` to each band — which requires `unsafe` split-pointer access — or use the simpler approach: wrap the entire plane in a shared raw pointer and rely on the correctness proof in Section 4 to justify concurrent access.

**Chosen approach: `UnsafeCell`-wrapped raw plane access.** Each band receives a struct containing:
- A raw `*mut u8` pointer to each plane's origin.
- The total plane byte length.
- The plane stride.
- Its assigned SB-row range.

This is the same pattern libvpx uses for its multi-threaded LF: the `LFWorkerData` struct carries a raw pointer to the frame buffer, and the synchronization protocol (Section 2.4) ensures no two workers write the same pixel.

### 2.4 Synchronization: Pipelined Row-Stagger with Atomics

The key insight: Band B+1 cannot start filtering SB row R until Band B has completed SB row R (because the horizontal filter at the top edge of B+1's SB row R reads pixels that Band B's SB row R writes). This creates a wavefront pipeline.

Each band publishes its progress via an `AtomicUsize` counter:

```rust
/// Per-band progress counter. Value = the number of SB rows this band
/// has fully completed (both vertical and horizontal passes, all planes).
progress: Vec<AtomicUsize>,  // progress[band_idx], length = N
```

**Protocol:**
1. Band 0 (top of frame) runs freely — no dependency above it.
2. Band B (B > 0) before starting SB row `local_row` checks:
   ```rust
   // Wait until the band above has completed enough rows.
   let required = local_row + STAGGER;
   while progress[B - 1].load(Ordering::Acquire) < required {
       std::hint::spin_loop();
   }
   ```
3. After completing SB row `local_row`, band B publishes:
   ```rust
   progress[B].store(local_row + 1, Ordering::Release);
   ```

where `STAGGER = 1` (see Section 3 for the proof that one SB row of stagger is sufficient).

**Why spin-wait, not condvar?** The expected wait time is sub-microsecond (one SB row takes ~200 us at 1080p; once the pipeline is full, each band finishes a row every ~200 us, so the next band waits at most one SB row's worth of latency). Condvar signalling overhead (mutex lock + futex wake) would dominate. libvpx uses the same spin-wait approach in its row-MT loop filter.

### 2.5 Band Entry Point (Parallel Driver)

A new public function in `crates/rvp9-core/src/loopfilter/apply.rs`:

```rust
/// Parallel loop-filter driver. Splits the frame into `num_bands`
/// horizontal SB-row bands and filters them concurrently with
/// pipelined stagger synchronization.
///
/// Requires `num_bands >= 1`. When `num_bands == 1`, falls through to
/// the serial `loop_filter_frame_with_non420` — zero overhead.
pub fn loop_filter_frame_parallel(
    yv12: &mut Yv12Buffer,
    lfm_grid: &[LoopFilterMask],
    lfm_stride: usize,
    sb_rows: usize,
    sb_cols: usize,
    mi_rows: usize,
    mi_cols: usize,
    info: &LoopFilterInfo,
    non420: Option<Non420Inputs<'_>>,
    scope: &FrameScope<'_, '_>,
    num_bands: usize,
) { ... }
```

**Implementation sketch:**
1. Compute band boundaries: `band_sb_start[b]`, `band_sb_end[b]`.
2. Allocate `progress: Vec<AtomicUsize>` on the stack (N entries, init 0).
3. Convert `yv12` to per-plane raw pointers (one `unsafe` block).
4. Submit N-1 band jobs to `scope`; run band 0 inline on the caller thread.
5. Each band job calls the existing `loop_filter_frame_with_non420` row-by-row loop (extracted into a `filter_band` inner function) with the stagger synchronization wrapper.

### 2.6 Fallback for Small Frames

If `sb_rows < num_bands`, reduce bands to `sb_rows`. If `sb_rows == 1` (e.g., 64-pixel-tall frame), fall through to fully serial execution. No overhead for sub-HD content.

## 3. Inter-Band Dependency Analysis

### 3.1 Maximum Horizontal Filter Span

The widest horizontal filter kernel is `lpf_horizontal_16` / `mb_lpf_horizontal_edge_w` (the 15-tap MB filter). From `crates/rvp9-core/src/loopfilter.rs:846-923`:

- The edge position is at row `s_index` (the first "q" row).
- **Reads** pixels at `s - 8*pitch` through `s + 7*pitch` (16 rows total: p7..p0, q0..q7).
- **Writes** pixels at `s - 8*pitch` through `s + 7*pitch` (all 16 positions).

So the maximum span is **8 pixel rows above the edge and 8 pixel rows below the edge** (including the edge row itself on the "below" side: rows -8 to +7 relative to `s_index`).

### 3.2 Where Do Horizontal Edges Sit Within an SB Row?

Within each 64x64 superblock (8 MI rows = 8 luma block-rows = 64 pixel rows), horizontal edges can appear at any 8-pixel boundary:
- Row 0 of the SB (= the "above" edge with the previous SB row)
- Rows 8, 16, 24, 32, 40, 48, 56 (internal edges)

The **first** horizontal edge of an SB row (at pixel row 0 of the SB, i.e., the boundary between this SB row and the one above) has its `s_index` at the SB-row's topmost pixel row. The 16-tap filter at this edge reads 8 pixels above it — those pixels belong to the **previous** SB row.

### 3.3 What Does Band B+1 Need from Band B?

Band B+1's first SB row has horizontal edges at pixel row 0 of its region. The widest filter at that edge reads 8 pixel rows above = rows that belong to the **last 8 pixel rows** of Band B's last SB row.

These pixels are:
- **Read** by Band B+1's horizontal pass on its first SB row.
- **Written** by Band B's filter passes on Band B's last SB row.

Therefore Band B must have **fully completed** its last SB row (both vertical and horizontal passes, all planes) before Band B+1 can start its first SB row's horizontal pass.

### 3.4 Vertical Filter Has No Cross-SB-Row Dependency

The vertical filter kernels (`lpf_vertical_*`) operate on at most 8 rows (or 16 for `_dual`) starting at the SB-row's top pixel. They read/write pixels at columns `s-8..s+7` horizontally, but vertically only within the current 8 or 16 pixel rows of the dual-row pass. Since the vertical pass for an SB row is entirely within that SB row's 64 pixel rows, there is no vertical cross-band dependency.

### 3.5 Minimum Stagger

**Key constraint:** Band B+1 cannot start the horizontal pass of its row R (specifically its topmost SB row) until Band B has completed the horizontal pass of its last SB row.

**Sufficient condition:** A stagger of **1 SB row** between adjacent bands is both necessary and sufficient.

```
STAGGER = 1  (in SB-row units)
```

Concretely: Band B+1 waits until `progress[B] >= band_B_last_sb_row + 1` before starting. Since we number progress from 0, Band B signals `progress[B] = sb_row_count_in_B` when done.

Actually, the wavefront is simpler because each band only needs the immediately preceding band to have finished **the SB row whose pixels overlap with its first SB row**. Since all of Band B's rows precede all of Band B+1's rows, and the dependency is only on Band B's last row, the stagger is:

```
Band B+1 starts only after Band B completes SB row (band_B_last_sb_row).
```

For the general pipelined case where bands have multiple SB rows each, the wavefront allows earlier rows to overlap. Band B+1 can start its 2nd SB row while Band B may still be on its last SB row, as long as Band B has completed all rows that the filter at the top of Band B+1's 2nd SB row depends on — but the 2nd SB row only depends on Band B+1's own 1st SB row (which is internal to B+1). So:

**Revised protocol (pipelined):**
- Band B+1's SB row 0 depends on Band B having completed **all** of its SB rows (since Band B+1's row-0 horizontal edge reads into Band B's last row).
- Band B+1's SB rows 1, 2, 3, ... depend only on Band B+1's own previously completed SB rows.

This means the only inter-band stall is at the **start** of each band — after that, Band B+1 runs freely through its remaining SB rows. The pipeline diagram:

```
Time →
Band 0: [=====R0=====][=====R1=====][=====R2=====][=====R3=====]
Band 1:                                            ↑ start      [=====R0=====][=====R1=====]...
Band 2:                                                                                     ↑ start ...
```

Wait — this is pessimistic. Let me reconsider.

### 3.6 Refined Pipelining (Per-SB-Row Progress)

Actually, with per-SB-row progress tracking, Band B+1 can start as soon as Band B finishes its **last** SB row. But if N = 4 and sb_rows = 17, each band has ~4 SB rows. The startup stall is ~4 SB-rows worth of serial time for Band 1, ~8 for Band 2, ~12 for Band 3. This reduces parallelism significantly.

**Better approach: finer-grained per-SB-row progress within each band.** Each band tracks how many SB rows it has completed. Band B+1 can start its first SB row once Band B has completed Band B's last SB row. Since the internal SB rows of B+1 have no dependency on Band B (only on B+1's own prior rows, which it processes sequentially), the protocol simplifies to:

```rust
// Band B+1 startup gate:
while progress[B].load(Acquire) < band_sb_count[B] {
    spin_loop();
}
// After passing the gate, Band B+1 runs all its SB rows sequentially.
```

This means the maximum pipeline parallelism is:
- Band 0 starts immediately.
- Band 1 starts after Band 0 finishes all its rows.
- Band 2 starts after Band 1 finishes all its rows.
- ...

**This is purely sequential!** There is no pipelining benefit if each band's first SB row depends on the previous band's last SB row.

### 3.7 Corrected Pipelining — Row-Level Stagger

The key realization: the horizontal filter at Band B+1's first pixel row only reads into Band B's **last** SB row. Specifically, it reads at most 8 pixel rows above = 8 rows into Band B's last SB row. Band B's last SB row is 64 pixels tall. So:

- The horizontal pass on Band B's last SB row processes internal edges at rows 8, 16, 24, 32, 40, 48, 56 (7 internal edges plus the top-edge from the SB above).
- The topmost internal edge of Band B's last SB row (the boundary between that SB and the one above) touches pixels 8 rows above that edge, which are in the SB row **before** Band B's last.
- Band B+1's first horizontal edge touches pixels 8 rows above — into the last 8 pixel rows (rows 56-63) of Band B's last SB row.

Those last 8 rows of Band B's last SB are written by:
1. Band B's **vertical** pass on that SB (writes to rows within the SB freely).
2. Band B's **horizontal** pass on internal edges at rows 48 and 56 of that SB.

So Band B+1 can start once Band B has completed **the entire filter** (both V and H passes, all planes) for its last SB row. Not earlier.

**Therefore, the effective parallelism pattern is a strict wavefront with 1-SB-row stagger at band boundaries, but full parallelism within interleaved SB rows:**

Wait, let me think about this more carefully with the libvpx approach. libvpx's row-MT loop filter uses a different decomposition: instead of coarse bands, it uses **per-SB-row parallelism** with a 1-row stagger. Each SB row is a unit of work, and SB row R+1 can start once SB row R is complete. With N workers pulling from a work queue:

```
Worker 0: SB row 0 → SB row 4 → SB row 8 → ...
Worker 1: SB row 1 → SB row 5 → SB row 9 → ...  (starts after row 0 done)
Worker 2: SB row 2 → SB row 6 → SB row 10 → ... (starts after row 1 done)
Worker 3: SB row 3 → SB row 7 → SB row 11 → ... (starts after row 2 done)
```

This gives maximum overlap: at any time, up to N adjacent SB rows can be in flight, each one SB row behind the previous.

### 3.8 Final Design: Per-SB-Row Wavefront

Adopt the per-SB-row wavefront model rather than coarse bands:

```rust
/// Per-SB-row progress. progress[r] = true once SB row r is fully filtered.
progress: Vec<AtomicBool>,  // length = sb_rows
```

Or equivalently, a single `AtomicUsize` counter representing the highest completed SB row:

```rust
/// Highest SB row index that has been fully filtered. All rows <= this
/// value are safe for the next row's horizontal pass to read from.
highest_complete: AtomicUsize,  // starts at 0 (meaning "row -1 done" / none)
```

**Work distribution:** A shared `AtomicUsize` work counter distributes SB rows:

```rust
next_row: AtomicUsize,  // starts at 0

// Each worker loop:
loop {
    let my_row = next_row.fetch_add(1, Ordering::Relaxed);
    if my_row >= sb_rows { break; }

    // Wait for dependency: my_row > 0 requires row (my_row - 1) complete.
    if my_row > 0 {
        while progress[my_row - 1].load(Ordering::Acquire) == 0 {
            std::hint::spin_loop();
        }
    }

    // Filter this SB row (all cols, V then H, Y/U/V).
    filter_sb_row(my_row, ...);

    // Signal completion.
    progress[my_row].store(1, Ordering::Release);
}
```

**Pipeline timing diagram (4 workers, 8 SB rows):**

```
Time →  [~200us per SB row]
W0: [====R0====][====R4====][====R8====]...
W1:  stall [====R1====][====R5====][====R9====]...
W2:        stall [====R2====][====R6====]...
W3:              stall [====R3====][====R7====]...
```

After the initial ramp-up (3 stalls of ~200us each = ~600us), all 4 workers run at full utilization. For 17 SB rows with 4 workers: total time = ramp-up + (17 - 4 + 1) rows / 4 workers per row = 600 + 14*200/4 = 600 + 700 = 1,300 us. Compare to serial: 17 * 200 = 3,400 us. Speedup: 2.6x on the LF phase alone.

## 4. Thread Safety — Proving No Write Conflicts

### 4.1 Vertical Filter

The vertical filter at column C, SB row R writes pixels at columns `C-8..C+7`, rows `SB_row_top .. SB_row_top + 15` (for the 16-row dual variant). All these rows are within the 64-pixel-tall SB row. Since each worker exclusively owns an SB row at a time (guaranteed by the atomic work counter), no two workers run vertical passes on the same SB row concurrently. No conflict.

### 4.2 Horizontal Filter

The horizontal filter at pixel row P (an 8-pixel-boundary within SB row R) reads/writes pixels at rows `P-8 .. P+7`. Two cases:

**Case A: Internal edges (not the SB row's topmost edge).** P >= SB_row_top + 8, so P-8 >= SB_row_top. The filter's entire 16-row window is within the current SB row's 64 pixels. No conflict with other workers (each worker exclusively processes one SB row at a time).

**Case B: The SB row's topmost horizontal edge.** P = SB_row_top, so P-8 = SB_row_top - 8. The filter reads/writes 8 rows into the previous SB row. But the previous SB row was fully completed before this worker started (enforced by `progress[my_row - 1].load(Acquire)`), meaning no other worker is writing those pixels. The current worker **does** write into the previous SB row's bottom 8 rows — but no other worker will ever touch those rows again (the previous SB row is done, and no future SB row's filter can reach back more than 8 pixels, which falls within the current row's own territory). Therefore: no conflict.

### 4.3 Formal Argument

Define `owned_write_rows(R)` as the set of pixel rows that the filter for SB row R may write:
- Lower bound: `R*64 - 8` (the top-edge horizontal filter writes 8 rows above).
- Upper bound: `R*64 + 63` (the bottom-most internal edge at row `R*64 + 56` writes up to `R*64 + 56 + 7 = R*64 + 63`).

For adjacent SB rows R and R+1:
- `owned_write_rows(R)` upper = `R*64 + 63`
- `owned_write_rows(R+1)` lower = `(R+1)*64 - 8 = R*64 + 56`

**Overlap zone:** rows `R*64 + 56 .. R*64 + 63` (8 rows).

This overlap is safe because:
1. Worker processing R+1 cannot start until worker processing R is complete (stagger enforcement).
2. Once R is complete, its worker never touches those rows again.
3. Worker processing R+1 is the only writer to those overlap rows from that point forward.

Therefore, temporal exclusion (enforced by the progress protocol) guarantees no concurrent writes to the same pixel.

### 4.4 Rust `unsafe` Justification

The `Yv12Buffer` must be cast to raw pointers shared across threads:

```rust
// On the main thread before spawning workers:
let y_ptr = yv12.y_plane_mut().data_mut().as_mut_ptr();
let y_len = yv12.y_plane_mut().data_mut().len();
// ... same for U, V planes.

// Wrapped in a Send-able struct:
struct SharedFrame {
    y_ptr: *mut u8,
    y_len: usize,
    y_stride: usize,
    // ... u, v ...
}
unsafe impl Send for SharedFrame {}
unsafe impl Sync for SharedFrame {}
```

Each worker reconstructs a `&mut [u8]` slice from the raw pointer for the full plane. The soundness argument relies on the temporal exclusion proof above: although multiple workers hold `*mut u8` to the same allocation, the progress protocol ensures they never concurrently write the same byte.

## 5. Integration

### 5.1 Changes in `crates/rvp9-decoder/src/lib.rs`

The `apply_loop_filter_to_frame` function gains a `scope: &FrameScope` parameter (or alternatively, a `pool: &mut WorkerPool` that it scopes internally). The call sites at lines ~1868 and ~2860 pass the decoder's existing `worker_pool`:

```rust
// Before (serial):
apply_loop_filter_to_frame(&mut yv12, &frame_mi_grid, ...);

// After (parallel):
self.worker_pool.scope(|scope| {
    apply_loop_filter_to_frame_parallel(&mut yv12, &frame_mi_grid, ..., scope, self.num_threads.get());
});
```

Alternatively, `apply_loop_filter_to_frame` can be modified in-place to accept an optional scope reference, falling through to serial when `None` is passed.

### 5.2 Changes in `crates/rvp9-core/src/loopfilter/apply.rs`

1. **New function:** `loop_filter_frame_parallel` (or `loop_filter_rows_parallel`) — the parallel driver that:
   - Allocates the progress vector.
   - Converts `&mut Yv12Buffer` to a `SharedFrame`.
   - Submits N-1 worker jobs + runs band 0 inline.
   - Each worker calls a new inner function `filter_sb_row(sb_row, ...)` which is the body of the existing `for sb_row in sb_start..sb_end` loop (lines 226-373).

2. **Extracted inner function:** `filter_sb_row` — factored out from the existing loop body. Pure refactoring; the serial path calls it in a loop. No behavioral change.

3. **No changes to filter kernels.** The `filter_block_plane_ss00`, `filter_block_plane_ss11`, `filter_block_plane_non420`, and all `filter_selectively_*` functions remain unchanged.

### 5.3 Single-Thread / Single-Tile Path

When `num_threads == 1` or `sb_rows <= 1`, the parallel driver falls through to the existing serial path with zero overhead (no atomics allocated, no scope submission). The serial `loop_filter_frame_with_non420` is preserved as-is for this case and for unit tests.

### 5.4 Impact on `profile-tiles` Instrumentation

The existing `t_lf_start` / `t_lf_end` cycle counters (lines 1867, 1882 in lib.rs) measure the total LF wall time including any parallelism. This remains correct — it captures the scope duration, which includes worker join. For finer-grained per-band instrumentation, optional per-worker cycle counters can be added behind the same `#[cfg(feature = "profile-tiles")]` gate.

## 6. Conformance Guarantee

### 6.1 Bit-Exactness Requirement

The loop filter is the most conformance-sensitive post-decode step. VP9 specifies deterministic output: the same bitstream must produce the same pixels regardless of decoder implementation. Row-parallel LF must produce **byte-identical** output to the serial path.

### 6.2 Why Parallelization Is Conformance-Safe

The loop filter's output for any given SB row depends **only** on:
1. The mask data (`lfm_grid[sb_row * lfm_stride + sb_col]`) — read-only, identical in both paths.
2. The threshold table (`info`) — read-only, identical.
3. The input pixel values in the 16-row window around each edge.

The serial path processes SB rows in order 0, 1, 2, ... N. Each row's horizontal pass reads pixels from the previous row's already-filtered state. The parallel path preserves this ordering guarantee via the progress protocol: SB row R+1's horizontal pass cannot execute until SB row R is fully complete, meaning the same pixels are in the same filtered state when R+1 reads them. Therefore the output is identical.

### 6.3 Validation Strategy

1. **Differential test:** Run the full conformance corpus (201 Profile-0 + Profile-1 vectors) with `num_threads=1` and `num_threads=4`. Compare frame MD5s. Must match exactly.
2. **Randomized SB-row-count fuzz:** Generate frames with odd SB-row counts (1, 2, 3, 5, 7, 13, 17) to exercise edge cases in band distribution.
3. **Single-row-frame test:** Frames with `sb_rows == 1` must still produce correct output (falls through to serial).

### 6.4 Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Off-by-one in band boundary → skipped or double-filtered SB row | Medium | Exhaustive range check: `union(band_ranges) == 0..sb_rows` assertion in debug |
| Horizontal filter at band boundary reads stale (pre-filter) pixels due to insufficient stagger | Low (protocol prevents it) | `debug_assert!` that `progress[r-1]` is set before filtering row `r`; differential test catches any slip |
| Spin-wait wastes cycles when bands are highly unbalanced | Low (SB rows are uniform-cost for LF) | Adaptive: if `sb_rows < 2*num_threads`, reduce band count |
| `unsafe` pointer aliasing UB under Miri | Medium | Run Miri on the parallel LF with a small (128x128) frame; all accesses through raw pointers, not references, to avoid `noalias` violations |
| Performance regression on small frames due to atomic overhead | Low | Gate: `if sb_rows >= MIN_PARALLEL_SB_ROWS { parallel } else { serial }` with MIN = 4 |
| Interaction with future features (segmented LF, HBD 10/12-bit) | Low | The parallel decomposition is orthogonal to filter strength or pixel bit-depth — the row-range split doesn't depend on either |
