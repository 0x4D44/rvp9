# HLD — Encoder hot-path SIMD (speed, byte-identity-preserving)

**Date:** 2026-05-29
**Driver:** Claude (with Arthur)
**Status:** Proposed — DESIGN ONLY, awaiting lead sign-off before any code
**Related:** `wrk_journals/2026.05.27 - JRN - encoder quality+speed measurement (where we stand).md`,
`wrk_docs/2026.05.26 - AUDIT A7 - speed features gap inventory.md`,
`wrk_docs/2026.05.27 - HLD - Encoder decision oracle.md` (format reference)

> **One-line thesis.** The picker's hot primitives (SAD, RD-model variance,
> per-candidate MC convolve) are scalar while the dsp already ships AVX2 kernels
> that the *decoder* uses. Phase 1 routes the picker through SIMD with a
> **byte-identical bitstream** guarantee — pure speed, zero decision movement —
> for a **committable ~3× overall encode speedup** (upside 3.5–4.5×; the diamond
> search is latency-bound, so 3× is the floor we plan against). Phase 2 (the
> partition double-pick) is decision-changing and is split out as a separate,
> quality-validated workstream.

## 1. Problem

rvp9 is **~18–19× slower than vpxenc** at `cpu-used 7` (RT/CBR), steady-state
(rvp9 ~21 fps vs vpxenc ~395 fps on foreman 320×256). A profiling pass
(established, not re-litigated here) found:

- **96 % of inter-frame time is in `pick_inter_mode`**, invoked twice:
  **52.7 %** in the partition-descent RD shape search
  (`nonrd_pick_partition_with_pruners`) and **37.4 %** per final leaf.
- **The motion-search / mode-decision hot primitives are SCALAR**, even though
  the CPU has AVX2 and the dsp already ships AVX2 kernels (used today only by
  decode / final-recon):
  - **SAD: zero SIMD.** Generic scalar `sad()`
    (`crates/rvp9-core/src/dsp/distortion.rs:120`) behind the per-size
    `vpx_sadWxH` shims (`distortion.rs:326-338`). The diamond search calls these
    through `sad_for` (`crates/rvp9-core/src/mv_search/full_pixel.rs:118`) and
    `int_pro_motion_estimation` calls four of them directly
    (`crates/rvp9-core/src/mv_search/int_pro_me.rs:310-313`). **No `sad` slot in
    `SimdDispatch`.**
  - **Variance / SSE: zero SIMD.** The RD model's variance is a *private*
    scalar `compute_variance` (`crates/rvp9-core/src/mode_decision/model_rd.rs:259`)
    and `compute_variance_8x8` (`model_rd.rs:565`); the sub-pel MV search uses
    scalar `vpx_sub_pixel_varianceWxH` (`distortion.rs:362-377`, called via
    `crates/rvp9-core/src/mv_search/sub_pixel.rs:172-183`). **No dispatch slot
    for either.**
  - **Picker MC convolve: scalar, bypasses existing AVX2.**
    `build_inter_prediction` (`crates/rvp9-core/src/mode_decision/inter.rs:2705`,
    one call per evaluated candidate) calls `crate::inter::filter::convolve8*`
    directly (`inter.rs:2789-2831`) — even though the **AVX2 `convolve8_avx2` is
    already wired into the dispatch table** (`dispatch.rs:1817-1843`) and proven
    byte-exact, and the decoder reaches it through `dsp::get().convolve8()`.

The headline: **the dominant cost is in primitives we have already SIMD-ported
for the decoder.** Phase 1 spends no new algorithm design — it ports three
well-understood libvpx AVX2 kernel families and re-points one call site.

## 2. Prior art (this is not greenfield — the pattern is in-tree)

The dsp dispatch infrastructure is mature and the pattern is fully established:

- **`SimdDispatch`** (`dispatch.rs:655`) is a struct of `fn`-pointer slots, one
  per kernel, each documented with its scalar reference and AVX2 wrapper.
  Built once by `SimdDispatch::build(caps)` (`dispatch.rs:1208`); each slot is a
  single `if caps.avx2 { avx2_wrapper } else { scalar_ref }` clause guarded by
  `#[cfg(target_arch = "x86_64")]` with a scalar `#[cfg(not(...))]` arm
  (canonical example: convolve8 at `dispatch.rs:1817-1843`).
- **Caps detection** (`crates/rvp9-core/src/dsp/caps.rs:55`) wraps
  `std::is_x86_feature_detected!`; `detect()` (`caps.rs:115`) is platform-generic.
- **Accessors** return the slot fn (`pub fn convolve8(&self) -> fn(...)`,
  `dispatch.rs:2430`); call sites do `dsp::get_ref().convolve8()(...)`.
  `get_ref()` (`dispatch.rs:2539`) is a single `OnceLock` atomic load — designed
  for hot per-block use (the comment notes ~24k calls/frame at 1080p).
- **The convolve8 AVX2 kernels are conformance-proven byte-exact** with their
  scalar references. `crates/rvp9-core/src/dsp/x86_64/convolve8_avx2.rs:122`
  (`differential_2d`) asserts `dst_scalar == dst_avx2` for all 13 VP9 shapes ×
  all 4 filter kernels × all sub-pel rows 1..16; `dispatch_round_trip`
  (`convolve8_avx2.rs:196`) asserts the forced-AVX2 vs forced-scalar dispatch
  legs agree. **This is the load-bearing evidence for the convolve re-pointing
  (see §9).**

What does **not** exist: any `sad`, `sad4d`, `variance`, or `subpel_variance`
slot in `SimdDispatch`. Those are the new slots Phase 1 adds.

## 3. Goal & non-goals

**Goal (Phase 1).** Make `pick_inter_mode` fast by routing its hot primitives
through AVX2, with a **byte-identical encoded bitstream** before/after on every
input. Realize the SAD/variance/convolve speedups (typically 4–8× at the kernel
level) on the ~90 %-dominant path.

**Committable headline: ~3× overall encode speedup.** The diamond search is
**latency-bound** — short dependency chains of small SADs with the running-best
threshold gating each step — so dispatch indirection plus AVX2 warmup on the
small 8×8/16×16 RT blocks erodes the per-call kernel win. We commit to **~3×**
as the floor and keep **3.5–4.5×** as upside (§4.4). State the 3× as the number
to plan against; treat anything above it as a bonus.

**Non-goals.**
- **No decision change in Phase 1.** Every SIMD kernel is bit-exact with its
  scalar counterpart; the picker sees identical numbers, picks identical modes,
  emits identical bits. (The partition double-pick — a decision-*changing*
  optimization — is Phase 2, §7, NOT part of Phase 1.)
- No new algorithms, no speed-feature heuristics, no quality trade in Phase 1.
- No HBD SIMD (the encoder is 8-bit; HBD slots stay scalar as today).
- No back-compat / migration choreography (dev sandbox).
- Not a `sad4d` for chroma or compound paths beyond what the diamond/full-pel
  search actually calls (don't predict the future — §5.2).

## 4. Phase 1 — SIMD the picker hot primitives (byte-identity-preserving)

Three SIMD sub-tracks (P1-A convolve re-point, P1-B SAD, P1-C variance/subpel),
sequenced as **four PRs** behind the **cross-process** byte-identity oracle (§8.2)
that lands first. PR staging and rationale are in §6; ordered by expected impact /
effort ratio with the lowest-risk move first.

### 4.1 Track P1-A — re-point `build_inter_prediction` at the AVX2 convolve (HIGHEST ROI, LOWEST RISK)

**Change.** In `build_inter_prediction` (`inter.rs:2787-2832`), replace the four
direct `crate::inter::filter::convolve*` calls with the dispatch accessors:

| current (`inter.rs`) | replacement |
|---|---|
| `crate::inter::filter::convolve_copy(...)` | `dsp::get_ref().convolve_copy()(...)` |
| `crate::inter::filter::convolve8_horiz(...)` | `dsp::get_ref().convolve8_horiz()(...)` |
| `crate::inter::filter::convolve8_vert(...)` | `dsp::get_ref().convolve8_vert()(...)` |
| `crate::inter::filter::convolve8(...)` | `dsp::get_ref().convolve8()(...)` |

The slot signatures are identical to the scalar fns (verified: `dispatch.rs:1074-1126`
vs the `inter::filter` fns the picker calls), so this is a mechanical swap.

**Hoist `get_ref()` to the search-call / `evaluate_candidate` level, NOT just
per `build_inter_prediction`.** `build_inter_prediction` is invoked **once per
evaluated candidate** (`inter.rs:2705`, called from
`evaluate_candidate_for_filter` at `inter.rs:2234`, which `evaluate_candidate`
(`inter.rs:2185`) drives per (mode, mv, filter) tuple). Hoisting the
`let dsp = dsp::get_ref();` to `evaluate_candidate` / the search-call frame and
threading `&dsp` (or the resolved fn pointers) down into
`build_inter_prediction` amortizes the `OnceLock` load across all candidates of a
block instead of paying it per candidate. The same hoist applies to the SAD slots
in the diamond search (resolve `sad`/`sad4d` once per `full_pixel` search, not per
step).

**Why this is the highest-ROI move.** The convolve8 AVX2 kernels already exist,
are already in the dispatch table, and are **already conformance-proven
byte-exact** (§2, §9). This sub-track adds **no new kernel** — it deletes a
bypass. It is the cheapest LOC and the lowest risk in the whole HLD.

**Byte-identity.** Guaranteed by the existing `differential_2d` /
`dispatch_round_trip` tests (`convolve8_avx2.rs:122/196`): the AVX2 path produces
the same `dst` bytes as the scalar `convolve8` the picker calls today, for every
shape/filter the picker can request. The prediction bytes are identical → the
residual is identical → the bitstream is identical. (See §9 for the verification
status of this claim.)

### 4.2 Track P1-B — AVX2 SAD (`sad` + `sad4d`/`sadx4`)

**New dispatch slots.** Add to `SimdDispatch` (mirroring the convolve8 slot doc
style):

```rust
/// Per-size SAD. Mirrors scalar `dsp::distortion::vpx_sad{W}x{H}`.
/// AVX2 wrapper on x86_64 caps.avx2; scalar ref otherwise.
pub(crate) sad: SadTable,        // indexed by BlockSize → fn(&[u8],usize,&[u8],usize)->u32
/// 4-candidate SAD: one src block vs four ref offsets, returns [u32;4].
/// Mirrors libvpx `vpx_sad{W}x{H}x4d`. AVX2 on caps.avx2; scalar 4×`sad` otherwise.
pub(crate) sad4d: Sad4dTable,    // indexed by BlockSize → fn(&[u8],usize,[&[u8];4],usize,&mut [u32;4])
```

Encode the per-size tables exactly as `sad_for` (`full_pixel.rs:118`) already
does — a `match BlockSize`. Cleanest is a `SadTable` newtype holding the 13
fn-pointers, populated in `build()` by the same `if caps.avx2` clause pattern.

**Sizes the search actually uses** (don't over-port):
- `sad_for` (`full_pixel.rs:120-132`): **all 13** VP9 sizes (4×4 … 64×64).
- `int_pro_me` (`int_pro_me.rs:310-313`): only **8×8, 16×16, 32×32, 64×64**.
- So the full-pel diamond needs all 13; the `sad4d` variant is needed only for
  the sizes the diamond's `all_in` fast path evaluates (see below). **Port all
  13 single `sad` (used everywhere) and the 13 `sad4d` (the inner loop is
  size-generic).**

**`sad4d` is the real win, not just `sad`.** The diamond search's `all_in` fast
path (`full_pixel.rs:418-447`) evaluates **exactly 4 axis-aligned candidate sites
per step** — one source block against four reference offsets. This is precisely
libvpx's `sdx4df` / `vpx_sad{W}x{H}x4d` contract. Porting `sad4d` lets one AVX2
call amortize the source-block load across all four candidates (libvpx's
`sad4d_avx2.c` loads the src row once, broadcasts, and accumulates four running
sums). The non-`all_in` slow path (`full_pixel.rs:448+`) and the
initial/cross SADs keep using single `sad`.

> **Design note — `sad4d` refactor of the diamond inner loop is the ONE
> control-flow byte-identity hazard. It MUST be gate-2-preserving.**
> Today the `all_in` loop (`full_pixel.rs:418-447`) scans `t = 0..searches_per_step`
> (4 axis sites), guards with an early `thissad < bestsad` (`full_pixel.rs:431`),
> then mutates `bestsad` **mid-loop** with a strict-`<` running-best
> (`if augmented < bestsad { bestsad = augmented; best_site = t }`,
> `full_pixel.rs:442-445`). `best_site` ends as the **last strict improver**, and
> the running threshold means a later site is only adopted if it strictly beats
> the *updated* best — not the original. This is the "gate 2" tie-break.
>
> **MANDATED refactor contract.** `sad4d` fills the **four raw SADs** into a
> `[u32; 4]` array; the loop body then stays **byte-for-byte**:
> ```rust
> for t in 0..searches_per_step {        // still 0..4, in order
>     let thissad = sads[t];             // ONLY change: precomputed, not sad_at(...)
>     if thissad < bestsad {             // same early guard, same threshold
>         let augmented = thissad + mvsad_err_cost(...);
>         if augmented < bestsad {       // same strict-< running-best mutation
>             bestsad = augmented;
>             best_site = t as i32;
>         }
>     }
> }
> ```
> **The byte-identity condition is exactly this:** the loop must keep the
> in-order scan, the mid-loop `bestsad` mutation, and the strict-`<` comparison.
> **Only the SAD *source* changes** (precomputed `sads[t]` instead of
> `sad_at(...)`). A plain `argmin` over the four values is **WRONG**: on tied SADs
> (common at symmetric diamond sites) argmin picks a *different* `best_site` than
> the running-best-with-strict-`<` scan, which **MOVES a decision** and breaks
> the bitstream. Do not "simplify" the loop into an argmin.
>
> Because this is the only non-kernel-level byte-identity claim in Phase 1, land
> `sad4d` as a **SEPARATE PR (PR3) after the always-safe single-SAD PR (PR2)**,
> and gate it on the cross-process byte-identity oracle (§8.2). If the oracle
> ever disagrees, **drop `sad4d` and keep single-`sad`** — still a 4–8× kernel
> win, zero control-flow change.

**Reference ports.** libvpx `vpx_dsp/x86/sad_avx2.c` (single `sad`, 32-/64-wide
`_mm256_sad_epu8` accumulation, `_mm_sad_epu8` for ≤16-wide) and
`vpx_dsp/x86/sad4d_avx2.c` (the 4-ref variant). Both are integer-exact: SAD is
`Σ|a−b|`, associative and overflow-free in the u32 accumulator for all VP9 sizes
(max 64×64×255 = 1 044 480 < 2³²).

**Call-site rewiring.**
- `full_pixel.rs`: `sad_for` returns `dsp::get_ref().sad[bsize]`; the `all_in`
  loop uses `dsp::get_ref().sad4d[bsize]` (gate-2-preserving, per the design
  note above — PR3 only).
- `int_pro_me.rs:310-313`: the four `vpx_sadWxH(...)` calls live inside
  `sad_block` (`int_pro_me.rs:302-316`), whose `match bsize` has a fail-soft
  default arm `_ => u32::MAX` (`int_pro_me.rs:314`) for non-{8,16,32,64} sizes.
  The slot-table swap **must preserve that fail-soft default verbatim**: only the
  four supported arms re-point to `dsp::get_ref().sad[bsize](...)`; the `_ =>
  u32::MAX` arm stays so an unsupported `bsize` returns the sentinel rather than
  panicking or indexing a slot table out of bounds. (Equivalently, if a full
  size-keyed slot table is used here, an unsupported `bsize` must map to a fn
  that returns `u32::MAX`, not OOB.)

**Byte-identity.** SAD is integer-exact by construction; the AVX2 horizontal sum
of byte-absolute-differences equals the scalar `Σ|a−b|` for any input. New
differential tests (§8) pin this per size.

### 4.3 Track P1-C — AVX2 variance / subpel-variance (the RD-model + sub-pel-search primitive)

This track has a **call-site subtlety that the design must respect**: the inter
RD model does **not** use `dsp::distortion::variance`. It uses two *private*
scalar functions in `model_rd.rs`:
- `compute_variance` (`model_rd.rs:259`) — block-level `(var, sse)` for
  `model_rd_for_sb_y` / `_uv` (`model_rd.rs:323/481`).
- `compute_variance_8x8` (`model_rd.rs:565`) — per-8×8-cell `(sum, sse)` grid for
  `model_rd_for_sb_y_large` (`model_rd.rs:698`), the ≥32×32 path.

The sub-pel MV search uses scalar `vpx_sub_pixel_varianceWxH`
(`sub_pixel.rs:172-183` → `distortion.rs`).

So three SIMD targets, three new slots:

```rust
/// Block (var, sse) for the RD model. Mirrors model_rd::compute_variance
/// (== libvpx `variance()` core). AVX2 on caps.avx2; scalar otherwise.
pub(crate) variance: VarTable,           // BlockSize → fn(&[u8],usize,&[u8],usize)->(u32,u32)
/// Per-8x8 (sum, sse) accumulation for the large-block RD model.
/// Mirrors model_rd::compute_variance_8x8 (== libvpx `get_sse_sum_8x8`).
/// Returns the 8x8 grid; AVX2 fills one cell per call with a single
/// `_mm_sad`-free madd reduction. AVX2 on caps.avx2; scalar otherwise.
pub(crate) get_var_sse_8x8: fn(&[u8],usize,&[u8],usize) -> (u32,u32),
/// Sub-pixel variance. Mirrors dsp::distortion::vpx_sub_pixel_variance{W}x{H}.
pub(crate) subpel_variance: SubpelVarTable,  // BlockSize → fn(&[u8],usize,usize,usize,&[u8],usize)->(u32,u32)
```

**The 8×8-cell core is the high-value one.** `compute_variance_8x8` is the per-leaf
hot loop for ≥32×32 blocks (the 37.4 % per-final-leaf cost lives largely here).
Rather than port a per-block `variance` and re-tile, port a **`get_var_sse_8x8`
that returns `(sum, sse)` for one 8×8 cell** (libvpx `get_sse_sum_8x8`: two
`_mm256` rows, `_mm256_sad_epu8` for the |diff| free… actually `_mm256_madd_epi16`
of `(a−b)` for sse and a separate add-reduce for sum). `compute_variance_8x8`
then calls the slot per cell, keeping its existing cell-loop and the `var = |sse −
(sum²>>6)|` finisher in *scalar* (it operates on the reduced scalars, not pixels —
cheap, and keeping it scalar guarantees the finisher arithmetic is unchanged).
`compute_variance` (block-level) similarly delegates the pixel reduction to a
`variance` slot and keeps its scalar `var = sse − (sum*sum)/n` finisher.

> **Byte-identity caveat — there are THREE DISTINCT scalar finishers, and ALL
> THREE stay byte-for-byte untouched. The AVX2 kernels return ONLY the
> integer-exact `(sum, sse)` reductions — never a variance.** An implementer must
> NOT "helpfully" unify these into one formula; they are deliberately different
> expressions and unifying any pair would move a decision.
>
> | # | Finisher | Location | Exact form |
> |---|---|---|---|
> | 1 | `compute_variance` block-level | `model_rd.rs:282` | `var = sum_sq.saturating_sub((sum*sum)/n)` (u64 `saturating_sub`) |
> | 2 | `compute_variance_8x8` per-cell | `model_rd.rs:602-607` | `var = if cell_sse > k { cell_sse - k } else { k - cell_sse }` with `k = (cell_sum²) >> 6` (**abs-diff, NOT saturating_sub**) |
> | 3 | `aggregate_to_tx_size` per-group | `model_rd.rs:655-661` | `var = if sse > k { sse - k } else { k - sse }` with `k = (sum²) >> tx_pixels_log2` (**abs-diff with a variable shift, distinct again**) |
>
> Note finishers #2 and #3 are an **abs-diff** form (`|sse − k|`), which is **NOT**
> the `saturating_sub` of #1 (`saturating_sub` clamps the negative case to 0; the
> abs-diff keeps the magnitude). They are arithmetically different and must each
> survive verbatim. For comparison, `dsp::distortion::variance` uses yet another
> form (an `i64` subtraction + `.max(0)`, `distortion.rs:111`) — do **not** reuse
> it for any of these call sites.
>
> **Mandate.** The AVX2 kernels supply only:
> - a block-level `(sum, sse)` reduction (feeds finisher #1), and
> - a **per-8×8-cell `(sum, sse)` reduction** (the `get_var_sse_8x8` slot), which
>   `compute_variance_8x8` consumes to fill `sse8x8[k]`/`sum8x8[k]`; finisher #2
>   then runs scalar per cell, and `aggregate_to_tx_size` (finisher #3) runs
>   scalar over the grid.
>
> Byte-identity thus reduces to "the `(sum, sse)` reductions are exact"
> (provably true; pinned by §8.1) — the three scalar finishers are out of the
> SIMD blast radius entirely.

**Reference ports.** libvpx `vpx_dsp/x86/variance_avx2.c` —
`variance_avx2`/`vpx_get_sse_sum_8x8_avx2` for the integer reductions, and
`vpx_sub_pixel_variance{W}x{H}_avx2` (bilinear first/second pass in AVX2 +
variance) for the sub-pel path.

**`subpel_variance` has TWO distinct exactness obligations (test both
separately).** It is not a single reduction — it is a bilinear interpolation
*followed by* a variance reduction, and each is its own exactness surface:
1. **The interpolated `u8` temp must be byte-identical.** The AVX2 bilinear
   first/second pass must produce the same rounded `u8` intermediate buffer as
   the scalar `round_power_of_two(·, FILTER_BITS)` path (`distortion.rs:66`, used
   at the bilinear passes). The 8-bit bilinear filter is integer-exact, so this
   is achievable — but the `ROUND_POWER_OF_TWO(·, 7)` intermediate is where a
   port bug (wrong rounding bias, premature truncation, 16- vs 32-bit lane
   width) would silently diverge. §8.1 must assert the **interpolated temp
   bytes** equal the scalar temp, *before* the variance, for every (xoff, yoff).
2. **The variance over the temp must be byte-identical** — same `(sum, sse)`
   reduction obligation as plain `variance`.

If the interpolated temp is byte-identical, the variance over it is identical;
but proving only the final `(var, sse)` hides interpolation bugs that happen to
cancel, so the test plan pins the intermediate explicitly.

**Sizes.** `compute_variance`/`subpel_variance` cover all VP9 sizes the picker
hits; `get_var_sse_8x8` is single-size (8×8) and feeds the grid. Reuse the
existing `sub_pixel.rs` size→fn table shape (`sub_pixel.rs:172-183`) and the
RD-model call sites.

**Call-site rewiring.** `model_rd.rs:259/565` delegate pixel reduction to the new
slots (finisher stays scalar, per the caveat); `sub_pixel.rs:172-183` returns the
`dsp::get_ref().subpel_variance[bsize]` fn.

### 4.4 Expected speedup (honest estimate — commit to ~3×, upside 3.5–4.5×)

SAD / variance / convolve are typically **4–8×** faster in AVX2 *at the kernel
level* (byte-wide SIMD over scalar). The profiler attributes ~90 % of
inter-frame time to these primitives inside the picker. But the **committable**
number is lower than the raw Amdahl arithmetic suggests, for two structural
reasons:

- **The diamond search is latency-bound, not throughput-bound.** Each step is a
  short dependency chain: compute SAD → compare to running best → decide the next
  center. The result of one SAD gates the next, so AVX2's wide-throughput
  advantage is partly wasted — we are waiting on latency, not saturating lanes.
- **Small RT blocks pay dispatch + warmup per call.** The RT path leans on
  8×8/16×16 blocks; the `OnceLock` load (hoisted, but still an indirection) plus
  AVX2 transition/warmup cost is amortized over only a few hundred bytes, eroding
  the per-call win that a 64×64 block would enjoy.

**So the committable headline is ~3×**, derived from a conservative blended ~4×
kernel factor with realistic per-call overhead on small blocks:

```
new_time ≈ 0.10 + 0.90/4 = 0.325   →  ~3.1× overall encode speedup  (COMMIT)
```

At ~3×: **~21 fps → ~63 fps**, ratio vs vpxenc **~19× → ~6.3×**.

**Upside (do NOT commit; treat as a bonus).** If the blended kernel factor lands
at ~5–7× (closer to libvpx's own SAD/variance gains on larger blocks):

```
new_time = 0.10 + 0.90/5 = 0.28    →  ~3.6× overall  →  ~75 fps, ratio ~5.3×
new_time = 0.10 + 0.90/7 = 0.229   →  ~4.4× overall  →  ~92 fps, ratio ~4.3×
```

**Plan-against number for sign-off: ~3× overall encode speedup (foreman ~19× →
~6× vs vpxenc), with 3.5–4.5× as realistic upside, all at zero bitstream
change.** Phase 1 does **not** close the gap to parity — the residual is the
partition double-pick (Phase 2) plus algorithmic speed-features, which are
decision-changing and out of Phase 1's byte-identity scope. State this honestly
to the lead: Phase 1 is the free, safe ~3×; it is not the whole gap.

## 5. Design details that follow the existing pattern exactly

### 5.1 Slot wiring

Each new slot adds **one clause** to `SimdDispatch::build` (`dispatch.rs:1208`),
in the established form:

```rust
#[cfg(target_arch = "x86_64")]
let sad_8x8: fn(&[u8],usize,&[u8],usize)->u32 =
    if caps.avx2 { crate::dsp::x86_64::vpx_sad8x8_avx2 } else { vpx_sad8x8 };
#[cfg(not(target_arch = "x86_64"))]
let sad_8x8 = vpx_sad8x8;   // scalar ref; `let _ = caps;`
```

The per-size tables (`SadTable`, `VarTable`, …) are small newtype structs of 13
fn-pointers built from 13 such clauses, indexed by `BlockSize` via a `match` or a
`[fn; N]` keyed on `bsize as usize`. This mirrors the convolve family's
one-clause-per-slot convention and keeps `build()` auditable.

### 5.2 Don't over-port

- No `sad4d` for sizes `int_pro_me` doesn't use; no compound/avg variance; no
  HBD. The `sad4d` set is driven by what the diamond `all_in` path evaluates.
- `convolve8_avg*` and `convolve8_scaled*` slots already exist and are already
  AVX2 — the picker's `build_inter_prediction` is single-ref (no compound, no
  scaling in the RT path), so P1-A only needs the four non-avg/non-scaled
  accessors.

### 5.3 Safety

AVX2 wrappers follow the in-tree convention: the `pub fn` is a safe wrapper that
the dispatch table only installs when `caps.avx2` is true (the `build()`
visibility note at `dispatch.rs:1199-1206` is the existing guard — `pub(crate)`
construction prevents fabricating an AVX2 table on a non-AVX2 host). The
`#[target_feature(enable = "avx2")]` `unsafe` core sits below the safe wrapper,
exactly as the convolve kernels do.

## 7. Phase 2 (NOTE ONLY — separate, later, quality-validated workstream)

**The partition-descent double-pick (52.7 %) is decision-changing — NOT part of
Phase 1.** The RD descent re-runs full `pick_inter_mode` per candidate shape in
`nonrd_pick_partition_with_pruners`, then again per final leaf. Halving that work
will change which partition/modes are chosen → quality risk → must be BD-rate /
quality-gated, not byte-identity-gated.

Options to spec later (sketch, not committed):
- **Cache/reuse descent leaf picks** — memoize the per-`(bsize, mi_offset)` pick
  during descent and reuse it for the final-leaf pass when the shape is chosen.
  Lowest quality risk (same picks, fewer recomputes) but needs a correctness
  argument that the cached context is still valid at finalize time.
- **Prune the descent at speed ≥ 7** to match libvpx's cheaper non-recursive
  `nonrd` partition (libvpx does *not* run a full recursive RD descent at
  `cpu-used 7`). This is the biggest win and the biggest decision change.
- **Quantify with `RVP9_A4_RD_PARTITION_DISABLE`** — the existing flag already
  toggles the RD partition descent; measure the fps gain and the BD-rate cost it
  produces to bound the Phase-2 opportunity *before* designing it.

Phase 2 gets its own HLD with a quality oracle (BD-rate vs the Phase-1 baseline,
plus the decision-diff tool from `2026.05.27 - HLD - Encoder decision oracle.md`).
**Do not start Phase 2 until Phase 1 has landed and re-baselined the profile** —
SIMD-ing the primitives may shift the 52.7 / 37.4 split.

## 8. Test plan

The strategy is: **prove each kernel bit-exact in isolation, then prove the whole
encoder produces an identical bitstream.** Two layers.

**8.1 Per-kernel SIMD-vs-scalar equivalence (the unit oracle).** For every new
kernel, a differential test in the same module (copying the proven
`convolve8_avx2.rs:122` `differential_2d` pattern):
- **Randomized inputs** (LCG-seeded, as the convolve tests use) over **all 13 VP9
  sizes**, ≥256 iterations each, asserting **exact equality**:
  - `sad`: `assert_eq!(scalar, avx2)`.
  - `sad4d`: `assert_eq!([s0,s1,s2,s3], avx2_out)` and each lane equals the
    single-`sad` of that ref offset.
  - `variance` / `get_var_sse_8x8`: `assert_eq!((sum,sse)_scalar, (..)_avx2)`
    (the per-8×8-cell `(sum,sse)` variant pinned too — it feeds finisher #2).
  - `subpel_variance`: **two-surface** test over all (xoff,yoff) ∈ 0..8 × 0..8 —
    (a) assert the AVX2 bilinear **interpolated `u8` temp** is byte-identical to
    the scalar `round_power_of_two(·, 7)` temp BEFORE the variance, then (b)
    assert the final `(sum, sse)` matches. Surface (a) catches interpolation
    bugs that surface (b) could mask (§4.3).
- **Edge sizes / strides**: non-contiguous strides (src_stride > w, as the
  convolve test does), the 4×N and N×4 shapes, and all-zero / all-255 / max-diff
  inputs (overflow corners of the u32 accumulator).
- **Forced-caps round-trip**: `SimdDispatch::build(caps{avx2:true})` vs
  `{avx2:false}` agree (mirrors `convolve8_avx2.rs:196`). Note this is reachable
  **only** because these tests live **in `rvp9-core`** where `build` is
  `pub(crate)`-visible; it is NOT available to the encoder crate (which is why the
  *system* oracle in §8.2 is cross-process, not in-process forced-caps).

**8.2 Encoder byte-identity (the system oracle — the real proof decisions didn't
move). This is the GATING system-level proof for every byte-identity PR.**

**It MUST be a cross-PROCESS oracle. An in-process forced-caps oracle CANNOT be
built (the obvious design is wrong — corrected here).**
- The encoder reaches the dsp **exclusively** via the process-wide `OnceLock`
  `rvp9_core::dsp::get()/get_ref()` (`dispatch.rs:2501-2543`). That `OnceLock`
  is built **once** from `SimdDispatch::build(detect())` and never re-pointed.
- `SimdDispatch::build(caps)` is **`pub(crate)`** (`dispatch.rs:1208`,
  intentionally — see its visibility note at `dispatch.rs:1199-1206`).
  It is **UNREACHABLE from `rvp9-encoder` or its integration tests.** So an
  in-process "build a forced-scalar table and a forced-AVX2 table, encode with
  each, diff the packets" oracle **cannot be written in ~20 LOC** — it cannot be
  written from the encoder crate at all without changing `build`'s visibility,
  which the dispatch design deliberately forbids (a `pub` `build` would let a
  caller fabricate an AVX2 table on a non-AVX2 host → UB).

**Committed oracle — CROSS-PROCESS, run the encoder binary twice:**
1. **Plumbing (the one small change, lands in PR1).** Honor an env mask in caps
   detection: in `X86Caps::detect()` (`caps.rs:55-63`) set
   `avx2: !force_scalar_env() && std::is_x86_feature_detected!("avx2")`, where
   `force_scalar_env()` reads `RVP9_FORCE_SCALAR=1` (and, defensively, also masks
   `ssse3`/`sse4_1` if we want a pure-scalar leg). Because `init()`/`get()`/
   `get_ref()` all call `SimdDispatch::build(detect())`, masking inside `detect()`
   makes the **entire process-wide table** forced-scalar with **no change to
   `build`'s visibility** — the env reaches caps detection, not the encoder.
   ~10 LOC in `caps.rs`.
2. **Oracle (`simd_byte_identity_gate.rs`, ~120 LOC).** Spawn the encoder binary
   twice on the same input — once with `RVP9_FORCE_SCALAR=1` (scalar leg) and
   once without it (AVX2 leg on an AVX2 host) — then **byte-diff the two IVF
   files**. Byte-identical IVF ⇒ the AVX2 path moved no decision. Run over
   foreman and the `testsrc_720p30` corpus the gates already use.
3. **Gate.** This cross-process IVF byte-diff is the **gating system-level proof
   for every byte-identity PR (PR1–PR4)**. A PR merges only if (a) the
   forced-scalar vs default(AVX2) IVFs are byte-identical AND (b) the existing
   goldens stay green (below).

This is also more robust than an in-process oracle would have been: it exercises
the **real** init path the production encoder uses, with no test-only dispatch
construction that could mask a wiring bug.
- **`cross_decoder_gate` stays green/unchanged** (`crates/rvp9-encoder/tests/cross_decoder_gate.rs`):
  rvp9-encoded bitstream decodes byte-exact through rvp9-decoder vs vpxdec. A
  decision change would alter the bitstream and could perturb this; it must stay
  4/4.
- **`quality_gate` unchanged** (`crates/rvp9-encoder/tests/quality_gate.rs`):
  PSNR/SSIM identical to the pre-change baseline (byte-identical output ⇒
  identical quality — this is a belt-and-braces cross-check, not the primary
  oracle).

**8.3 Success metric — before/after speed.** `realtime_gate`
(`crates/rvp9-encoder/tests/realtime_gate.rs`, `--release --ignored`) median
frame-time, plus a foreman 320×256 fps + ratio-vs-vpxenc measurement (the §1
baseline). **Phase 1 succeeds iff: (a) bitstream byte-identical, (b) foreman fps
improves ≥3×, (c) all gates green.**

## 9. Byte-identity verification status (explicit answer to the lead's question)

**Question: does the byte-identity claim hold for the convolve re-pointing — is
`dsp` AVX2 `convolve8` bit-exact with the scalar `inter::filter::convolve8` the
picker currently uses?**

**Verified by code inspection: YES, with one precise scope note.**
- The dispatch `convolve8` slot's scalar arm **IS** `crate::inter::filter::convolve8`
  (`dispatch.rs:1831/1843`) — the exact same scalar fn `build_inter_prediction`
  calls today (`inter.rs:2821`). So forced-scalar dispatch is a literal no-op
  swap.
- The AVX2 arm (`crate::dsp::x86_64::convolve8_avx2`, installed at
  `dispatch.rs:1829`) is **conformance-proven byte-exact against that same scalar
  fn**: `differential_2d` (`convolve8_avx2.rs:122-193`) asserts
  `dst_scalar == dst_avx2` calling `convolve8` (scalar) vs `convolve8_avx2` over
  all 13 VP9 shapes × {EightTap, Smooth, Sharp, Bilinear} kernels × sub-pel rows
  1..16; `dispatch_round_trip` (`convolve8_avx2.rs:196-228`) asserts the
  forced-AVX2 and forced-scalar dispatch legs agree. The module docstring
  (`convolve8_avx2.rs:13-23`) documents it composes the already-bit-exact
  single-axis AVX2 kernels.
- **Scope note (must hold for the claim to be airtight):** the picker calls four
  kernels — `convolve_copy`, `convolve8_horiz`, `convolve8_vert`, `convolve8`.
  I verified the **2-D `convolve8`** differential test directly. The single-axis
  `convolve8_horiz`/`convolve8_vert` and `convolve_copy` AVX2 kernels are stated
  bit-exact (the 2-D test depends on it, and they have sibling differential tests
  per the Wave-J convention), but I did **not** open each of their test modules
  in this pass. **Recommended pre-merge check (5 min):** confirm
  `convolve8_horiz_avx2.rs`, `convolve8_vert_avx2.rs`, `convolve_copy_avx2.rs`
  each carry a `differential_*` test asserting scalar==AVX2 over the picker's
  shape set. The §8.2 encoder byte-identity oracle is the backstop that catches
  any gap regardless.

**For SAD / variance / subpel-variance:** byte-identity is not "proven yet" — it
is **guaranteed by construction** (integer-exact reductions; finishers kept
scalar per §4.3) and **must be pinned by the new §8.1 differential tests before
merge.** Unlike convolve (port already done and proven), these kernels are new,
so the proof lands with the code.

## 10. Risks & rollback

| # | Risk | Handling |
|---|---|---|
| R1 | A SAD/variance AVX2 kernel is **not** bit-exact (horizontal-sum or madd corner). | §8.1 differential tests assert exact equality over all sizes + overflow corners; a failure blocks merge. Kernels are integer-exact by construction, so a failure means a port bug, fixed in the kernel. |
| R2 | The `full_pixel.rs` `sad4d` `all_in` refactor changes the gate-2 tie-break (mid-loop strict-`<` running-best) and moves a decision on tied SADs (the one control-flow byte-identity hazard, §4.2). | **Primary mitigation is the mandated gate-2-preserving contract** (§4.2): keep the in-order scan + mid-loop `bestsad` mutation + strict-`<`, change ONLY the SAD source; never an argmin. **Backstop:** the §8.2 cross-process IVF oracle catches any movement directly. **Rollback: drop `sad4d`, keep single-`sad`** — still a 4–8× kernel win, zero control-flow change. Structured as PR2 (single-`sad`) then PR3 (`sad4d`), so `sad4d` is a separable revert. |
| R3 | `model_rd` finisher divergence — there are **THREE** distinct scalar finishers (`compute_variance` `saturating_sub`; `compute_variance_8x8` abs-diff `>>6`; `aggregate_to_tx_size` abs-diff `>>tx_pixels_log2`), §4.3. An implementer could "helpfully" unify them. | Mitigated by design: AVX2 returns only `(sum, sse)` reductions (block-level + per-8×8-cell); **all three scalar finishers are untouched** and the HLD forbids unifying them. Byte-identity reduces to "reductions are exact", which §8.1 pins. |
| R4 | Per-call `dsp::get_ref()` overhead erodes the win in the hottest loop. | `get_ref()` is a single `OnceLock` atomic load, explicitly designed for hot per-block use (`dispatch.rs:2530-2542`). Hoist it once per `build_inter_prediction` / per search call. |
| R5 | Phase-1 SIMD shifts the 52.7/37.4 profile split, invalidating Phase-2 assumptions. | Expected and benign — §7 mandates re-baselining the profile after Phase 1 before any Phase-2 design. |
| R6 | Non-x86_64 / non-AVX2 hosts. | The `#[cfg(not(target_arch))]` and `if caps.avx2 { } else { scalar }` arms keep the scalar reference — identical behavior, no speedup, no breakage. Same as every existing slot. |

**Rollback (whole phase).** Each PR is a self-contained slot family + re-point.
Reverting any one PR restores the scalar call site verbatim (the scalar arm IS
the current code). P1-A alone (convolve re-point) is revertible to a 4-line diff.

## 11. Executive summary (for the lead)

- **Phase 1 is free speed: ~3× overall encode speedup committable (foreman ~19×
  → ~6× vs vpxenc), with 3.5–4.5× as realistic upside, at a byte-IDENTICAL
  bitstream.** It SIMDs the picker's scalar hot primitives (SAD, RD-model
  variance, per-candidate MC convolve) that dominate ~90 % of inter-frame time —
  primitives we **already** AVX2-ported for the decoder. The diamond search is
  latency-bound, so we commit to ~3× and bank anything above as bonus.
- **The single best move is nearly free: re-point `build_inter_prediction`
  (`inter.rs:2789-2831`) at `dsp::get_ref().convolve8*` — the AVX2 path already in
  the dispatch table (`dispatch.rs:1817-1843`) and already conformance-proven
  byte-exact.** No new kernel; deletes a bypass; ~15 LOC. **This is PR1**, landed
  together with the oracle.
- **New work is mechanical libvpx ports** (`sad_avx2`, `sad4d_avx2`,
  `variance_avx2`, `subpel_variance_avx2`) wired as new `SimdDispatch` slots
  following the established one-clause-per-slot pattern. **≈2 200–2 600 LOC
  realistic (1 830 is a soft floor)**, four PRs (PR1 oracle+convolve, PR2
  single-SAD, PR3 `sad4d`, PR4 variance/subpel), each gated on byte-identity.
- **Byte-identity is the oracle, two layers:** (8.1) per-kernel scalar-vs-AVX2
  differential tests with exact equality, in-crate where `build` is reachable;
  (8.2) the **gating system-level proof — a CROSS-PROCESS oracle**: run the
  encoder binary twice (`RVP9_FORCE_SCALAR=1` vs default-AVX2) and byte-diff the
  IVFs, with `cross_decoder_gate`/`quality_gate` staying green. SAD/variance are
  integer-exact by construction (all three scalar variance finishers stay
  untouched); the convolve re-point is already proven.
- **Phase 2 (the 52.7 % partition double-pick) is explicitly OUT of Phase 1** —
  it is decision-changing, needs a BD-rate/quality oracle, and gets its own HLD
  *after* Phase 1 re-baselines the profile. Phase 1 buys the safe ~3×; it does
  not close the whole gap.

**Resolved (was the "biggest open question").** *Does an encoder-level
forced-caps (scalar-vs-AVX2) hook exist?* **No — and an in-process one cannot be
built from the encoder.** The encoder reaches the dsp only through the
process-wide `OnceLock` `dsp::get()/get_ref()` (`dispatch.rs:2501-2543`), and
`SimdDispatch::build(caps)` is `pub(crate)` (`dispatch.rs:1208`), unreachable
from `rvp9-encoder`. We therefore **commit to the cross-process oracle**: a
~10-LOC `RVP9_FORCE_SCALAR` env mask in `X86Caps::detect()` (`caps.rs:55-63`)
that flows through `build(detect())` to the whole process-wide table, plus a
run-twice / diff-IVF gate (`simd_byte_identity_gate.rs`, ~120 LOC) that lands in
PR1 and gates PR1–PR4. No change to `build`'s visibility is required or made.
