## The two gate-blocking defects, verified

### `RVP9-BUG-KILN-00020` — confirmed by static read, blast radius narrower than feared

The chain is exactly as the reopen commit describes, and I read every link:

1. `validate_intra_predictor_layout` (`crates\rvp9-core\src\dsp\mod.rs:53`) returns
   `Err("unsupported block size")` for any `bs` outside `{4, 8, 16, 32}`.
2. `v_predictor_avx2` (`crates\rvp9-core\src\dsp\x86_64\v_predictor_avx2.rs:132`) turns that
   `Err` into `panic!` before reaching the kernel.
3. `intra_predict` (`crates\rvp9-core\src\intra_pred.rs:762`) routes `IntraMode::V` straight to
   `dispatch.v_predictor()`, which is that wrapper on AVX2 hosts.
4. `evaluate_intra_fallback` (`crates\rvp9-core\src\mode_decision\inter.rs:2370`) calls it with
   `bw = bh = 64` on `BLOCK_64X64` — the `pred` buffer there is literally `[0u8; 64 * 64]`.

**New finding that makes the refix small:** `validate_intra_predictor_layout` has exactly **one**
production call site in the whole crate — the V_PRED wrapper. H_PRED, D45, D135, D117, D153 and
the rest of the AVX2 intra family do not use it. The regression is confined to one dispatch
slot, so the fix is genuinely narrow: keep the geometry and CPU validation, route
non-`{4,8,16,32}` sizes to the scalar arm the inner kernel already carries, and add a
`BLOCK_64X64` V_PRED intra-in-inter regression.

### `RVP9-BUG-KILN-00062` — a known defect class with a known remedy

`crates\rvp9-harness\tests\tile_threading.rs:380-427` samples the process-global
`rvp9_core::frame::RVP9_G5_2_SCRATCH_ALLOCS` before and after a `decode_frame` call and asserts
the delta is exactly 8. Six sibling tests in the same binary decode concurrently inside that
window. Recorded evidence: default run `left: 12, right: 8` (reproduced twice, deterministic);
`--test-threads=1` passes 7/7; the test alone passes.

This is the same class as `RVP9-BUG-FLUX-00004`, fixed with a serializing mutex. Same remedy
applies, or a per-decoder counter instead of a global.

**Why it stayed hidden:** the test is vector-gated, and no vectorless worktree runs it. It only
became visible because the verification pass fetched vectors — which is itself the strongest
argument in yesterday's journal: *fetching vectors should be routine for a verification pass,
not optional.*
