# HLD — Encoder decision-level differential oracle (rvp9enc vs libvpx) — V1

**Date:** 2026-05-27
**Driver:** Claude (with Arthur)
**Status:** Proposed — revised after Round-1 team review
**Supersedes (conditionally):** `wrk_docs/Track_F/F0.2_HLD_per_block_oracle.md`
**Related:** `wrk_docs/E1_encoder_gap_analysis.md`,
`wrk_journals/2026.05.27 - JRN - encoder quality+speed measurement (where we stand).md`

> **Round-1 review changed this design materially.** The original draft
> (un-suffixed file) proposed decoding both bitstreams through the rvp9 decoder
> and reading per-block decisions, presented as a novel insight. The review
> established that (a) a per-block decision oracle **already exists** (F0.2), and
> (b) the decode-the-bitstream approach was **already evaluated and rejected** by
> F0.2 because of a decoder mi-grid bug. This version reframes the work as a
> conditional successor to F0.2, gated on a cheap spike, and folds in the
> methodology/domain/engineering fixes from the review.

---

## 1. Problem

rvp9enc is 86–95 % BD-rate behind libvpx. Our only attribution signal is
end-to-end PSNR, which integrates over thousands of per-block decisions and is
too noisy to localize a defect. Track-F has run 8 iterations for +0.74 dB
cumulative, per-iter gain now below the measurement floor. We need a tool that
attributes the gap to specific encoder-decision categories so the next fixes are
directed, not guessed.

## 2. Prior art (this is not greenfield)

Two existing artifacts cover most of this ground. The reworked design must build
on them, not reinvent them.

**E1 (`wrk_docs/E1_encoder_gap_analysis.md`, `e1_block_stats.rs`)** decoded
*both* libvpx's and rvp9enc's IVFs through the **same rvp9 decoder** and read
per-frame aggregates from `Decoder::last_frame_mi_grid()`. It found the #1 lever:
**over-partitioning** — rvp9 coded ~85 % of inter area as 8×8 leaves vs libvpx's
~79 % as 64×64, because rvp9 lacked `vp9_choose_partitioning`. Crucially, E1
established two facts we depend on:
- The **partition (`block_size`) field is trustworthy** through the decoder — it
  drives the loop filter, which is byte-exact cross-decode validated.
- The **mode / skip / ref_frame columns are NOT trustworthy** when read from
  `last_frame_mi_grid()` on libvpx streams: the decoder reported 80–100 % intra
  on libvpx inter frames costing <100 bytes — physically impossible. E1 labelled
  this a **decoder mi-grid population bug on the mode column**.

**F0.2 (`wrk_docs/Track_F/F0.2_HLD_per_block_oracle.md`, `f02_oracle.rs`,
`f02_block_oracle.rs`)** built a per-(frame,block) decision diff. Its §3.3
explicitly evaluated three ways to get libvpx's decisions and **rejected option
(a) — "decode libvpx's IVF through the rvp9 decoder and read decisions" — citing
the E1 mi-grid mode bug.** It chose option (b): **patch libvpx** to `fprintf`
its picker decisions, plus an env-gated thread-local sink on the rvp9 side.

**The original draft of this HLD re-proposed option (a) without knowing it had
been rejected.** That is the central finding of the review.

## 3. Why option (a) may still be the right answer

The F0.2 rejection rests on one observation: the *post-hoc* `last_frame_mi_grid()`
read gives wrong modes for libvpx streams. But:

- The decoder **reconstructs libvpx streams byte-exactly** (E1: 0 decode errors;
  cross-decoder gate is 4/4). Byte-exact reconstruction is impossible unless the
  decoder **parsed the modes correctly** — modes drive prediction. The mode
  information is therefore correct *somewhere in the decode path*; only the
  `last_frame_mi_grid()` **exposure/copy** of it is wrong.
- The original draft (and this version) emit at the **live per-block decode
  site**, where the parsed mode lives in a local `ModeInfo`, **before** it is
  copied into the published grid. This *should* sidestep the exposure bug.

This is a **hypothesis, not a fact** (flagged by the devil's-advocate reviewer).
If it holds, option (a) becomes strictly better than F0.2's option (b): no
libvpx patch to maintain, no separate patched-vpxenc build, no version-pin
fragility, and the tool works **symmetrically on any VP9 stream** (the same code
reads both legs, so any decoder parse quirk is common-mode and cancels in the
diff). If it does not hold, we fall back to F0.2's already-designed libvpx patch.

**This hypothesis is the Phase-0 go/no-go gate (§6).** We do not build Phase 1
until it is verified.

## 4. Goal

A tool that attributes rvp9enc's BD-rate gap to encoder-decision categories
(frame-level *and* per-block), ranked by **realized rate-distortion cost**, so
each subsequent fix targets the highest-impact lever and can be measured against
the same tool.

## 5. Non-goals

- **No libvpx patching** *if Phase 0 passes* (the whole point). If Phase 0 fails,
  we adopt F0.2's existing patch — not a new one.
- **No production decoder behaviour change.** The cross-decoder gate is the
  regression check; the recording path is `None` everywhere except this tool.
- **No environment variables, no Cargo feature flags.** Recording is a plain
  function parameter on a decode entry point, exercised only by the new binary.
  (F0.2's env-gated thread-local sink was needed because it instrumented the
  *encoder's realtime path*; a decode-side tool has no realtime budget and needs
  no env gate.)
- **No migration / back-compat.** Dev sandbox.
- **Not a BD-rate harness.** `bdrate` still measures end-to-end; this answers
  *why*.
- **Not a fix for the decoder mi-grid bug.** We sidestep it (or fall back).

## 6. Phase 0 — two cheap checks before building anything (~½ day)

Both are go/no-go. Neither writes the Phase-1 tool.

**6a. Mode-correctness spike (gates the whole decode-based approach).**
Add a temporary debug print at the live per-block decode site (`tile.rs`
`write_block` call sites) that dumps `(mi_row, mi_col, is_inter, ref_frame,
inter_mode, skip)` for **one libvpx inter frame** of `foreman`. Assert the frame
is *mostly inter* (not 80–100 % intra). 
- **Pass** → the exposure-bug hypothesis (§3) holds; proceed to Phase 1 option (a).
- **Fail** → mode is wrong even at the parse site; abandon option (a), adopt
  F0.2's libvpx patch for the libvpx leg. (Phase 1's diff/report design is
  unchanged either way — only the data source for the libvpx leg changes.)

**6b. Re-confirm the dominant lever on TODAY's encoder (cheap, uses trustworthy
fields only).** E1 is from May 23, before drift fixes, RDO dispatch, rect
partitions, ML pruning, and Track-F iters 1–8. Re-run the partition-size + bits
histogram on the **current** encoder using only the *trustworthy* `block_size`
field (no mode data needed). 
- If over-partitioning is **still** dominant, fixing `vp9_choose_partitioning`
  directly may close most of the gap and the full multi-category tool can wait.
- If the picture is now **diffuse** across categories, the full Phase-1 tool is
  justified.

This sequencing directly answers the devil's-advocate objection "is this tool
elaborate avoidance of a cheaper answer?": Phase 0 is the cheaper answer, run
first.

## 7. Phase 1 — the decision oracle (only if Phase 0 says build it)

### 7.1 Frame-level decision record (NEW — was missing)

The dominant levers are frame-level and are chosen *before any block*, so they
are **directly comparable even after references diverge** (no cascade problem).
Diff these **first**.

```rust
struct FrameDecision {
    frame_idx: u32,
    frame_type: FrameKind,          // KEY / INTER / INTRA_ONLY / SHOW_EXISTING
    base_qindex: u8,
    tx_mode: TxMode,
    loopfilter_level: u8,
    loopfilter_sharpness: u8,
    ref_deltas: [i8; 4],
    mode_deltas: [i8; 2],
    seg_enabled: bool,
    seg_abs_delta: bool,
    seg_alt_q: [i16; 8],            // per-segment Q delta
    refresh_flags: u8,              // which ref slots updated
    ref_frame_idx: [u8; 3],         // LAST/GOLDEN/ALTREF → slot map
    ref_sign_bias: [bool; 4],
    comp_ref_mode: CompMode,
}
```

### 7.2 Per-block decision record (revised)

```rust
struct BlockDecision {
    frame_idx: u32,
    mi_row: u16, mi_col: u16,       // top-left 8x8 cell of the leaf
    sb_mi_row: u16, sb_mi_col: u16, // 64x64 anchor (for partition grouping)
    bsize: BlockSize,               // leaf size = the partition outcome
    eff_qindex: u16,                // get_qindex(seg_alt_q[id], abs_delta, base_q)
    skip: bool,
    tx_size: TxSize,
    bits: u32,                      // entropy-coded size attributable to this block
    sse: u64,                       // SSE(reconstruction, source) over Y for this leaf
    kind: BlockKind,
}

enum BlockKind {
    Intra { y_mode: PredMode, uv_mode: PredMode },
    Inter {
        inter_mode: InterMode,      // NEAREST/NEAR/ZERO/NEW  (NEW — was missing)
        ref_frame: [Option<RefFrame>; 2],  // 2nd = Some only if compound
        mv: [Mv; 2],                // 1/8-pel raw; sub-8x8 caveat below
        interp_filter: InterpFilter,
    },
}
```

Changes from the draft, all from Round-1:
- **Dropped `tx_type` entirely.** It is not an independent decision: intra
  tx_type is a pure lookup from `y_mode` (`reconstruct.rs:resolve_tx_type`),
  inter is always `DCT_DCT`. A `tx_type` divergence can never fire independently
  of a `y_mode` divergence — recording it as a category is phantom signal.
- **Dropped `partition_path` / `ArrayVec`.** The partition outcome is fully
  captured by the multiset of `(local_offset, bsize)` of a superblock's leaves;
  no descent path and no new dependency needed.
- **Added `inter_mode`** — distinguishes a mode-selection bug from a
  search-precision bug (ZEROMV vs NEWMV(0,0) have identical MV but different
  rate).
- **Added `eff_qindex`** instead of comparing raw `segment_id` (meaningless
  across mismatched AQ maps).
- **Added `bits` and `sse`** — required for the RD-cost metric (§7.5).
- **Sub-8×8 caveat:** blocks below 8×8 carry four per-4×4 sub-MVs/modes; a single
  `mv[2]` collapses them. Phase 1 flags sub-8×8 leaves as "MV not fully captured"
  rather than expanding the schema (YAGNI; revisit if a lever needs it).

### 7.3 Decoder integration (corrected to match the real code)

The draft's API was factually wrong. Reality (verified against the decoder):
- Entry is `decode_frame(&mut self, frame: &ParsedFrame<'_>) -> Result<FrameBuf,
  DecodeError>`, dispatching to `decode_keyframe` / `decode_intra_only_frame` /
  `decode_inter_frame`, each with a **parallel (tile-threaded) and a serial**
  sub-path.
- Tiles are decoded on a worker pool with per-tile `Mutex` state. A single
  `&mut dyn Sink` is `!Send` and cannot cross the tile jobs — the draft's
  forwarder is **impossible** as written.
- There is no single emission site: leaves are written at three `write_block`
  call sites (`tile.rs` keyframe-intra, inter, intra-in-inter).

Corrected design:
- Each **tile job owns a `Vec<BlockDecision>`** in its existing per-tile state
  slot (same lifetime as `counts`/`seg_ids`). No locks.
- After the tile `scope` joins, the per-tile Vecs are **concatenated and sorted
  by `(frame_idx, mi_row, mi_col)`** — order is reconstructed from the data, not
  the thread schedule.
- The three `write_block` sites push one record (built from the `ModeInfo` and
  bit-position locals already present). `bits` = entropy-decoder position delta
  across the block's symbols; `sse` is filled after reconstruction.
- A new `decode_frame_traced(&mut self, frame, out: &mut Vec<BlockDecision>,
  fout: &mut Vec<FrameDecision>)` entry; the existing `decode_frame` is
  unchanged (no `Option`, no trait — the traced path is a separate entry used
  only by the binary). **No `DecisionSink` trait, no blanket `FnMut` impl** —
  over-engineered for one in-crate caller.

This keeps the production `decode_frame` byte-for-byte identical; the
cross-decoder gate remains the regression guard.

### 7.4 `decision-diff` binary

`crates/rvp9-harness/src/bin/decision_diff.rs` (harness crate — that is where
E1/F0.2 diagnostics live; do not scatter into bench):

```
decision-diff <a.ivf> <b.ivf> <source.y4m> [--out report.json]
```

Algorithm:
1. Decode A and B (traced), with `source.y4m` to compute per-block `sse`.
2. **Assert per-frame `frame_type` alignment** (not just frame count). On
   mismatch, report and stop — the streams are not comparable past that point.
3. Diff `FrameDecision` per frame (§7.1).
4. For each superblock present in both: compare the leaf multiset
   `(local_offset, bsize)`. If different → record a partition divergence and
   record how many leaves are thereby excluded (honest denominator). If same →
   diff each leaf's fields.
5. Emit the RD-cost-weighted report (§7.5), stratified by cascade distance (§7.6).

### 7.5 Metric — RD cost, not divergence count (core methodology fix)

Ranking categories by *count of differing blocks* is misleading: `tx_size` is
per-transform-block and high-cardinality, so it dominates any count while costing
little per instance; one wrong `ref_frame` can cost more than 300 marginal
`tx_size` picks. Instead:

- **Per block, we have realized `(bits, sse)` for both legs.** Define a
  **Pareto-dominance flag**: rvp9's block is *strictly worse* iff
  `bits_rvp9 ≥ bits_libvpx` **and** `sse_rvp9 ≥ sse_libvpx` (with at least one
  strict). This is assumption-free — it needs no λ and does not assume libvpx is
  optimal. It directly answers "is rvp9's choice here actually worse?", which is
  the only actionable signal (a mere *difference* from a non-optimal libvpx is
  not a defect).
- For ranking, combine via the frame's own λ (derived from `base_qindex`, which
  we know): `ΔJ = Δsse + λ·Δbits`. Aggregate `ΣΔJ` over the blocks where each
  category diverged. Categories overlap (a block can diverge in mode *and*
  tx_size); sums are not mutually exclusive — reported honestly. The category
  carrying the most `ΣΔJ` among Pareto-dominated blocks is the lever.
- Report **both** count and `ΣΔJ` per category; when they disagree, trust `ΣΔJ`.
  (The draft's instinct to weight ΔMV by magnitude was the right idea applied to
  one field; this generalizes it to all categories.)

### 7.6 Cascade handling — stratify, don't assert

Once an inter decision diverges, references diverge and downstream picks differ
for reasons unrelated to any single bug. The draft *asserted* categorical ratios
survive this. Instead we **validate it empirically** by reporting the category
histogram restricted to:
- (a) keyframe only — zero cascade (no references),
- (b) first inter frame only — references the same KF,
- (c) frames at cascade-distance 1 from a shared reference,
- (d) all frames.

If the category **ranking** is stable across (a)–(d), the all-frames ranking is
trustworthy; if it reorders, the all-frames numbers are cascade-contaminated and
we act only on (a)/(b). Inter-frame analysis is **gated on KF divergence being
near-zero first** (a diverged KF poisons every inter frame).

## 8. Test plan

1. **Self-consistency (decoder determinism):** `decision-diff a.ivf a.ivf src`
   reports zero divergences. Necessary but **not sufficient** — it passes even if
   the diff logic always returns zero.
2. **Injected-divergence positive control (proves the diff actually detects):**
   construct two streams differing in exactly one known block decision (or
   programmatically flip one field in one record), and assert the report names
   **exactly that category, at that `(frame, mi_row, mi_col)`, once**. This is
   the test that validates the attribution machinery.
3. **Structural invariant:** on any real run, KF divergence in inter-only
   categories (`ref_frame`/`mv`/`inter_mode`/`interp_filter`) is **exactly zero**
   (a keyframe has no inter blocks). A non-zero count here is a tool bug.
4. **Decoder regression:** `cross_decoder_gate` stays 4/4 after the decoder
   change (traced path is a separate entry; `decode_frame` untouched).
5. No "looks plausible" acceptance criteria — every check above is falsifiable.

## 10. Risks

| # | Risk | Handling |
|---|---|---|
| R1 | **Mi-grid bug is in the parse, not the exposure** — option (a) dead. | Phase-0 6a gates this. Fallback: F0.2 libvpx patch. Cost of being wrong: ½ day. |
| R2 | **Gap is cost-model-driven** (rate/distortion estimation) → divergence lights up *every* category roughly uniformly and points nowhere. The journal's own residual diagnosis (intra/lambda, inter mode-decision quality) makes this the *expected* mode, not a tail risk. | The RD-cost metric (§7.5) partially mitigates: even uniform *count* divergence will not be uniform in `ΣΔJ`. But if `ΣΔJ` is also flat, that is itself the finding — "the gap is in the cost model, not in any one decision category" — and points at the rate/distortion estimators as the next investigation. Define this NULL result up front so it is actionable, not confusing. |
| R3 | **Decode recovers the OUTCOME, not the picker's internal decision** (MV is post-clamp; skip may be forced; tx may be downgraded). | Accepted and documented. For a *bitstream*-quality gap, the signalled outcome is exactly what costs bits and determines distortion — it is the right thing to compare. The picker's pre-clamp intention is secondary and out of scope. Both legs are compared symmetrically as outcomes, so the comparison is fair. |
| R4 | **Config mismatch** — `--rt --lag-in-frames=0` makes vpxenc flat-GOP/no-ARF; if rvp9enc's GOP/ARF/TPL machinery activates, frame types misalign. | §7.4 step 2 asserts per-frame `frame_type` alignment and stops on mismatch. Test config pins both encoders to the same RT/no-lag profile and `--tile-columns` to keep tiling comparable. |
| R5 | **Partition-mismatch short-circuit biases the leaf sample** toward agreement (most-divergent SBs contribute no leaf detail on inter frames). | Report excluded-leaf count per frame so the denominator is honest (§7.4 step 4). |

## 11. Relationship to F0.2 (explicit)

- If **Phase 0 passes**: this tool **retires** F0.2's libvpx-patch path and the
  `build_f02_libvpx.ps1` / patch-maintenance machinery. The encoder-side
  `f02_oracle.rs` thread-local sink may still be useful for reading the picker's
  *internal pre-clamp* decisions (the one thing decode cannot recover, R3) — keep
  it, but it is no longer the primary oracle.
- If **Phase 0 fails**: this design's diff/report/metric (§7.4–7.6) is still the
  upgrade over F0.2 (frame-level records, RD-cost metric, stratification,
  positive-control test); only the libvpx-leg data source reverts to F0.2's
  patch. Net: F0.2's diff code is replaced by this; its libvpx patch is reused.

Either way the duplication is resolved: we end with **one** oracle, not two.
