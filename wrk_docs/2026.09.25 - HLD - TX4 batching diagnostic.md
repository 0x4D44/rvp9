# TX4 batching: evidence required before a kernel build

The exact Unit 1416 x86 profile charges 1,525 of 40,989 direct encoder rows
(about 3.72%) to the emission-side `choose_inter_luma_tx_size` call at
`crates/rvp9-encoder/src/lib.rs:11471`. This is a sampled callsite ceiling,
not the cost of TX4 or a promised saving. The selector walks TX16, TX8, and,
on eligible CPU6 single-layer leaves, TX4. The existing per-tile lower-bound
prune preserves the strict argmin.

The cross-family design consult proposed batching four TX4 tiles in an 8×8
region to amortize transform, quantizer, and block-error overhead. It must
still price each tile's coefficients in raster order, propagate its nonzero
context, and shift each tile's block error before summing. Candidate rate and
distortion are nonnegative, so checking the prune bound after a group rather
than after each tile cannot change the winning TX size; it can only perform
extra work. The final emitter and other TX candidates would stay unchanged.

That is an unverified hypothesis, not a build instruction. An older CPU6/T3
screen found a large TX4-off speed ceiling, but the current policy disables
TX4 for T3 (`realtime_tx4_candidate_enabled`), so that number does not
quantify today's CPU6 single-layer workload. Copied and zero-copy selected-TX
coefficient caches (Units 585–586) were byte-exact but timing-neutral; an
exact-zero selector shortcut (Unit 1413) also lost. No cache is proposed.

The diagnostic gates were:

1. Use the retained exact executable/PDB to split `lib.rs:11471` sampled IPs
   by inline frame, if DbgHelp exposes enough frames. Determine how much
   belongs to TX4 DCT, quantization, block error, coefficient costing, and
   bookkeeping. If the PDB has no inline contexts, do not treat that as
   evidence that any component is absent.
2. On the current three-clip CPU6 single-layer protocol, count eligible
   TX16-class leaves, the incumbent after TX8, TX4 tiles evaluated before
   pruning, and TX4 wins. Time each candidate only in a temporary diagnostic
   build, verifying its IVF hash against the uninstrumented control. Estimate
   the avoidable call overhead from those counts; require a plausible
   roughly 2.5% whole-encode ceiling before building the prototype.

Unit 1418 found that all 1,525 callsite rows have inline depth zero, so the
PDB cannot split the work. Existing runtime timers put the whole selector at
16.5% of instrumented inter-frame time on Ducks and about 4% on Tree/Town.
The TX4-off override reduced selector timer sums by 36–44%, but changed all
three IVF hashes, so it was only a directional ceiling.

Unit 1419 added temporary exact-output counters and restored the source.
All three diagnostic IVF hashes matched the integrated baseline. TX4 was
attempted 439,604 / 43,817 / 41,550 times on Ducks / Tree / Town and averaged
9.75 / 12.58 / 13.22 evaluated tiles per attempt. It was pruned on
438,299 / 43,550 / 40,595 attempts. Its measured candidate time was
141.15 / 17.98 / 17.88 ms, or 34.7% / 38.4% / 40.5% of instrumented selector
time. These are timer sums from a diagnostic build, not whole-encode speed
measurements. The batchable fraction within TX4 is still unknown; this data
supports a bounded prototype, not a predicted gain.

Discuss the invariant-bearing batch-kernel change with Arthur before
implementation. The acceptance oracle must compare batched and
existing exhaustive selection across leaf shapes, qindex edges, both fast and
zbin quantizers, scan/EOB patterns, and signaling costs. Deliberately corrupt
one tile's DC parameters or EOB and observe red before restoring. Then require
byte-identical three-clip output, focused AArch64/x86 tests, and two stable
paired Crucible screens; retain only a reproducible gain. Stop on any output
difference or a neutral screen.

Arthur approved the bounded prototype on 2026-09-25. The 2×2 scalar staging
candidate passed the tile and selector differential after a deliberate red
mutation, and all three Crucible clips were byte-identical. Its first full
15-pair/clip screen cost **1.028993×** current process CPU overall (Ducks
1.067092×, Tree 1.028787×, Town 0.992453×). It was therefore stopped before
screen B and not integrated. The code remains only on unpushed task branch
`task/20260925-TSK-HUM-prototype-exact-tx4-batching-in-inter-lu` at `44a406ce`;
the exact screen and validation are in
`wrk_docs/evidence/2026-09-25-tx4-batch-screen-a/README.md`. The result rejects
grouped scalar staging, not a future genuinely batched SIMD kernel.
