# HLD — MC-path audit + `extend_frame_borders` removal (Survey #2 redo)

**Date:** 2026-05-27
**Author:** design agent (10th autonomous investigation)
**Prior:** `wrk_journals/2026.05.26 - JRN - Survey 2 extend_frame_borders failed.md` (failed conformance 201/201 → 14/201).
**Track record:** 2 merged / 4 PGO-disproven / 3 shelved.
**Verdict:** **TRACTABLE** — but with a hard caveat on Phase 1 reclaim. See §7.

---

## 1. Context & ceiling

`extend_frame_borders` runs once at frame end on the main thread, costing
~108 µs/frame on `testsrc_1080p30 t=4` = **6.9 % of the post-LF-overlap 1571 µs
wall** (absolute ceiling). libvpx does not call this in the decoder path; its
decoder routes MC through the strict `extend_and_predict` fallback that
copies-and-replicates on the fly for any MV whose footprint touches even one
pixel outside the visible (cropped) plane.

Lever 9 (Phase 1a/1b border parallelization) was shelved at ~1.1 % EV. Removal
is structurally bigger (6.9 % ceiling) but conformance gated.

## 2. The Survey #2 failure — re-diagnosis

Survey #2 removed the two `extend_frame_borders` call sites
(`lib.rs:2234` keyframe path, `lib.rs:3587` inter path — locations verified
this session, drifted from the journal's `:2059 / :3196` by ~170 lines after
intervening commits) and observed 187/201 mismatched frames.

The journal listed candidate culprits but did not localise. **This audit
identifies a single structural bypass point**, not a pervasive set.

## 3. The audit — every MC pixel read in the production decoder

Production inter-MC reads are routed through **exactly one entry point** in
`crates/rvp9-decoder/src/reconstruct_inter.rs`:

| call site | line | description |
|---|---|---|
| `build_inter_predictor_with_mc_border` | reconstruct_inter.rs:463 | the **only** production MC-read entry; called from `reconstruct_inter_block` |

All other `ref_buf.y_plane()` / `ref_u` / `ref_plane.data[…]` accesses inside
the file (lines 1435, 1451, 1534, 1823, 1896, 1905, 2158, 2248, 2288, 2932) live
inside `#[cfg(test)]` (the test helpers explicitly call `buf.extend_borders()`
on their fixtures and remain bit-exact regardless of decoder behaviour).

There is no second MC read path. There is no separate sub-pel filter,
sub-block (4×4) loop, chroma boundary, or compound-avg path that bypasses
`build_inter_predictor_with_mc_border`.

## 4. The bypass — one predicate

`build_inter_predictor_with_mc_border` has two sub-paths chosen by
`needs_scratch` (`reconstruct_inter.rs:1116-1119`):

```rust
let bordered_x_lo = -(ref_plane.border_w as i32);     // = -32 (Y)
let bordered_y_lo = -(ref_plane.border_h as i32);
let bordered_x_hi = (ref_plane.width + ref_plane.border_w) as i32; // = aligned_w + 32
let bordered_y_hi = (ref_plane.height + ref_plane.border_h) as i32;

let needs_scratch = x0 < bordered_x_lo
    || y0 < bordered_y_lo
    || x1 > bordered_x_hi
    || y1 > bordered_y_hi;
```

**Fast path** (`!needs_scratch`): reads `ref_plane.data[src_base..]`
directly — pixels live in the **bordered region**, populated by
`extend_frame_borders`.

**Slow path** (`needs_scratch`): copies a `b_w × b_h` rectangle into a 25 KB
stack scratch via `build_mc_border` (which itself replicates from
`src_visible`, the visible top-left).

### Cross-check against libvpx — exact divergence

`vp9_decodeframe.c:660-697` (`dec_build_inter_predictors`):

```c
// Skip border extension if block is inside the frame.
if (x0 < 0 || x0 > frame_width - 1 || x1 < 0 || x1 > frame_width - 1 ||
    y0 < 0 || y0 > frame_height - 1 || y1 < 0 || y1 > frame_height - 1) {
  // Extend the border.
  ...
  extend_and_predict(...);
  return;
}
// otherwise direct inter_predictor on ref_frame buffer.
```

libvpx's predicate compares against `frame_width` / `frame_height` (the
**visible / cropped** dims). Anything outside the visible plane goes through
the scratch path. The encoder's `vp9_reconinter.c:build_inter_predictors`
(not used by the decoder) has no such check — it reads bordered pixels
directly because the encoder always pre-extends the reference.

**Concrete divergence:** for a typical 8×8 Y block at the right frame edge
with `subpel_x ≠ 0`, MV = 0:

| | libvpx (`dec_build_inter_predictors`) | rvp9 today (extend_frame_borders ON) | rvp9 if extend removed |
|---|---|---|---|
| `x0` | crop_w − 8 − 3 = crop_w − 11 | same | same |
| `x1` | crop_w − 8 + 1 + 4 = crop_w − 3 | same | same |
| `x1 > frame_width − 1`? | `crop_w − 3 > crop_w − 1` → **false** | falls inside `[−32, crop_w+32]` | same |
| direct path? | yes | yes | yes |
| reads | visible bytes only (footprint inside crop) | visible bytes (same footprint) | visible bytes (same footprint) |

That case is fine. The interesting case: 64×64 SB at the right edge with
`mv_x = +8` (1 px past edge mid-block), `subpel_x = 4`:

| | libvpx | rvp9 today | rvp9 if extend removed |
|---|---|---|---|
| `x1` | crop_w + 8 + 1 + 4 = crop_w + 13 | same | same |
| `x1 > frame_width − 1`? | **true** → scratch | within `[−32, crop_w + 32]` → **fast** | fast — reads stale border |
| reads | replicated edge from `build_mc_border` | replicated edge from `extend_frame_borders` | **uninitialised / stale** |

Without `extend_frame_borders`, the fast path reads uninitialised/stale
backing memory. Hence 187/201 mismatch.

## 5. Proposed fix — tighten the predicate (single-point)

Change `needs_scratch` to match libvpx's strict decoder predicate:

```rust
// Match libvpx dec_build_inter_predictors (vp9_decodeframe.c:681-682).
// The scratch path fires whenever the footprint touches even one
// pixel outside the visible (cropped) plane. The on-demand
// build_mc_border below replicates the edge into the scratch — we no
// longer rely on extend_frame_borders pre-populating the border.
let frame_w = crop.crop_w as i32;
let frame_h = crop.crop_h as i32;
let needs_scratch = x0 < 0 || x0 > frame_w - 1 || x1 < 0 || x1 > frame_w - 1
                 || y0 < 0 || y0 > frame_h - 1 || y1 < 0 || y1 > frame_h - 1;
```

That is a **~4-line predicate change**. No new call sites, no MC kernel
edits, no chroma-specific carve-out (chroma rides the same function with
its own `RefPlaneCrop`). The existing `build_mc_border` already replicates
from `src_visible` (line 1200-1213) and is well-tested (multiple unit tests
in §tests).

With this predicate change in place, removing both `extend_frame_borders`
calls (`lib.rs:2234`, `lib.rs:3587`) becomes safe — no production read path
remains that depends on pre-extended border bytes.

## 6. Conformance + correctness gate

The bit-exactness gate is sacred (201/201 + Miri + differential MD5).

### Phase 1 — strict-predicate flip only (no extend removal)

1. Apply the predicate change.
2. Run 201/201 conformance.
   - Expected: **still 201/201** — predicate is *more* conservative
     (scratch path fires *earlier*), so any vector that previously passed
     via the fast path still produces identical output via scratch
     (`build_mc_border` is the explicit edge-replication libvpx uses;
     the fast path reads the same edge-replicated bytes that
     `extend_frame_borders` placed there). The two are byte-identical by
     construction.
3. **If 201/201:** the predicate change is bit-exact independent of border
   pre-population. Proceed to Phase 2.
4. **If not 201/201:** the audit missed something. Stop, diagnose the
   specific mismatched frame (the same per-frame diff harness used in
   Survey #2). The candidate would be: a path that pre-extends-then-reads
   non-edge bytes (e.g. a sub-pel filter tail that needs sample
   `crop_w + 1` to *equal* `crop_w − 1` not `crop_w` — but `build_mc_border`
   and `extend_borders` both replicate from `ref_row[w−1]`, so this
   identity holds).

### Phase 2 — remove `extend_frame_borders`

5. Remove the two `extend_frame_borders(&mut yv12)` calls
   (`lib.rs:2234`, `lib.rs:3587`) + the `use` import (`lib.rs:79`).
6. Run 201/201 conformance.
   - Expected: **201/201** — every MC read now goes through `build_mc_border`
     for any footprint touching outside the visible plane; the bordered
     region's contents are irrelevant.
7. **If not 201/201:** another caller of `Yv12Buffer` reads border bytes
   we missed. Audit candidates (probably empty, but verify):
   - `apply_loop_filter_to_frame_dispatching` — LF processes the
     visible region only; never reads border. Documented at frame.rs:24.
   - Tile-merge / `merge_tile_columns_from` — copies visible region only.
   - Anything in `rvp9-encoder` consuming the decoder's frame — already
     ruled out by Survey #2's grep audit (encoder doesn't consume the
     decoder's `extend_borders` output).

### Per-vector diff

## 7. Tractability assessment

**TRACTABLE.** Reasons:

1. **One bypass point, one structural fix.** The MC-path audit
   identified a single production entry; the bypass is a single predicate;
   the fix is libvpx-aligned by construction (we're literally porting the
   strict decoder predicate from `vp9_decodeframe.c:681-682`).
2. **The on-demand replication (`build_mc_border`) already exists and is
   tested.** Lines 971-1035 implement libvpx's `build_mc_border` 1:1
   (verified line-by-line); 25 KB scratch is sized to match
   `extend_and_predict_buf` (160² to libvpx's 160²).
3. **Phase 1 (predicate-tighten) is bit-exact by construction** — the
   scratch path reads the same edge-replicated bytes that
   `extend_frame_borders` populates, just on demand instead of upfront.
   Both code paths call the same `inter_predictor_with_dispatch` kernel
   with the same kernel inputs.
4. **Code change estimate: ~10 LOC** (predicate change + 2 call-site
   removals + 1 `use` removal). Far below Survey #2's "80-200 LOC audit
   refactor" estimate, which assumed pervasive bypass.

### Honesty about reclaim — the Phase 1 reclaim catch

**Phase 1 alone (predicate flip) saves nothing** — it makes more MC blocks
take the slower scratch path. That's *increased* per-frame work, not less.
The reclaim comes from **Phase 2** (removing `extend_frame_borders`,
which buys back the 108 µs).

But the Phase 2 saving is **partially eaten** by Phase 1's added scratch
calls. How much? Some honest arithmetic:

- `extend_frame_borders` saved: **108 µs/frame** (measured).
- Additional scratch-path calls per frame: the marginal MC blocks whose
  footprint enters `[crop, crop + border]` but stays inside
  `[−border, crop + border]` — i.e. edge blocks. On a 1080p frame, the
  edge ring is ~`2 × (1920 + 1080 − 64) / 64 ≈ 92` SBs out of
  `34 × 17 = 578` SBs (`mi_cols / 8 × mi_rows / 8` for 8-mi SB) =
  ~16 % of SBs. Within those, only the blocks with MVs pointing past
  the edge actually flip from fast→slow. For testsrc_1080p30 t=4 the
  inter MV distribution is centred near zero with small magnitude
  (testsrc is synthetic); the fraction that points past the edge is
  small, maybe ~1-3 % of inter blocks.
- Each extra scratch call adds ~1-2 µs (160×160 = 25 KB memcpy +
  `build_mc_border` replication + the convolve, which already happens
  either way — only the memcpy/replicate is added). Net added cost:
  estimate **~5-20 µs/frame**.
- **Net Phase 2 reclaim: 108 − ~10 µs ≈ 90-100 µs/frame**, deflate by
  the session's 2× median deflation factor → **~45-50 µs/frame after PGO
  end-to-end**, i.e. **~2.9-3.2 % on the 1571 µs post-LF-overlap wall**.

This is **below the 5 % PGO ship gate set by the LF-thread-pool win**.

### EV table

| outcome | probability | reclaim |
|---|---|---|
| Phase 1+2 lands bit-exact, PGO ≥5 % | ~15 % | +5-7 % shipped |
| Phase 1+2 lands bit-exact, PGO 2-5 % | ~55 % | +2-5 % — strictly below ship gate; **discarded** |
| Phase 1 breaks conformance (audit miss) | ~10 % | 0 (early stop) |
| Phase 2 breaks conformance after Phase 1 | ~15 % | 0 (revert) |
| Phase 1+2 PGO ≤2 % / noise | ~5 % | 0 (discard) |

**EV ≈ 0.15 × 6 + 0.55 × 0 + 0.30 × 0 ≈ 0.9 % unconditional.**

That's the same EV class as Phase 1a/1b (the just-shelved border-extend
parallelization, ~1.1 % EV).

### Confidence

**High** on the audit ("the bypass is a single predicate"). **Medium-high**
on Phase 1 bit-exactness ("the scratch path is libvpx-identical and the
unit tests cover edge replication"). **Low-medium** on PGO ship-clearing
("the added scratch calls eat enough of the saving to land below 5 %").

## 8. Recommendation — **SHELVE, with the audit preserved**

Even though the lever is **mechanically tractable** (the audit identified
the single structural bypass; the fix is bounded and libvpx-aligned), the
**arithmetic is unfavourable**:

- Best modelled reclaim (after PGO deflation): ~3 %.
- Below the 5 % ship gate that's been binding on every other lever this
  session (LF overlap, border parallelization, row-MT, intra-envelope,
  etc.).
- EV ~0.9 % is in the same class as the just-shelved Lever 9.
- Track record: 4 PGO-disproven of 9. The "smaller than the model said"
  pattern would push the 3 % down to ~1.5 % with high probability.

**SHELVE** with this audit preserved as the design record. If Arthur
ever:
- Retargets to inter-heavy content where edge-MV blocks are rarer
  (smaller Phase 1 penalty, larger Phase 2 saving), OR
- Adds the lever to a multi-lever bundle where the 3 % becomes part of a
  ≥5 % aggregate, OR
- Lifts the ship gate (e.g. accepts mean-only or microbench gains for
  code-clarity reasons — the predicate change is also a libvpx-
  faithfulness improvement),

then the audit + fix recipe are sitting here ready to implement in <30
minutes of coding + 2-3 hours of A/B.
