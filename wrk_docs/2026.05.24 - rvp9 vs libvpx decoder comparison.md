# rvp9 vs libvpx Decoder Comparison Report

**Date**: 2026-05-24  
**Method**: 4-agent parallel investigation (decode pipeline, loop filter, architecture, devil's advocate)  
**Purpose**: Identify the true root causes of the ~10x performance gap between rvp9 and vpxdec

---

## Executive Summary

**The team has been optimizing the wrong things.** The previous narrative — "the serial loop filter is 35% of frame time and is the main bottleneck" — is misleading. Even if the loop filter cost were reduced to zero, rvp9 would still be **7x slower** than vpxdec. The actual gap is dominated by:

1. **DSP kernel quality** — IDCT uses i32 lanes (8/ymm) instead of i16 lanes (16-32/ymm); convolve8_horiz is labeled "AVX2" but uses only 128-bit SSE intrinsics
2. **Bounds-checked indexing** throughout the entire decode pipeline (zero `get_unchecked` in rvp9-decoder)
3. **Per-frame heap allocations** (5-8 large allocs/frame vs libvpx's zero)
4. **Missing compiler optimizations** (thin LTO instead of fat; no PGO)
5. **Loop filter parallelism** (real but secondary to the above)

The architectural optimizations shipped in Phase 1+2 (direct-to-frame tile decode, shared MI grid) were valid but addressed ~15-20% of a problem that is fundamentally about per-pixel throughput in DSP kernels.

---

## Finding 1: IDCT Kernels Use Half-Width Lanes (CRITICAL)

**Impact: 30-40% of the total performance gap**

rvp9's AVX2 IDCT kernels (idct8x8, idct16x16, idct32x32) operate on **i32 lanes** using `_mm256_mullo_epi32` — 8 elements per 256-bit YMM register.

libvpx's IDCT kernels use **i16 lanes** with `_mm_madd_epi16` (SSE2: 8 elements/128-bit) and `_mm256_madd_epi16` (AVX2: 16 elements/256-bit). This is 2-4x more elements processed per instruction.

**The fix already exists but isn't wired.** The file `crates/rvp9-core/src/dsp/x86_64/idct16x16_sse2_256.rs` is a line-by-line port of libvpx's SSE2 i16-lane approach, and it passes conformance. Its file header notes: *"Slice 1.5 (next session) will flip the AVX2 arm to the SSE2 i16 kernel after bench A/B."* That flip never happened. Currently, this kernel is wired as the **non-AVX2 fallback only** (dispatch.rs lines 1292-1298).

**Recommendation**: Wire the i16-lane SSE2 kernel as the primary path for idct16x16 immediately. Port idct8x8 and idct32x32 to i16 lanes next. This is the single highest-impact change available.

| Kernel | rvp9 lanes | libvpx lanes | Throughput ratio |
|--------|-----------|-------------|-----------------|
| IDCT 8x8 | i32 (8/ymm) | i16 (8/xmm or 16/ymm) | 1-2x disadvantage |
| IDCT 16x16 | i32 (8/ymm) | i16 (16/ymm) | 2x disadvantage |
| IDCT 32x32 | i32 (8/ymm) | i16 (16/ymm) | 2-4x disadvantage |

## Finding 2: convolve8_horiz Is Mislabeled — Uses 128-bit SSE, Not AVX2 (CRITICAL)

**Impact: 15-20% of the total performance gap**

`crates/rvp9-core/src/dsp/x86_64/convolve8_horiz_avx2.rs` imports only `_mm_*` (128-bit) intrinsics — zero `_mm256_*` intrinsics. Despite the `_avx2` filename, this kernel processes 8 output columns per iteration using 128-bit `_mm_maddubs_epi16`.

libvpx's AVX2 horizontal convolve (`vpx_dsp/x86/vpx_subpixel_8t_intrin_avx2.c`) processes **16 output columns** per iteration using full 256-bit registers. This is a **2x throughput disadvantage** on rvp9's most-called motion compensation kernel.

The vertical kernel (`convolve8_vert_avx2.rs`) does use `_mm256_*` intrinsics for some paths but only partially.

**Recommendation**: Rewrite convolve8_horiz to use full 256-bit AVX2 operations, doubling throughput.

---

## Finding 3: Zero `get_unchecked` in the Decoder — Full Bounds Checking (SIGNIFICANT)

**Impact: 10-15% of the total performance gap**

Across the entire `rvp9-decoder/src/` crate: **0 occurrences of `get_unchecked`**. The `rvp9-core/src/dsp/` directory has only 16 occurrences across 2 files (both in lesser-used kernels).

This means the full decode pipeline — entropy decoding, coefficient parsing, block reconstruction, MI grid access, above/left context lookups, loop filter application — runs with **Rust bounds checks on every array index**. Each bounds check is a comparison + conditional branch + potential panic unwind path. In a tight inner loop processing millions of blocks per frame, these accumulate.

libvpx uses raw pointer arithmetic with zero bounds checking everywhere.

**Recommendation**: Profile to identify the hottest indexing sites (likely MI grid walk, above/left context lookups in `tile_ctx.rs`, coefficient parsing in `bool_reader.rs`). Apply `get_unchecked` with SAFETY proofs in the top ~5 hottest loops. This is mechanical work with high payoff.

## Finding 4: Per-Frame Heap Allocations — 5-8 Per Frame vs Zero (MODERATE)

**Impact: 5-8% of the total performance gap**

libvpx pre-allocates all frame buffers, MI grids, segment maps, and MV grids at init time and reuses them across frames. Per-frame allocations in steady state: **zero**.

rvp9 allocates fresh Vecs on every frame:

| Allocation | Per-frame cost (1080p, 32,400 MI cells) |
|-----------|----------------------------------------|
| `frame_mi_grid: Vec<Option<ModeInfo>>` | ~32,400 × sizeof(Option<ModeInfo>) |
| `cur_segment_ids: Vec<u8>` | ~32,400 bytes |
| `cur_mv_grid: Vec<PrevFrameMvRef>` | ~32,400 × sizeof(PrevFrameMvRef) |
| `above_partition: Vec<u8>` per tile | ~240 bytes × N tiles |
| Per-tile `TileDecodeCtx` Vecs | variable |

These involve allocator calls + zero-initialization. At 30+ fps, this is thousands of unnecessary allocations per second.

**Recommendation**: Move `frame_mi_grid`, `cur_segment_ids`, and `cur_mv_grid` to `Decoder` struct fields. Resize only when frame dimensions change (like `prev_segment_ids` already does). This is a straightforward refactor.

## Finding 5: Compiler Settings — Thin LTO, No PGO (MODERATE)

**Impact: 5-10% of the total performance gap**

Current `Cargo.toml` release profile:
```toml
[profile.release]
opt-level = 3
lto = "thin"        # <-- should be "fat"
codegen-units = 1   # good
debug = "line-tables-only"
```

- **`lto = "thin"` → `"fat"`**: The decoder has hot paths crossing crate boundaries (rvp9-decoder → rvp9-core DSP kernels). Fat LTO enables full cross-crate inlining and dead-code elimination that thin LTO cannot achieve. Cost: longer compile time. Benefit: potentially significant for a decoder where every call into DSP matters.

- **PGO (profile-guided optimization)**: Not used. For a hot decode loop with predictable branch patterns, PGO can deliver 10-20% improvement through better branch prediction hints and code layout. Chrome and Firefox builds of libvpx benefit from PGO implicitly.

- **`target-cpu=native`**: Already set in `.cargo/config.toml`. Good.

**Recommendation**: Switch to `lto = "fat"` immediately (zero-risk). Investigate PGO as a follow-up (moderate effort, high payoff).

## Finding 6: Loop Filter Threading — Real but Secondary (MODERATE)

**Impact: Important but NOT the primary bottleneck**

The loop filter comparison found that the **kernel implementations are at parity or better** — rvp9 has AVX2 for all 12 LF kernel variants while libvpx only has AVX2 for 2 (the rest are SSE2). Mask computation is identical. Application strategy is identical.

The gap is purely in **parallelism**:

| Aspect | libvpx | rvp9 |
|--------|--------|------|
| Row-parallel LF | Yes (`loop_filter_rows_mt`, per-row mutex/condvar sync) | No |
| Decode+LF pipelining | Yes (`row_mt` mode — LF starts on row N while decode works on row N+1) | No |
| LF threading | N workers on N SB rows concurrently | Single-threaded, runs after all tiles complete |

libvpx's row-MT mode uses a **job queue** that interleaves decode and LF tasks. Workers dequeue either RECON_JOB or LPF_JOB entries, naturally alternating between decode and LF work. Cross-row dependencies are enforced with per-row atomic progress counters + condvar waits.

**However**, per the Devil's Advocate analysis: even zeroing LF entirely, rvp9 is still 7x slower. LF parallelism matters but is secondary to the DSP kernel throughput issues in Findings 1-2.

**Recommendation**: Implement row-parallel LF after addressing DSP kernel quality. The correct approach (proven by libvpx): row-interleaved dispatch with per-row progress counters, not per-SB-row wavefront (which was tried and failed).

## Finding 7: Minor Decode Pipeline Inefficiencies (LOW)

Several smaller gaps identified across the decode pipeline:

| Issue | libvpx | rvp9 | Impact |
|-------|--------|------|--------|
| ScaleFactors computation | Once per frame per ref | Per block per ref (`ScaleFactors::new()` with integer division) | Minor (1-2%) |
| dqcoeff buffer (intra path) | Pre-allocated in TileWorkerData, pointer-advanced | Thread-local `RefCell<Vec<i32>>` with TLS lookup per TX block | Minor (2-3%) |
| dqcoeff zeroing | Smart partial memset (eob-dependent: only zero what was written) | Full `[..seg_eob]` zero unconditionally | Minor (1-2%) |
| FrameContext handling | Pointer swap between working copy and bank | Full clone (~50-100 KB memcpy) per frame | Minor (per-frame) |
| Trace flag checks | Compile-time `#if CONFIG_*` (zero cost) | Runtime `OnceLock` reads per block | Negligible |
| Recursive decode_partition args | 6 arguments | 15 arguments (register pressure) | Negligible |

**Recommendation**: Address these as a batch after the high-impact items. Pre-compute ScaleFactors per-frame. Replace TLS dqcoeff with per-tile buffer. Implement smart partial zeroing. Replace FrameContext clone with swap.

## Finding 8: Benchmark Methodology Concerns (META)

The Devil's Advocate uncovered troubling inconsistencies:

1. **The CSV data tells a different story.** The `bench/results/decode-headtohead.csv` shows ratios of 62x–249x in early runs, not 10.8x. The "10.8x" from the journal appears to come from the best run after `-native` optimizations.

2. **The latest benchmark results have blank vpxdec columns.** The most recent runs used `-SkipVpxdec`, so we've been flying without a comparison baseline.

3. **rvp9dec has no timing instrumentation.** vpxdec has `--summary` with elapsed time and fps. rvp9dec's `--summary` only prints frame counts. An apples-to-apples CLI comparison requires adding timing to rvp9dec.

4. **The profiling numbers were estimated, not measured.** The "35.5% LF" figure came from phase-removal benchmarks, not instruction-level profiling (no perf/VTune/Superluminal traces cited).

**Recommendation**: 
- Always run with vpxdec comparison enabled
- Add `Instant`-based timing to rvp9dec `--summary` matching vpxdec's measurement scope
- Run an actual CPU profiler before the next optimization wave — stop estimating, start measuring

## Finding 9: Frame Buffer Alignment (LOW)

libvpx allocates frame buffers with `vpx_memalign(32, ...)` guaranteeing 32-byte alignment for AVX2. rvp9 uses `vec![0u8; N].into_boxed_slice()` which only guarantees 16-byte alignment (Rust's global allocator minimum for large allocations).

On modern x86-64 (Haswell+), unaligned 256-bit loads via `vmovdqu` have no penalty as long as they don't cross cache-line boundaries. The stride is 32-byte aligned, so the risk is limited. But if any SIMD kernel uses `vmovdqa` (aligned loads), misalignment would fault.

**Recommendation**: Low priority. Switch to aligned allocation if profiling shows cache-line split penalties.

## Revised Gap Breakdown

The team's previous narrative attributed the gap to architecture (serial merge, grid stitch, serial LF). The actual breakdown:

| Source | Estimated % of gap | Status |
|--------|-------------------|--------|
| **IDCT i32 lanes instead of i16** | 30-40% | Fix exists but not wired |
| **convolve8_horiz 128-bit instead of 256-bit** | 15-20% | Needs rewrite |
| **Bounds-checked indexing in decode pipeline** | 10-15% | Needs targeted unsafe |
| **Per-frame heap allocations** | 5-8% | Needs refactor to reuse |
| **Missing fat LTO + PGO** | 5-10% | Config change |
| **Loop filter parallelism** | 5-10% | Needs row-MT implementation |
| **Minor decode inefficiencies** | 5-8% | Batch of small fixes |
| **Architectural (merge/stitch)** | ~0% | Already fixed in Phase 1+2 |

## Priority-Ordered Action Plan

### Tier 1 — High Impact, Achievable Now

1. **Wire i16-lane IDCT as primary path** — the SSE2 i16-lane idct16x16 kernel already exists and passes conformance. Flip the dispatch. Then port idct8x8 and idct32x32.

2. **Switch `lto = "fat"`** — one-line Cargo.toml change, zero risk, guaranteed improvement.

3. **Rewrite convolve8_horiz with true 256-bit AVX2** — double the throughput of the most-called MC kernel.

### Tier 2 — Moderate Impact, Moderate Effort

4. **Eliminate per-frame allocations** — move MI grid, segment IDs, and MV grid to Decoder struct fields.

5. **Profile-guided `get_unchecked`** — run a real profiler, identify top 5 bounds-check hotspots, apply unsafe indexing with SAFETY proofs.

6. **Pre-compute ScaleFactors per-frame** — move out of the per-block loop.

### Tier 3 — Lower Impact or Higher Effort

7. **Row-parallel loop filter** — implement libvpx's row-interleaved approach with per-row progress counters.

8. **Decode+LF pipelining** — architectural change to overlap LF with decode (libvpx's `row_mt` mode).

9. **PGO build** — profile-guided optimization for branch prediction and code layout.

10. **Smart partial dqcoeff zeroing** — zero only the written coefficients based on eob.

---

## Conclusion

The 10x gap is not architectural — it's per-pixel. The decoder's structure is sound (same recursive partition walk, same SB-unit processing, same reference frame management, same persistent worker threads). The gap lives in the quality of the DSP kernels that process every pixel of every frame: transforms at half the lane width, convolution at half the register width, and safety overhead (bounds checks) on every array access. Fix those and the ratio should drop from ~10x to ~3-4x, at which point the loop filter parallelism and minor inefficiencies become the marginal gains that close the final gap to 2x.
