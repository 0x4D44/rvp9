# Stage 3.5 — Decoder hardening

## 1. Context

The Stage 3 conformance gate cleared on 2026-05-19 (`c43b438`, hard
assertion `total_mismatched == 0`). The decoder is **bit-exact with libvpx
on every frame it attempts**, but the gate doesn't cover everything a
production decoder needs. Eleven gaps remain. This HLD plans their
closure; execution interleaves with the Stage 4 encoder drive
(`notes/stage4-drive.md`).

The current scoreboard:

```
191 passed  /  0 mismatched  /  10 skipped  /  201 total
```

The 10 skipped frames are two `DecodeError::Unimplemented` arms; the
remaining gaps are quality, performance, coverage, and process debt that
the AOM 201-frame conformance set doesn't exercise.

## 2. Scope

**In:** the 11 numbered decoder gaps (G1 … G11 below), at full design
depth. Quick closeouts get a paragraph each; large items (G4 SIMD, G5
threading) get a multi-section design with rollout staging.

**Out:**
- Encoder work (Stage 4a in flight per `notes/stage4-drive.md`).
- Profile 2 / Profile 3 (high-bit-depth) — deferred to Stage 6+ per
  PLAN.md §Features.
- Frame-parallel decoding mode (libvpx `VPX_DECODER_CFG.threads >= 2 +
  frame_parallel_decoding_mode=1`) — not in PLAN.md gate list; revisit
  if a consuming application needs it.
- External-frame-buffer interface (libvpx `vpx_codec_set_frame_buffer_functions`)
  — same; revisit on demand.

**Quality philosophy (from CLAUDE.md):**
- Each item identifies its **testing oracle**: what encodes "correct"
  for that gap in a machine-checkable form.
- No env vars and no feature flags. Where rollout staging is needed,
  use separate crates (`rvp9-fuzz`), separate test binaries, or
  function-pointer dispatch already in place (`SimdDispatch`).
- Development sandbox: no migration or rollback support required.

## 3. Sharing analysis & worktree strategy

The encoder and decoder share `rvp9-core` but the overlap is narrower
than it looks. Decoder hardening can run in a worktree (`decoder-hardening`
branch) with low merge-conflict risk.

| Crate / module                       | Encoder uses | Decoder uses | Shared write? |
|--------------------------------------|--------------|--------------|----------------|
| `rvp9-decoder/`                      | no           | yes          | no             |
| `rvp9-encoder/`                      | yes          | no           | no             |
| `rvp9-core::bitstream::*`            | write_*      | parse_*      | **types only** |
| `rvp9-core::bitstream::modes_writer` | yes          | round-trip   | no             |
| `rvp9-core::entropy::BoolReader`     | no           | yes          | no             |
| `rvp9-core::entropy::prob_diff_writer` | yes        | no           | no             |
| `rvp9-core::transforms::inverse`     | no           | yes          | **G2 touches** |
| `rvp9-core::intra_pred`              | not yet      | yes          | low            |
| `rvp9-core::dsp` (SimdDispatch)      | will         | yes          | **G4 touches** |
| `rvp9-core::loopfilter`              | future       | yes          | low            |
| `rvp9-core::quant`                   | will         | yes          | read-only LUTs |
| `rvp9-core::frame`                   | will         | yes          | low            |

**Conclusion:** Wave A (cheap closeouts: G1, G2, G3, G10, G11) can run
in a `decoder-hardening` worktree with **zero conflict risk** against
Stage 4 encoder work — these touch only `rvp9-decoder` and the
inverse-transform module, neither of which the encoder is writing today.

Wave B (Profile 1, benchmarks, corpus, fuzz: G6, G7, G8, G9) is also
clean — touches separate test crates or adds code paths the encoder
doesn't read.

Wave C (SIMD, threading: G4, G5) touches `rvp9-core::dsp` and a future
`rvp9-core::tile_threading` that both crates will share. These should
land while the encoder is between sub-stages, not in the middle of a
hot path. Suggest gating them to a quieter encoder window; **not the
worktree's concern**, just a sequencing call.

## 4. Sequencing

Three waves, ordered by effort and conflict risk:

```
Wave A (1-2 days total)         Wave B (1-2 weeks total)        Wave C (~3 months)
-----------------------         ------------------------         ------------------
G3   empty-ref-slot error       G6  realtime benchmark           G4.1 SIMD pilot (idct8x8 all arches)
G10  doctest fix                G7  Profile 1 (4:2:2/4:4:4)      G5   tile threading
G1   IntraOnly decode           G8  real-world corpus            G4.2 SIMD transforms
G2   lossless WHT path          G9  fuzzing harness              G4.3 SIMD intra-pred + LF
G11  unsafe audit                                                G4.4 SIMD frame-buffers + dequant
                                       (each independent;
                                        dispatchable in parallel)
```

Wave A is dispatched as parallel agents in the `decoder-hardening`
worktree, then merged to main as a **single squash-merge** once all
five items are green.

Wave B items are independent and can dispatch as agent slots free up
between encoder sub-stages.

Wave C runs G4 and G5 in the same pass per Arthur's call (decision
2026-05-19, §7 Q1) but **sequences them to avoid mid-flight
kernel-file conflicts**:

1. **G4.1 first** — pilot SIMD on one representative kernel
   family (idct8×8) end-to-end across all arches. This locks the
   function-pointer signature shape and proves the dispatch pattern.
2. **G5 next** — tile threading lands against the now-stable kernel
   API. Threading code never sees a kernel file mid-rewrite.
3. **G4.2 → G4.4** — roll the pattern from G4.1 out to the
   remaining kernel families. Each family is a self-contained
   transform of the dispatch table; doesn't touch threading code.

## 5. Items

### G1. IntraOnly frame decode path

**Symptom:** `crates/rvp9-decoder/src/lib.rs:697` returns
`DecodeError::Unimplemented { reason: "intra-only frame decode …" }`
for any `FrameKind::IntraOnly` packet.

**libvpx anchor:** `vp9/decoder/vp9_decodeframe.c::decode_frame` —
the IntraOnly branch is structurally identical to the KeyFrame branch
except for three things:

1. **No FrameContext reset.** Keyframes overwrite all four
   `frame_contexts[]` banks with defaults; IntraOnly preserves them.
2. **Refresh-frame-flags follow `refresh_frame_flags` byte** rather
   than implicit "refresh all slots."
3. **Segmentation map** inherits from the previous frame's state
   (already preserved across our `Decoder` between frames; no extra
   work).

**Design:**

Add `Decoder::decode_intra_only_frame(&ParsedFrame) -> Result<FrameBuf, DecodeError>`
mirroring `decode_keyframe` (current source ~580 lines starting at
`lib.rs:721`). The body is a parameterised version of the keyframe
driver:

```rust
fn decode_intra_only_frame(&mut self, frame: &ParsedFrame<'_>) -> Result<FrameBuf, DecodeError> {
    // Identical to decode_keyframe EXCEPT:
    //  - Do NOT call `self.reset_frame_contexts()` on entry.
    //  - On exit, refresh only the ref_frame_map slots indicated by
    //    `tail.refresh_frame_flags` (a u8 bitmask).
    //  - All other steps (compressed-header parse, tile walk, partition
    //    walk, mode decode, recon, LF apply) are byte-identical.
}
```

Most of the keyframe driver is already parameterisable — the
`reset_frame_contexts` call and the slot-refresh loop are the only
deltas. Extract those into helpers shared by both drivers.

**Wire up the dispatcher** at `lib.rs:697`:
```rust
FrameKind::IntraOnly { .. } => self.decode_intra_only_frame(frame),
```

**Testing oracle:** the AOM conformance corpus doesn't contain
IntraOnly-mid-stream vectors in the Profile 0 set, so we need either
(a) a synthetic IntraOnly produced by libvpx's `vpxenc --intra-only`
flag, captured locally and added to a `decoder-hardening/` test
fixture; or (b) a round-trip via our own encoder once S4.x produces
IntraOnly output (deferred). Pick (a) — generate via vpxenc, MD5-pin.

**Effort:** 1 day. Bulk is refactoring the keyframe driver to share
the parameterised path.

**Exit:** synthetic IntraOnly vector decodes bit-exact; conformance
ratchet unchanged (no IntraOnly in current 201 vectors).

### G2. Lossless decode path (WHT inverse transform)

**Symptom:** Two sites return `DecodeError::Unimplemented`:
- `lib.rs:734` (keyframe path) — `"lossless decode (WHT inverse transform path) not yet wired"`
- `lib.rs:1113` (inter path) — `"lossless inter frame decode (WHT inverse transform path)"`

Both trip when `quantization.is_lossless()` (Qindex 0 + base_q_index =
0 — see `sub_parsers.rs:189`).

**libvpx anchor:** `vp9/common/vp9_idct.c::iwht4x4_1_add` /
`iwht4x4_16_add`. Lossless mode uses a Walsh-Hadamard inverse instead
of the standard idct4×4. Only `TX_4X4` is permitted in lossless; the
encoder is forbidden from emitting larger TX sizes.

**Design:**

Add `iwht4x4_16_add` and `iwht4x4_1_add` to
`crates/rvp9-core/src/transforms/inverse.rs`, mirroring the libvpx
implementation byte-for-byte (it's ~30 lines of straight integer
arithmetic — see libvpx `vp9_iwht4x4_16_add_c`).

Extend the IT-add dispatch (`transforms::inverse::iht4x4_add` and the
top-level `iht_add` dispatcher) with a new `TxType::WHT` variant or a
parallel `iwht_add` path. **Prefer the second** — `TxType::WHT` would
require widening every enum site; a separate `iwht_add` entry point
matches the libvpx call shape and stays out of the hot DctDct path.

In `reconstruct_intra_block` and `reconstruct_inter_block`, detect
lossless via `quantization.is_lossless()` (already threaded into the
decoder via tail) and route to `iwht_add` instead of `iht_add`.

Remove the two `Unimplemented` short-circuits at `lib.rs:734` and
`lib.rs:1113`.

**Testing oracle:** Generate a lossless-q0 vector via
`vpxenc --lossless` on a small clip, capture libvpx's
`--i420` reference output, MD5-pin. Should produce **identical
input/output pixels** (lossless invariant — useful additional check
beyond MD5: assert `decoded_yuv == source_yuv` for the source clip we
encoded from).

**Effort:** 1 day. ~30 lines of WHT kernel + dispatch wiring + tests.

**Exit:** synthetic lossless vector decodes bit-exact AND
pixel-identical to source.

### G3. Empty ref_frame_map slot error variant

**Symptom:** `lib.rs:1133` returns
`DecodeError::Unimplemented { reason: "inter frame referenced empty ref_frame_map slot" }`
when an inter frame names a `ref_frame_idx` whose slot is `None`.

**Critique:** This isn't actually "unimplemented" — there's nothing
to implement. The condition is **a malformed bitstream** (no
preceding keyframe ever populated that slot). Reporting it as
`Unimplemented` is misleading.

**Design:**

Add a new variant to `DecodeError`:

```rust
pub enum DecodeError {
    // ... existing variants ...

    /// Inter frame references a slot in `ref_frame_map` that has not
    /// been populated by any preceding decoded frame. Mirrors libvpx's
    /// `VPX_CODEC_CORRUPT_FRAME` for missing references.
    MissingReferenceFrame { slot: u8 },
}
```

Replace the `Unimplemented` return at `lib.rs:1133` with
`MissingReferenceFrame { slot: slot_idx as u8 }`.

**Testing oracle:** Unit test that constructs a Decoder, calls
`decode_frame` on a synthesised inter packet with `ref_frame_idx = 3`
(no preceding keyframe), asserts the new error variant.

**Effort:** 1 hour. Purely a typing fix.

**Exit:** new variant lands; existing call sites continue to compile;
conformance harness updates its skip-reason counter accordingly (the
empty-slot path doesn't fire on the 201 vectors so this is type-clean
only).

### G4. SIMD kernel rollout

**Symptom:** `crates/rvp9-core/src/dsp/dispatch.rs:50-55` —
`SimdDispatch` has *only* a `caps` field and zero per-kernel function
pointers. The comment at line 64 says: *"This will fan out to one
per-kernel selection clause as kernel families are added."* No kernel
families have been added. **The decoder is pure scalar Rust on every
architecture.**

**Critique:** This is by far the largest decoder gap by user-visible
impact. A scalar decoder runs ~4–10× slower than libvpx-with-SIMD on
identical hardware. 1080p60 real-time on modern x86_64 is unreachable
without SIMD on at least the inverse transforms, intra prediction, and
loop-filter kernels.

**libvpx anchor:** `vpx_dsp/x86/*`, `vpx_dsp/arm/*`,
`vp9/common/x86/*`, and the RTCD machinery in
`vpx_dsp/vpx_dsp_rtcd_defs.pl` + `vp9/common/vp9_rtcd_defs.pl`.
Seven kernel families per HLD-simd (already enumerated in
`dsp/dispatch.rs:34-44`):

| # | Family                  | LLD anchor             | Decoder kernels |
|---|-------------------------|------------------------|-----------------|
| 1 | `frame-buffers`         | frame-buffers.md       | scale, border extend |
| 2 | `entropy` (decoder side) | entropy.md            | none — BoolReader is scalar by design |
| 3 | `transforms` (inverse half) | transforms.md      | idct4/8/16/32, iadst4/8/16, iht*, iwht4 |
| 4 | `quant` (dequant side)  | quant.md               | dequantise |
| 5 | `intra-pred`            | intra-pred.md          | 10 modes × 4 sizes |
| 6 | `loopfilter`            | loopfilter.md          | 6 kernels × {vert, horiz} × {single, dual} |
| 7 | (encoder-only)          | —                      | n/a |

**Design — staged rollout:**

The dispatch infrastructure is already correct (`OnceLock<SimdDispatch>`,
detect-once-at-init, `&'static` passed to consumers). The work is
adding per-kernel function pointers and the per-arch impls.

**Stage G4.1 — One representative kernel family, end-to-end.**
Pick `idct8×8` (used everywhere, well-understood, libvpx ships
SSE2/SSSE3/AVX2 variants). Implement:
- Scalar reference (already exists at `transforms::inverse::idct8x8_64_add`).
- SSE2 impl behind `#[cfg(target_arch = "x86_64")]`.
- SSSE3 impl (libvpx's mainline production kernel).
- AVX2 impl.
- NEON impl behind `#[cfg(target_arch = "aarch64")]`.

Each impl gets a **scalar-differential test**: random inputs, both
scalar and SIMD outputs computed, assert byte-equal. This is the
testing oracle — scalar is the spec, SIMD must match. Test runs on
every target_arch via runtime caps gating (skip the SSE2 test on
aarch64, etc.).

Function-pointer slot lands in `SimdDispatch`:

```rust
pub struct SimdDispatch {
    pub caps: Caps,
    pub idct8x8_add: fn(input: &[i32; 64], dst: &mut [u8], stride: usize),
    // ... grows per-family ...
}
```

`SimdDispatch::build(caps)` selects the right impl at init time.
Consumers (decoder, eventually encoder) read via
`rvp9_core::dsp::get().idct8x8_add(...)` — zero per-call overhead
beyond an indirect call.

This stage proves the pattern end-to-end on one kernel; ~3-5 days.

**Stage G4.2 — Family 3 transforms complete.**
Roll out the pattern to every inverse-transform kernel
(idct4/8/16/32 + iadst4/8/16 + iht4/8/16 + iwht4). ~2 weeks per arch.

**Stage G4.3 — Family 5 intra-pred + Family 6 loopfilter.**
Most user-visible after transforms. ~1-2 weeks each per arch.

**Stage G4.4 — Family 1 frame-buffers + Family 4 dequant.**
Smaller, less per-frame contribution; closes the family list. ~1
week.

Total: **~6-10 weeks of focused SIMD work** if all four arches are
pursued. Faster if we scope to x86_64-only initially.

**Architecture priority order (suggested):**

1. x86_64 SSE2 (always-on baseline; libvpx requires it).
2. x86_64 SSSE3 (libvpx promotes to required for three idct kernels
   per `notes/lld/transforms.md` §7.4 divergence).
3. x86_64 AVX2 (typical modern x86 baseline).
4. aarch64 NEON (M-series Mac, ARM servers).
5. x86_64 SSE4.1 (libvpx ships some; lower priority than AVX2 — most
   AVX2-capable CPUs also have SSE4.1, so AVX2 makes SSE4.1 a fallback
   only for the narrow SSSE3-but-not-AVX2 cohort).

**No feature flags.** Per-arch SIMD is gated by `#[cfg(target_arch)]`
at the impl-source level, and runtime caps at the dispatch-build
level. No `--features simd` exists or should exist.

**Testing oracle:** scalar-differential per kernel. Random inputs,
assert SIMD output byte-equal to scalar. Property test with millions
of inputs gives strong coverage. Plus end-to-end: run the full
conformance harness with the SIMD-selected dispatch and assert
`total_mismatched == 0` still holds. (This is the load-bearing
end-to-end oracle — if SIMD breaks conformance, the differential
caught a bug the per-kernel test missed.)

**Effort:** 6-10 weeks total (stages G4.1 … G4.4). G4.1 alone is
worth its own merge — proves the pattern, lets us extrapolate.

**Exit:** all six decoder kernel families have at least one non-scalar
impl per supported arch; conformance gate green; `realtime` benchmark
(G6) shows the gain.

### G5. Tile-threaded decode

**Symptom:** `f8fe0b9` ("Stage 3 Task E.2: single-threaded multi-tile
decode") wired multi-tile *decode correctness* but iterates tiles
sequentially. Multi-tile streams decode but don't get the throughput
gain of parallel tile decode.

**libvpx anchor:** `vp9/decoder/vp9_decodeframe.c::decode_tiles_mt`
+ the worker pool in `vp9/decoder/vp9_thread.h`. Tile-row threading
is the load-bearing parallelism for VP9 decoding; tile-col threading
is also supported.

**Design:**

Add a `WorkerPool` to `rvp9-core::threading` (new module). The pool
is shared with the eventual encoder (per HLD-threading and Stage 4a
§7, both want it). Designing for that shared use case in the decoder
phase is fine — the pool API is small and the encoder's needs (job
queue + row-sync) are decoder-compatible.

**Module structure:**

```
crates/rvp9-core/src/threading/
  mod.rs              — public API: WorkerPool, JobHandle, RowSync
  pool.rs             — pthread-equivalent worker pool (std::thread + crossbeam-channel)
  job.rs              — per-frame job tracking + barriers
  rowsync.rs          — encoder row-MT helper (deferred until Stage 4a §7 calls)
```

Decoder integration in `rvp9-decoder::tile`:
- `WorkerPool::new(simd_dispatch: &'static SimdDispatch, num_threads: usize)`
  — workers receive an immutable `SimdDispatch` reference. This pins
  R-09 from HLD-simd by construction.
- `Decoder::new(config)` constructs the pool once; pool size is
  `config.threads.unwrap_or(num_cpus::get())` capped at the frame's
  tile count.
- `decode_tile_intra_keyframe` / `decode_tile_inter_frame` become a
  closure submitted to the pool, one closure per tile. The driver
  awaits all closures via a frame-scoped join barrier before applying
  loop filter (LF currently runs frame-globally; tile-local LF on
  tile boundaries is a stage 5 problem).

**Safety:**
- Each tile owns its `TileDecodeCtx` mutably (per-row + per-col
  context strips are tile-local).
- The `Yv12Buffer` destination is shared. Per-tile writes target
  disjoint plane regions; safety is proven by the tile-mi-rect →
  plane-rect lookup. Document this in an `// SAFETY:` block at the
  write site; mirror libvpx's `MacroBlock::dst` view discipline.
- The shared `BoolReader` source is *not* shared — each tile gets
  its own `&[u8]` slice from `parse_tile_buffers` and constructs its
  own reader.

**Design Q (call this out for Arthur):**

Per-tile entropy state. Today the decoder reuses one `FrameContext`
bank across tiles. In libvpx, *backward adaptation* runs once at
frame end, accumulating counts from all tiles. With multi-threaded
tile decode, the counts must be accumulated from each thread's local
`FrameCounts` instance.

Today's code path already builds per-frame `FrameCounts` and runs
`adapt_*_probs` at frame-end. We need to switch from
one-`FrameCounts`-per-frame to one-`FrameCounts`-per-tile + a
merge step at the join barrier. Mechanically: per-tile counts are
`+=` summed (every field is integer counts), result is identical to
the single-thread case. Mirrors libvpx
`vp9/decoder/vp9_decoder.c::accumulate_frame_counts`.

**Testing oracle:** Run the existing 201-frame conformance harness
with `num_threads = N` for N ∈ {1, 2, 4, 8}. **All four runs must
produce `total_mismatched == 0`.** This is the threading parity
oracle. Add to CI as a 4-way matrix.

Also: race detection via `cargo +nightly miri` (where feasible) and
TSan-equivalent fuzz of the join barriers.

**Effort:** 3-4 weeks. Pool + frame-scope + per-tile FrameCounts +
join + counts merge + safety review.

**Exit:** conformance harness green at N ∈ {1, 2, 4, 8}; throughput
benchmark (G6) shows scaling up to tile count.

### G6. Real-time benchmark (decoder throughput)

**Symptom:** No real-time benchmark exists for the decoder. Stage 3
secondary gate per `notes/stage4-drive.md` §Holds calls this out:
*"throughput bench … still pending."*

**libvpx anchor:** `vp9_decodeframe` throughput is the de-facto
benchmark; the comparison harness is `vpxdec` with `--summary` and
wall-clock measurement.

**Design:**

Add `crates/rvp9-bench/src/bin/decode-throughput.rs`. Inputs: an IVF
file + a target ms/frame budget. Output: median, p95, p99 frame
times; pass/fail vs budget; CSV for trend tracking.

Same harness style as the existing `bdrate` and `realtime` bench
bins. Differential mode: run `vpxdec` on the same input and report
**relative ms/frame** (us = scalar, them = SIMD libvpx — we expect
us to be 4-10× slower until G4 lands; the gap closes as SIMD
families ship).

**Tests:** Self-test that runs on a 10-frame synthetic IVF, asserts
the harness produces sane numbers (positive ms/frame, p99 ≥ median).
The actual throughput target is a soft gate — informational, not
asserted in CI.

**Effort:** 2 days.

**Exit:** harness exists, runs in CI as a smoke test, produces
trend-trackable CSV. Real-time gate from PLAN.md §"Real-time
performance" (720p30 ≤ 33ms median etc.) remains aspirational until
G4 + G5 land.

### G7. Profile 1 support (8-bit non-4:2:0 chroma)

**Symptom:** `crates/rvp9-core/src/frame.rs::Yv12Buffer` assumes 4:2:0
(chroma planes are `width/2 × height/2`). Profile 1 streams (4:2:2 or
4:4:4 at 8-bit depth) decode-rejects at the colour-config parse step
in `bitstream::header::parse_color_config`.

**libvpx anchor:** `vp9_decodeframe.c::setup_frame_size` honours
`cm->subsampling_x` and `cm->subsampling_y` per the bitstream's
color-config bits.

**Design:**

Widen `Yv12Buffer` to track `(subsampling_x: u8, subsampling_y: u8)`
alongside Y/U/V dims:
- 4:2:0 — `(1, 1)` (current; chroma planes half-width AND half-height).
- 4:2:2 — `(1, 0)` (chroma half-width, full-height).
- 4:4:0 — `(0, 1)` (chroma full-width, half-height).
- 4:4:4 — `(0, 0)` (chroma full size).

Plumb the subsampling pair through `FrameBuf` construction, through
the tile/recon/LF chain, into every plane-stride / plane-extent
calculation. Most of the work is mechanical (replace hardcoded `>> 1`
chroma shifts with `>> ss_y` / `>> ss_x`).

**Touch list:**
- `frame.rs` — `Yv12Buffer::new` accepts subsampling; `chroma_width()`
  and `chroma_height()` compute from it.
- `decoder/tile.rs` — chroma block iteration uses `n4_w >> ss_x` etc.
- `decoder/reconstruct.rs` / `reconstruct_inter.rs` — same.
- `core/loopfilter/apply.rs` — chroma mask cells span depends on ss.
- `core/intra_pred.rs` — DC predictor's left/above neighbour pixels.

**Testing oracle:** Generate Profile 1 vectors via
`vpxenc --profile=1` (4:4:4 8-bit) and `--profile=1` with appropriate
sampling config, MD5-pin libvpx reference. Add to conformance corpus
as a separate vector set (currently all 201 vectors are Profile 0 /
4:2:0).

**Effort:** 1 week. Mechanical but pervasive.

**Exit:** decoder accepts Profile 1 vectors; new vectors pass
bit-exact; Profile 0 conformance unchanged.

### G8. Real-world corpus

**Symptom:** Decoder has been tested only against AOM's 201-frame
conformance set, which is designed to exercise spec edge cases, not
to be representative of streams in the wild. Confidence for
production deployment is bounded by this corpus.

**Design:**

Assemble a real-world test corpus. Three sources:

1. **YouTube-extracted clips.** A handful of public-domain or
   permissively-licensed clips that YouTube serves as VP9. ~5
   clips, 720p–1080p, varied content (talking head, sports,
   animation, screen content).
2. **WebRTC captures.** Use Chrome's webrtc-internals dumping to
   capture a real WebRTC VP9 stream from a Meet/Hangouts session.
   1-2 captures.
3. **Livestream archive.** Twitch/YouTube live re-broadcasts in VP9.
   1-2 segments.

Total ~10 clips. Store outside the repo (`third_party/corpus/` or
similar, gitignored); fetch script `scripts/fetch-corpus.ps1`.

**Run protocol:** Decode each clip via both libvpx (`vpxdec --i420`)
and rvp9 (`cargo run -p rvp9-cli -- decode`). MD5 each frame, compare.
**No mismatches** = pass.

**Test harness:** New integration test
`crates/rvp9-harness/tests/real_world.rs` that walks the corpus.
Skipped in CI when corpus absent (`if !corpus_path.exists() { return Ok(()); }`).
Run manually on dev machines that have the corpus.

**Effort:** 3-5 days. Corpus assembly + harness + first run. Expect
real-world clips to surface 1-3 new bugs (encoder quirks the AOM set
doesn't exercise); add days as needed.

**Exit:** corpus assembled, fetch script in place, harness in place
and skip-clean when corpus absent. First real-world run produces a
clean MD5 sweep OR a list of new bugs filed.

### G9. Fuzzing harness

**Symptom:** No fuzzing. Decoders are common security targets;
malformed or truncated bitstreams must produce *errors*, not panics
or undefined behaviour. We've never tested that.

**Design:**

New crate `crates/rvp9-fuzz/`. Use `cargo-fuzz` (libFuzzer). Three
fuzz targets:

1. `fuzz_parse_packet` — raw bytes → `Decoder::parse_packet`. Asserts
   the function returns either `Ok(_)` or `Err(_)`, never panics,
   never UB.
2. `fuzz_decode_frame` — raw bytes → `Decoder::parse_packet`
   followed by `Decoder::decode_frame` on every yielded
   `ParsedFrame`. Same panic/UB invariant.
3. `fuzz_full_stream` — multi-packet sequence. Tests stateful bugs
   (ref-frame-map evolution, segmentation map carry-over,
   FrameContext drift).

**No feature flags.** `rvp9-fuzz` is a separate crate (per user
preference) instead of `--features fuzz` on the main crate. It depends
on `rvp9-decoder` like any consumer would.

**Seed corpus:** the 201 conformance vectors + the G8 real-world
corpus.

**CI:** A 5-minute fuzz pass per target on PR, longer overnight runs.

**Effort:** 1 week. Cargo-fuzz setup + 3 targets + seed corpus +
first 24-hour bake.

**Exit:** harness in place, three targets fuzzable, first 24-hour
bake produces zero crashes OR a list of crash inputs reduced to
minimal repros and filed.

### G11. `unsafe` audit + soundness review

**Symptom:** Stage 3 secondary gate per `notes/stage4-drive.md`
§Holds — *"unsafe-comment audit still pending — revisit before formal
Stage 3 sign-off."*

**Design:**

Enumerate every `unsafe` block in `rvp9-core` and `rvp9-decoder`.
For each, check:
1. Does it have an `// SAFETY:` comment naming the invariant?
2. Is the invariant correct (does the calling code actually uphold
   it)?
3. Is the `unsafe` minimal (smallest possible scope)?
4. Can it be replaced by a safe equivalent at acceptable cost?

Produce `notes/decoder-unsafe-audit.md` with one entry per `unsafe`
site:

```
- crates/rvp9-core/src/frame.rs:142 — Yv12Buffer::plane_mut_ptr
  invariant: caller holds &mut self, so no aliasing
  status: OK
- crates/rvp9-decoder/src/tile.rs:1843 — bool-reader slice raw access
  invariant: tile_size validated against tile_section.len()
  status: NEEDS WORK — slice bounds checked by caller, not enforced
                       at the unsafe site
- ...
```

**Effort:** 2-3 days. Mostly review; expect 1-3 sites to need
tightening.

**Exit:** audit doc lands; sites flagged `NEEDS WORK` get follow-up
commits; final state has every `unsafe` justified or removed.

## 6. Cross-item concerns

### 6.1 Test ratchet

The conformance harness ratchet is currently `MIN_PASSES = 191` and
`assert_eq!(total_mismatched, 0)`. **Don't relax these during decoder
hardening work.** If a Wave A item drops `MIN_PASSES`, it's a
regression. The skip count (currently 10) MAY drop as G1 + G2
implement the unimplemented paths — that's expected, and the harness
should reflect it.

After G1 + G2 land, the harness should assert:

```rust
const MIN_PASSES: usize = 201;            // G1 + G2 close the 10 skips
assert_eq!(total_mismatched, 0);
// And implicitly: total_skipped == 0 because passed + mismatched == total.
```

### 6.2 No feature flags, no env vars

Per Arthur's preference, none of the items above introduce a feature
flag or env var. Specifically:
- G4 SIMD: runtime caps detection, function-pointer dispatch. No
  build-time flags.
- G9 fuzzing: separate `rvp9-fuzz` crate. No `--features fuzz`.
- G6 throughput benchmark: separate `decode-throughput` binary in
  `rvp9-bench`. No flag.
- G7 Profile 1: code path additions, gated by parsed
  bitstream subsampling values, not by build config.

Diagnostic prints in `lib.rs` currently use `eprintln!` directly
(e.g., `lib.rs:1100`). Those should be promoted to `log::debug!` so
they don't fire on production runs. Tracked as drive-by inside G11.

### 6.3 Worktree workflow

Create `decoder-hardening` worktree at repo root:

```
git worktree add ../rvp9-2-decoder-hardening decoder-hardening
```

Wave A items dispatched as agents into that worktree. Final merge to
`main` after Wave A complete is a single squash-or-rebase merge.

Wave B items can either share the same branch or fork off as needed.
Wave C items get their own branches (`decoder-simd`, `decoder-tile-mt`).

## 7. Decisions (resolved 2026-05-19)

1. **Wave C scope.** Both G4 (SIMD) and G5 (tile threading) ship in
   this hardening pass. Sub-sequenced as G4.1 → G5 → G4.2-G4.4 to
   avoid mid-flight kernel-file conflicts (see §4 for the full
   ordering and §5 G4/G5 for cross-references).
2. **Wave A merge target.** Single squash-merge after all five items
   (G1, G2, G3, G10, G11) are green in the `decoder-hardening`
   worktree.
3. **G8 corpus location.** Gitignored `third_party/corpus/`
   directory with a `scripts/fetch-corpus.ps1` documenting sources.
   Harness skips cleanly when the corpus is absent.
4. **G9 fuzz target depth.** Three targets to start
   (`fuzz_parse_packet`, `fuzz_decode_frame`, `fuzz_full_stream`).
   Expand if the first 24-hour bake produces unreachable bugs.
5. **G7 Profile 1 priority.** Middle of Wave B, standard scope.
   Treat as any other Wave B item; ~1 week of mechanical work to
   widen chroma subsampling through the decode pipeline.
