# HLD — Intra-prediction path optimization

**Date:** 2026-05-27
**Author:** design agent (intra-pred workstream)
**Status:** DRAFT — awaiting team-lead sign-off. **No production code changed.**
**Scope gate:** intra-prediction path only. Does NOT touch IDCT /
convolve / loop-filter (owned by `notes/decoder-libvpx-kernel-audit.md`)
or entropy/detokenize (owned by another agent).

---

## 0. TL;DR

The profiled 38 % intra-prediction cost is **structural per-block
overhead, not slow kernels**. Two measured root causes:

- **R1 — opaque per-block dispatch.** Every TX block routes through
  `intra_predict` → a `match` → an indirect `SimdDispatch` `fn`-pointer
  call. The DC-4×4 AVX2 kernel does **~2.3 ns of real work** but costs
  **~16–18 ns through the production dispatch** — the indirection is
  **~6–13 ns/call**, i.e. the dispatch overhead is 2.5–6× the kernel
  itself. This is exactly the "death by a thousand tiny calls" regime
  the team-lead flagged, and it is *opposite* to the large-kernel result
  in the concurrent kernel-audit (idct16x16 has 256 elements; here we
  have 16-pixel 4×4 blocks).
- **R2 — over-eager reference-array construction.** `build_intra_predictors`
  for the hot DC-4×4 both-available interior case costs **~9.7 ns/block**;
  the libvpx equivalent (`build_intra_predictors` in
  `third_party/libvpx/vp9/common/vp9_reconintra.c:263`) **does not copy
  the `above` row at all** for this case — it sets
  `const_above_row = above_ref` (a pointer straight into the plane) and
  only gathers `left_col`. The measured zero-copy reference is
  **~1.6 ns/block** → an **~8 ns/block** avoidable delta.

**H1 is CONFIRMED** with one important correction (see §3): the cost is
NOT "indirect dispatch is uniquely bad" — libvpx *also* dispatches
through a `fn`-pointer table. The cost is that **our path adds a second
layer of indirection** (the `intra_predict` match + slot accessor on top
of libvpx's single `pred[mode][txsz]` call) **and the indirection blocks
the compiler from inlining a 2 ns kernel**. **H2 is CONFIRMED** — the
zero-copy `above` fast path is the single largest avoidable per-block
cost in the edge builder.

Estimated reclaim: **~20–28 % of the 38 % intra bucket** (so the
headline 1080p ratio could move from ~4.8× toward ~3.8–4.2× on these
intra-heavy vectors), at **medium confidence**. Details + phasing in §5–7.

## 2. Measured root-cause: where the intra time goes

### 2.1 Call frequency & block-size distribution (per frame, t=1)

`vp90-2-08-tile_1x4.webm` (1920×1080 conformance keyframe) — **32 474**
`intra_predict` calls in one frame:

| mode | total | 4×4 | 8×8 | 16×16 | 32×32 |
|------|------:|----:|----:|------:|------:|
| DC   | 10610 | 5887 | 3084 | 1054 | 585 |
| V    | 3376  | 1506 | 1058 | 196  | 616 |
| H    | 3674  | 2491 | 983  | 175  | 25  |
| D135 | 4525  | 3375 | 961  | 143  | 46  |
| D153 | 4348  | 3431 | 844  | 71   | 2   |
| D207 | 1692  | 934  | 618  | 132  | 8   |
| TM   | 1587  | 737  | 502  | 97   | 251 |
| D117 | 1133  | 744  | 289  | 13   | 87  |
| D45  | 810   | 366  | 325  | 95   | 24  |
| D63  | 719   | 353  | 280  | 67   | 19  |

DC availability arm (DC only): **both=9979 (94 %)**, top-only=429,
left-only=192, none(128)=10.

`testsrc_1080p30.ivf` (1920×1080 keyframe) — **9 486** calls; DC=4535
(both=4060). Notable shape difference: testsrc's biggest DC cell is
**32×32 (1490)**, vs tile_1x4 where 4×4 dominates. Both are DC-heavy and
both-neighbour-dominated.

**Key takeaways for the design:**

- **4×4 blocks dominate by count** (tile_1x4: ~18 800 of 32 474 calls =
  58 % are 4×4). 4×4 is exactly where per-call overhead hurts most
  (16 pixels of work amortising a ~16 ns dispatch).
- **DC_PRED is the single hottest mode** (~33 % of calls), and **94 %
  of DC calls have both neighbours available** — the exact case libvpx
  zero-copies. The `dc_predictor_4x4` AVX2 slot (DC, 4×4, both) alone is
  5658 calls/frame on tile_1x4.
- The whole top-7 modes (DC/V/H/D135/D153/TM and friends) are
  size-parametric and all go through the same `intra_predict` dispatch
  + `build_intra_predictors` per call. The overhead is paid **32 474×
  per frame** regardless of mode.

### 2.2 Dispatch-vs-inline cost (DC 4×4, both available)

Three runs of the throwaway `intra4x4` microbench, ns/call:

| shape                                   | run 1 | run 2 | run 3 |
|-----------------------------------------|------:|------:|------:|
| (a) full `intra_predict` dispatch       | 18.40 | 15.85 | 17.11 |
| (b) `SimdDispatch` slot `fn`-ptr only   | 15.21 | 14.64 |  9.60 |
| (c) direct inline `dc_predictor_4x4_avx2` | 2.32 |  2.68 |  1.96 |

- **Indirection cost (b)−(c): ~7.6–12.9 ns/call.** An indirect call to a
  `#[target_feature]` leaf the compiler cannot see prevents inlining of
  the kernel's slice-bounds setup, `read_unaligned` loads, and the
  4-row store loop, and forces a real call/return + register spill.
- **`intra_predict` match + ctx build (a)−(b): ~1.2–3.2 ns/call.**
- **Real kernel work (c): ~2–2.7 ns/call.** The kernel is *not* the
  problem.

So the profiler's `dc_pred_4x4_avx2` 10.5 % self-time is a fast kernel
whose own frame (prologue/epilogue + the work the compiler couldn't
hoist into the caller) is inflated ~6–8× by being a non-inlinable
indirect callee invoked ~5.6 k×/frame.

### 2.3 Edge-builder cost (`build_intra_predictors`, DC 4×4, both, interior)

Two runs, ns/block:

| shape                                          | run 1 | run 2 |
|------------------------------------------------|------:|------:|
| ours (`build_intra_predictors`)                | 9.73  | 9.73  |
| libvpx zero-copy (left-gather only, no above-copy) | 1.62 | 1.62 |
| **delta**                                      | **8.11** | **8.11** |

Our edge builder always `copy_from_slice`s the `above` row into
`edges.above_data[16..16+bs]` and writes `above_data[15]` (the
top-left). For DC both-available interior blocks libvpx skips the
`above` copy entirely (`const_above_row = above_ref`,
`vp9_reconintra.c:337-338`) and the DC kernel reads `above` straight
from the plane. Our `EdgeBuffers` design forces a copy because the
predictor takes an `&[u8]` slice that must outlive the call and the
`above_data[15]` corner write requires a separate scratch buffer.

### 2.4 Per-frame arithmetic (tile_1x4, ties measurement → 38 %)

The edge builder runs for all 32 474 calls; the dispatch runs for all
32 474. Using the measured per-call deltas (conservative low ends):

- Dispatch indirection avoidable: ~8 ns × 32 474 ≈ **260 µs/frame**.
- Edge-builder `above`-copy avoidable on DC-both (≈10 k calls,
  ~8 ns each) plus smaller savings on other modes' interior fast
  paths: **~80–150 µs/frame**.
- Frame total decode ≈ 15 465 µs (t=1, this run). Intra ≈ 38 % ≈
  5 877 µs. The two avoidable buckets ≈ **340–410 µs**, i.e. **~6–7 %
  of frame time / ~16–18 % of the intra bucket** from these two alone.

The remaining intra time is the *unavoidable* prediction + edge-gather
work that libvpx also pays; closing toward parity means making OUR
unavoidable work look like libvpx's (inlined kernels, zero-copy
`above`), not eliminating prediction.

## 3. H1 / H2 verdicts

### H1 (dispatch overhead on tiny kernels) — **CONFIRMED, with a correction**

CONFIRMED that per-call dispatch overhead dominates the tiny-kernel
cost: 2 ns of work behind 16+ ns of dispatch (§2.2). This is the
opposite regime to the concurrent kernel-audit's idct16x16 finding, and
their large-kernel result does NOT generalise here — verified by direct
measurement, not assumption.

**Correction to the framing:** libvpx ALSO dispatches intra predictors
through a runtime `fn`-pointer table (`pred[INTRA_MODES][TX_SIZES]` and
`dc_pred[2][2][TX_SIZES]`, `vp9_reconintra.c:56-60`, populated once in
`vp9_init_intra_predictors_internal`). So "indirect dispatch" per se is
not what makes us slower than libvpx. Our excess is:

1. **A redundant second indirection layer.** libvpx: one indirect call
   `pred[mode][txsz](dst, stride, above, left)`. Ours: `intra_predict`
   does a `match (mode, bs==4)` AND a `dispatched_dc_4x4` branch, THEN
   calls a slot accessor that returns the `fn`, THEN indirect-calls it.
   The DC-4×4 path even double-dispatches (the `dc_predictor_4x4` slot
   *and* the `dc_predict_full`/`dc_predict_with_availability` router
   both exist).
2. **Our kernels are smaller per call than libvpx's amortise.** libvpx's
   SSE2 `dc_predictor_4x4` is the whole predictor; the indirect call is
   inherent and unavoidable for them too — but they don't wrap it in a
   Rust `match` + accessor, and their kernel body is hand-tuned asm with
   no Rust slice-bounds prologue.

The actionable lever is therefore **not "remove dispatch"** (libvpx
keeps it) but **"collapse our extra layers and let the small kernels
inline at the call site when the ISA is statically known"** (§4).

### H2 (reference-array construction) — **CONFIRMED**

CONFIRMED: ~9.7 ns/block vs libvpx's ~1.6 ns for the hot DC-both-4×4
interior case, an ~8 ns/block delta, driven by an unconditional `above`
memcpy that libvpx avoids via `const_above_row = above_ref`. We
over-copy; we do not over-bounds-check egregiously (the slow clipped
paths mirror libvpx 1:1 and are rare). The win is the zero-copy `above`
fast path, not bounds-check removal.

## 4. Proposed design

Two independent levers; either ships alone. Both preserve bit-exactness
(the scalar predictors remain the oracle; see §5). Neither changes the
`SimdDispatch` slot table shape used by other crates.

### Lever A — inline the hot small-block predictors at the reconstruct site

**Problem:** `intra_predict` is an opaque dispatcher; the hottest
predictors (DC/V/H/TM at 4×4 and 8×8) lose inlining behind the
`SimdDispatch` `fn`-pointer.

**Change:** introduce a *monomorphic* fast path in `intra_predict`
(`crates/rvp9-core/src/intra_pred.rs`) for the small, both-available
cases, gated on a statically-known ISA token rather than a runtime
`fn`-pointer. Concretely:

- Add an `#[inline(always)]` private helper
  `intra_predict_small_avx2(mode, dst, stride, bs, ctx, dc_avail)` that
  is `#[target_feature(enable = "avx2")]` and contains a `match` over
  the common (mode, bs) pairs calling the AVX2 kernel **bodies**
  directly (the `_inner` functions, made `pub(crate)`), so the compiler
  inlines the kernel into the match arm. No `fn`-pointer load.
- In `intra_predict`, when `dispatch.caps.avx2` is true and `(mode, bs)`
  is in the hot set (DC/V/H/TM × {4,8}, plus DC × {16,32}), call the
  `unsafe { intra_predict_small_avx2(...) }` wrapper. Otherwise fall
  through to the existing slot-based path unchanged.
- The `caps.avx2` check is a single branch hoistable out of the
  per-block loop in a later refinement; even per-call it is a predicted
  branch (monotonic for the process), far cheaper than the `fn`-ptr
  indirection it replaces.

This mirrors libvpx's effective behaviour: the kernel runs as a
contiguous inlined body, not a call through an opaque pointer. The
existing public `SimdDispatch` slots stay for the scalar/non-AVX2 path
and for external callers (tests, other crates) — nothing is removed.

**Functions changed:**
`crates/rvp9-core/src/intra_pred.rs` — add the inline fast-path helper
and the gate in `intra_predict`. AVX2 kernel `_inner` fns in
`crates/rvp9-core/src/dsp/x86_64/{dc_pred_4x4_avx2,dc_predict_full_avx2,
v_predictor_avx2,h_predictor_avx2,tm_predictor_avx2}.rs` get
`pub(crate)` visibility on their `_inner` (currently private) so they
can be inlined from the intra_pred module under a single
`#[target_feature]` umbrella.

### Lever B — zero-copy `above` for the interior fast path (H2)

**Problem:** `build_intra_predictors` unconditionally copies `above`
into `edges.above_data` even when the plane row above is directly
usable.

**Change:** in `build_intra_predictors`
(`crates/rvp9-core/src/intra_pred.rs`), when the block is interior
(`have_top && have_left && !right_clipped && !bottom_clipped`) and
`mode` needs only `NEED_ABOVE | NEED_LEFT` (DC/V/TM/D135/D117/D153 — the
non-aboveright modes), return a `PredCtx` whose `above` slice borrows
the plane row directly (`&dst_plane[above_ref_start - 1 ..]`, so index 0
is the top-left corner and `above` proper starts at index 1) instead of
copying into `edges.above_data`. The `left_col` gather is unchanged
(libvpx copies left too).

The cleanest expression: have `build_intra_predictors` (or a new
`build_intra_predictors_fast` interior variant) return a `PredCtx<'a>`
borrowing either `edges` (slow/clipped path) or `dst_plane` (fast path),
rather than always writing `edges` and then calling `edges.pred_ctx()`
at the call site. The call site in
`crates/rvp9-decoder/src/tile.rs::reconstruct_intra_planes` (line ~1104)
and `crates/rvp9-decoder/src/reconstruct.rs` adapts to consume the
returned ctx.

**Borrow-checker note (this is the real design risk):** the predictor
writes `dst` (the current block) and now also *reads* `above` from the
same plane (`dst_plane`). These regions never overlap (the row above a
block is never inside the block), but Rust's borrow checker cannot prove
disjointness of two slices into the same `&mut` plane. Options, in
preference order:

1. Compute the `above` byte range as indices and pass it through a
   small `AboveRef { Borrowed(range) | Edges }` enum, resolving the slice
   only inside the kernel call after the `dst` sub-slice is taken via
   `split_at_mut` at the row boundary. The row above the block lies in
   the `head` half of a `split_at_mut(block_row_start)`, `dst` in the
   `tail` half — disjoint and checker-provable.
2. If (1) is awkward at all sizes, keep the copy for the rarer larger
   sizes and apply zero-copy only to 4×4/8×8 where the row-split is
   trivial. (Most calls are 4×4 anyway — §2.1.)

**Functions changed:**
`crates/rvp9-core/src/intra_pred.rs` (`build_intra_predictors`),
`crates/rvp9-decoder/src/tile.rs` (`reconstruct_intra_planes` call
site), `crates/rvp9-decoder/src/reconstruct.rs` (`reconstruct_intra_block`
signature if it stops taking a pre-built `PredCtx`).

### Interaction with Lever A

If both ship, the inlined fast path (A) consumes the zero-copy ctx (B)
directly — the kernel reads `above` from the plane and writes `dst` in
one inlined body, exactly libvpx's shape. They compose but are
independently shippable; **recommend A first** (larger measured win,
smaller borrow-checker risk).

## 5. Testability / oracle plan

Bit-exactness is sacred. The plan rests on **three independent oracles**,
all already in-tree:

### 5.1 Differential oracle: scalar vs optimized (the primary gate)

The scalar predictors (`dc_predictor`, `v_predictor`, `h_predictor`,
`tm_predictor`, and the directional ones) in
`crates/rvp9-core/src/intra_pred.rs` are the **bit-exact reference**.
Every AVX2 kernel already carries a co-located scalar-vs-AVX2 proptest
+ directed fixtures (e.g. `dc_pred_4x4_avx2.rs` `mod tests`:
`dc_predictor_4x4_scalar_eq_avx2_proptest`, rounding-seam sweeps,
misaligned-dst guards, and a forced-scalar-vs-forced-AVX2
`dispatch_round_trip`). The new inline fast path (Lever A) must be
covered by a **new differential test** that drives the *inlined* path
and the *scalar* path with identical (mode, bs, above, left, above_left,
dc_avail) and asserts byte-identical output — same shape as the existing
`dc_predictor_4x4_dispatch_round_trip`, but exercising the new
`intra_predict_small_avx2` arm. Because the inline path reuses the same
`_inner` kernel bodies that already pass the per-kernel proptests, this
new test only needs to prove the *routing* (the `match` and the gate)
is correct, not re-prove the kernels.

For Lever B (zero-copy `above`), add a differential test in
`build_intra_predictors`' test module that builds the edges via the
**copy path** and via the **zero-copy path** for the same synthetic
plane and asserts the resulting `PredCtx.above[..2*bs]`,
`.left[..bs]`, `.above_left` are byte-identical across all
`(mode, bs, have_top, have_left, right_clipped, bottom_clipped)`
combinations. This is the property: *the borrowed `above` slice equals
what the copy would have produced*. A directed test for the interior
fast path plus a proptest over random planes + positions.

### 5.2 End-to-end oracle: the 201/201 conformance suite (the load-bearing gate)

`crates/rvp9-harness/tests/conformance.rs::conformance_runner_walks_all_vectors`
MD5s every decoded *visible* frame against the committed `.md5` sidecar
for all 201 vectors (`tests/conformance/vectors/`). It is the
non-negotiable gate: any per-pixel divergence in any frame of any vector
fails the test with a named offending frame index. The change is
accepted only if this stays **201/201, zero mismatches**. Run:
`cargo test --release -p rvp9-harness --test conformance`.

This is a genuine differential oracle (libvpx-produced MD5s vs our
output), independent of our scalar reference — so even a bug *shared*
between our scalar and AVX2 paths (which 5.1 would miss) is caught here.

### 5.3 Hidden-frame / structural oracle

The same conformance test cross-checks superframe sub-frame counts via
an independent re-parse (`expected_sub_frame_count`) — unaffected by
this change but confirms we don't perturb frame ordering. No new work;
listed for completeness.

### 5.4 Regression guard for the borrow rework (Lever B)

`split_at_mut`-based disjointness is a *safety* property, not just
correctness. Add a `cargo +nightly miri` run over the
`build_intra_predictors` zero-copy tests (the scalar edge path is
already miri-covered per the module note in `dc_pred_4x4_avx2.rs`).
Miri proves no aliasing-UB in the new borrow split. AVX2 kernels are
miri-excluded, but the *edge-builder* (Lever B) is scalar pointer
arithmetic and IS miri-checkable.

### 5.5 Performance oracle (confirm the win, prevent silent regressions)

Re-run the throwaway `intra4x4` microbench (re-applied for the
before/after comparison only) to confirm (a)−(c) collapses toward (c),
and re-run the samply profile per the journal recipe to confirm
`dc_pred_4x4_avx2` self-% drops and frame time falls. The committed
`decode-throughput` ratchet
(`crates/rvp9-bench/tests/decode_throughput_ratchet.rs`) guards against
a *regression*; the headline head-to-head ledger
(`bench/results/decode-headtohead.*`) records the *improvement*.

## 6. Risk assessment & estimated speedup

### Estimated speedup

- **Lever A (inline small predictors):** the dominant lever. ~8 ns/call
  avoidable × ~32 k calls/frame ≈ 260 µs of the ~5 877 µs intra bucket
  on tile_1x4 ≈ **~4–5 % of frame time, ~12–16 % of the intra bucket**.
  On testsrc (fewer, larger blocks) the per-call win is the same but
  fewer calls → smaller frame-% but same direction.
- **Lever B (zero-copy above):** ~8 ns/block on ~10 k DC-both calls +
  smaller wins on other interior modes ≈ 80–150 µs ≈ **~1.5–2.5 % of
  frame time, ~4–8 % of the intra bucket**.
- **Combined (they overlap slightly — both touch the same blocks):**
  **~20–28 % of the 38 % intra bucket reclaimed**, i.e. intra drops from
  ~38 % toward ~28–30 % of frame time, moving the 1080p t=1 ratio from
  ~5.9× toward roughly ~4.8–5.2×, and t=4 from ~4.8× toward ~4.0–4.3×.

These are intra-heavy keyframe vectors; on inter-dominated content the
intra bucket is smaller so the absolute win shrinks, but the gate is
these vectors (per the profiler journal §caveats), so the work is
legitimate for the /goal.

### Confidence: **MEDIUM**

- The *direction* is high-confidence: the microbench delta (a)−(c) is
  large (6–13 ns) and reproducible; libvpx's source confirms the
  zero-copy fast path exists and that inlined kernel bodies are the
  norm.
- The *magnitude* is medium-confidence: microbench ns/call does not
  perfectly predict in-situ ns/call (cache state, branch predictor
  warmth, and the `caps.avx2` gate branch all differ in the real loop).
  The translation from "8 ns/call microbench" to "260 µs/frame" assumes
  the saving fully realises in-context; it may be 50–80 % of that.
  Phase 1 (§7) de-risks this by measuring the real delta before
  committing to the full surface.

### Risks

1. **Bit-exactness break (HIGH severity, LOW likelihood):** the inline
   path or zero-copy borrow produces different bytes. Mitigated by §5.1
   diff-tests + §5.2 201/201 conformance as a hard merge gate.
2. **Borrow-checker friction on Lever B (MEDIUM):** the `dst`/`above`
   disjointness. Mitigated by the `split_at_mut` row-boundary approach
   (§4 Lever B) and the fallback to copy-for-large-sizes.
3. **`#[target_feature]` inlining doesn't materialise (MEDIUM):** the
   compiler may still not inline across the `target_feature` boundary as
   hoped. Mitigated by Phase 1 measuring the *actual* inlined-path
   ns/call before expanding the surface — if it doesn't beat the slot
   path, we stop.
4. **Maintenance / divergence from libvpx (LOW):** adding a parallel
   inline path risks the scalar and inline paths drifting. Mitigated by
   reusing the *same* `_inner` kernel bodies (no duplicated logic) and
   the diff-tests pinning them together.

## 7. Phasing (smallest-first, each independently shippable & measurable)

**Phase 1 — DC-4×4-both inline fast path only (proof of concept).**
The single hottest sub-case (5658 calls/frame on tile_1x4). Add the
inline `intra_predict_small_avx2` covering *only* `(DC, bs=4, both)`,
gated on `caps.avx2`. Reuse `dc_predictor_4x4_avx2_inner`. Add the §5.1
diff-test; run §5.2 conformance. **Measure** the real in-situ delta
(re-profile + microbench). This proves the inlining lever works in
context with the smallest possible diff (~30 LOC) before widening.
*Gate to proceed: measurable frame-time drop, 201/201 green.*

**Phase 2 — widen Lever A to the hot mode/size set.** Extend the inline
match to DC/V/H/TM × {4,8} and DC × {16,32} (the cells > ~500
calls/frame in §2.1). Same oracle set. Incremental measurement per
mode added.

**Phase 3 — Lever B zero-copy `above` (interior fast path).** Larger
blast radius (touches `tile.rs` + `reconstruct.rs` signatures + the
borrow rework). Ship after A is proven so the two wins are attributable
separately. Add §5.4 miri guard. Fall back to 4×4/8×8-only zero-copy if
the all-sizes borrow split proves awkward.

Each phase is a standalone commit with its own diff-test + conformance
run. If Phase 1 fails to show an in-context win, the whole effort stops
there with minimal sunk cost — the smallest-first ordering is the
de-risking mechanism.
