### DRAFT-BUG-1 — `--passes 2` silently ignores `--threads` and `--tile-columns`
- **Severity:** Medium · **Priority:** Should · **Area:** cli/rvp9enc option contract · **Confidence:** confirmed (lead + adversarial verifier, every hop read)
- **Where:**
  - `crates/rvp9-cli/src/bin/rvp9enc.rs:958-976` — `run()` returns straight into `run_two_pass(...)` when `opts.passes == 2`.
  - `crates/rvp9-cli/src/bin/rvp9enc.rs:982` — `build_encoder_parallelism(opts)` is called *after* that return, so it is unreachable on the two-pass path.
  - `crates/rvp9-cli/src/bin/rvp9enc.rs:1257` — `encode_two_pass(*config, &views)` takes no parallelism argument; `opts.threads` / `opts.tile_columns` are read nowhere else in the file (only at `:1571-1572`, inside the unreachable helper).
  - `crates/rvp9-encoder/src/frame_loop.rs:850` and `:892` — both the second pass and `gather_first_pass_stats` construct `StreamEncoder::new(...)`, which resolves through `:2065-2067` → `:2051-2054` → `:2033-2036` to `SINGLE_THREADED { max_threads: 1, requested_log2_tile_cols: 0 }`.
  - `crates/rvp9-core/src/bitstream/sub_parsers.rs:569-590` — `log2_tile_cols` is written into the VP9 frame header, so this is bitstream-visible, not merely a speed knob.
- **Defect:** `rvp9enc --passes 2 --threads 8 --tile-columns 2 …` encodes single-threaded and single-tile. The user's tiling request never reaches the bitstream, and the one-pass path's own defaults (8 threads / log2 6, `rvp9enc.rs:1569-1574`) silently become (1 / 0). No warning, no error. `--help` tags both flags `[supported]` unconditionally, because the tag derives solely from `apply.is_some()` (`crates/rvp9-cli/src/args.rs:150-159`, `:174-180`) and knows nothing about `--passes`.
- **Why it matters:** this is a narrow recurrence of the exact class RVP9-BUG-KILN-00050 closed — "a `[supported]` flag must change behaviour or fail loudly". The contract is stated in `crates/rvp9-cli/src/args.rs:8-12`. The codebase already has the guard pattern twice for this very path: `rvp9enc.rs:955-957` rejects spatial SVC under `--passes 2`, and `:859-876` rejects `--frame-time-csv` under it. Neither was extended to the parallelism flags.
- **Missing coverage:** no test exercises `--passes 2` together with `--tile-columns` or `--threads` (grep over `crates/rvp9-cli/tests/`: the only `--passes 2` tests are `cli_arg_coverage.rs:290, 311, 429`).
- **Fix:** thread `EncoderParallelism` through `encode_two_pass` (signature change, and it should reach both passes) and pass it from `run_two_pass`. If that is deferred, the immediate honest fix is to reject `--threads` / `--tile-columns` when `opts.passes == 2`, following `rvp9enc.rs:955-957`. Add a test asserting the emitted header's tile-column count under `--passes 2`.
- **Effort:** trivial for the reject-guard; small–medium (~half a day + test) for real plumbing.

### DRAFT-BUG-2 — `rvp9dec` writes one Y4M header, so a mid-stream resolution change silently corrupts the output
- **Severity:** Medium · **Priority:** Should · **Area:** cli/rvp9dec output correctness · **Confidence:** confirmed (lead + adversarial verifier)
- **Where:**
  - `crates/rvp9-cli/src/bin/rvp9dec.rs:430` — `y4m_header_written` initialised once, outside the packet loop.
  - `crates/rvp9-cli/src/bin/rvp9dec.rs:583-589` — the header is written from the **first** displayed frame's `buf.width()` / `buf.height()`, then the flag latches.
  - `crates/rvp9-cli/src/bin/rvp9dec.rs:609-628` — `visible_planes()` sizes each frame's planes from *that* frame's own dimensions.
  - `crates/rvp9-io/src/y4m.rs:535-541` — `write_frame` emits `FRAME\n` plus whatever-length slices it is handed; it has no dimension parameter and validates nothing.
- **Defect:** VP9 permits per-frame resolution changes on inter frames, and rvp9's decoder implements them (`crates/rvp9-core/src/inter/scale.rs`, the reference-rescaling port). `Yv12Buffer::width()/height()` (`crates/rvp9-core/src/frame.rs:383-392`) return each buffer's own crop, so they genuinely vary within one stream. Decoding such a stream with `--y4m` yields a header declaring the first frame's geometry followed by frames of a different payload length — every standard Y4M consumer misparses from the first resized frame onward. Nothing detects it; exit status is 0.
- **Repro (uses a vector this repo already names):** `rvp9dec --y4m -o out.y4m vp90-2-05-resize.ivf`. That vector is referenced at `crates/rvp9-decoder/tests/conformance_coverage.rs:238` ("Mid-stream resize (the only IVF vector)") and `crates/rvp9-harness/src/md5file.rs:12-16`, whose own comment states *"Some vectors switch resolution mid-stream … so the width/height vary across lines for the same vector."*
- **No workaround exists:** libvpx's remedy is `vpxdec --scale`, which normalises every displayed frame to the render size. `rvp9dec` accepts `--scale` / `-S` as a warn-only no-op (`rvp9dec.rs:256-266`, "output at coded size"), so the one mechanism that would mask this is explicitly unimplemented.
- **Raw output shares the flaw, arguably worse:** `--i420` / `--yv12` (`rvp9dec.rs:591-602`) concatenate variable-size frames with no framing at all, so a fixed-geometry consumer misparses with not even a `FRAME` tag to resync on.
- **Why the suite is green:** `dec_y4m_single_header_then_per_frame_tags` (`crates/rvp9-cli/tests/cli_arg_coverage.rs:2289-2317`) pins "exactly one YUV4MPEG2 header" on a constant-size clip — the assertion is correct for that fixture and stays green here. No CLI test decodes a resizing stream; the conformance suites that *do* use resize vectors drive `Decoder` directly and compare per-frame MD5s, never routing through the CLI's Y4M writer.
- **Fix:** cache the emitted geometry and, on a change, fail with a clear message naming the frame index and both sizes (the honest minimum, and consistent with this crate's fail-loud style). Implementing `--scale` is the complete fix. Either way, add a CLI test over a resizing vector, gated on the vector being present.
- **Effort:** small (~2 h + test) for the error; medium–large for `--scale`.

### DRAFT-BUG-3 — out-of-range `--min-q` / `--max-q` / `--cq-level` / `--noise-sensitivity` are silently clamped, not rejected
- **Severity:** Low · **Priority:** Could · **Area:** cli/rvp9enc input validation · **Confidence:** confirmed (lead read)
- **Where:** `crates/rvp9-cli/src/bin/rvp9enc.rs:1523` (`opts.noise_sensitivity.map(|v| v.min(6) …)`), `:1526`, `:1527`, `:1554` (three `.min(255)` clamps).
- **Defect:** `rvp9enc --max-q 2555` (a plausible typo for 255) is accepted and encodes at `max_qindex = 255`; `--noise-sensitivity 99` silently becomes 6. The same flag table rejects out-of-range values for `--cpu-used` (`:808-814`) and, via `parse_range` (`:838-844`), for `--auto-alt-ref`, `--tile-columns` and `--spatial-layers`. The inconsistency means a user cannot tell from behaviour whether a value was honoured.
- **Stale comment:** the test at `:1833-1841` asserts the clamp and comments that "the parser's range-check should catch this too, but the saturation guard is the defensive belt-and-braces". There is no parser range check for `--noise-sensitivity` — the comment documents a guard that does not exist, which is how this stayed invisible.
- **Fix:** route all four through the existing `parse_range` with their documented domains (`0..=255` ×3, `0..=6`), and correct the test comment. Keep the `.min()` calls as defence in depth.
- **Effort:** trivial (~30 min).

### DRAFT-BUG-4 — `--inter-layer-pred` is validated and then silently discarded unless `--spatial-layers > 1`
- **Severity:** Low · **Priority:** Could · **Area:** cli/rvp9enc option contract · **Confidence:** confirmed (devil's advocate, lead re-verified by grep + read)
- **Where:** `crates/rvp9-cli/src/bin/rvp9enc.rs:518-527` (parsed and range-checked to `0`/`3` unconditionally, stored at `:524`); `:1134` — the **only** read of `opts.inter_layer_pred`, inside `run_spatial_one_pass`, which `run()` reaches only when `opts.spatial_layers > 1` (`:983-993`). Default `spatial_layers` is `1` (`:128`).
- **Defect:** `rvp9enc --inter-layer-pred=3 …` without `--spatial-layers=2|3` parses, validates, and then has zero effect. Same class as DRAFT-BUG-1 — a `[supported]` flag that is silently inert on the path the user is actually on — and the same file rejects two other cross-flag violations explicitly (`:955-957`, `:859-876`), so the inconsistency is internal to one function.
- **Missing coverage:** every use of the flag in the suite pairs it with spatial layers — `crates/rvp9-cli/tests/cli_roundtrip.rs:99` (with `--spatial-layers 3`) and the unit tests at `rvp9enc.rs:1636` and `:1648`, the latter only asserting that values other than `0`/`3` are rejected. The "used without spatial SVC" path is unpinned.
- **Fix:** reject `--inter-layer-pred` when `spatial_layers == 1`, in the same place as the existing cross-flag guards.
- **Effort:** trivial.

### DRAFT-BUG-5 — every non-SVC CLI test fixture is square (64×64), so a width/height transposition is undetectable
- **Severity:** Low · **Priority:** Should · **Area:** cli/tests · **Confidence:** confirmed (devil's advocate, lead re-verified by direct read)
- **Where:** `crates/rvp9-cli/tests/cli_arg_coverage.rs:33-34` and `crates/rvp9-cli/tests/cli_roundtrip.rs:24-25` — both declare `const W: usize = 64; const H: usize = 64;`, and nearly every test in both files builds on that fixture (one-pass and two-pass encode, `--md5`/`--framemd5`, `--limit`/`--skip`, and all four decoder output formats). The sole non-square fixture in the crate is `spatial_svc_cli_emits_three_component_access_units_and_decodes_top_layer` (`cli_roundtrip.rs:72-73`, 256×128), which exercises only `run_spatial_one_pass`.
- **Defect:** a fixture whose width equals its height cannot distinguish a correct dimension from a swapped one. A transposition or a stride computed from the wrong axis in `open_input`, `RawFrameReader`, the one-pass `YuvFrameRef` construction (`rvp9enc.rs:1026-1034`), the two-pass one (`:1245-1254`), or `rvp9dec`'s `visible_planes`/`write_frame` would pass the entire CLI suite. This is the "fixture whose fields all hold the same value" class CLAUDE.md calls out — the tests are green but prove less than they appear to.
- **Fix:** change `W`/`H` to distinct values (e.g. 128×64) in both files. Non-mechanical only where a test hard-codes `FRAME_BYTES` arithmetic, which is already derived from `W`/`H`. Worth doing once rather than adding a parallel non-square fixture.
- **Effort:** small (~1–2 h, mostly re-running the suite — which this session could not do).

## Confirmed design finding — req draft (to mint via `deltic reqs new`, Draft for Gate-1 triage)

### DRAFT-REQ-1 — every `[supported]` rvp9enc flag must be proven to reach the encoder on every encode path
`crates/rvp9-cli/src/args.rs:8-12` states the crate's central contract: `apply: Some` means wired, `apply: None` means fail-loud, and `--help` derives its tag from the same field so "the docs can never drift from reality". The contract is only half-tested. `enc_parse_only_flags_reject_and_are_tagged_not_yet` (`crates/rvp9-cli/tests/cli_arg_coverage.rs:812-886`) covers the `apply: None` direction thoroughly — 35 flags, exit code plus `[not yet]` in real `--help` output. The `apply: Some` direction is covered only by per-flag PROOF unit tests that call `build_encoder_config_for_test` (`rvp9enc.rs:1580-1588`), i.e. they prove the *one-pass* mapping and nothing else. `rvp9enc` now has three encode paths — one-pass (`run()`), spatial SVC (`run_spatial_one_pass`), two-pass (`run_two_pass`) — and DRAFT-BUG-1 and DRAFT-BUG-4 are both consequences: a flag correct on one path is silently inert on another, which is the class RVP9-BUG-KILN-00050 was closed on, recurring twice on paths added afterwards. Two independent instances found in one pass is the argument for the oracle. What is wanted is a mechanical oracle rather than another audit: enumerate the flag table, and for each `apply: Some` entry assert either that it reaches the encoder on every path or that the path rejects it explicitly. Priority: Should. Flow: heavy (per `reqs/README.md`, `light` stays disabled for RVP9).

## Report-only notes (confirmed, below the ledger bar)

- **Unreachable branch in the decode loop** — `crates/rvp9-cli/src/bin/rvp9dec.rs:467-472`: the `emitted >= lim` guard can never fire. The loop breaks at `:524-526` the moment `emitted == lim`, and the loop is entered only when `limit != Some(0)` (`:432`), so `emitted < lim` holds at every iteration top. Harmless, but it reads as if it were load-bearing flow control. Delete it or add a comment.
- **Partial IVF after a failed encode** — `rvp9enc.rs:1019-1021` creates and header-writes the output before the first frame is encoded, and `IvfStreamWriter::finish` (`crates/rvp9-io/src/container.rs:490-496`) is what patches the frame count, so a mid-encode failure leaves a file whose header claims 0 frames. **Already Open as RVP9-BUG-KILN-00065** — verified still present, not re-filed.
- **Two-pass holds the whole input in RAM** — `rvp9enc.rs:958-976` collects every source frame before encoding (`try_reserve`, so it errors rather than aborts). Not re-filed: the closure of RVP9-BUG-KILN-00053 explicitly permitted whole-sequence residency for the two-pass driver.
- **No end-of-options separator** — `crates/rvp9-cli/src/args.rs:82-116` has no `--` handling, so an input path beginning with `-` is unreachable and a bare `--` reports `unknown option '--'`. Matches vpx tooling closely enough to be low priority.
- **Per-frame allocation on the pixel-output path** — `rvp9dec.rs:609-628` allocates three fresh `Vec`s per displayed frame. Only on the `--y4m`/`--i420`/`--yv12` path (`--md5`/`--noblit` skip it), so it does not touch the decode-throughput ratchet. Reuse the buffers if this path is ever timed.
- **A value-taking flag swallows the next token even when that token is a live flag** — `crates/rvp9-cli/src/args.rs:137-146`: `rvp9enc --output --verbose in.y4m` sets `output = "--verbose"`, silently drops `--verbose`, and writes the IVF to a file literally named `--verbose`. This matches GNU/POSIX `getopt` semantics for required-argument options (and libvpx's own parser), so it is **not** filed as a defect — but it is untested: every "missing value" test in the suite (`cli_arg_coverage.rs:2256-2284`, `cli_roundtrip.rs:435-477`) puts the flag last, so the "value is itself a flag name" case is never exercised for any string-valued option. Numeric options self-correct via the `parse::<T>()` failure; `--output`/`-o` and `--frame-time-csv` do not.
- **`StreamEncoder::new`'s error wrapper appends a geometry note to every failure** — `rvp9enc.rs:994-999` (and `:1258-1262` for two-pass) suffixes *any* construction error with "coded width must be a multiple of 64 and coded height must be positive and even". So `rvp9enc --min-q 200 --max-q 10 …` fails with a message about frame dimensions, which is actively misleading. Make the note conditional on the error kind.
- **`--auto-alt-ref`'s `0..=6` range is finer than the behaviour** — `rvp9enc.rs:557-565` validates the full range, but `:1546` collapses it to `enable_alt_ref: v > 0`, so `1`..`6` are one indistinguishable bucket. The in-code comment admits this and `reaudit3_auto_alt_ref_plumbs_into_encoder_config` (`:2016-2040`) pins it deliberately — but `--help`'s "auto alt-ref frames (0..=6)" and the field doc at `:77-79` ("2+ enables multi-layer ARF") still read as though values 2–6 do something graduated. A help-text wording fix.
- **The "existing destination untouched" comment is scoped tighter than it reads** — `rvp9dec.rs:411-414` promises that container/packet/decode failures leave an existing `-o` file alone. True only *before* the first displayable frame: the sink is created (truncating) at `:499-501`, so a decode failure on a later packet (`:439-454`) leaves the destination truncated and partially rewritten. Inherent to streaming output and not filed as a defect, but the second sentence of that comment should say "before the first emitted frame". The existing test `dec_invalid_vp9_preserves_existing_output_file` (`cli_arg_coverage.rs:1916-1950`) covers only the pre-first-frame case.
- **Two-pass does not share KILN-00065's exposure** — worth noting when that bug is fixed: `run_two_pass` buffers packets and calls `write_ivf` (`crates/rvp9-io/src/container.rs:533-541`), which writes the true count up front and touches the filesystem only after the encode succeeds. The streaming one-pass and spatial paths are the exposed ones.

## Unverified (explicitly not confirmed, not reported as findings)

- **`--limit 0` parity with libvpx.** In rvp9, `--limit 0` means "emit nothing": `rvp9dec`'s loop guard (`rvp9dec.rs:432`) never enters, and `rvp9enc` fails with "input contained no frames" (`:934`) — the same message a genuinely empty input produces, since both readers honour `limit = 0` by yielding zero frames (`:1382-1384`), so the two causes are indistinguishable to the user. My recollection is that vpxenc/vpxdec treat `limit == 0` as *unlimited*, which would make this a parity divergence — but the libvpx submodule is **not** checked out in this worktree (`third_party/libvpx/` absent), so I could not read `vpxenc.c` / `vpxdec.c` to confirm. Deliberately not filed. Next pass with the submodule present should settle it, and should also distinguish the two error messages.
- **Partial-write behaviour of `write_ivf`** — the two-pass path writes `num_frames` before the packet bodies (`crates/rvp9-io/src/container.rs:533-541`), so a mid-write I/O failure (disk full) would leave a header overstating the body. Raised speculatively by the devil's advocate; forcing it needs I/O fault injection, which was not possible here. Also out of this area (`rvp9-io`). Not filed.
- **Two-pass temporal-SVC parity** — `opts.temporal_layers` reaches the shared `EncoderConfig` on every path (`rvp9enc.rs:1559`), but whether the two-pass driver honours it identically to the one-pass driver was not traced into `rvp9-encoder`. A question, not a demonstrated defect.

## Not reported (refuted or duplicate)

- *rvp9enc leaves a truncated IVF on failure* — real, already Open as RVP9-BUG-KILN-00065.
- *Two-pass whole-sequence memory residency* — real, explicitly accepted in RVP9-BUG-KILN-00053's closure.
- *`--summary` counts skipped frames in "showed frames"* — deliberate: pinned by `dec_summary_reports_skipped_and_emitted_counts` (`cli_arg_coverage.rs:2409-2432`) as vpxdec byte-compatibility, and documented at `rvp9dec.rs:536-555`.
- *Raw reader mis-sizes chroma for odd `-w`* — `RawFrameReader::open` uses `(width/2)*(height/2)`, which is wrong for an odd width, but `StreamEncoder::new` rejects any width that is not a multiple of 64 before a frame is consumed, so the state is unreachable.
- *`--temporal-layers` unrange-checked at the CLI* — the encoder validates it (`crates/rvp9-encoder/src/frame_loop.rs:339-356`) and the CLI comment says so; behaviour is fail-loud.
- *A required-argument flag swallowing the next flag as its value is a parser bug* (devil's advocate) — mechanism confirmed, **defect refuted**: this is standard GNU/POSIX `getopt` behaviour for required-argument options and matches libvpx's own parser. Kept as a report-only note for the untested case.
- *rvp9dec truncating an existing `-o` file on a late decode failure violates its documented contract* (devil's advocate) — behaviour confirmed, **defect refuted**: the comment at `rvp9dec.rs:411-414` scopes the guarantee to "until a decoded frame is ready to emit", and truncation after the first emitted frame is inherent to streaming output. The residual is a one-sentence doc imprecision plus a test gap, kept as a note.
- *rvp9enc leaving a `num_frames = 0` IVF after a mid-stream failure* (devil's advocate) — real and correctly diagnosed, but it is RVP9-BUG-KILN-00065, already Open. The new detail (two-pass is not exposed) is recorded as a note.
