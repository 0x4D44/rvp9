## §1 One-line summary

Add a **second, dedicated `WorkerPool`** (the `LfWorkerPool`) of `N` LF worker threads (default `N=2`), spawned at decoder construction. Per frame, the existing 4-worker decode pool runs tile-decode jobs as today; the new LF pool is dispatched **concurrently** with decode entry, consuming `decode_progress[r]` per SB row (Invariant L1 — LF row `r` begins only after `decode_progress[r+1] == num_tile_cols`). On a host with `available_parallelism ≥ decode_threads + lf_threads + 1`, the OS schedules them in parallel and LF overlaps decode wall, hiding ~507µs (1014µs / 2 LF threads) behind the 1208µs decode critical path. Modeled reclaim: ~22%; honest expectation after deflation: **8–15%**.

**This is the same Invariant L1 / column-wavefront LF kernel as the just-missed single-scope HLD.** The only difference is *which thread set* runs the LF jobs.

## §2 The mechanistic case (what differs from the in-pool overlap miss)

### §2.1 What the prior overlap lever actually did, and why it missed

The signed-off `Reduce t4 worker idle` HLD submitted LF jobs into the *same* `WorkerPool::scope` channel as the decode-tile jobs. With `num_decode_threads = 4`, `num_tiles = 4`, `num_lf_workers ≤ 4`, the FIFO crossbeam channel held up to 8 jobs ready to run. The expected behaviour was "as a worker finishes a tile it picks up an LF job". The closing diagnostic (`JRN - Final consolidation §"UPDATE — 6th investigation"`) verified the impl *correctly* used the recommended row-dispatch primitive (the column-wavefront, L1 gate, yield-spin) and *still* missed because:

- The 4 decode-tile jobs each run an **entire tile-column to completion** (~1208µs critical path, no sub-tile preemption point — a tile job is a single closure that walks all its SB rows in raster order).
- All 4 workers are pinned in the decode-tile job set for the full ~1208µs.
- LF jobs sit waiting on the channel; they only get picked up after the *first* decode-tile job completes (~1200µs into the frame).
- By that point, only ~30µs of tile imbalance remains for LF to overlap → empirical reclaim = 1.5–2%, below the 5% gate.

The mechanism is **worker-set starvation**: an LF job cannot run until a member of the shared worker set is free, and decode jobs hold them all until they finish.

### §2.2 Separate pool: workers cannot starve each other

With two pools — `WorkerPool` (4 decode workers) and `LfWorkerPool` (2 LF workers) — the two job classes have **physically distinct worker threads**. The LF threads sit parked at their own `crossbeam_channel::recv()`. The instant the main thread (or a decode worker) dispatches an LF batch, the OS scheduler runs them on whatever logical cores are idle; it does *not* need a decode worker to free up first.

The pipelining argument from the prior HLD now actually pipelines:
- t = 0: main dispatches decode jobs + LF jobs.
- t = 0+: 4 decode workers start tiles; 2 LF workers wake and spin on the L1 gate (`decode_progress[r+1] >= num_tile_cols`).
- t ≈ τ₀ (first SB-row of every tile complete): LF workers find L1 holds for `r = 0`, start filtering row 0 of the column-wavefront, then row 2, row 4, … (static row distribution).
- t ≈ decode_crit_path (1208µs): all decode work done; LF has been chewing trailing rows in parallel.
- t ≈ max(decode_crit_path, LF_wall_on_N_threads): both drained.

**The job-class blocking is broken by physical thread separation, not by a smarter row-claim policy.** The diagnostic verdict was clean about this: changing the row-claim within the same pool cannot help; changing the pool topology can.

### §2.3 The libvpx precedent — exactly what we are replicating

`third_party/libvpx/vp9/decoder/vp9_decodeframe.c:2027-2151` builds a **single dedicated `lf_worker`** (`pbi->lf_worker`, a `VPxWorker` with its own OS thread on `max_threads > 1`) and launches it once per tile-row from inside the `mi_row` decode loop:

```c
// vp9_decodeframe.c:2123-2140 (paraphrased)
if (cm->lf.filter_level && !cm->skip_loop_filter) {
  const int lf_start = mi_row - MI_BLOCK_SIZE;   // delay by 1 SB-row — INVARIANT L1
  LFWorkerData *const lf_data = ...;
  if (lf_start < 0) continue;
  winterface->sync(&pbi->lf_worker);              // wait for prior LF chunk
  lf_data->start = lf_start;
  lf_data->stop = mi_row;
  if (pbi->max_threads > 1) winterface->launch(...);   // async: separate OS thread
  else                       winterface->execute(...); // sync: same thread
}
```

That is the libvpx non-row_mt overlap topology: ONE separate LF thread, owned for the lifetime of the decoder, launched per SB-row chunk while the decode thread is still chewing tiles in `decode_tiles`. Our analogue is `LfWorkerPool` with N ≥ 1 threads instead of 1, driving the *column-wavefront* worker we already landed (Lever B v2) instead of libvpx's serial-per-row `loop_filter_rows`.

The libvpx **row_mt** path (`vp9_thread_common.c:loop_filter_rows_mt`, line 157) *re-uses* the tile-decode worker pool — which is exactly the topology the just-missed HLD tried, and which libvpx's own comment (line 184: "the decoder is capping num_workers because … using more threads on the loopfilter than there are cores will hurt performance") confirms is the topology that *needs* same-pool gating. **Libvpx itself uses the separate-pool path for the non-row_mt overlap.** We are choosing the separate-pool path.

### §2.4 Cores-available math on our hosts

Two host classes matter:

| host | physical cores | logical threads | (4 decode + N=2 LF) ≤ logical? | safety margin |
|------|----------------|-----------------|-----------------------------|---------------|
| Team-lead profiling box (4-core, agent quotes "4 worker threads") | 4 | 4–8 (depends on HT) | 6 ≤ 8 ✓ if HT; **6 > 4 ✗ if no HT** | thin |
| Sub-agent dev host (8P + 16E hybrid Alder/Raptor) | 8P + 16E = 24 | 24 | 6 ≤ 24 ✓ | huge |
| Generic 4-core no-HT dev box | 4 | 4 | **6 > 4 ✗ oversubscribed** | none |

**On the team-lead's 4-core profiling box (the one the PGO ship gate runs on), the margin is thin or zero.** This is the central feasibility question. See §4.1 risk (a)+(b) for the implications. We must:

1. Default `N_LF = min(2, available_parallelism − num_decode_threads − 1)`. On a 4-physical-core host with HT (8 logical), this is 2; on a 4-core no-HT host, this is 1 or 0 (kill the overlap, fall back to two-scope).
2. Gate enablement on `available_parallelism ≥ num_decode_threads + N_LF + 1`. Below that threshold, the LF pool is constructed but never dispatched; the decoder falls back to the existing two-scope (serial-after-decode) path. Default: overlap OFF.
3. The PGO ship gate runs on the team-lead's box. If that box has SMT/HT (likely on modern Intel/AMD), 8 logical threads ≥ 6 needed; survives. If not, the gate measures the fallback path and we shelve. **This is verifiable at sign-off time.**

## §3 Design — the new `LfWorkerPool` and its lifecycle

### §3.1 Pool topology

Add to `crates/rvp9-core/src/tile_threading/`:

- `lf_pool.rs` — `LfWorkerPool` mirrors the existing `WorkerPool` but is purposed for LF jobs. The implementation is structurally identical: long-lived `JoinHandle<()>` worker threads, an unbounded `crossbeam_channel::Sender<WorkerJob>`, and a per-frame scope mechanism that joins all dispatched jobs before returning. We do **not** refactor `WorkerPool` into a generic — copy-and-specialise keeps the soundness review small and avoids touching the existing decoder→`WorkerPool::scope` call graph.

- `Decoder::worker_pool: WorkerPool` stays as-is (4 threads, decode-only).
- `Decoder::lf_worker_pool: Option<LfWorkerPool>` is new. `Some(pool)` when `num_threads ≥ 2` AND the cores-available check passes (§2.4); `None` otherwise.

### §3.2 Lifetime

- **Construction:** `Decoder::new` allocates the LF pool once. Worker threads spawn immediately (eager, mirroring `WorkerPool::new`) and park at `recv()` until the first frame.
- **Per-frame:** the decoder opens both scopes simultaneously, see §3.3. No per-frame thread creation, no per-frame channel allocation. The only per-frame cost is `Sender::send` × N_LF (job dispatch) + the channel recv-wake on each LF worker.
- **Teardown:** `Drop` for `LfWorkerPool` is identical to `WorkerPool::Drop` — drop the sender, every worker's `recv()` returns Err, threads exit, join handles drained.

### §3.3 Per-frame integration — the dual-scope structure

The decoder today (post-Lever-B-v2) has two sequential scopes for `decode_inter_frame` / `decode_intra_frame_inner`:

```rust
// today
worker_pool.scope(|s| { for tile: s.submit(decode_tile) });   // JOIN — decode-only scope
... serial merge ...
apply_loop_filter_to_frame_dispatching(...) {
    worker_pool.scope(|s| { for w: s.submit(lf_worker) });    // JOIN — LF-only scope (re-uses same pool)
}
... border ...
```

Proposed (flag-gated, default OFF):

```rust
// new — flag = RVP9_LF_OVERLAP_POOL
let (decode_outcome, lf_outcome) = thread::scope(|os_scope| {
    let lf_handle = os_scope.spawn(|| {
        lf_worker_pool.scope(|lfs| {
            for w in 0..num_lf_workers {
                lfs.submit(|| run_split_edge_lf_worker(&state_w, &dispatch));
            }
        });
    });

    let decode_result = worker_pool.scope(|s| {
        for tile in tiles { s.submit(decode_tile_job); }
    });

    // implicit join on lf_handle at thread::scope close
    decode_result
});
... serial merge (counts/seg/mv merge already happens after decode scope) ...
... border ...
```

Three things to note:

1. **The main thread dispatches both pools and then blocks on `worker_pool.scope` (decode).** The LF pool runs `LfWorkerPool::scope` on a `std::thread::scope`-spawned helper thread. That helper thread *itself* is what calls `lf_worker_pool.scope`, blocks on its drain, then returns. The total thread count is `1 main + 4 decode + 1 helper + N_LF LF = 6 + N_LF`. With N_LF = 2: 8 threads. The helper thread does nothing but channel-send and block — its CPU cost is negligible.

2. **Why a helper thread to drive `LfWorkerPool::scope`?** Because `WorkerPool::scope` is a *blocking* call from the dispatcher's perspective (it drains the done-channel before returning, which is what guarantees the `'frame` borrow is sound). The main thread cannot itself `lf_pool.scope(...)` and `worker_pool.scope(...)` in parallel without somehow concurrently calling two blocking methods. The helper thread isolates the LF scope's drain loop while the main thread is in the decode scope's drain loop. This is the *only* new piece of orchestration; everything else reuses existing primitives.

3. **Alternative considered and rejected:** add a non-blocking `LfWorkerPool::dispatch(&self, jobs) -> LfBatchHandle` API where `LfBatchHandle::join(self)` is called after `worker_pool.scope` returns. This avoids `std::thread::scope` entirely. **Defer to implementation; whichever is simpler given the existing scope.rs lifetime machinery.** The helper-thread variant is conceptually equivalent and reuses 100% of the existing pool/scope code.

### §3.4 The data the LF pool needs

`ColumnWavefrontLfState` (already exists, `apply.rs`) carries the `SharedFrame` (raw pointers + lengths), the resolved filter levels, the `RowMaskInputs` slice references, and the `cur_sb_col` atomic vec. To this we add (from the just-missed HLD, unchanged):

```rust
pub struct ColumnWavefrontLfState<'a> {
    // ... existing fields unchanged ...
    /// L1 gate: published by tile workers via fetch_add(Release) once per SB row.
    /// LF row r blocks until decode_progress[r+1] >= num_tile_cols.
    pub decode_progress: Option<&'a [AtomicU32]>,
    pub num_tile_cols: i32,
    pub lf_delay: i32, // = 1 — see Invariant L1 §4
}
```

The `Option` is so the same struct serves both the dormant two-scope path (`decode_progress = None`, L1 trivially holds) and the new overlap path (`Some(slice)`, L1 spins on the gate). The `decode_progress[]` slice and `num_tile_cols` are owned by the per-frame allocations the decoder already makes (`AtomicU32` vec created fresh per frame at `lib.rs:2703` inter / matching intra; the prior HLD's "hoist" requirement still applies — see §6.4).

### §3.5 Pool sizing and the cores-available check

```rust
// At Decoder::new()
fn lf_pool_size(num_threads: NonZeroUsize, available: usize) -> Option<NonZeroUsize> {
    // Match libvpx vp9_thread_common.c:170 cap, then guard against
    // oversubscription on low-core hosts.
    let max_lf = num_threads.get();          // never more than decode-thread budget
    let want_lf = max_lf.min(2);             // default 2; tunable
    let budget = available.saturating_sub(num_threads.get() + 1);
    let n = want_lf.min(budget);
    NonZeroUsize::new(n)
}
```

- `num_threads = 4`, `available = 24` (sub-agent host): N_LF = 2 ✓.
- `num_threads = 4`, `available = 8` (team-lead host with HT): N_LF = 2 ✓ (8 − 4 − 1 = 3 ≥ 2).
- `num_threads = 4`, `available = 4` (4-core no-HT): N_LF = 0 → `None` → overlap unavailable, fall back to two-scope.
- `num_threads = 1`: N_LF = 0 (no overlap with single-thread decode).

The cap of `2` is mechanistic: column-wavefront LF on 1080p achieves ~2.22× speedup from 4 workers (HLD §2). At N_LF = 2, we get the bulk of the parallelism for half the thread count and a much smaller cores-available budget. N_LF tuning (1 vs 2 vs 4) is a Phase 1 measurement, not a design commitment — measure during the PGO A/B.

### §3.6 Park-vs-spin at the gate

The just-missed HLD's §3.4 analysis transfers verbatim:

- **Intra-LF column wavefront gate (`cur_sb_col[r-1] >= c + nsync`)**: sub-microsecond wait under a healthy wavefront → atomic + tight spin, no park.
- **New L1 decode-progress gate (`decode_progress[r+1] >= num_tile_cols`)**: at LF-pool *dispatch* the LF workers start spinning on row 0's gate while decode is just beginning row 0 — wait could be tens of µs (first SB row of one tile). Spin with `yield_now()` after a budget of 256, exactly like the existing wavefront gate. The expected wait per row is `~max_tile_first_row_decode_time` ≈ 70µs (one SB row × 4 tiles' worst-case imbalance); spin-yield holds the thread on the core, OS schedules a decode job onto the freed slot via `yield_now`.

**DO NOT park/condvar** (Lever-B-v2 §10 #4): Windows `NtWaitForAlertByThreadId` round-trip is ~5–15µs per wake. At 4 wakeups/frame × N_LF × 2 events (job dispatch + L1 unblock) we'd burn 80–120µs/frame on park overhead — eating ~25% of the 448µs reclaim budget. The atomic + yield-spin protocol survives the analysis; park does not. (See §4 risk (c).)

## §4 Honest pre-mortem (the load-bearing section)

Track record: **4 of 5 prior structural attempts missed under PGO.** Models were systematically optimistic. Below is a ruthless walk through the four candidates the team-lead asked me to address, with quantitative loss budgets.

### §4.1 (a) Windows hybrid P/E scheduling — the wild card

Alder/Raptor Lake schedules threads via the Hardware Thread Director: under Windows 11, ready threads on the "performance" SCHED class go to P-cores first, then E-cores, then SMT siblings. Our worker threads use the default scheduling class. With 4 decode + 2 LF = 6 active threads on an 8P+16E host, in steady state we expect:

- 4 decode threads on 4 P-cores (P-cores 0-3).
- 2 LF threads on **either P-cores 4-7 OR E-cores 0-15** depending on what the scheduler is doing with foreground/background.

**E-core SIMD throughput** (Gracemont): ~0.5–0.7× P-core for AVX2-heavy code; for the LF kernels specifically (lpf_v8/h8/v16/h16, all AVX2), this means LF wall on N_LF=2 E-cores would be `1014µs / 2 / 0.6 ≈ 845µs` instead of 507µs.

`max(1208µs decode, 845µs LF) + 363µs serial = 1571 vs 1571` — luckily the decode crit path still dominates, so an E-core demotion of the LF pool *does not break the model* on this fixture. But:

- If decode were faster (e.g. tile_1x4 fixture with PGO 21% boost, single tile) we'd flip to LF being the long pole and lose the reclaim.
- On the team-lead's 4-core profiling box (homogeneous, no E-cores), this risk evaporates but the cores-available margin becomes the constraint.

**Risk magnitude:** Medium. **Loss budget:** Up to 100µs of reclaim if LF lands on E-cores AND decode_crit drops. On the headline fixture under PGO (decode_crit ≈ 1208µs holding), survivable. Mitigation: use `SetThreadInformation`/`SetPriorityClass` to nudge LF threads to high-IPC class — out of scope for Phase 1, optional Phase 2. **Honest read:** I cannot rule out a measurable hit, but the model has slack on this fixture.

### §4.2 (b) Cache thrashing between decode and LF threads on the frame buffer

LF reads pixels the decode threads just wrote (row r-1's reconstructed pixels) and writes back over them. With decode and LF threads physically separated and running concurrently, the LF read of row r-1 happens while decode writes row r+1. Sharing patterns:

- **L1 (32–48KB per core):** disjoint. Each thread has private L1. No coherence traffic until eviction.
- **L2 (1.25MB per P-core on Alder Lake):** disjoint (private). Row r-1 luma (1920×16B = 30KB) fits comfortably; written by decode worker on P-core X, read by LF worker on P-core Y → fetched into Y's L2 via L3.
- **L3 (24MB shared):** the producer-consumer chain decode-writes → L3-evicts-from-private-L2 → LF-reads-from-L3 is the actual hot path. On modern Intel, L3 access is ~10–30 cycles vs ~4 cycles L1 hit; this is "free" relative to the work, especially because the per-pixel LF kernel cost dominates the load latency.

**Counter-argument that's stronger than I'd like to admit:** Today, the decode worker writes row r-1 and the *same worker* (in the LF scope) reads it back — peak temporal locality (still warm in L1 or L2 if the LF scope opens soon after). With separate threads, the warm cache is on a different core; the LF thread must pull through L3. This is *exactly* the same penalty libvpx accepts in its non-row_mt overlap topology (separate lf_worker thread) and has been measured to net-win there.

**Risk magnitude:** Low–Medium. **Loss budget:** 20–40µs/frame of additional L3 round-tripping vs the warm-cache same-worker case. Material relative to the 448µs reclaim ceiling but not catastrophic. **Honest read:** This shrinks the reclaim, but not below 5% on the modeled headline.

### §4.3 (c) Thread park/wake overhead on short LF work

LF wall on N_LF=2 = ~507µs (work). Per-frame, the new overlap topology has:

- **Dispatch**: main thread (or helper) `Sender::send` × N_LF = 2 sends. crossbeam-channel does a `Mutex` + `Condvar::notify_one` (or equivalent atomic CAS + `NtAlertThreadByThreadId` on Windows). Cost per send when receiver is parked: ~3–8µs.
- **Drain (join)**: when each LF worker completes, it `Sender::send(WorkerOutcome)` on the per-scope done channel. The helper thread's `recv()` wakes. Cost: ~3–8µs per worker × 2 workers = 6–16µs.
- **L1 gate spin-then-yield**: tight loop, sub-µs per check. Bounded by SPIN_YIELD_THRESHOLD = 256 then `yield_now()`. `yield_now()` on Windows is `SwitchToThread` — ~1–3µs context-switch if there's a ready thread, near-zero otherwise.

**Total park/wake budget per frame:** 2 dispatches × 8µs + 2 joins × 8µs + ~8 yield_now ticks × 2µs = ~40µs. Against a 448µs reclaim ceiling: **8.9% of the reclaim** eaten by overhead.

This is the candidate the user flagged as "borderline if ≥20µs/frame, 4 wakeups eats 80µs of the 448µs". I'm coming in at ~40µs upper bound. **It's not lethal but it's not free.**

**Risk magnitude:** Medium. **Loss budget:** 30–50µs/frame. Subtracting from the 448µs ceiling: realistic reclaim drops to ~400µs ≈ 19.8% of wall (still well above 5%).

**Filter_level == 0 frames (30% of testsrc):** these frames have no LF work. With the new overlap path, the LF pool still gets dispatched (sees zero rows, returns immediately) → 2 send + 2 recv ≈ ~30µs PER FRAME of pure overhead with zero benefit. Mitigation: short-circuit the LF dispatch entirely when `filter_level == 0` (already the existing eligibility check at `apply_loop_filter_to_frame_dispatching`). MUST be preserved in the new path.

### §4.4 (d) The serial floor caps total reclaim

`setup (80) + submit (16) + merge (51) + border (108) = 255µs` of main-thread work where every worker (decode AND LF) is parked. None of it is parallelisable by this lever. Frame wall floor = max(decode_crit, LF_wall) + 255 ≈ 1208 + 255 = 1463µs (vs measured 2019µs ⇒ 27.5% upper-bound reclaim).

After deductions:
- Hybrid P/E penalty (§4.1): −0 to −100µs ⇒ reclaim 27.5% → 22.5% in worst plausible.
- Cache thrashing (§4.2): −20 to −40µs ⇒ 22.5% → 20.5%.
- Park/wake overhead (§4.3): −30 to −50µs ⇒ 20.5% → 18%.
- 30% of frames with `filter_level == 0`: weighted average reduces headline by factor 0.7 ⇒ 18% × 0.7 = **12.6%**.
- Model optimism factor (the consistent track-record observation): historical 4-of-5 misses suggest models overstate by 1.5–3×. Dividing by 2 (median): **6.3%**.
- Pipelining fill latency (LF workers spinning on L1 for ~50µs while row 0 of every tile completes): −30 to −50µs ⇒ ~5%.

**Honest reclaim band: 4–15%.** Centre of band ≈ 8%. Above the 5% ship gate, but only just, and the lower end of the band MISSES the gate.

| upper-bound reclaim | 27.5% | — |

**This is meaningfully better than the prior overlap lever's prospects** (which the diagnostic shows could not exceed ~2% reclaim by topology constraint regardless of implementation quality). The prior lever's failure was *mechanistically impossible to exceed*; this lever's risk is *probabilistic deflation* — a fundamentally different risk class.

## §5 Recommendation

**PROCEED to Phase 1, flag-gated default OFF, with a hard escape clause.**

The decision criteria:
- The mechanism is sound and qualitatively different from the in-pool miss (verified mechanically in §2, not just claimed).
- The pre-mortem deflation lands on ~5–8% centre, with 55–60% probability of clearing the gate.
- The implementation cost is bounded (~250 LOC new + the prior HLD's hoist; no kernel changes; no entropy/parse touches).
- The Invariant L1 correctness argument is the prior HLD's, already team-lead-vetted.
- The downside on failure is "the dormant infra ships, the flag stays OFF, no perf regression, the negative result is documented".

**The case for SHELVE is real and the team-lead should weigh it:** the track record is 4-of-5 model-misses; centre of pre-mortem band is *at* the ship gate, not above it; success requires the team-lead's profiling box to have SMT/HT (verifiable at sign-off, but a constraint). A rigorous shelve here is defensible — the EV is positive but not overwhelmingly so, and the team's autonomous quick-lever space is already declared closed.

**My recommendation is PROCEED, narrowly**, on these grounds:
1. The mechanism's "in-pool overlap cannot exceed 2%" diagnostic is *mechanistically airtight* — this lever class is the only remaining structural lever that *can* mathematically clear the gate.
2. The infrastructure cost compounds with the prior dormant code (decode_progress publish, column-wavefront LF) — sunk costs deliver value here that won't elsewhere.
3. Phase 1 is reversible and behind a flag. The cost of a bad outcome is the implementation time, which is bounded.

If the team-lead's gut says "the track record dominates, shelve" — that is a valid call. I'd accept it without protest.

## §6 Design details

### §6.1 Bit-exact correctness — REUSED VERBATIM from the just-missed HLD §4

The Invariant L1 argument is identical because the *kernel* work and *gate logic* are identical. The only thing that differs from the prior HLD is *which thread set* executes the LF jobs; bit-exactness is determined by the gate ordering and the L1/L2/L3 invariants below, which are kernel-side and topology-agnostic.

> **Invariant L1 (LF delay):** A loop-filter worker may apply SB-row `r` only after `decode_progress[r + 1].load(Acquire) >= num_tile_cols` (all tiles have *finished decoding the row below*). For the final SB-row, the gate is "all rows decoded". This guarantees that every intra-pred read of row `r-1`'s pixels (which happens during decode of row `r` in the same tile) completes before LF of row `r-1` writes those pixels.
>
> **Invariant L2 (cross-row wavefront):** within the LF pass, row `r` column `c` may filter only after `cur_sb_col[r-1].load(Acquire) >= c + nsync`. Unchanged from Lever-B-v2.
>
> **Invariant L3 (per-SB order):** Y(V then H) → U(V then H) → V(V then H). Unchanged.

The decode worker's `decode_progress[r].fetch_add(1, Release)` (at `tile.rs:477` intra / `tile.rs:1572` inter) is the release edge; the LF worker's `decode_progress[r+1].load(Acquire)` is the matching acquire edge. Release/Acquire pairs across threads of different pools just as they do within one pool — the memory model is thread-set-agnostic. **Same correctness argument, different topology.**

The prior HLD's team-lead sign-off condition #3 — "confirm LF_DELAY=1 is provably sufficient, not just test-passing" — still binds. The reasoning: VP9 intra prediction reads at most 1 SB row up (top-row neighbours including TR extension), so delaying LF by 1 SB row strictly orders intra-read-of-row-(r-1) before LF-write-of-row-(r-1). This reasoning must be re-stated in the implementation PR as a SAFETY comment.

### §6.2 Lifetime and Send/Sync

The LF jobs borrow:
- `&ColumnWavefrontLfState<'frame>` — contains `SharedFrame` (raw ptr `Send+Sync` already audited Lever-B-v2), `&[AtomicU32]` (decode_progress slice, Sync), `&[AtomicI32]` (cur_sb_col slice, Sync), and `&[u8]` row-mask inputs (frozen mode-info grid, Send+Sync via Wave-5b pre-fill).
- All `'frame`-scoped, borrowed under the `LfWorkerPool::scope`'s `'frame` HRTB bound.

The new aliasing concern (vs the prior HLD): **decode workers and LF workers write the same frame buffer concurrently**. Decode writes row `r`'s reconstructed pixels; LF writes (= reads-then-writes-back) row `r-1`'s filtered pixels. The non-overlapping-write argument is identical to the prior HLD: L1+L2 jointly guarantee that LF's write to a given pixel happens-after the last decode-side read+write to that pixel (because intra-pred of row `r` reads row `r-1`, decode-finish of row `r` publishes `decode_progress[r]`, LF of row `r-1` is gated on `decode_progress[r] == num_tile_cols`, so LF of row `r-1` cannot begin until *every* tile finished row `r`, which is *after* every intra-pred read of row `r-1`).

**SAFETY chain** (must be written into the impl): (a) `SharedFrame` exposes raw pointers `Send+Sync` because access is temporally partitioned by L1+L2; (b) the partitioning holds across pools because Acquire/Release pairs through `decode_progress` and `cur_sb_col` are cross-thread, not cross-pool — the memory model treats them identically; (c) `'frame` lifetime is owned by `std::thread::scope` (the new outer scope) or by the dispatch-handle pattern, both of which strictly join before the borrow ends; (d) `LfWorkerPool::scope`'s drain loop is the borrow-soundness guarantee, structurally identical to `WorkerPool::scope`.

**The TSan run** the team-lead required is even more important here than in the prior HLD because we have two physically-separate worker sets sharing one buffer through atomic edges. On Linux nightly Rust: `-Zsanitizer=thread` on a tiny synthetic frame (sb_rows=4, scalar SIMD). **Windows MSVC TSan is unavailable** — note this as a limitation, not a blocker. WSL/Linux x86_64 nightly is the runnable path.

### §6.3 The eligibility / fallback dispatcher

```rust
fn should_use_lf_pool_overlap(&self) -> bool {
    self.lf_worker_pool.is_some()                     // §3.5 sized > 0
    && trace_flags().lf_overlap_pool                  // RVP9_LF_OVERLAP_POOL=1
    && self.num_threads.get() >= 2                    // need parallel decode
    && tile_rows == 1                                 // prior HLD risk 5
    && filter_level > 0                               // §4.3 no-LF short-circuit
    && !skip_loop_filter
    && !trace_flags().disable_row_mt
}
```

When the check returns false, the existing two-scope path runs unchanged. Phase 1 ships with the flag default OFF.

### §6.4 Hoist of the LF parameters

The just-missed HLD §8 noted: `resolve_filter_levels(filter_level, lf_deltas, seg_view)` and `LoopFilterInfo::new(sharpness)` are today computed *inside* `apply_loop_filter_to_frame_column_wavefront_dispatch` (after the decode scope joined). For the new path they must be computed **before** the outer `thread::scope` opens, since the LF helper thread needs them to build `ColumnWavefrontLfState`. They depend only on frame-level params already finalized after the merge step — actually that's the problem: merge happens AFTER decode. So either (a) the merge is moved before LF dispatch is possible (but merge IS post-decode by definition — can't pre-merge), or (b) the LF dispatch consumes seg-and-lf-delta resolution that's available pre-merge (the `lf_deltas` come from the bitstream header, the `seg_view` from the segmentation header — BOTH known after the frame header decode, BEFORE tile decode). So the hoist is sound.

Implementer must verify: the merge step (`merge_tile_counts_and_seg_and_mv`) does NOT modify `lf_deltas` or `seg_view` — it merges entropy counts, segment maps, mv refs. The LF parameters are stable from frame header. **Confirmed by inspection at sign-off; gate the impl on this.**

## §7 Testability / oracle plan

### §7.1 Bit-exact differential (primary oracle, every commit)

Identical to prior HLD §5.1: threads=1 (serial) vs threads=4 + `RVP9_LF_OVERLAP_POOL=1`. Per-frame MD5 must match. Covers key + inter + intra-only frames; multi-tile and single-tile vectors. The L1 gate is the new failure mode; this is what catches an L1 off-by-one.

### §7.2 201/201 conformance gate

Run twice on a corpus-complete tree:
- `RVP9_LF_OVERLAP_POOL` unset (default off): two-scope path, must stay 201/201.
- `RVP9_LF_OVERLAP_POOL=1`: new overlap path, must also stay 201/201.

### §7.3 Debug-build L1 assertion

`#[cfg(debug_assertions)]` in `run_split_edge_lf_worker`: before filtering row `r`, assert `decode_progress[(r + lf_delay).min(sb_rows-1)].load(Acquire) >= num_tile_cols`. Cheap; gated out of release.

### §7.4 PGO end-to-end A/B — THE SHIP GATE

Per the prior HLD's team-lead sign-off and the consolidation journal's binding rule: **PGO end-to-end A/B is the ONLY trustworthy oracle.** Non-PGO numbers systematically mislead.

- Build: existing `scripts/build-pgo.ps1`.
- Fixture (binding): `testsrc_1080p30 t=4`.
- Sanity rows (no regression allowed): `tile_1x4 t=4`, `testsrc_1080p60 t=4`.
- Methodology: `bench/results/decode-headtohead.md` — ≥1000 timed frames, ≥30 warmup, interleaved drift-cancelling A/B iterations.
- **Pass:** B's mean AND p50 frame-wall beats A's by ≥5% on `testsrc_1080p30 t=4`, AND no regression > 2% on the sanity rows.
- **Fail:** hold dormant behind `RVP9_LF_OVERLAP_POOL`, **do not revert**, **do not force default ON**. Report measured numbers; stop.

### §7.5 Optional TSan one-off (pre-merge, runnable path noted)

Run once on `cargo +nightly test --target x86_64-unknown-linux-gnu` with `-Zsanitizer=thread`, on a synthetic small frame (sb_rows≈4, scalar SIMD via existing dispatch path). The new sync edge is the cross-pool `decode_progress` Acquire/Release pair — exactly what TSan catches. **Windows MSVC TSan is unavailable; this is a known limitation, not a blocker.** WSL or Linux CI host is the runnable path. Not CI-blocking.

### §7.6 N_LF measurement

Phase 1 should additionally measure N_LF ∈ {1, 2, 4} on the headline fixture and pick the winner. The HLD's default of 2 is a model-based bet; only the bench can settle it.

## §10 DO-NOT list (inherited + new)

Inherited from the prior overlap HLD and Lever-B-v2:

1. DO NOT use a row barrier — keep the landed column-wavefront (Wave-2 was 1.5× regression with a row barrier).
2. DO NOT submit per-SB scope jobs — submit `N_LF` LF jobs only (Lever-B-v2 §10 #1).
3. DO NOT park/condvar on the gates — atomic + spin + `yield_now` only (§3.6, Lever-B-v2 §10 #4).
4. DO NOT let LF run before `decode_progress[r+1] == num_tile_cols` — **Invariant L1**, the new correctness rule.
5. DO NOT change `SharedFrame` / `TileFrameView` ownership semantics — soundness review depends on them (Lever-B-v2 §10 #5).
6. DO NOT enable overlap for `tile_rows > 1` in Phase 1 — fall back to two-scope (§6.3).
7. DO NOT revert if the PGO gate misses — hold dormant behind the flag and report (Lever-B-v2 §10 #2).
8. DO NOT touch the idct/convolve/LF-kernel files or the entropy/parse path (team-lead constraint).
9. DO NOT skip the differential test on any commit (Lever-B-v2 §10 #7).

New for this HLD:

10. DO NOT dispatch the LF pool when `filter_level == 0` — preserve the eligibility short-circuit (§4.3, §6.3). The park/wake overhead on no-LF frames would be pure cost.
11. DO NOT create a third pool or generalise `WorkerPool` into a generic — copy-and-specialise to `LfWorkerPool` to keep the soundness review small.
12. DO NOT default the flag ON before the PGO A/B clears the gate. Phase 1 ships with `RVP9_LF_OVERLAP_POOL=1` opt-in.
13. DO NOT skip the §6.4 hoist verification — confirm merge does NOT touch lf_deltas/seg_view before lifting the LF param computation. If it does, the hoist is invalid and the HLD is broken.
14. DO NOT enable the overlap pool when `available_parallelism < num_decode_threads + N_LF + 1`. This is the cores-available guard (§3.5). Generalisation to lower-core hosts requires a separate sign-off.
