## 3. Gap analysis

Cross-product of features that need Profile-1 coverage × chroma format × current coverage:

| Feature exercised | 4:4:4 | 4:2:2 | 4:4:0 | Notes |
|---|---|---|---|---|
| Single-tile default inter | YES (×2) | YES (×2) | YES (×2) | baseline; covered |
| Intra-only / keyframe-only | NO | NO | NO | needs `--lag-in-frames=0 --kf-min-dist=1 --kf-max-dist=1` |
| Multi-tile (1×2, 1×4, 1×8) | NO | NO | NO | needs `--tile-columns=N`; gates the `LF_PATH_SLOW` × multi-tile interaction |
| Frame-parallel | NO | NO | NO | `--frame-parallel=1`; gates the FP adaptation path × ss>0 |
| Resize (super-frame index) | NO | NO | NO | `--resize-allowed=1` mid-stream |
| Loop-filter deltas / sharpness | NO | NO | NO | `--sharpness=N` × non-`LF_PATH_FAST` |
| Segmentation | NO | NO | NO | exercises seg-aware chroma decoding |
| AQ-2 / aq=cyclic_refresh | NO | NO | NO | exercises adaptive Q on chroma |
| Show-existing-frame | NO | NO | NO | hidden alt-ref + show-existing × ss>0 |
| Large frame (≥720p) | NO | NO | NO | catches per-row mask-packing bugs at high `mi_rows` |

**Each empty cell is a real, observable test gap** — Profile 1 changes the `(ss_x, ss_y)` invariant fed into nearly every per-block hot path; running the *same* feature suite that Profile 0 has would meaningfully derisk the parametric loop-filter path (`LF_PATH_SLOW`, `filter_block_plane_non420`), the parametric `uv_plane_block_size`, and the sub-8 chroma MV averaging code (all called out in `wrk_docs/G7.1_profile1_decode_scope.md` §2.3 as the items most likely to harbour subtle bugs).

The Wave P journal already proved the cost of weak coverage: the foreman_c440 parser desync **was a real bug**, surfaced only because the self-encoded `.ivf` exercises a `skip=1 sub-8 block` pattern that the upstream `vp91-2-04-yuv440.webm` doesn't. Expanding the self-encoded set is exactly the right lever to find the equivalent of that bug in 4:2:2 and 4:4:4.

## 5. Harness integration

### 5.1 Extend `profile1_decode.rs`, do not split
`crates/rvp9-harness/tests/profile1_decode.rs` already has:
- Per-vector iteration through a `PROFILE1_VECTORS: &[&str]` slice (line 61).
- `decode_and_gate(name)` (line 93) which loads the triangulated ledger, decodes, and hard-asserts zero mismatches + full ledger coverage.
- Named per-vector fix-lock tests pattern (e.g. `profile1_440_foreman_decodes_bit_exact_wave_p`, line 205) — newly-added vectors that exercise a specific historical class can drop in next to this.

**Recommendation: extend the existing slice.** Per-format file splits add boilerplate without buying isolation that the current single test doesn't already give (`#[test]` runs per-function, but each vector is sequenced inside the loop). The loop pattern keeps the "zero mismatches across the full Profile-1 corpus" gate as a single load-bearing assertion. If/when a vector exposes a regression, copy the pattern of `profile1_440_foreman_decodes_bit_exact_wave_p` to add a named regression marker.

### 5.2 Keep the test fast
Per-vector cost is dominated by decoder construction + per-frame MD5 over visible planes. Empirically the 6-vector / 94-frame current corpus runs in <2s on `--release`. Scaling to N=20 vectors / ~400 frames stays well under the 30s informal soft-cap for an in-tree integration test.

- **Threading:** keep `Decoder::with_threads(1)` (line 114) for deterministic byte-exactness, as the Profile-0 conformance harness already does (`conformance.rs:142`). Adding a Profile-1 multi-tile vector with `--threads=4` is in scope for the harness as a separate test in `tile_threading.rs`, not for `profile1_decode.rs`.
- **Per-vector timeout:** Rust's test harness has no built-in per-test timeout; the assertion-driven design means a deadlocked decoder hangs forever. Acceptable for now (no Profile-0 vector hangs). If `cargo test --timeout` is desired, that's a separate Track-T-adjacent infra change.
- **Parallelism:** `cargo test` already runs `#[test]` functions in parallel by default. As long as `decode_and_gate` doesn't mutate shared state (it doesn't — fully self-contained), N named regression-marker tests can run concurrently.

### 5.3 Loader-script integration
Two equivalent paths, both must work:
- **Encoder script** (`encode-corpus.ps1`, extended): generates the `.ivf` AND both ledger sidecars (vpxdec + ffmpeg) atomically. Already does this for default-flag encodes; the Profile-1 extension just adds `-Profile1Format {444|422|440}` and a `--tile-columns` / `--frame-parallel` / `--kf-max-dist` passthrough.
- **Static fetch** (a Profile-1 variant of `fetch-vectors.sh`): only relevant for the 3 official `vp91-2-04-*` vectors, which are already committed. **No new fetch logic needed.**

The lead's preference (per Wave M/N tradition) is "ledgers in tree, regen on demand": commit the `.ivf` + both `.md5` sidecars per vector, with the encoder script as the regenerator-of-record.

## 6. Triangulated oracle

The Wave O `vpxdec ∧ ffmpeg` oracle (`scripts/oracle-ledger-ffmpeg.ps1`, `read_triangulated_ledger` in `crates/rvp9-harness/src/md5file.rs:251`) is exactly what's needed and is **already wired** for Profile-1. Every existing `tests/corpus/profile1/*.ivf` has a `.md5` (vpxdec) AND a `.ffmpeg.md5` sibling that ffmpeg's *native* VP9 decoder produced. The harness panics with attribution if they disagree.

The per-vector flow for every new vector:
1. `vpxenc … -o vector.ivf source.y4m`
2. `vpxdec --i{420,422,440,444} -o pat.iNNN vector.ivf` → hash visible planes → `vector.ivf.md5`
3. `oracle-ledger-ffmpeg.ps1 -Vector vector.ivf -Verify` → produces `vector.ivf.ffmpeg.md5` AND asserts equality with `vector.ivf.md5` before exiting 0.
4. Both ledgers commit.
5. Harness `read_triangulated_ledger` re-checks oracle agreement on every test run (cheap; just two file reads + linear scan).

A vector that fails step 3 (vpxdec and ffmpeg disagree) is *evidence of an upstream bug*, not of ours. Per Wave O policy, such a vector must NOT be added to the corpus until upstream attribution is resolved.

The `ffmpeg` oracle is genuinely independent: it's a from-scratch native VP9 decoder, not a libvpx wrapper (the script passes `-c:v vp9`, explicitly NOT `-c:v libvpx-vp9`). This is the gate that caught the foreman_c440 self-encoded vector before it could falsely accuse our decoder.

## 8. Risk register (top 3)

1. **Risk: a new vector decodes correctly on vpxdec ∧ ffmpeg but incorrectly on rvp9.**
   This is *the* expected outcome of expanding coverage on a thinly-tested path. It's a *real bug surfaced*, not a harness failure. Wave P (foreman_c440 parser desync) is the precedent. Mitigation: the triangulated oracle automatically attributes — if both upstream decoders agree, the bug is unambiguously ours. Standing protocol: don't disable the vector; fix the decoder or gate the new vector behind a named `#[ignore]`d follow-up test with the diagnosis embedded in a journal. Budget: assume 1–2 such vectors out of 12 will trip this; absorb that into the overnight plan.

2. **Risk: a new vector decodes differently on vpxdec vs ffmpeg.**
   Triangulation halts the vector's adoption. Likely causes: encoded with a `vpxenc` feature interaction that exposes an upstream bug, OR a rare bitstream edge case where ffmpeg's native decoder is genuinely non-conformant. Mitigation: do NOT commit the vector; pick a slightly different feature flag combination that the oracles agree on; document the rejection in the journal. **Do not weaken the oracle** to admit the vector — Wave O exists specifically to prevent this failure mode.

3. **Risk: `vpxenc` for an unusual flag combination (e.g. `--profile=1 --frame-parallel=1 --tile-columns=2`) produces a bitstream we didn't anticipate.**
   Some vpxenc flag interactions are weakly tested upstream. The encoder may silently downgrade (`--frame-parallel` may not stick with certain Profile-1 settings), producing a vector that doesn't actually exercise the targeted feature. Mitigation: after encoding, run `vpxdec --summary` or inspect the IVF header to confirm `tile_cols > 1`, `frame_parallel_decoding_mode = 1`, etc., before accepting the vector. If the encoder downgraded, switch sources or alter the source dimensions (frame-parallel + tiles requires sufficient width per tile to be meaningful).

A fourth latent risk worth naming: the harness today gates each new vector to byte-exact MD5 against the visible-plane hash. **Adding 12 vectors at once amplifies cascade-failure pain** if a single Wave-P-class bug is hit — every newly-added vector may fail simultaneously and the first-slice "+12 vectors" headline collapses to "+1 vector + a bug". Mitigation: stage commits in groups of 3 (per-format triples). Commit a triple only after that triple is green. A bug that lights up only on one format can then be addressed without rolling back the other 9.

## 9. Validation strategy

Every new vector must satisfy this chain:

1. **Oracle independence proof:** the vpxdec ledger (`.md5`) and ffmpeg ledger (`.ffmpeg.md5`) agree byte-for-byte (`oracle-ledger-ffmpeg.ps1 -Verify` exits 0 at generation time).
2. **In-harness re-verification:** `read_triangulated_ledger` re-asserts oracle agreement on every `cargo test` invocation; a future divergence is impossible to silently ignore.
3. **rvp9 ⊆ oracle:** `profile1_decode.rs::decode_and_gate` asserts rvp9's visible-plane MD5 equals the triangulated oracle on every shown frame.
4. **No vacuous pass:** `decode_and_gate` asserts shown-frame-count == ledger length (line 169-175). A truncated/short decode cannot pass.
5. **Profile-0 regression guard:** the full 201-vector conformance suite remains green per the existing `MIN_PASSES = 201` and `total_mismatched == 0` gates in `conformance.rs:261, 428`.

**Quantitative exit metrics for first slice:**
- Profile-1 vector count: 6 → 18 (12 new) or 6 → 22 (16 new, stretch).
- Profile-1 shown-frame count: 94 → ≥250.
- Multi-tile Profile-1 coverage: 0 → 3 (one per chroma format).
- Frame-parallel Profile-1 coverage: 0 → 3.
- Intra-only Profile-1 coverage: 0 → 3.
- Large-frame (≥720p) Profile-1 coverage: 0 → 2.
- Oracle-disagreement events: must be 0 (or the vector is rejected).
- Wave-P-class real-bug events: budget ≤2; each one fixed and journaled before close-out.

The headline reportable: "Profile-1 conformance corpus expanded from 2 official + 4 self-encoded ⇒ 18 vectors (3 official + 15 self-encoded), all bit-exact under the triangulated vpxdec ∧ ffmpeg oracle."
