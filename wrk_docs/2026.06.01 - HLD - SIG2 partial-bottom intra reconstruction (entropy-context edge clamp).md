# HLD — SIG2 partial-bottom keyframe decode divergence (entropy-context frame-edge clamp)

**Author:** Claude (investigation + design).
**Status: IMPLEMENTED & verified vs corpus (2026-06-01).** Option A, shared
intra+inter. Both 1080p keyframes (bbb + jellyfish) flipped `0`→`EXACT`; three
SIG1 clips stay EXACT; decoder lib tests 203 green; no warnings. See the JRN
Entry 3 for files + results. (Originally: DRAFT for lead sign-off.)
**Branch:** `track2-longclip-differential-gate` (local).
**Date:** 2026.06.01.
**Drive data:** `tests/corpus/longclips/bbb_1080p_kf48.ivf` frame 0 (1920×1080 keyframe, 4 tile-cols); oracle = `vpxdec` v1.14.1 raw I420. Trace + diff captured in `bench_tmp/sig2a_*`.

> **One-line root cause.** rvp9's coefficient entropy-context writeback
> (`detokenize.rs::set_coef_flags`) does not apply libvpx's **frame-edge clamp**
> (`vp9_set_contexts`, `vp9_blockd.c:87-122`): for a TX block with `eob>0` that
> crosses the frame's right/bottom edge, libvpx zeroes the beyond-edge
> above/left entropy-context cells, but rvp9 sets them to `1`. An adjacent large
> TX folds those corrupted cells into its entropy context → wrong token
> probabilities → **per-tile bool-coder desync** confined to the partial-bottom
> SB row. This is the entropy-context analog of the already-landed D.25 inter
> *iteration*-clamp fix.

---

## 1. Problem (measured)

`bbb_1080p_kf48.ivf` frame 0 (a keyframe, all-intra) mis-decodes vs the
reference decoder. Confirmed facts:

- **Trigger = partial-bottom SB row.** 1080 = 16·64 + 56. Re-encoding the same
  content at 1920×**1088** (no partial-bottom row) makes frame 0 bit-exact.
- **Region:** Y rows 1024–1079 (the partial-bottom SB row); rows 1017–1023 are
  loop-filter bleed from below. 19 483 Y bytes differ; chroma also affected
  (9 546). Worst pixel **(row 1056, col 355): rvp9=253 vs oracle=103, |Δ|=150**.
- **Hard cutoff at tile-column boundaries.** 4 tiles start at cols **0, 448,
  960, 1408** (`(t·30_sb)>>2`). Divergence spans cols 384–1407 → tiles 0,1,2
  corrupted in the partial-bottom row, **tile 3 (1408–1919) completely clean**.
  The cutoff is exact (not content-coincidental).
- Same signature on `jellyfish_1080p_kf48.ivf` (different content) ⇒ not
  content-specific; it is a partial-bottom-row decode bug.

## 2. Root cause (trace-derived + libvpx-cited)

### 2.1 It is a per-tile token desync, not a pixel-reconstruction bug
The originating cell `(352,1056)` (a `Block8x16` `Tx4x4` DC block) has
**bit-exact prediction inputs** — its neighbours at cols 350–351 and row 1055
match the oracle exactly (from `bench_tmp/sig2a_trace.txt` +
`bench_tmp/sig2a_diff.py`):

```
y=1055 cols350-361  oracle=[114,122,115,107,103,105,110,114,119,123,124,118]
        rvp9  =[114,122,115,107,103,105,110,114,119,123,124,118]   (match)
y=1056 cols350-361  oracle=[111,122,113,105,101,103,108,112,117,121,122,116]
        rvp9  =[111,122, 42,  0, 86,253,148,149,150,153,154,156]   (cols 352+ garbage)
```

DC prediction from the (correct) neighbours ≈ 114; the oracle output is a smooth
≈103–113 (small residual), but rvp9 emits garbage (42,0,86,253). **Same correct
prediction, garbage residual** ⇒ the *coefficients/tokens* decoded for this
block are wrong, even though prediction is right.

The tile-boundary cutoff is the tell: VP9 tiles have **independent bool
decoders**. A desync inside tile 0's partial-bottom row corrupts the rest of
tile 0 only (the partial-bottom row is the last SB row, so just its
bottom-right), and stops dead at the tile boundary — exactly what we see. (The
prior note's "cursor stays synced because the error doesn't reach the frame
edge" was confounded by this per-tile independence — corrected here.)

### 2.2 Ruled out
- **Per-cell skip / iteration clamp.** `Frame::y_plane().height()` returns
  `y_height = (1080+7)&!7 = 1080` (`frame.rs:219-220`, 8-aligned, **not**
  SB-aligned). The intra per-cell skip `tx_px_y >= 1080` therefore reconstructs
  exactly the same cell *set* as libvpx's `max_blocks_high` clamp
  (`mi_rows·8 = 1080`) for every block/TX size — verified by hand for 64×64 /
  32×32 / 16×16 / 8×8 / 4×4 at the bottom row. So the "mirror the inter clamp"
  idea is **not** the fix; the token-cell set already matches.
- **Partition-tree edge inference.** `tile.rs::decode_partition:507-560` is
  libvpx-faithful (`has_rows`/`has_cols`, the `probs[1]`/`probs[2]`/inferred-SPLIT
  arms) and the partition-context update `:659-663` matches
  `update_partition_context` (`bsize>=8x8 && (bsize==8x8 || partition!=SPLIT)`).

### 2.3 The actual divergence — entropy-context writeback misses the frame-edge clamp
libvpx `vp9_set_contexts` (`third_party/libvpx/vp9/common/vp9_blockd.c:87-122`):

```c
// left (bottom edge):
if (has_eob && xd->mb_to_bottom_edge < 0) {
  const int blocks_high = num_4x4_blocks_high_lookup[plane_bsize] +
                          (xd->mb_to_bottom_edge >> (5 + pd->subsampling_y));
  int left_contexts = tx_size_in_blocks;
  if (left_contexts + loff > blocks_high) left_contexts = blocks_high - loff;
  for (i = 0; i < left_contexts; ++i)            l[i] = has_eob;   // in-frame
  for (i = left_contexts; i < tx_size_in_blocks; ++i) l[i] = 0;    // BEYOND EDGE → 0
} else {
  memset(l, has_eob, tx_size_in_blocks);
}
// (above / right-edge is symmetric)
```

rvp9 `detokenize.rs:321-323`:

```rust
// Writeback: splat (eob > 0) across the (n × n) sub-block region.
coef_ctx.set_coef_flags(plane, x4, y4_in_sb, n, n, eob > 0);
```

`set_coef_flags` (`tile_ctx.rs`) clamps the write only to the **array bounds**
(above-row width, SB height = 16 4×4 rows) — see test
`set_coef_flags_clamps_at_edges`. It has **no frame-edge clamp**. For the
partial-bottom SB the off-frame rows (y4 14,15 = pixel rows 1080,1084) sit
*inside* the 16-row SB array, so a large TX (`Tx16x16`/`Tx32x32`) whose extent
crosses row 1080 writes `eob>0` into them, where libvpx writes `0`.

**Mechanism (matches the trace).** Tile 2 has adjacent bottom 32×32 blocks
`(960,1056)` and `(992,1056)` (both `Tx32x32`, rows 1056–1087, crossing the
1080 edge). `(960,1056)`'s writeback sets left-context y4 8..16 — including the
off-frame rows 14,15 — to `eob>0`. `(992,1056)` (also 32×32) folds left-context
y4 8..16 into its entropy context; if the in-frame rows happen to be 0 but the
off-frame rows were set to 1 (rvp9) vs 0 (libvpx), the folded context differs →
different coefficient probability → first divergent token → desync that
propagates through the rest of that tile's bottom row. Right/bottom-edge large
TX in tiles 0 and 1 do the same; tile 3's bottom content does not hit the
trigger, so it stays clean.

The bug is shared by intra **and** inter token decode (`set_coef_flags` is the
common writeback). D.25 fixed the inter *iteration* bound but not this
*context* writeback; its own comment ("same clamp in `predict_recon_intra`")
referred to iteration, not `vp9_set_contexts`.

## 3. Proposed fix (minimal, libvpx-faithful)

Apply the `vp9_set_contexts` frame-edge clamp to the entropy-context writeback.
Two design options for the lead to choose:

- **Option A (clamp at the call site).** In `detokenize.rs` (and the inter
  token-decode caller) compute `max_blocks_wide/high` for the TX's parent plane
  block (the inter path already computes these — `reconstruct_inter.rs:537-548`)
  and pass an explicit `(above_cells, left_cells)` in-frame count to a new
  `set_coef_flags_clamped(plane, x4, y4, n, n, above_cells, left_cells, eob>0)`
  that writes `eob>0` to the in-frame cells and `0` to the rest. Localizes the
  edge knowledge to the callers that already have it.
- **Option B (clamp inside the writeback).** Thread the block's
  `mb_to_right_edge`/`mb_to_bottom_edge` (or `mi_row/mi_col` + `mi_rows/mi_cols`)
  into `set_coef_flags` and replicate `vp9_set_contexts` verbatim. Keeps all
  edge logic in one place but widens a hot-path signature.

**Recommendation: Option A** — smaller blast radius, the inter caller already
has `max_blocks_*`, and the intra caller (`reconstruct_intra_planes`) has
`mi_row/mi_col` + `params.mi_rows/mi_cols` to compute them. Note the subtle
requirement: the beyond-edge cells must be **explicitly set to 0** (not left
stale), exactly as libvpx's second `for` loop does — a previous block in the
same SB row may have set them to 1.

Estimated change: ~1 new helper + 2 call-site edits + the `max_blocks_*`
computation already present in the inter path lifted/shared. No change to
iteration, prediction, or transform code.

## 4. Why it's correct
Byte-for-byte mirror of `vp9_set_contexts` (`vp9_blockd.c:87-122`), the single
reference function for the post-token entropy-context update. The in-frame
cells keep `eob>0` (unchanged behaviour for non-edge blocks — the overwhelming
majority), only the beyond-edge cells change from `1`→`0`, matching the spec.

2. `cargo test -p rvp9-harness --test longclip_differential -- --nocapture`.

3. `cargo test -p rvp9-decoder` — all decoder lib unit tests stay green

4. **New unit reproducer:** a `tile_ctx.rs` test
   `set_coef_flags_clamps_at_frame_edge` — a `Tx32x32` writeback at a block
   straddling the bottom edge must leave the off-frame `left_coef` rows `0` and
   the in-frame rows `1` (the test that would have caught this).
5. If only *some* 1080p rows reach EXACT, there is a second partial-bottom bug;
   re-bisect from the new first-divergent cell. (High confidence this is the
   complete cause for the 1080p keyframes given §2.3, but the gate is the
   arbiter.)

## 6. Risks / alternatives
- **Risk:** mis-identifying `max_blocks_*` for sub-8×8 blocks. Mitigation: reuse
  the inter path's exact `is_sub8` handling (`reconstruct_inter.rs:521-536`).
- **Risk:** the change also touches the inter context writeback (shared path).
  This is *correct* (the bug exists for inter too) and is covered by the
  existing conformance + longclip inter clips; watch for any inter ratchet
  movement.
- **Alternative rejected:** mirroring the inter *iteration* clamp into intra —
  ruled out in §2.2 (the cell set already matches; the bug is the context
  writeback, not iteration).
