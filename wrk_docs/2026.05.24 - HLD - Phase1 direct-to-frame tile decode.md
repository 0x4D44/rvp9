# HLD: Phase 1 — Direct-to-Frame Tile Decode

**Date:** 2026-05-24
**Status:** Draft (pre-implementation review)
**Scope:** Eliminate the pixel-merge phase from parallel tile decode by having workers write directly into non-overlapping column-range views of the shared output `Yv12Buffer`.

---

## 1. Problem Statement

The current parallel tile decode pipeline has three phases:

1. **Setup** — allocate per-tile scratch `Yv12Buffer`s from `Yv12ScratchPool`.
2. **Decode** — dispatch tile workers; each writes pixels into its own scratch buffer.
3. **Merge** — the main thread serially copies each tile's pixel rectangle from its scratch buffer into the output frame via `yv12.merge_tile_rect_from(...)`.

At 1080p with 4 tile columns, the merge phase costs approximately 1,246 us (12.8% of frame time). The cost is dominated by memcpy traffic: three planes x full-height x column-width, repeated per tile. At 8 tiles the traffic roughly doubles.

The merge exists because the current design gives each worker exclusive `&mut Yv12Buffer` access to its own allocation — the simplest way to satisfy Rust's aliasing rules. However, VP9 tile columns are SB-aligned (64-pixel = 8 MI boundaries) and spatially disjoint by spec. No two tiles ever write the same pixel. This means the output frame can be split into non-overlapping column-range views and each worker can write directly into its view, eliminating the scratch-allocate and merge-copy steps entirely.

## 2. Design

### 2.1 Splitting the Output Frame into Column-Range Views

A new type `TileFrameView` provides a per-tile mutable view into a sub-rectangle of the shared `Yv12Buffer`. It is constructed from raw pointers derived from the output frame before the worker scope opens.

```rust
/// A non-overlapping mutable view into a rectangular sub-region of a
/// `Yv12Buffer`. Semantically equivalent to `&mut` over the pixel
/// rectangle [row_start..row_end, col_start..col_end] across all three
/// planes, but implemented via raw pointers to avoid Rust's single-
/// &mut-to-the-whole-buffer restriction.
///
/// # Safety invariants (construction-time)
/// 1. The parent `Yv12Buffer` must outlive all `TileFrameView`s.
/// 2. No two `TileFrameView`s may cover overlapping byte ranges in
///    any plane.
/// 3. No other &mut reference to the parent buffer's `buffer_alloc`
///    may exist while any `TileFrameView` is alive.
pub struct TileFrameView {
    // Per-plane raw pointers to the first byte of the view's top-left
    // pixel (i.e. row_start * stride + col_start from the plane origin).
    y_ptr: *mut u8,
    u_ptr: *mut u8,
    v_ptr: *mut u8,

    // Strides (bytes per row) — same as the parent buffer's.
    y_stride: usize,
    uv_stride: usize,

    // Visible rectangle in this tile's coordinate space.
    // Width/height in luma pixels; chroma derived via ss.
    luma_col_start: usize,  // frame-absolute column of first pixel
    luma_col_end: usize,    // frame-absolute column past last pixel
    luma_row_start: usize,  // frame-absolute row of first pixel
    luma_row_end: usize,    // frame-absolute row past last pixel

    // Chroma subsampling (cached from parent).
    ss_x: usize,
    ss_y: usize,

    // Total plane dimensions (for bounds-checking in debug builds).
    y_width: usize,
    y_height: usize,
    uv_width: usize,
    uv_height: usize,

    // Chroma format (needed by downstream callers).
    chroma: ChromaFormat,
}
```

**Construction** (on the main thread, before the worker scope):

```rust
impl TileFrameView {
    /// # Safety
    /// Caller must guarantee:
    /// - `yv12` lives at least as long as the returned view.
    /// - No two views constructed from the same `yv12` overlap in
    ///   [row_start..row_end, col_start..col_end].
    /// - No other &mut to `yv12.buffer_alloc` exists concurrently.
    pub unsafe fn new(
        yv12: &mut Yv12Buffer,
        luma_row_start: usize,
        luma_row_end: usize,
        luma_col_start: usize,
        luma_col_end: usize,
    ) -> Self { ... }
}
```

The constructor computes per-plane pointers:
- `y_ptr = buffer_alloc.as_mut_ptr() + y_offset + row_start * y_stride + col_start`
- `u_ptr = buffer_alloc.as_mut_ptr() + u_offset + (row_start >> ss_y) * uv_stride + (col_start >> ss_x)`
- `v_ptr = buffer_alloc.as_mut_ptr() + v_offset + (row_start >> ss_y) * uv_stride + (col_start >> ss_x)`

### 2.2 Send Implementation

```rust
// SAFETY: TileFrameView is Send because:
// 1. It holds raw pointers into a single Box<[u8]> allocation.
// 2. The construction contract guarantees non-overlapping ranges,
//    so sending different views to different threads cannot produce
//    data races — each thread writes only to its own disjoint byte set.
// 3. The parent Yv12Buffer's lifetime is guaranteed by the scoped
//    thread pool (the scope borrows the parent, preventing drop).
unsafe impl Send for TileFrameView {}
```

`TileFrameView` is NOT `Sync` — it should not be shared between threads. Each view is consumed by exactly one worker.

### 2.3 Plane Access API

`TileFrameView` exposes a `PlaneMut`-compatible interface that tile decode functions can use:

```rust
impl TileFrameView {
    /// Mutable slice for the Y plane, starting at the view's top-left
    /// pixel. Length = (row_count - 1) * stride + col_count. The stride
    /// is the full frame stride, so rows are non-contiguous in the
    /// sub-region but contiguous in memory layout.
    pub fn y_plane_mut(&mut self) -> PlaneMut<'_> { ... }
    pub fn u_plane_mut(&mut self) -> PlaneMut<'_> { ... }
    pub fn v_plane_mut(&mut self) -> PlaneMut<'_> { ... }

    pub fn chroma(&self) -> ChromaFormat { self.chroma }
    pub fn aligned_y_width(&self) -> usize { self.y_width }
    pub fn aligned_y_height(&self) -> usize { self.y_height }
    // ... other accessors needed by tile.rs / reconstruct*.rs
}
```

**Critical point:** The returned `PlaneMut` slices start at the frame-absolute pixel position (`luma_row_start * stride + luma_col_start`), NOT at offset 0 of the allocation. The existing tile decode code already computes pixel coordinates in frame-absolute terms (`mi_col * 8`, `mi_row * 8`), so they index directly into these slices without any coordinate translation. The slices are sub-slices of the parent `buffer_alloc` via raw-pointer-derived references.

### 2.4 How Tiles Receive Their View

The `decode_tile_intra` / `decode_tile_inter` signatures change from:

```rust
pub fn decode_tile_intra(
    ...,
    dst_frame: &mut Yv12Buffer,
    ...
) -> Result<TileDecodeCtx, TileDecodeError>
```

to accepting a generic "frame destination" that can be either a `&mut Yv12Buffer` (serial path) or a `&mut TileFrameView` (parallel path). Two design options:

**Option A — Trait abstraction:**
```rust
pub trait TileFrameDst {
    fn y_plane_mut(&mut self) -> PlaneMut<'_>;
    fn u_plane_mut(&mut self) -> PlaneMut<'_>;
    fn v_plane_mut(&mut self) -> PlaneMut<'_>;
    fn chroma(&self) -> ChromaFormat;
    fn aligned_y_width(&self) -> usize;
    fn aligned_y_height(&self) -> usize;
}

impl TileFrameDst for Yv12Buffer { ... }
impl TileFrameDst for TileFrameView { ... }
```

**Option B (preferred) — Enum wrapper:**
```rust
pub enum TileDst<'a> {
    Full(&'a mut Yv12Buffer),
    View(&'a mut TileFrameView),
}
```

**Recommendation: Option A (trait).** The tile decode functions are large and hot; a trait with `#[inline]` accessors lets the compiler monomorphize without penalising icache, and avoids branching on every plane access. The trait lives in `rvp9-core::frame` alongside `Yv12Buffer`.

### 2.5 What Happens to the Merge Loop

The post-scope merge changes:
- **Pixel merge (`merge_tile_rect_from`) — REMOVED.** Tiles wrote directly into the output frame.
- **Counts merge (coef/mv/mode) — RETAINED.** These are small additive accumulations (<1 us total); they remain serial post-scope.
- **Seg-ID / MV-grid merge — RETAINED.** These are per-MI-cell, not per-pixel, and are small. They can later be optimised via the same direct-write pattern (Phase 2), but are not on the critical path today.

### 2.6 What Happens to the Scratch Pool

The `Yv12ScratchPool` is **no longer needed for pixel data** in the parallel path. However:

- The serial (single-tile or single-thread) path continues to write directly into `&mut yv12` — no scratch pool was ever used there.
- The scratch pool can be entirely removed from the parallel pixel path.
- The `seg_ids` and `mv_grid` per-tile allocations remain as they are (Vec-based, not Yv12Buffers).

**Deprecation plan:** Mark `Yv12ScratchPool` as unused in the parallel path. If no other consumer exists, remove it in Phase 1. Otherwise keep it but stop calling `.take()` in the parallel tile dispatch.

## 3. Safety Proof

### 3.1 Non-Overlapping Column Ranges Do Not Alias

**Memory layout of `Yv12Buffer`:** A single contiguous `Box<[u8]>` allocation with three planes laid out sequentially (Y, then U, then V). Within each plane, pixels are stored row-major with a constant stride. The byte address of pixel `(row, col)` in the Y plane is:

```
addr(row, col) = buffer_alloc_base + y_offset + row * y_stride + col
```

**VP9 tile column guarantee (spec section 6.2):** Tile column boundaries occur at superblock boundaries (multiples of 64 luma pixels = 8 MI units). For tiles with indices `i` and `j` where `i != j`:

```
tile_i.col_end <= tile_j.col_start   (or vice versa)
```

**Non-aliasing proof for a single plane (Y):** Consider two tiles A and B. Without loss of generality, `A.col_end <= B.col_start`. For any row `r`:

- Tile A's byte range: `[y_offset + r*stride + A.col_start, y_offset + r*stride + A.col_end)`
- Tile B's byte range: `[y_offset + r*stride + B.col_start, y_offset + r*stride + B.col_end)`

Since `A.col_end <= B.col_start`, these intervals are disjoint for every `r`. The union across all rows remains disjoint because the stride is constant and the column ranges don't change per-row.

For tile_rows > 1, the same argument applies to the row dimension: tiles in different rows have `A.row_end <= B.row_start`, making their byte ranges disjoint regardless of column overlap.

**Cross-plane:** Y, U, V planes occupy non-overlapping regions of `buffer_alloc` (enforced by the allocation layout in `Yv12Buffer::alloc`). Splitting each plane independently preserves disjointness.

### 3.2 Border Regions

Border pixels live in the padding region OUTSIDE the visible `[0..y_height, 0..y_width]` rectangle. Tiles never write to border pixels — they write only within their `[mi_row_start*8..mi_row_end*8, mi_col_start*8..mi_col_end*8]` rectangle, which is strictly within the visible region. Border extension (`extend_frame_borders`) runs AFTER all tiles complete and AFTER the loop filter, on the main thread with exclusive `&mut yv12` access. No conflict.

### 3.3 The Unsafe Contract

```rust
/// # Safety contract for TileFrameView construction
///
/// The caller (the parallel tile dispatch in lib.rs) MUST guarantee:
///
/// 1. LIFETIME: The `Yv12Buffer` that views are derived from must
///    not be dropped, moved, or reallocated while any TileFrameView
///    exists. Enforced by the scoped thread pool: `yv12` is borrowed
///    by the scope's closure, preventing the main thread from touching
///    it until scope.join().
///
/// 2. DISJOINTNESS: The set of TileFrameViews constructed from a
///    single Yv12Buffer must have pair-wise non-overlapping pixel
///    rectangles. Enforced by using tile bounds from `tile_bounds()`,
///    which produces non-overlapping rectangles by VP9 spec
///    construction.
///
/// 3. EXCLUSIVE ACCESS: No other reference (& or &mut) to the
///    buffer_alloc slice may exist while TileFrameViews are alive.
///    Enforced by the main thread not touching `yv12` between view
///    construction and scope.join().
///
/// Violation of any of these is instant UB (data races, dangling
/// pointers, or aliasing &mut violations).
```

## 4. Integration Points

### 4.1 Changes to `decode_tile_intra` / `decode_tile_inter` Signatures

Current:
```rust
pub fn decode_tile_intra(
    tile_data: &[u8],
    bounds: TileBounds,
    params: &FrameDecodeParams,
    fc: &FrameContext,
    dst_frame: &mut Yv12Buffer,   // <-- changes
    coef_counts: Option<&mut CoefCountsBank>,
    cur_segment_ids: &mut [u8],
    dispatch: &SimdDispatch,
) -> Result<TileDecodeCtx, TileDecodeError>
```

New:
```rust
pub fn decode_tile_intra<D: TileFrameDst>(
    tile_data: &[u8],
    bounds: TileBounds,
    params: &FrameDecodeParams,
    fc: &FrameContext,
    dst_frame: &mut D,            // <-- generic over TileFrameDst
    coef_counts: Option<&mut CoefCountsBank>,
    cur_segment_ids: &mut [u8],
    dispatch: &SimdDispatch,
) -> Result<TileDecodeCtx, TileDecodeError>
```

Same pattern for `decode_tile_inter`. The internal `reconstruct_intra_planes` and `reconstruct_inter_block` functions also become generic over `D: TileFrameDst` (or accept the already-extracted `PlaneMut` slices, which is what they mostly do today).

**Minimising churn:** The deepest callers (`reconstruct_intra_block`, `reconstruct_inter_block`) already receive `dst: &mut [u8]` + `dst_stride: usize` or `dst_frame: &mut Yv12Buffer`. The intra path only needs `PlaneMut` (already extracted at line 1029-1037 of tile.rs). The inter path calls `dst_frame.y_plane_mut()` etc. at line 294-300 of reconstruct_inter.rs. Both will work unchanged as long as `TileFrameView` implements the same `y_plane_mut()` / `u_plane_mut()` / `v_plane_mut()` API.

### 4.2 Changes to the Worker Closure in Parallel Dispatch

Before (lib.rs ~1608-1666):
```rust
// Setup:
let scratch_buffers = self.tile_scratch_pool.take(num_tiles, &yv12);
let slots: Vec<TileSlot> = scratch_buffers.into_iter().map(|scratch| TileSlot {
    scratch: Mutex::new(Some(scratch)), ...
}).collect();
// Worker:
scope.submit(move || {
    let mut scratch = slot.scratch.lock().take();
    decode_tile_intra(..., &mut scratch, ...);
    *slot.scratch.lock() = Some(scratch);
});
// Post-scope:
yv12.merge_tile_rect_from(&scratch, ...);
```

After:
```rust
// Setup (main thread, before scope):
let tile_views: Vec<TileFrameView> = per_tile_bounds.iter().map(|bounds| {
    // SAFETY: bounds are non-overlapping (VP9 spec); yv12 lives
    // through the scope; no other &mut to yv12 exists.
    unsafe {
        TileFrameView::new(
            &mut yv12,
            bounds.mi_row_start * MI_BLOCK_PIXELS,
            bounds.mi_row_end * MI_BLOCK_PIXELS,
            bounds.mi_col_start * MI_BLOCK_PIXELS,
            bounds.mi_col_end * MI_BLOCK_PIXELS,
        )
    }
}).collect();
// Wrap in Mutex<Option<>> for the handoff pattern:
struct TileSlot {
    view: Mutex<Option<TileFrameView>>,
    seg_ids: Mutex<Option<Vec<u8>>>,
    counts: Mutex<Option<Box<CoefCountsBank>>>,
    result: Mutex<Option<Result<TileDecodeCtx, TileDecodeError>>>,
}
// Worker:
scope.submit(move || {
    let mut view = slot.view.lock().take().unwrap();
    decode_tile_intra(..., &mut view, ...);
    // view is dropped here (no need to put it back — it holds no
    // owned allocation, just raw pointers that are now invalid).
    *slot.result.lock() = Some(res);
});
// Post-scope: NO pixel merge. Only counts + seg_ids merge.
```

### 4.3 Impact on the Serial (Single-Tile) Path

The serial path (lib.rs ~1794-1823) passes `&mut yv12` directly to `decode_tile_intra`. With the trait approach, this continues to work unchanged — `Yv12Buffer` implements `TileFrameDst`. No performance regression (the trait methods inline to the same code as today).

### 4.4 Impact on `extend_frame_borders`

`extend_frame_borders` runs on the main thread AFTER:
1. All tile workers have joined (scope returned).
2. The loop filter has run (modifies pixels in-place on `&mut yv12`).

At this point, exclusive `&mut yv12` access is re-established (no `TileFrameView`s exist — they were moved into workers and dropped/consumed inside the scope). `extend_frame_borders` operates on the full buffer with no conflict.

**No change required** to `extend_frame_borders`.

### 4.5 Impact on the Loop Filter

The loop filter (`apply_loop_filter_to_frame`) runs on the main thread after scope.join(), receiving `&mut yv12`. By this point all `TileFrameView`s are gone and exclusive access is restored. Same as today.

**No change required** to the loop filter.

## 5. Conformance Guarantee

### 5.1 Bit-Exact Equivalence

This change is purely a data-transport optimization. The pixels written by each tile are identical regardless of whether they land in a scratch buffer (then copied) or directly in the output frame:

- Same decode functions (`decode_tile_intra` / `decode_tile_inter`).
- Same input data (tile bitstream, frame context, reference frames).
- Same pixel coordinates (frame-absolute `mi_row * 8`, `mi_col * 8`).
- Same reconstruction kernels (intra_predict, IDCT, MC).
- Same loop-filter (runs identically on the final pixel state).
- Same border extension (runs identically on the final pixel state).

The only difference is WHERE the pixels land during decode (scratch vs. output frame). Since the merge was a byte-for-byte copy from scratch → output at the same coordinates, removing the intermediate hop produces identical final state.

### 5.2 Verification Plan

1. **Conformance suite:** Run all 201/201 VP9 conformance vectors. Each vector produces a deterministic per-frame MD5. The test harness already asserts exact match against reference MD5s.
2. **Regression suite:** The existing `cargo test` suite exercises single-tile, multi-tile (2/4/8 columns), and multi-row tile configurations.
3. **Differential oracle:** Decode every vector with both the old (merge) and new (direct) paths enabled (behind a runtime flag during development) and assert byte-identical output frames.

## 6. Risks & Mitigations

### 6.1 Risk: Stacked Mutable Borrows / Miri Violations

**Scenario:** Constructing `TileFrameView` from `&mut yv12` while `yv12` is still reachable could trip Stacked Borrows under Miri.

**Mitigation:** Derive the raw pointers from `yv12.buffer_alloc.as_mut_ptr()` ONCE, then immediately release the `&mut` borrow (the raw pointer doesn't hold a borrow). Ensure no `&` or `&mut` reference to `yv12` exists between view construction and scope.join(). In practice: construct views, move them into `TileSlot`s, then enter the scope (which borrows nothing from `yv12`). After the scope, reclaim `&mut yv12` normally.

**Verification:** Run the test suite under `cargo +nightly miri test` (with the threading shim). Miri validates Stacked Borrows compliance.

### 6.2 Risk: Tile Boundary Off-by-One

**Scenario:** A tile's pixel writes bleed into the adjacent tile's column range due to a geometry bug (e.g. rounding error in the chroma column start).

**Mitigation:**
- Debug-mode bounds assertions in `TileFrameView::y_plane_mut()` etc. that verify every write offset falls within `[col_start, col_end)`.
- VP9's tile boundaries are always at MI boundaries (multiples of 8 luma pixels, which are multiples of 4 chroma pixels even at 4:2:0). There is no rounding hazard — the `>> ss_x` division is always exact because 8 >> 1 = 4, an integer.
- Fuzz testing with pathological tile widths (1-SB-wide tiles, max-tile-column configurations).

### 6.3 Risk: Inter-Prediction Reads from Adjacent Tile's Region

**Scenario:** An inter block's motion vector points to a pixel in the current frame (intra-BC or same-frame MC) that falls in an adjacent tile's column — reading from a region that another thread is concurrently writing.

**Mitigation:** VP9 inter-prediction reads from REFERENCE frames (stored in the `ref_frame_map` pool), NEVER from the current frame being decoded. Intra-BC (IntraBC) is a VP9 feature that does NOT exist in VP9 — it was introduced in AV1. Therefore no inter-frame decode path reads from the current output buffer. The only reads from `dst_frame` during decode are intra-prediction edge reads (above/left neighbours), which are always within the SAME tile's column range (intra-prediction reads from already-decoded blocks in the same tile, and VP9 resets prediction context at tile boundaries per spec section 6.3).

### 6.4 Risk: Intra-Prediction Reads Across Tile Boundary

**Scenario:** An intra block at the left edge of tile N reads "left" neighbour pixels that were written by tile N-1.

**Mitigation:** VP9 spec (section 6.3) mandates that intra-prediction at tile boundaries treats the boundary as a frame edge — `have_left = false` for the leftmost column of each tile (and `have_above = false` for the topmost row). The existing code already enforces this via `have_left_block` / `have_above_block` computation in the partition walker. Therefore no tile ever reads pixels written by another tile.

### 6.5 Risk: Performance Regression from Trait Dispatch

**Scenario:** The generic `D: TileFrameDst` adds overhead vs. direct `&mut Yv12Buffer`.

**Mitigation:** The trait has only simple accessor methods (`y_plane_mut`, `u_plane_mut`, etc.) that compile to a pointer offset + length computation. With monomorphization (generics, not `dyn`), the compiler inlines these completely — zero overhead vs. today's direct calls. Benchmark before/after to confirm.

### 6.6 Fallback Plan

If the design hits a blocker (e.g., a soundness issue with Stacked Borrows that cannot be resolved, or unexpected reads across tile boundaries in a corner case):

- **Gate the new path** behind a `direct_tile_write: bool` field in `Decoder` config.
- **Retain the existing scratch-pool path** as the fallback, selectable at runtime.
- Both paths produce identical output (verified by the differential oracle in 5.2), so switching between them is always safe.

## Appendix A: Sequencing Summary

```
Main thread                          Worker threads (scoped)
-----------                          ----------------------
1. Allocate yv12
2. Compute per-tile bounds
3. Construct TileFrameViews          
   (one per tile, from &mut yv12)
4. Build TileSlots (view + seg_ids + counts)
5. Enter worker scope  ─────────────►  Workers take views from slots
6. (blocked)                            decode_tile_{intra,inter}(view)
                                        Workers write pixels INTO yv12
                                        Workers store results + counts
7. Scope joins  ◄────────────────────  All workers done
8. Merge counts (additive, serial)
9. Merge seg_ids + mv_grid (serial)
10. Build frame MI grid
11. Loop filter (in-place on &mut yv12)
12. extend_frame_borders(&mut yv12)
13. Insert into ref pool
```

## Appendix B: Memory Savings

Per tile, the scratch pool currently holds a full-geometry `Yv12Buffer`:
- 1080p Y plane: `1088 * 1984 = ~2.1 MB` (with stride + border)
- UV planes: ~1.05 MB (4:2:0)
- Total per scratch: ~3.2 MB
- 8 tiles: ~25.6 MB of scratch buffers eliminated.

The `TileFrameView` struct is ~80 bytes (pointers + dimensions). Total overhead for 8 tiles: 640 bytes. This is a ~40,000x reduction in per-tile memory.
