### RVP9-BUG-KIL-00093 — valid unknown-size Clusters become false nesting

[RFC 8794 §6.2](https://www.rfc-editor.org/rfc/rfc8794.html#section-6.2) ends an unknown-sized element when a new valid element shares its direct parent. [RFC 9559 §5.1.3](https://www.rfc-editor.org/rfc/rfc9559.html#section-5.1.3) defines `Cluster` as a top-level Master element with unknown sizes allowed. Both crate walkers instead assign an unknown Cluster the enclosing Segment's end. The next physical Cluster is therefore visited inside the previous Cluster and consumes another depth slot. A sufficiently long valid live-style file returns `BadEbml("recognized container nesting depth exceeds limit")`.

### RVP9-BUG-KIL-00094 — unknown-size policy ignores element schema

The same generic parent-end rule is wrong in the other direction for elements that cannot be unknown-sized. RFC 8794 permits unknown sizes only for enabled Master elements. `SimpleBlock` and `Block` are binary leaves, so the current readers can merge their following siblings into one packet; the streaming path can allocate that full remainder. `TrackEntry` is a Master element but does not enable unknown size in the Matroska schema. The streaming finder rejects it, while the in-memory finder accepts it. One central allowlist and two separate regression shapes cover the shared schema-enforcement defect.

### RVP9-BUG-KIL-00095 — malformed frame tags trigger unbounded tiny reads

After reading `FRAME` plus one non-newline byte, the reader performs one direct file read per byte until newline or EOF. A large malformed input can therefore spend arbitrary time in tiny syscalls and can consume frame bytes as header text. The [official libvpx Y4M reader](https://chromium.googlesource.com/webm/libvpx/+/refs/heads/main/y4minput.c) uses a small fixed frame-header extension bound, so compatibility does not require the open-ended scan.

### RVP9-BUG-KIL-00096 — a zero-frame request can allocate 384 MiB

The maximum accepted 16384×16384 4:2:0 source is exactly 384 MiB. `Y4mReader::open` allocates that body before storing the requested limit, although the first pull returns immediately when the limit is zero. This finding deliberately excludes active full-frame reads: the retained one-time body allocation there has prior benchmark evidence for heap locality and is by design.

### RVP9-BUG-KIL-00097 — the public Y4M writer breaks its own round-trip

The writer documentation describes the 4:2:0 writer/reader round-trip, but only `Yuv440` is rejected before output. Calls using zero, odd, oversized Yuv420 dimensions or a zero framerate produce a complete textual header that the same module refuses to parse. `write_frame` explicitly assigns plane-length validation to callers; `write_header` makes no equivalent invalid-metadata precondition.

### RVP9-BUG-KIL-00098 — malformed WebM can amplify memory during track discovery

The in-memory finder scans each level completely before processing recognized children, retaining a tuple for every child. Repeating the five-byte encoding of an empty recognized container grows pending memory independently of useful track data. This is malformed Matroska, but the parser already promises typed errors for malformed input; exhaustion is not an acceptable error path. The streaming finder demonstrates the bounded traversal shape.

### RVP9-BUG-KIL-00099 — helper cursor semantics are internally inconsistent

`parse_header` starts reading at the caller's current `File` position, then seeks to absolute `header_length`. `IvfStreamWriter::new` writes at the current generic sink position, then `finish` overwrites absolute byte 24. Prefixed use therefore mispositions Y4M reads and corrupts unrelated IVF prefix bytes while leaving the real header count at zero. Neither public API requires a zero cursor.

## Draft requirement

RVP9-REQ-KIL-00100 proposes shared, schema-aware WebM structural parsing across streaming and in-memory reader modes. This is durable structural debt rather than a second defect record. The implementations duplicate size decoding, boundaries, traversal, depth policy, track selection, and block validation at `container.rs:591-877` and `:882-1206`; the defects above already show policy drift. The requirement preserves separate packet ownership/output shapes and asks for shared primitives plus differential parity oracles, not a wholesale rewrite.

## Confirmed quality debt — report only

- `container.rs:21-23` still shows the old `read_packets(&data)` shape even though the public function now takes a path and returns owned bytes plus ranges. This is a documentation correction, not a runtime defect.
- The tests exercise each WebM API separately but do not feed the same fixture matrix through both. RVP9-REQ-KIL-00100 carries the durable parity oracle; individual bug fixes should add focused regressions first.
- `md5.rs:204-241` stages visible planes and then pads another complete digest buffer. The earlier I/O review already held this as efficiency debt, and this pass found no new correctness failure or production measurement that justifies a duplicate bug or requirement.

- The wall-time cost of the Y4M frame-parameter loop and the practical memory ceiling of pending WebM containers are unmeasured. Their unbounded source behavior is confirmed.
- No exhaustive equivalence audit covered every malformed IVF/WebM byte offset. Only the cited paths are classified.

## Not reported — refuted, duplicate, or by design

- **Odd-origin 4:2:0 center crops are not proven misaligned.** Even source and crop dimensions center each plane independently; the proposed defect assumed luma and chroma origins must share the same integer phase. That requirement is not established, so the finding was refuted.
- **The active full-frame Y4M body allocation is deliberate.** Earlier matched measurements found that removing it changed heap locality and hurt production-width latency. Only the zero-frame path, which never processes a frame, was promoted.
- **Reverse selection among duplicate sibling `Tracks` elements is not a standalone bug.** The proposed trigger is noncanonical Matroska and showed no boundedness or safety failure. The implementation drift remains valid evidence for RVP9-REQ-KIL-00100.
- **Whole-file `read_packets` and `md5_of_file` are explicit owned-buffer APIs.** Shipped decode uses `PacketReader`; no new uncapped CLI path was found.
- **Per-packet streaming allocation is the current owned-packet contract.** No project packet-size ceiling exists, so a size cap would be a product decision rather than a confirmed defect.
- Closed I/O bugs RVP9-BUG-KILN-00041 through RVP9-BUG-KILN-00048 were checked where they overlapped this slice. None of the seven new records duplicates their fixed behavior.
