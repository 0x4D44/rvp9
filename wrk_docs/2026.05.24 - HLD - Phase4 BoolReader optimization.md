## 1. Problem Statement

### 1.1 Current throughput

The BoolReader (`crates/rvp9-core/src/entropy/bool_reader.rs`) is the innermost hot loop of the VP9 decoder. Every symbol -- every coefficient token bit, every mode/partition decision, every MV component -- flows through `BoolReader::read(prob)`.

**Measured baseline** (Track T T-3 ledger, 2026-05-24):

| Metric | Value |
|--------|-------|
| Median ns/call | **4.45 ns** |
| Min across runs | 4.33 ns |
| Cross-run spread | 0.14 ns (~3.1%) |
| Implied throughput | ~225 Mbits/s single-thread |
| Hardware | Intel Core Ultra 9 285HX (Arrow Lake-HX) |

**Per-frame call volume:** A 1080p frame with typical content generates approximately 500,000--800,000 `BoolReader::read` calls (driven by coefficient decode, which dominates). At 4.45 ns/call, the BoolReader alone consumes **2.2--3.6 ms per frame**.

### 1.2 Fraction of tile-decode time

From T-5 profiling data (tile_1x4 fixture, 4 threads):
- Per-tile decode: ~3,400 us (median per-tile worker time = join/4)
- BoolReader contribution (estimated): at 500k calls/frame and 4.45 ns/call = 2,225 us = **~23% of single-tile decode time** (or ~65% of the parallel-decode budget per tile under 4-thread dispatch)

This makes the BoolReader the single largest contributor to the entropy-decode phase, ahead of context lookups and dequant arithmetic.

### 1.3 Comparison to libvpx

libvpx's `vpx_read` (`vpx_dsp/bitreader.h:77-136`) uses the **same algorithm** as our Rust port:
- Identical split computation: `split = (range * prob + (256 - prob)) >> 8`
- Identical branch structure: `if (value >= bigsplit) { range = r->range - split; value -= bigsplit; bit = 1; }`
- Identical renormalization: table-lookup `vpx_norm[(unsigned char)range]` then shift

Key differences:
1. libvpx uses a **256-byte lookup table** (`vpx_norm[256]`) for renormalization; we use **LZCNT** (replaced in R.7). On modern x86 with LZCNT support, LZCNT is 1-cycle throughput vs the ~4-cycle L1 table load. This is a **rvp9 advantage**.
2. libvpx's `vpx_reader_fill` uses a raw `memcpy(&big_endian_values, buffer, sizeof(BD_VALUE))` + byte-swap macro; we use `u64::from_be_bytes(slice.try_into())`. Both compile to `MOV + BSWAP` under optimization. **Parity**.
3. libvpx has `static INLINE` (equivalent to `always_inline`) on `vpx_read`; we use `#[inline]` (a hint). LLVM typically honors this at `-O2+` for a function this small. **Near-parity**.
4. libvpx's C compilers (clang/gcc) may generate CMOV for the `value >= bigsplit` branch; Rust/LLVM may or may not, depending on the cost model. **Unknown -- requires disassembly audit**.

### 1.4 Honest assessment

The T-3 Phase-2 HLD (already in-tree) concluded that after R.7 (LZCNT) + R.8 (from_be_bytes batch fill) + Phase-1 hot/cold split, the rvp9 BoolReader is **already close to libvpx's codegen quality**. The remaining gap, if any, is in the 0--15% range -- well within bench-noise territory for whole-frame measurements. This Phase-4 HLD identifies targeted strategies that could yield cumulative gains in that range without algorithmic changes that would break conformance.

## 2. Analysis: Current vs Optimal

### 2.1 Structure of `read()` (bool_reader.rs:79-117)

```rust
pub fn read(&mut self, prob: u8) -> u8 {
    let split: u32 = (self.range * u32::from(prob) + (256 - u32::from(prob))) >> 8;
    if self.count < 0 { self.fill(); }      // Branch A: refill check
    let bigsplit: u64 = (split as u64) << (BD_VALUE_SIZE - 8);
    let mut range = split;
    let mut bit: u8 = 0;
    if value >= bigsplit {                   // Branch B: bit decision
        range = self.range - split;
        value = value.wrapping_sub(bigsplit);
        bit = 1;
    }
    let shift = ((range & 0xff) as u8).leading_zeros() & 7;
    range <<= shift;
    value = value.wrapping_shl(shift);
    count -= shift as i32;
    // store back
    self.value = value; self.count = count; self.range = range;
    bit
}
```

### 2.2 Branch analysis

**Branch A** (`count < 0` -- refill trigger): Fires roughly once per 7-8 calls (the fill loads 48-56 bits; each read consumes 1-7 bits of shift). Prediction accuracy is very high (~87% not-taken). This is well-handled by the hot/cold split (`fill()` fast-path inlined, `fill_slow()` out-of-line). Minimal further gain available.

**Branch B** (`value >= bigsplit` -- bit decision): This is the **primary optimization target**. For the coefficient-decode prob mix (50% p=128, 30% p=32, 20% p=224):
- At p=128: bit outcome is roughly 50/50 -- **maximally unpredictable**
- At p=32: bit=1 occurs ~87% of the time -- well-predicted
- At p=224: bit=0 occurs ~87% of the time -- well-predicted
- Weighted average: ~50% of calls are at p=128, contributing ~3.5 mispredictions per 8 calls. Branch predictor hit rate for the combined distribution: ~70-75%.

A **misprediction penalty** on modern Intel cores is ~12-15 cycles. At 25-30% misprediction rate, the expected per-call penalty is ~3-4 cycles -- a significant fraction of the ~14-cycle total.

### 2.3 Does LLVM generate CMOV?

The structure of the Rust code is:
```rust
if value >= bigsplit {
    range = self.range - split;
    value = value.wrapping_sub(bigsplit);
    bit = 1;
}
```

This involves **three** conditional assignments (range, value, bit). LLVM's cost model for CMOV vs branch depends on:
- Number of instructions in the "taken" path (here: 3 ops)
- Whether the condition is data-dependent (yes -- `value` is unpredictable)
- Target CPU cost model

On modern x86_64 with `-C opt-level=3 -C target-cpu=native`, LLVM **may or may not** emit CMOV here. The three-assignment pattern is at the edge of LLVM's heuristic threshold (it prefers CMOV for 1-2 ops, but is conservative at 3+). **This is the single highest-impact investigation item**: if LLVM is generating a branch, restructuring for CMOV could save 2-3 ns/call (the misprediction penalty amortized).

### 2.4 Refill strategy comparison

| Aspect | libvpx | rvp9 |
|--------|--------|------|
| Fast-path trigger | `count < 0` | `count < 0` (identical) |
| Batch size | 8-byte load + BSWAP | 8-byte load + BSWAP (identical) |
| EOF handling | Byte-loop with `LOTS_OF_BITS` sentinel | Byte-loop (cold, out-of-line) |
| Call overhead | `static inline` -- always inlined | `#[inline]` -- usually inlined |

The refill strategies are **already at parity**. No gain from further refill changes.

### 2.5 Identified inefficiencies (ranked)

1. **Branch B misprediction** (~2-4 cycles/call on mixed-prob workloads) -- highest impact
2. **Store-to-load forwarding**: `self.value`, `self.range`, `self.count` are written at the end of each call and immediately re-read at the start of the next call. If the function is not fully inlined at the call site, this creates a store-forward dependency. In `decode_coefs`, LLVM should inline `read()`, keeping these in registers across iterations.
3. **`fill()` call-site overhead**: Even on the not-taken path, the branch + call setup occupies a fetch/decode slot. Moving the fill check to after the bit decision (where `count` has already been decremented) would let the refill happen one call later, but this changes semantics.
4. **Bound check on `buffer[pos..pos+8]`** in `fill()`: The `try_into().expect()` generates a panic path that LLVM must lay out. The `bits_left > BD_VALUE_SIZE` guard should let LLVM elide this, but if not, it adds icache pressure.

## 3. Optimization Strategies (ranked by expected impact)

### Strategy A: Branchless bit-decision restructuring

**Expected impact:** 15-25% reduction in ns/call (if LLVM is currently branching)
**Risk:** Low (pure refactoring of control flow; arithmetic is identical)
**Effort:** 1-2 days

#### Rationale

The `if value >= bigsplit` branch is the **only** hard-to-predict branch in the hot path. Converting it to branchless (CMOV) eliminates the misprediction penalty entirely, replacing it with the CMOV latency (~1 cycle on modern x86).

#### Implementation

Replace the branching pattern:
```rust
let mut range = split;
let mut bit: u8 = 0;
if value >= bigsplit {
    range = self.range - split;
    value = value.wrapping_sub(bigsplit);
    bit = 1;
}
```

With an arithmetic branchless pattern:
```rust
// Compute both outcomes unconditionally
let range_if_lps = split;                      // "lower probability symbol"
let range_if_mps = self.range - split;         // "more probable symbol"
let value_if_mps = value.wrapping_sub(bigsplit);

// Branchless select based on comparison
let bit = u8::from(value >= bigsplit);
let sel = u64::from(bit);  // 0 or 1

// Arithmetic select: bit=0 keeps (range_if_lps, value), bit=1 takes (range_if_mps, value_if_mps)
// Use wrapping arithmetic to avoid branches:
//   range = lps + (mps - lps) * sel = lps + (range - 2*split) * sel
//   value = value - bigsplit * sel
range = split.wrapping_add((self.range.wrapping_sub(split.wrapping_shl(1))).wrapping_mul(sel as u32));
// Simpler: just use the two precomputed values
range = if cfg!(target_arch = "x86_64") {
    // Force CMOV via select pattern LLVM recognizes
    [range_if_lps, range_if_mps][sel as usize]
} else {
    range_if_lps ^ ((range_if_lps ^ range_if_mps) & (sel as u32).wrapping_neg())
};
value = value.wrapping_sub(bigsplit & sel.wrapping_neg());
```

The most reliable way to force CMOV in Rust without inline asm:
```rust
let cond = value >= bigsplit;
let bit = u8::from(cond);
let mask = u64::from(cond).wrapping_neg(); // 0x0000... or 0xFFFF...

// value update: subtract bigsplit only if cond
value = value.wrapping_sub(bigsplit & mask);

// range update: select between split (false) and (self.range - split) (true)
let range_diff = self.range - split - split; // = (range-split) - split
range = split.wrapping_add((range_diff) & (mask as u32));
```

**Key insight:** The mask-based select (`x & mask`) is the canonical pattern LLVM converts to CMOV. If LLVM's cost model still chooses a branch, the fallback is `core::hint::black_box`-style trickery or `#[cfg(target_arch)]` inline asm for the critical two CMOV instructions.

#### Verification

After implementation, **disassemble** with `cargo asm` or `objdump` to confirm CMOV generation. If LLVM still emits a branch, escalate to Strategy A.2 (minimal inline asm for just the two CMOVs).

### Strategy B: Caller-side loop fusion (tree read specialization)

**Expected impact:** 10-20% on tree-heavy paths (partition decode, mode decode); ~5% on coefficient decode
**Risk:** Medium (more code to maintain, must remain bit-exact)
**Effort:** 2-3 days

#### Rationale

`BoolReader::read_tree` (bool_reader.rs:163-172) is a generic loop:
```rust
pub fn read_tree(&mut self, tree: &[i8], probs: &[u8]) -> i8 {
    let mut i: i8 = 0;
    loop {
        let bit = self.read(probs[(i >> 1) as usize]);
        i = tree[i as usize + bit as usize];
        if i <= 0 { return -i; }
    }
}
```

For the VP9 partition tree (`[-NONE, 2, -HORZ, 4, -VERT, -SPLIT]`), this always reads 1-3 bits. The generic loop has:
- Per-iteration overhead: array index bounds check, comparison, loop branch
- Inability to batch multiple reads without intermediate store-backs

A **specialized** partition-tree reader can unroll the 3-level binary decision into straight-line code with exactly 1-3 `read()` calls and no loop overhead.

#### Implementation

Add specialized methods to BoolReader or as free functions:

```rust
/// Decode a VP9 partition type (0-3) using exactly the partition tree structure.
/// Equivalent to read_tree(VP9_PARTITION_TREE, probs) but unrolled.
#[inline]
pub fn read_partition(&mut self, probs: &[u8; 3]) -> u8 {
    if self.read(probs[0]) == 0 {
        0 // PARTITION_NONE
    } else if self.read(probs[1]) == 0 {
        1 // PARTITION_HORZ
    } else if self.read(probs[2]) == 0 {
        2 // PARTITION_VERT
    } else {
        3 // PARTITION_SPLIT
    }
}
```

Similar specializations for:
- `vp9_intra_mode_tree` (10 leaves, max 4 levels)
- `vp9_inter_mode_tree` (4 leaves, max 3 levels)
- `vp9_switchable_interp_tree` (3 leaves, max 2 levels)

The coefficient token tree is already manually unrolled in `detokenize.rs` (lines 474-576) -- it does not use `read_tree` but instead has explicit `reader.read(prob[...])` calls for EOB, ZERO, ONE, and the Pareto-8 sub-tree. No further unrolling needed there.

#### Why this helps

1. Eliminates bounds checks on `tree[]` and `probs[]` array indexing (the specialization knows the exact shape).
2. Gives LLVM more context for register allocation (all probabilities are visible at compile time as fixed-offset loads from a single base pointer).
3. Removes the generic loop branch and its prediction overhead.

### Strategy C: Register-pinning via caller-side batching

**Expected impact:** 5-15% on coefficient-decode hot loop
**Risk:** Medium (requires restructuring `decode_coefs` inner loop)
**Effort:** 3-5 days

#### Rationale

In `decode_coefs` (detokenize.rs:465-618), the inner loop calls `reader.read()` 3-15 times per coefficient (EOB check, ZERO run, ONE-vs-higher branch, category extension bits, sign bit). Between calls, the code:
1. Updates `token_cache` (memory store)
2. Increments `c` and recomputes `ctx` (memory loads from `scan.neighbors`)
3. Reloads `prob_local` from `coef_probs[band][ctx]`

Each `reader.read()` call writes `(value, range, count)` back to `self` and the next call re-reads them. If LLVM fully inlines `read()` into the `decode_coefs` loop body, it can keep `(value, range, count)` in registers across multiple reads. But the interleaved memory operations (token_cache writes, neighbor lookups) may cause LLVM to spill the BoolReader state.

#### Implementation

Restructure the coefficient decode loop to minimize memory traffic between consecutive `read()` calls:

1. **Hoist reader state to locals**: At the top of the `decode_coefs` loop, destructure `(value, range, count)` into local variables. Call a sequence of `read`-like operations that operate on these locals. Write back to `self` only at the end of each scan-position.

2. **Batch the fixed-structure reads**: For the EOB + ZERO + ONE-vs-higher sequence, create a helper that performs all three decisions in a single function, keeping the reader state in registers throughout:

```rust
#[inline(always)]
fn decode_token_class(
    value: &mut u64,
    range: &mut u32,
    count: &mut i32,
    buffer: &[u8],
    pos: &mut usize,
    prob: &[u8; 3], // [eob_prob, zero_prob, one_prob]
) -> TokenClass { ... }
```

3. **Defer context updates**: Accumulate token-cache writes in a small stack buffer and flush after the BoolReader state is stored back.

This is the most invasive strategy and has the highest risk of introducing subtle bugs. It should only be pursued if Strategy A + B together do not yield sufficient gains.

### Strategy D: SIMD-assisted decode (research only)

**Expected impact:** Unknown (potentially 2-4x for specific patterns, but high integration cost)
**Risk:** Very high (algorithmic change, conformance risk, platform-specific)
**Effort:** 2-4 weeks (research + prototype)
**Status:** OUT OF SCOPE for Phase 4. Documented for completeness.

#### Concept

Asymmetric Numeral Systems (ANS) or vectorized range coding can decode multiple symbols in parallel by exploiting the fact that independent probability lookups can be computed ahead of time. However:

1. VP9's coefficient decode has **serial data dependencies**: each bit's probability depends on the previous bit's outcome (via `token_cache` and `ctx` updates). True parallelism is limited.
2. Converting from VP9's range coder to ANS would break bit-exact conformance with the spec.
3. SIMD gather of probability tables could speed up the `coef_probs[band][ctx]` lookup, but the lookup is a single 3-byte load that fits in L1 -- SIMD adds no value.

**Verdict:** Not applicable to VP9's serial entropy coding structure. A future codec (AV1's multi-symbol reader) could benefit, but VP9's single-bit-at-a-time design fundamentally limits parallelism.

## 4. Recommended Implementation Order

### Phase 4.1: Disassembly audit + branchless restructuring (Strategy A)

**Priority:** FIRST -- highest ROI, lowest risk
**Expected gain:** 15-25% on microbench (if LLVM is currently branching); 0% if already CMOV
**Timeline:** 1-2 days

Steps:
1. Run `cargo asm --release -p rvp9-core "bool_reader::BoolReader::read"` or equivalent `objdump` to inspect the generated x86_64 assembly.
2. Identify whether the `value >= bigsplit` comparison generates a conditional branch (`JB`/`JAE`) or a CMOV sequence.
3. If branching: apply the mask-based branchless pattern from Strategy A.
4. Re-run microbench (`dsp-microbench -- bool_reader`). Target: median < 3.8 ns/call (>15% improvement).
5. If microbench passes threshold: run conformance gate (201/201) and `decode-throughput` on testsrc_1080p30 t=4.

### Phase 4.2: Tree-read specialization (Strategy B)

**Priority:** SECOND -- moderate gain on mode/partition paths
**Expected gain:** 5-10% on partition-heavy content; ~3% on coefficient-dominated content
**Timeline:** 2-3 days

Steps:
1. Add `read_partition`, `read_intra_mode`, `read_inter_mode` specialized methods.
2. Wire them into the decoder's mode-read call sites (replacing `read_tree` calls).
3. Verify bit-exactness via conformance gate.
4. Micro-bench the partition-read path specifically (add a `partition_tree` subcommand to `dsp-microbench`).

### Phase 4.3: Caller-side register pinning (Strategy C)

**Priority:** THIRD -- only if 4.1+4.2 do not yield sufficient gains
**Expected gain:** 5-15% (highly dependent on LLVM's inlining/RA decisions)
**Timeline:** 3-5 days

This is the most invasive change and should only proceed if:
- Phase 4.1 yields <10% improvement (indicating LLVM already CMOVs)
- Phase 4.2 yields <5% improvement
- The combined shortfall vs target is >10%

### Measurement protocol

For each phase:
1. **Microbench** (`dsp-microbench -- bool_reader`): median of 5 runs, report min/max. Must show >= 10% improvement (per T-3 ledger decision criterion) to clear bench-noise.
2. **Full-frame benchmark** (`decode-throughput` on testsrc_1080p30 t=4): MWU test at p<0.05. Must show directionally consistent improvement.
3. **Conformance gate** (`cargo test -p rvp9-harness --test conformance --release`): must pass 201/201.

## 5. Conformance Guarantee

### 5.1 Invariant

The BoolReader **must produce identical decoded symbols** for any given `(buffer, prob_sequence)` input, regardless of internal optimization. This is non-negotiable: a single bit flip in the entropy decoder propagates to catastrophic frame corruption.

### 5.2 Verification strategy (layered)

**Layer 1: Unit round-trip tests** (existing, bool_reader.rs:360-451)
- `round_trip_bits_p128`: 200 bits at p=128
- `round_trip_skewed_probabilities`: 150 bits at extreme probs (32, 224)
- `round_trip_literals`: 5x8-bit literals
- `over_read_sets_error`: EOF semantics

These catch gross logic errors but are insufficient alone.

**Layer 2: Differential oracle via `snapshot()`/`restore()`**

For any code change, add a test that:
1. Encodes a 10,000-bit sequence with a mixed-prob model (same as microbench).
2. Decodes it with BOTH the old implementation (captured as a `_ref` function in `#[cfg(test)]`) and the new implementation.
3. After EVERY `read()` call, asserts `cursor_state()` matches between old and new.

The `BoolReader::snapshot()` and `BoolReaderSnapshot::from_parts()` APIs (bool_reader.rs:298-357) already support this pattern.

**Layer 3: Conformance corpus** (load-bearing safety net)

`cargo test -p rvp9-harness --test conformance --release` -- 201 VP9 test vectors. Any divergence in `BoolReader::read` manifests as wrong coefficients -> wrong pixels -> test failure at frame N. This is the ultimate gate.

**Layer 4: Microbench output validation**

The `dsp-microbench -- bool_reader` run already decodes 1,000,000 bits and asserts `!reader.has_error()`. Add an assertion that the final `cursor_state()` matches a golden value computed from the deterministic `(bit, prob)` sequence. This catches any implementation that produces wrong bits even when the round-trip tests pass (e.g., off-by-one in refill that produces correct bits for short sequences but diverges at scale).

## 6. Risks

### R1: Over-optimization that LLVM undoes at higher opt levels

**Severity:** Medium
**Description:** Hand-crafted branchless patterns (mask arithmetic, computed selects) may be "undone" by LLVM's optimization passes, which can convert branchless code back to branches if its cost model deems that profitable (e.g., on architectures without CMOV, or when the branch is predicted well enough).

**Mitigation:**
- Always verify with `cargo asm` after implementation.
- If LLVM consistently reverts to branches, the fallback is 4 lines of inline asm (`cmp; cmovae; cmovae; setae`) that override the optimizer. This is a last resort.
- Pin the optimization verification to the project's `rust-toolchain.toml` so a Rust version bump doesn't silently regress codegen.

### R2: Platform-specific behavior (x86_64 vs aarch64)

**Severity:** Medium
**Description:** CMOV is an x86_64 concept. On aarch64, the equivalent is conditional select (`CSEL`/`CSINV`). The branchless pattern should compile to `CSEL` on ARM, but ARM's branch predictor is often better than x86's, making branchless less valuable there.

**Mitigation:**
- The branchless restructuring uses standard Rust (no inline asm) so it compiles on all targets.
- If profiling on aarch64 shows a regression from branchless, add `#[cfg(target_arch = "x86_64")]` gating for the branchless variant, with the original branching code as the fallback.
- Phase 4 focuses on x86_64 (the dev box and primary target). aarch64 optimization is a separate future effort.

### R3: Breaking the existing test suite

**Severity:** Low (if Layer 2-4 verification is implemented)
**Description:** Any change to `read()` that alters even one bit propagates through the entire decoder.

**Mitigation:** The four-layer verification strategy (Section 5.2) catches this. The conformance gate (201 vectors) is the nuclear option -- it is structurally impossible to pass conformance with a wrong `read()` implementation. Run it before every commit.

### R4: R.15 regression precedent (icache bloat from over-inlining)

**Severity:** High (proven precedent)
**Description:** Commit 4286269 documented a 23% regression from `#[inline]` on the full `fill()` body. Any Phase 4 change that increases the inlined code size of `read()` risks repeating this.

**Mitigation:**
- Strategy A (branchless) should REDUCE instruction count (eliminating the branch + its taken-path prefix is fewer bytes than the mask arithmetic).
- Monitor `cargo bloat` diff on `bool_reader::BoolReader::read` before/after.
- Strategy C (caller-side batching) explicitly does NOT inline additional code into `read()` -- it restructures the *caller*.
- If any change increases the `read()` machine-code footprint by >20%, run the full `decode-throughput` sweep before shipping.

### R5: Benchmark-noise floor hides real gains

**Severity:** High (structural)
**Description:** The T-3 ledger documents a 3.1% cross-run spread on the microbench and ~5% sigma on `decode-throughput`. Any improvement <10% is statistically indistinguishable from noise on a single bench run.

**Mitigation:**
- The decision criterion from T-3 stands: ship only if median ns/call drops by >= 10% AND full-frame bench is directionally consistent.
- If Strategy A yields <10% on the microbench, honestly report it as "NOISE" and do not ship.
- Invest in reducing bench noise (CPU affinity, governor=performance, isolated cores) to lower the detection threshold for future work.

### R6: Thread-safety of any static/global state

**Severity:** Low
**Description:** `BoolReader` is a stack-local struct with no shared state. None of the proposed strategies introduce shared mutable state.

**Mitigation:** N/A -- all changes are to the `read()` method body, which operates entirely on `&mut self`.
