# Same-entry motion-search work census

The completed [Ducks operation census](evidence/2026-09-27-cross-codec-last-search-work/README.md) tripped the topology guard: RVP9 has 1.041× LAST entries but 0.469× four-way diamond SAD calls. The proposed checked-slice adapter is not supported as the primary parity lever by these counts. This document preserves the diagnostic design; the census result is not a CPU benchmark or an optimization approval.

The integrated encoder is 1.057638× pinned libvpx on equal-clip 60-frame CPU6/CBR1260 process CPU. Its largest clip gap is Ducks (~1.17×). Exact production-PGO instruction profiles place substantial Ducks work in full-pel and sub-pel search, but sampled symbol shares cannot price a removable operation. The [paired entry census](evidence/2026-09-26-paired-fullpel-entry-census/README.md) counted 393,364 RVP9 LAST full-pel entries versus 378,013 libvpx entries (1.041×). RVP9 also runs 236,166 GOLDEN full-pel searches while libvpx uses a different GOLDEN path. Since skipping GOLDEN changes output, this design compares **LAST with LAST**, then tests whether the per-entry work differs.

## First discriminator: count operations, not time

Build diagnostic-only, single-thread variants of both codecs from pinned source. For each LAST entry and block size, count diamond starts, visited steps, in-limit four-way steps, actual SAD4D batches and scalar SAD calls, refinement calls, and variance scores. Count sub-pel variance probes only where the call boundary can be attributed to the same LAST search without guesswork. Tag each count at the search call boundary, not by a sampled source line. Preserve each codec's canonical IVF hash and pin executable/source/input identities. Do not compare instrumented CPU times: the counters themselves add work.

The existing RVP9 code resolves four reference slices with `block_at` before a batched SAD4D call in `crates/rvp9-core/src/mv_search/full_pixel.rs:sad4d_at_from_source`; pinned libvpx computes four pointer offsets and calls `sdx4df` in `third_party/libvpx/vp9/encoder/vp9_mcomp.c:vp9_diamond_search_sad_c`. This is a *mechanism hypothesis*, not a measured saving. RVP9's MV-space `all_in` does not prove all four rectangles lie inside the visible plane, so a fast pointer path would need a separately proved per-search pixel-space box and a checked fallback. The prior checked-footprint AVX2 sub-pel rewrite was exact but slowed whole-encoder CPU; source-level simplification is not retention evidence.

If actual operation counts differ materially, the gap may be search topology rather than per-operation overhead; stop before rewriting the adapter. If counts are close, measure the same LAST entry on both codecs with bounded, calibrated same-host cycle totals, and reconcile the summed excess with process CPU. To close the current equal-clip gap through Ducks alone requires about 2.2% of Ducks CPU, roughly 48 ms at a 2.2 s Ducks encode. A smaller demonstrated ceiling rejects the candidate. Only then prototype one exact adapter change, compare old/new search results and boundary behavior with a deliberate-red differential, validate AArch64 and native x86, require canonical IVFs, and retain only repeatable paired production-PGO process-CPU gains. No new output-changing search policy follows from this census.

Tripwires: ambiguous LAST attribution; different encode outputs; a large per-entry operation-count mismatch; insufficient calibrated cycle gap; any replay mismatch; or a flat/slower paired production-PGO screen. The consultant's cross-codec component-share estimates are directional only because the captures, inlining and codecs differ; they are not entered as a CPU-saving estimate.
