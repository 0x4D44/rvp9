# HLD — Entropy / detokenize parity with libvpx

**Date:** 2026-05-27
**Author:** design agent (entropy/detokenize workstream)
**Status:** DRAFT — for team-lead review, not yet signed off
**Scope:** `BoolReader::read` + the coefficient token loop
(`decode_coefs` / `decode_block_tokens`). Strictly entropy/detokenize.
Does NOT touch intra prediction, IDCT, convolve, or loop filter.

**Parity target:** libvpx `vp9/decoder/vp9_detokenize.c` (`decode_coefs`,
`vp9_decode_block_tokens`) + `vpx_dsp/bitreader.{h,c}` (`vpx_read`,
`vpx_reader_fill`).

---

## 0. TL;DR

The bool-reader (H1) is **already a faithful, well-tuned libvpx port** —
wide u64 accumulator, big-chunk `from_be_bytes` refill, lzcnt renorm,
hot/cold split. Refill is **not** the problem (112 reads per fill;
refill amortised to noise). H1 is **largely REFUTED**, with ONE residual
structural gap worth a cheap experiment (register hoisting across the
loop, §3.1).

The token loop (H2) is **CONFIRMED structurally slower than libvpx**, and
the cause is specific and measured: a **two-pass dequant split** (Wave H
H5/H6) that libvpx does NOT have. Our `decode_coefs` pushes every
non-zero coefficient into four `Vec` scratch arrays in pass 1, then in
pass 2 does an **`OnceLock` atomic load + indirect function-pointer call**
into an AVX2 `plane_dequant_finisher` — on EVERY transform block.
libvpx fuses the dequant multiply + writeback inline into the token loop
(no scratch, no second pass, no indirect call).

The measured kicker: **96.2% of `decode_coefs` calls have eob == 0**
(all-zero block) and **97.4% of finisher calls process fewer than 8
entries** — so the AVX2 main loop (which needs ≥8 entries) almost never
fires. We pay the full two-pass + indirect-dispatch overhead on every
block to vectorise 2.6% of them, and the dominant all-zero block — where
libvpx does literally one `read()` and `break` — gets saddled with Vec
clears + an empty indirect finisher call.

**Proposed design:** revert the token inner loop to a libvpx-faithful
**single fused pass** (inline dequant + writeback), deleting the scratch
arrays and the `plane_dequant_finisher` dispatch from the decode path.
Estimated reclaim: **30–55% of the detokenize bucket** (the ~17%
`decode_block_tokens` slice), i.e. **~5–9 percentage points of total
serial decode time**. Confidence: H2 high, H1 medium.

## 1. Measured root-cause

### 1.1 Method

Throwaway instrumentation (process-wide atomics, gated `RVP9_INSTR=1`,
reverted after measurement) wired into `BoolReader::{read,fill}` and the
tail of `decode_coefs`. Run via the head-to-head bench on `foreman-fp1`
(profile-0, the only profile-0 fixture present in this worktree;
the intra-heavy gate vectors `tile_1x4` / `testsrc_1080p30` are not
fetched here — see §1.4 for why the conclusion still generalises and
strengthens for them). 200 timed frames, single-thread.

Static comparison against the vendored libvpx C in `third_party/libvpx`.

### 1.2 Raw numbers (foreman-fp1, t=1, 200 frames)

```
read() calls        : 2,848,474
fill() calls        : 25,306        → 112.6 reads per fill
avg renorm shift    : 0.874
decode_coefs calls  : 869,682
tokens (nonzero)    : 206,942
avg eob per block   : 0.637
avg reads per block : 3.28
avg reads per token : 13.76
finisher <8 entries : 847,299  (97.4%) — AVX2 main loop does NOT fire
finisher >=8 entries:  22,383  ( 2.6%) — AVX2 main loop fires
EOB histogram (blocks):
  eob==0 : 830,858  (95.5% of all blocks; 96.2% of finisher calls)
  eob==1 :   6,294
  eob==2 :   2,410
  eob==3 :   1,857
  eob==4 :   1,456
  eob 5-8:   5,756
  eob9-16:  14,058
  eob 17+:   6,993
```

### 1.3 What the numbers say

**The all-zero block dominates.** 95.5% of transform blocks decode to
eob == 0. libvpx's path for that block is: read the EOB bit (one
`read_bool`), it returns 0, `break`, and `decode_coefs` returns 0 having
written nothing (the dqcoeff buffer was memset by the caller). That is
**one bool read and a function return**.

Our path for the SAME all-zero block is heavier:
1. `read(prob[EOB_CONTEXT_NODE])` → 0, break. (Same as libvpx — fine.)
2. But before the loop we entered `DECODE_COEFS_SCRATCH.with_borrow_mut`
   (a `RefCell` borrow), zeroed `token_cache[..n_coeffs]` (up to 1024
   bytes for a 32×32), and `clear()`ed four `Vec`s.
3. After the loop (with zero entries) we still call
   `crate::dsp::get_ref()` — an **`OnceLock` atomic load** — and then make
   an **indirect function-pointer call** to `plane_dequant_finisher`,
   which immediately returns because the scratch is empty.

So the dominant case pays: a RefCell borrow, a token_cache memset whose
width scales with tx size, four Vec clears, an atomic load, and an
indirect call — to accomplish what libvpx does in one read + return.

**The two-pass vectorisation almost never pays off.** The AVX2 finisher
needs ≥8 coefficients to run its main loop. Only 2.6% of finisher calls
reach that; 97.4% fall straight through to the scalar tail (a plain
scalar loop, identical math to what libvpx does inline — but reached via
an indirect call after a deposit-to-Vec pass). We built a SIMD dequant
path and pay its setup cost on every block to serve 1-in-40 blocks.

**Even the non-zero blocks pay double.** For a block with eob = N
non-zero coefficients, libvpx does the multiply `(val*dqv)>>dq_shift`
and the writeback `dqcoeff[scan[c]] = v` inline, in the same iteration
that decoded the token — the value is already in a register. Our pass 1
instead does four `Vec::push` calls per coefficient (`raster`, `dqv`,
`val`, `sign`), then pass 2 re-reads all four arrays and does the
multiply + scatter. That is extra stores + reloads + bounds-amortised
pushes for zero algorithmic benefit on the small-eob blocks that make up
the bulk of non-zero blocks (eob 1–4 is 12k of the 39k non-zero blocks).

**The bool reader itself is the hot primitive, and it is tight.** 2.85M
`read()` calls, 13.76 reads per non-zero token, 3.28 reads per block.
The renorm shift averages 0.87 (cheap). Refill fires once per ~113
reads, so the big-chunk refill is fully amortised. There is no refill
pathology.

### 1.4 Why this generalises (and strengthens) for the gate fixtures

`foreman-fp1` is inter-heavy real motion. The gated parity fixtures
(`testsrc_1080p30`, `tile_1x4`) are keyframe/intra-heavy and low-motion
(per the 2026-05-26 profiling journal). Low-motion / intra-heavy content
has **even more** all-zero and low-eob transform blocks than foreman, so
the eob==0 dominance — and therefore the relative cost of the
per-block two-pass + indirect-dispatch overhead — is **higher**, not
lower, on the actual parity targets. The 17.2% `decode_block_tokens` +
7.5% `bool_reader::read` split from the journal is consistent with "a
fixed per-block overhead tax multiplied across a huge number of mostly-
trivial blocks."

## 2. H1 / H2 verdict

### H1 (bool reader): largely REFUTED

`BoolReader::read` and `fill` are a faithful, already-optimised port of
`vpx_read` / `vpx_reader_fill`:

| Aspect | libvpx | rvp9 | Verdict |
|---|---|---|---|
| Accumulator width | `BD_VALUE = size_t` (u64) | `u64` | Match |
| Renorm | `vpx_norm[range&0xff]` LUT | `leading_zeros()&7` (lzcnt) | rvp9 arguably faster (R.6) |
| Refill | `memcpy`+`HToBE64`, big chunk | `from_be_bytes`, big chunk (R.8) | Match |
| Refill frequency | — | 1 per 112 reads (measured) | Not a hotspot |
| Hot/cold split | single fn | fast inline + `#[cold]` slow (R.15) | rvp9 arguably better for icache |
| Inlining | `static INLINE` (always inlines) | `#[inline]` (hint) | **Residual gap — see §3.1** |

The one structural difference that survives: **libvpx hoists
`value`/`range`/`count` into function-local registers for the entire
duration of `decode_coefs`** (explicit source comment, `vp9_detokenize.c`
lines 148-149: *"Keep value, range, and count as locals. The compiler
produces better results with the locals than using r directly."*). Its
inner `read_bool` takes `BD_VALUE *value, int *count, unsigned int
*range` by pointer and operates on those hoisted locals, syncing back to
the `vpx_reader` struct only on loop exit (lines 257-259).

Our `BoolReader::read` reads and writes `self.value`/`self.range`/
`self.count` (struct fields behind `&mut self`) on **every** call. With
`#[inline]` and one hot call site, LLVM's SROA *may* already keep these
in registers across the loop — but this is unverified (the MSVC/PDB
toolchain frustrated symbol-level disasm; samply's Rust-name resolution
also fails per the journal). This is the only open H1 question and it is
cheap to settle experimentally (§3.1).

### H2 (token loop): CONFIRMED

`decode_coefs` is structurally slower than libvpx `decode_coefs` because
of the **Wave H H5/H6 two-pass dequant split**, which has no libvpx
analogue:

- libvpx: single fused loop, inline `v=(val*dqv)>>dq_shift`, inline
  `dqcoeff[scan[c]]=v`, no scratch, no indirect call.
- rvp9: pass 1 pushes `(raster, dqv, val, sign)` per coef into four
  `Vec`s; pass 2 does an `OnceLock` atomic load (`dsp::get_ref()`) + an
  indirect call to `plane_dequant_finisher`, whose AVX2 main loop fires
  on only 2.6% of calls.

This was a well-intentioned vectorisation (separate dequant arithmetic so
it can be done 8-wide), but the measured workload — dominated by eob==0
and eob 1–4 blocks — is exactly the workload where it loses: the per-block
fixed overhead (RefCell borrow, token_cache memset, 4 Vec clears, atomic
load, indirect call) is paid every time and the vector win is realised
almost never.

## 3. Proposed design

Two changes, independently landable, smallest-win-first ordering. Both
preserve bit-exactness (the differential oracle in §4 proves it).

### 3.1 Phase 1 (first, smallest, measurable) — revert the fused single-pass token loop

**The change:** restore `decode_coefs`'s inner loop to libvpx's fused
single-pass form. Inside the token loop, the moment a non-zero
coefficient's `val` and `sign` are known, compute
`v = (val * dqv) >> dq_shift` and write
`dq_coefs_out[raster_idx] = if sign { -v } else { v }` directly — exactly
as the existing verbatim reference `decode_coefs_libvpx_ref` already does
(`detokenize.rs` lines 944-968).

**Delete from the decode path:**
- the four scratch `Vec`s (`scratch_raster/dqv/val/sign`) and their
  per-call `clear()`;
- the pass-2 loop;
- the `crate::dsp::get_ref()` call and the indirect
  `plane_dequant_finisher` invocation **in `decode_coefs`**.

**Keep (untouched):**
- the `DecodeCoefsScratch` `token_cache` (still needed for context
  derivation — `get_coef_context` reads neighbour token magnitudes). It
  stays thread-local to avoid per-call alloc. Note: only the prefix
  `[..n_coeffs]` is zeroed per call; consider deferring even that (libvpx
  does not pre-zero `token_cache` — it writes each `token_cache[scan[c]]`
  before any neighbour reads it, because `get_coef_context` only reads
  positions already visited in scan order). Treat the token_cache-memset
  removal as a **sub-step** gated on the oracle, not a freebie.
- `plane_dequant_finisher` itself stays in `quant` / `dsp` (it is also
  reachable elsewhere and the AVX2 kernel + its differential tests are
  fine; we just stop calling it from `decode_coefs`).

**Functions changed:** `rvp9_core::entropy::detokenize::decode_coefs`
(the body of the `with_borrow_mut` closure). No signature change, no
caller change — `decode_block_tokens` (decoder wrapper) and the two
reconstruct call sites are untouched.

**Technique adopted from libvpx:** fused dequant-in-the-token-loop; no
separate vectorised pass for a workload whose per-block coefficient
count is tiny.

**Why this is the first increment:** it is a localised body change to one
function, it directly attacks the measured dominant cost (per-block fixed
overhead on 95% all-zero blocks), and its win is independently
measurable. It also *simplifies* the code (deletes the H5/H6 machinery
from the hot path), reducing maintenance surface — a stakeholder win.

### 3.2 Phase 2 (second) — hoist reader registers into `decode_coefs` locals

**The change:** mirror libvpx's "keep value/range/count as locals"
optimisation. Add a private, `#[inline(always)]` "raw" read entry point
that operates on caller-held `(value, range, count, pos)` locals, so the
token loop can pull reader state into locals once on entry and write it
back once on exit — keeping the bool-coder registers off the
`self` struct for the duration of the hot loop.

Two candidate shapes (decide during implementation, behind the oracle):
- **(a)** A `BoolReaderState` value type holding `{value, range, count,
  pos}` plus a `&[u8]`, with an `#[inline(always)] read(&mut self, prob)`;
  `decode_coefs` does `let mut st = reader.take_state(); … ;
  reader.put_state(st);`. Closest to libvpx's local-register pattern.
- **(b)** Keep the struct but verify (via targeted disasm or a
  micro-bench A/B) whether LLVM already hoists. If it does, Phase 2 is a
  no-op and we skip it. This is the cheap "settle the open H1 question
  first" path.

**Functions changed:** `BoolReader` (new internal raw-read + state
accessors), `decode_coefs` (loop uses the local state). Public API and
bit-grammar unchanged.

**Technique adopted:** libvpx's explicit value/range/count register
hoisting across the per-block decode.

**Ordering rationale:** Phase 2 only matters once Phase 1 has removed the
two-pass noise; measure Phase 1 in isolation first. If Phase 1 already
closes most of the gap and Phase 2's micro-bench shows LLVM was already
hoisting, Phase 2 can be dropped — *don't predict the future / don't
build the on-ramp to nowhere.*

### 3.3 Explicitly OUT of scope (anti-gold-plating)

- No token-tree restructuring. The Pareto8 high-magnitude tree
  (`detokenize.rs` lines 598-653) is a faithful libvpx mirror and is not
  on the hot path for the eob-dominated workload (most blocks never reach
  it). Leave it.
- No scan-order / neighbour-table changes. `get_coef_context` already
  uses `get_unchecked` on faithful tables.
- No SIMD work. The whole point is that SIMD dequant was the wrong call
  here; we are removing it from this path, not adding more.
- No changes to `encode_coefs` / `write_block_tokens` (encoder side) or
  to the M.4/M.6 reference port — those stay as oracles.

## 4. Testability / oracle plan

Bit-exact output is non-negotiable; conformance is sacred. Three layers,
all of which already have scaffolding in-repo.

### 4.1 Differential oracle (primary) — `decode_coefs_libvpx_ref`

The verbatim libvpx transcription `decode_coefs_libvpx_ref`
(`detokenize.rs` lines 864-980) already exists and is the gold reference:
a single-pass, fused, line-by-line mirror of the C. **After Phase 1, the
production `decode_coefs` becomes structurally identical to this
reference** (single fused pass) — so the differential becomes a near-
tautology, which is exactly the confidence we want.

Concrete checks:
- **Existing runtime differential (`RVP9_DEBUG_REFCOEFS=1`)**: snapshots
  the reader, runs production, rewinds, runs the ref port, panics on any
  `(eob, dq_coefs)` divergence. Run a full conformance pass with this env
  var set as a one-shot gate after each phase. (This path stays in the
  code; it is already gated to near-zero cost when unset.)
- **Existing proptest fuzz**: the `decode_coefs` vs `decode_coefs_libvpx_ref`
  N=100 differential (referenced at lines 855-858) and the scalar-vs-AVX2
  `plane_dequant_finisher` proptest (256 cases). Re-run; both must stay
  green. Extend the `decode_coefs` differential to N≥1000 cases across
  all four tx sizes and all scan orders as the per-phase acceptance gate.
- **Existing `decode_coefs_oracle_diff` harness bin**
  (`crates/rvp9-harness/src/bin/decode_coefs_oracle_diff.rs`) — wire into
  the phase acceptance run.

### 4.2 BoolReader invariants (property tests)

The bool reader has invariants worth pinning explicitly (some already
covered by the round-trip tests in `bool_reader.rs`):
- **Round-trip**: `BoolWriter` → `BoolReader` recovers the exact symbol
  sequence for arbitrary `(bit, prob)` streams (existing
  `round_trip_skewed_probabilities`; keep).
- **State equivalence (Phase 2 specific)**: a property test asserting the
  new local-state read path produces **identical `(value, range, count,
  pos)` and identical bit outputs** as the current `&mut self` path, for
  random `(prob, bitstream)` sequences. This is the Phase 2 oracle — it
  proves the register-hoist is a pure refactor.
- **`has_error` / `LOTS_OF_BITS` EOF semantics** unchanged (existing
  `over_read_sets_error`; keep).

### 4.3 Conformance suite (must stay 201/201)

The decoder conformance harness (`crates/rvp9-harness/tests/
conformance.rs`) walks every `.webm/.ivf` vector and asserts zero MD5
mismatches against the libvpx-produced `.md5` (and ffmpeg as a third
oracle). The acceptance bar per phase:
- **201/201 vectors pass, zero mismatches.** No regression in the gated
  count.
- Run the suite with `RVP9_DEBUG_REFCOEFS=1` once per phase so every
  single transform block in every conformance vector is checked against
  the verbatim ref port simultaneously — this is the strongest possible
  bit-exactness gate (every block, every vector, differential).
- (The conformance vectors must be fetched first via
  `scripts/fetch-vectors.ps1` — they are not present in this worktree.
  Implementation task must fetch them before claiming the gate.)

### 4.4 Anti-Goodhart notes

- The differential oracle is a *real* second implementation (the verbatim
  C transcription), not a tautology against the code under test — until
  Phase 1 makes them structurally converge, at which point conformance
  (4.3) is the independent check.
- No assertion-free tests; every test asserts `(eob, dq_coefs)` equality
  or MD5 equality.

## 5. Risk + estimated speedup

### 5.1 Estimated reclaim

Detokenize bucket on the gate fixtures ≈ **24%** of serial decode time
(`decode_block_tokens` ~17%, `bool_reader::read` ~7%).

- **Phase 1** attacks the per-block fixed overhead (RefCell borrow,
  token_cache memset, 4 Vec clears, OnceLock atomic load, indirect call)
  paid on ~95% all-zero blocks plus the double-store/reload on non-zero
  blocks. On intra-heavy gate content (even higher eob==0 share than
  foreman) this overhead is a large fraction of the `decode_block_tokens`
  slice. Estimate **reclaim 30–50% of the ~17% `decode_block_tokens`
  slice = ~5–8.5 pp of total serial time.** Confidence: **high** (the
  cost is measured, the fix removes it outright, and the result is
  structurally libvpx-identical).
- **Phase 2** (register hoist) targets the `bool_reader::read` ~7% slice.
  If LLVM is not already hoisting, plausibly **reclaim 10–25% of that 7%
  = ~0.7–1.75 pp.** Confidence: **medium-low** (LLVM may already do this;
  Phase 2 may turn out to be a no-op — that's an acceptable outcome, we
  measure before committing).

**Combined plausible reclaim: ~6–10 pp of total serial decode time**, the
bulk from Phase 1. As a fraction of the 24% bucket: **~30–45%
reclaimable**, mostly Phase 1.

### 5.2 Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Bit-exactness regression | Critical | §4 differential + `RVP9_DEBUG_REFCOEFS=1` conformance pass; Phase 1 converges to the verbatim ref so divergence would be self-evident. |
| `token_cache` memset removal breaks context derivation | Med | Treat as a separate gated sub-step; only remove the per-call zero after proving (oracle) that every read position is written before it's read in scan order. If unsure, keep the memset — it's cheap relative to the dispatch we're removing. |
| Phase 2 register-hoist is a no-op (LLVM already does it) | Low | Acceptable; we A/B micro-bench first and skip Phase 2 if so. Wasted effort is bounded to the micro-bench. |
| Removing the AVX2 finisher from this path "loses" a SIMD win on coefficient-dense streams | Low | Measured: only 2.6% of blocks reach the AVX2 main loop even on inter content; the per-block tax outweighs it. If a future high-bitrate fixture proves otherwise, the fused loop is still LLVM-auto-vectorisable for the dense inner case — but do not pre-build that. |
| Concurrent kernel-audit workstream touches `dsp::dispatch` | Low | We only stop *calling* `plane_dequant_finisher` from `decode_coefs`; we don't modify the dispatch table or the kernel. Coordinate the no-longer-called slot (leave it; harmless). |

### 5.3 What would REFUTE this design (honesty)

If, after Phase 1, the conformance + bench shows < ~2 pp improvement on
the gate fixtures, then the per-block overhead was already being elided
by LLVM (e.g. the indirect call devirtualised, the Vec pushes optimised
away on empty), and H2's "two-pass is the cost" hypothesis would be
weakened — at which point the remaining detokenize cost is simply the
irreducible bool-read work and the gap to libvpx is smaller than thought.
The Phase 1 bench is the decisive experiment.

## 6. Phasing summary

1. **Phase 1 — fused single-pass token loop.** Delete the two-pass
   scratch + `plane_dequant_finisher` dispatch from `decode_coefs`; inline
   dequant + writeback (the existing ref-port shape). Gate: 201/201
   conformance with `RVP9_DEBUG_REFCOEFS=1` + N≥1000 differential proptest
   + bench delta on the gate fixtures. **This is the smallest first
   increment with a measurable win.**
   - Optional sub-step 1b (gated separately): drop the per-call
     `token_cache[..n_coeffs]` zero if the oracle confirms write-before-
     read in scan order.
2. **Phase 2 — register hoist (conditional).** A/B micro-bench whether
   LLVM already hoists reader state across the loop. If not, add the local-
   state raw-read path. Gate: state-equivalence proptest + 201/201
   conformance + bench delta. Skip if the micro-bench shows no headroom.

## 8. Team-lead review & sign-off (2026-05-27)

**Verdict: Phase 1 SIGNED OFF for implementation, subject to the conditions
below. Phase 2 is measure-first (not yet approved for code).**

This is a strong, measured HLD. The root-cause is concrete (the Wave H
H5/H6 two-pass dequant split taxes the eob-dominated workload), and the
oracle plan is exactly what I want — it leans on the existing verbatim
`decode_coefs_libvpx_ref` differential + `RVP9_DEBUG_REFCOEFS=1` + 201/201
conformance, i.e. a real second implementation, not a tautology.

Conditions folded into the design (binding on the implementation agent):

1. **Gate-fixture re-measurement is a HARD acceptance gate, not an open
   item.** The foreman-fp1 → gate extrapolation (§1.4) is sound but the
   Phase 1 win MUST be confirmed end-to-end on BOTH `tile_1x4` and
   `testsrc_1080p30` (run `scripts/fetch-vectors.ps1` first). Record
   before/after `decode-headtohead` numbers for those two fixtures in the
   journal. Per §5.3, if the gate-fixture delta is < ~2 pp, we do NOT ship
   Phase 1 — LLVM was already eliding the overhead and we report that
   honestly.

2. **Keep Phase 1 minimal.** Phase 1 = the fused single-pass revert +
   deleting the two-pass scratch and the `plane_dequant_finisher` call from
   `decode_coefs`. The `token_cache` memset removal (sub-step 1b) is
   **explicitly deferred to its own later phase** — do NOT bundle it into
   Phase 1. Smallest first increment.

3. **Pre-flight the finisher removal.** Before deleting the decode-path
   call, confirm `plane_dequant_finisher` (scalar + AVX2) has NO other
   *decode* callers and that the encoder / its differential tests still
   build and pass with the decode call removed. Record the grep result in
