## §1 One-line summary

`extend_frame_borders` (108 µs/frame, ~6.9% of the post-LF-overlap 1571 µs wall) is a row-band memcpy/fill that runs serial on the main thread between LF and the next frame. **The honest pre-mortem (§4) puts the band centre at ~3% reclaim** — below the 5% PGO ship gate — driven by memory-bandwidth ceiling on parallel border (Phase 1a) plus model-optimism deflation (the 4-of-5 PGO-disproven track record). **Recommended action: SHELVE.** The mathematical case for the band-centre miss is in §4; the smaller "overlap-only, no parallelisation" variant (Phase 1b) is mechanistically the strongest candidate (~5% centre) but the same deflation chain lands it at ~3-4% and the LF overlap pool's own p50 +2.49%-but-mean +8.14% experience shows this scale of effect is exactly where these levers die.

If the team-lead overrides and wants Phase 1, the **smallest** variant is **1b alone (overlap border with next-frame setup, no parallel split)**: zero new pool, two synchronisation edges, ~150 LOC. The combined Phase 1a+1b is in §3 for completeness but is **not** the recommended phasing — Phase 1a parallelisation has the deepest model risk (memory bandwidth) and contributes the least if 1b succeeds.

## §2 Mechanistic case

### §2.1 What `extend_frame_borders` does (mechanics)

Per `crates/rvp9-core/src/frame.rs:602` and `:1011`, the kernel is per-plane (`extend_plane` for Y, then U, then V; `BorderUsage::Decoder` ⇒ border = 32 px). Each plane does:

1. **Horizontal pass** — for every visible row `r ∈ [0, height)`: read `alloc[origin + r*stride]` (left pixel), `fill` the 32 bytes left of column 0 with it; read `alloc[origin + r*stride + width - 1]` (right pixel), `fill` the `border + (aligned_width - crop_width)` bytes right of column `width-1` with it.
2. **Vertical pass** — `copy_within` the (now-horizontally-extended) first visible row into the 32 rows above; ditto for the bottom row replicated into the `border + (aligned_height - crop_height)` rows below.

For a 1080p Y plane (1920×1080, border 32, aligned_width 1920, aligned_height ~1088):
- Horizontal pass writes: `1080 rows × (32 left + ~32+8 right) ≈ 78 KB` of fill (memset-like).
- Vertical pass writes: `32 rows × ~1984 cols × 2 (top + bottom) ≈ 124 KB` of memcpy.
- Total Y: ~202 KB written. UV (chroma 4:2:0): each plane ~half-width × half-height × half-border ⇒ ~50 KB written each.
- **Total: ~300 KB written per frame at ~108 µs on the team-lead's box ⇒ effective write throughput ~2.8 GB/s.**

That's well below the team-lead Ultra-9-285HX's DRAM write bandwidth (~50+ GB/s) but the per-plane sequential `extend_plane` cannot hit it on one thread because each row read + fill is short and dispatch/issue/store-buffer latency dominates for these tight memset loops.

### §2.2 The disjoint-write decomposition

Border-extend's writes are **fully disjoint**, no synchronisation needed within border:

| sub-task | what it writes | rough cost |
|----------|----------------|------------|
| **A. Y horizontal** — all 1080 visible rows' left+right border | left col 0-31, right col 1920-1951 of every Y row | ~30% of Y wall |
| **B. Y top vertical** — 32 rows above first visible row | 32 rows × 1984 px | ~25% of Y wall |
| **C. Y bottom vertical** — `border + (aligned_h - crop_h)` rows below last visible row | ~40 rows × 1984 px | ~25% of Y wall |
| **D. UV horizontal** (both planes) | left + right of every UV row | ~10% of total wall |
| **E. UV vertical top+bottom** (both planes) | top + bottom UV rows | ~10% of total wall |

The H-pass corners are **implicitly handled** by the V-pass copying the horizontally-extended first/last row (which already includes the corner pixels). So sub-task ordering is constrained: **A must finish before B and C** (B and C read the H-extended top/bottom row); similarly D before E. Within {A, D} and within {B, C, E} the writes are disjoint.

**Schedule on N workers** (any ≥ 2):
1. Submit `A_top_band, A_mid_band, A_bot_band, D_uv_h` to the pool in parallel — N workers split A's 1080 rows into N row-bands, and one worker (or band 0) also handles D. Join here.
2. Submit `B_y_top, C_y_bot, E_uv_top, E_uv_bot` in parallel — natural 4-way split (top Y vert, bot Y vert, top UV vert, bot UV vert). Join here.

Two mini-barriers, each on disjoint memcpy work, no cross-thread synchronisation needed within a barrier.

### §2.3 Two attack angles (the user's question)

| angle | what it does | model gain on **1571 µs** wall | feasibility |
|-------|-------------|-----------------------|-------------|
| **1a. Parallel border-extend** | Split A-E across workers; main thread joins. 108 µs → ~50 µs on 4 workers (best-case 2× on memory-bound work, see §4.1). | ~58 µs ≈ **3.7%** | Mechanically straightforward (disjoint writes). Memory-bandwidth ceiling is the lever's mortal risk. |
| **1b. Next-frame overlap** | Frame N's border runs on a non-main worker (LfWorkerPool re-use or new tiny pool); main thread returns from `decode_frame(N)` immediately; frame N+1's setup/parse runs concurrently. Sync edge: before frame N+1 inter-MC reads `ref_frame_map`'s border pixels. Union becomes `max(setup_N+1, border_N) = max(80, 108) = 108 µs` vs sequential `80 + 108 = 188 µs`. | ~80 µs ≈ **5.1%** | Mechanically harder (cross-frame sync edge, lifetime management). |
| **1a+1b combined** | Parallel border (50 µs) running concurrently with next-frame setup (80 µs). `max(80, 50) = 80 µs` vs sequential `188 µs`. | ~108 µs ≈ **6.9%** | Both mechanisms compound; both risks compound too. |

### §2.4 The track record context

| lever | model | PGO outcome |
|-------|------|------|
| Entropy fused-dequant | −5% / −10% | merged +5% tile_1x4 |
| Intra inline dispatch | +6% | ~0 (discarded) |
| Intra zero-copy `above` memcpy | ~8 ns/block | ~0 (discarded) |

## §3 Design (presented for completeness; not recommended — see §5)

### §3.1 Phase 1b alone (the minimum-cost variant if the team-lead overrides SHELVE)

**Mechanism:**
- Frame N's decode flow today (`crates/rvp9-decoder/src/lib.rs:2234` intra / `:3587` inter):
  ```
  ... LF (in overlap pool, joined on lf_handle.wait()) ...
  extend_frame_borders(&mut yv12);          // serial, ~108 µs
  let frame_buf = Arc::new(yv12);
  ref_frame_map[slot] = frame_buf.clone();  // publish for frame N+1
  return Ok(decoded_frame);
  ```
- Proposed:
  ```
  ... LF in overlap pool, joined ...
  // Dispatch border-extend on a single worker via the existing
  // LfWorkerPool (idle once LF drained). DO NOT wait here.
  let border_handle = unsafe {
      lf_worker_pool.dispatch(move || extend_frame_borders_inplace(&mut yv12))
  };
  // store handle inside Decoder, parked across the decode_frame
  // call boundary. The pending border-extend is fenced by frame
  // N+1's tile-decode dispatch:
  return Ok(decoded_frame);              // border still in flight

  // ... in Decoder::decode_frame(N+1) entry, BEFORE we read
  // ref_frame_map[i] for any inter-MC, the pending border handle
  // is joined:
  if let Some(h) = self.pending_border.take() { h.wait(); }
  // Then frame N+1's setup proceeds; MC reads see fully-extended
  // borders.
  ```
- **Critical observation:** between frame N's `border_handle = dispatch(...)` and frame N+1's `pending_border.take().wait()`, the main thread runs:
  - Caller's loop overhead (return from `decode_frame`, fetch next packet).
  - Frame N+1's header parse + `parse_packet` work (does NOT touch `ref_frame_map[i]` pixels).
  - Frame N+1's setup phase (~80 µs).
  - Frame N+1's submit phase (~16 µs).
- The sync edge `wait()` is placed **before submit** (or before setup if we want overlap with setup): if border finishes in ≤80 µs of post-return work, the wait is non-blocking.
- The lifetime issue: `yv12` is owned by `Decoder` between frames (parked on `self.pending_border_yv12: Option<Box<Yv12Buffer>>`). The `Arc::new(yv12)` and `ref_frame_map[slot]` update **MUST happen after wait()**, because the published `Arc` is what later frames read. So `pending_border.take().wait()` is followed by `let frame_buf = Arc::new(self.pending_border_yv12.take().unwrap()); ref_frame_map[slot] = frame_buf.clone();` **inside the next decode_frame call**.

### §3.2 Phase 1a (parallel border) — optional augmentation

If 1b ships ON and the team-lead wants Phase 2:
- The border-extend job dispatched in 1b would itself parallelise across the existing decode `WorkerPool` (now idle, since decode hasn't started for frame N+1 yet, and frame N is done).
- Concretely, the dispatched closure does:
  ```rust
  worker_pool.scope(|s| {
      // sub-task A split into 4 row-bands of the Y plane horizontal pass
      for band in 0..4 { s.submit(move || extend_y_h_band(band, ...)); }
      // sub-task D (UV horizontal) on a 5th submission, runs on
      // whichever worker finishes A first
      s.submit(move || extend_uv_h(...));
  });
  // Barrier 1: all H-passes done. Now V-passes safe (they read H-extended rows).
  worker_pool.scope(|s| {
      s.submit(move || extend_y_v_top(...));
      s.submit(move || extend_y_v_bot(...));
      s.submit(move || extend_uv_v_top(...));
      s.submit(move || extend_uv_v_bot(...));
  });
  ```
- **But this is wrong** for the 1b-shipped world: frame N+1's `worker_pool.scope` for tile-decode is the very next thing the main thread does (after parse + setup). If the parallel border job is holding `worker_pool` open, frame N+1 cannot dispatch decode tiles. **The two pools are the same `WorkerPool`** (the LF pool is separate). So Phase 1a requires either:
  - (i) Border-extend uses the **LfWorkerPool only** (currently 1 thread per condition §11 of the LF HLD); split A-E across multiple submissions but they all run serially on 1 thread ⇒ no parallel speedup. Phase 1a degenerates to Phase 1b.
  - (ii) Bump `LfWorkerPool` to N_LF=2 or 4 specifically for border-extend AND LF (Phase 2 of the LF HLD, not yet sign-off'd). Couples two unrelated levers; rejected for Phase 1.
  - (iii) Spawn a tiny ephemeral pool just for border. ~150 LOC of pool code, soundness review, scope.rs lifetime audit. Disproportionate cost for 58 µs.
  - (iv) Reuse `worker_pool` for border but explicitly join border BEFORE frame N+1's tile dispatch. **This kills the 1b overlap** (main thread waits on border before setup) ⇒ Phase 1a alone, no overlap. Reclaim drops to 3.7%.

**Verdict on 1a:** every concrete topology either (a) eats the 1b win (option iv), (b) doesn't parallelise (option i), or (c) costs disproportionately (option ii/iii). **Phase 1a should not ship before Phase 1b, and shipping 1a *after* 1b requires Phase 2 LF-pool sizing.** This makes the "combined 6.9%" model in §2.3 not directly reachable in any Phase 1 shape.

### §3.3 Reuse-the-LfWorkerPool-for-border specifics

The LF worker pool (`crates/rvp9-core/src/tile_threading/lf_pool.rs`) is constructed with N_LF=1 and `dispatch` returns an `LfBatchHandle<'pool, 'frame>` that must be `wait()`-ed (or `Drop`-ped) before the borrowed state expires. For Phase 1b:
- LF for frame N: dispatched at decode-frame entry, joined inside the decode-LF overlap before merge/border.
- Border for frame N: dispatched **after LF join**, NOT joined locally — handle stored on `self.pending_border` with a `'static` lifetime (border doesn't borrow anything except the parked `yv12`, which is owned by `Decoder`).
- Frame N+1: at start of decode_frame, `pending_border.take().wait()` joins the prior border before any read.

**The `'frame` lifetime issue:** `LfBatchHandle<'pool, 'frame>` carries a `'frame` tie. For Phase 1b, `'frame` is *not* the current `decode_frame` call's stack frame — it's the *prior* call's. Concretely, the handle must outlive its `decode_frame` invocation and be stored on `Decoder`. That requires `'frame = 'static` on the dispatched closure, which means the closure cannot borrow any per-frame stack data — it must own `yv12` (or hold a raw pointer with explicit SAFETY).

Two options:
- **(a) Move `yv12` into the closure.** The closure does `let mut yv12 = yv12_owned; extend_frame_borders(&mut yv12); /* park yv12 in a Mutex<Option<Yv12Buffer>> on Decoder for the next-frame join to retrieve */`. The Decoder holds `pending_border_yv12: Arc<Mutex<Option<Yv12Buffer>>>`; the closure stores into it; the main thread retrieves after `wait()`. This is clean and works with `'static` closures.
- **(b) Raw pointer + custom SAFETY.** Cheaper, but adds an unsafe surface — the LF pool SAFETY chain has been carefully audited (`SAFETY.md` §7); adding a second consumer pattern doubles the review.

Option (a) is recommended; it costs one `Arc<Mutex<Option<Yv12Buffer>>>` field on `Decoder` and a 2-line lock/unlock dance.

### §3.4 Bit-exactness (this is the load-bearing argument)

**Current write→read edge for border bytes:** Border is written on the main thread (synchronously, inside `decode_frame`). The frame is then wrapped in `Arc<Yv12Buffer>` and stored into `ref_frame_map[slot]`. The next `decode_frame` call reads `ref_frame_map[i]` for inter-MC. The write→read is sequential within one thread (decode_frame N) and then crosses the harness call boundary (which is at-most a `pop` from a packet queue — no thread synchronisation needed, the next call is on the *same* main thread).

**Proposed write→read edge for Phase 1b:** Border is written on `LfWorkerPool`'s LF worker thread (background). The `Arc::new(yv12)` and `ref_frame_map[slot]` update happen AFTER `border_handle.wait()` returns. The wait happens at the start of `decode_frame(N+1)`. So the read site (MC inside frame N+1's tile decode) cannot run until `ref_frame_map[i]` is published, which cannot happen until `wait()` returns, which cannot return until the LF worker has finished border writes and sent on `done_rx`. **Acquire-release pair: the LF worker's `done_tx.send(LfOutcome::Ok)` is the release; the main thread's `done_rx.recv()` is the acquire.** All border writes happen-before the recv.

**Where the new sync edge lives:** `Decoder::pending_border: Option<LfBatchHandle<'static, 'static>>` field. At decode_frame entry: `if let Some(h) = self.pending_border.take() { h.wait(); }` then `let yv12 = self.pending_border_yv12.lock().take().expect(...); let frame_buf = Arc::new(yv12); self.ref_frame_map[self.pending_border_slot] = frame_buf.clone();`.

**Critical correctness invariants (must be encoded in the impl):**

> **Invariant B1 (border completion):** Before any pixel read of `ref_frame_map[i]`'s border bytes for frame N+1, frame N's border-extend dispatched at end-of-decode_frame(N) MUST have been `wait()`-ed by the main thread.

> **Invariant B2 (publishing order):** Frame N's `Arc<Yv12Buffer>` is published to `ref_frame_map[slot]` AFTER the wait, AFTER the border bytes are visible. No read of `ref_frame_map[slot]` may resolve to the pre-border `yv12`.

> **Invariant B3 (no concurrent decode on the same yv12):** Between `dispatch(border_closure)` and `wait()`, NO other code accesses `yv12`. The main thread proxies through the `Mutex<Option<Yv12Buffer>>`; the LF worker is the only accessor during the gap.

**Pre-existing assumption being preserved:** The encoder does not consume the decoder's border-extended frames (verified `2026.05.26 - JRN - Survey 2`, encoder grep returned 0 matches). MC paths that bypass `build_mc_border` (per the same journal's autopsy: rvp9's MC has at least one inter-prediction read path through the YV12 border region without `build_mc_border` cover) still see fully-extended borders because B1 fires before MC.

### §3.5 LF-kernel-adjacency risk (the prior HLD called this out)

The prior HLD §6.1 risk note flagged border-extend as "whole-frame and LF-kernel-adjacent". What specifically:
- **LF writes the same plane bytes** border-extend reads (the bottom 8 luma rows of row r-1 in LF horizontal pass).
- **Sequence today:** LF completes → border-extend reads LF-filtered visible pixels and replicates them to the padding. Border-extend's input is the post-LF reconstruction.
- **Sequence in Phase 1b:** LF completes (on the LF overlap pool worker) → main thread `lf_handle.wait()` → main thread dispatches border closure on the same LF worker → border-extend reads post-LF pixels (still correct, same input).
- **The risk:** if Phase 1b's border closure were to run *concurrent with* LF (e.g. by dispatching border before LF's wait), border would read pixels mid-filter ⇒ wrong borders ⇒ wrong inter-MC ⇒ bitstream divergence.
- **Mitigation (already in §3.1):** the dispatch order is `lf_handle.wait()` THEN `dispatch(border)`. Border CANNOT race LF. Phase 1b does not introduce LF/border concurrency; it overlaps border with **the next frame's setup**, which doesn't touch the current frame's `yv12`.

**LF-adjacency risk in Phase 1b is therefore not LF-vs-border (impossible by ordering) but border-vs-future-decode:** the next frame's tile-decode reads `ref_frame_map[i]` pixels. The invariants B1/B2 cover this exactly. There is no kernel-adjacent hazard beyond what B1 handles.

If Phase 1a (parallel border within the dispatched closure) ships later, the kernel-adjacency risk grows: multiple threads write disjoint regions of `yv12` concurrently. Disjoint writes are sound per the SharedFrame Send+Sync audit (already in place), but the sub-task ordering A-before-B/C must be a hard barrier within the closure (libvpx-faithful: H pass complete, then V pass). This is in §3.2's two-mini-scope shape, which works **only if** the parallelism uses a pool that has more than 1 worker. For Phase 1b alone, the closure is serial on the LF worker — no kernel-adjacency.

## §4 Honest pre-mortem (the load-bearing section)

### §4.1 (a) Memory-bandwidth ceiling on parallel border (Phase 1a)

`extend_plane` is dominated by memset (the `.fill()` calls) and memcpy (`copy_within` for the vertical pass). Per §2.1, total writes are ~300 KB / 108 µs ≈ 2.8 GB/s on one thread. On 4 threads writing disjoint regions:

- **L3 share:** the 24 MB L3 on Ultra-9-285HX is shared; border-extend's working set (300 KB) easily fits. Multiple writers don't conflict on L3 capacity.
- **DRAM write channel share:** modern Intel DDR5 has 2-4 channels; per-channel sustained write ~10-15 GB/s. Aggregate 30-60 GB/s. 4 threads × 2.8 GB/s = 11 GB/s sustained ⇒ easily within bandwidth.
- **Store buffer + ROB pressure:** the bottleneck on single-thread `extend_plane` is most likely *not* DRAM, it's the per-row dispatch overhead — each visible row is a tiny `.fill(32)` call, the OOO core has to issue, retire, advance. 1080 short fills per plane is ~1µs of per-row overhead conservatively (assuming 1ns/fill, which is wildly optimistic — `.fill()` on 32 bytes is one AVX2 store, but the loop overhead and the read of the edge pixel from a cold-ish cache line adds up).

**Best-case 4-thread speedup estimate: 2-2.5× (108 µs → ~45-55 µs).** Worse than 4× because:
- The vertical pass's `copy_within` of ~124 KB Y bottom-band is bound by sequential write bandwidth from a single source line; striping across threads gives diminishing returns past 2 (each thread's writes serialise at DRAM).
- E-core demotion (per the LF HLD §4.1): if 1 of the 4 LF threads lands on an E-core (Gracemont, ~0.6× P-core), the slowest thread paces the join.

**Loss budget for 1a:** model says ~58 µs saved; deflated reality ~40-50 µs ⇒ ~2.5-3.2% of 1571 µs wall. **Below the 5% gate by itself.**

### §4.2 (b) Dispatch overhead on a 30-50 µs job

LfWorkerPool dispatch + wait round-trip is ~5-10 µs per the LF HLD §4.3 analysis (crossbeam_channel send + wake + return signal). For Phase 1b, this is fixed overhead per frame:
- Border work itself: 108 µs serial (no parallelisation in pure 1b).
- Overlap with next-frame setup: union = max(80, 108) = 108 µs.
- Dispatch overhead: +10 µs (send to LF worker, receive done signal at next-frame entry).
- Effective gain: 188 - (108 + 10) = 70 µs ≈ **4.5% of 1571 µs wall**.

For Phase 1a+1b combined (~50 µs border + 10 µs overhead = 60 µs):
- Union = max(80, 60) = 80 µs.
- Gain: 188 - 80 = 108 µs ≈ **6.9%** (the §2.3 number).

For Phase 1a alone (no overlap, parallel border completes on main thread):
- Border: ~50 µs vs 108 µs.
- Gain: 58 µs ≈ **3.7%**.

**Loss budget for dispatch:** small (10 µs) but it eats ~17% of the 1a reclaim and ~12% of the 1b reclaim.

### §4.3 (c) Border is post-critical-path (the Amdahl trap)

The frame wall today is `setup + submit + max(decode_crit, LF_overlap) + merge + border = 80 + 16 + 1208 + 51 + 108 + 96 (channel overhead) ≈ 1559 µs ≈ 1571 µs measured.` Border is the **tail** of the serial chain, not the long pole. Reducing it shrinks the wall 1:1 because nothing else runs in parallel with it (in 1a) or because we overlap it with the next frame (in 1b).

**This part of the model is actually robust** — unlike the LF overlap (which had pipelining fill delays and worker-set contention), Phase 1b's "border with next-frame setup" overlap is a pure serial-tail shortening. No worker contention, no scheduling games. **The mechanism here is the strongest of the lever class** specifically because the overlap target (next-frame setup) is serial on the main thread and border is serial on a parked LF worker — they truly don't fight for resources.

The Amdahl trap is in **how much serial tail there is**: after LF overlap landed, the post-critical-path tail is `merge + border = 51 + 108 = 159 µs`. **Border is only 6.9% of wall, by definition the maximum possible reclaim from any border-only lever.** Even a 100% successful 1b+1a (border vanishes entirely) gives ≤6.9%. The lever's *ceiling* is just barely above the 5% gate.

### §4.4 (d) Track-record optimism factor

Of 5 modelled levers in this session (per `JRN - Final consolidation`):
- 2 hit (entropy +5%; LF pool +8.14% mean / +2.49% p50).
- 4 missed under PGO (intra A inline, intra B memcpy, intra envelope, in-pool overlap).
- 1 shelved by arithmetic (within-tile row-MT, addressable bucket 1.6% < 5% gate).

**Model-to-PGO deflation factors observed:**
- Entropy: model −5/−10%, PGO −5% tile_1x4, ~0 testsrc ⇒ deflation 1× on tile_1x4, ~∞ on testsrc.
- LF pool: model 5-15% centre, PGO +8.14% mean (centre of band) ⇒ deflation ~1× (best case observed).
- Intra envelope: model 10-25× kernel, PGO −3-4% **regression** ⇒ deflation ∞ + sign-flip.
- In-pool overlap: model 8-16%, PGO ~2% (estimate from diagnostic) ⇒ deflation ~5×.

**Median deflation across 5 levers: ~2×.** Applying to this lever's optimistic model (1a+1b = 6.9% ceiling):
- Combined optimistic 6.9% / 2 = **3.5%** centre of expected PGO band ⇒ **misses 5% gate.**
- 1b alone 5.1% / 2 = **2.6%** ⇒ misses.
- 1a alone 3.7% / 2 = **1.9%** ⇒ misses badly.

### §4.5 (e) The post-critical-path observation reframed

The user's prompt flags this directly: "the LF overlap already shifted the bottleneck — decode-critical-path is now the long pole and border is on the post-critical-path; reducing post-critical-path work doesn't shrink the critical path."

This is **partly correct, partly not** for border specifically:
- **Wall reduction yes:** border IS on the serial main-thread chain between frames. Removing/overlapping it shrinks wall by the amount overlapped. The 1571 µs wall includes 108 µs of border serial work; remove it and wall drops.
- **Critical-path framing no:** the "critical path" in a parallel decode is `setup + submit + max(decode, LF) + merge + border`. Border is part of this serial sum, not parallel to it. So reducing border *does* shrink the critical path.

**But the user's instinct is right in spirit:** when the *long* item (decode) is 1208 µs and border is 108 µs, the marginal value of reducing border is 108/1571 = 6.9% best case. If the long item could be attacked instead, the return would be higher. Border is one of the smallest remaining levers by definition.

### §4.6 (f) Variance / measurement noise

The PGO A/B gate (per the LF HLD §10) requires `≥5% mean+p50` on `testsrc_1080p30 t=4`. With 1000-frame iters, drift-cancelling A/B, the noise floor is ~1-2%. A 3-4% true effect would show but with significant per-iter variance; could easily fail the strict gate while having a real ~3% effect.

**The LF HLD's experience:** mean +8.14%, p50 +2.49%. The mean cleared, the p50 missed. The team-lead's call was that mean is the operational metric (matches vpxdec's `--summary` reporting). For this lever, with a 3-4% effective band centre, **even mean could miss** because the centre is below the gate.

### §4.7 Pre-mortem verdict

| factor | combined (1a+1b) | 1b alone | 1a alone |
|--------|------------------|---------|---------|
| upper-bound model | 6.9% | 5.1% | 3.7% |
| after dispatch overhead | 6.3% | 4.5% | 3.2% |
| after bandwidth ceiling | 5.5% | (n/a) | 2.5% |
| after E-core demotion risk | 5.0% | 4.3% | 2.2% |
| after track-record 2× deflation | **2.5%** | **2.2%** | **1.1%** |
| probability ≥ 5% PGO gate | ~20-25% | ~15-20% | < 5% |

**Even the most aggressive variant (1a+1b combined) lands at 2.5% expected reclaim after deflation.**

The dominant risk is **not** correctness — bit-exactness is straightforward (one new sync edge, B1/B2/B3 invariants, differentially testable). The dominant risk is **PGO miss probability ~75-80%**. By the track record, this lever shape (small-bucket optimistic model on memory-bound work) is the **exact** profile that died 4 of 5 times this session.

## §5 Recommendation: **SHELVE**

### §5.1 The decision arithmetic

The team-lead's published EV threshold from the LF HLD sign-off: "55-60% gate-clearing × 5-8% center reclaim → EV ~3-4.5%. After 4 disproven priors I'd normally pass on EV that thin, but the sunk-cost monetisation (existing dormant infra) + the libvpx precedent flip it positive."

This lever's EV by the same framework:
- Gate-clearing probability: 15-25% (per §4.7).
- Center reclaim (conditional on clearing): ~5-6%.
- Unconditional EV: 0.20 × 5.5% = **~1.1%** vs LF pool's 3-4.5%.
- **No sunk-cost monetisation:** unlike LF pool (which monetised Wave-5b grid pre-fill + column-wavefront LF + decode_progress publish), this lever lights up no dormant infra.
- **No libvpx precedent:** libvpx does NOT call `vpx_extend_frame_borders` in the decode path at all (per `Survey 2` journal). libvpx relies entirely on lazy `build_mc_border`. So the libvpx-faithful answer here is **delete the call**, but `Survey 2` showed our MC paths break at 187/201 conformance without it (an audit-first refactor estimated at 80-200 LOC and ~1 day's work). That audit-driven removal is a *different* lever, not addressed by parallelisation.

### §5.2 The mathematical/mechanistic argument for SHELVE

1. **Ceiling is 6.9%** (border is the only thing being shrunk; cannot exceed border's share of wall). Gate is 5%. **Margin to gate is 1.9% before any deflation.**
2. **Track-record deflation factor is ~2× median.** 6.9% / 2 = 3.5% ⇒ misses gate.
3. **Memory bandwidth bound on parallel work (Phase 1a)** caps the parallel speedup at ~2-2.5× ⇒ 1a alone is 3.7% before deflation ⇒ ~1.9% after.
4. **The only variant with a real shot (1a+1b combined) requires either Phase 2 of the LF HLD (N_LF≥2) or a third pool** — both of which couple this lever to other architectural decisions and cost disproportionately.
5. **No sunk-cost infra to monetise.** Unlike the LF overlap lever which lit up 3 pieces of dormant code, this lever builds new machinery from scratch.

### §5.3 What this lever would need to become viable

- **A bigger bucket.** Border is 108 µs in a 1571 µs wall. A lever targeting a >250 µs bucket has structurally higher headroom.
- **A higher parallel ceiling.** Memory-bound work caps at 2-2.5×. Compute-bound work caps at N_workers. Border is memory-bound.
- **Cheaper sync.** A 10 µs dispatch eats meaningful margin when the budget is 60 µs of work.
- **Sunk-cost infra.** Border-extend has no dormant precursor work waiting to be monetised.

None of these are likely to change. **The lever is not just borderline-by-arithmetic; it's structurally below the threshold that has been observed to win this session.**

### §5.4 If the team-lead overrides

Use Phase 1b only (LfWorkerPool reuse, overlap border with next-frame setup), N_LF=1 (no parallel border, no new pool). Cost: ~150-200 LOC + the `pending_border` field on Decoder + invariant B1/B2/B3 plumbing. PGO A/B has ~15-20% probability of clearing 5% mean. If it clears: ship behind `RVP9_BORDER_OVERLAP=1`, default OFF, follow LF HLD §10 flip-default protocol. If it misses: dormant landing per Lever-B-v2 §10 #2 (do NOT revert).

**Do NOT do Phase 1a in any form before Phase 1b lands and ships ON.** The combined gain is the only one that comfortably clears modelled gate, but as §3.2 shows, you cannot get parallel border without either (a) breaking Phase 1b's overlap by using `worker_pool`, or (b) committing to N_LF≥2 (a separate sign-off).

## §6 Bit-exactness (for the override path, §5.4)

### §6.1 The sync edge precisely

**Today (sync):**
```
Frame N main thread:
  ... LF ... → border-extend writes padding bytes → Arc::new(yv12)
  → ref_frame_map[slot] = arc.clone() → return from decode_frame(N)
Frame N+1 main thread:
  enter decode_frame(N+1) → ... parse + setup ... → tile-decode dispatch
  → tile workers call MC, read ref_frame_map[i] which includes border bytes
```

**Phase 1b:**
```
Frame N main thread:
  ... LF (via LfWorkerPool, joined via lf_handle.wait()) ...
  border_handle = lf_pool.dispatch(|| extend_frame_borders_inplace(yv12_owned))
  // yv12 moved into closure; closure parks it in
  // Decoder.pending_border_yv12 (Arc<Mutex<Option<Yv12Buffer>>>) before
  // sending the done signal.
  Decoder.pending_border = Some(border_handle)
  Decoder.pending_border_slot = slot   // for the ref_frame_map publish later
  return from decode_frame(N)

Frame N+1 main thread:
  enter decode_frame(N+1)
  // SYNC EDGE B1: join prior border before publishing ref_frame_map
  if let Some(h) = Decoder.pending_border.take() { h.wait(); }
  // The wait() acquire pairs with the LF worker's done_tx.send release.
  let yv12_done = Decoder.pending_border_yv12.lock().unwrap().take().unwrap();
  let frame_buf = Arc::new(yv12_done);
  ref_frame_map[Decoder.pending_border_slot] = frame_buf.clone();
  // Now safe to proceed with parse + setup + tile-decode.
```

The acquire-release pair (LF worker's `done_tx.send` ⊳ main thread's `done_rx.recv`) is the same pair that makes the LF overlap pool sound. It is well-audited (`SAFETY.md` §7). Reusing it costs no new unsafe surface.

### §6.2 Three invariants for the impl

> **Invariant B1:** Border completion ⊳ ref_frame_map publish. The `wait()` on `pending_border` happens BEFORE any read or write of `ref_frame_map[pending_border_slot]` for frame N+1.

> **Invariant B2:** Border closure has exclusive access to `yv12` between `dispatch()` and `wait()`. The main thread holds NO reference to the moved `yv12` during that window. The `Arc<Mutex<Option<Yv12Buffer>>>` is the rendezvous; the worker writes-then-stores, the main thread waits-then-takes.

> **Invariant B3:** Frame N+1's tile-decode workers see the post-border `Arc<Yv12Buffer>` exclusively. The `ref_frame_map[i]` they read was assigned AFTER `wait()` returned (B1). No tile worker reads a pre-border partially-extended buffer.

The differential test (§7.1) is the oracle that catches any B1/B2/B3 violation: an L1-style off-by-one would mean a tile worker reads padding bytes that haven't been written yet ⇒ inter-MC sees stale bytes ⇒ bitstream diverges on the very next frame.

### §6.3 What the worker sees, what the main thread sees

| moment | main thread state | LF worker state |
|--------|-------------------|-----------------|
| decode_frame(N) returns | pending_border=Some(h); pending_yv12 owns the not-yet-extended buffer (worker has it now) | running extend_frame_borders, owns yv12 by move |
| (gap) | running caller's loop, parse(N+1), setup(N+1) | finishing border, parking yv12 in Mutex, sending done signal |
| decode_frame(N+1) entry, wait() returns | pending_border=None; takes yv12 from Mutex; publishes Arc to ref_frame_map | parked on next dispatch (or shutdown) |
| tile dispatch for N+1 | tile workers see ref_frame_map[N's slot] = Arc<Yv12Buffer> with full borders | (idle / unrelated) |

No reader observes the buffer mid-extend. No writer observes it mid-read. Standard producer-consumer pattern.

### §6.4 The 187/201 break revisited (per Survey 2 journal)

The journal showed that **with extend_frame_borders removed entirely**, 187 of 201 conformance vectors broke. This means the border bytes ARE consumed by MC. **Phase 1b does NOT change this consumption**; it changes the *thread* and *timing* of the border-extend write. The bytes still exist, fully populated, by the time MC reads them (B1+B2 guarantee). **Phase 1b is bit-exact equivalent to the serial path by construction.**

## §12 Summary

**Recommendation: SHELVE.** The mathematical case:

- Border-extend is **108 µs ≈ 6.9% of post-LF-overlap 1571 µs wall**. That's the **absolute ceiling** for any border-only lever.
- Parallel border (1a) is memory-bandwidth-capped at ~2-2.5× speedup ⇒ ~3.7% gain modelled, ~1.9% after deflation ⇒ misses.
- Next-frame overlap (1b) is mechanistically clean and modelled at ~5.1% ⇒ ~2.5-3% after track-record deflation ⇒ misses by typical PGO outcomes.
- Combined (1a+1b) modelled at ~6.9% ⇒ ~3.5% deflated ⇒ misses. Also requires Phase 2 of LF HLD (N_LF≥2), coupling this lever to another sign-off.
- **No sunk-cost dormant infra to monetise** (unlike LF pool which lit up 3 pieces).
- **Track record**: 4 of 5 PGO-disproven; the ones that died had exactly this profile (small bucket, optimistic model, memory-bound mechanism).

If overridden, Phase 1b alone is the smallest-and-safest first attempt: ~150-200 LOC, one new acquire-release sync edge (reuses LF pool's well-audited pattern), bit-exact correctness straightforward (B1/B2/B3), dormant-landing failure mode preserves the PGO miss as documented negative result.

The libvpx-faithful direction (Phase 3 / delete-and-route-through-build_mc_border) has a higher ceiling and is a cleaner architectural call — flagged here, out of scope for this HLD.
