# HLD — SIG4: Profile-1 asymmetric-chroma (4:2:2 / 4:4:0) INTER decode wrongly debug-asserted

**Date:** 2026.06.04
**Author:** Claude (with Arthur).
**Branch:** `track2-longclip-differential-gate`.
**Status:** IMPLEMENTED + oracle-verified (this commit).
**Surfaced by:** the longclip real-world differential campaign — the new
`foreman_c422_p1.ivf` clip (Profile-1 4:2:2, `I P P P P P P P I P P P`) panicked
the `longclip_differential` gate at `crates/rvp9-decoder/src/tile.rs:1576` on its
first INTER frame.

---

## 1. One hypothesis

> The `debug_assert!` at `decode_tile_inter` (`tile.rs:1576`) restricts the inter
> reconstruction path to `Yuv420 | Yuv444`, but the per-block inter decode chain
> is already fully subsampling-aware for all four legal VP9 chroma formats (the
> same G7.1a parametric geometry / G7.1b inter-MC code as the intra path). The
> assert is a **stale conservative tripwire** left over from the G7.2 landing,
> not a real limitation. Relaxing it to mirror `decode_tile_intra`'s assert
> (allow all four formats) yields **bit-exact** 4:2:2 / 4:4:0 inter decode.

## 2. Evidence it is rvp9's bug (triangulated oracle)

- `foreman_c422_p1.ivf` carries TWO committed ledgers — `<clip>.ivf.md5`
  (libvpx vpxdec) and `<clip>.ivf.ffmpeg.md5` (ffmpeg NATIVE vp9). Both **agree**
  on all 12 shown frames (the `encode-corpus.ps1 -Verify` cross-check passed at
  build time; `read_triangulated_ledger` re-verifies in the gate). Two
  independent decoders agreeing ⇒ the bitstream is well-formed and the divergence
  was provably ours.
- After relaxing the assert, rvp9's per-shown-frame visible MD5 matches the
  oracle **byte-for-byte** on all 12 frames → `first_divergence=EXACT`.

## 3. Root cause (libvpx-cited)

Commit `a278399` (2026-05-23, "G7.2: VP9 Profile 1 fully landed (4:2:2 + 4:4:0 +
gate lift)") updated the chroma allow-list in **`decode_tile_intra`**
(`tile.rs:385`) to all four formats:

```rust
ChromaFormat::Yuv420 | ChromaFormat::Yuv422 | ChromaFormat::Yuv440 | ChromaFormat::Yuv444
```

but left the sibling assert in **`decode_tile_inter`** (`tile.rs:1576`) at the
pre-G7.2 set:

```rust
ChromaFormat::Yuv420 | ChromaFormat::Yuv444   // 4:2:2 / 4:4:0 wrongly excluded
"decoder gate should have rejected {:?} before decode_tile_inter"
```

VP9 imposes **no frame-type restriction on chroma subsampling**: `subsampling_x/y`
are sequence-level (read once in the keyframe/intra-only colour config) and apply
identically to key, intra-only, and inter frames. libvpx's `decode_tiles`
(`vp9_decodeframe.c`) drives every plane through `cm->subsampling_x/y` for all
frame kinds — there is no 420/444-only inter path. So the rvp9 assert's narrower
set had no spec/libvpx basis; it was a copy-paste oversight in the G7.2 commit.

Because `debug_assert!` is compiled out in release, the **release** decoder always
decoded 4:2:2/4:4:0 inter correctly (the recon is ss-generic). The bug manifested
ONLY in debug builds — where it silently broke the pre-existing `profile1_decode`
conformance test (its `foreman_c422*.ivf`, `foreman_c440*.ivf`, `vp91-2-04-yuv422`,
`vp91-2-04-yuv440` vectors are all `I P P P…` inter streams) from 2026-05-23 until
this fix.

## 4. Classification

NOT a parse-desync and NOT a reconstruction bug — the reconstruction was always
correct (oracle-verified). It is a **spurious decode-time guard**: a `debug_assert`
that wrongly rejected a fully-supported, bit-exact path.

## 5. Fix (smallest change)

Relax the `decode_tile_inter` assert to the same four-format set as
`decode_tile_intra` (`crates/rvp9-decoder/src/tile.rs`). One assert; no logic
change to the reconstruction path. The assert is retained (not deleted) as a
debug-only sanity check / documentation of the supported set, mirroring its intra
sibling.

## 6. Regression coverage

- **`profile1_decode.rs`** (harness): the main gate `profile1_vectors_decode_bit_exact`
  now passes (it panicked at `tile.rs:1576` before the fix). A NEW focused named
  marker `profile1_422_440_inter_decodes_bit_exact_sig4` decodes `foreman_c422.ivf`
  + `foreman_c440.ivf` (inter streams) bit-exact and points back at this HLD/journal
  (mirrors the existing Wave-P `profile1_440_..._wave_p` marker idiom).
- **`longclip_differential.rs`** (campaign gate): `foreman_c422_p1.ivf` → EXACT.

## 7. No regressions (verified)

- `cargo test -p rvp9-decoder --lib`: 203 passed.
- decoder conformance 14, panic_safety 4, doctests 3-ignored.
- harness: `profile1_decode` (now green), `conformance` 6, `multi_tile` 3,
  `intra_only` 1, `lossless` 1, `frame_parallel_regression` 1, `tile_threading` 7.
- All 13 longclips EXACT.

## 8. Scope note (4:4:0)

The fix enables 4:2:2 AND 4:4:0 inter (the recon path is shared and ss-generic).
4:2:2 is corpus-verified bit-exact here (`foreman_c422_p1` + `foreman_c422*` in
profile1). 4:4:0 inter is covered by the same code path and by `profile1_decode`'s
`foreman_c440*` vectors (now green); y4m cannot carry 4:4:0, so no 4:4:0 *longclip*
was added (the profile1 corpus already covers it).
