# Monotone round-trip skip bound

The 32×32/64×64 TX8 realtime picker could, in principle, stop a candidate's
Hadamard/quantizer tile loop once its luma skip choice is inevitable. This is
an exact candidate-local shortcut, not winner/loser pruning. It was screened
with an output-neutral diagnostic and is **not worth a production prototype on
the pinned Ducks/Tree/Town set**.

For `hadamard_only` large blocks in the S3 coefficient-distortion domain,
`inter.rs:evaluate_candidate_for_filter_with_pred` compares
`rd_cost(lambda, min(coef_rate, u32::MAX), coef_dist)` with
`rd_cost(lambda, 0, mrd.sse_y << s3_skip_shift)`. The second side is known
before the round trip. Each tile adds nonnegative SATD, EOB charge, and
coefficient error; the saturating sums and `rd_cost` remain monotone. Once a
non-skippable prefix reaches the skip side, later tiles cannot reverse
`take_skip=true`. A product implementation would also need to preserve full
coefficient fields for candidate tracing, the F.0.2 oracle, and A4 diagnostics.
The diagnostic **never exits early**: it records the first crossing, finishes
all tiles, and checks the completed RD against the same skip bound.

| --- | ---: | ---: | ---: | ---: |
| Ducks | 676 | 1,219 | 25,044 | 4.87% |
| Tree | 91,954 | 103,958 | 5,479,240 | 1.90% |
| Town | 58,307 | 58,154 | 4,014,756 | 1.45% |

There were zero final-skip mismatches. All three input hashes were pinned and
all three diagnostic IVFs matched integrated output hashes. These are **tile
counts, not CPU savings**; a bound check on every tile would consume work too.
The crossing generally arrives too late to justify that check. Tile
reordering might cross earlier, but would add sorting and change diagnostic
hash order; it is a different design with no measured advantage here.
