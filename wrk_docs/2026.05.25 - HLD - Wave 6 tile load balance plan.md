# HLD — Wave 6 Tile Load Balance Plan

**Date:** 2026-05-25
**Author:** architect agent (planning)
**Status:** **DEFERRED** by team lead per the agent's recommendation. Plan preserved for future revisit if frame-size or platform conditions change.

## 1. Problem framing

At t=4 the four tile workers join with a 3.1× P95 spread on `testsrc_1080p30` (median 1131 µs / P95 3513 µs) and the largest tile of `tile_1x4` consumes ~3.5 ms — half the frame. Because each tile column's bitstream is encoder-fixed and parsed serially through one `BoolReader` + CABAC state, the slowest column gates the whole scope. After Wave 5 the LF-overlap lever is spent; only the tile-decode tail remains.

## 2. Approach selection

### (A) Work-stealing at SB-row granularity within a tile
**Feasibility: NO.** A tile's `BoolReader` is a single serial cursor; SB-row R+1's parse requires SB-row R's CABAC state, `above` row, partition/coef contexts and segmentation state. There is no checkpoint format from which a second worker could begin parse at row k. **Cross-tile stealing** is also infeasible: each tile owns its own reader with its own probability tables and `above`/`left` reductions; you cannot resume one tile from another worker without re-parsing the prefix.

### (B) Pre-decode profiling + worst-tile split into two scope jobs
**Feasibility: NO (as literally described).** Same reason. Splitting "decode the second half of tile N" off as a job requires checkpointing the bitstream cursor at the midpoint — and the midpoint can only be reached by serial parse. The encoded byte-count of a tile is a poor predictor of decode cost (a tile can be byte-light but coefficient-heavy).

### (B′) Parse / reconstruct pipeline within the worst tile
A second worker would run the *reconstruct* half (intra-pred + IDCT + MC + write-to-frame) for SB-row R while the primary keeps parsing R+1. The parse step alone is ~30–40% of tile-decode (rough estimate from libvpx splits; not measured here — flagged risk). Maximum theoretical win: parse-only ≈ 0.4 × 3354 µs = 1.3 ms on `tile_1x4`, capped lower (~600–800 µs) on synthetic. Cost: a new shared queue, parsed-context staging buffers, and *one extra scope job slot* — re-using W2's `decode_progress` Acquire/Release row signal as the gate.

### (C) Row-MT within every tile (libvpx `row_mt`)
A second worker per tile pipelining parse vs reconstruct, on **every** tile, not just the worst. Cost = `num_tiles × extra_submit + extra_atomics`. At t=4 that is 4 extra `scope.submit` calls per frame (~4 × 3 µs = 12 µs) + 4 extra workers contending the pool's job channel. Plausibly fits inside the 50 µs/frame budget. Benefit is bounded by the **slowest** tile's parse fraction; the three fast tiles get zero gain and pay the overhead. Net win equals B′'s win plus dispatch tax minus gain on already-fast tiles ≈ B′ − 12 µs.

### Recommendation: **DEFER (NONE).**
All three options fail at least one of {bitstream feasibility, W2-overhead ceiling, post-W5 frame-size economics}. The closest viable is **B′** but it requires a non-trivial parse/reconstruct refactor (~600–1200 LOC) for a predicted 200–700 µs gain on `testsrc_1080p30` t=4 (6–22% of frame) with high implementation risk and a 30%+ chance of net regression on small frames (the W2 trap). The honest read of the survey numbers is that the tile-join tail at t=4 is dominated by one outlier tile whose *intrinsic* serial decode work exceeds 3 ms — there is no parallelism budget hiding in there that doesn't require parse/reconstruct splitting.

**Defer Wave 6 unless the lead is willing to accept a high-risk, medium-confidence dispatch on B′ with a hard rollback gate.** Better candidates likely exist:
- `BoolReader::peek_bit` table cache (survey honourable mention)
- Smaller intra-prediction or quantize kernel wins
- 4K conformance sizing (where the calculus inverts — parallelism budget grows with frame size)

## 3. If forced to implement — B′ file-by-file change list

If the lead overrides the defer recommendation:
- `crates/rvp9-decoder/src/tile.rs` — split `decode_tile_intra` / `decode_tile_inter` into `parse_tile_sb_row` (parse + write ModeInfo + write coef tokens to a per-row scratch buffer) and `reconstruct_tile_sb_row` (consume scratch → intra/IDCT/MC → frame). ~400 LOC.
- `crates/rvp9-decoder/src/lib.rs` — opt-in dispatch: profile pre-scope (cumulative bytes per tile), pick the largest, submit one extra "reconstruct-only" job for it; the primary tile worker signals row-ready via existing `decode_progress[r].fetch_add(1, Release)`. ~150 LOC.
- `crates/rvp9-decoder/src/tile_ctx.rs` — per-SB-row scratch struct (token list + partition tree + ModeInfo splats). ~100 LOC.
- `crates/rvp9-decoder/src/trace_flags.rs` — `RVP9_TILE_PIPE=1` opt-in; default off. ~5 LOC.

## 4. Synchronisation primitive design (B′)
Re-use Wave 2 C2 atomics. The primary writes `decode_progress[sb_row].store(parsed_marker, Release)` immediately after writing the SB-row's parse scratch to a stable slot in a `RowScratchRing` (lock-free SPSC ring sized to `sb_rows`). The reconstruct worker spins-with-pause on `decode_progress[r].load(Acquire) >= parsed_marker`, then consumes the slot. Release/Acquire pairs every published scratch write with the consumer's first read. **No new condvar; no per-row mutex.** All atomic; the spin is bounded by parse latency (<200 µs/row) — fall back to `std::hint::spin_loop` not `park`.

## 5. Bitstream-parse dependency analysis
Strictly serial within a tile (must run in tile-order): `BoolReader` cursor; `above`/`left` ModeInfo reductions; `coef_ctx.above_coef`; `part_ctx`; segmentation predictor state; FrameContext probability tables (read-only across a frame, but the `above` reductions depend on previously-parsed blocks). May run in any order *after parse*: intra-prediction sample reads from already-reconstructed neighbours, IDCT, MC, writes to `TileFrameView`. **B′'s split-point is exactly the boundary between `decode_partition_parse` and `reconstruct_block`.** Today these are fused; splitting them is most of the LOC.

## 6. Test plan
1. Full 201-vector conformance with `RVP9_TILE_PIPE=0` and `RVP9_TILE_PIPE=1`; per-frame MD5 must match in both modes.
2. New differential test in `crates/rvp9-harness/tests/`: each multi-tile fixture decoded threads=1 vs threads=4 vs threads=4+`TILE_PIPE=1`; all three MD5 outputs identical.
3. Perf gate (`bench-pin.ps1`): require `testsrc_1080p30 t=4` median ≤ pre-W6 median + 50 µs/frame *with the flag OFF* (zero overhead when off) AND ≥ 5% improvement *with the flag ON* before merging the default-flip.

## 7. Risk register
| # | Risk | Mitigation |
|---|------|-----------|
| 1 | W2 trap — scope/dispatch overhead exceeds gain on small frames | Opt-in only; perf gate at +50 µs/frame off-state; defer the default-flip until gate is met |
| 2 | Conformance break in parse/reconstruct split | Stage the refactor: first land parse/reconstruct split *with no concurrency* (fused-serial-equivalent), validate 201/201, then introduce the second worker |
| 3 | RowScratchRing memory blow-up on large frames | Cap ring depth = 4 SB rows (worker can't fall more than 4 rows behind); back-pressure the primary if depth saturates |
| 4 | Parse fraction <30% — gain too small to amortise overhead | Add a one-shot calibration in the bench harness *before* implementation; abort Wave 6 if measured parse fraction ≤ 25% |
| 5 | Spin-wait burning a core when LF worker also wants it | Spin budget cap (1000 iterations ≈ 3 µs) then yield; revert to Acquire load (no park, no condvar) |

## 8. Rollout switch
`RVP9_TILE_PIPE` env var (read by `trace_flags.rs`, same OnceLock pattern as `RVP9_ROW_MT`); CLI flag `--tile-pipe` on `decode-profile-tiles`. **Default OFF.** Same opt-in pattern as the Wave 2 outcome.

## 9. DO-NOT list
- DO NOT introduce a *per-SB* scope job (only 1 extra job per scope, period).
- DO NOT add a condvar / park-based wait path; spin on the existing `decode_progress` atomics.
- DO NOT split parse across multiple workers (CABAC seriality).
- DO NOT re-introduce per-tile scratch `Yv12Buffer`s (Phase 1 eliminated them; the second worker writes into the same `TileFrameView` as the primary, on disjoint SB rows).
- DO NOT flip the default to ON in the same commit that introduces the path — require a separate, perf-gated default-flip commit (Wave 2 pattern).

## 10. Trigger conditions for revisiting

This plan should be re-evaluated if any of the following change:
1. Frame sizes grow significantly (4K conformance corpus added → per-frame budget for dispatch overhead grows linearly).
2. Pinning/PGO/etc reduces single-tile decode below ~800 µs (then dispatch tax becomes large fraction).
3. We acquire a measurement showing parse fraction > 40% on a real-world fixture (would justify B′).
4. The decoder gains a need for HBD or 4:4:4 (intrinsically much more parse work, shifting the calculus).
