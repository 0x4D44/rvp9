## §0 TL;DR for the team-lead

**Verdict: SHELVE for `testsrc_1080p30 t=4`.** Within-tile row-MT decode is
the libvpx-faithful textbook answer to "more parallelism per tile", but on
the *headline fixture* it cannot help because:

1. The headline fixture is **already at 4 tiles / 4 workers**, with **only
   1.6% measured tile imbalance** (overlap HLD §2). The remaining 29% idle
   is dominated by **serial main-thread work (12.6%)** + **LF-scope
   under-utilisation (10.1%)** + **wake/park residual (~5%)**, NOT by
   intra-tile imbalance.
2. The mechanism that within-tile row-MT exploits — parse/recon split —
   adds **per-SB scratch buffers, an MPMC job queue, and a sustained
   parse↔recon wavefront-fill stall** that, on a fixture already busy with
   4 decode workers, is **strictly added overhead** with **no parallelism
   to unlock**.
3. The two predecessors that died (Wave-2 row-MT-LF: 1.5× regression;
   single-scope overlap: missed the 5% PGO gate) **failed for exactly the
   same root cause**: their sync-and-orchestration tax exceeded the idle
   reclaimed under PGO. Within-tile row-MT has *strictly more sync
   overhead* than the overlap lever (parse↔recon wavefront *plus* the
   tile-cross merge), and *less idle to reclaim* (only 1.6% imbalance,
   versus the overlap's 10.1% LF-scope target). It would fail the same
   gate, harder.

**The only conditions where this lever would win:**
- **Fixtures with `#tile_cols < #workers`** (e.g. single-tile 1080p, t=4).
  No such fixture is in the bench matrix today. **Adding one would be a
  retarget decision, not a lever to apply to the existing headline.**
- A fixture with *large per-tile imbalance* (> ~15% on the headline; we
  measured 1.6%).

If Arthur wants to retarget "match vpxdec" to a single-tile fixture,
Phase 1 of this design (sketched in §7) is the libvpx-faithful blueprint
and is worth ~1.2-1.5× on such a fixture. **On the current headline, this
HLD's recommended action is SHELVE — same failure mode as overlap / Wave-2,
documented and disproved.**

## §1 What within-tile row-MT decode actually is (libvpx model)

Citations from `third_party/libvpx/vp9/decoder/vp9_decodeframe.c` and
`vp9_decoder.c`:

- **Parse stage (serial per tile):** `parse_intra_block_row_mt` /
  `parse_inter_block_row_mt` (vp9_decodeframe.c:338, :421) read the
  partition tree + mode info + **coefficients** for one SB row using the
  per-tile `BoolReader`, writing **dequantised coefficients into per-SB
  scratch buffers** (`row_mt_worker_data->dqcoeff[plane] + (sb_num <<
  DQCOEFFS_PER_SB_LOG2)`, eob arrays, partition tree). It does **NO**
  pixel writes — no intra-pred, no MC, no IDCT, no transform-add.
- **Recon stage (row-parallel within a tile):**
  `predict_and_reconstruct_intra_block_row_mt` /
  `reconstruct_inter_block_row_mt` (:362, :437) consume those per-SB
  scratch buffers and do the pixel-producing work (intra-pred + IDCT +
  add, or MC + IDCT + add). Reads previous-row pixels for intra
  neighbours; gated on a **column-wavefront** `cur_sb_col[r-1]` exactly
  like LF (`map_read` at :1713 with `nsync_sb_cols` headroom).
- **Job queue:** a single MPMC queue holds both PARSE and RECON jobs.
  Worker pulls any job; PARSE for tile T row R is sequential-after-PARSE
  for tile T row R-1 (same per-tile BoolReader state); RECON for any
  tile's row R can run as soon as its PARSE finishes AND its column
  predecessor satisfies the wavefront.
- **Tile-cross merge:** the LF gate `recon_done_mutex` + `num_tiles_done`
  (:1755) coordinates when all tiles have finished row R so LF row R can
  proceed.

The fundamental restructuring: **parse and recon, which today live in one
fused function (`reconstruct_intra_block` / `reconstruct_inter_block`
called *inside* `decode_block`), become two separate, schedulable units
communicating through per-SB scratch buffers.**

## §2 Where rvp9 stands today (the code shape)

I read the relevant files end-to-end:

- `crates/rvp9-decoder/src/tile.rs:681 decode_block` calls
  `reconstruct_intra_planes` (:1190) which calls
  `reconstruct_intra_block` (`reconstruct.rs:165`) which threads the
  `BoolReader` into `decode_block_tokens` (entropy decode of
  coefficients) and immediately into IDCT + add. **Fully fused.**
- `tile.rs:1493 decode_tile_inter` → `decode_inter_partition` (:1585)
  → eventually `reconstruct_inter_block` (`reconstruct_inter.rs`) with
  the same BoolReader-threading pattern. **Fully fused.**
- The per-tile `BoolReader` (`tile.rs:397, 1520`) carries the sequential
  arithmetic-coder state — **no way to advance it out of order; parse
  is strictly serial per tile**.
- The Wave-2 `decode_progress[r].fetch_add(1, Release)` publish point
  (`tile.rs:477` intra / `tile.rs:1572` inter) already exists and is
  consumed only by the LF column-wavefront today.
- The worker pool (`crates/rvp9-core/src/tile_threading/pool.rs`) is a
  long-lived crossbeam-channel job queue with `scope`-bounded submission
  and a single `done_rx.recv()` join — well-suited for adding more job
  kinds inside a scope. **But:** the channel does FIFO MPMC; the libvpx
  `vp9_job_queue` allows priority dequeue (PARSE > RECON when both ready)
  which rvp9's pool cannot do today without modification.

**LOC estimate for the parse/recon split, before benchmarking:**
- Restructure `reconstruct_intra_planes` + `reconstruct_inter_block` to
  separate the *coefficient decode + dequant* (parse arm, takes
  BoolReader) from the *intra-pred + IDCT + add* / *MC + IDCT + add*
  arm (recon arm, takes pre-decoded coef buffer): **~300-400 LOC**
  refactor of two of the densest paths in the decoder (the parse path
  must materialise mode-info + bmi + tx_size + skip + eob + dq_coefs per
  SB into a thread-shared scratch struct).
- Per-SB scratch buffer allocation (`dqcoeff[plane]`, `eob[plane]`,
  `partition[]`, `mode_info` slab — libvpx: `dec_alloc_row_mt_mem` —
  for 1080p `sb_rows × sb_cols × 3-plane × MAX_TX_COEFFS × i32` =
  ~17 × 30 × 3 × 1024 × 4 = ~6 MiB per frame, recyclable across frames):
  **~80 LOC + pool plumbing**.
- New `WorkerPool` job-priority API or a separate "parse" sender — the
  libvpx model **requires** that PARSE jobs (which unblock everything)
  are picked up ahead of RECON jobs, else workers will idle on the
  wavefront waiting for parse to catch up: **~100 LOC** in the pool +
  scope + SAFETY.md update (this is **load-bearing** for any win).
- LF integration (PARSE-done → RECON-done → LF can start row R): reuse
  the existing decode_progress signal; no new code beyond what the
  overlap HLD already proposed.
- Differential test extension + TSan one-off: **~50 LOC**.
- **Total: 500-700 LOC**, exactly the team-lead's a-priori estimate, and
  matches the "architectural" scale of the brief.

## §3 The four claims this HLD must make (and what it actually finds)

The brief explicitly demands a specific, evidence-based case for each of
(a)-(d). I take them one by one. **Only (d) is provable; (a)-(c) fail.**

### §3.1 (a) Is there a measurable PGO-surviving idle to reclaim?

The overlap HLD §2 measured (under `profile-tiles`, ~PGO-equivalent) the
29% t=4 worker idle, decomposed as:

| idle source | % capacity | recoverable by within-tile row-MT decode? |
|-------------|-----------|--------------------------------------------|
| A. Serial main-thread phases (setup + submit + merge + border) | 12.6% | **NO.** Border-extend / merge / setup are main-thread, single-threaded work on whole-frame structures. Within-tile row-MT changes *tile-internal* scheduling — irrelevant to A. |
| B. Decode-scope **tile imbalance** | **1.6%** | **YES — but this is the *only* source the lever touches, and it's tiny.** Per-tile decode work varies by ~2.6% on the headline; with 4 tiles / 4 workers, that translates to 1.6% idle. |
| C. LF-scope under-utilisation | 10.1% | NO. LF scope is bounded by the LF column-wavefront, not by parse/recon. Already targeted (and missed-the-5%-gate) by the overlap HLD. |
| residual (wake/park, alloc jitter) | ~4.9% | NO. Smaller than the new sync overhead row-MT would add. |

**The reclaim ceiling for within-tile row-MT decode on the headline is
~1.6% of frame wall — far below the 5% PGO ship gate.** This is not
opinion; it is the overlap HLD's measured tile-imbalance number, which
the team-lead reviewed and signed off. The 29% idle is real but *not in
the bucket within-tile row-MT attacks*.

The single-scope overlap reached for the 10.1% LF-scope bucket (the *next*
biggest after the 12.6% irreducible serial floor) and **still missed the
5% PGO gate**, because PGO + the scheduler already collapsed most of the
notional barrier. Within-tile row-MT targets a 6× smaller bucket (1.6% vs
10.1%). It cannot clear the gate.

### §3.2 (b) Is the sync overhead provably lower than the idle reclaimed?

**No — it is provably *higher*.** Comparison:

| sync mechanism | overlap HLD | within-tile row-MT |
|----------------|-------------|---------------------|
| New atomic gates per frame | **1**: `decode_progress[r+1] >= num_tile_cols` checked **once per LF SB row** (17 acquires on 1080p × num_lf_workers) | **two**: per-SB column-wavefront PARSE→RECON gate (`cur_sb_col` per row, checked at nsync boundary, ~7-8 acquires per row × sb_rows × num_recon_workers) + the libvpx `recon_done`/`num_tiles_done` cross-tile gate before LF |
| Per-frame scratch alloc | none (reuses existing `decode_progress` Vec) | **~6 MiB per frame** dqcoeff/eob/partition slabs (poolable, but cold-cache the first frame and dirty L2 every frame) |
| Job-queue restructure | none (uses existing crossbeam channel + scope) | priority queue (PARSE > RECON) — **requires WorkerPool change** OR risks starvation |
| Pipeline-fill stall | none (LF jobs immediately ready when decode_progress[1] fires) | **PARSE row 0 must complete before any RECON can start** — every frame pays a "row 0 PARSE" startup latency at the top of the decode wall, in addition to the existing decode-tile startup |

The overlap missed the 5% PGO gate because — we now believe — PGO's
profile-guided codegen + the OOO core's out-of-order dispatch already
hide most of the *barrier* and *wake* overhead the model attributed to
the two-scope topology. The remaining "reclaimable" idle turned out to
be largely *inherent serial work* (the border-extend / merge / setup
12.6% that no threading topology touches).

Within-tile row-MT adds **strictly more sync edges** than the overlap
*plus* a non-trivial per-frame scratch-buffer working set that competes
for L2 with the active SB. Its sync overhead is provably higher; its
target idle is provably smaller. **The arithmetic forecloses (b).**

### §3.3 (c) Does the headline fixture benefit?

**No.** The headline (`testsrc_1080p30 t=4`) is 4 tiles / 4 workers with
1.6% tile imbalance. Within-tile row-MT decode helps when **either**:
1. `#tile_cols < #workers` — workers have nothing to do at the tile level,
   so subdividing one tile across workers fills them. **Not the
   headline.** The bench matrix has *no* such fixture: the only
   single-tile rows (`quantizer-00`, `testsrc_720p30`, `foreman-fp1`)
   are all `threads=1`. The closest near-miss is `testsrc_1080p60 t=8`
   (4 tiles, 8 threads), where 4 workers idle at the tile level — but
   the bench shows t=8 ≈ t=4 (1.6ms each), strongly suggesting the
   excess workers cost ~0 today and we're already near the saturation
   wall.
2. Per-tile imbalance is large enough to dwarf the new sync cost. **At
   1.6% the headline has 5× less imbalance than the within-tile-row-MT
   sync overhead the comparable libvpx mechanism imposes.**

For a real-world inter-heavy single-tile 1080p stream (which we *don't*
currently bench), the lever could plausibly yield ~1.2-1.5× on t=4. But
that is a different lever and a different campaign: **it requires
retargeting "match vpxdec" away from the testsrc family**, which is the
team-lead's listed strategic option (3) in the final consolidation. It is
NOT what the brief asks me to argue for.

### §3.4 (d) Bit-exactness preservation

**This is the only claim I can make affirmatively.** The libvpx model
preserves bit-exactness by:

1. **Parse stage is strictly serial per tile** (the BoolReader state
   cannot be parallelised). All entropy-coded values (mode info, MV refs,
   tx_size, skip, coefficients, partition tree) are decoded in the
   identical order they would be in the serial path — byte-identical
   probability state evolution. The split is in *where the decoded
   value goes* (scratch buffer instead of immediately consumed by recon),
   not in *what value is decoded*.
2. **Recon stage** reads from scratch and writes pixels. Intra-pred reads
   row r-1's pixels; the column-wavefront `cur_sb_col[r-1] >= c + nsync`
   gate (libvpx `vp9_thread_common.c`'s `map_read`, identical to the LF
   one we already shipped) guarantees row r-1 has been fully *reconned*
   `nsync` columns ahead before row r's recon at column c reads them.
3. **The libvpx LF gate** (`recon_done_mutex`/`num_tiles_done`) ensures
   LF row R starts only after every tile has reconstructed row R — same
   shape as the overlap HLD's L1 invariant (`decode_progress[r+1] ==
   num_tile_cols`). The libvpx-style `LF_DELAY = 1` requirement carries
   over.

The invariants are:
- **D1 (parse order):** PARSE of tile T row R may not begin before PARSE
  of tile T row R-1 completes. Enforced by *not submitting* PARSE_T,R
  until PARSE_T,R-1's atomic flag is set, OR by structuring PARSE jobs
  as one-per-tile and walking rows internally.
- **D2 (recon column wavefront):** RECON of tile T row R column c may
  not read row R-1's column c pixels before RECON_T,R-1 has finished
  column c + nsync (same as LF).
- **D3 (parse-before-recon):** RECON of tile T row R may not begin
  before PARSE_T,R has finished (the scratch buffer must be populated).
- **D4 (LF gate):** unchanged from overlap HLD's L1, plus `LF_DELAY=1`.

D1 + D3 together imply the parse-vs-recon scratch buffer is always
written-before-read; D2 mirrors the proven Lever-B-v2 LF wavefront; D4
is libvpx-faithful.

**Differential test:** the standard threads=1 (fully serial) vs
threads=4 (within-tile-row-MT) per-frame MD5 differential catches any
invariant violation, exactly as it caught Lever-B-v2's `c+nsync-1` bug.
This is the same testing oracle the overlap HLD relied on. Cheap and
sufficient.

(d) is fine. (a), (b), (c) are not.

## §4 Why this fails for the *same reason* overlap and Wave-2 failed

The brief asks me to design *around* the prior failures, not replicate
them. I can't. Here is the failure-mode analysis:

### §4.1 Wave-2 row-MT-LF (1.5× regression)
- Used a **row barrier** (`lf_progress[r-1] == 1` before *any* of row r).
- Every LF worker stalled an entire row's worth of LF work at each
  boundary; the sync cost > the parallelism gained.
- **Root cause:** sync overhead exceeded recovered parallelism on the
  fixture.

### §4.2 Single-scope overlap (missed 5% PGO gate)
- Used the **proven column-wavefront** (no row barriers — designed
  *around* Wave-2's failure mode).
- Targeted ~10.1% LF-scope under-utilisation (the largest *non-irreducible*
  idle bucket).
- Model predicted 13-16% reclaim; measured under PGO: **< 5%**.
- **Root cause:** PGO + scheduler had already collapsed most of the
  notional barrier cost. The "idle" the model assumed could be reclaimed
  was largely (a) inherent serial floor and (b) sync/wake overhead the
  threading change couldn't avoid.

### §4.3 Within-tile row-MT decode (this HLD)
- Would use the proven column-wavefront for recon (designed *around*
  Wave-2's failure mode — good).
- Targets ~1.6% tile-imbalance idle (the *smallest* bucket — bad).
- Adds *more* sync edges and per-frame scratch buffers than the overlap
  lever (the comparison in §3.2).
- **The exact same root cause as the overlap miss**, only worse: even
  smaller idle target, even larger sync surface. Under PGO, the residual
  idle the threading change can actually reclaim will be a fraction of
  1.6% — and the added per-SB sync + scratch-buffer cost will dwarf it.

This isn't an off-by-one or a design choice that can be tuned. It is the
**arithmetic of the gap**: there is no meaningful within-tile parallelism
to extract on a 4-tile-4-worker fixture with 1.6% imbalance. Implementing
the libvpx mechanism cannot create idle that isn't there.

### §4.4 The honest "why libvpx ships this anyway"

libvpx's `row_mt=1` is **not** a peak-perf knob for the 4-tile-4-worker
case. Looking at the libvpx commit history and how Google deploys it, it
exists to:

1. Improve perf on **single-tile** streams (which dominate Android /
   Chromecast playback of YouTube content, where tile count is often 1
   for compatibility with hardware decoders).
2. Improve perf on **#threads > #tile_cols** configurations, the typical
   "give me all your cores" desktop case.
3. Be a *correctness* primitive for the frame-parallel decode path.

It is **not** intended to improve perf on the case rvp9 actually has
(4 tiles / 4 workers, ~no imbalance). On that case libvpx itself doesn't
recommend `row_mt=1`. We would be applying it outside its design intent.

## §5 Sketch of what we WOULD do (if a future single-tile retarget happens)

Recorded for posterity / handoff, **not** as a recommendation to act on
today. This sketch presumes Arthur retargets to a single-tile 1080p
fixture as a new headline.

### §5.1 Topology
Single scope hosting three job kinds:
1. PARSE_T (one per tile) — serial walk of all SB rows within tile T,
   publishes `parse_progress[r]` per row.
2. RECON_T,R (potentially many in flight) — gated by
   `parse_progress[r] >= 1` AND column-wavefront on `recon_sb_col[r-1]`.
3. LF_W (existing column-wavefront workers) — gated as in overlap HLD.

PARSE_T runs on whichever worker is free. RECON walkers are
dispatched per row; for `tile_cols == 1` and `nworkers == 4`, ~4 RECON
walkers process consecutive rows in parallel under the column wavefront.

### §5.2 The data scratch (the load-bearing artifact)
Per frame, per tile, per SB row: a `ScratchSb` of mode_info + bmi +
tx_size + skip + per-plane eob[16] + per-plane dq_coefs[1024 i32] +
partition tree. Sized to the worst-case SB. Allocated from a per-tile
pool, recycled each frame. ~6 MiB for 1080p single-tile.

### §5.3 Parse/recon split point
- Inside `decode_block` (`tile.rs:681`), the existing call to
  `reconstruct_intra_planes` (:887) becomes a write into the scratch
  followed by `parse_progress[r].fetch_add(1, Release)` once the whole
  row has been parsed.
- A new `reconstruct_intra_planes_from_scratch` (recon-only — takes the
  scratch instead of the BoolReader) is called by RECON workers, gated
  by D2 + D3.
- Same shape for the inter path against `reconstruct_inter_block`.

### §5.4 Worker pool changes
- Add a priority field to `scope.submit` (PARSE high, RECON low). Without
  this, RECON jobs can starve a worker into waiting on parse_progress,
  pinning a core. Roughly 100 LOC + SAFETY.md update.

### §5.5 Test plan
- Differential threads=1 vs threads=4 per-frame MD5 (always-on, every
  commit).
- TSan one-off on the new parse_progress + recon_sb_col edges + the
  scratch buffer producer/consumer pair.
- 201-vector conformance both flag-states.
- PGO end-to-end A/B with a real single-tile 1080p fixture. **Ship gate:
  ≥5% mean+p50 vs the two-scope baseline.**

### §5.6 Cost estimate (sketch only)
~500-700 LOC, ~2-3 weeks calendar including the worker-pool prio change,
TSan validation, and fixture acquisition. **Worth ~1.2-1.5× ONLY on a
single-tile 1080p fixture.** Worth ≈0 on the current headline.

## §7 Recommendation

**SHELVE on the current headline fixture (`testsrc_1080p30 t=4`).**

The case for within-tile row-MT decode on this fixture cannot be made
because:
1. The measurable reclaim ceiling is ~1.6% of frame wall (the measured
   tile imbalance). Below the 5% PGO ship gate.
2. The sync + scratch overhead is **strictly larger** than the overlap
   lever's, which already missed the same 5% gate on a 6× larger target
   bucket. Same failure mode, deeper.
3. The headline's gap is *not* in the bucket within-tile row-MT attacks.
   The gap is the inherent ~12.6% serial floor + the ~2-3× per-work
   overhead the gap characterisation journal identified, and neither is
   reachable by adding more parallelism on a near-saturated fixture.

**Optional pivot (Arthur's call, not this HLD's recommendation):** if
"match vpxdec" gets retargeted to a single-tile 1080p inter-heavy
fixture, §5 sketches the libvpx-faithful implementation. ~500-700 LOC,
~1.2-1.5× expected on such a fixture, ~2-3 weeks calendar. But that is a
**target-change decision**, not a lever to apply to the current headline.

**The autonomous quick-lever class is, by the consolidation journal's own
words, "thoroughly mapped and exhausted." Within-tile row-MT decode is
the architectural option the consolidation called out as the next step
"if pursuing", but only with eyes open about the headline-fixture
ceiling. With eyes open: this HLD says don't pursue on the current
headline.**

## §8 DO-NOT list (if a future pivot revisits this)

1. DO NOT use a row barrier. Wave-2's failure mode.
2. DO NOT submit per-SB scope jobs. Wave-2 / Lever-B-v2 #1 — channel
   overhead is ~50-100 µs per `scope.submit`, would dwarf the budget.
3. DO NOT park/condvar on the parse/recon wavefront. Same shape as the
   LF wavefront — atomic + spin + `yield_now` is the proven primitive.
4. DO NOT under-prioritise PARSE jobs. Without PARSE > RECON priority,
   workers will starve on parse_progress and the pipeline stalls.
5. DO NOT scope the lever to fixtures where `#tile_cols == #workers` and
   imbalance is small. It cannot help there. The lever lives or dies on
   single-tile / understaffed-tile fixtures.
6. DO NOT touch the entropy/parse mathematical path. The split is
   *where the decoded value goes*, not *what is decoded*. The BoolReader
   state evolution must be byte-identical to the serial path.
7. DO NOT take the PGO gate as optional. Five levers in this drive have
   shown that non-PGO signals lie. ≥5% mean+p50 under PGO end-to-end on
   the chosen fixture is binding.
8. DO NOT skip the differential test on any commit (inherited from
   every prior wave).
