# 2026.06.25 - PLN - performance test hardening

## Purpose

Turn the current performance measurement work into a dependable regression system
for both decoder and encoder performance.

The decoder mostly works functionally, so decoder performance should now move from
"informative benchmark output" to "release-quality signal". Encoder performance is
less mature and needs broader coverage before it can protect the realtime goals.

## Current State

### Decoder

The decoder has the better performance apparatus today.

Implemented:

- `crates/rvp9-bench/src/throughput.rs`
  - Measures steady-state `Decoder::decode_frame`.
  - Excludes file I/O and most container work.
  - Reuses one decoder per fixture.
  - Drops warmup frames.
  - Loops to at least 1000 timed frames.
  - Reports p50, p95, and p99.
- `crates/rvp9-bench/tests/decode_throughput_ratchet.rs`
  - Defines a 10% p50 regression ratchet.
  - Uses committed rows in `bench/results/decode-throughput.csv`.
  - Currently has no pinned host, so it is not a hard gate.
- `crates/rvp9-bench/src/bin/decode-headtohead.rs`
  - Runs the rvp9 side of the head-to-head matrix.
  - Supports thread-count sweeps.
- `scripts/bench-headtohead.ps1`
  - Orchestrates rvp9 vs `vpxdec`.
  - Generates `bench/results/decode-headtohead.md`.
  - Appends `bench/results/decode-headtohead.csv`.
- `bench/results/decode-headtohead.md`
  - Latest committed ledger has rows for single-tile, multi-tile, 720p30,
    1080p30, 1080p60, and Profile 1.

Gaps:

- `PINNED_HOSTS` is empty, so the ratchet does not hard-fail anywhere.
- The head-to-head gate is `PASS-info` / `FAIL-info`, not a real release gate.
- The local checkout does not always have benchmark fixtures populated.
- `vpxdec` is not guaranteed to exist on the machine running the test.
- Current committed numbers show rvp9 under absolute realtime budgets, but still
  several times slower than `vpxdec` on common rows.
- PLAN still asks for decoder throughput within 2x of libvpx; current head-to-head
  rows are not consistently near that bar.

### Encoder

The encoder has useful checks, but weaker performance coverage.

Implemented:

- `crates/rvp9-encoder/tests/realtime_gate.rs`
  - Ignored release-mode 720p30-ish realtime gate.
  - Measures `StreamEncoder::encode_frame`.
  - Uses a 1280x704 crop of `testsrc_720p30.y4m`.
  - Asserts median <= 33 ms after warmup.
- `crates/rvp9-encoder/tests/quality_gate.rs`
  - Measures quality/bitrate behavior against libvpx when fixtures/tools exist.
  - This is a compression signal, not a pure performance regression gate.
- `crates/rvp9-bench/src/bin/realtime.rs`
  - Older binary that times an external encoder by total wall time.
  - Useful for subprocess comparisons, but too coarse for rvp9 internal
    regression protection.

Gaps:

- No broad encoder realtime matrix equivalent to decoder head-to-head.
- No encoder perf ratchet.
- 1080p30 and 1080p60 encoder realtime goals are not covered as hard tests.
- Current encoder realtime test uses median only; tails are not protected.
- The test source is narrow: mostly `testsrc`, not enough real-motion content.
- Encoder quality gates and encoder speed gates are coupled socially but not
  mechanically balanced.

## Target State

### Decoder Target

Decoder performance should have two layers:

1. Fast local signal:
   - Runs on normal developer machines.
   - Reports p50/p95/p99.
   - Warns on unpinned hosts.
   - Never blocks work due to host noise.

2. Hard pinned signal:
   - Runs on one named, stable host.
   - Uses fixed power/perf settings.
   - Has populated fixtures and `vpxdec`.
   - Fails on regression.
   - Records trend data.

Release bars:

- Absolute realtime budgets from `PLAN.md`:
  - 720p30: median <= 33 ms, p99 <= 50 ms.
  - 1080p30: median <= 33 ms, p99 <= 50 ms.
  - 1080p60: median <= 16 ms, p99 <= 25 ms.
- Relative libvpx bar:
  - Track and improve toward <= 2x `vpxdec`.
  - Treat > 2x as a performance debt item until closed.

### Encoder Target

Encoder performance should have a separate realtime gate set from quality gates.

Release bars:

- 720p30: median <= 33 ms, with a tail guard.
- 1080p30: median <= 33 ms on the intended thread/tile configuration.
- 1080p60: median <= 16 ms on the intended thread/tile configuration.
- No performance win should be accepted if it materially harms the active quality
  gate, and no quality win should be accepted if it misses the realtime gate.

## Plan

## Phase 1 - Make Decoder Perf Reproducible

Goal: every performance run has the inputs and tools it claims to use.

Tasks:

1. Restore or build `vpxdec`.
   - Preferred path: `build/libvpx/vpxdec.exe`, matching `scripts/bench-headtohead.ps1`.
   - Verify with: `build/libvpx/vpxdec.exe --help`.
   - If the repo prefers a sibling-tree stock build, document the exact path and
     update the scripts to probe it consistently.

2. Populate decoder benchmark fixtures.
   - Required conformance vectors:
     - `vp90-2-00-quantizer-00.webm`
     - `vp90-2-08-tile_1x2.webm`
     - `vp90-2-08-tile_1x4.webm`
     - `vp90-2-08-tile_1x8.webm`
   - Required corpus fixtures:
     - `tests/corpus/fixtures/testsrc_720p30.ivf`
     - `tests/corpus/fixtures/testsrc_1080p30.ivf`
     - `tests/corpus/fixtures/testsrc_1080p60.ivf`
     - `tests/corpus/fixtures/foreman-fp1.ivf`

3. Add a small fixture readiness command.
   - Either add a script such as `scripts/check-perf-fixtures.ps1`, or add a
     `--check-only` mode to `scripts/bench-headtohead.ps1`.
   - It should report missing inputs without starting a benchmark.
   - It should return non-zero when a required pinned-run fixture/tool is missing.

4. Document fixture generation.
   - Keep generated `.ivf` fixtures gitignored.
   - Put exact commands in `tests/corpus/fixtures/README.md` or this plan's
     successor HLD.
   - Include source clip expectations and frame counts.

Acceptance:

- `scripts/bench-headtohead.ps1 -SkipRvp9Bench -SkipVpxdec` can validate fixture
  presence without confusing missing-tool failures.
- A fresh performance machine can be prepared from documented commands.

## Phase 2 - Promote Decoder Ratchet to a Real Gate

Goal: decoder regressions fail on a stable host.

Tasks:

1. Pick the pinned host.
   - Record its `host_fingerprint()` output.
   - Record CPU model, core count, OS, compiler/toolchain, and power settings.
   - Prefer a Linux runner with CPU governor pinned; if using Windows, document
     the limits honestly.

2. Update `PINNED_HOSTS`.
   - File: `crates/rvp9-bench/tests/decode_throughput_ratchet.rs`.
   - Add only the selected stable host fingerprint.
   - Keep dev machines warning-only.

3. Seed pinned baselines.
   - Run:
     - `cargo run --release -p rvp9-bench --bin decode-throughput -- --pinned`
   - Commit the resulting `bench/results/decode-throughput.csv` rows.
   - Confirm the rows have `unpinned=false`.

4. Make the ratchet cover p95/p99 as well as p50.
   - Current ratchet checks p50 only.
   - Add thresholds:
     - p50: +10% max.
     - p95: +15% max.
     - p99: +20% max.
   - Keep p50 as the primary signal; tails catch scheduler-sensitive or
     allocator-sensitive regressions.

5. Keep local runs non-blocking.
   - On non-pinned hosts, report violations as warnings.
   - On pinned hosts, fail the test.

Acceptance:

- `cargo test --release -p rvp9-bench --test decode_throughput_ratchet` hard-fails
  on the pinned host when a fixture exceeds its threshold.
- The same command remains warning-only on ordinary developer machines.

## Phase 3 - Promote Decoder Head-to-Head Budgets

Goal: absolute realtime budgets and libvpx-relative performance are visible and
actionable.

Tasks:

1. Keep `decode-headtohead` as the broad performance ledger.
   - It should remain the human-readable overview for decoder performance.
   - It covers the right dimensions: resolution, tiles, threads, and libvpx ratio.

2. Add pinned-host hard gate semantics.
   - On pinned host:
     - `PASS-info` becomes `PASS`.
     - `FAIL-info` becomes `FAIL`.
     - Any `FAIL` exits non-zero.
   - On unpinned hosts:
     - Keep `PASS-info` / `FAIL-info`.

3. Add p99 budget comparison for rvp9.
   - The ledger already records rvp9 p99 in CSV.
   - Surface p99 in the Markdown table or a second "tail budget" table.
   - Compare against PLAN p99 bars:
     - 720p30 / 1080p30: p99 <= 50 ms.
     - 1080p60: p99 <= 25 ms.

4. Split absolute and relative verdicts.
   - Absolute budget verdict:
     - Is rvp9 real-time enough?
   - Relative verdict:
     - Is rvp9 within 2x `vpxdec`?
   - Do not hide a 4x-to-7x libvpx gap behind an absolute PASS.

5. Add trend comparison workflow.
   - Use existing `crates/rvp9-bench/src/bin/bench-compare.rs`.
   - Standard command shape:
     - baseline sweep: `scripts/bench-headtohead.ps1 -Runs 5 -SkipVpxdec`
     - candidate sweep: `scripts/bench-headtohead.ps1 -Runs 5 -SkipVpxdec`
     - compare timestamps with `bench-compare`.
   - Require this for performance-sensitive decoder changes.

Acceptance:

- The head-to-head report says four things clearly:
  - rvp9 absolute median verdict.
  - rvp9 absolute tail verdict.
  - rvp9 vs `vpxdec` ratio.
  - whether the run was pinned or informational.

## Phase 4 - Broaden Decoder Fixture Coverage

Goal: avoid optimizing only synthetic/testsrc and short conformance clips.

Tasks:

1. Add at least one real-motion 720p fixture.
   - Candidate source: `foreman_cif.y4m` scaled/cropped to a stable fixture, or a
     Derf 720p clip already used by repo corpus scripts.
   - Use a fixed encode recipe.
   - Keep generated fixture gitignored.

2. Add one high-res multi-tile natural-content fixture.
   - This should exercise tile threading and loop-filter behavior on non-flat
     content.
   - Prefer 1080p30 over 4K until the suite cost is understood.

3. Add one segmentation or unusual-bitstream fixture to perf coverage only if it
   represents a realistic cost risk.
   - Do not let rare conformance oddities dominate the median suite.

4. Keep the default suite small.
   - Target: 8-12 rows for the head-to-head matrix.
   - Larger experiments can live behind explicit `--row` arguments.

Acceptance:

- The broad decoder suite includes:
  - small single-tile control,
  - multi-tile control,
  - 720p realtime,
  - 1080p30 realtime,
  - 1080p60 realtime,
  - one real-motion content row,
  - one profile/non-default row.

## Phase 5 - Build Encoder Performance Gates

Goal: make encoder realtime regressions visible before they become quality work
confounds.

Tasks:

1. Extend `realtime_gate.rs` into a small matrix.
   - Keep the current 720p30 row.
   - Add 1080p30 row.
   - Add 1080p60 row.
   - Use the intended realtime config for each row.

2. Record more than median.
   - Current test reports a five-number summary but gates median only.
   - Add tail guards:
     - p95 or p99 for each row.
   - Keep thresholds looser than decoder initially to avoid flaking on local
     machines.

3. Separate local informational mode from pinned hard mode.
   - Match decoder policy:
     - unpinned: report only,
     - pinned: fail on threshold breach.

4. Add an encoder perf trend CSV.
   - Similar to `decode-throughput.csv`.
   - Columns:
     - schema_version,
     - timestamp,
     - host,
     - unpinned,
     - git_sha,
     - config label,
     - source label,
     - width,
     - height,
     - frames,
     - warmup_frames,
     - p50_ms,
     - p95_ms,
     - p99_ms,
     - output_kbps,
     - q summary if cheap to expose.

5. Add an encoder perf ratchet.
   - Start warning-only.
   - Promote to pinned hard gate once the runner exists.
   - Threshold proposal:
     - p50: +10% max.
     - p95/p99: +20% max.

6. Keep quality and speed paired.
   - Performance-sensitive encoder PRs should run:
     - encoder realtime matrix,
     - Stage 4a/4b quality gate relevant to the touched area,
     - cross-decoder gate.
   - A speed win that blows up BD-rate or matched PSNR is not a win.

Acceptance:

- Encoder has a standard "speed gate" command that covers 720p30, 1080p30, and
  1080p60.
- The command emits machine-readable trend rows.
- Local runs are useful, pinned runs are enforceable.

## Phase 6 - Add Microbenchmark Discipline

Goal: use microbenchmarks to explain changes, not replace end-to-end gates.

Tasks:

1. Keep `dsp-microbench` for kernel-level work.
   - File: `crates/rvp9-bench/src/bin/dsp-microbench.rs`.
   - Use it for transform, MC, intra-pred, bool-reader, and similar low-level
     changes.

2. Add or keep focused decoder profiling tools.
   - `decode-profile-tiles` should remain the tile-dispatch investigation tool.
   - Use it when changing worker scheduling, tile boundaries, or loop-filter
     overlap.

3. Require end-to-end confirmation.
   - A microbenchmark improvement only counts if it moves:
     - `decode-throughput`,
     - `decode-headtohead`, or
     - encoder realtime matrix.

4. Store notable microbenchmark baselines in `wrk_docs/` only when they affect a
   decision.
   - Avoid committing every scratch number.

Acceptance:

- Microbenchmarks are linked to concrete end-to-end before/after runs in journals
  or PR notes.

## Risks

- Host noise can make performance gates worse than useless if they run as hard
  gates on arbitrary machines.
- `target-cpu=native` means release binaries are host-tuned; do not compare across
  different CPUs as if the numbers are portable.
- Short fixtures distort mean timings when replay loops re-decode keyframes.
  Prefer p50 for rvp9 on short rows and disclose any `vpxdec` setup smear.
- Absolute realtime PASS can hide a large libvpx-relative gap. Keep both signals.
- Synthetic/testsrc content can overstate progress. Add natural-content rows before
  using the suite as a release argument.

## Definition of Done

This plan is done when:

- Decoder perf has one pinned hard gate.
- Decoder head-to-head reports absolute median, absolute tail, and libvpx ratio.
- Encoder perf has a 720p30 / 1080p30 / 1080p60 matrix.
- Both decoder and encoder write trend data.
- Local developer runs stay useful but do not block on host noise.
- Performance-sensitive changes have a standard validation bundle:
  - focused test,
  - relevant perf gate,
  - quality/cross-decoder pairing where applicable.
