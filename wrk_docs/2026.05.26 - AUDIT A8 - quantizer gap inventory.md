## 1. `vp9_set_quantizer` — frame-level entry (libvpx `vp9_quantize.c:291-303`)

libvpx's `vp9_set_quantizer` writes `cm->base_qindex = q`, zeros all three delta fields (`y_dc_delta_q`, `uv_dc_delta_q`, `uv_ac_delta_q`), then — if `oxcf.delta_q_uv != 0` — applies the chroma delta and re-runs `vp9_init_quantizer` to rebuild every (q, plane, band) row.

**Status: NOT PORTED.** There is no rvp9 entry-point named `vp9_set_quantizer` / `set_quantizer` (grep returns zero hits across `crates/`). The frame-loop writes `QuantizationParams { base_qindex, y_dc_delta_q: 0, uv_dc_delta_q: 0, uv_ac_delta_q: 0 }` into the header tail at `crates/rvp9-encoder/src/frame_loop.rs:1618-1622, 1870-1874` and `crates/rvp9-encoder/src/lib.rs:495-503, 656-660, 836-844, 5945-5953` — all four call sites hard-code the deltas to `0`. No `oxcf.delta_q_uv` plumb-through exists; no re-init on delta-change exists.

## 2. `vp9_init_quantizer` — per-qindex table precompute (libvpx `vp9_quantize.c:184-244`)

libvpx walks all 256 qindex rows ahead of time, populating `quants->y_quant[q][i]`, `y_quant_shift`, `y_quant_fp`, `y_round_fp`, `y_zbin`, `y_round`, plus the `cpi->y_dequant[q][i]` and mirrored `uv_*` slots. Indices 2..8 are filled with the AC row (segment alt-Q broadcast).

**Status: PARTIAL.** rvp9 implements the per-row math in `crates/rvp9-core/src/quant/forward.rs:472-507` (`init_plane_quantizers`) but with deliberate one-row-at-a-time evaluation (module docs explicitly call this out: "We materialise only one cell because the per-frame `q_index` is fixed once frame setup picks it"). What is missing:

- **No `QUANTS` table**. The decoder-side eight-element `y_quant[q][0..8]` etc. arrays are never materialised. This is fine while no segment uses an alt-Q row > 0, but it precludes a per-frame "build all rows, look up per-leaf" pattern.
- **Sharpness override** (`vp9_quantize.c:192-203`) — when `oxcf.sharpness > 0 && q > 0`, libvpx replaces `qzbin_factor` / `qrounding_factor` with `64 ± sharpness_adjustment` and overrides `qrounding_factor_fp` to `64 - sharpness_adjustment`. rvp9's `init_plane_quantizers` takes no sharpness parameter and the docstring at `crates/rvp9-core/src/quant/forward.rs:469-471` says "Sharpness is fixed to `0` (the default … When we later expose a sharpness setting (post-MVP), this signature gains a `sharpness: i32` parameter)". `sharpness_level: 0` is hard-coded at every `LoopFilterParams` construction site (e.g. `crates/rvp9-encoder/src/frame_loop.rs:1612, 1864`, `crates/rvp9-encoder/src/lib.rs:493, 650, 834, 5943`). This means CLI `--sharpness=N>0` is silently ignored at the quantizer side.
- **8/10/12-bit `get_qzbin_factor` cutoffs** — rvp9's `qzbin_factor_8bit` at `crates/rvp9-core/src/quant/forward.rs:513-522` uses the 148 cutoff for 8-bit. The 10-bit (`<592`) and 12-bit (`<2368`) cutoffs are NOT PORTED. (Row 5/6.)
- **`y_quant[q][2..8]` segment-alt-Q rows** (`vp9_quantize.c:226-242`) — broadcast of the AC values into rows 2..7. Not materialised in rvp9 because we evaluate per-call.

## 3. `vp9_init_plane_quantizers` — per-MB resolve (libvpx `vp9_quantize.c:246-285`)

Resolves `qindex` for this MB via `vp9_get_qindex(seg, segment_id, base_qindex)`, then copies the right row of every quant array into `x->plane[i]`, sets `xd->plane[i].dequant`, computes `quant_thred[0/1] = zbin * zbin`, sets `x->skip_block` from `SEG_LVL_SKIP`, stores `x->q_index`, calls `set_error_per_bit(x, rdmult)` and `vp9_initialize_me_consts(cpi, x, q_index)`.

**Status: PARTIAL.**

- `qindex` resolve **is ported** (`effective_qindex_for_segment` flows into `init_plane_quantizers` at `crates/rvp9-encoder/src/lib.rs:1368-1374`, `:2903-2910`, `:3434-3447`).
- `x->plane[*].quant{,_fp,_shift}`, `round{,_fp}`, `zbin` **are ported** via the `PlaneQuantizers` struct (`crates/rvp9-core/src/quant/forward.rs:421-438`).
- `xd->plane[i].dequant` **is ported** via `plane_dequant_pair` (`crates/rvp9-core/src/quant/forward.rs:553-561`) and consumed by the picker at `crates/rvp9-encoder/src/lib.rs:2907`, `:3444`.
- **`quant_thred[0/1] = zbin*zbin`** (libvpx `vp9_quantize.c:263-264, 275-276`) — **NOT PORTED**. Grep for `quant_thred` across `crates/` returns zero. This field is consumed in libvpx by the RDO trellis (`vp9_encodemb.c::optimize_b` and friends). The RT/non-RD path rvp9 currently lives in is not affected, but the RDO path Tier-3 work is.
- **`x->skip_block` from `SEG_LVL_SKIP`** (libvpx `vp9_quantize.c:279`) — **NOT PORTED**. rvp9 always passes `skip_block: false` to `vp9_quantize_b` (every call site verified: `crates/rvp9-core/src/mode_decision/inter.rs:2898-2924`, `intra.rs:382`, `crates/rvp9-encoder/src/lib.rs:1566-1591`, `:4740-4762`). The seg-skip feature short-circuit at the quantizer is therefore inactive even when the segmentation map flags it.
- **`set_error_per_bit(x, rdmult)`** (libvpx `vp9_quantize.c:282`) — **NOT PORTED**. Grep for `set_error_per_bit` across `crates/` returns zero. The picker uses a separate `compute_rd_mult` call (`crates/rvp9-core/src/cost/rd_mult.rs:62`) but never folds it into a per-MB "error per bit" the MV-search uses to compare SAD against a rate cost. The MV search reads a flat constant.
- **`vp9_initialize_me_consts(cpi, x, q_index)`** (libvpx `vp9_quantize.c:284`) — **NOT PORTED**. Grep for `me_consts` / `initialize_me_consts` / `sad_per_bit*` returns zero hits across `crates/`. libvpx uses this to set `x->sadperbit16` / `x->sadperbit4` from a qindex LUT (`vp9_rd.c:65-72, 191-195`), which the MV-search uses to compare SAD against rate. Without it, the full-pixel / sub-pixel MV search at `crates/rvp9-core/src/mv_search/` uses an effectively-frozen rate scaling.

## 5. `quantizer_to_qindex` / `qindex_to_quantizer` (libvpx `vp9_quantize.c:307-326`)

The `quantizer_to_qindex[]` LUT maps the 0..63 external "quantizer" CLI value to the internal 0..255 qindex (a roughly 4× step). `vp9_qindex_to_quantizer` is a linear scan that returns the smallest external bucket whose qindex meets-or-exceeds the input.

**Status: NOT PORTED.** Grep for `quantizer_to_qindex` / `qindex_to_quantizer` across `crates/` returns zero hits. The CLI `--quantizer 0..63` value-space is not surfaced by `rvp9enc`; the encoder takes a `base_qindex` directly. This is a real gap because `vpxenc --min-q/--max-q/--cq-level/--quantizer` are documented as the external 0..63 axis.

## 11. Cross-cutting gaps

### 11.1 `oxcf.sharpness` plumb-through

**Status: NOT PORTED.** Grep for `sharpness` across `crates/rvp9-encoder/src/` returns 7 hits — all writing `sharpness_level: 0` into `LoopFilterParams`. The CLI `rvp9enc` exposes no `--sharpness` flag. The libvpx semantics are:

1. Quantizer side (`vp9_quantize.c:194-197, 202-203`): `qzbin_factor = 64 + 16*(7-sharpness)/7`, `qrounding_factor = 64 - 16*(7-sharpness)/7`, `qrounding_factor_fp = 64 - 16*(7-sharpness)/7`.
2. Loopfilter side (separate; A9's territory).

Without quantizer-side sharpness, the encoder always behaves as `--sharpness=0`. Impact: medium — sharpness is a documented vpxenc knob; users who pass it get silent no-op.

### 11.2 `oxcf.delta_q_uv` plumb-through

**Status: NOT PORTED.** Grep for `delta_q_uv` across `crates/` returns zero. libvpx's `vp9_set_quantizer:299-302` re-inits the whole quant table when it changes. Encoder writes `uv_dc_delta_q: 0, uv_ac_delta_q: 0` always (six sites verified). UV planes therefore share Y's qindex exactly. Impact: medium — `vpxenc --tune-content=screen` and several other presets set delta_q_uv ≠ 0.

### 11.3 `quant_thred[0/1]` (RDO trellis input)

**Status: NOT PORTED.** Grep for `quant_thred` across `crates/` returns zero. libvpx computes `zbin*zbin` once per MB at `vp9_quantize.c:263-264, 275-276` and the trellis (`vp9_encodemb.c::optimize_b`) reads it to gate the "keep zero vs keep non-zero" decision. Without it the RDO path can't run faithfully. Impact: high for the RDO Tier (A13).

### 11.4 `set_error_per_bit(x, rdmult)` + `vp9_initialize_me_consts(cpi, x, q_index)`

**Status: BOTH NOT PORTED.** Both libvpx calls happen inside `vp9_init_plane_quantizers` (lines 282 and 284). They populate `x->errorperbit` and `x->sadperbit{4,16}` — the qindex-dependent rate-vs-distortion scales the MV search uses. Without these, the MV-search uses flat constants. Impact: HIGH on MV-search quality across the whole qindex range — overcharges MVs at low Q and undercharges at high Q.

### 11.5 SIMD dispatch table has no quantize slot

**Status: NOT PORTED.** The whole `SimdDispatch` machinery exists (`crates/rvp9-core/src/dsp/dispatch.rs:665+`), but it has no field for `quantize_b`, `quantize_b_32x32`, `quantize_fp`, or `quantize_fp_32x32`. All five encoder call sites (`crates/rvp9-encoder/src/lib.rs:1566-1591, 4740-4762, 4876-4898` and `crates/rvp9-core/src/mode_decision/{inter,intra}.rs`) call the scalar Rust kernels directly with no dispatch indirection. Impact: HIGH (perf) — quant kernels run at every leaf of every MV-candidate, so the AVX2 speedup factor is large.

### 11.6 UV plane init uses `QuantizerDeltas::Y`

**Status: PARTIAL bug.** `crates/rvp9-encoder/src/lib.rs:1373-1374` calls `init_plane_quantizers(leaf_qindex, QuantizerDeltas::Y)` for BOTH the `qp_y` and the `qp_uv` (literally — both lines pass `QuantizerDeltas::Y`). This is a latent bug masked by the fact that `delta_q_uv == 0` everywhere — but if/when section 11.2 is fixed, this UV table will silently keep using Y deltas. The same pattern recurs at `:3439-3442` (only `qp_y` materialised, UV's delta is computed inline as `{dc_delta:0, ac_delta:0}` for the dequant pair only, no `qp_uv` PlaneQuantizers built). The UV quantize at `crates/rvp9-core/src/mode_decision/intra.rs:1355` and other UV sites silently uses the Y `PlaneQuantizers`.

### 11.7 No `vp9_frame_init_quantizer` entry-point — recomputation per leaf

**Status: ARCHITECTURAL DIVERGENCE.** libvpx pre-computes all 256 rows at `vp9_init_quantizer` time, then per-MB does a row-pointer copy (`x->plane[0].quant = quants->y_quant[qindex]`, etc.) — O(1) per MB. rvp9's frame loop calls `init_plane_quantizers` for EVERY leaf (`crates/rvp9-encoder/src/lib.rs:1373, 1879, 2903, 3439`) — O(log² q · LOC) per leaf because it does an `invert_quant` per call. Impact: low-medium (perf) — this is a per-leaf integer-arithmetic call so not catastrophic, but a 64×64 SB with cyclic-refresh AQ enabled does this ~64 times.

### 11.8 `vp9_quantize_fp` is reachable from the F.1 block_yrd path only

**Status: OK-but-narrow.** Grep across `crates/` for `vp9_quantize_fp` returns hits in `mode_decision/inter.rs:2951-2972` (F.1 block_yrd via Hadamard) and the scalar definition itself. There is NO `vp9_quantize_fp` call from the actual encode loop (`encode_block` equivalents) — the encode loop at `crates/rvp9-encoder/src/lib.rs:1565-1591, 4740-4762, 4876-4898` always uses `vp9_quantize_b{,_32x32}`. libvpx's RT path uses `quantize_fp` for the **actual** encode at speed 6+ (see `vp9_speed_features.c::sf->use_quant_fp = 1`). The mismatch matters: `quantize_fp` skips the zbin gate, so the bitstream the rvp9 encoder produces is `quantize_b`-quantized while the libvpx RT bitstream is `quantize_fp`-quantized — a rate / distortion divergence at the actual encoded coefficient level.
