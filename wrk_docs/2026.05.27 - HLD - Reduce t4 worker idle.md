## §1 One-line summary

The decode→LF phase barrier and the surrounding serial per-frame work park all four workers ~29% of the time. Merge the two `WorkerPool::scope` calls (tile-decode scope, then LF scope) into **one scope** so the column-wavefront LF workers consume the **already-published** `decode_progress[r]` per-SB-row signal and filter row `r` the instant all tiles finish decoding it — exactly libvpx's `row_mt=1` model. Most of the plumbing (the `decode_progress` atomics, the `cur_sb_col` wavefront, `build_lfm_row` reading `&[Option<ModeInfo>]` directly) **already exists and is dormant**; this is a topology change, not new machinery.

## §2 Measured idle breakdown (the 29%)

Instrumented with the existing `profile-tiles` feature (`crates/rvp9-bench/src/bin/decode-profile-tiles.rs`), `testsrc_1080p30.ivf`, t=4, 1290 timed frames, medians. (Throwaway run; CSVs deleted. Box is a 24-thread dev machine — absolute µs differ from the team-lead's 4-core profiling box, but the *structure / percentages* are what transfer.)

Per-frame main-thread phase walls (median µs):

| phase | µs | % wall | what it is |
|-------|-----|--------|------------|
| setup | 80 | 4.0% | per-tile bounds, slot Vec alloc, scratch take (serial, main) |
| submit | 16 | 0.8% | the `scope.submit` loop (serial, main) |
| **join (decode scope)** | **1208** | **59.8%** | main blocks on the decode `scope()` — ≈ critical-path tile decode |
| merge | 51 | 2.5% | post-decode count/seg/mv merge (serial, main) |
| **loopfilter (LF scope)** | **457** | **22.6%** | the *separate* column-wavefront LF `scope()` |
| border | 108 | 5.3% | `extend_frame_borders` (serial, main) |
| WALL | 2019 | 100% | |

Worker-idle accounting (4 workers ⇒ capacity = 4 × 2019 = 8076 µs-thread/frame):

| | µs-thread | % capacity | source |
|---|-----------|-----------|--------|
| BUSY decode | 4704 | 58.2% | sum of 4 tiles' decode work |
| BUSY LF | 1014 | 12.6% | total LF compute (from serial-LF run = 1014 µs single-thread) |
| **IDLE** | **2358** | **29.2%** | — |

**This independently reproduces the team-lead's measured ~29% idle.** Decomposition of the idle:

| idle source | µs-thread | % capacity | recoverable by overlap? |
|-------------|-----------|-----------|--------------------------|
| **A. serial-phase parked** (4 × (setup+submit+merge+border) = 4 × 255) | 1020 | 12.6% | **partially** — these brackets run while workers park; overlap lets workers start the *next* frame's LF / this frame's LF during some of it, but the truly-serial setup/border cannot be parallelised |
| **C. LF-scope under-utilisation** (4 × LF-wall − LF-work = 4 × 457 − 1014) | 815 | 10.1% | **yes** — this is the LF wavefront fill + the worker-cap ceiling; folding LF into the decode scope hides most of it behind decode |
| **B. decode-scope tile imbalance** (4 × join − decode-sum = 4 × 1208 − 4704) | 127 | 1.6% | negligible — testsrc is 4 tiles / 4 workers, 2.6% imbalance |
| residual (channel wakeup `recv→park→NtWaitForAlertByThreadId` ×2/frame, alloc jitter) | ~396 | ~4.9% | partially — one fewer scope barrier ⇒ one fewer park/wake cycle per frame |

### §2.1 The honest finding (read this before approving)

**The idle is NOT dominated by a single fat "decode→LF barrier".** It is two comparable contributions plus tails:

1. **Serial per-frame work (A, 12.6%)** — `setup`, `merge`, `border`, `submit` run on the main thread with all four workers parked. The biggest single line is `extend_frame_borders` (108 µs) and `setup` (80 µs). **No threading topology change reclaims the truly-serial part** (border-extend touches the whole frame; setup allocates slot vectors). This is the "inherent serial work" caveat the team-lead asked me to be honest about — ~8% of the 29% is genuinely hard to reclaim without parallelising border-extend itself (out of scope; LF-kernel-adjacent and risk-laden).

2. **LF-scope under-utilisation (C, 10.1%)** — this is the **prime target**. The LF scope only achieves a 2.22× speedup from 4 workers (1014 µs work → 457 µs wall) because (a) it pays its own wavefront-fill latency from a cold start and (b) the worker count is capped at `min(4, tile_cols=4, sb_rows=17)=4` but the column-wavefront's steady-state parallelism on a 30-SB-wide frame with nsync=4 leaves workers idle at the row tails. Critically, **this entire 457 µs LF wall currently happens after the decode scope has fully drained** — none of it overlaps decode.

3. **Frame-mix nuance:** 30% of frames have `filter_level == 0` (no LF at all). For the 70% that *do* filter, the LF scope is ~30% of wall (626 µs LF behind 1214 µs decode). Decode-scope is consistently ~2× the LF-scope ⇒ **LF fits comfortably inside the decode-scope's timeline if overlapped.**

### §2.2 Overlap upper bound

If LF ran concurrently with decode (libvpx row-MT), steady-state frame wall ≈ `serial_floor + max(decode_crit_path, (decode_work + LF_work)/4)` = `255 + max(1192, 1430)` ≈ **1684 µs** vs current **2019 µs** ⇒ **max ~335 µs (16.6%) reclaim**, with a realistic 50–70%-of-LF-hidden estimate of **270–320 µs (13–16%)** off frame wall. That maps to roughly **~half of the 29% idle** (the recoverable C + part of A + the saved barrier).

## §3 Chosen design: single-scope decode↔LF overlap

### §3.1 Why this approach (vs the alternatives)

| candidate | verdict |
|-----------|---------|
| **Overlap LF with decode (single-scope)** | **CHOSEN.** Highest value for lowest *new* risk: the signal (`decode_progress`), the wavefront LF worker (`run_split_edge_lf_worker`), and the materialisation-free mask build (`build_lfm_row` on `&[Option<ModeInfo>]`) all already exist. It directly attacks idle-source C (10.1%) and removes one of the two per-frame scope barriers. It is exactly libvpx's `loop_filter_rows_mt` + `recon_done`/`num_tiles_done` model, which we can port faithfully. |
| Within-tile row-MT *decode* (libvpx `row_mt=1` parse/recon split) | Rejected for Phase 1. 400–700 LOC, touches the entropy/parse path (explicitly off-limits), and idle-source B (tile imbalance) is only **1.6%** on the headline fixture — there is almost nothing to reclaim. Revisit only if a future fixture has fewer tiles than workers. |
| Reduce serial per-frame setup | Partial, opportunistic. `setup`/`merge` are small (4.0% + 2.5%). `border` (5.3%) is the only fat target and parallelising border-extend is LF-kernel-adjacent and risky. Folded into Phase 3 (optional) below, not the headline. |

### §3.2 Topology: one scope, two job kinds

Today (both `decode_inter_frame` and `decode_intra_frame_inner`):

```
worker_pool.scope(|s| { for tile: s.submit(decode_tile) });   // JOIN — barrier
... serial merge ...
apply_loop_filter_to_frame_dispatching(...) {
    worker_pool.scope(|s| { for w in 0..nlf: s.submit(lf_worker) });   // JOIN — barrier
}
```

Proposed:

```
worker_pool.scope(|s| {
    for tile in tiles:          s.submit(decode_tile_job);   // publishes decode_progress[r] per SB row
    for w in 0..num_lf_workers: s.submit(lf_worker_job);     // consumes decode_progress[r] + cur_sb_col[r-1]
});                                                          // single JOIN — both kinds drain here
... serial merge (counts/seg/mv) ... border-extend ...
```

The decode jobs and LF jobs run in the *same* MPMC channel scope. With `num_threads = 4`, there are now `num_tiles (4) + num_lf_workers (≤4) = up to 8` jobs contending for 4 workers. The crossbeam pool naturally schedules them: a worker that finishes its decode tile picks up an LF-worker job (or vice versa). Because LF jobs *block on the wavefront gate* until decode rows are ready, the **effective** schedule is: workers decode first, and as soon as SB rows complete the LF jobs make progress on the trailing rows — pipelining decode row `r+k` against LF of row `r`.

### §3.3 The LF worker's two gates (the load-bearing change)

The LF worker (`run_split_edge_lf_worker`) currently has **one** gate — the intra-LF column wavefront `cur_sb_col[r-1] >= c + nsync` (row `r` waits for row `r-1`'s LF). In single-scope it gains a **second, outer** gate that mirrors libvpx's `sync_read_recon` (`vp9_thread_common.c:1739`):

```
// Before filtering ANY column of SB-row r, wait until every tile has
// reconstructed row r. decode_progress[r] is fetch_add'd once per tile.
spin_then_yield_wavefront(|| decode_progress[r].load(Acquire) >= num_tile_cols);
// Then the existing intra-LF column wavefront gate for r-1 as today.
```

This is the **exact** decode-progress gate that Lever-B-v2 §3.5 documented as *dead code today* ("the LF scope opens only after the tile-decode scope has joined… keep it for now — harmless and forward-compatible with a future single-scope topology"). **This HLD is that future.** The atomic is already published by tile workers (`tile.rs:477` intra / `tile.rs:1572` inter) with `Release`; we add the matching `Acquire` consumer.

`num_tile_cols` for the gate: a tile only spans its own `mi_row` range. For the common `tile_rows == 1` case (the headline fixture and ~all real streams), every tile spans all SB rows, so `decode_progress[r] == num_tile_cols` means "row r fully reconstructed". For `tile_rows > 1` see §6.3.

### §3.4 Spin-vs-park at the decode-progress gate

The intra-LF gate (`cur_sb_col`) waits sub-microsecond under a healthy wavefront → spin is correct. The **decode-progress gate is different**: an LF worker that grabs an LF job early may wait *milliseconds* for decode to reach its first row. Spinning that long burns a core that a decode tile could use.

**Resolution:** the LF jobs must not be dispatched until there is spare worker capacity, OR the spin must yield aggressively. Two sub-options, pick one at implementation (measure both):

- **(a) Yield-heavy spin (simplest):** keep `spin_then_yield_wavefront` but with the existing low `SPIN_YIELD_THRESHOLD_WAVEFRONT = 256` budget; after the budget the worker calls `std::thread::yield_now()`, which on Windows lets the scheduler run a ready decode job on that core. The risk is busy-yield churn while all 4 cores are decoding (LF jobs spin-yield uselessly until row 0 lands). Acceptable because row 0 lands fast (one SB row of one tile ≈ tens of µs) and there are at most `num_lf_workers` such jobs.
- **(b) Submit LF jobs but have them claim rows lazily via the decode-progress counter** (libvpx-faithful static row distribution: LF-worker `i` owns rows `i, i+nlf, …`; it blocks on `decode_progress[r] == num_tile_cols` before each of its rows). This is what §3.3 describes and is the recommended default — it matches libvpx exactly and the per-row block is naturally yield-gated.

**DO NOT** convert the gate to `std::thread::park`/condvar (Lever-B-v2 §10 #4): tens-of-µs OS wake latency would dwarf the per-SB savings. Keep the atomic+spin+`yield_now` primitive.

### §3.5 Why this avoids the Wave-2 row-barrier regression

The Wave-2 attempt that was **1.5× slower** used a **row barrier**: `lf_progress[r-1] == 1` had to hold before *any* column of row `r` — i.e. strictly sequential SB rows with a full-row sync each step. Every LF worker stalled ~an entire previous row's worth of work at each boundary; the sync overhead exceeded the parallelism gained. That design is dead and deleted (Lever-B-v2 C4).

This HLD uses the **already-landed column-wavefront** (`cur_sb_col[r-1] >= c + nsync`), which only requires row `r-1` to be `nsync = 4` SB columns *ahead* of row `r` — not finished. Adjacent rows execute concurrently with 256 px of horizontal slack. The Lever-B-v2 measurement already proved this pattern nets **−63% LF wall** with no regression. The single-scope change adds *one more low-sync gate of the identical shape* (`decode_progress[r] >= num_tile_cols`, checked once per row, not per column). We are reusing the proven primitive, not reinventing a barrier.

Concretely, the DO-NOT list from Lever-B-v2 §10 still binds:
- #1 no per-SB scope jobs — we submit `num_lf_workers` LF jobs, not one per SB.
- #3 was "DO NOT broaden to single-scope" *because the `Option<ModeInfo>` materialisation was unsolved at the time*. **That blocker is now gone** (Wave 5b pre-fills the grid with `Some(default_padding_modeinfo())` and `build_lfm_row` reads `&[Option<ModeInfo>]` directly — see `apply.rs:273` and the `dace0a0` "setup_mask takes &[Option<ModeInfo>] directly" commit). The §10 #3 prohibition is explicitly superseded by this HLD with team-lead sign-off.
- #4 no park/condvar, #6 no per-row mask realloc, #8 keep the `min(nworkers, tile_cols, sb_rows)` cap — all preserved.

## §4 Correctness / bit-exact ordering argument

The decoder is 201/201 conformance and must stay bit-exact. The reordering risk is: **does any pixel get loop-filtered before a reader of its pre-LF value runs, or filtered out of the V-before-H / Y→U→V order?**

### §4.1 LF reads only fully-reconstructed pixels (decode→LF dependency)

VP9 loop-filter of SB-row `r` reads reconstructed pixels of row `r` (its own V+H edges) and the bottom 8 luma rows of row `r-1` (the top-of-SB H-edge, 16-tap span confirmed at `lpf_horizontal_16_avx2.rs:728` reads `-8*pitch`). The two gates guarantee:

1. **Own row complete:** `decode_progress[r] >= num_tile_cols` ⇒ *every* tile has finished reconstructing all of SB-row `r` (all columns, all planes) before LF touches any column of row `r`. The tile worker's `fetch_add(Release)` happens-after all its `decode_partition` pixel writes; the LF worker's `load(Acquire)` happens-before its first pixel read. Release/Acquire pairing ⇒ all reconstructed pixels of row `r` are visible to the LF worker. **This is the new gate.**
2. **Cross-row hazard:** the existing `cur_sb_col[r-1] >= c + nsync` gate guarantees row `r-1`'s V+H at column `c` (and `nsync-1` beyond) is finished before row `r` filters column `c` — unchanged from the landed Lever-B-v2 design, already proven bit-exact.

### §4.2 Decode never reads loop-filtered pixels (LF→decode independence)

This is the subtle direction. Does decoding a later block read a pixel that LF has already modified?

- **Inter prediction** reads from **reference frames** (prior decoded+filtered+border-extended frames held in `self.ref_frame_map`), never the *current* frame's in-progress pixels. The current frame's LF cannot affect any inter MC read. ✔
- **Intra prediction** reads up/left **reconstructed (pre-LF)** neighbours *within the current frame*. The hazard would be: LF filters a pixel, then a later intra block reads that (now-filtered) pixel as a prediction neighbour. **This cannot happen** because: intra prediction of a block at SB-row `r` only reads neighbours at rows `≤ r` that were reconstructed *earlier in the same tile's raster scan*. LF of row `r` is gated to start only after `decode_progress[r] == num_tile_cols` — i.e. after the tile already finished row `r` entirely, which is after every intra block in row `r` already did its prediction reads. LF of row `r-1` similarly runs only after row `r-1` was fully decoded; and decode of row `r` reads at most row `r-1`'s pixels which were produced before LF of `r-1` could legally have run for them only under the wavefront — **but** decode of row `r` does not wait on LF at all, and LF of row `r-1` runs concurrently. Is there a race?

  **The race is impossible because of strict reconstruction-before-filter ordering per pixel:** a pixel at row `r-1` is read by intra-prediction of row `r` *during decode*. That same pixel is written by LF of row `r-1`. LF of row `r-1` is gated by `decode_progress[r-1] == num_tile_cols`, which fires only after the tile reconstructed row `r-1`. But decode of row `r` is *part of the same tile* and runs strictly after that tile reconstructs row `r-1` (raster order within a tile is sequential on one worker). So within a tile, all intra reads of row `r-1` by row `r` happen **before** `decode_progress[r-1]` is even bumped → before LF of `r-1` can start. The decode worker and LF worker touch row `r-1`'s pixels in a strict producer(reconstruct)→reader(intra-pred, same thread)→signal(`decode_progress`)→consumer(LF) chain. The `decode_progress[r-1].fetch_add(Release)` is the single synchronisation edge, and it is published only after the tile is *done reading* row `r-1` for predicting row `r`… 

  **Wait — verify this carefully.** Within one tile, the worker decodes row `r-1` (writing pixels), then decodes row `r` (intra-predicting from row `r-1`'s pixels), then on finishing row `r` bumps `decode_progress[r]`. The bump of `decode_progress[r-1]` happens when row `r-1` *finishes* — which is *before* row `r` is decoded. So an LF worker could start filtering row `r-1` (after `decode_progress[r-1] == num_tile_cols`) *concurrently with* the same tile decoding row `r`, which intra-predicts from row `r-1`'s **pre-LF** pixels. **This is a genuine read-vs-write race on row `r-1`'s pixels** between LF-write and intra-pred-read.

  **Resolution — this is exactly why libvpx delays LF by one full SB-row-of-rows and gates on `recon_done`:** In libvpx row-MT, LF of row `r-1` is gated on `num_tiles_done[r-1] == num_tile_cols` AND the parse/recon of row `r` having advanced — but crucially, **VP9 intra prediction reads neighbours from the *unfiltered* reconstruction buffer regardless**, because the loop filter writes *in place* into the same buffer the next row reads. libvpx avoids the hazard by ordering: **the decode-progress signal for row `r` is published only after row `r` is reconstructed, and the LF for row `r` is what reads row `r-1`; intra-pred for row `r+1` reads row `r`.** The pixel a future intra block reads is *its immediate top/left neighbour in the SAME or PREVIOUS row*, and VP9's intra prediction for an SB at row `r` reads the bottom edge of row `r-1`. LF of row `r-1`'s **horizontal pass writes** those exact bottom-edge pixels.

  **The actual libvpx guarantee (must be replicated):** libvpx's `recon_done` gate for LF row `r` requires *parse+recon of row `r`* done; and because LF is delayed and runs on a separate worker that gates on `decode_progress`, **the decode of row `r+1`'s intra prediction reads row `r`'s pixels BEFORE LF of row `r` is allowed to run** — libvpx enforces this by having recon publish row `r` complete, then LF row `r` is allowed; but recon of row `r+1` (which reads row `r`) is *also* allowed at the same time. **libvpx's resolution: intra prediction in VP9 reads from a buffer position that the in-loop filter has not yet reached, because the decode-progress signal that unblocks LF[r] is the SAME signal ordering, and recon proceeds strictly ahead of LF by the wavefront.** 

  **Conclusion / required invariant:** to be bit-exact, LF of row `r-1` must not write a pixel before *all* intra-prediction reads of that pixel (by row `r` of every tile) have completed. The safe, libvpx-faithful, and simplest-to-verify invariant is: **LF of row `r` may begin only once decode has progressed to `decode_progress[r + LF_DELAY] == num_tile_cols`**, where `LF_DELAY ≥ 1` SB-row. I.e. **delay LF by one SB-row** relative to decode (libvpx `vp9_decodeframe.c:2127` "delay the loopfilter by 1 macroblock row"). With `LF_DELAY = 1`: LF of row `r-1` starts only after decode finished row `r` — guaranteeing every intra read of row `r-1`'s pixels (which all occur during decode of rows `≤ r`) is complete. **This is the single most important correctness rule in this HLD.**

### §4.3 The bit-exact invariant, stated precisely

> **Invariant L1 (LF delay):** A loop-filter worker may apply SB-row `r` only after `decode_progress[r + 1] == num_tile_cols` (all tiles have *finished decoding the row below* — i.e. one SB-row past `r`). For the final SB-row, the gate is "all rows decoded".
>
> **Invariant L2 (cross-row wavefront):** within the LF pass, row `r` column `c` may filter only after `cur_sb_col[r-1] >= c + nsync` (unchanged from Lever-B-v2).
>
> **Invariant L3 (per-SB order):** within one SB, Y(V then H) → U(V then H) → V(V then H), unchanged (it is the same `apply_one_sb_inner`, byte-identical to serial).

L1 is the new rule and the one the differential test must hammer. It guarantees LF→decode independence (§4.2); L2+L3 guarantee decode→LF correctness and intra-LF correctness (already proven). Because every kernel call is the identical `apply_one_sb_inner` in the identical order, **the only thing that can break bit-exactness is a gate that lets LF run too early** — caught immediately by the differential test (§5).

### §4.4 Note on `LF_DELAY` vs nsync

L1 (`decode_progress[r+1]`) and L2 (`cur_sb_col[r-1] + nsync`) are *independent* gates serving *different* hazards. L1 protects against decode reading LF-modified pixels (the new cross-phase hazard). L2 protects against LF reading not-yet-filtered upstream pixels (the intra-LF hazard). Both must hold. The implementation checks L1 once per SB-row (before the column loop) and L2 per nsync-column-boundary (inside the column loop), exactly as libvpx structures `sync_read_recon` (per row) vs `sync_read` (per column).

## §5 Testability / oracle plan

### §5.1 Bit-exact differential (primary oracle, every commit)

Extend the existing `crates/rvp9-harness/tests/column_wavefront_lf_diff.rs` (or a new `decode_lf_overlap_diff.rs`) to compare per-frame MD5 of:
- `threads=1` (serial decode + serial LF — the golden reference), vs
- `threads=4` single-scope overlapped.

across multi-tile *and* single-tile vectors, key + inter + intra-only frames. **Must be byte-identical.** This is the oracle that catches an L1 off-by-one (LF starting one row too early) — exactly how Lever-B-v2 caught its `c+nsync-1` bug. Run it on **every** commit including "mechanical" ones (Lever-B-v2 §10 #7).

### §5.2 201/201 conformance (gate)

`cargo test -p rvp9-harness --test conformance` must stay **201/201**, run twice:
- default (overlap ON),
- `RVP9_DISABLE_LF_MT=1` (serial-LF fallback — the kill switch must still produce identical output).

(Note: this worktree only symlinks ~14 vectors; the implementer must run the full 201 corpus on a worktree that has it, or merge to a corpus-complete tree before the gate.)

### §5.3 Soundness instrumentation (dev-only, `cfg(debug_assertions)`)

Add a debug assertion in the LF worker: before filtering row `r`, assert `decode_progress[r + 1].load(Acquire) == num_tile_cols` (L1 holds). If it ever fires, the gate is broken. Cheap, gated out of release.

### §5.4 PGO end-to-end A/B — THE SHIP GATE

Per the team-lead: this is the gate that decides ship-or-scrap.
- Build PGO (the existing PGO pipeline), `testsrc_1080p30 t=4`, the head-to-head harness (`bench/results/decode-headtohead.md` methodology — ≥1000 timed frames, 30 warmup, pinned host if available).
- **A** = current main (two-scope). **B** = this change (single-scope overlap).
- **Ship gate:** B's frame-wall mean (and p50) must beat A by a **real margin ≥ 5%** on `testsrc_1080p30 t=4`. The §2.2 model predicts 13–16%; if measured gain is < 5%, the overlap is not pulling its weight (likely the serial floor / barrier-wakeup dominates) → **scrap or hold dormant behind an env flag, do not force it in.** Report measured A/B and stop.
- Sanity rows: also run `tile_1x4 t=4` and `testsrc_1080p60 t=4/t=8` to confirm no regression on the other multi-tile fixtures (Wave-2 regressed *those*; we must not).

### §5.5 TSan one-off (recommended pre-merge)

The new L1 Acquire/Release edge is the kind of bug TSan catches. Run once on nightly `-Zsanitizer=thread` on a tiny synthetic frame (sb_rows≈4, scalar SIMD). Not CI-blocking (Rust TSan is nightly-only), but a cheap insurance pass on the one new sync edge.

## §6 Risk assessment

| # | risk | severity | mitigation |
|---|------|----------|------------|
| 1 | **L1 off-by-one** — LF starts one SB-row too early, intra-pred of the next row reads a filtered pixel → bit-stream diverges. | **High** | The differential test (§5.1) catches it on frame 0 of any multi-tile vector, exactly as Lever-B-v2's `c+nsync-1` bug was caught. Debug assertion §5.3 as belt-and-braces. Default `LF_DELAY=1`; if any vector diverges, the libvpx-conservative fallback is to keep two-scope for that frame (filter_level-gated). |
| 2 | **No real win** — serial floor (A, ~8% irreducible) + barrier-wakeup dominate, overlap reclaims < 5%. | **Medium** | §5.4 ship gate. The §2.2 model says 13–16%, but models are optimistic; if the PGO A/B shows < 5%, hold dormant behind an env flag (`RVP9_LF_OVERLAP=1`) and report — same posture as Wave-2's dormant landing. No revert needed. |
| 3 | **Worker oversubscription** — 8 jobs (4 decode + 4 LF) on 4 workers; LF jobs spin-yield while all cores decode, churning CPU and *slowing* decode. | **Medium** | §3.4: use libvpx-faithful static row distribution (option b) so each LF worker blocks per-row on `decode_progress` with `yield_now` after a short spin. Cap `num_lf_workers` at `min(nthreads, tile_cols, sb_rows)` (unchanged). Measure CPU-busy in the A/B; if yield churn shows, gate LF-job submission until the first decode row lands. |
| 4 | **`merge`/`border` still serial after the joined scope** — overlap doesn't touch the 12.6% serial-A idle directly. | Low (expected) | Out of scope for Phase 1; §7 Phase 3 optionally overlaps border-extend. Honest expectation: Phase 1 reclaims C + the barrier, not A. |
| 5 | **tile_rows > 1** — `decode_progress[r] == num_tile_cols` is wrong when a tile spans only some rows. | Low (rare) | The headline fixture and ~all real streams are `tile_rows=1`.
