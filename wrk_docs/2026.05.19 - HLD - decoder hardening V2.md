# Stage 3.5 — Decoder hardening

## 1. Context

The Stage 3 conformance gate cleared on 2026-05-19 (`c43b438`, hard
assertion `total_mismatched == 0`). The decoder is **bit-exact with libvpx
on every frame it attempts** out of the 14-vector AOM conformance set
(201 frames). 10 frames are still skipped due to two
`Unimplemented` arms.

The current scoreboard:

```
191 passed  /  0 mismatched  /  10 skipped  /  201 total
```

The gate doesn't cover everything a production decoder needs. This HLD
plans the closure of 12 gaps (G1 … G12). Execution interleaves with
the Stage 4 encoder drive (`notes/stage4-drive.md`).

**Implicit-oracle limit (acknowledged):** every gap in this plan except
G2 (lossless), G8 (real-world corpus diversity), and G9 (fuzz) uses
*libvpx* as the spec oracle. If libvpx is wrong, we are wrong. Known
divergence anchors live in `notes/divergence-ledger.md`. G2's
`decoded == source` test is the one spec-anchored property check we add;
other items inherit the libvpx-faithful posture by design.

## 2. Scope

**In:** twelve numbered gaps (G1 … G12 below), at full design depth.
Cheap closeouts get a paragraph each; large items (G4 SIMD, G5
threading) get a multi-section design with rollout staging.

**Out:**
- Encoder work (Stage 4a in flight per `notes/stage4-drive.md`).
- Profile 2 / Profile 3 (high-bit-depth) — deferred to Stage 6+ per
  PLAN.md §Features.
- Frame-parallel decoding mode (libvpx `frame_parallel_decoding_mode=1`
  with `threads >= 2`) — not in PLAN.md gate list.
- External-frame-buffer interface (libvpx `vpx_codec_set_frame_buffer_functions`).

**Quality philosophy (from CLAUDE.md):**
- Each item identifies its **testing oracle**: what encodes "correct"
  for that gap in a machine-checkable form.
- No env vars and no feature flags. Where rollout staging is needed,
  use separate crates (`rvp9-fuzz`), separate test binaries, or
  function-pointer dispatch already in place (`SimdDispatch`).
- Development sandbox: no migration or rollback support required;
  no obligation to preserve old code paths.

## 3. Sharing analysis & worktree strategy

The encoder and decoder share `rvp9-core` but the overlap is narrower
than it looks. Decoder hardening can run in a worktree
(`decoder-hardening` branch) with low merge-conflict risk.

| Crate / module                       | Encoder uses | Decoder uses | Shared write? |
|--------------------------------------|--------------|--------------|----------------|
| `rvp9-decoder/`                      | no           | yes          | no             |
| `rvp9-encoder/`                      | yes          | no           | no             |
| `rvp9-core::bitstream::*`            | write_*      | parse_*      | **types only** |
| `rvp9-core::bitstream::modes_writer` | yes          | round-trip   | no             |
| `rvp9-core::entropy::BoolReader`     | no           | yes          | no             |
| `rvp9-core::entropy::prob_diff_writer` | yes        | no           | no             |
| `rvp9-core::transforms::inverse`     | no           | yes          | **G2 touches** |
| `rvp9-core::transforms::forward`     | future       | no           | none today     |
| `rvp9-core::intra_pred`              | future (mode-decision) | yes | low      |
| `rvp9-core::dsp` (SimdDispatch)      | will         | yes          | **G4 SHAPE COORD** |
| `rvp9-core::tile_threading` (new)    | future       | yes (G5)     | **G5 PLANS BOTH** |
| `rvp9-core::loopfilter`              | future       | yes          | low            |
| `rvp9-core::quant`                   | will         | yes          | read-only LUTs |
| `rvp9-core::frame`                   | will         | yes          | low (G7 widens `Yv12Buffer`) |

**Coordination points (explicit, must be honoured during execution):**

1. **`SimdDispatch` struct shape (G4).** Adding per-kernel `fn`-pointer
   fields is a non-additive change. The encoder will eventually populate
   the same dispatch table for forward transforms / SAD / variance. If
   the encoder lands a `SimdDispatch` field for forward DCT before G4.1
   ships, we coordinate by both sides agreeing the field layout via the
   HLD. **Action:** when G4.1 dispatches, post a note to the Stage 4
   drive ledger (`notes/stage4-drive.md`) naming the in-flight kernel
   family and the field-naming convention (`{kernel}_{variant}`).
2. **`tile_threading` module name and pool API (G5).** This module is
   shared infrastructure for encoder tile-MT (Stage 4a §7) and decoder
   tile-MT (G5). The encoder LLD (`notes/lld/tile-threading.md`)
   currently puts the pool in `rvp9_encoder::threading`. G5 moves it to
   `rvp9-core::tile_threading` because both crates need it. **Action:**
   when G5 lands, update `notes/lld/tile-threading.md` §1.2 to match
   the new module path; this is part of G5's exit criteria.

**Conclusion:** Wave A (cheap closeouts: G1, G2, G3, G10, G12; G11 added
as ongoing) touches only `rvp9-decoder` + `rvp9-core::transforms::inverse`
(G2) + `rvp9-core::frame` (G3 if `Yv12Buffer::alloc` panic-safety surfaces
there) — zero conflict with Stage 4 encoder work.

Wave B (G6, G7, G8, G9) is clean — touches separate test crates or adds
code paths the encoder doesn't read. G7's `Yv12Buffer` widening (chroma
subsampling) is additive and the encoder doesn't use `Yv12Buffer` today.

Wave C (G4, G5) touches `rvp9-core::dsp` and the new
`rvp9-core::tile_threading`. The coordination points above are the
contract between the two worktrees.

1. **G4.1 first** — pilot SIMD on one representative kernel family

**Wave C realistic-effort flag:** G4 + G5 together is ~6-12 months

long, the natural cut is **arch scope** (e.g., x86_64 AVX2 only,
NEON deferred to a later stage). The doc proposes x86_64 first; aarch64
NEON is a continuation, not a blocker.

## 5. Items

### G1. IntraOnly frame decode path

**Symptom:** `crates/rvp9-decoder/src/lib.rs:697` returns
`DecodeError::Unimplemented { reason: "intra-only frame decode …" }`
for any `FrameKind::IntraOnly` packet.

**libvpx anchor:** `vp9/decoder/vp9_decodeframe.c::decode_frame` —
the IntraOnly branch is structurally identical to the KeyFrame branch
except for three things:

1. **No FrameContext reset.** Keyframes overwrite all four
   `frame_contexts[]` banks with defaults; IntraOnly preserves them.
2. **Refresh-frame-flags follow `refresh_frame_flags` byte** rather
   than implicit "refresh all slots."
3. **Segmentation map** inherits from the previous frame's state
   (already preserved by our `Decoder` between frames; no extra
   work).

**Design:**

Refactor the existing `decode_keyframe` (currently ~580 lines at
`lib.rs:721`) by extracting the shared intra driver:

```rust
/// Shared intra-frame decode driver. Used by both KeyFrame and
/// IntraOnly paths. The two callers differ only in their entry-and-exit
/// gymnastics around FrameContext state.
fn decode_intra_frame_inner(
    &mut self,
    frame: &ParsedFrame<'_>,
    refresh_mask: u8,                 // 0xFF for keyframe; tail.refresh_frame_flags for IntraOnly
) -> Result<FrameBuf, DecodeError> {
    // body: compressed header parse, tile walk, partition walk,
    //       mode decode, recon, LF apply, ref-slot refresh
}

fn decode_keyframe(&mut self, frame: &ParsedFrame<'_>) -> Result<FrameBuf, DecodeError> {
    self.reset_frame_contexts();
    self.decode_intra_frame_inner(frame, 0xFF)
}

fn decode_intra_only_frame(&mut self, frame: &ParsedFrame<'_>) -> Result<FrameBuf, DecodeError> {
    let refresh = frame.header.tail.as_ref()
        .ok_or(DecodeError::WrongFrameKind)?
        .refresh_frame_flags;
    self.decode_intra_frame_inner(frame, refresh)
}
```

Wire the dispatcher at `lib.rs:697`:
```rust
FrameKind::IntraOnly { .. } => self.decode_intra_only_frame(frame),
```

**Testing oracle (TWO vectors required):**

1. **All-slots refresh:** synthetic IntraOnly with `refresh_frame_flags = 0xFF`.
   Verifies the basic decode path.
2. **Selective refresh + read-back:** synthetic IntraOnly with
   `refresh_frame_flags = 0x05` (slots 0 and 2), followed by inter
   frames that read from BOTH refreshed (slot 0 or 2) AND preserved
   (slot 1, 3, …) slots. Verifies the refresh-mask is honoured and
   non-refreshed slots are not clobbered. **This case is what fails
   silently if (b) is broken.**

Both generated via libvpx: `vpxenc --intra-only --refresh-mask=…` or
equivalent; capture, MD5-pin, commit to `decoder-hardening/fixtures/`.

**Effort:** 1-2 days. Refactor + two fixtures + tests.

**Exit:** both synthetic vectors decode bit-exact; conformance ratchet
unchanged (no IntraOnly in current 201 vectors).

### G2. Lossless decode path (WHT inverse transform)

**Symptom:** Two sites return `DecodeError::Unimplemented`:
- `lib.rs:734` (keyframe path) — `"lossless decode (WHT inverse transform path) not yet wired"`
- `lib.rs:1113` (inter path) — `"lossless inter frame decode (WHT inverse transform path)"`

Both trip when `quantization.is_lossless()` (`sub_parsers.rs:189`).

**libvpx anchor:** `vp9/common/vp9_idct.c::iwht4x4_1_add` /
`iwht4x4_16_add`. Lossless mode uses a Walsh-Hadamard inverse instead
of the standard idct4×4. Only `TX_4X4` is permitted in lossless.

**Design:**

Add `iwht4x4_16_add` and `iwht4x4_1_add` to
`crates/rvp9-core/src/transforms/inverse.rs`, mirroring the libvpx
implementation byte-for-byte (~30 lines of integer arithmetic).

**Dispatch:** add a parallel `iwht_add` entry point alongside the
existing `iht_add`. **Not a `TxType::WHT` enum widening** —
`TxType` is used as a table index (0..4) across `scans.rs`, dequant
scan-order LUTs, etc.; widening would cascade into LUT shape changes
that don't reflect any spec-level coupling (lossless mode bypasses
the type field entirely). Keep `TxType` at 4 variants.

In `reconstruct_intra_block` and `reconstruct_inter_block`, detect
lossless via `quantization.is_lossless()` (already threaded into the
decoder via tail) and route to `iwht_add` instead of `iht_add`.

Remove the two `Unimplemented` short-circuits.

**Testing oracle:** spec-anchored, not libvpx-anchored. Generate a
lossless vector from a known raw Y4M source via:

```
vpxenc \
    --lossless \
    --kf-min-dist=0 --kf-max-dist=0 \
    --end-usage=q --cq-level=0 \
    --aq-mode=0 \
    --auto-alt-ref=0 \
    -o lossless.ivf source.y4m
```

The pinned flags eliminate altref placement, AQ, frame reordering —
i.e., everything that could make `decode(encode(src)) ≠ src` at the
sample level for a lossless encode. Assert:

```rust
assert_eq!(decoded_yuv_planes, source_y4m_planes);  // exact byte equality
```

This oracle does **not depend on libvpx being right** — it's a
property test for the lossless invariant. (Side check: MD5 against
libvpx output for regression-trace tightness; if libvpx ships a
lossless bug the spec-anchored test still passes and we get a flag.)

**Effort:** 1-2 days. ~30 lines of WHT kernel + dispatch wiring +
tests + fixture generation.

**Exit:** synthetic lossless vector decodes bit-exact AND
pixel-identical to source.

### G3. Error variant cleanup — `MissingReferenceFrame`

**Symptom:** `lib.rs:1133` returns
`DecodeError::Unimplemented { reason: "inter frame referenced empty ref_frame_map slot" }`
when an inter frame names a `ref_frame_idx` whose slot is `None`.
The error variant is misleading (the condition is malformed-bitstream,
not unimplemented-feature).

**Existing variant in play:** `DecodeError::EmptySlot { slot: u8 }`
already exists at `lib.rs:1997` and is returned by
`decode_show_existing_frame` for the same conceptual error
(referenced slot is empty).

**Design:** reuse `EmptySlot` rather than adding a parallel
`MissingReferenceFrame` variant. The condition is identical from the
consumer's perspective ("a slot you asked for is empty"); two
variants is API smell. Replace the `Unimplemented` return at
`lib.rs:1133`:

```rust
return Err(DecodeError::EmptySlot { slot: slot_idx as u8 });
```

If discriminating the call site matters downstream, add a `context`
field once:

```rust
pub enum DecodeError {
    EmptySlot { slot: u8, context: EmptySlotContext },
    // ...
}

#[non_exhaustive]
pub enum EmptySlotContext {
    ShowExistingFrame,
    InterReference,
}
```

Decision: ship the discriminator field; two call sites with different
diagnostic context justifies it. Update the existing
`decode_show_existing_frame` site to pass `ShowExistingFrame`.

**Testing oracle:** unit test constructs a Decoder, calls
`decode_frame` on a synthesised inter packet with `ref_frame_idx = 3`
(no preceding keyframe), asserts `EmptySlot { context: InterReference, .. }`.

**Effort:** 2-3 hours.

**Exit:** existing `EmptySlot` consumers updated, no behavioural
change, error name now matches the semantics.

### G4. SIMD kernel rollout

**Symptom:** `crates/rvp9-core/src/dsp/dispatch.rs:50-55` —
`SimdDispatch` has *only* a `caps` field and zero per-kernel function
pointers. **The decoder is pure scalar Rust on every architecture.**

**Realistic effort flag:** this is the biggest item in the HLD by an
order of magnitude. libvpx's SIMD library took multiple engineer-years
to build to its current quality. A bit-exact-matching scalar-Rust
port plus per-arch SIMD impls plus differential testing is a
multi-month effort:

- **x86_64 only (AVX2 baseline) + scalar reference:** ~4-6 months.
- **x86_64 (SSE2, SSSE3+SSE4.1, AVX2) + aarch64 NEON:** ~6-12 months.

The HLD initially estimated 6-10 weeks. That was wrong. The right
framing: G4.1 (one kernel family, x86_64 AVX2) is ~2 weeks; the rest
follows that pattern. **If timeline pressure exists, the natural cut
is arch scope** — ship x86_64 AVX2 first, defer SSE2/SSSE3 and NEON.
Most modern WebRTC/livestream hardware has AVX2.

**libvpx anchor:** `vpx_dsp/x86/*`, `vpx_dsp/arm/*`,
`vp9/common/x86/*`. Seven kernel families per HLD-simd (already
enumerated in `dsp/dispatch.rs:34-44`):

| # | Family                  | Decoder kernels |
|---|-------------------------|-----------------|
| 1 | `frame-buffers`         | scale, border extend |
| 2 | `entropy` (decoder side) | none — BoolReader is scalar by design |
| 3 | `transforms` (inverse half) | idct4/8/16/32, iadst4/8/16, iht*, iwht4 |
| 4 | `quant` (dequant side)  | dequantise |
| 5 | `intra-pred`            | 10 modes × 4 sizes |
| 6 | `loopfilter`            | 6 kernels × {vert, horiz} × {single, dual} |
| 7 | (encoder-only)          | n/a |

**Design — `SimdDispatch` shape:**

```rust
// drop the existing `Copy` impl — too easy to accidentally copy
// a multi-KB function-pointer table.
#[derive(Debug, Clone)]
#[non_exhaustive]
pub struct SimdDispatch {
    pub caps: Caps,
    // per-kernel slots, grown as G4.x stages roll out:
    pub idct8x8_add: fn(input: &[i32; 64], dst: &mut [u8], stride: usize),
    // ...
}
```

Plain `fn` (not `unsafe fn`, not trait objects, not generics) is the
right choice:
- Runtime caps selection is the whole point — generics monomorphise
  away the choice we need.
- The safety contract is "valid slice layout" which Rust slices
  enforce; making the pointer `unsafe fn` forces every call site
  into `unsafe {}` for no gain.
- **Alternative considered:** `#[target_feature]` multi-versioning
  via the `multiversion` or `cpufeatures` crate. This branches to
  inlined per-arch code at the dispatch site, avoiding the indirect
  call entirely. **Rejected** because the per-call indirect cost
  (~1-3 cycles when BTB-predicted) is negligible vs. the cost of
  losing the centralised dispatch table for instrumentation,
  testing, and future-kernel rollout.

**Architecture tier strategy:**

| Tier | Arches | Why |
|------|--------|-----|
| **Tier 1** | x86_64 AVX2 (with SSE2/SSSE3/SSE4.1 baseline) | Modern WebRTC/livestream production hardware; libvpx's mainline. **Pilot scope for G4.1; default scope for G4.2-G4.4.** |
| **Tier 2** | aarch64 NEON | M-series Mac, ARM servers, mobile. Continuation after Tier 1 complete. |
| (no tier) | SSE2-only (pre-2011 x86_64) | Library targets `target_feature = "+sse2"` floor (Rust default for x86_64) but won't ship hand-optimised SSE2 unless an SSSE3 kernel needs it (libvpx mainline does for three idct variants). |

**Note on tier 1:** SSE4.1 is **not a fallback** for an AVX2-minus
cohort — several libvpx SSSE3 kernels (`vpx_idct32x32_135_add_ssse3`,
others) use SSE4.1 instructions (PMULLD, PMOVZX). Treat SSE4.1 as
part of the SSSE3-promoted tier, not below it.

**Design — staged rollout:**

- **G4.1 — Pilot.** `idct8×8`, x86_64 AVX2 only. Add the function-
  pointer slot, the AVX2 impl, the dispatch wiring, and the
  scalar-differential test infrastructure (see oracle below). Proves
  the pattern end-to-end and locks the per-kernel fn-pointer
  signature shape. **~2 weeks.**
- **G4.2 — Inverse transforms.** Roll the pattern to every inverse
  transform (idct4/8/16/32, iadst4/8/16, iht4/8/16, iwht4) across
  the x86_64 tier. **~6-10 weeks.**
- **G4.3 — Intra-pred + loop-filter.** Per-arch impls for 10 intra
  modes × 4 sizes (G4.3a) and the 12 LF edge kernels (G4.3b).
  **~6-10 weeks.**
- **G4.4 — Frame-buffers + dequant.** Smaller families; closes
  family list. **~2-4 weeks.**

Total tier-1 (x86_64): **~4-6 months**. Tier-2 (aarch64 NEON) is a
straight continuation pattern on the same dispatch slots; ~3-6
additional months if pursued.

**Testing oracle (revised — proptest, not bare random):**

Per-kernel scalar-differential, but with **stratified property-based
generation**:

```rust
proptest! {
    #[test]
    fn idct8x8_scalar_eq_avx2(input in input_strategy()) {
        let scalar = compute_scalar(&input);
        let avx2 = compute_avx2(&input);
        prop_assert_eq!(scalar.dst, avx2.dst);
    }
}

fn input_strategy() -> impl Strategy<Value = Idct8x8Input> {
    // 30% uniform random over the i32 coefficient range
    // 30% sparse (1-4 nonzero coefficients) - exercises DC-only fast path
    // 20% high-magnitude (near +/- i16::MAX) - exercises saturation
    // 20% pathological (all-equal, all-min, all-max, alternating sign)
    prop_oneof![
        30 => uniform_strategy(),
        30 => sparse_strategy(),
        20 => high_magnitude_strategy(),
        20 => pathological_strategy(),
    ]
}
```

Plus directed corner-case fixtures:
- All-zero input (DC-only fast path).
- Single-coefficient impulse at every position 0..63 for idct8×8.
- `dst` aligned at offsets 0, 1, 3, 7, 15 — exercises unaligned-load
  paths and catches kernels that wrongly assume aligned `dst`.

Plus end-to-end:
- Full conformance harness MUST pass with SIMD-selected dispatch.
  If `total_mismatched > 0` after a G4.x lands, the per-kernel
  differential missed a bug — investigate as a property-test gap.

**Effort:** see staged rollout above. G4.1 is the only commitment to
make now; G4.2-G4.4 are dispatchable once G4.1 proves the pattern.

**Exit:** all six decoder kernel families have at least one non-scalar
impl on Tier 1 (x86_64 AVX2); conformance gate green; throughput
benchmark (G6) shows ≥3× speedup vs scalar.

### G5. Tile-threaded decode

**Symptom:** `f8fe0b9` ("Stage 3 Task E.2: single-threaded multi-tile
decode") wired multi-tile *decode correctness* but iterates tiles
sequentially. No throughput gain from parallel tile decode.

**libvpx anchor:** `vp9/decoder/vp9_decodeframe.c::decode_tiles_mt`
+ the worker pool in `vp9/decoder/vp9_thread.h`.

**Module home — name and decision:**

New module `crates/rvp9-core/src/tile_threading/`. The existing
`notes/lld/tile-threading.md:40` LLD currently places the worker pool
in `rvp9_encoder::threading`. G5 moves it to `rvp9-core::tile_threading`
because **both** crates need it (decoder G5 here; encoder Stage 4a §7
later). Updating the LLD is part of G5's exit criteria.

The previously-proposed `rowsync.rs` submodule (encoder row-MT helper)
is **removed from G5 scope** — that's an encoder-only piece, not
needed until Stage 4a §7 actually consumes it. Adding it now would be
an "on-ramp to nowhere" per CLAUDE.md.

```
crates/rvp9-core/src/tile_threading/
  mod.rs              — public API: WorkerPool, JobHandle
  pool.rs             — long-lived worker pool
  job.rs              — per-frame job tracking + barriers
```

**Pool choice (rayon vs crossbeam vs std):**

Use `std::thread + crossbeam-channel` (not rayon, not tokio). Reasoning:

- **Rayon** is ergonomic for scoped fan-out, but `rayon::scope` spawns
  workers per-scope (cheap on Linux; **expensive on Windows** where
  thread creation is ~100us). At 1080p60 with multi-tile, per-frame
  spawn cost dominates. We need **long-lived workers**.
- **Tokio** is for IO-bound concurrency; this is CPU-bound. Wrong tool.
- **Crossbeam-channel** + `std::thread` gives long-lived workers
  receiving work from a per-frame submission queue, with a join
  barrier per frame. Matches libvpx's pthread model.

API shape:

```rust
pub struct WorkerPool {
    workers: Vec<JoinHandle<()>>,
    job_tx: crossbeam_channel::Sender<TileJob>,
    done_rx: crossbeam_channel::Receiver<TileDone>,
    simd_dispatch: &'static SimdDispatch,  // R-09: passed to every worker
}

impl WorkerPool {
    pub fn new(simd_dispatch: &'static SimdDispatch, num_threads: usize) -> Self { ... }
    pub fn submit_frame<'frame>(&self, tiles: Vec<TileJob<'frame>>) -> FrameJoinHandle<'frame> { ... }
}
```

`SimdDispatch` is `&'static` so workers can hold the reference without
lifetime concerns. R-09 (HLD-simd) enforced by construction.

**Disjoint-write safety (the unsafe surface):**

G5 introduces the **first real `unsafe` blocks** in `rvp9-core` (today
there's effectively zero — only doc-comments). The pattern is shared
write access to `Yv12Buffer` plane regions from multiple worker
threads, where each tile's region is disjoint.

**First-pass design: try safe APIs before reaching for `unsafe`.**
Per-plane row slicing via `std::slice::split_at_mut` chained per
tile-row boundary may avoid `unsafe` entirely. Borrow-checker may
or may not be able to express the disjoint-rect partition — try the
safe approach first; fall back to `unsafe` only if it doesn't
type-check.

If `unsafe` is required, the SAFETY chain is non-trivial. Five
links must hold:

```rust
// SAFETY:
// (a) `tile_mi_rect` was parsed from a structurally-valid header
//     (header parser rejects malformed / out-of-bounds rects;
//     see crates/rvp9-core/src/bitstream/header.rs:NNN).
// (b) The header parser also rejects overlapping tile rects per
//     VP9 spec §6.4.X.
// (c) `tile_rect_to_plane_rect()` is monotonic and disjoint-preserving:
//     overlapping output ranges imply overlapping input ranges,
//     contradicting (b).
// (d) `Yv12Buffer` stride matches `plane_rect`'s assumed pitch
//     (asserted at allocation time; see frame.rs:NNN).
// (e) No other code path reads from the destination Yv12Buffer during
//     this frame's tile decode (reference-frame slot is held read-only
//     in ref_frame_map; current-frame slot is exclusive-write until
//     all tile jobs complete via the join barrier).
unsafe { ... }
```

Each link references its enforcement site. Add as a dedicated
`SAFETY-G5.md` doc under `notes/decoder-hardening/` rather than inline
in code (the chain is too long for an inline comment).

Soundness review by Arthur before G5 ships.

**Per-tile FrameCounts and the DV-TT-05 divergence:**

**This is the most subtle correctness point in the doc.** Current
ledger entry `notes/divergence-ledger.md` DV-TT-05 (mirrored in
`crates/rvp9-core/src/entropy/adapt.rs:1-37`) documents that libvpx
multi-tile decode has a **counts double-count bias**: per-worker
counts are initialised by `memcpy` from a baseline that causes
`(N_tiles - 1) × baseline` over-counting after merge. rvp9 mirrors
this bias intentionally for byte-parity with libvpx — meaning today's
single-tile path and the future multi-thread N-tile path can produce
*different probability adaptation* even on the same input.

**This invalidates a naive "merge per-tile counts via `+=` then run
adapt" design.** Either G5 must mirror libvpx's bias (each worker's
counts start from a per-worker baseline `memcpy`, leading to the
documented (N-1)×baseline accumulation), **or** rvp9 abandons libvpx
byte-parity for multi-tile inter-frame counts (drops DV-TT-05) and
the conformance test must split into single-tile and multi-tile
buckets.

**Recommendation: mirror libvpx's bias.** Conformance is the gate;
breaking it for "cleaner code" is the wrong trade. The mechanical
work is: per-worker FrameCounts initialised by `memcpy` from the
post-compressed-header baseline (today done once per frame), then
`+=` merged at the join barrier. The current single-tile path becomes
the N=1 case of the same code; no code-path bifurcation.

**Testing oracle (revised — TSan + determinism + scale):**

1. **Conformance at N ∈ {1, 2, 4, 8}.** All four must pass
   `total_mismatched == 0`. (Existing harness, parameterised.)
2. **Inter-thread-count determinism.** For each multi-tile vector,
   `decode(input, threads=1) == decode(input, threads=8)` byte-for-byte.
3. **Per-field merge equality.** Add a debug-only oracle:
   `merged_FrameCounts(threads=1) == merged_FrameCounts(threads=8)`
   field-by-field. Catches merge-order bugs that the byte-equal
   output check might mask.
4. **ThreadSanitizer.** Run the conformance harness under
   `cargo +nightly -Zsanitizer=thread test --test conformance` for
   at least one vector per tile-count (4 runs). Required in nightly CI.
5. **Repeat-runs for flakes.** Loop the 4-way matrix 100× in nightly
   CI to catch non-deterministic threading bugs.

(Miri does not support `std::thread` in any useful way for this
target. Don't include Miri in the G5 gate.)

**Effort:** revised **4-5 weeks** (was 3-4). Adds: TSan-clean
implementation (TSan often surfaces real bugs that pass logically),
determinism oracle, repeat-run nightly infra, LLD update.

**Exit:** all five oracles pass; LLD updated; soundness review
complete; G6 throughput benchmark shows scaling up to tile count.

### G7. Profile 1 support (8-bit non-4:2:0 chroma)

**Symptom:** `crates/rvp9-core/src/frame.rs::Yv12Buffer` assumes 4:2:0
chroma. Profile 1 streams decode-reject at the colour-config parse
step.

**Existing type to reuse:** `crates/rvp9-core/src/bitstream/frame.rs:180`
defines `pub enum ChromaFormat { Yuv420, Yuv422, Yuv440, Yuv444 }` with
`subsampling_x()` / `subsampling_y()` accessors. `Yv12Buffer` already
imports `ChromaFormat`. Use this enum — do not introduce a parallel
`(u8, u8)` field pair.

**Design:**

Widen `Yv12Buffer` to store a `ChromaFormat` field:
- 4:2:0 — `Yuv420` (current; chroma planes half-width AND half-height).
- 4:2:2 — `Yuv422` (chroma half-width, full-height).
- 4:4:0 — `Yuv440` (chroma full-width, half-height).
- 4:4:4 — `Yuv444` (chroma full size).

Plumb the `ChromaFormat` through `FrameBuf` construction, through the
tile/recon/LF chain, into every plane-stride / plane-extent
calculation. Replace hardcoded `>> 1` chroma shifts with
`>> chroma_format.subsampling_x()` / `>> chroma_format.subsampling_y()`.

**Touch list:**
- `frame.rs` — `Yv12Buffer::new` accepts `ChromaFormat`;
  `chroma_width()` and `chroma_height()` compute from it.
- `decoder/tile.rs` — chroma block iteration uses
  `n4_w >> ss_x` etc.
- `decoder/reconstruct.rs` / `reconstruct_inter.rs` — same.
- `core/loopfilter/apply.rs` — chroma mask cells span depends on ss.
- `core/intra_pred.rs` — DC predictor's left/above neighbour pixels.
- **`crates/rvp9-harness/src/lib.rs::md5_of_yv12_visible`** —
  currently 4:2:0-locked, must accept `ChromaFormat`. Without this
  update the harness will MD5 phantom bytes for non-420 streams.

**Testing oracle:**

Generate Profile 1 vectors via libvpx. Three sub-modes minimum:

```bash
vpxenc --profile=1 --i422 -o profile1_422.ivf source_422.y4m
vpxenc --profile=1 --i440 -o profile1_440.ivf source_440.y4m   # if supported
vpxenc --profile=1 --i444 -o profile1_444.ivf source_444.y4m
```

Reference output:
```bash
# NOT --i420 (would downconvert and destroy the chroma signal)
vpxdec --rawvideo profile1_422.ivf -o profile1_422_ref.yuv
```

MD5-pin each frame against the `--rawvideo` reference.

**Effort:** 1 week. Mechanical but pervasive — touches several core
modules + the harness.

**Exit:** decoder accepts Profile 1 vectors at all three sub-modes;
new vectors pass bit-exact via `--rawvideo` reference; Profile 0
conformance unchanged.

### G9. Fuzzing harness

**Symptom:** No fuzzing. Decoders are common security targets;
malformed or truncated bitstreams must produce errors, not panics
or undefined behaviour.

**Design — separate crate (no feature flag):**

`crates/rvp9-fuzz/`. Uses `cargo-fuzz` (libFuzzer). The separate-crate
arrangement is required by `cargo-fuzz`'s `#![no_main]` design and
avoids `--features fuzz` on the main crate (per CLAUDE.md "no feature
flags").

**Three fuzz targets (structured input, NOT naive byte mutation):**

Naive byte-mutation libFuzzer on a VP9 IVF stream wastes 99.9% of
its compute budget producing invalid uncompressed-header garbage
that fails in the first 50 bytes of `parse_packet`. Structure is
mandatory.

```rust
// crates/rvp9-fuzz/fuzz_targets/fuzz_parse_packet.rs
use libfuzzer_sys::fuzz_target;
use arbitrary::Arbitrary;

#[derive(Arbitrary, Debug)]
struct PlausibleVp9Packet {
    profile: u8,            // 0..=3, constrained
    show_frame: bool,
    show_existing_frame: bool,
    frame_kind: PlausibleFrameKind,
    width: u16,
    height: u16,
    body: Vec<u8>,          // free-form, mutated by libFuzzer
}

fuzz_target!(|input: PlausibleVp9Packet| {
    let bytes = input.encode_to_ivf();
    let mut decoder = Decoder::new(Default::default());
    let _ = decoder.parse_packet(&bytes);
    // Pass = didn't panic. Result value is irrelevant.
});
```

Plus a **libFuzzer dictionary** (`fuzz/fuzz.dict`) with:
- IVF magic bytes (`DKIF`).
- VP9 uncompressed-header marker bits.
- Common syntax-element bit patterns.

Plus a **seed corpus**: the 14 AOM conformance vectors + the G8
in-repo subset.

**Three targets:**

| Target | Input shape | Catches |
|--------|-------------|---------|
| `fuzz_parse_packet` | `PlausibleVp9Packet` | parser panics / UB |
| `fuzz_decode_frame` | `PlausibleVp9Packet` → `parse_packet` → `decode_frame` | recon path crashes |
| `fuzz_full_stream` | `Vec<PlausibleVp9Packet>` | stateful (ref-map, segmentation, FC drift) bugs |

**Sanitizer matrix:** ASan is implicit with cargo-fuzz. **Also run
UBSan** (`RUSTFLAGS=-Zsanitizer=undefined cargo fuzz run …`); UBSan
catches integer-overflow bugs that media decoders accumulate. MSan
is harder to get clean with `std::` use; defer.

**Why libFuzzer (not AFL++ or honggfuzz):**
- cargo-fuzz is the idiomatic Rust route; AFL++ Rust support is
  workable but additional setup.
- libFuzzer's in-process model handles stateful `fuzz_full_stream`
  fine; coverage-guided mutation across packet boundaries works.
- If post-bake we find libFuzzer plateaus on a target, adding
  honggfuzz or AFL++ for that one target is straightforward (the
  `fuzz_target!` body is reusable).

**CI:** 5-minute fuzz pass per target on PR. 24-hour bake nightly.

**Effort:** 1 week. Crate setup + three targets with `arbitrary`
inputs + dictionary + seed corpus + first 24-hour bake.

**Exit:** harness in place; three targets running; first 24-hour
bake produces zero crashes OR a list of crash inputs reduced to
minimal repros and filed as bugs.

### G12. Public API hygiene

**Symptom (newly added in V2):** "Production-ready library" per
PLAN.md §2 is not just bit-exactness. The decoder's public API surface
has several unaddressed concerns:

- `Decoder` is not annotated `Send` or `Sync`; downstream users must
  guess.
- ~74 `eprintln!` sites in `decoder/src/lib.rs` fire on production
  runs (addressed by G11 lint).
- No documented panic-safety contract: if `decode_frame` errors mid-
  way through a tile decode, can the next `decode_frame` call succeed,
  or is the `Decoder` poisoned?
- `Yv12Buffer::alloc` can OOM via `Vec::with_capacity`; behaviour is
  undocumented (currently `Vec` panics on alloc failure).
- No `Drop` ordering / cleanup guarantees specified.

**Design:**

1. **`Send` + `Sync` audit + annotation.** Walk the `Decoder` field
   set:
   - `FramePool` — already `Arc<Yv12Buffer>` per slot; `Sync` follows
     once `Yv12Buffer` is.
   - Owned `Vec`s, `Box`s — `Send + Sync` by default.
   - Interior mutability sites (`UnsafeCell`, `RefCell`) — none today
     in `Decoder`; reaffirm.
   - **Conclusion (expected):** `Decoder: Send + !Sync` (mutable
     decode state precludes Sync). Annotate explicitly via marker
     impl OR via auto-derive plus a `static_assertions::assert_impl_all!`.
2. **Panic-safety contract.** Document in `Decoder` doc-comment:
   "after `decode_frame` returns `Err(_)`, the `Decoder` is in a
   well-defined state; subsequent calls may succeed for unrelated
   inputs. The poisoning contract is: ref_frame_map and FrameContext
   banks are NOT reverted on error; consumers expecting transactional
   semantics must clone the decoder before risky inputs." (Or:
   implement transactional semantics if cheap; doubt it is.)
3. **OOM behaviour.** `Yv12Buffer::alloc` is documented to panic on
   allocation failure (today's `Vec` behaviour). Long-term: switch
   to `Vec::try_reserve` and surface `DecodeError::OutOfMemory`.
   For Stage 3.5, document the current behaviour; defer the
   try_reserve migration.
4. **`Drop` review.** `Decoder` owns `FramePool` which owns `Arc<Yv12Buffer>`s;
   drop order is automatic, but the doc-comment should call out that
   in-flight references from previous `decode_frame` returns must be
   dropped *before* the decoder, otherwise their backing storage
   outlives the decoder via the `Arc`. Add an example.

**Testing oracle:**
- `assert_impl_all!(Decoder: Send)` in `lib.rs` — compile-time
  check.
- `assert_not_impl_all!(Decoder: Sync)` — compile-time check.
- Panic-safety unit test: feed a corrupt packet, verify error;
  feed a valid keyframe, verify success.
- OOM test: skipped on CI (hard to inject); documented behaviour
  only.

**Effort:** 2-3 days.

**Exit:** `Decoder: Send` asserted; doc-comments updated; panic-
safety test passes; eprintln sweep complete (via G11 lint).
