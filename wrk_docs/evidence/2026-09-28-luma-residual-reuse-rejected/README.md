# Selected-luma residual reuse: exact, slower on production PGO

The unintegrated [prototype patch](0001-perf-enc-prototype-reuse-of-selected-luma-residual.patch.gz), commit `f9295dc1`, forwards the TX selector's full-leaf luma residual to final emission as a strided view. It avoids a second source-minus-prediction subtraction only when the TX selector ran; other leaves and E9 prediction diagnostics retain the old path. This is distinct from the earlier rejected coefficient-forwarding caches. The source change is **not** on `origin/main`.

The focused old-path differential compares TX4/TX8/TX16 transform and quant outputs for nonuniform, zero and nonzero bottom-right tiles under both fast and regular quantization. It was deliberately made red with an inverted assertion, restored, and passed on AArch64 and native Crucible x86. AArch64 `cargo fmt --all --check`, `cargo check --locked -p rvp9-encoder`, the focused `inter_emit_` tests, and a five-frame 4:2:0 CPU6/CBR encode matched the integrated local IVF byte-for-byte. The five-frame IVF SHA-256 was `798956a3c6a8cebf0c36fcc6363c4aa281a0dd42262811eb3b189ae51c9475df` for both arms.

Crucible built the candidate with the unchanged 28-row, 60-frame [production-PGO recipe](../../../scripts/build-encoder-pgo.sh). The [manifest](candidate-pgo-manifest.txt) records source commit `f9295dc1`, Rust/Cargo 1.95.0, x86_64 MSVC, FFmpeg 8.1.1, the training matrix, and 31 raw profiles. The merged profile SHA-256 was `8b1a55c7c2fcf9fb384c3aa03ffc53c39cc0d2ca8827af8152f1c2b96daefd14`. The candidate EXE SHA-256 was `14adee4b220345a5222f89d8cffd5270e56c5fee2c359830fc35be6b50c07aa8`; the [integrated control](../2026-09-27-fresh-integrated-pgo-direct/README.md) was the same pinned production-PGO EXE SHA-256 `3c294166213bce7dc707734bf6fbe86e2387b23ef533c16ed16acf4780aaf3ad` used for the latest direct libvpx screen.

The [paired runner](screen-luma-residual.ps1) checked both EXE hashes, all three canonical input hashes, warmed both arms, alternated arm and clip order, measured process CPU, and required the canonical per-clip IVF hash on every encode. Crucible granted a quiet lease and reported zero heavy build processes before the run. The 96 encodes, including six warmups, all exited zero and matched their expected IVF SHA-256. An independent parse of the [raw rows](screen-raw.csv) recomputed all 15 ratios per clip with zero failed or mismatched rows; [identity](screen-identity.csv) and [runner summary](screen-summary.csv) are retained.

The candidate is slower on every clip, especially Ducks. The retained screen is enough to reject this implementation without a second campaign or a candidate/libvpx comparison. It does **not** change the latest integrated direct ratio of **1.057638×** pinned libvpx equal-clip CPU against the ≤1.05× target. The exact mechanism of the regression is unproven; likely suspects are strided residual reads, the added branch/scan, or changed PGO code layout, not a measured attribution.
