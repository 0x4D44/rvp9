# Four-way diamond reference-bounds batch: exact, slower in production PGO

The integrated Ducks PGO profile has 305 direct samples attributed to `full_pixel.rs:387`, where `sad4d_at_from_source` resolves four reference blocks. Hash-matched x86 disassembly at RVAs `0x161ba1..0x161d74` showed four repeated row/column checks, multiplications, and slice-end checks before the SAD4D call. These samples justified an exact-output experiment, not a promised saving.

Private code commit `25dcc45e` introduced one checked union footprint for all four references. If that entire footprint fits the declared plane and backing slice, it derives each reference slice directly; otherwise it retains the former per-lane `block_at` fallback. No search order, cost, tie, or clipped-lane policy changed. A scalar differential covered interior references, right/bottom edges, mixed clipped lanes, shortened backing data, and invalid source. Deliberately flipping one fast-path lane's SAD made the interior test fail; restoring it passed. All 21 focused `full_pixel` tests passed on AArch64 and Crucible x86-64. AArch64 `cargo check --locked -p rvp9-encoder`, `cargo fmt --all --check`, and `git diff --check` passed. The exact rejected code is retained in the [private-commit patch](candidate.patch.gz).

Crucible built the candidate from integrated source `b5968270` plus the one changed file (local/remote SHA-256 `51fa9f003635ca0eaf2983183f12a4ffca918858edd1869bfbbac3fbca79ffdc`) with the unchanged 28-row, 60-frame production-PGO recipe. Candidate executable SHA-256 was `2d3f84d87f4b58e3c820f9d59b9b83cb5ddca46dba4da05c8ad502152954e6dc`; integrated-control PGO SHA-256 was `3caee3f4416087ffe13069b4280f48fe92435bc32c9c0a41bebb7c187a73b3ee`. The [training manifest](training-manifest.txt) preserves compiler and row identity. The paired [runner](screen-bounds.ps1) checked all input and output hashes, warmed both arms, alternated arm/clip order, and kept every pair. Its [five-pair](screen01/summary.csv) and independent [15-pair](screen02/summary.csv) screens retain identities and every raw CPU/wall/output row. Crucible had four other heavy build processes at the start of the first screen; the longer screen was allowed under the relaxed load policy, and process CPU—not wall time—is the comparison metric.
