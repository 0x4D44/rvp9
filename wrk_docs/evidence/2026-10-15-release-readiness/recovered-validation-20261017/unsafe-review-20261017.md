## Additional finding: unchecked NEON span arithmetic

`crates/rvp9-core/src/dsp/aarch64/convolve8_neon.rs:625–626` (`validate_horiz`), `:633–634` (`validate_vert`) and `:831–832` (`convolve8_neon`) use ordinary `usize` multiplication/addition to establish slice spans before unsafe entry. They do not reject overflow. The horizontal/vertical wrappers accept arbitrary `usize` strides and heights. The private module is reachable through public safe function pointers: `SimdDispatch::convolve8_horiz` at `dsp/dispatch.rs:3169`, type `Convolve8OneAxisFn` at `:602`, and native NEON selection at `:2046`.

Concrete source-only counterexample on 64-bit AArch64 **with overflow checks disabled**: source length16, destination length24, `w=8`, `h=3`, `src_stride=1usize<<63`, `dst_stride=8`, and any ordinary supported filter. The horizontal source expression `(h-1)*src_stride+w+7` wraps to15, so both span assertions pass. The first row has16 readable bytes; the second row attempts `src.add(1<<63)` in `convolve8_horiz_inner` at `:586` (or corresponding I8MM/dotprod row-pointer code), which cannot satisfy the allocation/isize pointer-offset preconditions. The baseline NEON branch suffices; this concern does not require I8MM. Enabled overflow checks instead panic during validation.

Release-profile analysis: `Cargo.toml:73–78` sets optimization3, fat LTO, one codegen unit and `panic="abort"`, with no `overflow-checks=true`; the normal Cargo release default disables integer overflow checks. `.cargo/config.toml` adds only `target-cpu=native`. Canonical `scripts/build-encoder-pgo.sh:225–230/:293–298` adds native-CPU/profile-generate or profile-use flags and calls `cargo build --release`, without enabling overflow checks. Therefore this concern survives the repository's default release/PGO profile: the assertions remain, but their arithmetic can wrap. Panic-abort does not make wrapping arithmetic checked. An external profile/flag override enabling overflow checks changes this example to a validation panic. No compiled artifact was executed or disassembled for this claim.

This is a distinct oversized-geometry failure mechanism from FLU-00039's ordinary width4 11-versus12-byte load mismatch. The earlier report named legacy geometry/transitive kernels as unreviewed and did not analyze this validator overflow. No current ledger match was found in a targeted convolution/overflow search. This finding needs independent lead confirmation/ledger disposition and bounded regression/sanitizer work; no runtime reproduction, decoded-bitstream trigger, production-geometry reachability or exploitability is claimed here.
