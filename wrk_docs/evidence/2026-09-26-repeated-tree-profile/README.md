# Repeated exact-image Tree CPU profile

Nine fresh-process Crucible WPR captures used the same 60-frame Tree Y4M and
the unchanged post-zero-EOB encoder. This is an instruction-location map,
**not** a speed comparison: WPR sampling was enabled and libvpx was not paired.
The current uninstrumented RVP9/libvpx result remains 1.134647× equal-clip
process CPU.

The encoder source commit was `48cab42d2dba1a46c502a5da2faf907d79d78ac1`.
The release EXE SHA-256 was
`c4b24b2c5b16add984a2dd6d32e5a7080037290e58b254aff838a0dcf26d63c1`;
the matching PDB SHA-256 was
`085c7c7cc7f724ed7674797dc88bf27011e6662d27d7661e9758677004bd8f9c`.
Every captured IVF matched the canonical Tree SHA-256
`5e3ce26ae1c1394d1e096502add7d87cc38559e7f86265004900580582641b41`.
Every xperf trace-stat report recorded zero lost buffers and events. The
machine's `xperf -ProfInt` after capture read 1221 units (0.1221 ms), consistent
with the higher sample density than the previous ~1 ms captures. The interval
was not recorded inside each ETL, so this is an inference, not a per-run proof.

The five aggregate CSV/JSON files here were generated by the hash-pinned
`aggregate-samples.py` from `../2026-09-26-repeated-ducks-profile/`; its checks require nine consecutive
run IDs, the exact PE/PDB pair, and zero trace loss. The first planned run,
`run-01`, never started WPR because a wrapper scope error left its log path
empty. It is excluded. Runs `run-02` through `run-10` each completed and
yielded **94,152 direct encoder samples** in total. Raw ETLs, individual
extractions, and all run logs remain in the Crucible profile worktree at
`D:\worktrees\rvp9-2\20260926-TSK-HUM-crucible-profile-after-zero-eob\.scratch\repeated-tree-ip\`.
The per-run verification records and aggregate identity data identify them.
The three Tree wrapper scripts here adapt the earlier Ducks capture/extract/
aggregate scripts with exact hash checks; they are checked-in copies of what
ran from that profile worktree's `.scratch` directory.

The generic AVX2 sub-pixel variance body retained 14,552/94,152 direct
samples (15.46%). Disassembling the hash-matched EXE and grouping stable RVAs
gave 3,229 samples (3.43% of process samples) in its full horizontal pass,
2,894 (3.07%) in its full vertical pass, 3,886 (4.13%) in variance reduction,
2,358 (2.50%) in vertical-only interpolation, 2,076 (2.20%) in horizontal-only
interpolation, and 109 (0.12%) in setup. The highest individual sub-pixel RVA,
`0x6ac84` (546 samples), is a loop-back jump after a 16-byte store, not a
standalone removable store. `0x6b5d8` (443) is a dot-product reduction.
These are operation locations, not estimates that removing a line saves its
entire sample share.

The earlier exact work census found an immediately reusable horizontal key
in only 13.25% of Tree two-axis calls. Even a free one-entry cache could thus
recover at most about **0.45%** of this profile's whole-process samples
(3.43% × 13.25%); copying and lookup lower the real ceiling. A larger cache
has a roughly 1.17% theoretical first-pass ceiling from the 34.16% all-prior
repeat rate, but also more memory and search cost. No cache is justified from
these data alone; the prior 16×16 fused kernel already screened neutral.

Other leading Tree RVAs also do not isolate a cheap omission: `0x8a7c0`
(1,004 samples) is the quantizer's EVEX coefficient multiply/add work;
`0x4cc9c` (716) is an 8-tap horizontal convolution shuffle in an already
optimized tail; `0xa4352` (691) belongs to the identity-scale path whose
fixed-core retest reversed its apparent gain; and `0x8789c` (580) is a register
move after the necessary full-metrics call, not a 580-sample register-move
cost. This pass selects **no production edit**. The next bounded discriminator
is shape-specific attribution or microbenching for 32×32/64×64 sub-pixel
interpolation, then an exact differential and paired CPU screen for a concrete
change. The prior work census says 32×32 accounts for 61.70% of Tree
interpolation pixels; that is a pixel-volume proxy, not direct stack evidence.
