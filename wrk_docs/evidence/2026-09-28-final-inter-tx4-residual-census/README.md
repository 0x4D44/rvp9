# Final inter-emission TX4 residual census

**Decision: do not prototype a final-emission TX4 SSE2 subtraction yet.** On canonical CPU6/CBR1260 Ducks, only 114,836 of 1,441,589 inter TX blocks reached the per-TX residual path with TX4 (7.97%); 94,644 of those were chroma. Tree and Town were 4.08% and 4.73%. The earlier 2.26 million *selector-trial* TX4 tiles are not final-emission opportunities. This count does not measure cycles or exclude a small gain, but the narrow target is weak for the remaining parity gap. If Ducks alone closed the current 1.057638× equal-clip result to 1.05×, it would need about 2.15% less Ducks CPU, or roughly 347 ns saved per observed TX4 residual block at the recent 1.85 s control CPU. That is a required saving, **not** a measured kernel cost or a mathematical no-go. Choose a broader profiled path before spending a production-PGO screen on this scalar loop.

The diagnostic-only local commit `83c6ce72` on `task/20260928-TSK-HUM-count-final-inter-emission-tx4-blocks` is **not integrated**. It extends the existing opt-in `runtime-profiling` / `RVP9_EMIT_PROFILE` frame report with per-plane TX4/8/16/32/64 bins. Counters increment only after the final per-TX residual closure returns, including its zero-residual fast path; the luma skip-transform bulk-marker path and the early chroma proof bypass do not reach that closure and are intentionally absent. This is exactly the path an x86 TX4 subtraction specialization would affect. Existing total and plane counters were moved to the same boundary, and every reported frame reconciled with the new bins. The focused merge/reconciliation test was made red once before restoration, then passed on AArch64 and native x86 with the profiling feature. AArch64 format and diff checks passed; the native release CLI built. The x86 test emitted only existing unrelated dead-code warnings in `frame_loop.rs` and `pre_analysis.rs`.
