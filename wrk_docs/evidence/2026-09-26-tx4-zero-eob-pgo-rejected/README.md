# TX4 zero-EOB AVX2 shortcut: exact, but no repeatable CPU gain

Astra's read-only second opinion identified an untested narrow path: production `vp9_quantize_fp_avx2_with_order` tracked zero EOB for TX8/TX16 but not TX4. The exact current PGO executable (`0fa1028b1310fee93b22731794dcb3fdc14e9b5e05dbe428f3e112c4b30cb395`) really has sixteen unrolled, indexed reverse-scan checks on its TX4 path at RVAs `0x178357`–`0x1784f0`; this is a machine-code observation, not a cost estimate. The existing TX4 selector census found zero EOB in 62,082/67,081 Ducks tiles, 7,362/8,516 Tree, and 7,582/8,508 Town. Those counts justified a scratch test, not a predicted speedup.

The unintegrated prototype is commit `d87860a0` on local branch `task/20260926-TSK-HUM-prototype-tx4-exact-zero-eob-shortcut`. It enables the existing exact quantized-lane OR and zero-DC return for the production TX4 wrapper, without changing qcoeff/dqcoeff stores or the direct/no-iscan wrapper. A new TX4 differential checks every raster position under three standard scans against scalar qcoeff, dqcoeff, and EOB. Deliberately omitting the second vector from the OR made it fail at DctDct raster 8 (EOB 0 versus 5); restored code passed all eight AVX2 quantizer tests on Crucible. AArch64 passed 24 forward-quant tests and `cargo check --locked -p rvp9-encoder`; formatting and diff checks passed. This is exactness evidence, not performance evidence.

Crucible built the candidate from the same `443be778` source base plus that one changed file, using the unchanged 28-row, 60-frame production PGO recipe: 31 raw profiles, no observed profile-use warning. [Build manifest](build-manifest.txt) records the compiler, host, profile and output identity. Candidate EXE SHA-256 was `b4d4de6a165afb39f67c5583035e96e480433b9d7d87456a414202c20a46f197`; the control was the current PGO EXE above. Candidate source SHA-256 was `ddfb2e900ec149b190060764a6d64d18f0abd5aab4213a7d5ff99e5204934419`. The [build wrapper](build-pgo-tx4-crucible.sh) and [paired runner](screen-tx4.ps1) are the exact scratch scripts used, and their bytes were checked after copying to Crucible.

Three independent screens used the pinned 60-frame 1080p Ducks, In-to-Tree and Old-Town Y4Ms at CPU6/CBR1260, one thread/no tiles, AQ0/noise0/lag0/KF60. Each warmed both arms, alternated arm and clip order, and kept every pair. All **228 encodes** exited zero and reproduced the established RVP9 IVF SHA-256 values. `screen*/identity.csv`, `raw.csv`, and `summary.csv` preserve identities, per-encode process CPU/wall time, hashes, and pairs. Independent CSV parsing checked row counts, output equality, and geometric means. Lower candidate/current CPU is better.

Ducks was slower in all three screens, and the overall result changed sign. Even counting small gains, this is not a repeatable improvement; **do not integrate the code prototype**. Some wall times stalled by several seconds and host process-CPU times shifted across screens, so the paired process-CPU ratios—not wall time or cross-run absolute seconds—are the signal. No pair was removed for background load. A candidate/libvpx screen would not help select a candidate that already failed the paired RVP9 control gate. The current direct production PGO/libvpx result remains **1.096110×** equal-clip CPU, above the ≤1.05× target.
