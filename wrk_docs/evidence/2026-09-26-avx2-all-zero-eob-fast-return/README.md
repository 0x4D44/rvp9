# AVX2 all-zero EOB fast return: exact output and paired CPU gain

Code commit `5dce3277` changes only `crates/rvp9-core/src/dsp/x86_64/quantize_fp_avx2.rs`. The production TX8/TX16 quantizer ORs its exact stored eight-lane AC qcoeff values while quantizing. If that aggregate and the separately quantized DC are zero, it returns EOB 0 before the reverse tail probe and inverse-scan reducer. A provisional AC result in raster lane 0 can only miss this shortcut, because scalar DC overwrites that lane; it cannot create a false EOB 0. TX4, direct/no-iscan calls, skip-block, and all nonzero blocks retain their prior paths. The source SHA-256 on AArch64 and Crucible was `657df5f9dad106e72a7e23fd68179276f3dd3a5f1edd136270bf1166ce5d4926`.

The integrated x86 profile assigned 97/2,451 Ducks, 33/1,189 Tree, and 41/1,017 Town direct samples to the EOB fallback source line. A prior output-neutral census found zero EOB in 79.1%, 85.2%, and 86.9% of fallback calls. Exact baseline disassembly placed 91 Ducks samples at RVA `0x8c1d2`, the loop-control instruction after a qcoeff load. These observations selected the shortcut, not its predicted gain. The old full-EOB 16-lane prototype was slower; this change isolates only the zero case.

Three Crucible candidate/control screens used pinned 60-frame 1080p Ducks, In-to-Tree, and Old-Town inputs at CPU6/CBR1260, one thread, no tiles, AQ0, noise0, lag0, and KF60. Each screen ran a warmup on both arms and 15 alternating-order pairs per clip. Screen 02 pinned both arms to logical CPU 0; the others did not pin. All **288** encodes exited zero and matched the accepted IVF SHA-256 for their clip. The current integrated-code control EXE SHA-256 was `004844ee055dde9dbfd17c849f83da74c4dbd8aaf3762b40939b0b4a970018ca`; the candidate EXE was `4722560ef8a5071c2b8acd0304d6c658071bf6dad77651f6f0613b525c441d3e`. There were no shipped-file changes from the control's integrated source base to the candidate branch base other than this quantizer file. `screen*/identity.csv`, `raw.csv`, and `summary.csv` retain hashes, per-encode CPU/wall time, and paired ratios.

The combined nine clip-screen geometric mean is **0.978050×**, a 2.2% CPU saving. Every clip favoured the candidate in every screen, but individual pairs were noisy, especially screen 02's Tree and Ducks outliers. The paired medians were also below one on all nine clip-screens. Crucible lacked `deltic quiet`; no strict load cutoff was applied. Wall stalls reached several seconds in otherwise normal CPU-time encodes, so wall time is not the retention measure. No pairs were discarded or selected by load.
