# Rolling-row AVX2 sub-pixel prototype: no-go

The bounded 16×16 two-axis rolling-row prototype is exact but slower in the affected kernel, and it did not improve whole-encoder CPU. Do not integrate code commit `7fda80be`. The integrated RVP9/libvpx equal-clip process-CPU ratio remains **1.057638×**.

The prototype in `crates/rvp9-core/src/dsp/x86_64/subpel_variance_avx2.rs` replaced the full widened horizontal intermediate with two rolling `[i16; 16]` rows for nonzero x/y phases at 16×16 only. It still wrote the existing byte temp before variance. Its differential test covers all 49 nonzero phase pairs, exact and padded strides, temp bytes, variance and SSE, and short-slice panic behavior. Deliberately swapping the top and bottom rows made the new test fail at phase `(1,1)`; restoring the implementation passed it and the full native AVX2 sub-pixel module (6/6 tests). `cargo fmt --all --check` and `git diff --check` passed. AArch64 validation was not run: the local quiet window would not open before this prototype was already rejected.

The exact-source frozen-profile PGO candidate EXE SHA-256 was `0323304e5104d3c1f8d1eae1f4d3b318b25b144b94eea4c8c5286da535c79f1d`; the integrated control EXE was `3c294166213bce7dc707734bf6fbe86e2387b23ef533c16ed16acf4780aaf3ad`. The profile was `3f02af95fbeca067d6d94b233a353681bce4ed25c76930a94f0564895ac10335`. Five measured pairs per clip, plus warmups, gave candidate/control process-CPU ratios of **1.015693 Ducks**, **0.983767 Tree**, and **1.003416 Town**: equal-clip geometric mean **1.000872** (+0.087%, effectively flat). All 36 encodes produced the canonical IVF hashes. The changed function had a PGO control-flow hash mismatch, so the compiler discarded up to 6,149,929 profile counts; this frozen-profile screen alone is not a final production-PGO forecast.

An independent native non-PGO `dsp-microbench` A/B/B/A check makes the kernel result clearer. Control and candidate binaries were `531b5e17022ff1156e708064b5b54a3158a013a7bd152d96676d988d7aa10dd9` and `657f3eaa4230c2998d76d3757ae90e361523471ce7d95e64ed6bd6e5b1ed37c7`. The affected 16×16 two-axis dispatch at phase `(4,4)` took **24.5/23.7 ns control** versus **27.5/27.4 ns candidate**; phase `(3,5)` took **24.6/23.8 ns control** versus **27.6/27.4 ns candidate**. Identity phase `(0,0)` stayed at 16.1–16.2 ns. The rolling implementation is roughly 12–16% slower where it applies. A fresh-PGO build would not justify retaining this exact kernel.
