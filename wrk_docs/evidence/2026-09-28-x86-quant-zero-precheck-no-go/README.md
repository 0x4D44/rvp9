# x86 final-quant zero precheck: production-PGO no-go

**Decision:** do not integrate the x86 TX8/TX16 fast-quant zero precheck. It preserved exact output and looked 1.33% faster in a plain release screen, but two independently run, unchanged-recipe production-PGO screens showed no repeatable CPU gain. The pooled 30-pair-per-clip candidate/control ratio was **1.006722×** (0.67% slower). The [direct integrated parity result](../2026-09-27-integrated-pgo-direct-repeat/README.md) therefore remains **1.057638× pinned libvpx** equal-clip process CPU, above the 1.05× bar.

The [final-emission census](../2026-09-28-final-inter-quant-zero-census/README.md) showed that 87–90% of final residual transforms quantize to EOB zero. Astra suggested a bounded precheck: for x86 fast-quant TX8/TX16 with trellis off, test whether AVX2 quantization would produce any nonzero coefficient *before* writing qcoeff/dqcoeff. The existing x86 zero-EOB shortcut runs after those stores. The prototype mirrors the signed quantizer arithmetic, handles DC separately, ignores provisional AC lane zero, and falls back to the full quantizer when the predicate fails. TX4, TX32, regular quantization, trellis, and the full quantizer API remain unchanged. Its code is committed only on the local unintegrated task branch (`a9a36e0d`, followed by test commit `61d575e0`); the native x86 copy was used solely for validation and measurement.

Ratios below 1 mean the candidate used less process CPU. Each run alternated arm and clip order after one warmup per arm and clip; warmups are excluded from ratios. The first PGO screen had a transient CPU surge in both arms, so all pairs were retained and a second independent screen was run. The second screen was steadier and was slower on all three clips. The pooled result uses the geometric mean of all 90 paired ratios, with 30 pairs for each clip. The plain-release result was a positive *whole-encoder* screen, stronger than the synthetic microbenchmark proposed in the census note, and justified the PGO trial; it is not a substitute for production-PGO evidence.

The committed [plain screen](plain-screen-01/), [PGO screen 1](pgo-screen-01/), and [PGO screen 2](pgo-screen-02/) directories each hold `identity.csv`, `raw.csv`, and `summary.csv`. [Plain](plain-screen.ps1) and [PGO](pgo-screen.ps1) runners contain the exact CPU6/CBR1260, one-thread, 60-frame command and hash checks. The candidate used the same [28-row PGO training manifest](pgo-manifest.txt) as the integrated control. Control PGO EXE SHA-256 was `3c294166213bce7dc707734bf6fbe86e2387b23ef533c16ed16acf4780aaf3ad`; candidate PGO EXE SHA-256 was `11949108d863eda5b5c7ada658870d82edf83d144d59bef688217d1290b1e338`. The plain control and candidate EXE hashes are in that screen's `identity.csv`.

Independent parsing checked every raw encode's exit code and output hash: **66/66 plain** and **96/96 in each PGO screen** matched the integrated reference IVF exactly. A native x86 differential test for boundary quantizers and reused scratch was deliberately made red by omitting the final eight-coefficient vector, then restored green; focused encoder tests, AArch64 cross-compile/check, formatting, and changed-code lint checks also passed. The test-only extension covering nonzero DC/AC deltas was cross-compiled after the native run, but not rerun natively; that is a validation limit, not a reason to retain the slower candidate.

The lesson is narrow: many zero-EOB blocks are reachable, but this precheck's branch/vector work outweighed any saved stores under production PGO. It does not establish that quantization as a whole is exhausted. Future candidates need a production-PGO paired gain that survives an independent repeat, especially on Ducks, before integration.
