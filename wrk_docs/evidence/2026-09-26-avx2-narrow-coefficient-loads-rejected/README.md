# AVX2 narrow coefficient loads: exact, slower in production PGO

The integrated production-PGO image's hot `0x1400aa5d1` coefficient load sits in a 16-coefficient quantizer path; nearby transform output also has 16-byte stores. A read-only Fable consultation proposed a store-to-load-forwarding penalty between forward-transform stores and AVX2 quantizer loads. Disassembly showed that the simple 8×8 explanation did not itself identify the hot 16-coefficient path. A synthetic Crucible [dependency-chain microbenchmark](forwarding-microbench.rs) with fixed instruction widths measured about 17.4 cycles/iteration for two 32-byte stores and loads, 24.1 for four 16-byte stores and two 32-byte loads, and 21.5 for four 16-byte stores and four matching 16-byte loads. The first draft accidentally compiled four 16-byte stores into one 64-byte store; only the explicit-instruction rerun is cited. Synthetic cycles establish a hardware mechanism, not encoder benefit.

Unintegrated local prototype commit `90644924` changed only `crates/rvp9-core/src/dsp/x86_64/quantize_fp_avx2.rs`, using two explicit 16-byte reads per eight i32 coefficients. On Crucible x86-64, the scalar-equivalence differential passed for TX4/TX8/TX16; deliberately shifting the second load by four bytes made it fail on TX4 qcoeff; restoring it passed all seven AVX2 quantizer tests. AArch64 `cargo test --locked -p rvp9-core quant::forward::tests::vp9_quantize_fp_round_trip_at_q_index_60`, `cargo fmt --all --check`, and `git diff --check` passed. The subsequent AArch64 encoder check was deferred by another agent's quiet-window guard, and is not claimed.

Crucible trained the unchanged 28-row, 60-frame production PGO recipe from integrated source `6b47631c` plus the one prototype file (local and remote source SHA-256 `64b43236f74248a6af61d5c84d6b8fe1ec496393392b6ebb52cfc5acf36802bb`). Candidate executable SHA-256: `6cafe84e3e0bca4eeee46094864b1d9fbe63b165c1a143f61d9318901a25ba4f`; integrated-control PGO executable SHA-256: `3caee3f4416087ffe13069b4280f48fe92435bc32c9c0a41bebb7c187a73b3ee`. The training [manifest](training-manifest.txt) preserves the compiler, training rows and binary path. The paired [runner](screen-narrow.ps1), [identities](screen01/identity.csv), [raw rows](screen01/raw.csv), and [summary](screen01/summary.csv) preserve inputs, executable hashes, process CPU, wall time, exact output hashes and pair ratios. Crucible reported two other heavy builds before the screen; under the relaxed load policy, process CPU was the comparison metric. The screen warmed both arms, alternated arm/clip order, and retained all five pairs per clip. All 36 encodes exited zero and matched established IVF hashes.

The PGO encoder loses 3.4% overall and 7.6% on the limiting Ducks clip, despite the synthetic forwarding result. Reject the prototype; do not integrate or compare it with libvpx. The last direct integrated-code libvpx result remains 1.099305× equal-clip CPU. The likely explanation is instruction/assembly cost or codegen interaction, but that has not been isolated, so it is not a reason to rewrite the transform producer without new evidence.
