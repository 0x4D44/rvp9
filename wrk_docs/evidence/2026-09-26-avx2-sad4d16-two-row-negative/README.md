# Two-row AVX2 SAD4D16 prototype: exact, not retained

The candidate packed consecutive 16-byte rows into the low and high lanes of a YMM vector for the 16×16 four-reference SAD kernel. The source profile assigned 120/2,451 Ducks direct samples to this kernel (4.9% self share), so a meaningful whole-encode gain needed a large kernel saving. Earlier even/odd row accumulators and equal-stride addressing experiments were different changes and had already failed their CPU screens. The candidate was based on integrated code at `ae569e16` (the current `284b3e6c` trunk adds only evidence). Its one-file source SHA-256 was `2f8751bfc9a05ea13c2f0dc0cf55280770785c4ff256a9502226b0b17808fbe`. The exact rejected source and test change is archived in `prototype.diff.gz` (SHA-256 `9059fa62644e7a59a024202428f25fdc804bbcdd9ca2c1b6ae9398a07e55678f`); its decompressed patch passes `git apply --check` against the clean base tree.

The new deterministic 16×16 test pins four distinct outputs with non-tight, differing source/reference strides. Crucible's AVX2 focused suite passed 5/5. Duplicating the first row into the high lane made that new test fail (`[7936, 12288, 16640, 20992]` versus `[8192, 12544, 16896, 21248]`); restoring the correct second-row load made it pass. AArch64 `cargo check` passed for core, encoder, and CLI; the core library suite passed 1,719 tests, with two ignored. Formatting and diff checks passed. Focused x86 Clippy passed with three pre-existing warnings outside the changed file and no new warnings. The native x86 release candidate EXE SHA-256 was `117dee9bf5215f06d03f66c29950e260c99bd7aa3160fb7b4488579409da0a92`; the clean integrated control EXE SHA-256 was `004844ee055dde9dbfd17c849f83da74c4dbd8aaf3762b40939b0b4a970018ca`.

Two full Crucible screens used 15 alternating-order candidate/control pairs per clip, plus one warmup per arm and clip: 192 encodes total. They used CPU6/CBR1260, one thread, 60 frames, logical CPU 0, pinned Ducks, Tree, and Town clips. Every encode exited zero and matched the established IVF SHA-256 for its clip. `identity.csv`, `raw.csv`, and `summary.csv` in each screen directory preserve exact assets, per-encode CPU/wall time and output hashes, and paired CPU ratios. Lower is better.

The combined six clip-screen geometric mean is **1.005302×**, slightly slower. The first screen contained several high-CPU pairs on both arms; the second settled near neutral. Neither establishes a reproducible CPU gain. This production-code prototype stays out of `origin/main`. The last accepted pinned-libvpx comparison remains [1.168613× process CPU](../2026-09-26-guarded-hadamard-pairwise/README.md); these within-RVP9 screens do not change that number. The next candidate should address another measured hot path rather than assume further 16×16 SAD arithmetic rearrangement will repay its packing cost.
