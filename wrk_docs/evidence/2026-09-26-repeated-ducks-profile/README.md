# Repeated exact-image Ducks CPU profile

Ten fresh-process Windows CPU-sampling captures encode the same 60-frame Ducks input with the unchanged post-zero-EOB RVP9 executable. This is hotspot-selection evidence, **not** a new RVP9/libvpx speed measurement: tracing perturbs CPU time, and there is no paired libvpx run here.

The source tree is `48cab42d2dba1a46c502a5da2faf907d79d78ac1`; the release executable SHA-256 is `c4b24b2c5b16add984a2dd6d32e5a7080037290e58b254aff838a0dcf26d63c1`, and its PDB SHA-256 is `085c7c7cc7f724ed7674797dc88bf27011e6662d27d7661e9758677004bd8f9c`. The extractor also verifies the PE/PDB GUID, age, and image size. The Ducks Y4M SHA-256 is `6d2d866613f7a8c7b11bd2c27374f7637cd4a0748ff6fea4a671b23cfbcde6d7`; every encoded IVF has SHA-256 `8d0458b89ca00cbfb96961e1c16e6018bf88b18790ea7e9d6eeb8c80bd659089`.

`capture-repeats.ps1` pins those identities, adapts the earlier reviewed WPR capture without overwriting it, checks that WPR is idle, and makes unique numbered runs. `extract-repeats.ps1` verifies each run and invokes the exact-PE/PDB extractor. `aggregate-samples.py` refuses inconsistent run identities, sample counts, or nonzero trace loss; `test_aggregate_samples.py` covers those checks and observed a deliberate red before restoration. Ten runs yielded **23,207 direct encoder samples**, 7,386 unique exact RVAs, and zero lost buffers/events in every trace. Per-run direct counts are in `aggregate/runs.csv`; run-specific full IPs and ASLR-stable RVAs are retained separately. Source-line groups are broad context, not disassembled operation counts.

The checked-in `runs/run-NN/` records contain each capture's log, output/ETL hashes, zero-loss report, extractor summary, and xperf trace statistics. The raw ETLs and per-run direct-sample CSVs remain at `D:\worktrees\rvp9-2\20260926-TSK-HUM-crucible-profile-after-zero-eob\.scratch\repeated-ducks-ip\run-NN\` on Crucible. They are deliberately not committed: the ETLs exceed 1 GB together. Their individual hashes are in `verification.txt`. `aggregate/` contains the combined exact-IP tables and identity-checked summary.

The capture has no reliable caller-stack attribution yet: xperf's sampled-stack report labels encoder frames `rvp9enc.exe!***unknown***`. Treat the direct-IP evidence as instruction-location samples only. A follow-up must inspect disassembly and a work census before estimating removable CPU or choosing a kernel.

## Selection result

The five largest exact RVAs recur in all ten runs. Their counts are `0x7d0ca` 408 (picker state load), `0x8aaf1` 269 (quantizer DC multiply), `0xa4352` 230 (prediction slice/scale setup load), `0x137c56` 164 (instruction after an atomic increment in the encoder partition closure), and `0x80f04` 135 (post-diamond-search return/unpack). Counts are out of 23,207 direct samples. The first, second, third, and fifth map to previously screened denoiser-minima, DC-lane, identity-scale, and search-reuse paths. The denoiser result was not repeatable; the identity-scale entry point saved about 0.41% across three clips but was previously rejected as too small on its own. The counter's specific static and whether it is avoidable remain unresolved; removing it would not be justified from broad source-line attribution. None is a credible new bounded optimization on these samples alone.

The next higher-value experiment is a diagnostic, exact-output work census on both RVP9 and pinned libvpx by caller, block shape, and horizontal/vertical sub-pixel phase. That can separate extra RVP9 evaluations from slower same-shape kernels and surrounding search work. Do not use diagnostic-build CPU timings as performance evidence.
