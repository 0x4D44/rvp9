## Confirmed findings — bug drafts (to mint via `deltic bugs new`)

### DRAFT-BUG-1 — bdrate `--limit` shorter than the clip breaks every PSNR measurement
- **Severity:** Medium · **Priority:** Should · **Area:** bench/bdrate · **Confidence:** confirmed (lead read)
- **Where:** `crates/rvp9-bench/src/bin/bdrate.rs:188-190` (forwards `--limit` to both encoders), `:229-247` (`decode_and_psnr` compares against the full-length reference), `:451-452` (call sites pass un-truncated `args.reference_input`); `crates/rvp9-bench/src/lib.rs:219-245` (`mean_y_psnr` returns `None` on frame-count desync).
- **Defect:** with `--limit N` where N < clip frames, the encoded/decoded output has N frames but the PSNR reference keeps its full length; `mean_y_psnr` desyncs at frame N+1 and returns `None` → NaN → `measured_bd_rate` fails with "PSNR measurement failed" for every RD point. The tool cannot produce a BD-rate for the standard fast-sweep invocation its own header documents.
- **Fix:** truncate the reference to `--limit` frames before comparison — the pattern already exists in `bdrate-svc.rs` (`write_reference_operating_points` builds an `expected_frames`-bounded reference Y4M). Also compare `a_frames == t_frames` explicitly (as `bdrate-svc.rs:1218-1220` does) so mismatches are diagnosable. **Effort:** small (~1–2 h + a regression test).

### DRAFT-BUG-2 — bdrate `polyfit3` degenerate fit silently fabricates a finite BD-rate
- **Severity:** Medium · **Priority:** Should · **Area:** bench/bdrate · **Confidence:** confirmed (lead read)
- **Where:** `crates/rvp9-bench/src/bin/bdrate.rs:351-354` (singular pivot returns `[0.0; 4]` with "caller should ignore"), `:271-272` (`bd_rate` never checks for the sentinel), `:305-315` (`measured_bd_rate`'s `is_finite()` guard does not catch it).
- **Defect:** if either RD curve's normal-equations matrix is numerically singular (e.g. PSNR collapses to near-identical values across bitrates — exactly the rate-control-regression shape BD-rate exists to catch), the zero polynomial integrates to 0 and the reported BD-rate becomes an arbitrary finite wrong number, silently. The sibling implementation `rvp9-harness`'s `polyfit3` returns `Option` and propagates the failure; the two bins diverge on the identical input.
- **Fix:** make `polyfit3` return `Option<[f64; 4]>` and propagate `None` through `bd_rate` (mirroring `rvp9_harness::bdrate`), or delegate to the harness implementation outright. **Effort:** small.

### DRAFT-BUG-3 — ambient `RVP9_*` env vars silently distort bdrate / bdrate-svc / realtime measurements
- **Severity:** Medium · **Priority:** Should · **Area:** bench/env-hygiene · **Confidence:** confirmed (lead grep + read)
- **Where:** `crates/rvp9-bench/src/bin/encode-headtohead.rs:798-820` (`remove_rvp9_environment`, applied before every child spawn — only in this one binary); no equivalent in `bdrate.rs`, `bdrate-svc.rs`, or `realtime.rs` (verified by grep: no `env_remove`/`RVP9_` handling); in-process bins (`decode-throughput`, `decode-headtohead`, `soak`) inherit the shell env directly.
- **Defect:** CLAUDE.md's own debugging guidance encourages setting `RVP9_FORCE_SCALAR`, `RVP9_DISABLE_ROW_MT`, `RVP9_FIXED_Q`, `RVP9_TRELLIS`, etc. A forgotten export changes the timed/measured code path with no trace in any CSV/TSV schema. Worse, for the BD-rate gate the distortion is asymmetric: the libvpx anchor ignores `RVP9_*` while the rvp9 test encoder honours it, directly biasing the release-gate number. `encode-headtohead.rs` proves the crate's authors know this hazard; the defence was not carried to the sibling tools.
- **Fix:** extract `remove_rvp9_environment` into `rvp9-bench`'s lib, apply it to every child spawn in `bdrate.rs` / `bdrate-svc.rs` / `realtime.rs`; for in-process bins, at minimum warn (or record in the CSV row) when any `RVP9_*` var is set. **Effort:** small.

### DRAFT-BUG-4 — checked-in decode-throughput baseline is mislabeled `--pinned` and can never match the ratchet's fixtures
- **Severity:** Medium · **Priority:** Should · **Area:** bench/decode-throughput · **Confidence:** confirmed (lead read of artifact + both code paths)
- **Where:** `bench/results/decode-throughput.csv` (all 8 rows: `host=windows-x86_64`, `unpinned=false`, fixtures `testsrc_720p30.ivf`/`testsrc_1080p30.ivf`); `crates/rvp9-bench/src/bin/decode-throughput.rs:97-99` (`unpinned=false` is written only when the operator passes `--pinned`) and `:31-36` (docs reserve `--pinned` for the disciplined Linux CI runner); `crates/rvp9-bench/src/throughput.rs:91-96` (`DEFAULT_FIXTURES` = `vp90-2-*.webm`); `crates/rvp9-bench/tests/decode_throughput_ratchet.rs:141-151`.
- **Defect:** two independent problems in the artifact of record. (1) Every row claims pinned-quality discipline but was recorded on a Windows dev box via `--pinned`, contradicting the binary's documented contract — and the rows show ~26% p50 spread (1520→1924 µs) on identical fixture/host/build, confirming they carry no baseline discipline. (2) All rows name `testsrc_*.ivf` fixtures (recorded via `--fixture` overrides) while the ratchet measures only `DEFAULT_FIXTURES` (`vp90-2-*.webm`), so even once a pinned host exists these rows can never seed a baseline — the "self-bootstrapping" story in the ratchet's module docs is broken in practice. (The empty `PINNED_HOSTS` itself is documented as deliberate — noted in RVP9-BUG-KILN-00058's closure — and is not re-raised here; see DRAFT-REQ-2 for the design follow-up.)
- **Fix:** relabel or drop the mislabeled rows (they are misleading trend data), and either record `DEFAULT_FIXTURES` rows or add the `testsrc_*` fixtures to the ratchet's fixture set so the artifact and the gate agree. **Effort:** small (data + one constant), plus a decision on which fixture set is the ratchet's.

### DRAFT-BUG-5 — rvp9-bench unit tests race on fixed shared temp paths across concurrent worktrees
- **Severity:** Low · **Priority:** Should · **Area:** bench/tests-flaky · **Confidence:** confirmed (lead read)
- **Where:** `crates/rvp9-bench/src/lib.rs:315-319, 335-339, 358-362` (fixed names `rvp9_test_ref.y4m`, `rvp9_test_ref2.y4m`, `rvp9_test_ref3.y4m`… in `std::env::temp_dir()`); `crates/rvp9-bench/src/throughput.rs:703-705` (`csv_roundtrip_v1` uses fixed dir `rvp9_throughput_csv_test_v1`, starts with `remove_dir_all`, then asserts `rows.len() == 4`), `:785, :801` (fixed CSV names).
- **Defect:** two worktrees running `cargo test` concurrently on the same box (the normal fleet situation) collide: `csv_roundtrip_v1` deterministically fails when interleaved (one process deletes/appends the shared dir mid-run, so the exact-count assertion sees 0–8 rows), and the PSNR tests can read a half-written file. Same class as FLUX-00010 / KILN-00061 / KILN-00064 but an uncovered site — note `throughput.rs`'s own `malformed_ivf_packet_is_reported_with_fixture_and_index` already does this right (`process::id()` in the name).
- **Fix:** suffix every temp path with `std::process::id()` (and clean up), matching the in-file precedent. **Effort:** trivial.

### DRAFT-BUG-6 — soak defaults `--vpxdec` to an out-of-worktree machine-specific binary (KILN-00039 class)
- **Severity:** Low · **Priority:** Could · **Area:** bench/soak · **Confidence:** confirmed (lead read)
- **Where:** `crates/rvp9-bench/src/bin/soak.rs:169-171` (`unwrap_or_else(|| PathBuf::from(r"D:\language\libvpx-stock\vpxdec.exe"))`), `:36` (usage doc shows the same path).
- **Defect:** the exact defect class Closed bug RVP9-BUG-KILN-00039 removed from the harness crate — a hard-coded absolute default outside the current worktree. On a box where that path exists (the main dev box), `--cross-decode` silently validates against a stock binary of unknown version instead of the repo-built `build/libvpx/vpxdec.exe`; on any other box the documented default simply never resolves. Also contradicts 00039's closure sweep, which stated `D:\language` appeared in rvp9-bench only in doc comments.
- **Fix:** default to `build/libvpx/vpxdec.exe` under the workspace root (the repo's documented reference-binary location), or require an explicit `--vpxdec` and keep the existing fail-fast. **Effort:** trivial.

## Confirmed design findings — req drafts (to mint via `deltic reqs new`, Draft for Gate-1 triage)

### DRAFT-REQ-1 — realtime gate must enforce a tail-latency budget when gating real-time compliance
`crates/rvp9-bench/src/bin/realtime.rs:400-420`: the only mandatory pass/fail is *average* ms/frame over the whole run; the p99 check requires both `--frame-time-csv` and `--p99-budget-ms` opt-in flags. A run with 95% of frames at 10 ms and 5% at 200 ms passes a 33 ms budget while being visibly non-real-time in an RTC deployment. The module doc names this binary the Stage-4+ real-time compliance gate, so before it gates a release the tail budget should be mandatory (or the gate invocation standardised to always pass both flags). Note also the avg metric spans process spawn + file I/O (`:354-374`), while the CSV path measures encoder-only time — the gate should state which it means.

### DRAFT-REQ-2 — make the decode-throughput ratchet noise-aware before pinning any host
Three compounding facts: the checked-in baseline shows ~26% run-to-run p50 spread against a 10% budget (`bench/results/decode-throughput.csv` rows 2–9); baseline selection is latest-row-wins (`crates/rvp9-bench/src/throughput.rs:573-595`), so pass/fail would hinge on which run landed last; and `host_fingerprint()` (`throughput.rs:375-377`) is only `<os>-<arch>` while release builds are `target-cpu=native`, so two different CPUs collide on the same fingerprint — the exact cross-host trap the ratchet's own comment warns about (`decode_throughput_ratchet.rs:46-48`) with no field able to enforce it. Before a host is added to `PINNED_HOSTS`, the ratchet needs a statistical compare (the crate already ships `mwu::mann_whitney_u` used by bench-compare) or a median-of-N baseline, and a finer fingerprint (CPU brand string or CPUID hash).

### DRAFT-REQ-3 — soak should detect (not just print) memory growth, and watchdog its in-process legs
`crates/rvp9-bench/src/bin/soak.rs`: RSS is sampled and printed at start and each report (`:565-568`, `:643-676`) but never compared to a baseline or threshold — a 72-hour leak is only discoverable by a human reading stderr or by OOM. And `run_with_timeout` guards only the external `vpxdec` leg (`:484`); the in-process `encode_frame`/`decode_frame` loop has no wall-clock guard, so the rare-hang class the soak exists to surface wedges the harness silently. Add an RSS growth check (fail past a configured slope/ceiling) and a watchdog (iteration deadline on a monitor thread) that turns a hang into a reported failure.

## Report-only notes (confirmed, below ledger bar)

- **`latest_per_fixture` doc contradicts its code** — `crates/rvp9-bench/src/throughput.rs:566-573`: doc says "each (fixture, host) pair is reduced independently" / "does NOT silently merge across hosts", but the map is keyed by fixture only, so with >1 pinned host the latest row from either host wins. Harmless today (callers pass ≤1 host); fix the comment or key by (fixture, host) when DRAFT-REQ-2 lands.
- **`check_metric_ratchet` passes on NaN** — `throughput.rs:608-625`: `NaN > budget` is false, and `"NaN".parse::<f64>()` succeeds in Rust, so a corrupted baseline cell would silently pass the gate. One `is_finite()` guard.
- **Mean-of-per-frame-dB PSNR convention** — `crates/rvp9-bench/src/lib.rs:190-251`: `mean_y_psnr` is the per-frame-average ("Average PSNR" in libvpx terms), not aggregate-MSE "Overall PSNR"; per Jensen it flatters the encoder with higher frame-to-frame variance. Both curves use the same function, so the sweep is self-consistent, but the choice is undocumented and can skew anchor-vs-test comparisons when GOP/RC smoothness differs. Worth one doc paragraph + ideally reporting both.
- **bench-compare's A/B design is block-sequential** — all baseline samples come from one contiguous sweep and all candidate samples from a later one (`scripts/bench-headtohead.ps1` runs N back-to-back per build), so `mann_whitney_u` cannot distinguish a build change from host drift (thermal/background) between sweeps. Methodology caveat to note in bench-compare's output; interleaved A/B would fix it properly.
- **`bdrate` vs `bdrate-svc` measure "bitrate" differently** — file-size-based (`bdrate.rs:250-254`, container included) vs payload-only (`bdrate-svc.rs`); justified for SVC operating points but undocumented, so the two tools' kbps aren't comparable side-by-side.
- **dsp-microbench loopfilter cases time a 1 KB `copy_from_slice` inside the measured window** (`dsp-microbench.rs:998-1004`); documented as cancelling in the ratio, but that assumes the C harness's memcpy costs the same — compresses cheap-kernel speedups toward 1.0×.
- **Praise where due:** `mwu.rs` is correct end-to-end (exact permutation two-sided p via the min(U_a,U_b) fold, tie-corrected normal-approx variance, A&S phi coefficients all verified by the lead; rank sums are exact multiples of 0.5 in f64, so no FP-tie hazard). `encode-headtohead.rs` is the crate's methodological high-water mark (env scrubbing, alternating arm order, determinism hashes, load-gating, full manifest); `Stats::from_sorted` nearest-rank percentiles and `count_ivf_frames` are correct; `bench_compare_cli.rs`/`soak_cli.rs` tests assert distinguishing fixtures, not constants.
